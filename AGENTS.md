# AGENTS.md

Answerable monorepo. Bun 1.3.1, Turborepo. Two apps: `apps/web` (Next.js 16: the site, the docs at `/docs`, the design page at `/design`) and `apps/id` (Answerable ID: Bun, Hono, Better Auth, Postgres, and its browser pages). Shared packages: `packages/ui` (React components and Tailwind theme), `packages/countries` (ISO country data), `packages/design` (the Answerable profile of DESIGN.md: the parser on Google's official linter, the generator of `packages/ui/src/styles/tokens.css`, colour, Google Fonts and the React runtime; `PROFILE.md` is the profile), `packages/config` (`defineConfig`: each service's environment variables, typed, with their development and test defaults), `packages/auth` (Answerable ID access-token verification), `packages/mcp` (the SDK for MCP servers, on the official MCP SDK), `packages/id-admin` (a server's machine client on ID's admin API, and the fake ID), `packages/mcp-postgres` (the intent store, the evidence chain and the drizzle base schema for servers with a Postgres database), `packages/mcp-platform` (what every server Answerable runs shares: evidence and spans for every call and refusal, the audit-log poller, `/health`, each MCP's database), `packages/acceptance` (the real-ID acceptance kit and journeys) and `scripts` (`bun mcp` and `bun run env:inventory`). Runnable MCPs live in `mcps/*`; `mcps/e2e` is the reference MCP, served `both`, and the permanent local acceptance consumer; `mcps/example` is the finished example, whose files the docs include; `mcps/toolbox` is the Toolbox: the hub, and every `standalone` or `both` MCP at its own path, with its own Postgres databases `answerable_toolbox` and `answerable_toolbox_test`; `mcps/admin` is the staff-only admin MCP, with `answerable_admin` and `answerable_admin_test`. The deployment lives in `infra/*` and `charts/*`: `infra/civo` (Terraform for the two Civo environments), `infra/k8s` (the kind stack and the chart tests), `infra/ops` (the `bootstrap`, `register` and `make-admin` Jobs), `infra/pipeline` (the scripts the workflows call), `charts/answerable` (ID, the Toolbox and the admin MCP) and `charts/platform` (Traefik); `infra/README.md` is the runbook and `docs/12-deployment.md` the design. Read `README.md`, then `docs/00-orientation.md`. Decisions live in `docs/`; `docs/02-plan.md` lists what not to re-propose.

## Documentation

Docs are MDX in `apps/web/content/docs`, rendered with Fumadocs at `/docs`. The API reference is generated from `apps/id/openapi.json` and `apps/id/openapi.admin.json`. Never edit those files by hand; run `UPDATE_SNAPSHOT=1 bun test src/openapi.integration.test.ts` in `apps/id`.

**Keep code and types in sync.** Never paste code or a type into a page; the build renders them from the repository:

- Code: `<include lang="ts" meta='title="…"'>../relative/path.ts#region</include>`, from a file the repo typechecks and tests, with `//#region name` … `//#endregion` around the part to show. Snippets that no server runs live in `mcps/example/src/docs/`.
- A type's fields: `<AutoTypeTable path="../../packages/…" name="…" type="…" />` (path relative to `apps/web`), from the type and its doc comments. A field without a comment shows a blank: write the comment in the source.
- What the repository computes: `<ScaffoldFile>` (what `bun mcp new` writes), `<CliReference />`, `<CliSteps />`, `<CliExitCodes />` and `<CliErrors />` (every command, flag, step, exit code and error of `bun mcp`, from `scripts/mcp/definitions.ts` and `errors.ts`; `scripts/mcp/errors.test.ts` runs the real command for every error row), `<ManifestEntry>`, `<GrantStrings>`, `<ErrorCodes>` (typed by the SDK's `ErrorCode`, so a new code fails the web typecheck until described), `<PolicyClasses>` and `<Configuration group="…">` (a group of `packages/config/inventory.json`, or several in one table), in `apps/web/components/docs/generated.tsx`.
- Every component has a Markdown form (`asMarkdown()`, `apps/web/components/docs`), so `.md` pages carry the same tables and code: a page and its `.md` show the same words. Use no Fumadocs component without one, and none that hides content until clicked (Fumadocs' own type table does; ours renders every row).
- The Fumadocs packages must share one `fumadocs-core`, or `asMarkdown()` never opts in and every `.md` page prints JSX. `apps/web/lib/fumadocs.test.ts` fails when they do not; declare the optional peer that differs (`@mdx-js/mdx`, `zod`, `lucide-react`) in `apps/web/package.json` at the version the others use.
- `bun --filter web test` fails on a link to a missing page, heading or docs source file. Add every repository path the docs read at build to `web#build`'s inputs in `turbo.json`.

Here's how we write documentation. These are Lee Robinson's ten principles (https://leerob.com/docs), adapted to this repo; read that page before writing a docs page, and keep the numbering below in step with it. Not adopted yet: a feedback widget, an Ask AI sidebar, and shipping the docs as an MCP server.

1. Fast
   - Every docs page is static. No client-side data fetching, no runtime calls to Answerable ID.
   - No image unless it shows something words cannot.
2. Readable
   - Be concise. Make every token count.
   - No jargon, no idioms, no marketing. Sentence-case headings. British spelling.
   - Write for skimming: short paragraphs, a bold lead term, lists and tables over prose.
   - Start simple. Reveal complexity later on the page, or on a linked page.
   - Show a copy-pasteable example (cURL first) before you explain it.
3. Helpful
   - Document what exists. If it is not built yet, write "Not yet." and link the plan. Never describe planned behaviour in the present tense.
   - Document workarounds, even when they expose a product gap.
   - Every error code a person can hit gets a row: code, meaning, what to do.
4. AI-native
   - Prefer cURL over "click here". Prefer a prompt over a tutorial.
5. Agent-ready
   - Every page is Markdown too: append `.md` to the URL, or send `Accept: text/markdown`.
   - `/llms.txt` indexes the docs; `/llms-full.txt` carries all of them. Keep both working when you add pages or routes.
6. Polished
   - Every page has a `title` and a `description`. The build fails without them; they become the canonical tag and the OG image.
   - Headings are anchors. Do not rename one without checking inbound links; the link check test fails on a broken one. A moved page gets a redirect in `apps/web/next.config.mjs`.
   - Cross-link related guides and API pages in both directions.
7. Localized
   - English only for now. No `/en` in URLs; no locale hardcoded in paths.
8. Responsive
   - Keep the mobile menu working.
9. Accessible
   - Alt text on every image. Respect `prefers-reduced-motion`.
10. Universal

- Ship rules files (this one). Keep the OpenAPI contract honest: only routes a client can reach.

## Repo card

- Gates, from the root: `bun run typecheck` · `bun run lint` · `bun run build` · `bun --filter web test` · `bun --filter @answerable/id test:coverage` (needs Postgres: `bun run env:up`, then `bun --filter @answerable/id db:test:migrate`) · `bun --filter @answerable/countries test` · `bun run --filter @answerable/design test` (fails on any error in the root `DESIGN.md` and on a `tokens.css` that differs from `bun run --filter @answerable/design generate`) · `bun run mcp:test` (Turborepo, four suites at a time and never from its cache, so that 200 MCPs stay inside Postgres's 100 connections and CI's four cores; the Toolbox's, the admin MCP's and `mcp-postgres`'s suites reset their own test databases first: `bun --filter @answerable/mcp-toolbox db:test:migrate`) · `bun run mcp:check <workspace>` for the MCP workspace you changed · `bun run mcp:test:e2e` (runs `bun test` in `packages/acceptance`; Docker and Playwright Chromium) · `bun run infra:check` (charts, Terraform, workflows; no cloud, no Docker) · `bun run infra:test` (the kind stack; Docker, kind, Playwright Chromium). CI runs the same. `bunx knip` (configured in `knip.json`) lists unused files, exports and dependencies; run it before a release and after deleting code.
- Design page: `/design` renders the root `DESIGN.md` through `@answerable/design`, parsed at build, light, in its own root layout (`apps/web/app/(design)`; the rest of the site is `app/(site)`, dark); its pane edits any token live. `/design.md` serves the file as `text/markdown`.
- First run: Start the service (the platform organisation is seeded at boot), then with the root bearer, `ROOT_ADMIN_SECRET` (in development a fixed development-only value unless you set one), add the platform domain and SSO provider, sign in once, and add yourself to the `platform-admins` group; root locks itself afterwards.
- Ports: web 47100 · id 47300 · toolbox 47400 · admin MCP 47520 · postgres 47432 · the kind stack 48443 (Traefik, on `127.0.0.1` and `[::1]`), 47710 and 47711 (its company directories) and 47700. The acceptance's ports are under MCP kit and Toolbox.
- Style: Prettier without semicolons in `apps/web`, `packages/ui`, `packages/countries` and `packages/design`, with semicolons in `apps/id`. No semicolons in `packages/auth`, `packages/config`, `packages/id-admin`, `packages/mcp`, `packages/mcp-postgres`, `packages/acceptance`, `mcps/*`, `infra/*` and `scripts`. Tests are colocated `*.test.ts`; `apps/id` enforces 100% line and function coverage, integration tests end in `.integration.test.ts`; the MCP workspaces' gates are under MCP kit and Toolbox.
- OpenAPI: `UPDATE_SNAPSHOT=1 bun test src/openapi.integration.test.ts`, in `apps/id` (Turborepo strips the variable), regenerates `apps/id/openapi.json` and `apps/id/openapi.admin.json`; the same test fails when either drifts.
- Dependencies: `bunfig.toml` sets Bun's hoisted linker, so every workspace shares one copy of a package: drizzle's tables, queries and types must come from one `drizzle-orm`.
- Env: each service's variables are defined in code with `@answerable/config`'s `defineConfig`, with their development and test defaults, so nothing needs a `.env` locally but the credentials another system issues. Add a variable to its service's definition, then run `bun run env:inventory`, which writes `default.env` (every variable, empty values), `.env.example` (those credentials) and `packages/config/inventory.json`; `bun --filter @answerable/scripts test` fails when one drifts. `.env` files stay ignored and never hold committed values.
- Commits: imperative, sentence case, no prefix, no trailing period.

## MCP kit and Toolbox

Make an MCP with `bun mcp`, from the repository root, or from `mcps/<name>` without the name. Every MCP gets its own database schema and its sign-in through Answerable ID automatically, locally and on every deploy: never create either by hand. Without a terminal `bun mcp` never waits: a missing answer exits with code 2 and prints the command to run, with placeholders. `bun mcp help` lists every command and flag.

```text
New MCP:  bun mcp new <name> --description "…" --serve toolbox|standalone|both [--tool <domain.operation> --tool-description "…" [--mutation]]
New tool: bun mcp add tool <name> <domain.operation> --description "…" [--mutation]
Check:    bun mcp check <name>        List: bun mcp list [--json]
Run:      bun mcp setup (once, with your local ID running), then bun mcp dev <name>: migrates, serves it, registers it in your local ID, prints the claude mcp add command
Database: bun mcp db <name> generate (after a change to src/db/schema.ts), then bun mcp db <name> migrate (the local schema)
Ship:     a tag staging/<name>-<change> on a commit of main, then production/<name>-<change> on the same commit; the owner pushes both, never an agent
Never hand-edit *.generated.* or charts/answerable/mcps.json: bun mcp writes them (and the lists' package.json dependencies). Commit what bun mcp check rewrites.
```

Read `docs/07-mcp-platform-draft.md` (the foundation decisions that still hold) and `docs/08-capability-platform.md` (the platform) before extending the kit, and `docs/11-admin-mcp.md` before changing the admin MCP; `docs/09-mcp-design-standard.md` holds the rules, `apps/web/content/docs/mcp/create.mdx`, `add-a-tool.mdx`, `database.mdx`, `sign-in.mdx` and `deploy.mdx` show how to make an MCP, add a tool, use its database, sign it in and ship it, `cli.mdx` lists every command, and `apps/web/content/docs/toolbox/add-tools.mdx` shows how to mount one in the Toolbox by hand. Build on the official MCP SDK's primitives rather than re-implementing transport or OAuth. Do not add a Better Auth instance to an MCP.

- **Workspaces.** `packages/auth` verifies tokens. `packages/mcp` is the SDK: `defineTool`, `defineMutation`, `defineProvider`, `createMcpServer`, the conformance kit and the in-process client in `@answerable/mcp/testing`. `packages/id-admin` is `createIdAdmin` and, in `@answerable/id-admin/testing`, the fake ID. `packages/mcp-postgres` is the Postgres intent store, the evidence chain and the drizzle base schema (`evidenceEvents`, `evidencePayloads`, `intents`), with `migrate(db, { folder, legacy })`, ID's migrator. Every database has one model: a server's `src/db/schema.ts` composes the package's tables with its own, `db:generate` writes its drizzle journal, its custom migration `0001_evidence_chain.sql` is the package's `evidenceChainSql`, and an applied migration is never edited, regenerated or removed. `db:migrate` adopts a database the old file migrator built. `packages/mcp-platform` is what every server shares: `createCalls` (evidence and a span for every call and every refusal, a refusal because ID did not answer included; a commit's row names its intent and receipt), `startAuditPoller` (one audit-log reader that invalidates grants and profiles), `health`, `mcpDatabases` (each declared MCP's `db` through `mcpDatabase`, and the serving login's assertion) and, in `@answerable/mcp-platform/testing`, shared and own MCP databases of a suite's own. `packages/acceptance` is the real-ID kit and its journeys. `mcps/e2e` is the reference MCP, its records in Postgres, served `both`. `mcps/example` is the finished example. `mcps/toolbox` is the Toolbox; it serves `src/mounted.generated.ts`: each `toolbox` or `both` MCP mounted in its hub, and each `standalone` or `both` one alone, with its own `createMcpServer` and resource `<origin>/<name>/mcp`. `mcps/admin` is the admin MCP: staff-only, each tool behind a role (`answerable-team`, `answerable-admin`, `answerable-owner`) read from ID's member access view once per request, never cached. `scripts/mcp` is `bun mcp`: `cli.ts` parses and dispatches, `commands/*.ts` are the commands, `templates/*.ts` the files it writes, which the docs render, and `generate.ts` writes `charts/answerable/mcps.json`, the Toolbox's generated list and its `package.json` dependencies from every `mcps/*/mcp.json` and manifest. `mcps/retired.json` lists the names of removed MCPs, never used again.
- **Commands.** `bun mcp new <name>` makes `mcps/<name>`: it installs it, creates its schema in `answerable_mcps`, writes its first migration and manifest, and checks it. `bun run mcp:check <workspace>` typechecks, lints and tests one workspace, as CI does, and fails on a stale manifest; `bun mcp check <name>` rewrites it instead and says to commit it. `bun run mcp:test` runs the package, server and `bun mcp` suites, and picks up every MCP under `mcps/`; `bun mcp`'s end-to-end test makes a randomly named MCP in a copy of the working tree, and drops its schemas afterwards. `bun run mcp:test:e2e` runs the journeys against real ID. Root `bun dev` starts apps only; `bun run toolbox:dev` and `bun run admin:dev` serve the Toolbox and the admin MCP; `bun mcp db <name> migrate` makes each served MCP's local schema first.
- **Gates.** `packages/auth`, `packages/config`, `packages/id-admin`, `packages/mcp`, `packages/mcp-postgres`, `mcps/e2e`, `mcps/toolbox` `mcps/admin` and `scripts` enforce 100% line and function coverage, and so does every MCP `bun mcp new` makes; `packages/acceptance` is test support and has no coverage gate. Every provider runs `assertProviderConformance` and commits its `manifest.json`: after changing a definition, run `bun mcp check <name>`, or `UPDATE_MANIFEST=1 bun run --filter <workspace> test` for a hub, and commit the file (Turborepo's strict environment strips the variable, so `mcp:check` cannot write it). `apps/web/content/docs/mcp/reference.mdx` is generated from the documentation comments by `bun run --filter @answerable/mcp reference`, a test fails when it drifts, and every export of `@answerable/auth` and `@answerable/mcp` needs a comment. MCP unit tests run in-process and open no port, except the Toolbox's and the admin MCP's entry-point tests; the Toolbox's, the admin MCP's, `mcp-postgres`'s, `bun mcp`'s and every database MCP's suites also need the development Postgres.
- **Ports and databases.** The Toolbox runs on 47400 with `answerable_toolbox` and `answerable_toolbox_test`, and the admin MCP on 47520 with `answerable_admin` and `answerable_admin_test` (all created by `infra/postgres/init`); the Toolbox reaches the MCPs' tables in `answerable_mcps` as `answerable_mcps_toolbox`. `packages/mcp-postgres` tests reset `answerable_mcp_postgres_test`; the Toolbox's and `packages/mcp-platform`'s make shared MCP databases of their own (`answerable_toolbox_test_mcps` and `answerable_toolbox_test_migrate`, `answerable_mcp_platform_test` and two beside it), and each own-database MCP's `answerable_toolbox_test_<name>`, each with logins of its own, and drop them at the end. `mcp:test` runs suites concurrently, so no two suites may reset one database, and every test login's name is generated: logins are cluster-wide. The acceptance owns ports 47532 (its own disposable Postgres, which also holds `answerable_toolbox_acceptance`, `answerable_admin_acceptance` and `answerable_mcps_acceptance`), 47600, 47603, 47604 (the Toolbox), 47605 (a second Toolbox) and 47606 (the admin MCP), and never touches the normal ID database. Its two lanes, `bun packages/acceptance/scripts/host-lane.ts` and `admin-lane.ts`, keep ID and the servers up for Claude Code by hand on the same ports, and add 47700 and 47701 for Claude Code's callbacks; neither runs beside the acceptance, and the journeys are their proof.
- **Agents and worktrees.** Never run `bun run env:up` from a worktree: its Compose project has the main checkout's name, so it recreates the running Postgres; use the one on port 47432. Never run two acceptances at once: the Compose project name is fixed, so one run's cleanup removes the other's Postgres. Never run two kind stacks at once: the cluster is always named `answerable-local` and its host ports are fixed, so `bun run infra:test` runs once per machine.

## Deployment

Read `docs/12-deployment.md` (what runs where and why) and `infra/README.md` (the runbook) before changing `infra/*`, `charts/*` or `.github/workflows`. The decisions are in `docs/goals/civo-deploy/decisions.md` (D3 to D38; the gaps are decisions that named another cloud and were removed). Civo is the only cloud named anywhere in the deployment, down to variable names: `infra/civo/terraform.sh` is the one place that maps the state credential to the S3 backend's own names.

- **Nothing is done by hand from a laptop.** A tag `staging/<name>` or `production/<name>` on a commit of `main` ships; `bootstrap.yml` and `ops.yml` run by hand from GitHub. Never `terraform apply`, `destroy` or `-replace` against an environment yourself, and never `helm upgrade` against its cluster: Terraform runs in the shipping workflows, production behind the owner's approval. `infra/civo/terraform.sh <environment>` exists for break-glass reads.
- **Every secret lives in the GitHub environment or is generated where it is used.** The owner pastes five per environment (`CIVO_TOKEN`, `CLOUDFLARE_API_TOKEN`, `MICROSOFT_CLIENT_ID`, `MICROSOFT_CLIENT_SECRET`, `GH_SECRETS_TOKEN`); `bootstrap.yml` writes the state credential and ID's secrets; Terraform writes `KUBE_SERVER`, `KUBE_CA`, `KUBE_TOKEN` and the certificates' keys; the ops Jobs write the database logins and the machine clients' secrets into Kubernetes Secrets. The deploy step is handed the deployer token and ID's secrets, never a Civo key.
- **Migrations are expand, then contract.** The previous image keeps serving during a rollout and after a rollback, so a migration never breaks it; a destructive change ships in a later release than the code that stopped using what it removes.
- **The image tag is the commit SHA** (`sha-<40 hex>`), and the cluster runs images by digest. Never a mutable tag, never a rebuild for production.
- **Never a plaintext secret** in a commit, a values file, a Terraform variable, a workflow log or a report. Terraform holds no secret as input; what its providers generate stays in its state, in the environment's object store.
- **The kind stack** is the cluster `answerable-local` on ports 48443, 47710, 47711 and 47700, one per machine; `infra/k8s/local/README.md` keeps it for a look.
- **`bun run infra:check` is CI's to arbitrate on macOS.** A Terraform provider killed on start (exit 137) is a rewritten plugin cache, not a code fault (`infra/civo/README.md`, Checks); the `infra-check` job decides.
- **Gates.** `infra/ops` and `infra/pipeline` enforce 100% line and function coverage; `infra/k8s` is test support and has none. `bun run mcp:test` runs the two suites with the MCP suites.

## ID and consumer boundaries

All ID login, consent, organisation selection, security and error pages are Hono server-rendered pages in `apps/id`, using shared UI definitions and a stylesheet `hono-tailwind` compiles at build time, never at runtime. Never put identity-provider pages in `apps/web`. The web app is a separate OAuth consumer through its development-only `/oauth-test` page; it must not read ID cookies, root credentials or the ID database.
