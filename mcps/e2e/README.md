# E2E MCP

A permanent test consumer of `@answerable/mcp-base`. It provides tenant-scoped test records and an interactive MCP Apps view. Development/test only.

**Status:** real local ID login, PKCE resource tokens, tenant isolation and rendered Apps actions have passed. Refresh, revocation, measured expiry, interruption cleanup also pass. See [evidence](../../reports/mcp-foundation-evidence.md).

## One-command local acceptance

```sh
bun install
(cd mcps/e2e && bun x playwright install chromium)
bun run mcp:test:e2e
```

Requires Docker Compose and Bun 1.3.1. The command starts an isolated PostgreSQL container, real Answerable ID, ID’s browser login pages, two local corporate OIDC fixtures and the MCP. The client follows the MCP authentication challenge and ID discovery metadata. Chromium signs in, selects each organisation, consents, then creates and deletes records through the Apps bridge. It checks tenant isolation and rejection at another resource. It refreshes each grant, disables the fixture organisation using ID's lifecycle service, verifies refresh denial and waits for the actual 60-second access-token expiry before checking rejection. The test uses no injected ID sessions or substitute resource tokens.

Ports: PostgreSQL `47532`, ID `47600`, MCP `47602`, OAuth callback `47603`, runner guard `47604`. Keep these free. Allow roughly two minutes for a run, including the real expiry wait. The guard prevents simultaneous runners; remaining fixture servers use allocated loopback ports. The database belongs to Compose project `answerable-mcp-e2e`; teardown removes its disposable data. Normal ID data and configuration are unused.

A failed assertion exits non-zero and runs cleanup. After the successful journey, the command starts another fixture, interrupts it with SIGTERM and checks that the container and all reserved ports are released. The upstream fixture simulates corporate SSO; external chat-host and real corporate-provider acceptance remain separate tests.

## Run against a configured local ID

```sh
bun install
bun run --filter @answerable/mcp-e2e build
bun --env-file=.env run --filter @answerable/mcp-e2e start
```

These commands require an existing ID resource registration, client, capability and assignments. Configure:

| Variable | Purpose |
| --- | --- |
| `MCP_ID_ISSUER` | Exact trusted Answerable ID issuer |
| `MCP_ID_JWKS_URL` | Trusted deployment's JWKS endpoint |
| `MCP_RESOURCE_URL` | Canonical audience/URL, for example `http://localhost:47500/mcp` |
| `MCP_RESOURCE_INSTANCE_ID` | Immutable UUID of that registered resource |
| `MCP_RECORDS_PATH` | SQLite path owned by this test instance |
| `MCP_ALLOW_LOCAL_HTTP` | Explicit `true` for local loopback HTTP; default `false` |
| `MCP_PORT` | Listening port; default `47500` |

The entry point binds to loopback. No credential is generated by starting the MCP. Authentication uses only ID-issued user resource tokens.

## Prompts and resources

`fixture_walkthrough` describes a safe create/read workflow. `fixture://guide` explains tenant ownership, scopes and operation keys. Both require `e2e:read`; retrieving them does not change records. The real-ID acceptance command retrieves both before checking the initially empty tenant list.

## Tools

| Tool | Scope | Behaviour |
| --- | --- | --- |
| `identity_get` | `e2e:identity` | Safe verified identity and scopes |
| `records_list` | `e2e:read` | First 100 tenant-owned records in stable order |
| `records_get` | `e2e:read` | One record, constrained to the caller's tenant |
| `records_show` | `e2e:read` | Record list with a portable Apps view |
| `records_create` | `e2e:write` | Create with an operation key |
| `records_delete` | `e2e:write` | Delete with an operation key |

Creation and deletion receipts share a SQLite transaction with their effect. Reuse the same key and input after an uncertain response. Receipts are bound to the resource, tenant, subject and tool. The base checks current token permissions before a replay reaches storage.

The browser view uses the same tools. It receives no bearer token and stores no credentials. Native form submission is avoided so the view works in a scripts-only sandbox.

## Tests

```sh
cd mcps/e2e
bun x playwright install chromium
bun test src
bun run typecheck
bun run lint
```

The Apps test starts local JWKS/MCP/host servers and Chromium, loads the UI resource through the MCP client, and proves allowed and denied actions. It uses synthetic signed credentials. The record tests prove tenant isolation and durable receipt behaviour. The separate `mcp:test:e2e` command exercises real ID authentication.

The HTML build uses the shared base's isolated Bun browser builder; no per-MCP Vite setup is needed. Source schemas in `src/contracts.ts` are browser-safe; SQLite and authentication code never belong in a view bundle.

## Errors

| Code | Meaning | Action |
| --- | --- | --- |
| `invalid_token` | Missing or unacceptable ID resource token | Authenticate through ID for this resource |
| `insufficient_scope` | Required tool permission missing | Obtain the appropriate authorised grant |
| `record_not_found` | No record accessible in this tenant | List available records |
| `operation_key_reused` | Same operation key with different input | Use a new key for a new operation |
| `tool_failed` | Unexpected failure; details withheld | Inspect server evidence and retry an uncertain write with its original key |

## Composition

Start a new consumer with the [authoring guide](../../apps/web/content/docs/mcp/authoring.mdx). This workspace is the executable reference, including its test-only storage and authentication harness.

`createE2eMcp` accepts injected record storage and compiled view HTML. Its `readOnly` option selects the same reusable read tools while omitting write tools entirely. It is a normal consumer of the base; no test auth bypass is built into its handlers.
