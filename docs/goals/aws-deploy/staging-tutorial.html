Part 1

Your Mac

Every tool is already installed on this Mac. These steps bring the code up to date and confirm the versions.

1.1Get the latest code

2 min

Open Terminal in the repository folder and update main.

cd ~/code/answerable
git checkout main
git pull
bun install
You should see git pull bring in the deployment work and bun install end without errors.

1.2Check your tools

1 min
bun --version; terraform version | head -1; sops --version | head -1; age-keygen --version; openssl version; kubectl version --client | head -1; helm version --short; civo version | head -1; gh auth status
You should see Bun 1.3.1, Terraform v1.16.5, sops 3.13, age v1.3, OpenSSL 3, Helm v4.3.0, Civo CLI v1.5.5, and gh logged in as Rieranthony.
kubectl on this Mac is 1.32; the cluster will be newer. Upgrade it now with brew upgrade kubectl. If Terraform says v1.12, open a new terminal: version 1.16.5 is in ~/.local/bin, which comes first on your PATH.
Part 2

Civo

The account you created is the staging account. Production gets its own account later.

2.1Check the account's quota

3 min

New Civo accounts start on a basic quota. Open dashboard.civo.com/quota. Staging needs room for:

  • a Kubernetes cluster of 2 Medium nodes (2 CPU and 4 GB each, so 4 CPU and 8 GB in all);
  • a Small PostgreSQL database;
  • 1 load balancer, 1 reserved IP, 1 object store, 1 private network and 3 firewalls.

If anything is short, press Request quota increase and paste:

Staging environment in LON1: a Kubernetes cluster with 2 Medium nodes, a Small PostgreSQL database, 1 load balancer, 1 reserved IP, 1 object store, 1 private network and 3 firewalls.
Done when the quota covers the list, or Civo has approved your request.

2.2Copy the API key into your password manager

2 min

In the Civo dashboard, open your profile's Security section and copy the API key. If your account sits in an organisation, the page lists one key per account: take the staging account's. Save it in your password manager as Civo · answerable-staging · API key. This key can do anything in the account, so it never goes in a file or a chat.

2.3Give the key to the Civo CLI

2 min

Run this, type answerable-staging as the name, then paste the key when asked. It stays out of your shell history.

civo apikey save

Then select it and London:

civo apikey use answerable-staging
civo region use LON1
civo kubernetes ls
You should see an empty list of clusters and no error. That proves the key works.
Part 3

Cloudflare

All of this happens on the zone answerable-staging.uk, the domain you bought. Terraform sets every other Cloudflare setting for you.

3.1Check the zone is active

1 min

On dash.cloudflare.com, open answerable-staging.uk. The overview should say Active. A domain bought through Cloudflare is active straight away.

3.2Switch off Bot Fight Mode

1 min

In the zone, go to Security → Bots and turn Bot Fight Mode off. Left on, it shows a "are you human?" page to Claude Code and the MCP servers, which are not browsers. No token can change this setting, so it is the one manual switch.

3.3Create Terraform's token

4 min
  1. Top right: your profile → My Profile → API Tokens → Create Token → Create Custom Token.
  2. Name it answerable-staging terraform.
  3. Add these six permission rows:
ZoneZoneRead ZoneDNSEdit ZoneSSL and CertificatesEdit ZoneZone SettingsEdit ZoneConfig RulesEdit ZoneCache RulesEdit
  1. Under Zone Resources: Include → Specific zone → answerable-staging.uk.
  2. Continue to summary → Create Token. Copy the token into your password manager as Cloudflare · answerable-staging · Terraform. Cloudflare shows it only once.

3.4Create cert-manager's token

3 min

A second, smaller token. It lives inside the cluster and lets it obtain the HTTPS certificates from Let's Encrypt. Same steps, named answerable-staging cert-manager, with only two rows:

ZoneZoneRead ZoneDNSEdit

Same zone resource: answerable-staging.uk only. Save it as Cloudflare · answerable-staging · cert-manager.

Both rows matter. Without Zone Read the certificate never issues and the site never answers. The two tokens must be different: the setup refuses Terraform's token here.

Part 5

Load your keys into one terminal

From here to part 9, use one terminal window in the repository folder. Each line below asks for one value and hides what you paste. Copy and run one line at a time: pasting several at once would feed the next line in as your secret.

5.1Paste each value when asked

2 min
printf 'Civo API key: '; read -rs CIVO_TOKEN; echo; export CIVO_TOKEN
printf 'Cloudflare token for Terraform: '; read -rs CLOUDFLARE_API_TOKEN; echo; export CLOUDFLARE_API_TOKEN
printf 'Cloudflare token for cert-manager: '; read -rs CERT_MANAGER_CLOUDFLARE_TOKEN; echo; export CERT_MANAGER_CLOUDFLARE_TOKEN
printf 'Entra client ID: '; read -r MICROSOFT_CLIENT_ID; export MICROSOFT_CLIENT_ID
printf 'Entra client secret: '; read -rs MICROSOFT_CLIENT_SECRET; echo; export MICROSOFT_CLIENT_SECRET
export ALLOWED_API_CIDRS='[]'

Check each is set, without showing it:

for v in CIVO_TOKEN CLOUDFLARE_API_TOKEN CERT_MANAGER_CLOUDFLARE_TOKEN MICROSOFT_CLIENT_ID MICROSOFT_CLIENT_SECRET; do [ -n "${(P)v}" ] && echo "$v set" || echo "$v MISSING"; done
You should see five lines ending in set.
If you close this terminal before part 9, open a new one and run part 5 again, and the two lines of step 6.3.
Part 6

Build the servers

Terraform creates everything in your Civo account and on the Cloudflare zone. It shows what it will create and waits for you to type yes each time. Civo starts billing here.

6.1Create staging's encryption key

2 min

This key encrypts staging's secrets file. Its public half goes in the repository; the private half stays on this Mac.

bun run setup age-init --environment staging

Now back the private key up: drag this file into your password manager as a document, age · answerable-staging.

open -R ~/.config/sops/age/answerable-staging.txt
Do not skip the backup. Without this file, nobody can ever read staging's secrets again.

6.2Create the network, cluster and database

15–25 min
bun run setup first-apply --environment staging

Type yes each time Terraform asks. First it makes the bucket that will hold Terraform's records, moves its records there (answer yes to copying the state), then creates the cluster, the database and the firewalls. Creating the cluster and the database takes most of the time.

You should see it stop on purpose, saying two certificate files are missing and naming origin-pull and database-ca. Just before that, it prints a line AWS_ACCESS_KEY_ID=…: the bucket's key ID. Keep it on screen for the next step.

6.3Load the bucket's key

2 min

Every later step reads Terraform's records from the bucket, so this terminal needs its key. Replace the placeholder with the value after AWS_ACCESS_KEY_ID= in 6.2's output:

export AWS_ACCESS_KEY_ID=<the access key ID from 6.2>

This prints the matching secret key. It is the one time a secret appears on screen:

civo objectstore credential secret --access-key "$AWS_ACCESS_KEY_ID"

Copy it into your password manager as Civo · answerable-staging · state secret key, then load it and clear the screen:

printf 'State secret key: '; read -rs AWS_SECRET_ACCESS_KEY; echo; export AWS_SECRET_ACCESS_KEY
clear

6.4Create the certificate Cloudflare shows the servers

3 min

Cloudflare presents this certificate on every request it forwards, and the cluster refuses any request without it. That is how only Cloudflare can reach staging.

bun run setup origin-pull --environment staging --zone answerable-staging.uk
You should see it upload the certificate, wait until Cloudflare reports it active, and write infra/civo/envs/staging/edge-ca/ca.pem.

6.5Record the database's certificate

3 min

The servers check the database's identity on every connection. This reads its certificate from inside the cluster and saves it.

bun run setup database-ca --environment staging
You should see the certificate's subject, issuer, validity and a SHA-256 fingerprint. Copy the fingerprint and today's date into a note: this is the identity everything else trusts from now on.
It ends with It covers …, the host in database_admin_url.
If it says Warning: it does not cover … instead, stop here and send me its output. That is one of the facts only this first run can reveal, and the fix is a one-line change.

6.6Finish the infrastructure

5–10 min

The rest: Traefik and cert-manager inside the cluster, the deploy account GitHub will use, and the DNS records and settings on Cloudflare.

bun run setup first-apply --environment staging --resume
You should see Apply complete!, then Applied staging. In Cloudflare, the zone's DNS now has three proxied records: id, toolbox and admin-mcp.
Part 7

Secrets and GitHub

7.1Generate staging's secrets file

1 min

Generates ID's signing secrets and root secret, adds the database administrator's address and the two tokens you loaded, and encrypts it all with the key from 6.1.

bun run setup init-secrets --environment staging
You should see Verified: … decrypts to the three Secrets, with each Secret's key names and never a value.

7.2Hand GitHub what it needs to deploy

2 min

Creates the GitHub environments staging and infra-staging, stores their secrets, and switches on deploys to staging.

bun run setup publish-env --environment staging --enable
You should see Published to Rieranthony/answerable-monorepo, the secret names it set, and repository variable DEPLOY_STAGING: true. In GitHub, Settings → Environments now shows both environments.
Part 8

The first deploy

8.1Commit the four files and push

1 min

First a safety check that the secrets file is encrypted. The number must be above zero:

grep -c 'ENC\[' infra/civo/envs/staging/secrets.enc.yaml
git add .sops.yaml infra/civo/envs/staging/edge-ca/ca.pem infra/civo/envs/staging/database-ca.pem infra/civo/envs/staging/secrets.enc.yaml
git commit -m "Set up the staging environment"
git push origin main

8.2Watch the run

20–25 min

Open Actions → Deploy staging. In order: CI runs every test (about 15 minutes), Apply the staging infrastructure finds nothing to change, eight Build jobs and four Publish jobs make the images, then Deploy to staging and Smoke test staging.

The deploy creates the three databases and their logins, runs the migrations, starts ID, and registers the Toolbox and the admin MCP with ID by itself.

8.3Make the four images public

5 min

GitHub makes new images private, and the cluster pulls them without a password. So the first Deploy to staging will fail with ImagePullBackOff or ErrImagePull. Once the four Publish jobs are green:

  1. Open your profile's Packages.
  2. For each of answerable/id, answerable/toolbox, answerable/admin-mcp and answerable/ops: Package settings → Danger Zone → Change visibility → Public, and type the name to confirm.
  3. Rerun the failed jobs:
gh run list --workflow deploy-staging.yml --limit 1
gh run rerun <the run's ID from the line above> --failed
This is once only: later deploys reuse the same four packages.

8.4Check it's live

2 min

Run the same smoke test the pipeline runs, from your Mac:

bun infra/pipeline/src/cli.ts smoke --environment staging --wait 120
You should see a table of checks (ID's health, readiness, discovery and signing keys, the Toolbox's and the admin MCP's health and metadata) ending in PASSED. The first HTTPS certificate can take a few minutes; --wait retries for two.

Part 11

Finish

11.1Pin the cluster's version

3 min

Civo chose its latest Kubernetes version for the cluster. Writing it down stops a future apply from trying to change it.

civo kubernetes show answerable-staging-cluster | grep -i version

Add that version to infra/civo/envs/staging/terraform.tfvars as a new line, then commit and push:

kubernetes_version = "<the version shown above>"
git add infra/civo/envs/staging/terraform.tfvars
git commit -m "Pin the staging cluster's Kubernetes version"

11.2Close the terminal

1 min

Close the terminal from part 5 so the keys leave memory. Everything you need again is in your password manager: the Civo API key, two Cloudflare tokens, the Entra secret, the state secret key, and the age key file.

11.3Reset your local database

5 min

Separate from staging: your local development database moved to PostgreSQL 17, and the Toolbox and admin MCP now refuse the owner login. Once, knowing it deletes your local data:

bun run env:reset
bun run env:up
bun --env-file=.env run --filter @answerable/id db:migrate

Your .env has none of the MCPs' database lines yet. Copy the six lines starting TOOLBOX_DATABASE_ and ADMIN_DATABASE_ (not the _TEST_ ones) from .env.example into it, then migrate the two MCPs:

bun --env-file=.env run --filter @answerable/mcp-toolbox db:migrate
bun --env-file=.env run --filter @answerable/mcp-admin db:migrate
Reference

If something goes wrong

Every setup command says which step failed and why. The usual causes:

What you seeWhat to do
Terraform: an authentication or permission error from CloudflareA token is missing a row. Compare it with step 3.3 (six rows) or 3.4 (two rows), edit the token in Cloudflare, and rerun the same command.
Terraform: a quota error from CivoRaise the quota as in step 2.1, then rerun. If 6.2 had already moved the state, use first-apply --resume with the step 6.3 lines loaded.
already keeps its state in the bucketThe first part of 6.2 is done: load 6.3, then run first-apply --environment staging --resume.
A failure writing staging.tfstate.tflockCivo's storage refused Terraform's lock file. Set use_lockfile = false in infra/civo/envs/staging/backend.tf and rerun; it means only one person applies at a time.
AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY must hold …The terminal lost the bucket's key: redo step 6.3.
these commands need OpenSSL 3brew install openssl@3, then export PATH="$(brew --prefix openssl@3)/bin:$PATH".
database-ca: no certificate from the databaseIt prints the exact commands to run by hand; run them as shown.
Deploy: ImagePullBackOff or ErrImagePullThe images are still private: step 8.3.
Browser: Cloudflare error 526 or 525, or the smoke test times out on HTTPSThe first certificate is still being issued, which can take a few minutes. If it lasts over 15 minutes, the cert-manager token is probably missing Zone Read (step 3.4).
Claude Code gets an HTML page or a challengeBot Fight Mode is still on: step 3.2.
ID refused the root secret (401)The cluster has older secrets than the file: push again so the deploy reapplies them.
ID refused the root secret (403 root_locked)An administrator already exists: part 9 is done.
The connectivity test in 9.1 reports problemsAlmost always the tenant ID: recheck step 4.2.
Anything elseCopy the command's last lines (they never contain a secret) and send them to me.

After today

  • Every push to main deploys staging. CI runs first; a failing test stops the deploy. A deploy whose new version never becomes healthy rolls itself back.
  • To stop deploys without deleting anything: gh variable delete DEPLOY_STAGING. Civo keeps billing; to stop the cost, follow "Destroy an environment" in infra/README.md.
  • Roll back by running Deploy staging by hand with an earlier sha-… tag.
  • Next on the plan: OpenBao, the secrets server, lands on staging (brief B7b), then the production rehearsal (B7c). Production needs its own Civo account and a way for GitHub to reach it, which is the one open decision (D30).
  • The full runbook for every day-two task (rotating a secret, restoring the database, scaling) is infra/README.md; the design is docs/12-deployment.md.
