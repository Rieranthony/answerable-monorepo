# B7a — First staging deployment

**Executor:** the owner, with an agent that has the cloud session and the browser. **Depends on:** B0 to B6 on `main`, and [D28](../decisions.md). **Decisions:** [D8](../decisions.md), [D13](../decisions.md), [D26](../decisions.md), [D28](../decisions.md).

> **Revised 10 October 2026 for portability; D28 decided on 12 October: Civo, two accounts; on the same day the owner placed OpenBao right after staging is up, so this brief is now B7a (staging only), [B7b](b7b.md) is OpenBao and [B7c](b7c.md) is the production rehearsal, which the former step 11 below became.** The steps below run on Civo, staging in the `answerable-staging` account, with these substitutions: "apply staging" applies that cloud's root and installs the platform chart; "first deploy" is the first `helm upgrade`; the lockdown proof is against the cloud load balancer's address; "retire the laptop keys" means the AWS IAM user if AWS is used and, on Civo, confirming the account API key is held only where B0 says. On Civo two steps are added before any production data: a **restore drill** (take Civo's backup, restore it to a new database, run `ops:preflight` against it, record what Civo's backup actually is, its age and how long the restore took), and a **failover check** if additional database nodes are bought. The evidence report is `reports/staging-evidence.md`. A rehearsal on a second cloud is its own owner-approved step with its own costs.

## Goal

Staging is live and used: a person signs in through the real Entra, Claude Code talks to the staging admin MCP and onboards a test organisation into the staging Toolbox, the preflight passes, a restore drill succeeds, and the numbers are measured. Production is proved one click away by standing it up, smoke-testing it and destroying it again (or keeping it, the owner's call). The laptop's long-lived AWS keys are gone.

## Owner inputs

- An Entra app registration for staging: multi-tenant, redirect URIs `https://id.answerable-staging.uk/auth/sso/callback` and `https://id.answerable-staging.uk/login`, a client secret with its expiry noted (`docs/06` § Platform applications); optionally a Google client for staging.
- The go for the production rehearsal, and whether production stays up afterwards.
- The first sign-in, and the admin-consent for the staging app in Answerable's own tenant.

## Steps, in order

0. **The edge, once per zone** ([D18](../decisions.md), [D19](../decisions.md)); staging first on `answerable-staging.uk`, production on `answerable.org` at step 11. In the Cloudflare dashboard: switch Bot Fight Mode off. From a trusted machine: generate the environment's origin-pull CA and a client certificate (`openssl` ECDSA P-256, CA valid 10 years, client certificate 5 years, CN `cloudflare-origin-pull.<zone>`), commit the CA's public certificate as `infra/aws/envs/<env>/edge-ca/ca.pem`, store the client key and certificate in that environment's Secrets Manager (`edge/origin-pull-client`), and upload the client certificate and key to the zone with `PUT /zones/<zone>/origin_tls_client_auth` (zone-level Authenticated Origin Pulls). The environment's Terraform apply then switches origin pulls on and writes the zone settings and rules. Proof for production: `curl https://www.answerable.org` is unchanged (DNS-only, Vercel). Universal SSL issues the edge certificate on its own once the proxied records exist; confirm it is `active` on the zone's SSL page.
1. **Apply staging.** Merge an empty change under `infra/aws/` or dispatch `infra.yml`; the `apply-staging` job creates the environment. Record the resource count and the apply duration. DNS: the three proxied CNAMEs appear in the `answerable-staging.uk` zone and resolve to Cloudflare addresses; `curl -sI https://id.answerable-staging.uk/healthz` answers through Cloudflare and the ALB (a fixed 404 until the service runs is fine). Proof of the lockdown: `curl --resolve id.answerable-staging.uk:443:<ALB address>` without a client certificate fails the TLS handshake, and from any address outside Cloudflare's ranges the connection times out at the security group.
2. **Fill the human secrets** on a trusted machine by editing `infra/civo/envs/staging/secrets.enc.yaml` with `sops` (D23): `BETTER_AUTH_SECRET` (`openssl rand -base64 48`), `UPSTREAM_TOKEN_SECRETS` (the JSON array with a 32-byte base64url key), `ROOT_ADMIN_SECRET`, `MICROSOFT_CLIENT_SECRET`, the zone's Cloudflare token for cert-manager, the origin-pull client key; `GOOGLE_CLIENT_SECRET` only with a Google client. Commit the encrypted file; the deploy applies it. `MICROSOFT_CLIENT_ID` goes in the values file (not a secret).
3. **First deploy.** Push to `main` (or dispatch `deploy-staging`): images build, `ops-bootstrap` creates the databases and logins and writes the URL secrets, the three migrates run, the services start, the smoke passes. Record: image sizes in ECR, build time, time from push to green smoke, the ID container's time from start to `readyz`.
4. **ID first run** (`docs/06` step 7) with the root secret read from Secrets Manager: platform domain `answerable.org` (the staff email domain, unchanged by the staging zone), the SSO provider on the staging Entra app (tenant-specific issuer), the connectivity test, the owner's sign-in at `https://id.answerable-staging.uk/login`, the `platform-admins` membership. Root locks itself; confirm with a 403. **Address proof**: before locking root, make one deliberately failing request to `/auth/*` through Cloudflare with a forged `X-Forwarded-For: 203.0.113.9`, then read the newest `auth.signin.failed` or denial row through `GET /api/admin/v1/audit-events`: its address must be the machine's real public address, not `203.0.113.9` and not a Cloudflare address. This is the end-to-end proof of [D6](../decisions.md)'s trusted-proxy chain.
5. **Register the MCPs** with `ops.yml` (`register`, staging) using a staff token (root is locked now: get the token as `docs/id/onboard.mdx` § Get a staff token describes and put it in `ops/staff-token`); the Toolbox and admin MCP redeploy and their `/health` and metadata pass the smoke.
6. **Claude Code against staging** (`https://admin-mcp.answerable-staging.uk/mcp`): the printed `claude mcp add` commands; `admin_whoami` shows the owner's roles; onboard a test organisation (a spare directory is not available in AWS, so use a second Entra tenant the owner controls, or Google Workspace; otherwise onboard the organisation and stop before its sign-in) and enable the Toolbox for it through the admin MCP, as the admin lane story does (`apps/web/content/docs/admin/setup.mdx` § Try it locally).
7. **Preflight**: run `ops:preflight` as a one-off task (add an `id-preflight` task definition in B4's `task` module if it is not there) and record its counts.
8. **Restore drill**: restore the latest automated snapshot to a new `db.t4g.micro`, run the preflight against it from a one-off task with a `DATABASE_URL` override, time the restore (RTO) and note the snapshot's age (RPO), delete the instance. Record in the evidence report; this is E7's input, not its closure.
9. **Measure**: `max_connections` on the live instance (`show max_connections` through a one-off task), RDS `DatabaseConnections` at idle and after the sign-in, ALB `TargetResponseTime` p50 and p99 for `/readyz` and `/.well-known/openid-configuration` over an hour, CloudWatch Logs ingestion per day, the month's cost after seven days from Cost Explorer extrapolated, and compare with the estimate.
10. **Alarms**: stop one task by hand (`aws ecs stop-task`) and confirm the running-count alarm and its email; let it recover.
11. **Production rehearsal**: moved to [B7c](b7c.md), after OpenBao ([B7b](b7b.md)) is on staging, so production launches with OpenBao from its first minute.
12. **Retire the laptop keys**: delete the access keys of `anthony-laptop` and the user itself once `aws sso login` works for everything the owner does; note it in the evidence report.
13. **Evidence**: `reports/aws-staging-evidence.md` with every number above, the dates, what passed, what was skipped and why; link it from `docs/12` and from the release plan's E5–E7 inputs.

## Constraints

- No secret value in any report, log excerpt or commit; redact before pasting.
- Production is never deployed from a laptop; only the workflow.
- A failed step is fixed in a brief-sized change on `main` and the step is rerun; the evidence report says it happened.

## Acceptance

The evidence report exists and is linked; staging answers every smoke check; the owner has used Claude Code against staging; the production click worked once end to end; no long-lived AWS key exists.
