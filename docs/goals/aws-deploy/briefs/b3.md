# B3 — The ops image: database bootstrap and registration

**Executor:** Codex (GPT-6 Astra, medium); Fable reviews and lands. **Depends on:** B2. **Decisions:** [D4](../decisions.md), [D7](../decisions.md), [D10](../decisions.md), [D23](../decisions.md).

> **Revised 12 October 2026.** The `SecretStore` interface stands, but the production implementation is a **`KubernetesSecretStore`**, not AWS Secrets Manager: it reads and writes named `Secret`s in the release namespace through the Kubernetes API, from inside the Job, with a ServiceAccount whose Role allows `get`, `create` and `patch` on exactly the secret names it owns (`id-database`, `toolbox-database`, `admin-database`, `toolbox-id-client`, `admin-id-client`). `bootstrap` therefore resets a password it cannot find (the cluster, not a store, is where generated passwords live) and `register` rotates a client secret it cannot find, as already specified. The `FileSecretStore` stays for the kind stack. The `@aws-sdk/client-secrets-manager` implementation is not written now; it returns with External Secrets when a company store exists.

## Goal

Two idempotent commands that turn an empty Postgres and an empty ID into a working environment without a person typing SQL or cURL: `bootstrap` creates the databases and logins and puts their URLs in the secret store; `register` creates the MCPs' resources, machine clients, host clients and grants in ID per the docs and puts the client secrets in the store. Both run as one-off ECS tasks in AWS and inside the local stack, where the stack test proves the whole story: boot, bootstrap, migrate, register, a staff sign-in through the containers and a tool call on the admin MCP.

## Facts to start from

- Production needs three databases, each with an owner login that migrates and a runtime login that serves ([D4](../decisions.md), B1); ID's `db:migrate` provisions its runtime role's permissions but the login itself must exist first (`docs/06` § Install, step 1).
- The registrations are documented as cURL with fixed `Idempotency-Key`s: the Toolbox in `apps/web/content/docs/toolbox/index.mdx`, the admin MCP in `apps/web/content/docs/admin/setup.mdx`; the acceptance kit does the same through `packages/acceptance/src/admin-mcp.ts` and `src/admin.ts` (test support, not importable by production code).
- The root bearer works until a person holds `platform:write`; afterwards `register` needs a staff token ([`docs/06`](../../../06-deploying-answerable-id.md) step 7, `docs/admin/setup.mdx`).
- ID generates a `client_secret_basic` client's secret and returns it once in the creation response; a replayed idempotency key returns the receipt without it, and a lost secret means `POST /clients/:clientId/rotate-secret`, which revokes the client's tokens ([findings](../findings.md#what-has-to-run)). `register` stores the secret the moment the creation answers, and when the secret is missing from the store but the client exists, rotates and stores the new one.
- The AWS secret store is Secrets Manager; Terraform creates the secrets empty and the values come from here or from a person ([D7](../decisions.md)).

## What to build

- `infra/ops/src/bootstrap.ts`, `register.ts`, `secret-store.ts` (interface `SecretStore { get(name): Promise<string | undefined>; put(name, value): Promise<void> }`, `FileSecretStore` for the stack, `AwsSecretStore`), `cli.ts`, `Dockerfile` (same base and layout as the servers, `CMD ["bun", "infra/ops/src/cli.ts"]`), `README.md`.
- `register` prints what the admin lane prints: the Claude Code `claude mcp add` commands for the environment's admin MCP and Toolbox, with the right callback ports.
- The stack: profile `ops` with `ops-bootstrap` and `ops-register` services; `stack.test.ts` as above; `infra/docker/README.md` describing the stack and how to use it by hand (`bun run infra:up`, `infra:down`) to try Claude Code against the containers, mirroring the admin lane.
- Root scripts `infra:up` / `infra:down` for the hand-driven stack; `infra:test` already exists.

## Constraints

- No production code imports test support: `register` reimplements the few admin calls it needs with `fetch` (the docs' cURL), or `@answerable/id-admin` if its machine client can act with a bearer; it must not import `packages/acceptance`.
- Secrets never printed; errors name the secret's name, not its value.
- The idempotency keys are the docs' (`toolbox-resource-v1`, `admin-mcp-resource-v1`, `claude-code-admin-v1`, …); changing a definition means a new suffix in the docs and here together.
- `infra/ops` follows the MCP workspaces' style (no semicolons) and the 100% gate.
