# B3 — The ops image: database bootstrap and registration

**Executor:** Codex (GPT-6 Astra, medium); Fable reviews and lands. **Depends on:** B2. **Decisions:** [D4](../decisions.md), [D7](../decisions.md), [D10](../decisions.md), [D23](../decisions.md).

> **Revised 12 October 2026.** The `SecretStore` interface stands, but the production implementation is a **`KubernetesSecretStore`**, not AWS Secrets Manager: it reads and writes named `Secret`s in the release namespace through the Kubernetes API, from inside the Job, with a ServiceAccount whose Role allows `get`, `create` and `patch` on exactly the secret names it owns (`id-database`, `toolbox-database`, `admin-database`, `toolbox-id-client`, `admin-id-client`). `bootstrap` therefore resets a password it cannot find (the cluster, not a store, is where generated passwords live) and `register` rotates a client secret it cannot find, as already specified. The `FileSecretStore` stays for the kind stack. The `@aws-sdk/client-secrets-manager` implementation is not written now; it returns with External Secrets when a company store exists.

## Goal

Two idempotent commands that turn an empty Postgres and an empty ID into a working environment without a person typing SQL or cURL: `bootstrap` creates the databases and logins and puts their URLs in the secret store; `register` creates the MCPs' resources, machine clients, host clients and grants in ID per the docs and puts the client secrets in the store. Both run as one-off ECS tasks in AWS and inside the local stack, where the stack test proves the whole story: boot, bootstrap, migrate, register, a staff sign-in through the containers and a tool call on the admin MCP.

## Facts to start from

- Production needs three databases, each with an owner login that migrates and a runtime login that serves ([D4](../decisions.md), B1); ID's `db:migrate` provisions its runtime role's permissions but the login itself must exist first (`docs/06` § Install, step 1).
- The registrations are documented as cURL with fixed `Idempotency-Key`s: the Toolbox in `apps/web/content/docs/toolbox/index.mdx`, the admin MCP in `apps/web/content/docs/admin/setup.mdx`; the acceptance kit does the same through `packages/acceptance/src/admin-mcp.ts` and `src/admin.ts` (test support, not importable by production code).
- The root bearer works until a person holds `platform:write`; afterwards `register` needs a staff token ([`docs/06`](../../../06-deploying-answerable-id.md) step 7, `docs/admin/setup.mdx`).
- ID generates a `client_secret_basic` client's secret and returns it once in the creation response; a replayed idempotency key returns the receipt without it, and a lost secret means `POST /clients/:clientId/rotate-secret`, which revokes the client's tokens ([findings](../findings.md#what-has-to-run)). `register` stores the secret the moment the creation answers, and when the secret is missing from the store but the client exists, rotates and stores the new one.
- The AWS secret store is Secrets Manager; Terraform creates the secrets empty and the values come from here or from a person ([D7](../decisions.md)).

## Constraints

- No production code imports test support: `register` reimplements the few admin calls it needs with `fetch` (the docs' cURL), or `@answerable/id-admin` if its machine client can act with a bearer; it must not import `packages/acceptance`.

- The idempotency keys are the docs' (`toolbox-resource-v1`, `admin-mcp-resource-v1`, `claude-code-admin-v1`, …); changing a definition means a new suffix in the docs and here together.

## Notes from the build

Built per the revised block, on this Mac (Docker 28.3.2, kind 0.33.0 with Kubernetes 1.37.0, Helm 4.3.0, Bun 1.3.1; the stack's PostgreSQL is 17.11). How to run and change it: `infra/ops/README.md` and `infra/k8s/local/README.md`.

**What exists.**

- `infra/ops` (`@answerable/infra-ops`, 100% lines and functions):
  - `kubernetes.ts`: the in-cluster API client; Secrets by merge patch, create on 404; Deployments' replicas; field manager `answerable-ops`.
  - `secret-store.ts`: `createKubernetesSecretStore`, and `createFileSecretStore` for running outside a cluster.
  - `bootstrap.ts`, `register.ts`, and `commands.ts` (the `OPS_*` configuration and the exit codes); `cli.ts` is the entry alone.
  - `testing.ts`: in-memory Kubernetes, a secret store, and ID's admin API with idempotency per caller and key.
  - `Dockerfile`: the services' layout. The image is 218 MB and carries only `infra/ops/src` and `packages/mcp-postgres`.
- The chart's ops Jobs: `ops.yaml`, the ops NetworkPolicy, the replicas gate in `_server.tpl`, and the values.
- The stack runs the real story (below). It ships with `apps/id/scripts/stack-directories.ts` and a `hostname`/`port`/`origin` option on `src/__tests__/oidc-issuer.ts`.

**Where it differs from the text above.**

- **Store keys.** No AWS store and no `OPS_SECRET_PREFIX`. The store's keys are the conventions' Secret names and keys (`id-database`/`DATABASE_URL`, …, `toolbox-id-client`/`TOOLBOX_ID_CLIENT_SECRET`, `admin-id-client`/`ADMIN_ID_CLIENT_SECRET`).
- **Register's fake.** `register` is tested against its own fake of ID's admin API (`src/testing.ts`), not `@answerable/id-admin/testing`. That fake serves a server's machine client and has no `/resources`, `/clients`, rotation or root bearer.
- **The register calls.**
  - `register` makes the docs' calls with the docs' keys, in order (`toolbox/admin.mdx`, `admin/setup.mdx`), and leaves out the Toolbox's `toolbox-staff` client: its secret is the operator's and no Secret consumes it.
  - Both host clients get the docs' one callback port, `47700`; 47701 is only the admin lane's.
  - An object that exists under another key or caller (`409 conflict`, or `200` on a link PUT) counts as already there. Groups are found by slug after creation, because a replay answers the receipt, not the group.
- **Which token register uses.** `OPS_ID_TOKEN` comes from an optional `ops-staff-token` Secret; `OPS_ID_ROOT_SECRET` comes from `id-env`'s `ROOT_ADMIN_SECRET`, also optional. The command takes the staff token when there is one, and names both when neither is set. The chart needs no `lookup` for this, and the root secret goes unused once a staff token exists.
- **The servers wait for their client secret.** `toolbox` and `admin-mcp` render `replicas: 0` while their client Secret does not exist (Helm `lookup`), and `register` scales them to their replicas, or to `minReplicas` with autoscaling (`OPS_START_DEPLOYMENTS`).
  - Without this, a first install's `--wait` fails on pods that cannot read a missing Secret, and `--rollback-on-failure` undoes the release.
  - `helm template` has no cluster, so it always renders them at zero; the chart test says so.
- **RBAC.** The Role allows `get` and `patch` on exactly the Secrets of the Jobs switched on, plus `get` and `patch` on the Deployments `toolbox` and `admin-mcp` for `register`.
  - `create` on Secrets names no Secret, because Kubernetes cannot limit a create by name. A Job creates a Secret only after a read by name found none.
  - `trivy config` of the production overlay rendered with both Jobs on: 0 HIGH or CRITICAL findings.
- **Network.**
  - The ops NetworkPolicy renders whenever an ops image is named, not only when a Job is on. The Jobs are hooks, which run before the release's own resources, so a pre-upgrade `bootstrap` would otherwise find only `default-deny`.
  - `networkPolicy.kubernetesApi` is set per environment. Locally it is the `kubernetes` Service and `172.16.0.0/12`. On Civo it is any address on 6443, because Civo serves the API at a public endpoint (narrow it to the cluster module's `api_endpoint` when the overlay can carry it).
  - `id.extraEgress` is new, for a company directory on a private network.
- **Job settings.** `backoffLimit: 0`; `ttlSecondsAfterFinished: 86400`; the ServiceAccount mounts no token, and only the ops pods turn the token on.

- **The order.** Postgres starts with only `dbadmin` (`CREATEDB CREATEROLE`, not a superuser). Then:
  1. The install with `ops.bootstrap=true` creates the databases, logins and URL Secrets, then runs the migrations and starts ID.
  2. The upgrade with `ops.register=true` registers both servers and scales them up.
  3. A machine token for `admin-mcp` with `toolbox:admin` lists the Toolbox's providers.
  4. The platform organisation gets its domain and SSO provider through the admin API with root. A staff member signs in with the directory on the host, and the official MCP client calls `admin_whoami`: no role, then `owner` after root adds the membership to the owner group.
  5. Both Jobs run again in one upgrade and change no Secret's `resourceVersion`.
- **The ops Jobs.** `bootstrap` takes 4 s and `register` 4 s inside the upgrades. The first run of each wrote the expected log, and no log contains a generated value or the root secret (asserted).
- **Reaching the directory.** ID's pods reach the directory on the host at `host.docker.internal` as the kind node resolves it (192.168.65.254 on Docker Desktop), or at kind's network gateway on Linux. ID trusts both of its origins (`BETTER_AUTH_TRUSTED_ORIGINS`) and may reach it through `id.extraEgress`. Better Auth fetches only the token endpoint and the keys server-side, and they must be trusted origins because the address is private.

**Measured surprises for the next agent.**

- **Client certificates in Playwright under Bun.** Playwright's `clientCertificates` hang under Bun: the navigation never loads, while the same script under Node loads in 0.8 s. A Node-hosted `run-server` driven from Bun gave no answer within 120 s either. In the first full run, the test after the hung sign-in also hung, on a request that answers in 0.2 s on its own; the cause is not established, and the next run, with the proxy below, had neither. So the sign-in sends Chromium (`--host-resolver-rules`) to a small proxy in the test process on `[::1]:48443`, which forwards with the origin-pull certificate (`startBrowserEdge`).
- **Bun's fetch and Host.** Bun's `fetch` given an explicit `Host` header with a port fails with `ConnectionRefused`; the same request without it answers 200.
- **Lazy `Bun.SQL` queries.** A `Bun.SQL` query object passed to `expect(…).rejects` never ran and the test hung. Awaiting the query inside an `async` facade fixed it.
- **Coverage of a class.** For the coverage gate, Bun counts a class's implicit constructor as a function: an `extends Error {}` class left one function uncovered.
- **TLS in the URL.** Bun.SQL ignores `sslrootcert` in a URL; with `sslmode=verify-full` and the right CA it still refused ("unable to verify the first certificate"). With a `tls.ca` option and no `sslmode` it connected even with the wrong CA. `connect` in `@answerable/mcp-postgres`, which bootstrap uses, keeps `verify-full` and passes the CA, and the stack proves it.

**Civo Database versus the kind Postgres: what the first real bootstrap must confirm.**

In kind, the administrative login is ours: `CREATEDB CREATEROLE`, not a superuser, on PostgreSQL 17, with a server certificate naming the Service's DNS names. Civo's administrative user is Civo's. Run these against staging before trusting `bootstrap` there, then read `kubectl -n answerable logs job/ops-bootstrap`:

1. **Its attributes and version.** Run `select rolname, rolsuper, rolcreatedb, rolcreaterole from pg_roles where rolname = current_user` and `show server_version`. `bootstrap` needs `CREATEDB` and `CREATEROLE`. A superuser also works.
2. **Membership in the owner roles.** On PostgreSQL 16 and later, `GRANT <owner> TO current_user` lets a `CREATEROLE` login create a database owned by the owner. Kind accepts it. A service that restricts role membership would fail at that statement; the log names it.
3. **TLS.** Each URL connects with `sslmode=verify-full` to the host of the administrative URL, or to `database.host`. Kind's certificate names `postgres.database.svc.cluster.local`. If Civo's endpoint is a private IP, its certificate must carry that IP, or `database.host` must be a name it carries, and `postgres-ca` must hold Civo's CA. Otherwise every service refuses to start.
4. **The database the administrative URL names.** It is `postgres` in kind; Civo may give another default database.
5. **Attributes it cannot change.** Only a superuser can clear `SUPERUSER`, `REPLICATION` or `BYPASSRLS` on an existing role, so `bootstrap` refuses such a role rather than altering it. A fresh Civo database has none of ours.
6. **The API from the Jobs.** The ops Jobs reach the Kubernetes API from inside the cluster under Cilium and Civo's firewall:
   - The overlay's `kubernetesApi` admits any address on 6443. If Cilium gives the API server its `kube-apiserver` identity, which a plain `ipBlock` does not select, the Jobs time out on their first Secret read. The fix would then be a `CiliumNetworkPolicy` with `toEntities: [kube-apiserver]`.
   - In production, the cluster firewall admits 6443 only from `allowed_api_cidrs` (`infra/civo/README.md`), the same open question as the nodes'.

**For the integrator.**

- **First deploy.** `deploy --bootstrap` runs `bootstrap` only. The Toolbox and the admin MCP then stay at zero replicas, so the smoke test's two `/health` checks fail until `run-job register`. Both Jobs can run in the first upgrade instead: `register` is a post-install hook, ID is up by then, and the stack's last upgrade does exactly that. Consider making `--bootstrap` switch on `register` too.
- **Replicas after the first register.** With autoscaling, the first upgrade after `register` drops `replicas` from the manifest. With client-side apply, Kubernetes resets it to 1 until the HPA restores `minReplicas`: a dip once, not measured (the stack does not autoscale).
- **Secrets the sops files must hold.**
  - `postgres-admin`, key `OPS_DATABASE_ADMIN_URL`: the administrative URL, ending `?sslmode=verify-full&sslrootcert=/etc/ssl/db/ca.pem`.
  - `ops-staff-token`, key `OPS_ID_TOKEN`: added once root locks.
