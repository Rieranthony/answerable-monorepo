# B4 — The chart (B4a) and the cloud roots (B4b)

**Executor:** Codex (GPT-6 Astra, medium); Fable reviews and lands. **Depends on:** B4a on B3; B4b on B0 and B4a. **Decisions:** [D3](../decisions.md) to [D7](../decisions.md), [D12](../decisions.md), [D14](../decisions.md), [D18](../decisions.md) to [D27](../decisions.md).

> **Revised 10 October 2026 for portability** ([`portability.md`](../portability.md)). The AWS-specific text further down (ALB, ECS services, task definitions, SSM image parameters) is superseded; it stays for the record of what the Fargate design would have been and for the parts B4b's AWS root reuses (network, RDS, secrets, monitoring budget, the `edge` module). The brief is now two:
>
> **B4a — the chart.** `charts/answerable`: a `Deployment` per service (`id` from `dist/server.js`, `toolbox`, `admin-mcp`) with `readinessProbe` on `/readyz` or `/health`, `livenessProbe` on `/healthz` or `/health`, resource requests and limits from values, `securityContext` (non-root, read-only root filesystem, no capabilities, seccomp `RuntimeDefault`), `topologySpreadConstraints` across nodes, a `RollingUpdate` strategy with `maxUnavailable: 0`; a `HorizontalPodAutoscaler` per service (CPU 60%, min and max from values); a `PodDisruptionBudget` of one; `NetworkPolicy` allowing ingress only from ingress-nginx and egress only to the database, DNS, ID's hostname and the identity providers; a `Service` per Deployment; an `Ingress` per hostname with the `auth-tls-*` annotations pointing at the environment's origin-pull CA secret and cert-manager's issuer annotation; `Job`s: `id-migrate`, `toolbox-migrate`, `admin-migrate` as `pre-upgrade` hooks ordered by weight, each mounting only its owner-URL secret, and `ops-bootstrap`, `ops-register` as `post-install`-weighted Jobs that run when a value enables them, with the ServiceAccount and Role from B3's note; **no `ExternalSecret`s** (D23, revised 12 October): the chart references Secrets by name (`existingSecret` values), the human-provided ones applied by the deploy workflow from the `sops` file and the generated ones written by the Jobs; `values.yaml` with environment and cloud overlays (`values-civo-staging.yaml`, …) carrying the image tag, hostnames, `TRUSTED_PROXY_CIDRS`, the Postgres CA mounting (a `ConfigMap` from the provider's bundle), replicas and sizes. `charts/platform`: ingress-nginx, cert-manager (with a `ClusterIssuer` for Let's Encrypt DNS-01 through the zone's Cloudflare token, a Secret from the `sops` file), the Grafana `k8s-monitoring` agent, pinned as chart dependencies with values; External Secrets Operator is not installed (D23). Tests: `helm lint`, `helm template` rendered for every values file and checked with `kubeconform` against the pinned Kubernetes version, policy checks with `trivy config` (no privileged pod, no `latest` tag, requests set, NetworkPolicy present), and the kind install from B2 extended to run the Jobs and the ExternalSecrets with a fake store. `bun run infra:check` gains Helm lint and `kubeconform`.
>
> **B4b — the cloud roots** (Civo's two roots are built and applied, one per Civo account, per [D28](../decisions.md); the AWS and Google roots are written and `terraform validate`d only), each a small Terraform root per environment that provides the same outputs (cluster kubeconfig or endpoint, database host and CA, load balancer firewall, state) and runs the `kubernetes` and `helm` providers to install `charts/platform` and create the `deployer` ServiceAccount, its namespace-scoped `Role` and a bound token stored as a GitHub environment secret by the owner:
> - `infra/civo/envs/<env>`: `civo_network`, `civo_firewall` for the cluster (6443 from the owner's addresses; nothing else inbound), `civo_kubernetes_cluster` (CNI Cilium, the Traefik marketplace app removed, node pool of Standard Medium nodes, count from values, in LON1), `civo_database` (PostgreSQL 17, size from values, in the private network, with a firewall admitting 5432 from the cluster's nodes only, additional nodes for production once their price is known), the load balancer firewall admitting 443 from Cloudflare's ranges (attached through the Service annotation `kubernetes.civo.com/firewall-id` in the platform values), a `civo_object_store` for state, the Cloudflare records to the load balancer's reserved IP (`civo_reserved_ip`), and the deployer ServiceAccount. Measured in this brief: whether the Civo load balancer passes the client address (PROXY protocol or `externalTrafficPolicy: Local`), and whether the object store accepts Terraform's lockfile writes.
> - `infra/aws/envs/<env>`: the `network`, `database` (PostgreSQL 17), `secrets` (only if the AWS store is chosen), `monitoring` (budget, the RDS alarms) and `edge` modules from the original text; EKS (standard, managed node group of Graviton nodes, private endpoint, IRSA for External Secrets if used; Auto Mode is a priced option) in place of the ECS modules; a Network Load Balancer created by the platform chart's Service with the AWS Load Balancer Controller or the in-tree provider, its security group from Cloudflare's ranges; the OIDC deploy role reduced to EKS access for the `deployer` identity; S3 state as before.
> - `infra/google/envs/<env>`: VPC, GKE Autopilot (private nodes), Cloud SQL PostgreSQL 17 with private IP, a TCP load balancer firewall rule from Cloudflare's ranges, Workload Identity Federation for GitHub, GCS state. Written and `terraform validate`d; applied only when the owner chooses Google.
> `infra/README.md` documents the portable core once and each cloud's root in its own section.

## Goal

`terraform apply` in `infra/aws/envs/staging` creates everything one environment needs, from the VPC to the alarms, with no value typed by hand except `terraform.tfvars`; `envs/production` is the same modules with production sizes. `bun run infra:check` keeps it formatted, valid, linted and policy-clean without cloud access, and runs in CI.

## Constraints

- No value that is a secret, an account ID or a role ARN in `.tf` files: account IDs and ARNs come from `terraform.tfvars` (committed; they are not secrets) or data sources, the Cloudflare token from the environment.
- Every resource tagged through `default_tags`; names prefixed `answerable-<env>-`.
- No `aws_iam_policy_document` with `*` on resources except where the API has no resource-level permissions (list them in the module README).
- Terraform's native tests and `trivy config` must both run with no network and no credentials.
- Exact provider pins and a `.terraform.lock.hcl` committed per root with hashes for `darwin_arm64` and `linux_amd64` and `linux_arm64` (`terraform providers lock -platform=…`).

### B4b (13 October 2026)

Built and proved without a Civo account or a Cloudflare token: `terraform init -backend=false`, `validate`, `terraform test` with mocked providers, `tflint`, `trivy config`. Nothing was planned against a real account; the runbook and the first-apply questions are in [`infra/civo/README.md`](../../../../infra/civo/README.md).

**What landed.** `infra/civo/modules/{network,cluster,database,ingress-firewall,state,platform,deployer,edge}`, the roots `infra/civo/envs/{staging,production}` (identical `.tf` files except `backend.tf`; `terraform.tfvars` differs), a lock file per root with hashes for `darwin_arm64`, `linux_amd64` and `linux_arm64`, `infra/.terraform-version` (1.16.5), `infra/.tflint.hcl` (the bundled Terraform ruleset, preset `all`), `infra/.trivyignore` (empty), `infra/check.ts` behind `bun run infra:check`, and the `infra-check` job in `ci.yml`. Fifty `terraform test` runs across ten directories, all `command = plan`. `infra:check` takes about 30 seconds warm.

**What differed from the brief.**
- **Resource names.** In `civo/civo` 1.3.3, `civo_network`, `civo_firewall` and `civo_reserved_ip` are deprecated aliases. The modules use `civo_vpc_network`, `civo_vpc_firewall` and `civo_vpc_reserved_ip`.
- **A `platform` module.** It holds the `answerable` and `platform` namespaces and the `helm_release` of `charts/platform`, which the revised text asks the root to install. The module list in the build brief left it out. The release must use the cluster's admin credential because the chart carries cluster-wide objects. Terraform sets three values the chart must accept: `ingress-nginx.controller.service.annotations` `kubernetes.civo.com/firewall-id` and `kubernetes.civo.com/ipv4-address`, and `ingress-nginx.controller.config.proxy-real-ip-cidr`.
- **The restricted Pod Security Standard is enforced** on `answerable`. Every pod and Job in `charts/answerable` must run as non-root with `allowPrivilegeEscalation: false`, all capabilities dropped and seccomp `RuntimeDefault`. The kind stack should label its namespace the same way, so the local proof matches Civo.
- **Firewalls.** The cluster firewall also admits the private network's own range (TCP and UDP), because the load balancer reaches the node ports and the nodes reach one another over it. The load balancer's and the database's outbound traffic is limited to the private network. Each of these is a first-apply question.
- **`allowed_api_cidrs`** is neither in `terraform.tfvars` nor printed in plans. It is set as `TF_VAR_allowed_api_cidrs`, the variable is `sensitive`, and the module refuses `0.0.0.0/0`, because an operator's address is personal data in a public repository.
- **Traefik.** The cluster removes `Traefik-v2-nodeport`, the name in Civo's CLI documentation; the provider's own example says `-Traefik`. A postcondition on `installed_applications` fails the apply if Traefik is installed anyway.
- **Providers.** `hashicorp/kubernetes` 3.3.0 and `hashicorp/helm` 3.3.0 are both majors past 2.x; after both v3 upgrade guides, the modules use the versioned `_v1` resources and Helm's `kubernetes = { … }` object. `hashicorp/random` is not used; tflint would flag an unused provider.

**Facts measured.**
- `cloudflare_ip_ranges` exists in 5.27.0, with `ipv4_cidrs`, `ipv6_cidrs` and `etag`; no `http` data source is needed.
- Cloudflare's configuration rules need **Zone > Config Rules > Edit** and cache rules **Zone > Cache Rules > Edit**, on top of B0's four token permissions ([config rules API](https://developers.cloudflare.com/rules/configuration-rules/create-api/), [cache rules API](https://developers.cloudflare.com/cache/how-to/cache-rules/create-api/)). Bot Fight Mode is `cloudflare_bot_management.fight_mode`, which needs Bot Management Edit, so it stays a dashboard toggle.
- `civo_database` has no CA certificate attribute, so the `postgres-ca` ConfigMap cannot come from Terraform. It keeps the administrator's `username` and `password` in state. `civo_kubernetes_cluster` keeps the admin kubeconfig there once `write_kubeconfig = true`, which this root needs. "Terraform holds no value" (D7) therefore cannot hold on Civo: the state bucket is private and its credential is the infra environment's. Nothing outputs the database password; how `bootstrap` receives it is B3's call.
- Civo load balancer annotations, from the [Civo docs](https://www.civo.com/docs/networking/load-balancers/creating-load-balancers) and the [cloud controller manager](https://github.com/civo/civo-cloud-controller-manager): `firewall-id`, `ipv4-address` (an address or a reserved address's name), `loadbalancer-enable-proxy-protocol`, `server-timeout` and `client-timeout` (both 60 s by default). PROXY protocol is not configured, so `trusted_proxy_cidrs` includes the private network's range.
- Civo object store endpoint `https://objectstore.<region>.civo.com`, path-style ([adding files](https://www.civo.com/docs/object-stores/adding-files-to-object-stores)). Whether it accepts `use_lockfile` stays unmeasured; the README's step 4 measures it and gives the fallback.
- **GitHub-hosted runners cannot be admitted to the API firewall.** The `actions` list at `api.github.com/meta` has 5,508 IPv4 ranges. B5's deploy job, and any CI `terraform apply` of these roots (the kubernetes and helm providers call the API), needs a fixed egress address or an owner decision to open 6443. This is in the README under "Not yet".
- Trivy 0.75.0 has no checks for Civo or Cloudflare resources and reports 0 findings on the roots, so the policy lives in the Terraform tests. `infra:check` runs trivy with its embedded checks (`--skip-check-update`), which keeps the gate deterministic.

**Second delta, after an independent review (13 October 2026).**
- **The cluster firewall's rules from the private network.** They spanned every TCP and UDP port, 6443 included. They are now the named ports only:
  - TCP 30000-32767: Kubernetes' NodePort range, for the load balancer;
  - TCP 10250: the kubelet;
  - UDP 8472: Cilium's VXLAN tunnel;
  - TCP 4240 and ICMP: cilium-health.

  The sources are the [k3s inbound rules](https://docs.k3s.io/installation/requirements#inbound-rules-for-k3s-nodes), [Cilium's firewall rules](https://docs.cilium.io/en/stable/operations/system_requirements/#firewall-rules) and the [Kubernetes NodePort range](https://kubernetes.io/docs/concepts/services-networking/service/#type-nodeport), cited in `modules/cluster/README.md`. 6443 now answers `allowed_api_cidrs` and `api_open_to_internet` only. The tests pin the exact set of rules from the network and fail on any such rule that reaches 6443 or spans every port.
  - Two new first-apply questions in the runbook. k3s says its server's 6443 must be "accessible by all nodes", and Civo runs the control plane without documenting whether nodes reach it through this firewall, so production (whose API is closed) must show its nodes Ready. `kubectl logs` and `exec` need the control plane to reach 10250.
- **The database still admits the private network.** "Nodes only" cannot be expressed on Civo. Firewall rules are CIDRs. The provider exposes no node address, only `instance_names`. `civo_kubernetes_cluster` and `civo_kubernetes_node_pool` take a `network_id` and nothing narrower. `civo_vpc_subnet` takes no range. Checked in the provider schema: no 1.3.3 resource has a `subnet_id`. A pool in a separate network could not reach the database. `modules/database/README.md` and a new "Known limits" section in `infra/civo/README.md` record what is on that network: the nodes, the load balancer (which forwards only 443 to the node port) and the database.
- **The deployer reads no other namespace.** `read_namespaces` already defaulted to `[]`; both roots now pass `[]` too, the module test checks the default grants nothing, and a new `read_namespaces` output lets the root tests check it. The variable stays for a future diagnostic.
- **`allowed_api_cidrs` defaults to `[]` in both roots**, so runs with `-input=false` never stop to ask for it. A validation in the roots (and the module's own) fails the plan when it is empty and the API is closed: staging plans without it, production does not. Root tests cover both.
