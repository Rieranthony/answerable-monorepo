# B2 — Containers and the production-shaped local stack

**Executor:** Codex (GPT-6 Astra, medium); Fable reviews and lands. **Depends on:** B1. **Decisions:** [D5](../decisions.md), [D9](../decisions.md), [D13](../decisions.md), [D21](../decisions.md), [D22](../decisions.md), [D26](../decisions.md).

> **Revised 10 October 2026 for portability.** The images section stands as written. The local stack is no longer Docker Compose with Caddy: it is a **`kind` cluster** (`infra/k8s/local`, workspace `@answerable/infra-k8s`) running the real chart from B4a with the platform pieces, so the local proof exercises what production runs. Until B4a exists, this brief writes the first version of the chart's three Deployments, Services and Ingresses itself, minimal, and B4a completes it. Concretely:
> - `kind` with a config that maps ports 48443 (ingress HTTPS) and a loopback Postgres port; a PostgreSQL 17 StatefulSet with `ssl=on`, `hostnossl … reject` and a certificate from a stack CA (a cert-manager self-signed `ClusterIssuer` issues both the Postgres certificate and the ingress certificates, so the test trusts one CA); ingress-nginx with `use-forwarded-headers`, `compute-full-forwarded-for: "true"`, `proxy-real-ip-cidr` set to the kind node range, and `auth-tls-*` verifying a stack-issued "Cloudflare" client certificate; the chart installed with `values-local.yaml` (`NODE_ENV=production`, `BETTER_AUTH_URL=https://localhost:48443`, `TRUSTED_PROXY_CIDRS` = the kind ranges, `TOOLBOX_HOST=0.0.0.0`, the images built locally and loaded with `kind load`).
> - The same proofs as the compose version (health, discovery, JWKS, ingress refusal when bypassing the ingress through a direct port-forward, Toolbox metadata and 401, TLS-only Postgres with `verify-full` from both drivers, first-start provisioning), plus: a request without the client certificate is refused by ingress-nginx with 400, and a forged `X-Forwarded-For` through the ingress does not change the address ID resolves (read it back through the audit API with the root secret).
> - Secrets in the local stack are plain Kubernetes Secrets the test creates; the ExternalSecrets of the chart are disabled by a value (`secrets.external=false`).
> - `bun run infra:test` creates and deletes the kind cluster around the run; CI installs `kind` and `helm` at pinned versions on `ubuntu-24.04-arm`.
> The `infra/docker` workspace is not created. The "sidecar forwarder" trick is unnecessary: inside the cluster the issuer `https://localhost:48443` is reached through a `Service` named by an `/etc/hosts` entry in the pods (`hostAliases` mapping `localhost`'s stand-in hostname to the ingress service) or, simpler, the local hostname is `id.answerable.localhost`-style only if the test runner resolves it; B2 measures which works on macOS and Linux and records it in [`findings.md`](../findings.md).

## Goal

Three images that run ID, the Toolbox and the admin MCP exactly as production will (non-root, read-only, `NODE_ENV=production`, verified TLS to Postgres, restricted logins, behind a TLS-terminating proxy that sets `x-forwarded-for`), and a local Docker stack plus a `bun test` that builds them and proves ID and the Toolbox through the proxy. B3 extends the same test to the admin MCP and a sign-in.

## Facts to start from

- ID builds to `dist/server.js` with `hono-tailwind` external and reads `dist/tailwind.css` next to its pages at runtime (`apps/id/src/http/pages/index.ts:66`); the Toolbox imports `mcps/e2e/dist/records.html` at load, so its image must run the e2e build; both MCPs bind `127.0.0.1` ([findings](../findings.md#what-has-to-run)).
- `pg` honours `sslmode=verify-full&sslrootcert=<file>` in the URL; `Bun.SQL` exposes a `tls` option and its types say nothing about URL parameters ([findings](../findings.md#database-tls-from-the-services)).
- ID refuses a production request whose address cannot be resolved through `TRUSTED_PROXY_CIDRS` with `403 untrusted_ingress`, except health and readiness.
- Precedent for a container reaching a host-visible URL at the same address the host uses: the host lane's `bridge` service forwards loopback ports inside the LibreChat container to `host.docker.internal` (`packages/acceptance/host-lane/compose.yaml`).
- GitHub's arm64 runners are free for this repository; Docker 28 with BuildKit is on this machine and on the runners.

## Failing tests first

`infra/docker/stack.test.ts`, workspace `@answerable/infra-docker` (test support, no coverage gate), run by `bun run infra:test`:

1. `docker compose build` of the three images succeeds; each image's `USER` is not root and its root filesystem is read-only in compose (`read_only: true`, `tmpfs: /tmp`).
2. `up --wait` brings up TLS-only Postgres, Caddy, then (after the migrate containers exit 0) ID and the Toolbox healthy.
3. Through the proxy: ID `/healthz` and `/readyz` answer `ok`; `/.well-known/openid-configuration` has `issuer` equal to `BETTER_AUTH_URL`; `/auth/jwks` has a key; `GET /auth/get-session` without a cookie answers through the ingress (not 403). Direct to ID's container port (published on loopback for the test only): `/auth/get-session` answers `403 untrusted_ingress`; `/healthz` still answers.
4. Through the proxy: the Toolbox `/health` is `ok`; `GET /mcp` without a token answers `401` with a `WWW-Authenticate` naming `/.well-known/oauth-protected-resource/mcp`; that document names ID as the authorization server.
5. A plain-TCP connection to Postgres is refused (`hostnossl ... reject`) and a `verify-full` connection with the stack's CA succeeds, from a one-off container running each service's own driver: `pg` for ID's URL shape and `Bun.SQL` for the MCPs' (this is the measurement [findings](../findings.md#open-facts-a-brief-must-measure) asks for; record the answer there).
6. ID's log lines contain `platform organisation answerable: provisioned`, and a second `up` prints `verified`.

## What to build

### Images

- `apps/id/Dockerfile`, `mcps/toolbox/Dockerfile`, `mcps/admin/Dockerfile`, build context the repository root, `.dockerignore` at the root (`node_modules`, `.git`, `coverage`, `.next`, `.turbo`, `**/dist` except what the build stage produces, `.env*`).
- Stages: `base` from `oven/bun:1.3.1-slim@sha256:<digest>` (record the digest in the Dockerfile; Debian slim, not Alpine, [D9](../decisions.md)); `install` copies every `package.json` and `bun.lock` and runs `bun install --frozen-lockfile`; `build` copies the sources and runs `bun run --filter @answerable/id build` (ID) or `bun run --filter @answerable/mcp-e2e build` (Toolbox); `runtime` copies the installed workspace and build output, drops dev dependencies with `bun install --frozen-lockfile --production` (try `--filter <workspace>` first and keep it only if the image boots; record the image sizes either way), adds the RDS bundle from `https://truststore.pki.rds.amazonaws.com/global/global-bundle.pem` at `/etc/ssl/rds/global-bundle.pem` with its SHA-256 pinned in the Dockerfile (the download fails the build when the hash moves; bump deliberately), sets `USER bun`, `ENV NODE_ENV=production`, `WORKDIR /app`, and `CMD` of `bun apps/id/dist/server.js`, `bun mcps/toolbox/src/server.ts`, `bun mcps/admin/src/server.ts`. OCI labels `org.opencontainers.image.source`, `.revision` (build arg) and `.title`.
- The migrate commands run from the same images: `bun apps/id/scripts/migrate.ts`, `bun mcps/toolbox/scripts/migrate.ts`, `bun mcps/admin/scripts/migrate.ts` (so the migrate scripts and their dependencies stay in the runtime stage; ID's `drizzle/` directory too).
- Bind hosts: `TOOLBOX_HOST` and `ADMIN_HOST` in the two `environment.ts` schemas, default `127.0.0.1`, set to `0.0.0.0` by the images' `ENV`; `default.env`, `.env.example` and the two docs configuration tables gain the variable. ID already listens on every interface.
- `Bun.SQL` TLS: after proof 5, either document the URL shape that works, or add `connect(url)` to `@answerable/mcp-postgres` that reads `sslmode` and `sslrootcert` from the URL and passes `tls: { ca }`, used by both servers and both migrate scripts; tested in `mcp-postgres` with a fake file. Record the outcome in [`findings.md`](../findings.md).

### The stack, `infra/docker`

- `compose.yaml` on a fixed network `10.47.0.0/24`: `postgres` (`postgres:16-alpine`, `ssl=on`, a `pg_hba.conf` with `hostssl all all all scram-sha-256` and `hostnossl all all all reject`, the server certificate issued at first start by an `openssl` init container from a stack CA kept in a named volume), `caddy` (TLS from its internal CA for `localhost`, HTTPS on `48443`, `48444`, `48445` on the host, `reverse_proxy` to `id:47300`, `toolbox:47400`, `admin-mcp:47520`; Caddy adds `X-Forwarded-For` and `X-Forwarded-Proto` and keeps `Host`), `id`, `toolbox`, `admin-mcp` with `read_only: true`, `tmpfs: /tmp`, `cap_drop: [ALL]`, no published ports except ID's loopback port for proof 3, and each MCP container paired with a loopback forwarder in its network namespace (`network_mode: service:toolbox`, a `bun -e` TCP forwarder as the host lane does) so that `https://localhost:48443` is ID inside the container as well as on the host: one issuer string everywhere. Profiles `migrate` (`id-migrate`, `toolbox-migrate`, `admin-migrate`, owner URLs) and `ops` (B3).
- `env/` files per service with production values: `NODE_ENV=production`, `BETTER_AUTH_URL=https://localhost:48443`, `BETTER_AUTH_TRUSTED_ORIGINS` with the stack's directory origins (B3), `TRUSTED_PROXY_CIDRS=10.47.0.0/24`, `DATABASE_URL=postgres://answerable_id_runtime:…@postgres/answerable_id?sslmode=verify-full&sslrootcert=/etc/ssl/stack/ca.pem` (the stack CA mounted read-only where the image expects a bundle; the same path convention as RDS so the URL shape is identical), the ID secrets generated into a git-ignored `.env.stack` by the test (never committed), `TOOLBOX_HOST=0.0.0.0`, and so on. The admin MCP exits until B3 registers it; in B2 compose starts it with `restart: on-failure` and the test does not wait for it.
- `stack.test.ts` drives `docker compose -p answerable-stack`, exports Caddy's root CA to a temp dir and sets `NODE_EXTRA_CA_CERTS` for its own fetches, and tears everything down including volumes on exit and Ctrl-C (reuse `packages/acceptance/src/cleanup.ts`'s pattern).
- Root `package.json`: workspace `infra/*`, script `infra:test` → `bun run --filter @answerable/infra-docker test`; `turbo.json`: `@answerable/infra-docker#test` with `cache: false`; `knip.json` workspace entry.
- CI: a job `containers` in `ci.yml` on `ubuntu-24.04-arm` running `bun run infra:test`, needing `validate` (so a red suite never builds images).

## Constraints

- Ports: the stack owns `48443`–`48445` and a loopback ID port; add them to the README's port table.
- Never two stacks at once (fixed project name); never beside the acceptance's Postgres (different ports, so this one is allowed).
- No semicolons in `infra/*`; Prettier as the MCP workspaces.
- The images contain no `.env`, no test files, no coverage, no git metadata.
- `bun run mcp:test:e2e` and every existing gate stay green.
