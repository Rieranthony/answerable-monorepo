> - The same proofs as the compose version (health, discovery, JWKS, ingress refusal when bypassing the ingress through a direct port-forward, Toolbox metadata and 401, TLS-only Postgres with `verify-full` from both drivers, first-start provisioning), plus: a request without the client certificate is refused by ingress-nginx with 400, and a forged `X-Forwarded-For` through the ingress does not change the address ID resolves (read it back through the audit API with the root secret).
> - Secrets in the local stack are plain Kubernetes Secrets the test creates; the ExternalSecrets of the chart are disabled by a value (`secrets.external=false`).
> - `bun run infra:test` creates and deletes the kind cluster around the run; CI installs `kind` and `helm` at pinned versions on `ubuntu-24.04-arm`.
> The `infra/docker` workspace is not created. The "sidecar forwarder" trick is unnecessary: inside the cluster the issuer `https://localhost:48443` is reached through a `Service` named by an `/etc/hosts` entry in the pods (`hostAliases` mapping `localhost`'s stand-in hostname to the ingress service) or, simpler, the local hostname is `id.answerable.localhost`-style only if the test runner resolves it; B2 measures which works on macOS and Linux and records it in [`findings.md`](../findings.md).

## Goal

Three images that run ID, the Toolbox and the admin MCP exactly as production will (non-root, read-only, `NODE_ENV=production`, verified TLS to Postgres, restricted logins, behind a TLS-terminating proxy that sets `x-forwarded-for`), and a local Docker stack plus a `bun test` that builds them and proves ID and the Toolbox through the proxy. B3 extends the same test to the admin MCP and a sign-in.

- ID builds to `dist/server.js` with `hono-tailwind` external and reads `dist/tailwind.css` next to its pages at runtime (`apps/id/src/http/pages/index.ts:66`); the Toolbox imports `mcps/e2e/dist/records.html` at load, so its image must run the e2e build; both MCPs bind `127.0.0.1` ([findings](../findings.md#what-has-to-run)).

- Precedent for a container reaching a host-visible URL at the same address the host uses: the host lane's `bridge` service forwards loopback ports inside the LibreChat container to `host.docker.internal` (`packages/acceptance/host-lane/compose.yaml`).
- GitHub's arm64 runners are free for this repository; Docker 28 with BuildKit is on this machine and on the runners.

**`Bun.SQL` and TLS, the answer.** Bun 1.3.1 reads `sslmode` from the URL: `require` encrypts without checking, `verify-ca` checks the chain, `verify-full` the chain and the host name. It **ignores `sslrootcert`**, so a `verify-full` URL naming a private certificate authority fails every handshake ("unable to verify the first certificate"). It also **forwards the unknown parameter to the server as a startup setting**, which Postgres refuses (`unrecognized configuration parameter "sslrootcert"`). `tls: { ca }` in the options works and checks both chain and host. Hence `connect(url)`: it reads the file into `tls.ca`, strips the parameter, and refuses `sslrootcert` without `verify-full` or `verify-ca`. The stack proves it from the Toolbox's pod against the TLS-only PostgreSQL:
- `connect` gives `ssl=true`;
- `sslmode=disable` is refused by `pg_hba` ("no encryption");
- `sslrootcert` naming another CA is refused ("unable to verify");
- `new SQL(url)` without `connect` is refused.

`pg` in ID honours `verify-full` and `sslrootcert` from the URL, as findings said; the same three checks pass from ID's pod. `NODE_EXTRA_CA_CERTS` also makes `Bun.SQL` and `fetch` trust a CA, but process-wide. The stack therefore gives the database its own CA, separate from the edge's, so the edge's trust cannot mask the database check. One anomaly: in the very first probe, a wrong `tls.ca` connected once. It did not reproduce in seven later runs.

The upgrade path, the hooks re-running on `helm upgrade`, was exercised by hand.

**Hostnames, the scheme that worked.** On the host, the names are `id.127-0-0-1.sslip.io`, `toolbox.…` and `admin-mcp.…` at `:48443`. Public DNS resolves them to 127.0.0.1 on this Mac (and should on the runner, which has public DNS), where kind publishes ingress-nginx's host port. Inside the cluster, the pods' `hostAliases` map the three names to the edge Service at a fixed ClusterIP (10.96.48.43); Bun honours `/etc/hosts`. Measured against `*.localhost`: Bun's `fetch` resolves it on macOS, but `Bun.dns.lookup` does not. On Linux, Bun special-cases `.localhost` to `::1` only (ConnectionRefused for a server on 127.0.0.1), so it is unusable on the runner unless `/etc/hosts` names it. The scheme therefore relies on sslip.io's public DNS on the host side.

**The stand-in edge and `TRUSTED_PROXY_CIDRS`.** In-cluster callers (the Toolbox calling ID's issuer) cannot pass ingress-nginx without the origin-pull certificate, so the stack needs Cloudflare's part. It is an nginx beside the controller, in the controller's pod, added once cert-manager has issued its certificates. It terminates TLS for the public names, presents the client certificate, appends the caller to `X-Forwarded-For`, and connects to the controller on 127.0.0.1. Measured with an echo server:
- the host's requests reach the controller from the Docker gateway (172.25.0.1 here);
- a pod through the controller's ClusterIP arrives as its own pod IP;
- through the node's host port it arrives as 10.244.0.1;
- a hostNetwork pod arrives as the node IP.

So **locally `TRUSTED_PROXY_CIDRS` is `127.0.0.1/32` only**. Trusting the pod range, as the Civo values do, would leave every in-cluster call through the edge with no untrusted address, and ID would answer 403. In a cloud that is harmless, because pods reach ID through Cloudflare from the nodes' public address. The `sslip.io` names, the edge and `127.0.0.1/32` exist only in `values-local.yaml` and `infra/k8s/local`.

**Found on the way.**
- **Service links.** Kubernetes sets `TOOLBOX_PORT=tcp://<ip>:47400` in every pod of a namespace with a Service named `toolbox`, which overrode the image's `TOOLBOX_PORT` and crashed the Toolbox (`expected number, received NaN`). Every pod in the chart now has `enableServiceLinks: false`, and the chart test asserts it.
- **Host ports on one node.** On a single node with host ports, ingress-nginx's default rolling update never schedules the new pod, so the local controller is `Recreate`.
- **Bun's `fetch` and resumed sessions.** In one process, a request without a client certificate after one with it got 200, even with keep-alive off; a fresh process gets 400. That is consistent with TLS session resumption. The negative checks run in a fresh process.
- **ID's health bodies.** `/healthz` and `/readyz` answer `{"status":"ok"}`, not `ok`.
- **kindnet enforces NetworkPolicy** in kind 0.33.0, so the chart's policies are really exercised.

**Before B1 merges.** The stack runs the Toolbox and the admin MCP on their owner logins, through one switch: `database.mcpOwnerLogins: true` in `charts/answerable/values-local.yaml`. Set it to `false` once B1's migrate scripts read `*_DATABASE_MIGRATION_URL`. The stack already creates `answerable_toolbox_runtime` and `answerable_admin_runtime` and their Secrets.
