# B5 — Pipeline: push to deploy, one click to production

**Executor:** Codex (GPT-6 Astra, medium); Fable reviews and lands. **Depends on:** B4a, B4b. **Decisions:** [D8](../decisions.md) to [D10](../decisions.md), [D16](../decisions.md), [D24](../decisions.md), [D25](../decisions.md).

> **Revised 10 October 2026 for portability.** The shape stands; the mechanics change:
> - **Images go to GHCR** (`ghcr.io/rieranthony/answerable/<service>:sha-<sha>`, public, with `provenance: mode=max`, `sbom: true` and a keyless cosign signature), not to ECR; the `images` job needs `packages: write` and `id-token: write` only.
> - **Secrets step before the deploy** (D23): `sops --decrypt infra/civo/envs/<env>/secrets.enc.yaml | kubectl apply -n answerable -f -`, with `SOPS_AGE_KEY` from the GitHub environment and `sops` and `age` installed at pinned versions; the decrypted text never touches disk or the log (`set +x`, piped). The file is a list of `Secret` manifests, so what the deploy applies is exactly what a reviewer saw encrypted in the pull request.
> - **Deploy is `helm upgrade --install answerable charts/answerable --atomic --wait --timeout 10m -f values-<cloud>-<env>.yaml --set image.tag=sha-<sha>`**: the pre-upgrade migration Jobs run first by Helm's ordering, `--atomic` rolls back on failure. The `deploy.ts` script from the original text becomes a thin wrapper that logs in to the cluster, runs Helm, and prints the Jobs' logs on failure; `smoke.ts` is unchanged.
> - **Cluster login per cloud**: Civo and every other cloud through the `deployer` ServiceAccount token stored as the environment's secret (`KUBE_TOKEN`, `KUBE_SERVER`, `KUBE_CA`); AWS may use OIDC to the EKS role instead; Google may use Workload Identity Federation. The `infra` workflow keeps the cloud credentials (Civo API key on the protected environment, AWS OIDC apply role, Google WIF) because Terraform needs them; the deploy workflow never has them.
> - `ops.yml` runs `register` by enabling the Job through a Helm value for one upgrade (`--set ops.register=true`), then restarts the two MCP Deployments so they read the client secrets the Job wrote.
> - The SSM image parameters and the `amazon-ecs-*` actions are gone; the image tag lives in the Helm release, and `helm history` is the deploy log. Rollback is `helm rollback` or a redeploy of an earlier tag.
> - Branch protection, environments and concurrency as written; the GitHub environments are `staging` and `production` ([D28](../decisions.md): Civo), `production` with the owner as required reviewer; each carries its Civo account's cluster credentials for the deploy (the `deployer` token) and, on the protected `production` environment and an `infra-staging` environment, the Civo API key for Terraform.

## Goal

A push to `main` that passes CI builds the images once, stages them in both registries, migrates and deploys staging, and smoke-tests it; a reviewed click does the same to production with the digest staging runs; infrastructure changes plan on pull requests and apply on `main` for staging, and only through the click for production; `register` is a click too.

## Facts to start from

- CI already runs the whole suite including `mcp:test:e2e` in about 15 minutes on `ubuntu-latest` (`.github/workflows/ci.yml`); the arm64 runners are free ([findings](../findings.md#this-machine-and-these-accounts-8-october-2026)).
- B0 created the roles and their trust: `github-plan` for pull requests and `main`, `github-apply` and `github-deploy` for the environments, `github-ecr-push` in production for `main`.
- Terraform ignores the services' `task_definition` and reads the image from SSM ([D11](../decisions.md)); migrations are one-off tasks from the same image ([D10](../decisions.md)); `bootstrap` is idempotent (B3).

## Failing tests first

Workflows have no unit tests; `actionlint` (in `infra:check`) catches the syntax and expression errors, and B7 is the proof. Still, write first:

1. `infra/aws/scripts/deploy.ts` (Bun, run by the workflows and by hand) with tests in `infra/aws/scripts/deploy.test.ts` against a mocked AWS SDK: given an environment, a service and an image tag, it writes the SSM parameter, registers a new task definition revision from the current one with the image replaced (`describe-task-definition` → strip the read-only fields → `register-task-definition`), updates the service, waits for stability, and on a one-off task runs it with the image override, waits for `STOPPED`, prints the task's log stream and fails on a non-zero exit. Every step is a function; the CLI composes them. This keeps the workflows thin and the logic tested.
2. `infra/aws/scripts/smoke.ts` with tests: for a hostname set, asserts `/healthz`, `/readyz`, discovery `issuer`, a non-empty JWKS, the Toolbox and admin MCP `/health`, and the protected-resource metadata of both MCPs naming the issuer; prints a table; exits 1 on any failure.

## What to build

- `.github/workflows/deploy-staging.yml`: `on: push: branches: [main]`, `concurrency: deploy-staging`, `permissions: id-token: write, contents: read`. Jobs: `ci` (reuse `ci.yml` through `workflow_call`, or make `ci.yml` call these jobs after `validate`; pick the one that keeps one status per push) → `images` (`ubuntu-24.04-arm`; `docker/setup-buildx-action`, `docker/build-push-action` per image with `provenance: mode=max`, `sbom: true`, `cache-from/to: type=gha`, tags `sha-<sha>` in staging's ECR through `github-deploy` and production's through `github-ecr-push`; the build arg `REVISION`) → `deploy` (environment `aws-staging`; assume `github-deploy`; `deploy.ts run-task ops-bootstrap`, then the three migrates, then `deploy.ts deploy id|toolbox|admin-mcp`) → `smoke` (`smoke.ts staging`).
- `.github/workflows/promote-production.yml`: `on: workflow_dispatch` with inputs `image_tag` (default `staging`: resolved by a job reading staging's SSM parameters with `github-plan`), `apply_infra` (boolean, default true); `concurrency: deploy-production`; jobs `resolve` → `infra` (environment `aws-production`; `terraform init` and `apply -auto-approve` of `envs/production` with `github-apply` and the Cloudflare token; skipped when `apply_infra` is false) → `deploy` (environment `aws-production`; bootstrap, migrates, deploys, with the resolved tag) → `smoke`. The environment's required reviewer makes the dispatch one click plus one approval; the approval is the owner's.
- `.github/workflows/infra.yml`: `on: pull_request: paths: [infra/aws/**]` → `check` (`bun run infra:check`) and `plan` for each environment with `github-plan` (`terraform plan -detailed-exitcode -out`, the plan's summary posted as a sticky PR comment with `actions/github-script`, no secrets in the output: `-no-color`, and Terraform's own secret masking for sensitive values); `on: push: branches: [main], paths: [infra/aws/**]` → `apply-staging` (environment `aws-staging`, `github-apply`). Production applies only in `promote-production`.
- `.github/workflows/ops.yml`: `on: workflow_dispatch` with inputs `environment` (`staging`|`production`) and `command` (`register`, later others); runs `deploy.ts run-task ops-register` in that environment with its root or staff token read by the task from Secrets Manager (`id/root-admin-secret`, or a staff token the operator puts in a short-lived secret `ops/staff-token` that the task deletes after use), then redeploys the Toolbox and the admin MCP so they read their new client secrets (`deploy.ts deploy …` with the current tag).
- `ci.yml`: gains `infra:check` (no credentials) and `containers` (`infra:test`, from B2) as jobs on every push and pull request; the deploy workflows depend on `validate` passing.
- Rollback runbook entry: a previous `sha-…` tag passed to `promote-production` or, for staging, a `workflow_dispatch` on `deploy-staging` with an `image_tag` input (add it) redeploys it; the circuit breaker handles a deploy whose tasks never become healthy; migrations are expand-then-contract so the previous image runs on the newer schema (`infra/aws/README.md`, B6).
- GitHub settings the brief documents (the owner applies them in the UI): environments `aws-staging` (variables from B0) and `aws-production` (required reviewer, `main` only), the repository variable for production's ECR push role, the secret `CLOUDFLARE_API_TOKEN` on both environments, branch protection on `main` requiring `validate`, `infra:check` and `containers`.

## Constraints

- No AWS key anywhere; every job assumes a role with `aws-actions/configure-aws-credentials` and OIDC; pin every action by commit SHA.
- `permissions` minimal per job; `id-token: write` only where a role is assumed.
- The deploy never runs `terraform`; `promote-production`'s `infra` job is the only production apply.
- No `latest` tag, no mutable tag ([D9](../decisions.md)).
- Workflow and script style: no semicolons in `infra/aws/scripts`; `actionlint` clean.

## Acceptance

`bun run infra:check` green (actionlint included), `bun test` in `infra/aws/scripts` green with 100% coverage of the two scripts, `bun run typecheck`, `bun run lint`; the owner has applied the GitHub settings and the brief's checklist is ticked in `progress.md`. The workflows run for real in B7.
