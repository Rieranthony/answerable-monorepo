## Assumptions to challenge

- **B1-1 The idempotency journal on all 48 mutations.** `Idempotency-Key` required everywhere, permanent reservations in `admin_operations`, receipts with the original status, `Operation-Id` and `Idempotency-Replayed` headers, `getOperationStatus`, crash and replay proofs, `noop` receipts. Who sends a key today (the admin MCP sends the intent id; `infra/ops`; cURL callers from the docs)? For each mutation class (create, update, enable/disable, erase, rotate, put/replace, link) what goes wrong on a retry without the journal: a duplicate row (which uniques refuse it anyway), a second secret, a repeated audit event? Then the minimal design that keeps the safety: a key only where a retry is not naturally idempotent (create, rotate), receipts with a TTL instead of permanent reservations, or the journal as is. Measure the journal's cost per mutation on 47434 (rows, bytes, the extra statements per command; the schema audit measured 629 B per receipt).
- **B1-2 Revisions, ETags, `If-Match` on seven PATCH routes and the optional revision on two PUTs.** Who sends `If-Match` (the admin MCP binds the organisation's ETag on `organisations_update`; anyone else?). What a lost update costs on each of the seven resources. Is `revision` needed on the wire when the journal already refuses changed input under a reused key?
- **B1-3 Two authorisation layers and the vocabulary.** The tier middleware (`x-tier`, `x-scopes`) and the in-transaction `authorizeCommand`. The cleanup kept both ("both sources agree on all 81 routes and drift fails closed"). Does the second layer check anything the first cannot (freshness after a lock wait, authority at commit time), and is that worth two sources of truth? Six scopes (`platform:read|users|write`, `org:read|users|write`): who holds `platform:users` or `org:users` distinct from `write` (the admin MCP's three roles map to which scopes)? Propose the smallest vocabulary the consumers need.
- **B1-4 Denial audit** (`denial-audit.ts`, `signin-audit.ts`, the `*_rejection_audit_unavailable` signals): an audit row for an unauthenticated or unauthorised request. Measure what an unauthenticated loop against `/api/admin/v1/me` with a bad bearer writes per second on 47434 (rows and bytes), with no limiter on `/api/admin` (`Q-ADMIN-API-RATE-LIMIT`). What does a denial row carry that the request log does not, and who reads it (the audit-events routes, the admin MCP)? Options: a log line, a row only for authenticated-but-forbidden, or as is.
- **B1-5 Routes without a caller.** From your map, every route no consumer calls: `diagnoseSignIn`, `testSsoProvider` (`sso-test.ts`, 228 lines, probes an issuer's discovery document), `getMemberAccess`, `listTargetAccess`, `getMemberConfiguration`, `getOperationStatus`, `listUserSessions`, `revokeUserSession(s)`, `retireUserEmail`, `reinstateMember`, `rotateClientSecret`, the enable/disable pairs. For each: the consumer or the operational need (an operator with cURL counts, if the docs show the command), and the cost of keeping it (lines, a tier, a scope, a journal kind, tests). A route the docs show to a staff member is a consumer; a route nothing shows is a candidate.
- **B1-6 The principal** (`principal.ts`, 399 lines): session cookie with Origin check, machine bearer, user bearer, root secret. Which principals reach the admin API today (the admin MCP's user tokens, the Toolbox's machine token, the ops Jobs' root secret, a staff member's browser cookie from `/security`?). If no browser calls the admin API, what does the cookie principal and its CSRF logic serve?
- **B1-7 The root secret, its self-lock and `ROOT_ADMIN_BREAK_GLASS`** (`root-secret.ts`): `infra/ops/make-admin.ts` and `commands.ts` use it. Read them. Is the self-lock (root stops working once a human holds `platform:write`) a safety or a trap for the Job that runs again? What does the Job do when root is locked?
- **B1-8 OpenAPI** (`openapi.ts`, `schemas.ts`, `openapi.admin.json`, the `x-tier`/`x-scopes`/`x-kind` extensions, operation ids as tool names, the hand-built public document in `src/http/openapi.ts`): who reads each extension (the admin MCP? the docs build? `packages/id-admin`?). Is the public document (`/openapi.json`) consumed by anything but the docs snapshot?
- **B1-9 `problem.ts`, `pagination.ts`, `validation.ts`, `request-limits.ts`**: cursor pagination (who pages: the Toolbox poller, `pages()` in id-admin), the 256 KiB body limit with a 5 s acquisition deadline, the problem vocabulary. Small, but check for an unused problem code or a limit nothing can reach.
- **B1-10 `audit-events.ts` and the three list routes** (`listAuditEvents`, `listOrganizationAuditEvents`, `listUserAuditEvents`): the Toolbox poller is the consumer; what it filters on, and whether three routes serve one query.

For every route you propose to delete, state the OpenAPI change, the admin MCP or docs change, and the test files that go.
