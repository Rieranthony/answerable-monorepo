## Assumptions to challenge

- **B2-1 `isolation.ts` and the scope modes** (7 after the schema audit: the code that sets them, restores them through savepoints, rollback and pool reuse). Map every `setDatabaseScope` call site to the RLS policy it satisfies. Is the scope set once per request at the context boundary, or re-set along the way? Could one `SET LOCAL` per transaction in `db/client.ts` carry it? Measure the statements a tenant-tier read and a tenant-tier command issue on 47435 (`pg_stat_statements` or `log_statement=all`): how many are scope and lock bookkeeping, how many are the work.
- **B2-2 `runtime-role.ts`**: every non-test start checks role attributes, memberships, ownership and protected-object permissions before listening. What does the check cost at boot, what does it refuse that the migration's provisioning would not have produced, and is it a boot-time test of the migration script wearing a runtime coat? Both run from code the repository controls (`infra/ops/bootstrap` runs `db:migrate`).
- **B2-3 `locks.ts` and the lock order**: `lockOrganization`, `lockClient`, `lockResource`, `lockUser`, the policy locks in the services. For each service command: which rows it locks, which of those locks protect a real race (name the two commands that race) and which lock a row the transaction only reads. The schema audit found `protect_grant_context`'s member lock stalled admissions behind member updates; look for the same pattern in the services (a lock on a hot row, such as the organisation, taken by a frequent command).
- **B2-4 The entity services** (13 files, about 3,300 lines): after the cleanup they share `found`, `recordCommandEvent`, `assertRevision`, the erasure helpers. What is left that is per-entity ceremony: a command that is a status flip in five steps, a service function that is one query call, an audit payload assembled by hand where a generic before/after would do (the schema audit chose one `data` shape per action; check the writers for the repetition that choice left). Count the lines per command kind (create, update, enable, disable, erase) across the entities; the median is the ceremony.
- **B2-5 `federation.ts` (263 lines)** and `sso-providers.ts`: the SSO provider configuration, the byte order the cleanup kept as revision-bound, the credential modes (with A-5). What a provider PUT does end to end, and whether the service and the auth layer's `verified-sso.ts` each hold a copy of the provider's shape.
- **B2-6 `client-secrets.ts`, `clients.ts` (517 lines)**: client creation, rotation, owners, resource links, `authorization_version`. Which of the client fields the provider reads (the schema audit deleted three; check the code still carries none of them) and which the admin MCP's `register` Job or the Toolbox need. Is `authorization_version` bumped by the right commands only?
- **B2-7 `bootstrap.ts` (254 lines)**: provision once, verify afterwards (the cleanup's ownership rule). With `infra/ops` Jobs now doing `bootstrap`, `register` and `make-admin`, which of the boot's steps are still needed at every start of every replica (two replicas boot concurrently; the schema audit's concurrent-bootstrap proof exists)? Could the platform binding be the migration's job (a seed in `0001_invariants.sql` is schema, out of scope; a seed in `scripts/migrate.ts` is code and in scope)?
- **B2-8 `db/client.ts`**: the pool settings (20, 5 s checkout, 10 s idle, three per-connection timeouts), `mapDatabaseError`, `isRetryableDatabaseError`, `temporarilyUnavailable`. Who sets the three `SET` statements per connection and whether `pg`'s `options` or the role's `ALTER ROLE ... SET` (a migration concern, note it only) would do.
- **B2-9 `queries/**` (about 3,700 lines)**: after the cleanup's `optionalEq`, `contains`, `cursorPage`. For each query module: a query with one caller that is the service's only line (fold or keep: the test audit's rule is that a fact is proved once), a query that re-filters `deleted_at` on a row reached through a live foreign key (the cleanup's rule says it needs none), a query that returns more columns than any caller reads (measure with the TypeScript types: which selected fields no caller touches).
- **B2-10 `client-principal.ts`**, `queries/health.ts`, `queries/sessions.ts`, `queries/oauth-tokens.ts`, `queries/grant-contexts.ts`: small files; each either has a reader or goes.
- **B2-11 The migrate scripts** (`migrate.ts`, `reset-test-database.ts`, `test-migrations.ts`, `regenerate-migrations.ts`, `db/migrate.ts` with the receipt check): four scripts and a module for a service that has never shipped. The README says `regenerate-migrations.ts` goes after the first production migration; `db:regenerate`'s window closes at the staging deployment (brief B7a of the civo goal). What stays after that, and does `test-migrations.ts` prove anything `migrations.integration.test.ts` does not?
- **B2-12 Scaling**: for the three hottest admin reads the Toolbox and the admin MCP make (the poller's audit list, the member lookup, `listTargetAccess` or `getMemberAccess`), `EXPLAIN (ANALYZE, BUFFERS)` on 47435 with 10,000 users, 50 organisations, 200,000 audit events seeded by a script you write (keep it under `/tmp/v0-code-audit/probes/b2/`). Report the plans and any sequential scan on a growing table.

Anything else in scope that fails the five questions, report it.
