## Assumptions to challenge

- **C-1 `operations/metrics.ts`** (fixed-cardinality JSON summaries every 30 s, `[id] operations`): the Toolbox and admin MCP export OpenTelemetry spans (`OTEL_EXPORTER_OTLP_ENDPOINT`). Does any collector in `charts/*` or `infra/*` read ID's summaries? Options: delete (the ingress and Postgres have their own metrics; Traefik counts statuses per route), replace with the same OTel the Toolbox uses (more code, not less; only if a consumer exists), keep. Measure what the middleware costs per request (`begin`/`finish` on every request).
- **C-2 `operations/preflight.ts` and `scripts/operations-preflight.ts`** (custody preflight: decrypt every signing key and every account's upstream token, paged scans): with A-4 (upstream token storage) possibly going, what remains is "can we decrypt the JWKS private keys with the configured secrets", which `GET /auth/jwks` and a sign-in prove. Who runs `ops:preflight` (`infra/*`, a workflow, a README)? Delete, or fold into `/readyz`, or keep.
- **C-3 `operations/protocol-sweep.ts`**: kept by the schema audit (2 M rows in 25 s). Yours is the code: the advisory lock, the batch loop, the interval, the three variables. Is the lock needed with two replicas (a concurrent sweep deletes the same expired rows; what does the second one hit)? Could `PROTOCOL_SWEEP_BATCH` and the interval be constants?
- **C-4 `env.ts` (273 lines, 30 variables)**: for each variable, the reader (`rg` the camelCase name) and whether a deployment sets it (`charts/answerable/values*.yaml`, `infra/k8s/local/stack.ts`, `.env.example`, `default.env`). A variable with a default nothing overrides is a constant; a variable only tests set is a test seam. Candidates: the six `DATABASE_*` timeouts, `OPERATIONAL_LOG_INTERVAL_MS`, `PROTOCOL_SWEEP_*`, `OAUTH_REFRESH_REUSE_INTERVAL_SECONDS` (0 everywhere, `Q-REFRESH-PARALLEL`), `OPENAPI_ENABLED`, `PLATFORM_ORGANIZATION_SLUG`/`_NAME`, `ADMIN_RESOURCE_IDENTIFIER`, `BETTER_AUTH_SECRETS`, `UPSTREAM_TOKEN_SECRETS`, the production default of `BETTER_AUTH_URL`.
- **C-5 `runtime.ts` and `server.ts`**: startup order (environment, pool, runtime-role check, auth, bootstrap, listen, sweep, metrics, shutdown handlers). What is ceremony around `Bun.serve` and what is a real ordering constraint (a replica that listens before bootstrap verifies the binding, for example). The cleanup fixed the pool closing under in-flight requests; check the shutdown still waits for Traefik (the deployment's `preStop`, commit f10ea02e).
- **C-6 The pages** (`http/pages/**`, about 1,500 lines with views): `hono-tailwind` at runtime (C30, deferred twice): run the spike: build the stylesheet once (`scripts/build-css.ts` exists), serve the file, drop `hono-tailwind` from runtime and from `--external` in the build, and prove the bundle in `dist/` runs without `node_modules` (the Dockerfile's final stage; check what it copies). `gateway.ts` (the in-process call into Better Auth's handler), `login-routing.ts`, `error-copy.ts`: each either carries a page a user sees or goes. `lib/user-agent.ts`: who displays a parsed user agent (the Security page?) and whether a raw string would do. The font: one variable woff2; fine unless unused weights ship.

Are they test support that belongs in `packages/acceptance` or `infra/k8s`, and does `mcp-e2e-fixture.ts` still provision anything after the cleanup's C35 ("the fixture stops provisioning tenants")?
- **C-8 `scripts/export-openapi.ts` and `build-css.ts`**: fine if short; note their line counts and whether `export-openapi.ts` could be a test that writes the snapshot under `UPDATE_SNAPSHOT=1` like the MCP manifests (one mechanism in the repo, not two).
