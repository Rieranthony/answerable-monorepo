## Assumptions to challenge

- **A-1 The native-* and user-token-* modules re-implement the provider.** For each of `native-client-authentication`, `native-code-replay`, `native-refresh-family`, `native-token-cleanup`, `narrow-authorization-code`, `user-token-boundary`, `user-token-revocation`: what does the pinned `@better-auth/oauth-provider` do on the same path (cite dist lines), what does ID add on top, and is the addition a policy ID needs (tenant policy at the grant boundary, docs/05 §3) or a duplicate of the plugin's own check? Where ID wraps a plugin step to re-run it inside its own transaction, can the plugin's hooks (`databaseHooks`, `hooks.before/after`, the adapter) carry it with less code?
- **A-2 `user-token-assertions.ts` (181 lines)**: the "signed output and persisted state must agree before commit" check. Kept in the cleanup on docs/05 §3. What failure has it ever caught (search the git log and the tests), what would an inconsistency look like in practice, and is it a test-time assertion wearing a runtime coat?
- **A-3 Verified SSO's `run` (AsyncLocalStorage), the adapter's `observe` and `beforeTransaction` hooks, `sso-origin.ts`'s session `before` hook**: map every state these carry across the Better Auth callback (account, provider revision, tenant, `upstream_auth_time`, membership provisioning). Which of them could the `sso` plugin's `resolveUser` or `databaseHooks` carry directly? Is the AsyncLocalStorage needed because of a plugin limitation you can cite, or by construction?
- **A-4 Upstream refresh-token storage** (`upstream-token-storage.ts`, `UPSTREAM_TOKEN_SECRETS`, the account transform, the preflight's decrypt of every account): stored only for `Q-AID-RECHECK`, which is Not yet. What does the service do with a stored upstream refresh token today? If nothing: delete the storage, the key ring, the variable, the preflight's account scan and the docs; the column stays (schema settled) or goes in a later migration. State what returning to the feature later would cost. Measure the per-sign-in cost of the transform.
- **A-5 `platform-applications.ts`** (Google and Microsoft credentials injected on read, `credentials: "platform"`): is a credential mode per SSO row needed, or is "the platform application unless the row carries its own `oidc`" the same thing with fewer branches?
- **A-6 `member-permission.ts` (432 lines) and `user-resource-policy.ts`**: the exact-pair evaluator. Walk one `authorize`, one code exchange, one refresh and one machine grant: how many database round trips and locks each takes (measure on 47433 with `pg_stat_statements` or query logging), which checks repeat between the layers (the provider's, ID's hook, `createResourceGrant`'s), and whether the refresh path at 10,000 users with 900 s tokens is bounded by these checks (the schema audit measured about 135 refreshes a second per process, CPU-bound; find what the CPU is doing).
- **A-7 Machine grants** (`machine-provider.ts`, `machine-identity.ts`, `machine-capability.ts`, `machine-audit.ts`): the Toolbox and admin MCP are the callers (`packages/id-admin`). What does the ceiling computation cost per `client_credentials` call, and is the audit event per machine token (kept by the schema audit) needed now that `packages/id-admin` caches? Check the cache.
- **A-8 `auth-allowlist.ts` (190 lines)**: an explicit allowlist of Better Auth routes. Compare with what the installed plugins mount: is the list still exact, does it hide a route the docs claim, and would a denylist of the plugin routes ID refuses be shorter and as safe? List every route the allowlist opens and its consumer.
- **A-9 `audit-hooks.ts`, `user-oauth-audit.ts`, `signin-audit.ts`, `machine-audit.ts`**: the rejection audits write a database row for refused sign-ins and token requests. Under a scan or a credential-stuffing load, how many rows per second can an unauthenticated caller make ID write (measure: a loop of refused token requests against the in-process app on 47433), and what does the row carry that a log line would not? Is this a database-write amplifier with no limiter in front?
- **A-10 `BETTER_AUTH_SECRETS` ring beside `BETTER_AUTH_SECRET`**: who rotates it, what the installed 1.7.2 does with `secrets`, and whether the ring and its README section are needed for v0 or a procedure for later.
- **A-11 The jwt plugin, `openAPI({ disableDefaultReference: true })`, `organization` plugin with `allowUserToCreateOrganization: false`**: for each plugin in `createAuth`, which of its routes and tables ID uses; what the `organization` plugin provides beyond its tables (the cleanup kept the Drizzle relations it joins).
- **A-12 `fresh-authentication.ts` and `tenant-authentication.ts`**: the five-minute freshness is accepted (docs/05 §11). The mechanism is yours: is it computed in one place and read by the command layer, or re-derived?

Anything else in scope that fails the five questions, report it.
