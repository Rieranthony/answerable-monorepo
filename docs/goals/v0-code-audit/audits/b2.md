### B2-1 Scope modes: where the scope is set, and what one request costs

**Is it set once at the context boundary?** The command's own scope is (one `setDatabaseScope` after `authorizeCommand`). The authority evaluation is not: `effectiveGrants` switches to `policy-user` and `tenantAuthentication` nests `protocol` inside it, each through `withDatabaseScope` (savepoint, read the five settings, set, run, restore, release). That happens once in the middleware (`http/principal.ts:361`, its own transaction), once in the context, and once more after **every** lock a command takes (`context.revalidate()`).

**Could one `SET LOCAL` per transaction carry it?** No. Authority is evaluated under `policy-user` and `protocol`, which see the caller's memberships across tenants and the native session rows; the command must then run under its own narrower scope. Two scopes per transaction are the floor. What can go is the repetition (b2-1) and the savepoint ceremony (b2-2).

#### b2-1 Per-lock `revalidate()`: delete (or one horizon check)

*What it is.* Fifteen query functions (`lockOrganizationForCommand`, `findOrganizationDomainForCommand`, `findGroupForCommand`, `readGroupPolicyForCommand`, `findGroupMemberForCommand`, `findEntitlementForCommand`, `readEntitlementAudience` (two branches), `findMemberConfiguration`, `readClient` (write case), `lockClientForCommand`, `readResourceForPolicy`, `lockResourceForCommand`, `findSsoProviderForCommand`, `users.lockUser`) call `context.revalidate()` after taking a row lock, which re-runs the whole `authorizeCommand` for a human caller. `createEntitlement` with a group, a client and a resource re-runs it five times; `updateEntitlement` four.

*The assumption.* That another transaction may revoke the caller's authority while the command waits on a lock. It cannot: the first `authorizeCommand` share-locks the user and session (`command-authority.ts:34-47`), the caller's authenticating organisation and the admin resource (`grants.ts:54-76`), and the native SSO provider, account and session (`tenant-authentication.ts:48-62`). Every writer that could take authority away (member commands, entitlement, group, assignment and capability commands, organisation disable, SSO changes, user disable or erase, session revocation, resource disable) needs `FOR UPDATE` on one of those rows, so it waits for the command to commit, or deadlocks and one side gets a retryable 503. What remains is time: a membership, assignment, capability or session window that ends during the wait, bounded by `lock_timeout` (2 s) per wait.

*Run (probe 07).* With `revalidate` a no-op the suite is 1,557 pass, 1 fail: `verified-sso.integration.test.ts:1208`, which moves a fake clock past a membership's `validUntil` while a rotate-secret command waits on the client row. No other test, including the lock-order, replay and erasure-race files, notices. Statements: PATCH entitlement 129 → 53, PATCH member window 74 → 55, create group 69 → 50.

*Also observed.* Machine callers never revalidate (`if (principal.type === "user")`), so a capability window that ends during a machine command's wait is already accepted today; the guarantee is human-only.

*Alternative tried (probe 07b).* One re-check after the command body instead of one per lock keeps the expiry test green (5 files, 111/111), but the full suite fails `capabilities.integration.test.ts:677` ("the bound platform ceiling can be removed even when it supplies the last writer"): a re-check after the writes sees the command's own effect and refuses it (403). A re-check has to run before the first write, which no generic place in the runner knows. (The suite's other failure in that run, `user-oauth.integration.test.ts:1223`, is a one-second `expires_in` boundary under load; it passes alone, probe 07c.) The exact alternative is a **horizon**: `authorizeCommand` returns the earliest end among the admitting membership, assignment, group assignment, capability and session windows (all already selected by `memberPermissionFields`), and the runner refuses when `statement_timestamp()` has passed it: one comparison, no re-evaluation, about 15 lines in `member-permission.ts` and `command-authority.ts`.

*Proposal.* Delete the fifteen calls and both `revalidate` members; delete the one test. If the owner wants expiry to hold to the second during lock waits (Q1), add the horizon check instead.

*What a user would notice.* Nothing, except that a staff command admitted just before its admitting window ends can commit up to 2 s per lock wait after the end. Commands get faster: 19 fewer round trips per lock, and the organisation row is held for a shorter time.

*Risk for thousands of users.* None for tenant isolation; the share locks are unchanged. The change is the bounded window slack above, for staff and tenant administrators only (end users never run admin commands).

#### b2-2 `withDatabaseScope`'s savepoint: challenged, kept

*The assumption.* The savepoint exists only so an error "rolls back the savepoint and settings", which matters only if a caller catches an error inside a transaction and continues; no production caller does (the one `.catch` in the protocol paths, `create-resource-grant.ts:169`, rethrows).

*Run (probe 09).* Without the savepoint (read, set, run, restore; no restore when it opened its own transaction): tenant read 42 → 34 statements, PATCH member window 74 → 62, create group 69 → 57, PATCH entitlement 129 → 105, machine read 31 → 27. Full suite 1,557 pass, 1 fail: `runtime-role.integration.test.ts:474-487`, which throws a JavaScript error inside a `policy-user` scope, catches it and expects the tenant scope back.

*Why it holds.* That test is the case the savepoint exists for: a JavaScript error (not a database error) leaves the transaction usable, so without the savepoint a caller that caught it would go on under the wider scope, failing open. The savepoint makes the restore correct for both kinds of error at two statements per nesting; a `try`/`finally` restore would have to handle an aborted transaction and keep the original error. Keep. Two small simplifications stand without that risk: no restore when `withDatabaseScope` opened its own transaction (it commits next; one statement per middleware evaluation), and `findClientPrincipal` (`client-principal.ts:21`) running in the caller's transaction when it has one instead of a nested savepoint (two statements per machine request in the context). Together about 3 statements per request.

#### b2-3 `bootstrap` scope switches: simplify

`provision` sets `tenant-write` to insert the group and entitlement, `platform-write` for the capability, then `tenant-write` again before the audit insert; `verify` sets `tenant-write` before touching only `organizations`, `oauth_resources` and `audit_events`. `tenant_write` admits `platform-write`, `audit_insert` admits any scope, and the other three tables have no RLS (`pg_class.relrowsecurity`). Spike (probe 11, in the combined run): one `platform-write` in `provision`, none in `verify`: 1,558 pass, 0 fail, 100% lines and functions. Nothing a user sees; one statement fewer at every start.

#### b2-4 Pass-through read services: delete

Ten service functions are `return queries.x(context, query)` (57 lines, probe 12; median read service 6 lines, probe 04). The query already takes the branded context, which is the authority boundary; the service adds nothing. `http/admin/audit-events.ts:7` already imports a query directly. The `found(...)` wrappers (`getUser`, `getMember`, `getGroup`, `getGroupMember`, `getEntitlement`, `getSsoProvider`, `getMemberConfiguration`) stay: they carry the 404 title. Spike (probe 12, in the combined run): the ten replaced by re-exports of their query; typecheck clean; 1,558 pass, 0 fail, 100% lines and functions. The real change: each route imports the query module for its list read, and four services lose an unused context import. No consumer sees a difference.

#### b2-5 Audit projections: simplify

`organizations.configuration`, `domains.auditDomain`, `groups.configuration`, `groups.assignment`, `entitlements.configuration` and `resources.auditResource` each list the row's columns except `live`, `createdAt` and `updatedAt` (checked against `information_schema.columns` on 47435). One `evidence(row)` that drops those three produces the same JSON keys. `users.state` (no email or name), `clients.auditClient` (no secret or JWKS), `sso-providers.configuration` (redacted) and the member shapes stay. Spike (probe 14, in the combined run): 69 lines replaced by a 6-line helper; typecheck clean; 1,558 pass, 0 fail, 100% lines and functions. The payloads are unchanged, so docs/04 and `audit_event_users` are untouched (the capture trigger reads `memberId`, `userId` and named arrays, `0001_invariants.sql:71-116`). Capabilities already record the full row including the three bookkeeping columns (`capabilities.ts:164-171`); `evidence` there would make the payload consistent but change it, so it is left.

**b2-10 `runtime-role.ts`.** *Assumption challenged:* it is a boot-time test of the migration script. Half true: the privilege clauses re-check what `configureRuntimeRole` grants. **b2-13 Locks.** Per command:

| Command family | Rows locked, in order | Race the lock protects (the two commands) |
| --- | --- | --- |
| Organisation update, disable, enable, erase | organisation U | disable vs token issuance (`FOR SHARE` on the organisation); erase vs any policy command |
| Domain create, status, delete | organisation U, domain U | domain change vs sign-in (membership and session inserts take `KEY SHARE` through their foreign keys); the domain lock is redundant under the organisation lock but costs nothing once b2-1 goes |
| Group create, update, status, erase | organisation U, group U, (status) assignments and entitlements S | group status vs user erasure, which soft-deletes assignments and entitlements without the organisation lock |
| Group member put, remove | organisation U, group U, assignment U | remove vs user erasure (same) |
| Entitlement create, update, status, remove | organisation U, entitlement U, client S, resource S, audience members S | update vs user erasure; create vs client or resource erasure and scope narrowing; the audience vs new memberships (blocked by the organisation U through the foreign key) |
| Capability create, update, remove | organisation U, client S, resource S | create vs client scope narrowing |
| SSO put, delete | organisation U, provider U | put vs Better Auth's provider update at sign-in (`database-adapter.ts:88-101`, `KEY SHARE` on the organisation) |
| Member window, remove, reinstate | organisation U, member U | member command vs user erasure (`deleteUser` locks members by user, without the organisation) |
| User disable, enable, retire, erase | user U (erase: members, sessions, refresh tokens U) | vs sign-in (`verified-sso.ts:159` locks the user) and session creation |
| Session revoke | user U, session U | vs session refresh |
| Client commands | client U (create: organisation U; link: resource U) | vs token issuance (`FOR SHARE` on the client) |
| Resource commands | resource U | vs issuance and entitlement or capability validation (`FOR SHARE`) |

The only locks on rows a transaction merely reads are the `FOR SHARE` reads in validation and audience capture, and each serialises against a named writer above. The pattern the schema audit found in `protect_grant_context` (a frequent command blocked on a hot row) does not recur in the services: their `FOR UPDATE` locks are taken by infrequent staff commands, and audience capture and the last-administrator guard rely on `FOR UPDATE` (not `NO KEY UPDATE`) blocking new memberships through the foreign key's `KEY SHARE` (`grants.ts:136-137`). The frequent lockers are readers: every admin request and every token issuance takes `FOR SHARE` on the caller's organisation, user, session and resource and, for issuance, the client, a row every tenant's users of that host share. Probe 08 measures what a share lock on a hot row costs: a plain read of the organisation row writes no WAL; with `FOR SHARE` each transaction writes 104 bytes alone and 174 bytes with 8 concurrent clients, and 1,000 concurrent transactions created 969 multixacts. That is an optimisation for later, not a change now; b2-1 shortens how long commands hold the organisation row. Keep.

## 4. Unsafe or wrong

**W1. A sign-in that takes over a disabled user's email leaves no audit trace on that user.** `services/federation.ts:228-236`: when a new directory identity signs in with an email held by a disabled user, the resolver moves the holder's address to `retired_email` and sets its email to `<id>@retired.invalid`, through the adapter, inside the sign-in transaction. The only event written is the new user's `auth.signin.succeeded` (`auth/sso-origin.ts:127-145`, actor the new user). The admin route that does the same thing records `user.email_retired` (`services/users.ts:145-152`). docs/05 §5: "Successful effects, audit events, durable subjects and command receipts share the transaction." Reproduction (probe 10): `federation.integration.test.ts`'s "releases a disabled holder's recycled email" with the audit rows printed: one event, the new user's `auth.signin.succeeded`, and 0 `audit_event_users` rows for the holder. Effect: `GET /users/:holder/audit-events` shows no event for the change of the holder's email; an investigator sees the address move only by comparing rows. Fix (for the owner, not done): record `user.email_retired` for the holder in that branch, with the system actor and the `before`/`after` shape docs/04 already defines; `audit_event_users` picks the holder up through `target_type = 'user'`. Also: `emailUser?.deletedAt` in that condition is unreachable, because erasure already moves the email (`queries/users.ts:296-297`).

**W2. `DELETE /users/:id/sessions` records `session.revoked_all` when nothing changed.** `services/sessions.ts:74-86` writes the event unconditionally and returns `changed: false`, so the receipt says `noop` while the audit log says something happened. Every other command writes no event for a no-op (D7; `services/audit.ts:11-12`). `sessions.integration.test.ts:138-156` asserts the event at count 0, so the behaviour is pinned, not accidental; it contradicts the rule the schema audit took. Fix: `if (changed)` around the event; the test's second iteration expects none.

No hole in tenant separation was found in scope: every query on an RLS table runs under a scope that admits only the caller's rows, and the spikes that removed per-lock re-checks (07) and savepoints (09) changed no tenant-separation test.

## 5. Open questions for the owner

**Q1. Must a staff command's authority hold to the second while it waits on a lock?** Today a human command re-evaluates its whole authority after every lock (19 statements each; a PATCH of an entitlement is 129 statements, 53 without). Two defensible designs: (a) delete the re-checks and accept that a command admitted just before a membership, assignment or capability window ends may commit up to 2 s per lock wait after it (machine callers already work this way); (b) keep exact expiry with one horizon comparison at the end instead of re-evaluation. Recommended: (a), the simpler one; (b) if exact expiry is a promise to customers.
