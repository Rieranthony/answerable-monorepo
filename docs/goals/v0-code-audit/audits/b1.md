## 3. Findings in detail

### B1-U1 Permanent receipts make the documented break-glass recovery a no-op (unsafe)

**Evidence (04b).** After the last platform administrator left both groups, with `ROOT_ADMIN_BREAK_GLASS=true`:
- `make-admin` for the same person sends `PUT …/groups/{g}/members/{m}` with its constant keys `admin-first-owner-v1` and `platform-admin-membership-setup` (`make-admin.ts:4`). ID replays the first run's receipts: `201`, `Idempotency-Replayed: true`, outcome `applied`. Nothing is created. The Job then fails with "is ROOT_ADMIN_BREAK_GLASS true in ID's environment? Unset it and deploy", sending the operator the wrong way.
- `make-admin` for anyone else: `409 idempotency_key_reused`; the message says to change the key "here and in the docs".
- `docs/06` step 7, which says "repeat this step", by hand with its key `platform-admin-1`: `201 replayed=true`, zero live platform-admin rows. A cURL user sees success.

docs/05 §4 states the rule ("A matching key never repeats later effects, even after enable/delete/replacement"); the callers that hard-code keys were written against it. The same applies to any constant key the docs print for a step a reader may repeat after the state was undone (`platform-domain-setup`, `platform-sso-setup`).

**Why receipts cannot simply expire (14).** The runtime role has only INSERT and SELECT on `admin_operations`, and `audit_events.operation_id` references it: a receipt is the audit trail's operation anchor. Expiry would reopen the schema.

**Proposal.** Fix the callers. `make-admin` needs no stable key: it already treats `412` (`If-None-Match: *`) as "already in" (`make-admin.ts:42`); use a key per invocation, reused only by the Job's own retry. `register` already treats `409 conflict` and `200` on PUT as "already there" (`register.ts:55`); its creation keys can stay. `docs/06` step 7 and `onboard.mdx` step 5: generate the key (`$(uuidgen)`) and say a key retries one attempt, never repeats a step later. **User-visible:** recovery works in one run. **Test after:** an `infra/ops` test (fake) or a journey that removes the last administrator, turns break-glass on, runs make-admin, and asserts a live membership. **Risk:** the path is rare but is the one used when nobody can administer.

### B1-U2 Anonymous requests write audit rows (unsafe; simplify)

**Evidence.** Every unauthenticated request to `/api/admin` (`invalid_token`, `unauthenticated`) inserts an `admin.auth_failed` row before answering 401. One client process with 16 connections wrote 3,922 rows/s on an idle database (10b), 2,837/s beside the test suite (02a): 358 B of heap and index and 818 B of WAL per row, five secondary indexes plus the subject trigger per insert. An unsigned JWT's `client_id` is stored as `data.claimedClientId`, bounded only by Bun's header limit: 12,000 random characters, 12,224 B per row (02e). At the 02a rate one attacker writes ~245 million rows and ~88 GB of heap a day, ~2.9 TB a day with 12 kB claims, into an append-only table the runtime cannot purge. The insert also holds a pool connection per request: a legitimate read's p95 went from 29 ms to 116 ms (10). Without the insert the same flood answered 20,951 req/s and wrote nothing (02f). Cloudflare absorbs volumetric attacks, but a few thousand requests per second from many addresses is within a scanner's reach, and `/api/admin` has no limiter (`Q-ADMIN-API-RATE-LIMIT`).

The rows also slow the Toolbox poller, which reads every event newest first: after 70,488 denial rows its next poll took 353 requests and 8.2 s and found nothing (03).

**Who reads them.** Nothing: no code filters on `admin.auth_failed`; the docs' only denial query (`onboard.mdx:471`) filters by `organizationId`, which these rows never carry. Over the ingress log a row adds `reason`, the request id and the unverified claim.

**Proposal.** Write a denial row only when the credential verified and the actor is known: keep `user_disabled`, `untrusted_origin`, `origin_required`, `client_unowned`, `organization_disabled` (each needs a valid session or a signed token, so their rate is bounded by credentials) and `admin.denied`; replace `invalid_token` and `unauthenticated` rows with an operational log line counted in the existing metrics, without the claim. Spike 11: only tests asserting the rows fail (about 15 in `denial-audit.integration.test.ts`, `principal.test.ts`, `request-security.integration.test.ts`). **User-visible:** none. **Risk:** per-request rows for invalid tokens go; the ingress log keeps time, address and path.

### B1-1 The journal: keep receipts, make the key optional

**Who sends a key.** The admin MCP: the intent id, resent once after no answer or a 5xx (`calls.ts:66-71`). `@answerable/id-admin`: a random UUID per call, reused only when a 401 forces a new token (`index.ts:138`). The Toolbox: random per call; its enable operation is repeated by re-running it against existence checks (`admin-enable.ts:93-109`), never by key. `infra/ops`: constants (B1-U1). The acceptance: random. Docs: a variable per command, constants in the first run.

**A retry without the journal, per class** (uniques from `db/schema`):

| Class | Retry without the journal |
| --- | --- |
| create organisation, group, domain, resource, capability, entitlement, client with `clientId` | refused by a unique: `409 conflict` instead of the first answer |
| create client without `clientId` | **a second client and secret** (the docs' "Staff automation" omits it) |
| PATCH with `If-Match` | `412` (the first write moved the revision) |
| PATCH without, enable/disable, link/unlink, member remove/reinstate | noop |
| erase | `404` instead of `204` |
| rotate secret | a second rotation returning a usable secret; the journal's replay returns a receipt without one, which is worse for the caller |
| revoke all sessions | also ends sessions created since |

The journal's real work is stable answers after a lost response, the one non-idempotent create, and `Operation-Id`, which links audit events and the admin MCP's evidence (`calls.ts:73` refuses an answer without it). It cannot go without consumer changes and a schema change (14). It is cheap: 3 statements, 557 B per command, 9.6 ms per command end to end (05).

**Proposal.** Keep receipts and fingerprints; make `Idempotency-Key` optional, journalling a command without one under a server key. Spike 13: one test fails, the one pinning the 400. The cURL friction goes, every command keeps its `Operation-Id`, and readers stop copying constants (B1-U1). Keep the Origin checks (B1-6), which become the CSRF guard for a bodiless `POST …/disable` once no custom header is required. OpenAPI: the parameter becomes `required: false` and `adminRoute()`'s sentence changes; the fake ID in `packages/id-admin` follows.

### B1-2 Preconditions: keep

`If-Match` is sent by the admin MCP (`organisations_update`, `sso_set` replace, `groups_addmember` change), the Toolbox (`PATCH` of its resource's `allowedScopes`, a read-modify-write where a lost update drops another provider's grant strings) and every PATCH and PUT in `manage.mdx`; `If-None-Match: *` by the admin MCP, `make-admin` and `register`. The other four PATCH routes are docs-only, but share `assertRevision` and cost an optional header; a lost update there changes scopes or redirect URIs. The fingerprint is no substitute: it refuses a changed input under one key, not a concurrent writer under another.

### B1-3 One authorisation layer, five scopes

**Spike 09** removed the `authorize` middleware from every route. Of 873 tests in `src/http`, 142 failed, every one for one of two reasons: no `admin.denied` row, or `403` where `404` is expected for an organisation the caller holds no grant in. No response was 2xx and every tenant-separation `leaked` list stayed empty: `authorizeCommand` inside the transaction (reads through `withPlatformRead`/`withTenantRead`, writes through `httpCommand`) refuses everything the middleware refuses. The reverse is false: "fleet reads reject platform authority revoked after middleware" passes only because of the in-transaction layer. The `tier` variable is written in production and read only by `authorize.test.ts` and `route-table.test.ts`.

**Proposal.** Delete `authorize`, `deny`, `tier`, `Tier`, `tierOf` and `x-tier`; in `authorizeCommand`, answer `404 not_found` when the path names an organisation the principal holds no grant for and no platform grant (the rule at `authorize.ts:94-96`) and record `admin.denied` there through `recordAdministrativeDenial` on the pool, outside the rolled-back transaction. One source of truth remains: the route table's scopes reach `authorizeCommand` through the contexts. Cost: a forbidden but authenticated caller opens a transaction and has its body validated first (400 before 403); its rate is bounded by valid credentials. `authorize.test.ts` (209 lines) goes; the route matrix keeps its status assertions.

**Vocabulary.** `org:write` is required by no route (15: three fixtures ask for it) and documented as reserved for a Not-yet: delete it (boot syncs the admin resource's scopes; an entitlement still listing it confers nothing). `platform:users` is held apart from `platform:write` in practice: register gives the Toolbox and the admin MCP `platform:read platform:write`, so neither can disable users, revoke sessions or change memberships; the admin MCP's three roles are grant strings on its own resource, not ID scopes. `org:read` and `org:users` are the documented tenant-administrator pair. Five scopes.

### B1-4 Denial audit

See B1-U2. `admin.denied` (authenticated, forbidden) names the actor, the route and a known organisation; the docs show staff querying `outcome=denied`. Keep it, moved into the in-transaction refusal. `admin.root_request` on every root call is the documented break-glass trail; root calls are rare once locked. Keep. The Toolbox poller should read `&outcome=success` (03b: 26 pages instead of 572 for the same 2,009 relevant events): a denial never changes what a member may use.

### B1-6 The principal: keep

Three principals reach the admin API: machine bearers (admin MCP, Toolbox, ops staff token), the root secret (ops first run, acceptance, k8s stack) and a staff member's copied session cookie (`onboard.mdx` step 6, "The next staff member", the staff-token commands). There is no user-bearer principal: user-delegated tokens are refused (`principal.ts:295-298`). The cookie is where docs/05's five-minute freshness applies, so it stays. Its Origin checks are a third CSRF layer today (SameSite=Lax; no CORS on `/api/admin`, `app.ts:83-87`; a required custom header) and become the second once the key is optional (B1-1): keep.

### B1-7 Root self-lock: keep

The lock makes a leaked root secret (it sits in the GitHub environment and in `id-env`) useless once a person administers. A second `make-admin` after the lock exits cleanly (04a). After the lock, `register` needs a staff token placed by hand with `kubectl` and deleted after (`infra/README.md`, Register again); the token is an access token with the admin resource's 600 s lifetime. That is a by-hand step in a "nothing from a laptop" deployment: open question 2. The trap is B1-U1, not the lock.

### B1-8 OpenAPI

No code reads `x-tier`, `x-scopes`, `x-kind` or `x-fresh-authentication`; `manage.mdx` explains them and docs/08 names `x-kind`/`x-scopes` as the input of the Not-yet OpenAPI adapter. `x-tier` is derivable from `x-scopes.org` and goes with B1-3a. "Operation ids are the tool names" (`app.ts:183`) is false today (the admin MCP's tools are `organisations_list` and so on): correct it. The public `/openapi.json` reaches the docs through the committed snapshot (`apps/web/lib/openapi.ts:7`); the runtime routes are off in production by default (`env.ts:231`). Keep.

### B1-9 Problems, pagination, limits: keep

Every code checked is reachable; `http_error` answers malformed JSON (07), documented at `manage.mdx:298`. `pages()` asks for the 200 maximum. The 256 KiB limit and 5 s deadline guard what Bun's 128 MB default would not.

### B1-10 Audit reads: keep three routes

`listAuditEvents` serves the poller, the admin MCP and the journeys; `listOrganizationAuditEvents` is the only tenant-tier view (RLS-scoped, link visibility rule); `listUserAuditEvents` reads through `audit_event_users`, a different query. One consumer change: the poller reads `outcome=success` (03b).

### B1-11 and B1-12

- `updateGroup`'s patch has one field, `name`, and is not strict, so `{unlessOnly:["name"]}` demands freshness only when a caller adds unknown keys that validation strips. Set it to `false`, as `updateOrganization` (16: no test fails).
- `sso-test.ts` (228 lines) re-implements discovery: URL and host checks, a DNS lookup, manual redirects, required fields, issuer match. The pinned `@better-auth/sso` exports `discoverOIDCConfig` with the same checks (`index.mjs:356`, `:420-505`, `:647`). Probe 06: the two disagree on a trailing-slash issuer (ours reports `issuer_mismatch`, Better Auth accepts). Using the plugin's function makes the probe say what sign-in does. Optional: the response shape changes, so the admin MCP's `sso_test` output schema and register's log line change. Not spiked against the suite.

## 4. Unsafe or wrong

1. **B1-U1** (`04-break-glass.sh`): the documented recovery from "no platform administrator left" replays old receipts (`201`, outcome `applied`) and creates nothing, or answers `409` for a different person.
2. **B1-U2** (`02-run.sh`, `02e-random-claim.ts`): an anonymous request writes a permanent audit row, up to 12,224 B of attacker-chosen bytes; ~3,900 rows/s from one process; legitimate p95 ×4 during it.
3. Responses expose `deletedAt` and `live` on group and organisation creates and reads (08): fields no schema declares.
4. Docs drift: `docs/06` step 7 uses keys `platform-domain-1`, `platform-sso-1`, `platform-admin-1`; `onboard.mdx` uses `platform-domain-setup`, `platform-sso-setup`, `platform-admin-membership-setup`; `docs/06` omits `If-None-Match` on the SSO PUT.
5. For audit A: `user-oauth.integration.test.ts:1246` compares a replayed token response whose `expires_in` is recomputed across a second boundary (300 vs 299); it failed in the baseline under probe load.
