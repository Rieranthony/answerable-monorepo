In short

Holds up

  • One shared Postgres database with a schema per MCP. Measured at 200 MCPs: a burst of 1,000 queries runs on 10 connections; provisioning takes 0.7 s and the first migration 2 s.
  • Row-level security by organisation, and a typed db built once per process.
  • One mcps image, register on every deploy, every standalone MCP by path on one hostname, and lists generated from mcp.json.
  • bun mcp's exit codes, fix lines and refusing every wrong answer at once; MCP tests on real Postgres; docs rendered from the code.

Does not

  • A developer's local ID now accepts a public root password from any machine on the same network (A4).
  • Three pieces serve a future with no date: a standalone server whose only MCP is a test fixture, a database mode no MCP uses, and per-MCP roles that do not separate MCPs sharing a process.
  • Under load, the readiness check can take every Toolbox pod out of service (C3).
  • The test gate fails between 50 and 100 MCPs, measured, while the PR is built for 200 (F18).
  • A newcomer cannot reach a first tool call from the docs alone, and the documented undo breaks bun install (F1, F2).
  • The same facts live in several places: two fakes of ID, every CLI refusal asserted twice, the templates in three copies, register described in ten places.

2. Decisions for you

Each of these reverses something you asked for or approved, or trades a guarantee for less code. My recommendation comes first. The line counts are the auditors', and most are estimates.

D-1

Standalone serving: one process, or none until a real MCP needs it

C1 · C2 · E1 · E2 · B7 · C11 · E11 · C6
  • No MCP is standalone. The only both MCP is e2e, the test fixture.
  • For it, every environment runs the standalone server (2 to 4 replicas in production) with:
    • its own database and two logins;
    • a third login on the MCP database;
    • the standalone-hub machine client;
    • the mcp.<zone> hostname;
    • a migration Job on every deploy;
    • e2e's rows in ID.
  • The two servers' entry points are the same file with the names changed. The separation isolates nothing: a both MCP's code also runs in the Toolbox.
  • You asked for the choice of Toolbox, standalone or both in the CLI.
Recommended

Keep the choice, and serve standalone MCPs from the Toolbox's process at mcp.<zone>/<name>/mcp. This removes the standalone Deployment, its database, logins and Secrets, standalone-hub, standalone-migrate and a network policy: about 1,500 lines (estimate). The second sign-in model and standalone_enable stay. Risk: the Toolbox and standalone MCPs share one failure domain, as a both MCP already does.

Or

Delete standalone serving, and the serve choice, until the first MCP whose users must sign in to it alone. This removes about 2,250 lines in whole files, 15 variables, a client, a Deployment and a staff flow, and adds a register row with that trigger.

Or

Keep both servers, and serve e2e from the Toolbox only, so no environment runs the standalone server. One line. The code stays, untested in deploys.

D-2

The own database mode: delete it, and keep the door open

B1 · A9 · C10 · D12
  • No MCP uses it: both mcp.json files say shared.
  • An own database sits on the same Civo instance as everything else, with the same CPU, disk, backups and maintenance window.
  • Its runtime login's URL is a variable of the shared Toolbox and standalone processes, so any MCP mounted beside it can read it.
  • It costs 30 to 40 connections per own MCP per server, the cost D1 was chosen to avoid.
  • You asked to leave the door open. It stays open without the mode: the tables are schema-qualified, so moving an MCP to a separate instance is the dump and restore D1 describes.
Recommended

Delete the mode, along with the database field, the --database flag, the connection-budget step and the per-MCP variables. Record Q-MCP-OWN-DATABASE, triggered by the first MCP that must live on a separate Postgres instance. This removes 359 lines measured, about 500 with the scattered branches (estimate), and four test databases. Risk: none today.

Or

Keep it as it is.

D-3

Per-MCP database roles: replace them with grants

B2 · B3 · B9 · F16
  • reproduced A serving login is a member of the role of every MCP it serves. Inside one MCP's role, select set_config('role', 'other', true) switches to another MCP's role and reads its rows. Postgres checks a role change against the login, not the current role.
  • So the roles stop a schema named by mistake, but not code that switches role on purpose. The migration scanner and bun mcp check's scan both miss that form.
  • What the roles cost:
    • 400 cluster-wide roles at 200 MCPs, on the Postgres that also holds ID;
    • a role lock;
    • a role prefix in eight signatures, in two production variables and as eleven test prefixes;
    • a hand-written migration loop, because the owner role cannot use drizzle's own migrator.
Recommended

Keep the schema per MCP, the one database, one pool per serving process and row-level security. The migrator owns every MCP schema, and each serving login is granted the tables of the MCPs it serves. Delete the per-MCP roles, both role scans and the migration scanner. This removes about 340 lines (estimate), 400 roles at 200 MCPs, 11 prefixes and 2 variables. Risk: raw SQL in one MCP that names another MCP's schema would succeed instead of being refused. Organisation isolation is unchanged: the auditor's probe showed row-level security holds without the roles.

Or

Keep the roles. Make both scans catch set_config('role', …), and describe the roles as a guard against mistakes.

D-4

C4 · C6 · C7
  • Every handler waits for the member and the organisation from ID's admin API, cached for 60 s. Only mcps/example reads a name.
  • A cold call took 28.9 ms against 4.4 ms cached (the acceptance).
  • With ID down and a cold cache, a tool that reads nothing of the profile is refused.
Recommended

Keep it, as you asked: "who is connected… so we can address who they are". Start the read beside the grants read (C5). Move createIdProfiles into @answerable/mcp-platform, so the ID admin client stops depending on the SDK (C7). The one-hour stale window follows D-1, since it helps only standalone MCPs.

Or

Read the profile only when a tool asks, with await context.profile(). This removes the admin MCP's poller, and the cold round trip for tools that don't ask. It changes the shape you approved in D17.

D-5

Test MCPs in production: accept them, and say so

E3 · C13
  • Every environment's Toolbox mounts e2e, which now writes to Postgres, and example, the docs' MCP. Before the PR it mounted only e2e, in memory.
  • No organisation sees either until staff enable it.
  • There is no per-environment switch (D10).
Recommended

Accept it, and write it in docs/12: e2e is every deploy's smoke target, and example is the docs' living MCP. No code. Risk: staff enable a test MCP for a customer by mistake.

Or

Keep example out of the shipped lists. That needs a field in mcp.json, which is the per-environment switch D10 deferred.

D-6

The CLI's surface: keep what you asked for, delete what nothing reads

D3 · D4 · D5 · D6 · D2 · D14
Recommended
  • Keep the terminal prompts (D4) and new --tool (D6): you asked for both.
  • Keep the guidance comments in each generated file (D14), which you asked for. Shorten them where they repeat each other.
  • Keep the error table (D5), since the docs rule asks for a row per code. Take F4 and F15 instead, which remove the duplicate assertions.
