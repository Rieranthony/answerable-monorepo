1 · The big picture

One request, start to finish

Three programs of ours run in the cloud: Answerable ID (sign-in and permissions), the Toolbox (the MCP server that gives AI tools their capabilities) and the admin MCP (our staff's management tools). Each runs as copies of a container inside a Kubernetes cluster on Civo, in London. In front of them sit two doors: Cloudflare on the internet, then our own entry point inside the cluster. Behind them, one managed PostgreSQL database holds all the data. GitHub builds and ships new versions when we push a tag. The website stays on Vercel, untouched.

2 · Accounts and guard rails

A Civo organisation, two accounts, two GitHub environments

A Civo account owns resources and a bill; nothing in one account can see or touch another. We use two, one for staging and one for production, grouped under one Civo organisation so roles are defined once. A mistake in staging, a leaked staging key or a bad Terraform run cannot reach production, because they live in different accounts. This is the pattern Civo's own documentation recommends for splitting environments.

Teams and roles

People join an account through a team with a role. "Owners" see billing and everything; "Technical Administrator" manages clusters and resources but not billing. Agents and colleagues get the second.

The API key

Civo gives each account one key that can do anything in that account, with no scoping and no expiry. So it is pasted once into that account's GitHub environment and lives nowhere else; only the Terraform step is handed it. The deploy step never sees it: it uses a token limited to one namespace in the cluster.

Secrets, without a store

There is no company secret store, and none is needed yet. Five values you paste live in the GitHub environment; everything else is generated by a workflow, by Terraform or inside the cluster, and no person ever sees it. Section 9 explains.

What Civo does not give us

No diary of API calls, no threat detector, no encryption keys we control, and the cluster's control plane always has a public address. We compensate with the two-account split, firewalls, the namespace-limited deploy token, and ID's own audit log of everything that matters to the product. The gaps are written down, not hidden.

3 · Cloudflare, the first door

DNS, TLS, the shield, and a certificate at our door

Cloudflare already holds our domain names. We keep it in front: every request from the internet goes to Cloudflare first, and Cloudflare forwards it to Civo. That gives us protection against floods of traffic, a basic web application firewall, and TLS (the padlock) at the edge, for free. Two details matter for a sign-in service, and both are solved.

DNS

The phone book: id.answerable.org → our load balancer. Records are "proxied", which means visitors see Cloudflare's address, not ours.

TLS, twice

Cloudflare's certificate faces the visitor; a second certificate faces Cloudflare, so the hop between them is encrypted too ("Full strict"). That second one comes from Cloudflare's own Origin CA: Terraform asks for it, it lasts fifteen years, and only Cloudflare trusts it, which is exactly right, since only Cloudflare ever reaches us. Free, and nothing to renew.

Authenticated origin pulls

Cloudflare presents a certificate we issued when it connects, and Traefik checks it. Terraform makes that certificate and uploads it to the zone. Without it, anyone could bypass Cloudflare by calling our address directly, or send traffic through another Cloudflare customer's zone. Free.

What Cloudflare must not do here

No caching of sign-in or MCP responses, and no "are you a robot?" challenges on the API hostnames: AI tools and our own services are not browsers and would be blocked. Those are switched off by configuration rules.

4 · The private network

A Civo private network and three firewalls

A Civo private network is a fenced area in one region where our resources can talk to each other without crossing the internet. Inside it, firewalls are the door policies: short lists of who may connect to what, on which port. The load balancer admits Cloudflare only; the database admits the private network only; the cluster's control plane answers the internet but only to a valid credential, as every Civo cluster does, which is what lets GitHub deploy. Civo has one London region, LON1, so resilience comes from several nodes and extra database nodes rather than from separate data centres.

5 · The front door

The Civo load balancer and Traefik, the receptionist

The Civo load balancer is created for us the moment the cluster asks for one; it has the public address and the Cloudflare-only firewall, and it passes connections through untouched. Traefik, a program running inside the cluster, is the real receptionist: it unwraps TLS, checks Cloudflare's certificate, reads the hostname the visitor asked for and hands the request to a healthy copy of the right service. The certificate it presents to Cloudflare is the Origin CA one Terraform requested; there is no renewal to run.

6 · Containers on Kubernetes

The cluster, nodes, pods, Deployments, autoscaling

A container is our program plus everything it needs, sealed in a box that runs the same everywhere. Kubernetes is the manager that keeps the right number of boxes running across a set of machines, the nodes. Civo runs the manager for free; we pay for the nodes. A running box is called a pod, and a Deployment is a promise such as "keep two copies of the ID image running, replace any that die, and send them traffic only once they answer the health check." Our three Deployments, with everything around them, are written once as a Helm chart.

The Helm chart

One folder, charts/answerable, describing the three Deployments, their health checks, resource limits, hardening (non-root, read-only, no extra privileges), the entry rules, the network rules, the migration Jobs and the secrets. A small values file per environment sets the sizes and hostnames. The same chart installs on any Kubernetes cluster.

Autoscaling and resilience

A rule starts another copy when the existing ones are busy and stops it when quiet; production floors at two copies, spread across nodes, and a budget rule keeps at least one up during node maintenance.

Network rules inside the cluster

Each service accepts connections only from Traefik and opens connections only to the database, DNS, ID and the identity providers. A compromised pod cannot wander.

Sizes and cost

Staging: two Medium nodes (2 vCPU, 4 GB each), $43.46 a month, running one copy of everything. Production: three Medium nodes, $65.19, running two copies of each service. The control plane is free.

Why Kubernetes

It is what Civo sells, and it runs every service the same way, with scaling, rollouts and network rules built in.

7 · Images and the registry

Docker images on GHCR

An image is the sealed box before it runs: our code and the Bun runtime, built once by GitHub from a Dockerfile for amd64, the architecture Civo's nodes run. The images are stored on GHCR, GitHub's own registry. Every image is named after the exact commit it came from, carries a record of how it was built and a signature. Production never rebuilds: it runs the same image bytes that staging proved, and refuses a commit staging never shipped.

8 · The database

Civo Database, PostgreSQL 17

All state lives in one PostgreSQL 17 server per environment, run by Civo as a managed service: Civo patches it and keeps automatic backups; extra nodes that take over if one fails are an option we take once a failover has been measured. Inside the server are three separate databases, one per program, each with two logins. Two honest notes: Civo's PostgreSQL service is labelled beta, and its backup schedule and restore procedure are not documented, so the plan rehearses a restore before any production data exists.

Sizes and cost

Staging: Small (2 vCPU, 4 GB, 40 GB), $43.45 a month. Production: Medium (4 vCPU, 8 GB, 80 GB), $86.91, on one node to begin with.

TLS "verify-full"

Civo documents nothing about its database's certificate, so on the first run the bootstrap Job records the one the database presents, inside the private network, and logs its fingerprint; from then on every service checks the database against it, so no one can sit between a pod and the database.

The growing line

At 30,000 daily users the audit and evidence tables grow about 15 GB a month because nothing is ever deleted. On Civo storage comes bundled with the size, so an 80 GB database fills in about five months. Deciding how long to keep them (the open question Q-EVIDENCE-RETENTION) is a prerequisite for production, not a later optimisation.

Why not run Postgres ourselves

Running it in the cluster would hand us backups, failover and patching, exactly the work a managed service exists to take.

9 · Secrets

Pasted once into GitHub, generated everywhere else

Five values exist before anything is built, because they are born in someone else's console: the Civo key, the Cloudflare token, the Entra app's ID and secret, and a GitHub token that lets our workflows write secrets. You paste them into the environment once, in the browser; GitHub encrypts each before it even reaches GitHub, stores it write-only, hides it in logs and hands it only to the workflow steps that name it. Everything else is made where it is used and never seen by a person: a workflow generates ID's three random secrets into the environment; Terraform makes the certificates' keys and the deploy's credentials and puts the latter into the environment; the bootstrap and registration Jobs make the database passwords and the machine-client secrets straight into the cluster. Nothing is typed into a terminal.

Rotation

The root secret and the upstream keys: the bootstrap workflow's rotate input, then a tag; the next deploy rolls ID. A vendor token: paste the new one. A database password or a machine-client secret: empty its Secret and tag; the Jobs make a new one.

What is deliberately not here

A secret server with per-service identities and a read audit (OpenBao was planned and withdrawn). No pod holds an API token, so a pod can read only the Secrets mounted into it; for three services and one operator a read audit has no reader. It returns when a second team or a compliance need asks for it.

10 · Logs and alarms

Logs, for now

Logs

Each pod's printed lines are read with kubectl logs; a failed deploy prints the migration and ops Jobs' logs in the workflow. ID prints a summary of its traffic and database pool every 30 seconds; those lines are the health signal its operations manual describes.

The smoke test

After every deploy, a check of every hostname through Cloudflare: health, readiness, discovery, signing keys, the MCPs' metadata. Civo's dashboard shows the database's own metrics.

Not yet: an agent and alerts

Civo has no logging or alerting service. A metrics and logs agent with alerts is switched on when a measurement says it pays; the chart carried one, switched off, and it was removed on 19 October.

Not yet: tracing

The Toolbox's OpenTelemetry export stays off until there is somewhere to send it.

11 · From a push to a deploy

GitHub Actions and the tag

Nobody deploys from a laptop. A tag staging/<name> on a commit of main starts a GitHub Actions run that tests, applies the infrastructure, builds, migrates and deploys staging. A tag production/<name> on a commit staging has shipped does the same for production, after you approve it. The deploy step signs in to the cluster with a token that may touch one namespace and nothing else; the account's API key is handed to the Terraform step only.

12 · Terraform and the chart

Everything above, as code

Terraform reads files that describe the cloud layer (this network, these firewalls, this cluster, this database, these DNS records) and makes Civo and Cloudflare match them. Run it twice and it changes nothing; change a file and it shows exactly what will change before doing it. The Helm chart does the same job for everything inside the cluster. Both live in the repository, reviewed like any code, so there is no clicking around a console that nobody can reproduce later.

Layout

infra/civo, one root with a values file per environment; charts/answerable for our services and charts/platform for Traefik. Terraform also owns the certificates and writes the deploy credentials into the GitHub environment.

State

Terraform remembers what it created in a "state" file, kept in each account's Civo object store, which the bootstrap workflow creates. The state holds what Terraform's providers generate (the database password, the admin credential, the certificates' keys), so the bucket's credential is guarded like the account's key.

Checks without the cloud

bun run infra:check lints the chart, validates and policy-scans the Terraform and the workflows on every push, with no cloud access.

Why Terraform

Every resource is readable in the repository, and Civo, Cloudflare and GitHub have providers for it, so one tool covers the whole plan, and it runs from GitHub before every deploy.

13 · The dress rehearsal

A cluster on the laptop, with the real chart

Before anything touches Civo, the same images and the same chart run on a laptop in a throwaway Kubernetes cluster (kind): Traefik, self-signed certificates standing in for Cloudflare's, a TLS-only PostgreSQL 17 with the two-login scheme, and NODE_ENV=production. A test builds the images, installs the chart, runs the migrations and the one-off Jobs, signs a staff member in through the cluster and calls a tool on the admin MCP. If that passes, the images and the chart are known good; the Civo layer is proved by Terraform's own checks and the staging deploy.

bootstrap

A one-off Job that records the database's certificate on the first run, then turns an empty database server into the three databases and six logins, writing the passwords it generates into Kubernetes Secrets. Safe to run again; it changes nothing the second time, and recreates what a rebuilt cluster lost.

migrate

Each service's own migration script, run from its image with the owner login, before new pods start.

register and make-admin

Tells ID about the Toolbox and the admin MCP (their addresses, their machine identities, which staff may use them), exactly as the public docs describe with cURL, stores the generated client secrets in the cluster, and connects the staff directory. After your first sign-in, make-admin makes you the administrator and locks the root secret.

14 · What is deliberately missing

Named as "not yet", with the reason

  • Caching or challenges at Cloudflare for sign-in and MCP traffic. Caching would serve one person's response to another; challenges would block AI tools.
  • A GitOps controller in the cluster. The pull model would remove even the namespace-limited deploy token from GitHub and let the control plane close to the internet; it is the next step if that token ever worries us.
  • Image signature enforcement in the cluster. Images are signed today; a policy that refuses unsigned ones comes later.
  • A secret server. OpenBao was planned and withdrawn: pods hold no API token and read only their own Secrets, and a read audit for three services and one operator has no reader. It returns with a second team or a compliance need.
  • A metrics and logs agent, and alerts. When a measurement says they pay.
  • A second region. Civo has one London region; a regional failure is a later decision with a real cost.
  • Redis. Nothing in the code reads it yet.
  • Keeping production warm from day one. It costs nothing until the first production tag, and that run proves it works.
The numbers to remember: staging about $103 a month; production about $170 on a single database node; and the audit log grows every month until retention is decided.
