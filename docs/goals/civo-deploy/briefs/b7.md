# B7a — First staging deployment

**Executor:** the owner, with an agent that has the browser. **Depends on:** B0 to B6 on `main`, and [D28](../decisions.md). **Decisions:** [D8](../decisions.md), [D13](../decisions.md), [D26](../decisions.md), [D28](../decisions.md).

> **Revised 18 October 2026.** The first run is now the setup commands, and [`staging-tutorial.html`](../staging-tutorial.html) walks the owner through them; this brief keeps what the first run must prove and record. OpenBao is [B7b](b7b.md) and the production rehearsal is [B7c](b7c.md).

## Goal

Staging is live on Civo and used: a person signs in through the real Entra, Claude Code talks to the staging admin MCP and onboards a test organisation into the staging Toolbox, the preflight passes, a restore drill succeeds, and the numbers are measured.

## Owner inputs

- The Civo account `answerable-staging` with its quota raised if needed, its API key, and the zone `answerable-staging.uk` on Cloudflare with Bot Fight Mode off.
- The two Cloudflare tokens of [`infra/README.md`](../../../../infra/README.md) § Accounts, once per environment: Terraform's (six permissions) and cert-manager's (Zone Read and DNS Edit).
- The Entra app registration, multi-tenant, with the redirect URIs `https://id.answerable-staging.uk/auth/sso/callback` and `https://id.answerable-staging.uk/login`, and a client secret with its expiry noted (`docs/06` § Platform applications); optionally a Google client for staging.
- The first sign-in, and the admin consent for the app in Answerable's own tenant.

## Steps, in order

0. **First run**: [`infra/README.md`](../../../../infra/README.md) § First-time setup, steps 0 to 15, as the tutorial lays them out. Record the date, each apply's duration and resource count, the database certificate's SHA-256 fingerprint, and the answer to every question in [`infra/civo/README.md`](../../../../infra/civo/README.md) § What the first apply must confirm (the state lock, the certificate's names, the administrator database, the pod range, the Kubernetes version Civo chose).
1. **The edge**: the three proxied records resolve to Cloudflare addresses; the zone's edge certificate is `active`. **Lockdown proof**: `curl --resolve id.answerable-staging.uk:443:<load balancer address> https://id.answerable-staging.uk/healthz` without the origin-pull client certificate fails the TLS handshake, and from an address outside Cloudflare's ranges the connection times out at the firewall.
2. **First deploy, measured**: image sizes on GHCR, build time, time from push to a green smoke test, and the ID container's time from start to `readyz`.
3. **Address proof**: make one deliberately failing request to `/auth/*` through Cloudflare with a forged `X-Forwarded-For: 203.0.113.9`, then read the newest `auth.signin.failed` or denial row through `GET /api/admin/v1/audit-events` with a staff token: its address must be the machine's real public address, not `203.0.113.9` and not a Cloudflare address. This is the end-to-end proof of [D22](../decisions.md)'s trusted-proxy chain.
4. **Claude Code against staging** (`https://admin-mcp.answerable-staging.uk/mcp`): `admin_whoami` shows the owner's roles; onboard a test organisation (a second Entra tenant the owner controls, or Google Workspace; otherwise onboard it and stop before its sign-in) and enable the Toolbox for it through the admin MCP, as the admin lane story does (`apps/web/content/docs/admin/setup.mdx` § Try it locally).
5. **Preflight**: run `ops:preflight` (`apps/id`) once in the cluster, as a one-off Job from the ID image with the runtime `DATABASE_URL`, and record its counts.
6. **Restore drill**: [`infra/README.md`](../../../../infra/README.md) § Restore, The database. Take a Civo backup, restore it to a new database, run the preflight against the copy, time the restore (RTO), note the backup's age (RPO) and what Civo's backup actually is, delete the copy, and rewrite that section with what happened. This is E7's input, not its closure.
7. **Measure**: `max_connections` on the database, its connections at idle and after a sign-in, `/readyz` and `/.well-known/openid-configuration` latency p50 and p99 over an hour, log ingestion per day, and the first week's Civo bill extrapolated to a month against the estimate (about $103).
8. **Credentials**: confirm the Civo API key, both Cloudflare tokens, the Entra secret, the state credential and the `age` key are held only by the owner and in the GitHub environments `publish-env` wrote, and that the terminal used for the setup is closed.
9. **Evidence**: `reports/staging-evidence.md` with every number above, the dates, what passed, what was skipped and why; link it from `docs/12` and from the release plan's E5 to E7 inputs.

Alerts are Not yet ([`docs/12`](../../../12-deployment.md)); the production rehearsal is [B7c](b7c.md).

## Notes from the build

### Setup commands

Built on 13 October 2026 (Agent G, branch from `claude/civo-deploy` at 7a309c3): the workspace `infra/setup` (`@answerable/infra-setup`, `bun run setup <command> --environment <env>`) with `age-init`, `first-apply`, `origin-pull`, `database-ca`, `init-secrets`, `publish-env`, `id-first-run` and `id-make-admin`. The first run in order, with what each command needs, writes and how to undo it, is [`infra/setup/README.md`](../../../../infra/setup/README.md); `infra/civo/README.md` § First apply links to it.

What differed from the brief, and why:

- **Rotating the origin-pull certificate does not upload first.** Cloudflare's [manage certificates](https://developers.cloudflare.com/ssl/origin-configuration/authenticated-origin-pull/set-up/manage-certificates/) page says that with two certificates active "the most recently deployed certificate will be the one enabled and used", so an upload before Traefik trusts the new CA refuses every request until the apply. `origin-pull --force` writes `ca.pem` with the new CA and the old one, waits while the operator applies, uploads, waits for `active`, then writes the new CA alone and prints the `curl` that deletes each older certificate. Answering `no` at the pause restores the old `ca.pem` and uploads nothing.
- **Cloudflare's route.** The API reference marks the top-level `origin_tls_client_auth` methods deprecated in favour of the `zone_certificates` sub-resource, which has the same route: `POST /zones/{zone_id}/origin_tls_client_auth` with `certificate` and `private_key`, permission SSL and Certificates Write. It lists no status values beyond `active`; the command fails on `deployment_timed_out`, `deleted`, `pending_deletion` and `deletion_timed_out` and keeps polling anything else for `--wait` seconds (default 300).
- **`terraform init -input=false -migrate-state` fails** ("Can't ask approval for state migration when interactive input is disabled"), measured with Terraform 1.16.5 against a local backend standing in for the bucket. Without `--yes` the command lets Terraform ask; with `--yes` it passes `-force-copy -input=false`. A targeted apply does write the outputs that depend on the target, so `state_access_key_id` and `state_secret_access_key` are readable after step 2.
- **The state credential after the migration.** It lives only in the bucket it opens, so every later command that reads Terraform's state needs `STATE_ACCESS_KEY_ID` and `STATE_SECRET_ACCESS_KEY` from the operator (named so on 18 October; `infra/civo/terraform.sh` and the setup commands hand them to the S3 backend). `first-apply` prints the key ID (a non-sensitive output) and `civo objectstore credential secret -a <key id>`, which is from Civo's documentation and unproved here: the `civo` CLI is not installed on this machine.
- **`database-ca`'s pod.** The pinned `postgres:17.11-alpine` image has no `openssl` binary, so the printed `kubectl run` uses `alpine:3.24.2` pinned by digest and installs `openssl` when it starts. That needs egress from the `default` namespace, which holds at step 5 (no NetworkPolicy exists yet). Revised on 13 October at the coordinator's request: both roots output the cluster's admin kubeconfig as `admin_kubeconfig` (sensitive, from the cluster module's `kubeconfig`, which the provider marks sensitive and writes only with `write_kubeconfig = true`), and `database-ca` runs the pod itself through it, from a 0600 file in a temporary directory that is deleted afterwards. `--from-stdin` stays for operators who run the pod themselves.
- **`publish-env` keeps existing secrets** and lists them, rather than refusing the whole run, so a rerun after one rotation sets only what is missing; `--force` replaces. It also refuses `--enable` for production.
- **`init-secrets --rotate`** refuses `BETTER_AUTH_SECRET` (it encrypts ID's stored signing keys; the ring `BETTER_AUTH_SECRETS` is the way) and rotates `UPSTREAM_TOKEN_SECRETS` by putting a new version first and keeping the previous ones.
- **OpenSSL 3 is required.** macOS's `/usr/bin/openssl` is LibreSSL 3.3.6; the commands refuse it with the fix.

Measured on the first build: 79 unit tests, 100% lines and functions; `bun run --filter @answerable/infra-setup prove`, 31 of 31 checks in 6 s with the images pulled: real `age-keygen` and `sops` 3.13.3 (a multi-document file encrypted from standard input under the creation rule and decrypted back), real OpenSSL 3.6.2 (P-256, 3650 and 1825 days, the client signed by the CA, the uploaded key matching the client certificate, the temporary directory gone), and PostgreSQL 17.11 with TLS in Docker read from this machine and through the pod command's script in the Alpine image.

For the next agent and the coordinator:

- **Resolved: the names are readable now.** `sops` with a rule of only `path_regex` and `age` encrypted `apiVersion`, `kind` and `metadata.name` too, so a reviewer could not see which Secret changed, which [`portability.md`](../portability.md) promises. The coordinator approved `encrypted_regex: ^(data|stringData)$` on every rule; `age-init` writes it and adds it to a rule that lacks it. The proof shows the names and keys in clear text, the values encrypted, a renamed Secret refused by `sops`' MAC, and the deploy's `sops --decrypt | kubectl apply` creating the three Secrets in a kind cluster. After the delta: 81 unit tests at 100%, and the proof at 41 of 41 checks in 86 s, kind cluster included.
- `database_admin_url`, the `DEPLOY_STAGING` gate and the repository name in the signature check landed on `claude/civo-deploy` after the first build.
