# B7a — First staging run

**Executor:** the owner, with an agent that has the browser. **Depends on:** the 19 October simplification on `main`. **Decisions:** [D8](../decisions.md), [D23](../decisions.md), [D30](../decisions.md), [D32](../decisions.md) to [D38](../decisions.md).

## Goal

Staging is live on Civo from GitHub alone and used: a person signs in through the real Entra, Claude Code talks to the staging admin MCP and onboards a test organisation into the staging Toolbox, the preflight passes, a restore drill succeeds, and the numbers are measured. Nothing is run from a laptop except `git tag` and the browser.

## Owner inputs

- The Civo account `answerable-staging`, its API key, and the zone `answerable-staging.uk` on Cloudflare with Bot Fight Mode off.
- One Cloudflare token scoped to that zone with Zone > Zone > Read, Zone > DNS > Edit, Zone > SSL and Certificates > Edit, Zone > Zone Settings > Edit, Zone > Config Rules > Edit and Zone > Cache Rules > Edit ([`infra/civo/README.md`](../../../../infra/civo/README.md) § Credentials).
- The Entra app registration, multi-tenant, with the redirect URIs `https://id.answerable-staging.uk/auth/sso/callback` and `https://id.answerable-staging.uk/login`, and a client secret with its expiry noted (`docs/06` § Platform applications); the tenant ID of Answerable's own staff directory.
- A fine-grained GitHub token for `Rieranthony/answerable-monorepo` alone, with read and write on Environments and Secrets, and an expiry in the owner's calendar.
- The GitHub environment `staging`, created with no deployment-branch restriction (Terraform restricts it to `main` and `staging/*` on the first apply), holding the five secrets: `CIVO_TOKEN`, `CLOUDFLARE_API_TOKEN`, `MICROSOFT_CLIENT_ID`, `MICROSOFT_CLIENT_SECRET`, `GH_SECRETS_TOKEN`.
- The first sign-in, and the admin consent for the app in Answerable's own tenant.

## Steps, in order

0. **The environment**: the inputs above, then `id.staffDomain: answerable.org` and `id.entraTenant: <tenant ID>` committed in `charts/answerable/values-civo-staging.yaml`. Run the **Bootstrap** workflow for `staging` and read its summary: the state bucket exists and the environment holds its credential and ID's secrets.
1. **The first tag**: `git tag staging/first && git push origin staging/first`, then `gh run watch`. Record each job's duration: CI, the infrastructure (the first apply creates the cluster and the database), the four builds, the deploy (the bootstrap Job's log names the database certificate's SHA-256 fingerprint: record it), the smoke test. If the deploy failed to pull an image, make the four GHCR packages public (`answerable/id`, `toolbox`, `admin-mcp`, `ops`: Package settings > Change visibility) and rerun the failed jobs. Record the answer to every question in [`infra/civo/README.md`](../../../../infra/civo/README.md) § What the first apply must confirm.
2. **The edge**: the three proxied records resolve to Cloudflare addresses; the zone's edge certificate is `active`; the origin certificate's expiry is Terraform's `origin_certificate_expires_on` output in the run's log. **Lockdown proof**: `curl --resolve id.answerable-staging.uk:443:<load balancer address> https://id.answerable-staging.uk/healthz` without the origin-pull client certificate fails the TLS handshake, and from an address outside Cloudflare's ranges the connection times out at the firewall.
3. **Address proof**: one deliberately failing request to `/auth/*` through Cloudflare with a forged `X-Forwarded-For: 203.0.113.9`, then the newest `auth.signin.failed` or denial row through `GET /api/admin/v1/audit-events` with a staff token: its address must be the machine's real public address, not `203.0.113.9` and not a Cloudflare address.
4. **Sign in** at `https://id.answerable-staging.uk/login` with your work account, then run the **Ops** workflow with `staging`, `make-admin` and your email: its log says you are in `answerable-owner` and `platform-admins` and that root is locked.
5. **Claude Code against staging** (`https://admin-mcp.answerable-staging.uk/mcp`, the `claude mcp add` lines are in the register Job's log): `admin_whoami` shows `owner`; onboard a test organisation and enable the Toolbox for it through the admin MCP, as `apps/web/content/docs/admin/setup.mdx` § Try it locally does.
6. **Preflight**: `ops:preflight` (`apps/id`) once in the cluster, as a one-off Job from the ID image with the runtime `DATABASE_URL`; record its counts.
7. **Restore drill**: [`infra/README.md`](../../../../infra/README.md) § Restore. Take a Civo backup, restore it to a new database, run the preflight against the copy, time the restore (RTO), note the backup's age (RPO) and what Civo's backup actually is, delete the copy, and rewrite that section with what happened. This is E7's input, not its closure.
8. **Measure**: `max_connections`, connections at idle and after a sign-in, `/readyz` and discovery latency p50 and p99 over an hour, log volume per day, and the first week's Civo bill extrapolated to a month against the estimate (about $103).
9. **Credentials**: confirm that the five pasted secrets exist nowhere but in the GitHub environment and their vendors' consoles, and that no terminal held one.
10. **Evidence**: `reports/staging-evidence.md` with every number above, the dates, what passed, what was skipped and why; link it from `docs/12` and from the release plan's E5 to E7 inputs.

## Constraints

- No secret value in any report, log excerpt or commit; redact before pasting.
- Production is never deployed from a laptop; only the workflow.
- A failed step is fixed in a brief-sized change on `main`, tagged again; the evidence report says it happened.

## Acceptance

The evidence report exists and is linked; staging answers every smoke check; the owner has used Claude Code against staging; the restore drill has run; every credential is held only where step 9 says.
