# B1 — Least-privilege database roles for the Toolbox and the admin MCP

**Executor:** Codex (GPT-6 Astra, medium); Fable reviews and lands. **Depends on:** nothing. **Decisions:** [D4](../decisions.md), [D5](../decisions.md), [D26](../decisions.md).

## Goal

The Toolbox and the admin MCP run as restricted Postgres logins, as ID does, so that the evidence chain's append-only and erase-only triggers hold against the application credential, and migrations are the only path that needs the owner.

## Facts to start from

- Today both servers and both migrate scripts use the owner login (`.env.example`: `TOOLBOX_DATABASE_URL`, `ADMIN_DATABASE_URL`), and nothing provisions a runtime role for them ([findings](../findings.md#what-has-to-run)).
- ID's pattern: `apps/id/scripts/migrate.ts` migrates with `DATABASE_MIGRATION_URL` then calls `configureRuntimeRole` for `DATABASE_RUNTIME_ROLE`; `apps/id/src/db/runtime-role.ts` grants and `assertRuntimeRole` refuses an unsafe role before listening; `infra/postgres/init/002-create-runtime-role.sql` creates the local login.
- `packages/mcp-postgres` owns `evidence_events`, `evidence_payloads`, `intents` and `schema_migrations`; the Toolbox adds `providers`, `capabilities`, `organisation_catalogue`, `host_clients` and the rest of `mcps/toolbox/migrations/0001_initial.sql`; the admin MCP has no tables of its own.
- The acceptance kit creates databases on its own Postgres (`packages/acceptance/src/id.ts` `createDatabase`) and starts the servers with owner URLs; the admin lane and host lane do the same.

## Failing tests first

1. `packages/mcp-postgres/src/runtime-role.test.ts`: `configureRuntimeRole(db, role, grants)` makes a role that can insert and select `evidence_events` but gets the trigger's refusal on update and delete and a permission error on `DROP TRIGGER` and `ALTER TABLE`; can insert, select and update `evidence_payloads`; can select, insert, update and delete `intents`; has no `CREATE` on schema `public` and no `TEMP` on the database; repeated runs change nothing. `assertRuntimeRole(db)` refuses a superuser, a `CREATEROLE`, `CREATEDB` or `BYPASSRLS` role, a role that owns any table in `public`, and the owner itself, naming the attribute in the error; accepts the provisioned role.
2. `mcps/toolbox/src/db/migrate.test.ts` (or where the Toolbox's migrator is tested): after `migrate` with the owner, the runtime role holds exactly the grants the Toolbox's tables need (the catalogue is written at boot and read on every request; host clients are written by the admin API) and nothing on `schema_migrations` beyond `SELECT`.
3. `mcps/toolbox/src/server.test.ts` and `mcps/admin/src/server.test.ts` (entry-point tests): starting with an owner URL exits before listening with a message naming the privilege; starting with the runtime URL serves.
4. `packages/acceptance`: the journeys unchanged in intent, now against servers started on runtime URLs; the kit's `createDatabase` returns both the owner and the runtime URL.

## What to build

- `packages/mcp-postgres`: `configureRuntimeRole(db, role, grants: Grant[])` and `assertRuntimeRole(db)` exported, with the package's own `runtimeGrants` (its three tables) exported for servers to extend; `migrate(db, directories)` is unchanged. The grants are idempotent `GRANT`s with the explicit `REVOKE` of `CREATE ON SCHEMA public` and `TEMP ON DATABASE` for the role, and `ALTER DEFAULT PRIVILEGES` so that a later migration's table is covered only when the migrator grants it again (no implicit grants: a new table needs a new grant line, as in ID).
- `mcps/toolbox/scripts/migrate.ts` and `mcps/admin/scripts/migrate.ts`: migrate with `TOOLBOX_DATABASE_MIGRATION_URL` / `ADMIN_DATABASE_MIGRATION_URL`, then provision `TOOLBOX_DATABASE_RUNTIME_ROLE` / `ADMIN_DATABASE_RUNTIME_ROLE` (defaults `answerable_toolbox_runtime`, `answerable_admin_runtime`); `--test` keeps resetting the test database with the owner and provisions the role too, so suites run against a provisioned schema.
- `mcps/toolbox/src/server.ts`, `mcps/admin/src/server.ts`: `await assertRuntimeRole(db)` before `Bun.serve`, closing the pool on failure and exiting 1 with the message, as the admin MCP already does for `readPlatform`.
- `infra/postgres/init/005-create-mcp-runtime-roles.sql`: the two local logins with password `answerable`, `NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOREPLICATION NOBYPASSRLS`. Existing volumes need the file run by hand; say so in the README's local environment section as `002` already does for ID.
- `.env.example`: the servers' `*_DATABASE_URL` on the runtime logins, the new `*_DATABASE_MIGRATION_URL` on the owner; `default.env`: the four new variables.
- `packages/acceptance`: `createDatabase(name)` also creates `<name>_runtime`, returns `{ owner, runtime }`; the journeys, `admin-lane.ts` and `host-lane.ts` migrate with the owner and start the servers with the runtime URL.
- Docs: `apps/web/content/docs/toolbox/index.mdx` (configuration table and the migrate command), `apps/web/content/docs/admin/setup.mdx` and `admin/index.mdx` where they name the variables, `packages/mcp-postgres/README.md`, `mcps/toolbox/README.md`, `mcps/admin/README.md`; the reference page regenerates if a documented export changed (`bun run --filter @answerable/mcp reference` is for `@answerable/mcp`; `mcp-postgres` has no generated reference, so its README carries the two functions).
- `docs/09-mcp-design-standard.md` or `docs/08-capability-platform.md`: one sentence where the standard describes a server's database, saying a server runs as a restricted login and migrates as the owner. Check the standard's own rule list first and add the rule where the others are.

## Constraints

- 100% line and function coverage in `packages/mcp-postgres`, `mcps/toolbox`, `mcps/admin`; the acceptance kit has no gate.
- `mcp:test` runs suites concurrently and no two may reset one database: the runtime-role tests use each suite's own test database.
- No semicolons in these workspaces; British spelling in docs; an applied migration file never changes (the grants are not a migration: they run after every migrate, as ID's do).
- Update the two servers' `CHANGELOG.md` and `manifest.json` only if a definition changed (it should not).

**Decisions made while building, for review.**

- **No `UPDATE` or `DELETE` on `evidence_events` at all.** The brief's failing test expected the trigger's refusal on the runtime role; that needs the role to hold the privileges. Least privilege, and ID's precedent for `audit_events`, say otherwise: the role gets `permission denied`, the trigger stays as the second layer, and `assertRuntimeRole` refuses a login that holds either privilege. The trigger's refusal against the runtime role is proved on `evidence_payloads`, which the role may update (only an erasure passes). `DROP TRIGGER` and `ALTER TABLE … DISABLE TRIGGER` answer `must be owner of relation` and `must be owner of table` on 17.
- **Nothing on `schema_migrations`**, where the brief allowed `SELECT`: nothing reads it at run time.
- **`providers` needs `SELECT`.** `insert … on conflict (id) do nothing` reads the arbiter column: with `INSERT` alone PostgreSQL 17 answers `permission denied for table` (measured with a probe role).
- **The in-process suites serve through a runtime login.** Beyond the brief: `serving()` in each server's `src/test/database.ts` migrates as the owner and returns a fresh login with the server's grants, and every Toolbox and admin MCP test that serves uses it, so 80 and 122 tests prove the grants are enough before the acceptance does. Inspection queries in those files run on the same login (it may read every table it serves).
- **`005` is idempotent**: it creates each login, or turns a role that a migration created first (without login) into the login. It ran at `initdb` on a fresh 17 volume, and twice by hand.
- **The two servers' changelogs and manifests are untouched**, as the constraint says: no definition changed. Their start-up behaviour did; the integrator may want a line in each changelog.

**What 17 revealed.** Nothing in the schema. ID's migration proofs and its 1,564 tests pass unchanged on 17.9; the catalogue comparison found no difference. 17 shows its new `MAINTAIN` privilege in ACLs (`arwdDxtm`); `revoke all` covers it and the runtime roles never hold it.

**For B3 (bootstrap).** `configureRuntimeRole`, like ID's, revokes `TEMP` on the database and `CREATE` on schema `public` from `PUBLIC`. Those revokes take effect only when the migrating owner owns the database (or the schema); otherwise PostgreSQL warns and changes nothing, and the server then refuses to start with `holds TEMP on database <name>`. Bootstrap must create each database owned by its owner login.
