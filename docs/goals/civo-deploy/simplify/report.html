Simplify the deployment

Audit of infra/*, charts/*, the workflows and the remaining briefs, 19 October 2026, before B7a. Every claim below was tested: a grep, a render, a provider schema, GitHub's run history, or the vendor's page. Planning files and probe results: docs/goals/civo-deploy/simplify/.

Decided, later the same day The owner asked for as much automation as possible, with every secret in a GitHub environment and nothing done from a laptop. Decision A below is therefore superseded: Terraform runs from GitHub for both environments and the state stays in Civo's object store, created by a bootstrap workflow. B, D and E stand as recommended; a tag staging/<name> or production/<name> ships. The shape as built is in simplify/task_plan.md.

Verdict

The deployment is sound where it matters: one Civo account per environment, Cloudflare as the only path, verified TLS, least-privilege logins, images by digest, a namespace-scoped deploy token, and a local proof that runs in CI. Around that core it carries pieces built for cases that no longer exist: pull requests, three clouds, a Grafana workspace, an unknown node architecture, a future diagnostic. Those go now. Four larger pieces rest on choices worth revisiting before the first apply, because each is simpler to change today than after staging exists. Those are the four decisions at the end.

Decisions recommended option first

  1. A. Terraform runs from your machine only, and its state lives encrypted in the repository.

    Today staging's Terraform applies from CI on every push, so the unscoped, never-expiring Civo key, the Cloudflare token and the state credential sit in a GitHub environment with no reviewer, readable by any branch of the repository (the pipeline README says so). Production's Terraform cannot run from CI at all (D30), so the two environments already differ. State lives in a 500 GB object-store block per environment ($5.43 a month each) that holds a few kilobytes, created by a two-phase bootstrap with a lock question the first apply must answer.

    Recommended: both environments apply by hand from a trusted machine, the way production must; the state file is sops-encrypted with the environment's age key next to secrets.enc.yaml (it holds the same class of secret, and a lost key costs the same either way). A 30-line wrapper decrypts before Terraform and re-encrypts after. Deletes: infra.yml, the infra job, the apply_infra step, the infra-staging environment, the state module, both backend.tf, terraform.sh's credential mapping, STATE_* everywhere, steps 2 to 4 of first-apply, and every Civo and Cloudflare credential from GitHub. Then S2 becomes a plain change. Cost: a Terraform change is applied by you, not by a push; one operator at a time (true today).

    Alternative: keep the CI apply and the bucket. Then only infra.yml goes.

  2. B. Production's Kubernetes API is reachable from the internet, authenticated by the cluster, as staging's is.

    Civo clusters always have a public API. Staging admits the internet on 6443 (D30); production admits only ALLOWED_API_CIDRS, which GitHub's runners are not in, so promote-production.yml cannot run, and nobody has scheduled the GitOps or tunnel follow-up. The closed API also raises two first-apply questions about nodes joining with 6443 shut to the private network.

    Recommended: the same posture in both environments, the one every default Civo, DigitalOcean and GKE cluster has: TLS, then a credential. The deploy holds a token that reaches one namespace; the admin credential exists only in state. Deletes api_open_to_internet, allowed_api_cidrs, their validations and tests, ALLOWED_API_CIDRS in the setup and the workflows, and the two questions; promote-production.yml works on day one. Recorded as D30 resolved, with GitOps named as the hardening if it is ever wanted.

    Alternative: keep production closed. Then production deploys by hand from your machine (deploy --environment production, which exists) and promote-production.yml is deleted rather than kept unusable.

  3. D. Origin certificates from Cloudflare's Origin CA, issued by Terraform, instead of cert-manager with Let's Encrypt.

    Only Cloudflare ever reaches the services, by design and by firewall. Yet the origin presents a public certificate from Let's Encrypt, obtained by cert-manager through a DNS-01 challenge with a second Cloudflare token kept in the sops file, renewed every two months, and "proved only by rendering" until the first apply. Cloudflare's Origin CA issues certificates that only Cloudflare trusts, for up to 15 years, through the token Terraform already holds (Zone, SSL and Certificates, Edit), and they are "compatible with Strict SSL mode".

    Recommended: Terraform makes the key, the request and the certificate (cloudflare_origin_ca_certificate, in the pinned provider) and writes the TLS Secret into answerable, which it already manages. Deletes cert-manager (a controller, CRDs, two webhooks, a startup Job, 80 lines of issuers), the second token, the cloudflare-api-token Secret and its rotation, the issuer annotation and values, and one first-apply unknown. Cost: the key sits in Terraform state (the same class as the admin kubeconfig already there), rotation is a -replace with the expiry date recorded, and the kind stack makes its three test authorities with openssl instead of seven cert-manager objects. This is the largest change of the set; the proof is infra:test and CI.

    Alternative: keep cert-manager and Let's Encrypt.

  4. E. OpenBao (D29, brief B7b): not yet.

    D29 promises OpenBao right after staging: three replicas in production, Raft, a seal key that lives in the same sops file, Kubernetes auth, policies, snapshots, alerts, a ceremony. The gains named were per-service identities, a read audit and revocation. No pod mounts an API token, so a pod can read only the Secrets mounted into it; revocation is a changed Secret; a read audit for three services and one operator has no reader. The cost is a stateful product to run.

    Recommended: record OpenBao as Not yet with a trigger (a second team, or a compliance need), keep sops, and remove the sentences that promise it. No code changes.

    Alternative: keep B7b as planned.

Applied unless you say otherwise

  • amd64 only (row 3 above), on Civo's own word.
  • Production's database on one node, not three. Civo says a multi-node database "can continue to operate even if one or more nodes fail", and nothing about how; the two extra nodes are about $173 a month for a database still in beta. Raise it after B7c measures a failover. One line in terraform.tfvars and the cost table.

Assumptions only the first apply can test unchanged, flagged

  • Does Civo's database serve TLS at all? New. Civo's connect page shows a plain connection string and says nothing about SSL, TLS or a certificate; its provider exposes no CA attribute. Every URL asks for verify-full and the ops image refuses less. If Civo serves no certificate, B7a stops at the bootstrap Job, and the fallback (plain connections on the private network) is a decision to take then, not now.
  • The load balancer's path through the node-port firewall and its private-network-only egress, what address Traefik sees without PROXY protocol, and whether Cilium tunnels over VXLAN: the questions already listed in infra/civo/README.md. Decision B removes the two about 6443.
  • Civo's backups: documented as "automatic", nothing more. The restore drill in B7a stays the first real test.

Kept, and why

  • Kubernetes. D20 chose it for portability across three clouds; the owner has since chosen Civo alone. The reason is gone, but the charts, the kind stack and the ops Jobs are built and proved, Civo sells Kubernetes as its product, and VMs with Compose give up rolling deploys and scaling. Not a deletion that pays.
  • Cloudflare's ranges at the firewall plus Traefik's client-certificate check. Two cheap layers for one invariant; each catches what the other misses.
  • The ops Jobs, the zero-replica wait, register in the first upgrade. The only way one upgrade brings up ID and then registers the MCPs against it.
  • infra/setup. Large, but it is the first run you are about to do; it shrinks with A, B and D.
  • cosign signing and the verification before a production deploy. One step each; the only check that production's bytes came from a commit that passed CI.
  • The kind stack and its CI job. The local proof you asked for.

After the decisions
