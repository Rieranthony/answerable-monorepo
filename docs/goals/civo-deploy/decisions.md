# Decisions: deploying Answerable on AWS

Stable IDs; never renumber. Each one names the alternatives it rejected and why. Facts behind them: [`findings.md`](findings.md). A decision the owner overrules is struck through, not deleted.

| ID | Decision | Alternatives rejected | Why |
| --- | --- | --- | --- |
| D1 | **One AWS account per environment** (`staging`, `production`) under an AWS Organization whose management account is the existing 409892201591, with IAM Identity Center for people and no IAM users with long-lived keys once the goal lands. | One account with two VPCs; prefixes and tags for separation. | Account boundaries are the only hard isolation AWS offers: a staging credential, bug or Terraform mistake cannot touch production. Costs nothing. The current laptop IAM user and its keys are retired at the end of B7. |
| ~~D2~~ | ~~**ECS on Fargate (arm64), not Kubernetes.**~~ Withdrawn on 10 October 2026 by D20: the owner requires the deployment to run on Civo, AWS and Google, and Fargate exists only on AWS. The reasoning stands as the record of why Fargate would have been cheaper and simpler on AWS alone. | EKS (standard or Auto Mode); k3s on EC2; App Runner; Lightsail. | EKS costs $73 a month per cluster before any node, plus an ingress controller, cert-manager or the load balancer controller, IRSA, add-ons and a Kubernetes upgrade every year, for three stateless Bun processes. Fargate has no cluster fee, native ALB, Secrets Manager and CloudWatch integration, and scaling is a number. Everything else in this plan (images, pipeline, database, secrets, DNS) is the same under Kubernetes, so the choice is reversible at the compute layer alone. |
| D3 | **Terraform, hand-written modules, no third-party modules**, providers pinned to exact versions, state in S3 with Terraform's native lockfile, one root module per account. Terraform 1.16.5 at the time of writing; `required_version` pins the minor. | OpenTofu; AWS CDK; Pulumi; `terraform-aws-modules/*`. | Terraform is installed here and the owner knows it; every resource in the repository is readable and reviewable; community modules add a supply chain and thousands of lines nobody reads. OpenTofu is a drop-in later if licensing matters. |
| D4 | **RDS for PostgreSQL 16** (`16.15` or newer 16.x), one instance per environment holding `answerable_id`, `answerable_toolbox` and `answerable_admin`, each with its own owner login and its own runtime login; encrypted with a customer-managed KMS key; `rds.force_ssl=1`; not publicly accessible; automated backups 7 days (staging) and 35 days (production); Multi-AZ and deletion protection in production. | Aurora Serverless v2; Postgres 17; one database owner for all three; a Postgres container on ECS. | Aurora Serverless v2's floor (0.5 ACU) costs about four times a `db.t4g.micro`. The repository pins 16 in compose and docs and its migrations are proved on 16; 17 is a later, separate upgrade. Separate owners mean a compromised MCP credential cannot read ID's tables. Self-hosted Postgres would hand us backups, failover and patching. |
| D5 | **The services connect with `sslmode=verify-full`** against the RDS certificate bundle shipped in the images; the Toolbox and admin MCP get a least-privilege runtime role like ID's (B2). | `sslmode=require`; the MCPs as owners. | `require` without a CA accepts any certificate (`pg` even warns); the evidence chain's append-only triggers are only a guarantee when the application cannot drop them. |
| D6 | **One internet-facing ALB per environment behind Cloudflare** (D18): ACM public certificate, one HTTPS listener (no port 80: Cloudflare redirects), TLS 1.3 policy, **mutual TLS in verify mode** against a trust store holding Answerable's own origin-pull CA, a security group admitting 443 only from Cloudflare's published ranges, host-header rules to three target groups, a fixed 404 default, access and connection logs to S3, invalid headers dropped, strictest desync mitigation; services and the database in private subnets, admitted only from the ALB's security group; **`TRUSTED_PROXY_CIDRS` = Cloudflare's published IPv4 and IPv6 ranges**, read by Terraform at apply time. | NLB; API Gateway; CloudFront; Cloudflare Tunnel with an internal ALB; the ALB open to the internet with Cloudflare DNS-only. | With Cloudflare appending the connecting address to `x-forwarded-for` and the ALB appending Cloudflare's, ID's right-to-left walk over Cloudflare's ranges yields the real client; that holds only if nothing but Cloudflare can reach the ALB, which the security group and the exclusive origin-pull certificate guarantee together (a security group alone would admit any Cloudflare customer's traffic). Cloudflare Tunnel would remove the public ALB altogether but adds a `cloudflared` process and a tunnel credential to every environment; revisit if the ranges-plus-mTLS pair proves brittle. The ALB health-checks `/readyz` and `/health`, which bypass the ingress check by design. |
| D7 | (Superseded by D23 on 12 October 2026 for the mechanism; the rule that Terraform never holds a secret value stands.) **AWS Secrets Manager** holds every secret, injected into tasks by ARN; Terraform creates empty secrets and never knows their values; the database bootstrap task and the registration script write the values they generate; people write the rest with `aws secretsmanager put-secret-value` from a trusted machine. This resolves `Q-SECRET-STORE` for the AWS deployment. | SSM Parameter Store SecureString (free); Doppler, 1Password, Infisical; values in Terraform state. | $4.80 a month buys per-secret resource policies, CloudTrail on every read, versioning and rotation hooks; the MCP and ID secrets are too few to justify a third party; keeping values out of state means a state leak leaks no credential. |
| D8 | **Staging deploys on every push to `main`; production is one click**: a `workflow_dispatch` that applies production's Terraform (a no-op once applied), runs the idempotent bootstrap and migrations, and deploys the image digest that staging runs, behind a GitHub environment with a required reviewer. Production's Terraform stays unapplied, and costs nothing, until the first click. | Deploy production on every merge; a release branch; tags. | The owner asked for staging first and production on demand. Reusing the digest, not rebuilding, means production runs the bytes staging proved. |
| D9 | **Images build once per commit on GitHub's free arm64 runners**, tagged with the commit SHA, pushed to each environment's ECR (push-only roles), scanned on push, immutable tags; `oven/bun:1.3.1-slim` pinned by digest; non-root; read-only root filesystem. | Build on QEMU; one shared registry; `latest` tags; Alpine. | Native arm64 avoids emulated Bun builds. Production pulling from the staging account would make production depend on staging. Alpine's musl is where Bun and Node-API modules misbehave. |
| D10 | **Migrations run as a one-off ECS task before each rollout**, from the same image, with the owner login that the services never receive; the pipeline waits for exit 0 before `update-service`. Migrations are expand-then-contract: a migration never breaks the previous image, because the old tasks keep serving during the rollout. | Migrate at container start; init containers. | `docs/06` requires the owner login only in migration runs, and a migration at start would give every replica the owner credential and race the rollout. |
| D11 | **Terraform owns the task definitions and the services; the deploy writes the image to an SSM parameter the task definition reads**, and the service's `task_definition` is ignored by Terraform. | Terraform applies every deploy; the deploy registers revisions Terraform does not know. | Environment, secrets and roles stay code-reviewed in Terraform; deploys stay fast and do not need the Terraform apply role; an apply after a deploy renders the same revision and changes nothing. |
| D12 | **Hostnames** (the owner's, 8 and 10 October 2026): production `id.answerable.org` (the documented issuer), `toolbox.answerable.org` and `admin-mcp.answerable.org` in the `answerable.org` zone; staging `id.answerable-staging.uk`, `toolbox.answerable-staging.uk` and `admin-mcp.answerable-staging.uk` in the **separate `answerable-staging.uk` zone**, already registered and on Cloudflare. **Proxied** CNAME records to each environment's ALB, managed by Terraform's Cloudflare provider; ACM validation records DNS-only. Every name is first-level, so **Universal SSL covers both zones** and no certificate add-on is needed ([findings](findings.md#cloudflare-in-front)). | `*.staging.answerable.org` (second-level, needs Advanced Certificate Manager); Route 53 with a delegated subzone; DNS-only records. | A zone per environment gives each pipeline a token that cannot touch the other zone, keeps staging's edge experiments away from `www.answerable.org`, and removes the add-on. Changing `BETTER_AUTH_URL` later invalidates every token, so the production issuer is fixed now. |
| D13 | **Production-shaped local stack** at `infra/docker/compose.yaml`: the three images, Postgres with TLS only, Caddy terminating TLS and forwarding `x-forwarded-for`, `NODE_ENV=production`, restricted runtime roles, the real migrate and bootstrap paths; a `bun test` builds and boots it and proves health, ingress refusal, discovery, a machine-token round trip and a staff sign-in through the containers. This is the local proof the owner asked for. | Trust the staging deploy; LocalStack. | Images that only ever run in AWS fail in AWS. LocalStack's ECS, RDS and ALB are paid and unfaithful; the AWS layer is proved by `terraform plan`, policy scanning and the staging apply, the container layer locally. |
| D14 | **Observability v1**: CloudWatch Logs per service (KMS-encrypted, 30 days staging, 90 days production), ALB access logs, alarms on ALB 5xx rate, unhealthy targets, running-task deficit, RDS CPU, free storage, connections and memory, an SNS topic to the owner's email, and an AWS Budget per account. Container Insights and the Toolbox's OTLP exporter stay off until a brief measures their cost. | Datadog, Grafana Cloud, Container Insights from day one. | Nothing in the repository reads metrics yet; ID's `[id] operations` lines are the signal `OPERATIONS.md` documents and they land in CloudWatch unchanged. |
| D15 | **Deferred, named in the docs as Not yet**: Control Tower, Security Hub and AWS Config, ECS Exec, image signing, a second NAT gateway in production, scheduled scale-to-zero for staging, KMS-backed token signing (`Q-AID-KMS`), a second region, Redis, an email provider. GuardDuty and the organisation CloudTrail are **in**. | Doing them now. | Each adds cost or process the three services do not yet need; the docs say so rather than describing them in the present tense. |
| D16 | **GitHub environments `aws-staging` and `aws-production`** (new), not the existing `Production`, carry the AWS deployments; account IDs and role ARNs are environment variables; the only Actions secret is the Cloudflare DNS token; AWS access is OIDC federation with the subject pinned to this repository, `main` and the environment. | Reusing Vercel's `Production` environment; AWS keys in secrets. | Vercel's GitHub app records deployments against `Production`; a required reviewer there could interfere with the site's deploys. OIDC leaves no key to rotate or leak. |
| D17 | **Who runs what**: B0 and B7 need the owner (account emails, console sign-ins, Entra and Google consoles, the first sign-in); B1 to B6 are coding briefs delegated to Codex (GPT-6 Astra, medium) with Fable reviewing and landing, per the house memory; B8 is the coordinator's cleanup. | — | Matches the previous goals' routing. |
| D18 | **Cloudflare stays in front** (the owner's decision, 8 October 2026, replacing `docs/02-plan.md`'s "no CDN/WAF for now" for these three hostnames): proxied records, SSL mode Full (strict), Always Use HTTPS, minimum TLS 1.2, HSTS set at the edge, zone-level Authenticated Origin Pulls with a certificate Answerable issues and uploads once, Cloudflare's free managed WAF ruleset, and for the API hostnames a configuration rule that turns off Browser Integrity Check and sets Security Level to essentially off, Bot Fight Mode off, a cache rule that bypasses everything except `/assets/*`. Cloudflare does **not** cache, challenge or buffer the MCP endpoints, ID's `/auth/*` or `/api/admin/*`. | DNS-only records (the previous plan); Cloudflare Tunnel; Cloudflare Access in front of the admin MCP. | DDoS absorption, the managed WAF and TLS at the edge for the price of a $10-a-month certificate add-on. Challenges and bot heuristics would break MCP hosts and ID's machine clients, so they are off where machines call. Cloudflare Access would double-authenticate staff in front of ID's own OAuth and is Not yet. The edge is now part of the trust chain, so its settings are Terraform too (D19), and `docs/02`'s sentence changes to say what Cloudflare does and does not do. |
| D20 | **Kubernetes is the compute layer, because it is the only one Civo, AWS and Google all offer** (the owner's requirement, 10 October 2026): Civo Kubernetes, EKS and GKE Autopilot run one and the same Helm chart; each cloud supplies a cluster, a managed PostgreSQL, a TCP load balancer, a secret store, state storage and a CI credential through a thin Terraform root. The design is [`portability.md`](portability.md). | Fargate on AWS with a "we could move later" note; Cloud Run; plain VMs with Docker Compose on every cloud. | Fargate and Cloud Run are single-cloud, so "compatible" would have meant a rewrite at the moment of moving. VMs with Compose are portable but give no rolling deploys, autoscaling or self-healing without building them. Kubernetes is the one abstraction all three vendors sell as their product, and Civo sells nothing else. |
| D21 | **One Helm chart, `charts/answerable`, is the deployable unit**: three Deployments with readiness probes, HorizontalPodAutoscalers, PodDisruptionBudgets, NetworkPolicies, Services, one Ingress per hostname, pre-upgrade Jobs for the migrations and on-demand Jobs for `bootstrap` and `register`, and ExternalSecrets; values files per environment and per cloud; linted and installed into a `kind` cluster in CI and on the laptop with the real images. | Kustomize overlays; raw manifests per cloud; a GitOps controller from day one. | A chart keeps the cloud differences to a values file; Kustomize scatters them across overlays; GitOps (Flux or Argo) is the right next step if the push model's credentials ever become the weak point, and is named Not yet. |
| D31 | **Traefik, not ingress-nginx, is the in-cluster edge** (the coordinator, 13 October 2026, during the build). The Kubernetes project retired Ingress NGINX in March 2026: "no further releases, no bugfixes, and no updates to resolve any security vulnerabilities", and "choosing to remain with Ingress NGINX after its retirement leaves you and your users vulnerable to attack" ([announcement](https://kubernetes.io/blog/2025/11/11/ingress-nginx-retirement/), [statement](https://kubernetes.io/blog/2026/01/29/ingress-nginx-statement/)); its last chart is 4.15.1 of 19 March 2026. Traefik is maintained, is the controller Civo installs by default (now kept as our own pinned chart dependency rather than the marketplace copy), verifies client certificates per host through a `TLSOption` with `clientAuth` (Cloudflare's origin-pull certificate), trusts forwarded headers only from configured ranges (`forwardedHeaders.trustedIPs`) and appends the connecting address to `X-Forwarded-For`, so ID's walk is unchanged. D22's design stands with Traefik in ingress-nginx's place; everything the agents proved on ingress-nginx is re-proved on Traefik in the kind stack before the first deploy. | Staying on ingress-nginx with a vendor's paid patches; Envoy Gateway or Cilium's Gateway API (client-certificate verification at the gateway is still experimental in the Gateway API); HAProxy. | A retired controller is the one component a security review would stop on; Traefik gives the same two guarantees with a maintained release line and a Civo-native path. |
| D22 | **The edge moves into the cluster**: ingress-nginx terminates TLS with cert-manager certificates (Let's Encrypt, DNS-01 through Cloudflare), verifies Cloudflare's origin-pull certificate per host (`auth-tls-*`), and trusts `X-Forwarded-For` only from Cloudflare's ranges with `compute-full-forwarded-for` on, so ID's walk is unchanged; the cloud's load balancer is a TCP pass-through whose firewall admits 443 from Cloudflare's ranges only; `TRUSTED_PROXY_CIDRS` is Cloudflare's ranges plus the cluster's pod range. D6's ALB-specific parts are withdrawn; D18 (Cloudflare in front) is unchanged. | Each cloud's L7 load balancer with its own controller (AWS Load Balancer Controller, GKE Ingress); Traefik, which Civo installs by default. | A per-cloud L7 controller is three different ingress configurations to keep in step; ingress-nginx is the same on all three and its client-certificate and forwarded-header behaviour is documented. Traefik is removed from the Civo marketplace selection so one controller serves everywhere. |
| D23 | **Secrets without a secret store, for now** (revised 12 October 2026: the owner's 1Password is personal and stays out of the automation). Two kinds: **human-provided secrets** (ID's signing and upstream keys, the root secret, the Microsoft and Google secrets, each zone's Cloudflare token, the origin-pull client key) are kept **encrypted in the repository with `sops` and one `age` key pair per environment** (`infra/civo/envs/<env>/secrets.enc.yaml`); the deploy workflow decrypts them with the environment's `SOPS_AGE_KEY` secret and applies them as Kubernetes Secrets before `helm upgrade`. **Generated secrets** (the six database logins' passwords from `bootstrap`, the two machine clients' secrets from `register`) are written by those Jobs straight into Kubernetes Secrets and never leave the cluster; a rebuilt cluster re-runs `bootstrap`, which resets the passwords it cannot find, and `register`, which rotates a client secret it cannot find. Terraform holds no value (D7 stands). This is the interim until OpenBao lands (D29, brief B7b); afterwards the `sops` file carries only OpenBao's seal key. | External Secrets with 1Password (the 10 October choice); plain Kubernetes Secrets typed by hand; Infisical or Doppler now; the Civo marketplace's self-run Sealed Secrets, Vault or Bitwarden; Cloudflare Secrets Store; a small store of our own on Workers and D1 behind External Secrets' webhook provider (sketched in [`portability.md`](portability.md#the-tooling-the-core-relies-on), three to five days, deferred); **OpenBao in the cluster with the static-key seal chained to the `sops` file, which the owner is weighing on 12 October 2026** (facts and the viable shape in the same section). | The owner declined automating a personal vault, and no company store exists yet; Civo offers no managed one, only apps you operate yourself ([portability](portability.md#civo)); Cloudflare's Secrets Store is in beta and readable only from Workers and AI Gateway, never through its API, so a cluster cannot fetch from it without a Worker of our own in between ([portability](portability.md#the-tooling-the-core-relies-on)). Sealed Secrets is the nearest "built-in" option and keeps its decryption key inside the cluster, so a lost cluster loses the ability to read every sealed file unless that key was backed up; `sops` keeps the key outside and works for anything, not only Kubernetes. Vault is a product to run, patch and unseal. `sops` keeps the secret values out of plain text in git while keeping the file diffable and reviewable, works the same on every cloud, and needs no service. The cost is honest: the age private key on the GitHub environment is the crown jewel, so it is protected by the environment rules and kept by the owner in a safe place of their own; there is no per-read audit; and Kubernetes Secrets rest in Civo's etcd, whose encryption is undocumented. Letting the cluster own the generated passwords means losing the cluster loses nothing that the idempotent Jobs cannot recreate. |
| D24 | **Images live on GHCR**, public, named by commit SHA, with provenance attestations and keyless cosign signatures; every cloud pulls from the same place and no cloud registry is created. | ECR per account (D9's choice); a registry per cloud with mirroring. | The source is public, the images carry no secret by design, and one registry removes a per-cloud difference and the ECR push roles. Signature verification in the cluster (Kyverno or policy-controller) is Not yet. D9's hardening of the images stands. |
| D25 | **Deploys are `helm upgrade --install --atomic` from GitHub Actions**, authenticating with OIDC to AWS and Workload Identity Federation to Google, and on every cloud through a namespace-scoped `deployer` ServiceAccount token created by Terraform; Civo's account API key is held only by the owner and by the protected infra environment, never by the deploy workflow. D11's SSM-parameter mechanism is withdrawn; the image tag is a Helm value. | The cloud's admin kubeconfig in GitHub secrets; a GitOps controller pulling from git. | A ServiceAccount limited to one namespace is the least privilege a push-based deploy can hold, and it is the same object on all three clouds. GitOps is the Not yet alternative if even that token is too much. |
| D26 | **PostgreSQL 17 on every cloud and locally** (confirmed by the owner on 12 October 2026), because Civo offers only 17 (in beta) and RDS has 17.11 in London; the migrations and every suite are proved on 17 before any deploy. Managed Postgres per cloud: Civo Database, RDS, Cloud SQL, each with the two-login scheme and `verify-full` against its CA. On Civo a restore drill precedes any production data, since its backup behaviour is undocumented. | Keeping 16 on AWS and Google. | Staging and production must run the same engine version as the suites; one version everywhere is the only way to keep that true across clouds. |
| D27 | **Terraform state per cloud**: S3 on AWS, GCS on Google, Civo's S3-compatible object store on Civo. Whether Civo's store supports the conditional writes Terraform's native S3 locking needs is checked in B4b; the fallback is the lockfile off with one operator at a time, documented. | One state bucket on AWS for every cloud. | Cross-cloud state would make Civo depend on an AWS credential at every apply. |
| D28 | **Civo runs staging and production** (decided by the owner on 12 October 2026), **each environment in its own Civo account** under one Civo organisation, both in LON1; the owner's personal 1Password is not part of the automation (D23). AWS and Google stay written and validated roots that nobody applies until the owner asks; the AWS Organization work in B0 is deferred with them. | AWS for production with Civo for staging; AWS for both as first instructed. | The owner's priority and the cost (about $103 a month for staging, $170 to $340 for production). The security gaps Civo leaves are mitigated as [`portability.md`](portability.md#where-the-three-clouds-differ-in-security-honestly) lists and named in the docs; one account per environment is the strongest boundary Civo offers and the pattern its own documentation recommends. |
| D29 | **OpenBao becomes the secret store, right after staging is up** (the owner, 12 October 2026): the official chart in each environment's cluster, Raft storage, one replica in staging and three in production, the **static key seal** chained to the one secret that stays in the `sops` file, Kubernetes auth for the services, the ops Jobs and External Secrets, policies per service, the audit device shipped to Grafana, nightly Raft snapshots to the environment's object store, a restore drill before production data, the root token revoked after configuration and the recovery shares kept offline by the owner. D23's `sops` scheme is the interim until brief B7b lands and remains the carrier of the seal key afterwards. Resolves `Q-SECRET-STORE` when B7b lands. | Staying on `sops` alone; a store of our own; a cloud's store. | An identity provider deserves per-service identities, a read audit and revocation, which files in git cannot give; OpenBao runs on every cloud we care about; its static seal removes the manual unseal that would otherwise need a person at every restart ([`portability.md`](portability.md#the-tooling-the-core-relies-on)). The cost is a product to operate, bounded for three services and written into the runbook. |
| D30 | **Staging's Kubernetes API stays reachable from the internet for now** (the coordinator, 13 October 2026, during the build): Civo clusters always have a public API address, and GitHub's hosted runners publish thousands of address ranges, too many for a Civo firewall rule, so the deploy job cannot be admitted by address. The cluster module refuses `0.0.0.0/0` unless `api_open_to_internet = true` is set deliberately; staging sets it, production refuses it until the follow-up lands. The API is still authenticated: the deploy holds only the namespace-scoped `deployer` token over TLS. The follow-up, for the owner to pick, is either a GitOps pull (Flux in the cluster reads `main`, decrypts the `sops` file with an in-cluster age key, so GitHub needs no cluster access at all) or a Cloudflare tunnel with Access service tokens in front of the API. | Self-hosted runner with a fixed address (a machine to run); GitHub larger runners with static addresses (paid); blocking the deploy on a tunnel before staging exists. | Staging must exist before the hardening can be tested, and the exposure is the one every default Civo cluster has, with per-namespace credentials limiting what the deploy token can do. Recorded as Not yet in the docs and as a candidate brief after B7b. |
| D19 | **Each environment owns its Cloudflare zone through an `edge` module in its own root**: zone settings, origin pulls, the configuration and cache rules and the DNS records, with a Cloudflare API token scoped to that one zone (staging's in the `aws-staging` environment, production's in `aws-production`). The origin-pull client key is generated per zone and uploaded once from a trusted machine with the Cloudflare API, kept in that environment's Secrets Manager for re-upload, and never passes through Terraform; Terraform manages the ALB trust store (the CA's public certificate) and the "enabled" switch. | One shared `infra/edge` root (the plan before the staging zone existed); the key as a Terraform variable. | With a zone per environment nothing is shared, so the environment root is the natural owner and the staging pipeline holds no credential for the production zone. A private key in state would break D7. The production zone still carries Vercel's DNS-only `www`: zone-wide SSL settings apply only to proxied records, so it is untouched; if it is ever proxied, Vercel serves a public certificate and Full (strict) still holds. |
