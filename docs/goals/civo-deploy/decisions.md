# Decisions: deploying Answerable on Civo

Stable IDs; never renumber. Each one names the alternatives it rejected and why. Facts behind them: [`findings.md`](findings.md). A decision the owner overrules is struck through, not deleted. D1, D2, D4, D6, D7, D9, D11 and D13 to D16 named another cloud's services and were removed with that cloud on 19 October 2026 (D28 made Civo the only one; the owner then asked that the record name no other).

| ID | Decision | Alternatives rejected | Why |
| --- | --- | --- | --- |
| D3 | **Terraform, hand-written modules, no third-party modules**, providers pinned to exact versions, Terraform's minor pinned (`~> 1.16`), one root for both environments with a var file each, state in each environment's own Civo object store (D27). | OpenTofu; Pulumi; community modules. | Every resource in the repository is readable and reviewable; community modules add a supply chain and thousands of lines nobody reads. OpenTofu is a drop-in later if licensing matters. |
| D5 | **The services connect with `sslmode=verify-full`** against the database's CA, which the bootstrap Job records on first use (D38); the Toolbox and the admin MCP run as least-privilege runtime logins like ID's. | `sslmode=require`; the MCPs as owners. | `require` without a CA accepts any certificate; the evidence chain's append-only triggers are only a guarantee when the application cannot drop them. |
| D8 | **A tag ships** (revised 19 October 2026, D32): `staging/<name>` on a commit of `main` deploys staging; `production/<name>` deploys the images staging built for that commit, after the production environment's reviewer approves. Production is never rebuilt. | Deploy staging on every push to `main` (the first plan); a release branch; a dispatch with a tag input. | The owner asked that each environment ship only when a tag says so. Reusing staging's digests means production runs the bytes staging proved. |
| D10 | **Migrations run as Helm hook Jobs before each rollout**, from the same image, with the owner login that the services never receive. Migrations are expand-then-contract: a migration never breaks the previous image, because the old pods keep serving during the rollout and after a rollback. | Migrate at container start; init containers. | `docs/06` requires the owner login only in migration runs, and a migration at start would give every replica the owner credential and race the rollout. |
| D12 | **Hostnames** (the owner's, 8 and 10 October 2026): production `id.answerable.org` (the documented issuer), `toolbox.answerable.org` and `admin-mcp.answerable.org` in the `answerable.org` zone; staging `id.answerable-staging.uk`, `toolbox.answerable-staging.uk` and `admin-mcp.answerable-staging.uk` in the separate `answerable-staging.uk` zone. Proxied A records to the environment's load balancer, managed by Terraform's Cloudflare provider. Every name is first-level, so Universal SSL covers both zones. | Second-level staging names (they need Advanced Certificate Manager); DNS-only records. | A zone per environment gives each pipeline a token that cannot touch the other zone and keeps staging's edge away from `www.answerable.org`. Changing `BETTER_AUTH_URL` later invalidates every token, so the production issuer is fixed now. |
| D18 | **Cloudflare stays in front** (the owner, 8 October 2026): proxied records, SSL mode Full (strict), Always Use HTTPS, minimum TLS 1.2, HSTS set at the edge, zone-level Authenticated Origin Pulls with a certificate Answerable issues, and for the API hostnames a configuration rule that turns off Browser Integrity Check and sets Security Level to essentially off, Bot Fight Mode off, a cache rule that bypasses everything except `/assets/*`. Cloudflare does not cache, challenge or buffer the MCP endpoints, ID's `/auth/*` or `/api/admin/*`. | DNS-only records; Cloudflare Tunnel; Cloudflare Access in front of the admin MCP. | DDoS absorption and TLS at the edge for nothing. Challenges and bot heuristics would break MCP hosts and ID's machine clients, so they are off where machines call. |
| D19 | **Each environment owns its Cloudflare zone through the `edge` module** (revised 19 October 2026): zone settings, origin pulls, the configuration and cache rules, the DNS records, and now the certificates too: the origin-pull CA and client certificate, and the Origin CA certificate the services present (D35), all made by Terraform with a Cloudflare token scoped to that one zone. No certificate passes through a person or a file. | A shared edge root; the origin-pull key generated on a laptop and uploaded by hand (the shape until 19 October). | With a zone per environment nothing is shared. The keys live in Terraform state, beside the admin kubeconfig and the database password already there, and the state bucket is guarded accordingly. |
| D20 | **Kubernetes is the compute layer** (revised 19 October 2026). Chosen on 10 October because it was the one layer every cloud under consideration offered; D28 then chose Civo alone. It stays because Civo Kubernetes is what Civo sells, because rolling deploys, scaling and self-healing come with it, and because the charts, the ops Jobs and the kind stack are built and proved. | Virtual machines with Compose. | Compose on a VM gives none of those without building them, and nothing already built would be reused. |
| D21 | **One Helm chart, `charts/answerable`, is the deployable unit**: three Deployments with readiness probes, HorizontalPodAutoscalers, PodDisruptionBudgets, NetworkPolicies, Services, one Ingress per hostname, pre-upgrade Jobs for the migrations and the ops Jobs; one values file per environment; linted and installed into a kind cluster in CI and on the laptop with the real images. | Kustomize overlays; raw manifests; a GitOps controller from day one. | A chart keeps the environments' differences to a values file. GitOps is the Not yet alternative if the push model's credentials ever become the weak point. |
| D22 | **The edge is in the cluster**: Traefik (D31) terminates TLS with the Origin CA certificate (D35), verifies Cloudflare's origin-pull client certificate on every host, and trusts `X-Forwarded-For` only from Cloudflare's ranges and the load balancer's private network, so ID's walk over `TRUSTED_PROXY_CIDRS` is unchanged; the Civo load balancer is a TCP pass-through whose firewall admits 443 from Cloudflare's ranges only. | The cloud's own L7 load balancer. | Civo's load balancer is TCP; the client-certificate check and the forwarded-header rules have to live in the cluster. |
| D23 | **Every secret lives in the GitHub environment, or is generated where it is used** (revised 19 October 2026, D33). The owner pastes five values into each environment once: the Civo key, the Cloudflare token, the Entra client ID and secret, and a fine-grained GitHub token that lets workflows write that environment's secrets. The bootstrap workflow generates ID's three random secrets and the state bucket's credential into the environment; Terraform writes the deploy credentials there and the database administrator's URL into the cluster; the ops Jobs generate the database logins and the machine clients' secrets into Kubernetes Secrets. No `sops`, no `age` key, no secrets file, no setup command on a laptop. | `sops` and `age` with the human secrets encrypted in the repository (the shape from 12 to 19 October); External Secrets with a vault; a self-hosted store. | The owner asked that nothing be done by hand from a laptop. GitHub encrypts each secret before it reaches GitHub, stores it write-only, masks it in logs and scopes it to an environment with a reviewer; that is the same class of protection the `age` key had in a GitHub secret, without the key file. The costs are named in `docs/12`: no reviewable history of a secret change, and write access to `main` is access to every secret of the `main`-scoped environments. |
| D24 | **Images live on GHCR**, public, named `sha-<commit>`, with provenance attestations and keyless cosign signatures. | A registry per cloud; mutable tags. | The source is public and the images carry no secret by design; one registry removes a difference. Signature verification in the cluster is Not yet. |
| D25 | **Deploys are `helm upgrade --install --rollback-on-failure` from GitHub Actions**, through a namespace-scoped `deployer` ServiceAccount token that Terraform creates and writes into the GitHub environment; the deploy step is handed that token and ID's secrets, never the Civo key. | The admin kubeconfig in GitHub secrets; a GitOps controller pulling from git. | A ServiceAccount limited to one namespace is the least privilege a push-based deploy can hold. |
| D26 | **PostgreSQL 17 everywhere**, locally and on Civo (confirmed by the owner on 12 October 2026); the migrations and every suite are proved on 17 before any deploy. A restore drill precedes any production data, since Civo documents its backups as "automatic" and nothing more. | Keeping 16 locally. | Staging and production must run the same engine as the suites. |
| D27 | **Terraform state in the environment's own Civo object store**, one bucket per environment, created by the bootstrap workflow with the Civo CLI, its credential written into the GitHub environment. | State in the repository; state in a third-party backend. | A bucket per account keeps each environment's state, which holds that environment's secrets, inside that environment's boundary. |
| D28 | **Civo runs staging and production**, each environment in its own Civo account under one Civo organisation, both in LON1 (the owner, 12 October 2026); the owner's personal 1Password is not part of the automation. On 19 October the owner asked that the deployment name no other cloud, anywhere. | Another cloud for production; two clouds. | The owner's priority and the cost (about $103 a month for staging, about $170 for production). One account per environment is the strongest boundary Civo offers. |
| ~~D29~~ | ~~OpenBao as the secret store right after staging.~~ Withdrawn on 19 October 2026 (D33): no pod mounts an API token, so a pod reads only the Secrets mounted into it; revocation is a changed Secret; a read audit for three services and one operator has no reader; and the store would have been a stateful product to run, seal and snapshot. Not yet, with a trigger: a second team, or a compliance need for a read audit. | | |
| D30 | **The Kubernetes API is reachable from the internet in both environments, authenticated by the cluster** (resolved 19 October 2026). Civo clusters always have a public API; the firewall admits 6443 from everywhere, as every default Civo cluster does; TLS, then a credential: the namespace-scoped deployer token from the workflows, or the admin certificate that lives only in Terraform state. | Admitting the operators' addresses only in production (the shape until 19 October, which left production undeployable from GitHub until a tunnel or a GitOps controller existed); a self-hosted runner with a fixed address. | GitHub's hosted runners cannot be listed in a firewall, and the owner asked for everything to run from GitHub. The compensating controls are the token's reach and the pinned actions; GitOps is the hardening if it is ever wanted. |
| D31 | **Traefik, not ingress-nginx, is the in-cluster edge** (13 October 2026). The Kubernetes project retired Ingress NGINX in March 2026 ([announcement](https://kubernetes.io/blog/2025/11/11/ingress-nginx-retirement/)); Traefik is maintained, is the controller Civo installs by default (kept as our own pinned chart dependency rather than the marketplace copy), verifies client certificates through a `TLSOption` with `clientAuth`, trusts forwarded headers only from configured ranges and appends the connecting address. | Staying on ingress-nginx; Envoy Gateway or Cilium's Gateway API; HAProxy. | A retired controller is the one component a security review would stop on. |
| D32 | **Two shipping workflows, each started by a tag** (the owner, 19 October 2026): `deploy-staging.yml` on `staging/*`, `promote-production.yml` on `production/*`; both refuse a commit that is not on `main`; production refuses a commit staging never built, and waits for the environment's reviewer. CI runs on every push; `ops.yml` and `bootstrap.yml` run by hand. | Deploying on every push; dispatch inputs. | A tag is an explicit, reviewable act that names what shipped, and the same mechanism rolls back. |
| D33 | **GitHub environments hold every secret; nothing is done from a laptop** (the owner, 19 October 2026). See D23 for the shape. Two environments, `staging` and `production`, each allowed for `main` and its own tags, production with the owner as required reviewer, both policies set by Terraform. | Four environments splitting infrastructure from deploy credentials. | One environment per target is what the owner asked for and is enough: a workflow step is handed only the secrets it names, so the deploy step never sees the Civo key. |
| D34 | **Terraform runs from GitHub Actions for both environments**, before every deploy, with `-target` for the cluster and the database first and then the full apply, both no-ops afterwards. | Applying by hand from a trusted machine; a plan comment on pull requests (deleted with the pull-request workflow on 19 October). | D33, and D30 made production reachable. |
| D35 | **Origin certificates come from Cloudflare's Origin CA, and the origin-pull certificates from Terraform**; no cert-manager, no Let's Encrypt, no second Cloudflare token. Terraform requests one ECC certificate for the three hostnames, valid 5475 days, with the token it already holds, and writes it as the Secret `origin-tls`; it makes the origin-pull CA and client certificate and uploads the client pair to the zone. The platform chart is Traefik alone. | cert-manager with Let's Encrypt through DNS-01 (the shape until 19 October); a wildcard origin certificate. | Only Cloudflare reaches the origin, by design and by firewall, so a certificate only Cloudflare trusts is enough, and it removes a controller, a token, a renewal and a first-apply unknown. Rotation is `terraform apply -replace` on the key and a short interruption. |
| D36 | **Images are built for linux/amd64 only.** | Both amd64 and arm64 (the shape until 19 October). | Civo's own guide: "Civo's nodes are amd64, so the image has to be built for linux/amd64". CI proves the images on that architecture. |
| D37 | **Production's database runs one node** until a failover has been measured. | Three nodes from the first day. | Civo says a multi-node database "can continue to operate even if one or more nodes fail" and nothing about how; the two extra nodes cost about $173 a month for a database still in beta. B7c measures it before the count rises. |
| D38 | **The first run happens inside the cluster and in workflows.** The bootstrap Job records the database's certificate on first use (trust on first use, fingerprint in its log); the register Job adds the staff domain and the Entra SSO provider to the platform organisation; the make-admin Job makes the owner the admin MCP's owner and a platform administrator after their first sign-in, which locks the root secret. | The setup commands on a laptop (deleted 19 October). | D33. |
| D17 | **Who runs what**: the owner creates the Civo accounts, the Cloudflare tokens, the Entra app and the GitHub environments, pastes five secrets per environment, signs in once and runs `make-admin`; everything else is a workflow, Terraform or a Job. Code changes are landed on `main` by the coordinator after review. | | |
