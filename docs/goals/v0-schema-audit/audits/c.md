# Audit C: evidence and growth (v0 schema audit, 19 October 2026)

Auditor C. Container `audit-pg-c` (PostgreSQL 17.9, port 47435, `shared_buffers` 128 MB, `max_connections` 100). Worktree `agent-ac2438c350f9d5635` at main 9833960 after `bun install --frozen-lockfile`. Probes in `$S/probes/c/` (`$S` = the session scratchpad). Host load (`uptime`) 5.3 to 7.5 throughout; every timing is from that loaded laptop, so read them as relative (on against off, 1M against 2M rows), not as production latencies. Nothing was committed; the three throwaway probe test files were removed from the worktree after use (copies in the probes directory).

## 1. Summary

1. **One action is the growth.** At the common model (10,000 users, 3 hosts each, 8 h a day, the Toolbox at its registered 900 s) ID writes about 967,000 audit events a working day, 960,000 of them (99.3%) `oauth.user.issued` for a refresh. Measured cost per refresh event: 2,043 B of heap with its real payload, 229 B of `audit_events` indexes and 131 B of `audit_event_users`, so 2.4 KB. That is **2.32 GB a working day and about 603 GB a year, 99.4% of it refreshes**. 100,000 users: 23 GB a day, 6.0 TB a year. At the acceptance's 60 s TTL, 15 times more. Production's 80 GB Civo database fills in about 35 working days at 10,000 users. Without per-refresh events the same model writes 6,807 events a day, 3.6 GB a year.
2. **Verdict: stop writing an audit event per refresh** (`oauth.user.issued` with `grantType: refresh_token`, and `oauth.user.replayed`). Keep the per-grant facts (`oauth.user.authorized`, `denied`, the code-exchange `issued`, `revoked`), the machine `oauth.token.issued`/`rejected` per token (about 1,700 a day) and `auth.signin.*`. No programmatic consumer reads refresh events: the Toolbox poller skips every `oauth.*` row and the acceptance filters them out by hand (`admin.journeys.test.ts:504`). Whatever the owner decides there, **drop `decision.grant` from the user OAuth payloads**: it copies all 17 columns of the immutable `grant_contexts` row the event already targets (stored payload 1,478 B to 1,117 B, −24%).
3. **The Toolbox poller scales with refreshes it ignores.** Its query is a backward walk of the primary key (0.12 to 0.14 ms at 1M and 2M rows), but one 200-event page of refresh events is 716 KB of JSON (a 300 KB page took 17 ms through ID's route). At 10,000 users a 15 s poll has 504 new events (2.5 pages per Toolbox process); 100,000 users, 25 pages; 100,000 at 60 s, 375 pages per 15 s, which a poll cannot finish. Deleting refresh events fixes it with no poller change.
4. **Indexes: keep all five.** Each serves a filter the admin MCP, the tenant route or the acceptance sends; rare-action, actor, target and operation lookups stay at 0.06 to 0.3 ms from 1M to 2M rows (probe 05). One query does not scale: a tenant's history with `from`/`to` and no action reads every heap page holding that tenant's rows (111 ms and 31,050 buffers at 2M; it grows with the table). It becomes small with the table once refreshes go.
5. **`audit_event_users`: keep.** In October it was the growth driver (7.2 KB per refresh); now it is 131 B per event, 5% of the bytes, and about 5,200 rows a day without refresh events. It answers `GET /users/:id/audit-events` (an operator cURL in `onboard.mdx:462`) in 0.47 to 0.6 ms at 1M and 2M rows. Without it, the same history costs 0.9 ms from existing indexes plus 3.8 ms to find manifest-named users by testing every manifest event's jsonb, a cost that grows with the platform's history. Its two triggers add 0.11 to 0.20 ms per audit insert (probe 07).
6. **The 25 `*_unchanged` actions: delete.** Each is written exactly when the journal records `outcome = 'noop'` (one `changed` flag picks both); no consumer reads one; they make the Toolbox invalidate caches for nothing. 47 code lines, 29 test lines in 16 files, 17 lines of docs/04. The brief's count of 20 is 25 in `auditActions`.
7. **Refresh-token rows are the second growth item: bounded, large, a security trade.** Every rotation leaves a 649 B row (heap and 7 indexes) for 30 days: 20.5 million rows, 13.3 GB steady at 10,000 users; 133 GB at 100,000; 200 GB at 10,000 with 60 s tokens. The rotated row is the refresh-reuse detector, so a shorter retention is the owner's call, needed before 100,000 users. With `OAUTH_REFRESH_REUSE_INTERVAL_SECONDS` above 0 each rotated row also keeps its 5,094 B encrypted replay blob for 30 days (5,488 B rows, 15 times larger).
8. **No retention rule is needed before 100,000 users** for `admin_operations` (629 B per receipt, 33 MB a year at 200 commands a day), `grant_contexts` (about 0.4 KB per authorisation, 0.17 GB a year), `oauth_consents` (one ~0.3 KB row per authorisation, never read after its flow) or `sessions` (swept).
9. **Sweep: keep. Pool: what breaks first is the 5 s pool wait, not Postgres.** 2,000,000 expired rows swept in 25.4 s at batch 1,000 (79,000 rows a second); refreshes during it p50 27.6 ms, p95 33.2 ms (30.3 after). 200 concurrent refreshes on one process: all succeed in 1.4 to 1.6 s with a pool of 5, 20 or 40 alike: one ID process is CPU-bound at about 135 refreshes a second on this host. 1,000 concurrent refreshes on one process with the production pool: **753 succeed, 247 get `503 temporarily_unavailable` at 5 s** (the `DATABASE_CONNECTION_TIMEOUT_MS` pool wait); 1,000 machine tokens all succeed in 2.7 s. Two replicas would split the load (not run).

## 4. Considered and kept

- **The primary-key cursor and the poller's query.** UUIDv7 ids in time order make the poller's page an index walk whose cost does not depend on table size (0.134 ms at 1M, 0.141 at 2M). The scaling problem is the number of pages, not the query.
- **The five secondary indexes.** Each has a caller: `(organization_id, id)` the tenant route and the admin MCP's `organizationId`; `(action, occurred_at)` the `action` filter (admin MCP, tenant route, acceptance `?action=organization.created`); `actor_id` (admin MCP, acceptance `?actorId=admin-mcp`); `(target_type, target_id)` (admin MCP, acceptance `targetId`); `operation_id` (admin MCP, acceptance `?operationId=`). `actor_id`, `target` and `operation_id` deduplicate to 6.5 to 12 B per event. With refresh events gone they cost nothing measurable.
- **`audit_event_users` and its two triggers** (recorded decision D8). New evidence does not change it: once refresh events go it holds ~5,200 rows a day and answers the documented offboarding lookup in O(page). The manifest-named users (5.6% in October) are the part a read-time query reaches only by scanning manifest events. `record_user_oauth_subjects` also refuses a user OAuth event that names a grant of another organisation or actor (`user_oauth_audit_provenance`), an integrity check worth its 0.05 to 0.1 ms.
- **Per-grant and per-machine-token evidence.** docs/04 "Machine issuance evidence" and "Authentication transaction boundary" ask for them; together they are under 4 GB a year at 10k.
- **`admin_operations` retention.** 629 B a receipt; at 200 commands a day 33 MB a year: permanent receipts cost nothing worth a rule.
- **The protocol sweep.** It deletes 79,000 rows a second at batch 1,000, each batch in its own short transaction with `pg_try_advisory_xact_lock`, and token issuance did not notice it (p95 +3 ms, a 200-request burst unchanged). At 10k/900 s it has about 960,000 refresh rows a day to delete (~13 batches a minute over a working day).
- **The 30-day refresh-row life.** It is the plugin's reuse detector and the grant's life; shortening it trades theft detection for space, so it stays until the owner decides (row 11).
- **Pool settings.** The pool size is not what limits throughput (5, 20 and 40 connections gave the same wall time within 25%); Postgres was never the bottleneck (no statement or lock timeout in any run). The 5 s connect timeout turns a backlog into a fast 503 with `temporarily_unavailable`, which the OAuth guide documents as retryable.

## 5. Open questions

1. **Production `max_connections`.** docs/12 says Civo's value is measured in B7a; production's autoscaler ceiling opens 200 connections. Not verified here (the container's default is 100).
2. **Two replicas under 1,000 concurrent refreshes.** One process failed 247 of 1,000 at the 5 s pool wait; two replicas behind a balancer were not run. Settle with the kind stack or staging.
3. **Payload size in real organisations.** The decision carries the matching entitlement and capability sources; probe 01's organisation had 2 entitlements and 3 capabilities. An organisation where a member reaches a resource through many groups writes larger events (not measured).
4. **The poller's missed-event window.** `poller.ts` stops at the first event whose id is not newer than the last one seen; an id is minted before its transaction commits, so an admin event that commits after a newer refresh event was read is skipped (source read, not reproduced). Refresh traffic makes a newer committed event almost always available; the 60 s grant cache bounds the staleness, but no `list_changed` is sent for the skipped change. Deleting refresh events shrinks the window to the rare overlap of two admin commands.
5. **Theft-detection window for refresh tokens** (row 11): owner's call.
6. **5 million rows.** Not run (disk). Plans A to D and G to K are index probes whose times did not move between 1M and 2M; E and F grow with the tenant's rows; L3 grows with the user's own events.

## Working notes (facts read before probing)

- Refresh rows: `createRefreshToken` sets `expiresAt = iat + refreshTokenTtl` on every rotation and marks the old row `revoked`/`rotated_at` (`@better-auth/oauth-provider` 1.7.2 `dist/introspect-C6P1zrTr.mjs:1545-1597`); ID sets `refreshTokenExpiresIn: grantLifetimeSeconds` = 2,592,000 s (`apps/id/src/auth.ts:229`, `auth/user-oauth-flow.ts:37`). The sweep keeps a rotated row until its own expiry (`operations/protocol-sweep.ts:24-27`).
- Production TTLs: `infra/ops/src/register.ts:97,106` registers the Toolbox resource and the admin MCP resource at `accessTokenTtl: 900`; the acceptance shortens the Toolbox to 60 s (`packages/acceptance/src/toolbox.ts:34`). ID's admin resource is 600 s (`apps/id/src/bootstrap.ts:54`); `createIdAdmin` renews 30 s before expiry (`packages/id-admin/src/index.ts`).
- The Toolbox poller pages `/audit-events` with `limit=200` (`packages/id-admin/src/index.ts:82`), no filter, newest first, back to the last id seen (`mcps/toolbox/src/poller.ts`), every 15 s, one poller per Toolbox process (`mcps/toolbox/src/server.ts:24`), acting only on `capability.`, `entitlement.`, `group_member.`, `group.`, `member.`, `organization.`, `user.`. Its grant cache lives 60 s (`mcps/toolbox/src/grants.ts`).
- Toolbox evidence per call (`packages/mcp-postgres/migrations/0001_evidence.sql`): organisation, actor, client, capability, outcome, request and trace ids, chained. It proves use by a principal; ID's grant events prove the authority. Neither needs a per-refresh ID event to prove its part.
- `OAUTH_REFRESH_REUSE_INTERVAL_SECONDS` defaults to 0 (`env.ts:114-118`, `.env.example:50`, docs/06).
- Consents: `consentReferenceId` is the flow's grant id (`auth/user-oauth-flow.ts:101`); the plugin finds consent by client, user and reference (`authorize-BmTe2VYG.mjs:72-88`), so each authorisation creates one.
- pg-pool queues a request when the pool is full and fails it after `connectionTimeoutMillis` (`pg-pool/index.js:206-231`); ID maps that to `503 temporarily_unavailable` (probe 10).
