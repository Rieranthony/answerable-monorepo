Estimated lines: about 1,080 removed and 160 added in `apps/id/src` (net about −920, 8% of the scope), plus 23 test assertions and two route-metadata tests reshaped. Most of the removal is route metadata the code already derives or writes twice.

**The five changes that matter most:**

1. **B1-14 Delete the capability-context registry.** 164 `require*Context` call sites, two WeakSets, single-use `close()` flags and frozen copies re-check at runtime what the private-symbol brand already guarantees at compile time. The one real hazard it names, a query after commit, is real at the driver level (drizzle does not invalidate `tx`; the pooled client goes back to the pool), but the check only fires at function entry, services and queries already pass the raw `tx` to other functions (65 sites), and the realistic cause, a missing `await`, is caught statically by `no-floating-promises`: 6.5 s, 0 hits in this scope. Keep the brand types and the authorisation; delete the registry; add the lint rule.
2. **B1-20, B1-21, B1-22 Stop writing route metadata the code already knows.** Every one of the 49 mutation routes restates the idempotency contract in its description (at least 10 wordings), declares `idempotencyParameter`, `commandResponseHeaders` and its 400/409/503 problems by hand; all 79 route-level `standardResponses(...)` calls are applied a second time by `adminRoute()`; the command name passed to every command equals the route's `operationId` (49/49). Derive all of it from `kind` and the route: about 450 lines.
3. **B1-31 A non-JSON body answers 500.** The JSON validator sees `{}` when `Content-Type` is not JSON, the handler then parses the real body; on `putGroupMember` (the one body schema that accepts `{}`) a `text/plain` body that fails the schema, or is not JSON, answers `500 internal_error` (measured). Refuse a non-JSON `Content-Type` in `validate("json")`.
4. **B1-29 Fresh authentication is checked twice before the mutation and again on every revalidation.** `authorizeCommand` runs `freshAuthenticationGuard`, then `httpCommand` runs it again a statement later, then checks before and after the mutation, and `revalidate()` repeats it: 8 or more freshness queries for a tenant member command (6 or more for a platform command) where 3 suffice. One owner: `httpCommand`.
5. **B1-15, B1-16, B1-17 Three shared helpers.** 12 local `requireRow`-like helpers plus 7 inline 404s (`found(row, title)` in `http/problem.ts`), 11 local `audit(...)` wrappers with 47 calls (`recordCommandEvent(context, event)`), 9 copies of the revision precondition (`assertRevision` in `http/admin/revision.ts`): about 170 lines net.

Also worth doing, smaller: B1-30 (the SSO probe's hand-rolled private-host list misses 100.64.0.0/10, 198.18.0.0/15 and 224.0.0.0/4, where the installed `@better-auth/core/utils/host` catches them), B1-26 (seven read routes publish a receipt union in the contract), B1-33 (`operation-status.ts` re-implements `withPlatformRead`).

### Note on B1-14: what the registry catches that the types do not

- **Forged or copied contexts.** A context cannot be built outside its module without the unexported symbol; a spread copy or a cast can. Every test that exercises this needs `as unknown as`, `as never`, `Reflect.apply` or `{ ...context }`. That is code review's job, not a runtime check's.
- **Wrong kind.** `access` is a literal type, so a directory context passed where a configuration context is required fails to compile. The runtime `access !==` checks repeat the type.
- **Use after the callback.** Real at the driver: `drizzle-orm` 0.45.2 `NodePgSession.transaction` commits and calls `session.client.release()` without invalidating `tx`, so a later `tx.select()` runs on a pooled connection, possibly inside another request's transaction. The registry only checks at a query function's entry; a function that already destructured `tx` keeps it, and services and queries pass the raw `tx` to `recordAuditEvent`, `protect`, `protectPlatformUser` and others 65 times (`grep -rnE '\((tx|executor)[,)]' services db/queries`). It reaches the hazard only when a stored context is passed to a new query function after the callback. A stored context means our own code kept it, deliberately. The realistic path is a missing `await`, which `no-floating-promises` catches statically (6.5 s, no hit in `http`, `services` or `db`).
- **Cannot be centralised cheaply.** A getter on `tx` in the four constructors covers the same entry checks, but a spread copies the value rather than the getter, so it is weaker than today at the same cost. Deleting is simpler.
- **The 23 tests** prove the mechanism. Nothing replaces them at test level; the lint rule replaces the property they stand for.

## 5. Challenged and kept

- **Two authorisation layers** (`http/authorize.ts` from the request-start grants, `services/command-authority.ts` inside the transaction). Decided by the test audit ("the middleware's `tier` variable and `authorize.test.ts`: the only way to tell ID's two authorisation layers apart"). I checked that both sources of truth agree: splitting every route module, the declared `platformScope`/`orgScope` and the in-transaction scope match on all 81 routes (41 platform write, 5 platform users, 3 tenant member commands, 13 platform reads, 14 directory, 1 history, 2 member access, 1 configuration, 1 open). Any future drift fails closed: the stricter layer refuses. The `tier` variable has only test readers and stays for the same reason.
- **`context.req.param("x")!` (86) and `context.get("principal")!` (13).** Safe by construction: Hono always supplies a matched route's named parameters, and the validator already refused malformed values; the principal middleware runs before every admin route. Removing the assertions needs either a cast (`context.req.valid(target as never) as z.output<S>`, because `registerRoute`'s `Handler<AppEnvironment>[]` erases the validator's types) or a separate admin environment type. Both are churn for no behaviour. Keep, unless the coordinator wants the typed accessor; in that case it belongs in `validation.ts` and needs B1-31 first.
- **Handlers re-parse validated input (22 query, 17 JSON).** Idempotent and cheap; today the JSON re-parse is what reads the real body when the validator saw `{}` (B1-31). After B1-31 it is redundant but harmless; keep with the assertions above.
- **The client-admission predicate written twice** (`principal.ts:263-310`, `command-authority.ts:110-137`). Two sites, under the three-site threshold, and each is the check of one of the two decided layers, held by its own tests. A shared `admitClient(claims, client)` would be reasonable if a third copy ever appears.
- **The expiry re-check after the client lookup** (`principal.ts:272`). Held by `principal.test.ts` "rejects a verified token that expires during principal lookup"; one comparison. Only the `isFinite` operand is dead (B1-11).
- **`!environment.rootAdminSecret` in `authorizeCommand` (line 39).** Unreachable in production (a root principal exists only after the secret matched) but pinned by `command-authority.integration.test.ts:133`; one operand on the authority path. Keep.
- **`PrincipalDeps`.** A test seam with one production factory; `principal.test.ts` builds on it for cases that need no database (expiry during lookup, denial attribution). Keep.
- **`createJwksResolver`** (single-flight refresh, five-minute cache, throttled unknown-key reload). Better Auth's JWKS is read from the database, so jose's `createRemoteJWKSet` does not apply; the throttle stops attacker-chosen key ids from forcing reloads. Keep.
- **`executeOperation` authorises before it reads the try-lock result.** A refused caller gets 403, not `operation_in_progress`, for a key it does not own. Keep.
- **`mapDatabaseError`'s exact pg-pool messages.** A dependency on library text, acknowledged in the comment and pinned by `problem.test.ts`; pg-pool has no code for checkout timeouts. Keep.
- **The constraint name in a 409's detail.** Admin callers only; it names the colliding unique key that the descriptions rely on ("conflict means the slug is already in use"); no row data. Keep.
- **The unexpected-error log without the error.** Deliberate fixed cardinality: "Do not inspect error objects: driver parameters can contain credentials" (`machine-provider.ts:158`), pinned by `problem.test.ts:162-168`. Keep.
- **`limitRequestBody`.** Bun has no per-request body timeout or size cap before parsing; 413/408 are documented. Keep.
- **`SsoTestOptions.fetch`, `timeoutMs` and optional `trustedOrigins`.** Test seams for an outbound probe; production sets only `trustedOrigins` and the fixture's `allowPrivateHosts`. Resolve-then-fetch leaves a DNS-rebinding window; Better Auth documents the same limit for sign-in and the route is staff-only. Keep.
- **A generator for the enable/disable pairs or the list routes.** 7 status pairs and 11 list routes. After B1-20, B1-21 and B1-22 each pair is two route entries of about 14 lines and two handlers of about 20; every description is entity-specific (what is revoked, what is not restored) and the service result shapes differ until B1-28. A generator would save about 100 more lines and hide the per-route contract a reader and the docs need. The explicit form is the better V0.
- **Services as thin read wrappers** (11 list functions are `cursorPage(await queries.x(...), limit)`). Routes always call services; splitting reads to call queries directly gives two patterns. Keep (see question 5 on where the page slicing belongs).
- **`services/capabilities.ts` holding its SQL inline**, unlike every other entity. Moving 60 lines to `db/queries` is churn without a defect. Keep.
- **`federationFailureCodes` and the diagnosis code lists** overlap but differ on purpose: diagnosis excludes `email_conflict` because it never reads global accounts. Keep.
- **`services/root-secret.ts` and `client-secrets.ts` as files.** Two small crypto primitives, each with its own test; `secretMatches` is constant time (SHA-256 then `timingSafeEqual`). Keep.
- **Tenant id from the URL before the tenant check.** `deny()` attributes it only when the principal holds a grant there (the column is a foreign key) and `admitRoot` keeps it in `data`; `withTenantRead` and `authorizeTenantMemberCommand` lock the organisation row before authorising, on purpose (serialise with revocations), and answer 403 before 404 for a missing organisation, so there is no existence oracle. Pagination cursors are UUIDs applied with `lt` under the organisation filter. The idempotency key is length-checked, hashed and namespaced by actor, authority scope and command. No finding.
