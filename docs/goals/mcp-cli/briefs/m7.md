# M7: trying an MCP locally, and journeys that sign real people in

You implement brief M7 of the MCP CLI goal. Read [`README.md`](README.md) first.

**Goal.** Two commands:
- **`bun mcp setup`,** run once, connects the CLI to the developer's local Answerable ID.
- **`bun mcp dev <mcp>`** runs that MCP locally, migrated, in the Toolbox or the standalone server according to its `serve`, registered in the local ID, and prints the exact `claude mcp add` command to try it in Claude Code.

The acceptance gains journeys that prove a CLI-made MCP end to end through real ID in each mode.

## What to build

1. **`bun mcp setup`.**
   - **What it does:** creates a local machine client in the developer's local ID, `mcp-dev`, with `platform:read platform:write` on ID's admin resource and `toolbox:admin` on the Toolbox's admin resource.
   - **Where the secret goes:** the gitignored root `.env`, as `MCP_DEV_ID_CLIENT_ID` and `MCP_DEV_ID_CLIENT_SECRET`, through the typed configuration's definition for the CLI.
   - **When root is unlocked locally:** it uses `ROOT_ADMIN_SECRET`.
   - **When root is locked:** it asks once, in a terminal, for a staff token, and says where to get one (the onboarding page). Without a terminal, it exits with the exact flag, `--staff-token`, and that page's address.
   - **Re-runs:** a second run finds the client and does nothing.
   - **The developer's organisation:** `--organisation <slug>`, stored as `MCP_DEV_ORGANISATION`. It defaults to the local ID's platform organisation (the one `system_bindings` names, `answerable` locally), which `bun mcp dev` grants access to.
   - **When the local ID isn't running:** it says to start it from the main checkout with `bun dev`, or with `bun --filter @answerable/id dev`. Never from a worktree, where `bun dev` would run `env:up` (`AGENTS.md`).
2. **`bun mcp dev [mcp]`.**
   1. Migrates the MCP's local schema (`bun mcp db … migrate`).
   2. Starts the standalone server (`standalone`, `both`) and/or the Toolbox (`toolbox`, `both`) with hot reload, then waits for each `/health` to list the MCP. The generated lists already mount every MCP, so nothing is filtered. The steps below need the servers up: the Toolbox's enable refuses a provider it doesn't mount (`mcps/toolbox/src/admin-enable.ts:95-96`).
   3. For `standalone` or `both`:
      - makes sure the local ID has its resource (`http://localhost:47510/<name>/mcp`), a `claude-code-<name>` client and the link, with the same code as the register Job (M6);
      - gives the developer's organisation access with the same writes as `standalone_enable` with `everyone: true` (M6), so the developer can call every tool.

      Both are safe to run again.
   4. For `toolbox` or `both`:
      - enables the provider for the developer's organisation in the local Toolbox, through its admin API with the `mcp-dev` client;
      - adds an entitlement for the provider's grant string to that organisation;
      - says that both are local-only conveniences: staging and production stay staff decisions.
   5. Prints, in this order:
      - the MCP's local address;
      - `claude mcp add --transport http <name> http://localhost:47510/<name>/mcp --client-id claude-code-<name> --callback-port 47700` (for the Toolbox, its existing client);
      - "In Claude Code, run /mcp, choose <name>, then Authenticate".
   6. On Ctrl-C, stops what it started.
   - **What it refuses, each with the command to fix it:**
     - `bun mcp setup` not run;
     - the local ID down;
     - the development Postgres down;
     - the port taken.
3. **The journeys** (`packages/acceptance/src/journeys/`):
   - **`mcp-cli.journeys.test.ts`:**
     - with `mcps/example` (`toolbox`, made by the CLI in M3), a person of an organisation enabled and granted calls `example_notes_add`, prepares, commits, then `example_notes_list` returns the note;
     - a person of a second organisation sees none of it;
     - `person.name` in a preview is the name ID holds.
   - **The standalone side,** with e2e (`both`) at its path resource:
     - sign-in through the SDK's OAuth client;
     - `records_list`, the tool's name when served alone (`e2e.journeys.test.ts:40`);
     - a valid token for another resource (the Toolbox's) is refused at `/e2e/mcp`, which proves the audience binding with one standalone MCP.
   - **A CLI-made MCP in the acceptance:** decide whether a third, `standalone`, MCP made by `bun mcp new` inside the acceptance's own temporary checkout is worth its run time, or whether e2e covers it. Report the measured cost and your choice.
4. **The lanes** (`packages/acceptance/scripts/host-lane.ts`, `admin-lane.ts`) keep working, and say in their output that `bun mcp dev` is the everyday local loop. The lanes stay for the host checks.

## Tests first

- **`setup`:**
  - against the fake ID: mints, stores, does nothing on a second run;
  - root locked asks for a token (terminal) or prints the flag (no terminal);
  - local ID down.
- **`dev`, in process with fakes:**
  - the order of steps;
  - registration made safe to run again;
  - the printed commands, exactly;
  - each refusal;
  - stopping what it started.
- **The journeys above,** through real ID.

## Measure, and put in the report

- The time from `bun mcp dev` to "ready", cold and warm.
- The new journeys' run time.
- One by-hand run of the printed `claude mcp add` against the local stack, with Claude Code listing the tools. This needs a person at the keyboard to sign in. If you can't complete it, say so and give the exact steps for the owner.
