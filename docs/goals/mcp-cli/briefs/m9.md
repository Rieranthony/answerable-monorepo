## Notes from M7 (build these in the pass, with tests)

- **One registrar.** `scripts/mcp/local-id.ts` copies the register Job's helpers (`infra/ops/src/register.ts` keeps them in closures), and `scripts/mcp/register-conformance.test.ts` pins that the two never differ. Move the registrar into one module both use, keeping it free of runtime imports from `@answerable/mcp` (the ops image's constraint; M1 and M6 explain it). Then delete the conformance test.
- **Servers that exit under `bun --hot`.** On SIGTERM, a `bun --hot` server closes its port but stays alive, watching for changes. `bun mcp dev` ends the process group after a second; `bun run toolbox:dev` and `standalone:dev` leave a process behind. One such leftover held 47400 for a day. Make `close()` in `mcps/toolbox/src/server.ts`, `mcps/standalone/src/server.ts` and `mcps/admin/src/server.ts` end with `process.exit(0)` once everything is closed, and keep their entry-point tests green.
- **Duplicated default.** `ROOT_ADMIN_SECRET`'s local default is copied from ID's definition into the CLI's config group, and `config.test.ts` fails if they differ. Read it from one place if typed configuration allows it.

## What to do

1. **The pass over the goal's diff,** with the cleanup prompt in the README, applied to the whole range. In particular:
   - an option with one value, a function with one caller, or a file that only re-exports;
   - two ways to do one thing: the old `mcp:new`, a static example kept in a fixture's `examples` map (only inputs a static `example` can't express belong there), a hand import beside a generated list;
   - comments that repeat the code;
   - "Not yet." lines for things now built, and present tense for things not built;
   - generated files edited by hand.
2. **`bunx knip`** clean, with every finding resolved or explained.
3. **The scale benchmark,** a script under `packages/mcp-postgres/bench/` and `mcps/toolbox/bench/`, not a gate. Run on the development Postgres's own throwaway database, or a disposable container on a free port, removed afterwards. For 200 synthetic MCPs, each with 5 tools in 2 domains and one table with organisation isolation:
   - provisioning;
   - first migration and a migration with nothing pending (`migrateMcps`);
   - the Toolbox's boot ingest, first and unchanged;
   - a burst of 1,000 tool calls over every MCP through the Toolbox's pool, with the time, the connection count and the errors;
   - the median and maximum latency of one tool call with a cached profile;
   - the rendered chart size (M5's number, rerun).

   Compare each with the probe's number in `findings.md` F4 and F8a.
4. **Every gate,** on the tree that lands:

   ```sh
   bun run typecheck --force
   bun run lint
   bun run build
   bun --filter web test
   bun --filter @answerable/id test:coverage
   bun run mcp:test
   bun run mcp:test:e2e
   bun run infra:check
   bun run infra:test
   bunx knip
   ```

   Run `mcp:test:e2e` and `infra:test` one at a time, each alone on the machine.
5. **The end-to-end proof, once more, from a clean copy of the tree.**
   1. `bun mcp new demo … --serve both` without a terminal.
   2. `bun mcp add tool demo items.list`, then `items.add --mutation`.
   3. `bun mcp check demo`.
   4. Then, in the kind stack: the commit ships `demo`'s schema, migration, registration, Toolbox mount and standalone path; a person signs in to each.
   5. Afterwards, delete `demo` and the copy. Drop its schemas and roles from every Postgres the run touched, and confirm nothing of it remains in the main tree or in the development databases.
