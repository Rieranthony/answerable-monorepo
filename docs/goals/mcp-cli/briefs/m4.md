# M4: the runtime that serves every MCP

You implement brief M4 of the MCP CLI goal. Read [`README.md`](README.md) first.

**Goal.** Every declared MCP is served with its database and its context:
- **`toolbox` and `both` MCPs:** mounted in the Toolbox from a generated list;
- **`standalone` and `both` MCPs:** served by one new process, the standalone server, at `/<name>/mcp`.

The wiring the Toolbox and the admin MCP each build by hand (authority, evidence, profiles, health) becomes one package that all three use. e2e becomes an ordinary database-backed MCP served `both`, and the acceptance runs against that.

- [`../design.md`](../design.md): "Where an MCP runs", "What every tool receives" and "Database".
- [`../decisions.md`](../decisions.md): D2, D14, D15 and D18.

## What to build

1. **The shared wiring:** `packages/mcp-platform`, `@answerable/mcp-platform`. Name it otherwise if a clearer name exists, and say why. It holds what every server Answerable runs needs, lifted from the Toolbox and the admin MCP and changed only to fix the known gaps:
   - **Evidence on every call and every refusal,** including a refusal because ID did not answer the authority read. That closes `Q-SDK-ALLOW-EVIDENCE`; if the SDK needs a hook for it, add the hook in `packages/mcp`. A commit's evidence row names the intent and the receipt.
   - **Spans,** as the Toolbox has them today.
   - **Profiles:** `createIdProfiles` from M2, plus the poller's `invalidate(organisationIds, userIds)`. Lift the poller (`mcps/toolbox/src/poller.ts`) here, so both hubs invalidate grants and profiles from one audit-log reader.
   - **Health:** each database checked, with the mounted or served provider ids listed in the body.
   - **The database per MCP:** from a declared entry and the process's pools, through M1's `mcpDatabase`. The organisation getter is the SDK's call scope.
   - **The serving login's assertion,** M1's, before listening.
2. **The generated lists.** M3's generator gains:
   - `mcps/toolbox/src/mounted.generated.ts`: every `toolbox` or `both` MCP's provider import and mode;
   - `mcps/standalone/src/served.generated.ts`: every `standalone` or `both` MCP;
   - the `dependencies` of both workspaces' `package.json`.

   Drift tests for each.
3. **The Toolbox.**
   - It mounts from `mounted.generated.ts`, with no import by hand in `server.ts`.
   - Each mounted MCP's `db` is built once at boot:
     - **`shared`:** through one pool to `answerable_mcps`, as the login `answerable_mcps_toolbox`, from the new `TOOLBOX_MCPS_DATABASE_URL` in the Toolbox's typed configuration;
     - **`own`:** through one pool per MCP, from `TOOLBOX_MCP_<NAME>_DATABASE_URL`, the variable named by the generator.
   - **Profiles** come beside the grants, and the poller drops both through `invalidate(organisationIds, userIds)`.
   - **Ingest is batched per provider:** one read of the provider's stored capabilities, then one write. The contract checks and the "new capability stays off" rule stay exactly as they are. Measure it at 200 providers × 5 tools against the probe's 1.6 to 1.8 s.
   - **`/health`** lists the mounted providers, for the smoke test in M5.
   - **What the admin API leaves alone:** its routes and its enable operation don't change. The enable call still widens the Toolbox resource with the provider's grant strings.
4. **The standalone server:** `mcps/standalone`, `@answerable/mcp-standalone`.
   - **Routing:** one Bun process. It serves each MCP in `served.generated.ts` with its own `createMcpServer`, resource `${STANDALONE_ORIGIN}/<name>/mcp` and audience. A request goes to the MCP whose path matches:
     - `/<name>/…`;
     - `/.well-known/oauth-protected-resource/<name>/mcp`.

     Anything else gets `404`, and `/health` answers at the root.
   - **Its own database:** `answerable_standalone`, for intents and evidence, the same model as the Toolbox's: a drizzle journal, the runtime role, `assertRuntimeRole`, and a migrate script.
   - **MCP databases:** one pool to `answerable_mcps` as `answerable_mcps_standalone`, and one per `own` MCP.
   - **Profiles** come through its own `platform:read` machine client.
   - **Configuration:** a typed definition with `STANDALONE_HOST`, `STANDALONE_PORT` (47510), `STANDALONE_ORIGIN`, `STANDALONE_ID_ISSUER`, `STANDALONE_DATABASE_URL`, `STANDALONE_MCPS_DATABASE_URL`, the per-`own` URLs, and `STANDALONE_ID_CLIENT_ID`, `STANDALONE_ID_CLIENT_SECRET` and `STANDALONE_ID_ADMIN_RESOURCE`, with development and test defaults.
   - **SIGTERM** closes cleanly, as the Toolbox does.
   - **Locally:** `answerable_standalone` and `answerable_standalone_test`, and the logins `answerable_standalone_owner` and `answerable_standalone_runtime`, go into `infra/postgres/init` and into M1's local ensure step.
5. **The admin MCP** moves onto `@answerable/mcp-platform` for evidence, profiles and health. Its behaviour, roles, Deployment and database stay as they are (D15).
6. **e2e.**
   - It becomes CLI-shaped, the way `bun mcp new` lays an MCP out (M3): `src/mcp.ts`, a `database`, one file per tool, `mcp.json` `both` and `shared`.
   - Its records go in Postgres, in schema `e2e`, with the organisation isolation of D19.
   - It keeps its five tools, its prompt, its resource and its view.
   - **Its contracts stay byte for byte the same** (names, kinds, risks, input and output schemas), or its version moves to a new date. The Toolbox's ingest refuses to boot on a changed contract under the same version (`mcps/toolbox/src/catalogue.ts:33-41`), and staging's catalogue holds e2e's current contracts. Prove it by comparing the manifest before and after.
   - `mcps/e2e/src/server.ts` goes, with the `MCP_ID_*` variables M2 added for it. The standalone server serves e2e. If nothing else reads `readMcpEnvironment` and `parseEnvironment`, delete them and their docs rows (`bunx knip` will name them). `bun run mcp:dev` is replaced by `bun run standalone:dev`.
7. **The acceptance kit.**
   - **The stacks:**
     - `startToolboxStack` and the e2e stack start the Toolbox and the standalone server with the generated lists, against the acceptance's own Postgres (47532), on its fixed ports;
     - the standalone server takes the port the e2e server had in the acceptance;
     - the kit creates `answerable_mcps_acceptance` and `answerable_standalone_acceptance`.
   - **The journeys:**
     - e2e is reached at its path resource;
     - the Toolbox journeys run unchanged in what they prove;
     - **a new journey:** a person's `person.name` and `organisation.name`, from real ID, reach a tool;
     - **another:** two organisations through real tokens can't see each other's e2e records.
   - **The lanes** (`host-lane.ts`, `admin-lane.ts`) follow the change.
8. **Remove** e2e's in-memory record store and every reference to it, including the Toolbox's server and its Dockerfile COPY lines. The image change itself is M5's, but nothing may still import the removed store.

## Notes from M3

- **The CLI exists.** `bun mcp new` and `add tool` lay an MCP out as `src/mcp.ts` (`withDatabase`), `src/provider.ts` (markers `// bun mcp: tools`), `src/tools/<domain>-<operation>.ts`, `src/db/schema.ts` (`<name>Schema`, tables bound to their domain) and `mcp.json`. Make e2e match it. Its `mcp.json` (`both`, `shared`) already exists.
- **The generator** (`scripts/mcp/generate.ts`) writes `charts/answerable/mcps.json` today. You add the Toolbox's and the standalone server's generated lists and their `package.json` dependencies to it, and `bun mcp check` already fails on generated drift.
- **Local URLs.** `bun mcp list` prints `http://localhost:47400/mcp` for Toolbox MCPs and `http://localhost:47510/<name>/mcp` for standalone ones. The quickstart and the example's README say running a CLI-made MCP locally is Not yet: make it true and update both.

## Notes from M2

- **Bump the MCP SDK first.** `@modelcontextprotocol/server` and `client` 2.4.0 were out on 2026-10-23, and the repository pins 2.1.0. Move to the latest before building, read the changelog from 2.1.0, and run the acceptance once on the bump alone.
- **What M2 left in place for you:**
  - `createToolbox({ mount })`, where `providers` was;
  - `startGrantsPoller({ id, grants, profiles })`, still in `mcps/toolbox`, for you to lift;
  - `createIdProfiles` in `@answerable/id-admin`.
- **A failed `profiles` call** runs inside `wrapCall`, so it is evidence (`capability.completed`, failure, `UPSTREAM_UNAVAILABLE`), which the coordinator confirmed is wanted. A failed `allow` still leaves no row: that is `Q-SDK-ALLOW-EVIDENCE`, yours to close.
- **A member or organisation ID answers 404 for** is refused with `PERMISSION_DENIED`, and never served from a cached value.
- **The e2e server's machine client** (`MCP_ID_*` in `readMcpEnvironment`) exists only until e2e moves into the standalone server. Delete it then.

## Notes from M1

`assertServingLogin` refuses more than the design's four conditions: a login missing a membership for an MCP it serves, `SET FALSE`, `ADMIN OPTION`, and `CREATE` or `TEMPORARY` on the database. With a missing membership, the server refuses to start, naming it, rather than serving tools that would fail. Run provisioning, then the assertion, in that order, in every test that starts a server.
