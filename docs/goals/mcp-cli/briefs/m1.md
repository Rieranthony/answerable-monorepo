# M1: the database model in `@answerable/mcp-postgres`

You implement brief M1 of the MCP CLI goal. Read [`README.md`](README.md) first: it holds the working rules, the gates every brief runs, the cleanup pass and the report contract.

**Goal.** `@answerable/mcp-postgres` gains everything later briefs need to give every MCP a database, in either mode (D1):
- provisioning;
- migrations under the MCP's own owner role;
- grants;
- a drizzle database whose borrowed connections take the MCP's role, schema and the caller's organisation;
- organisation isolation by row-level security (D19);
- the assertion for the logins that switch role;
- the test helper.

Nothing outside this package and the local Postgres set-up changes in M1. Later briefs wire it in.

**Read first.**
- [`../design.md`](../design.md): "Database", and "What every tool receives" for how `db` is used.
- [`../decisions.md`](../decisions.md): D1, D11 and D19.
- [`../findings.md`](../findings.md): F4 (both models measured, the five conflicts with today's package, drizzle-kit's `CREATE SCHEMA` line, drizzle's `migrationsSchema`), F9 (drizzle's `pgPolicy` and `enableRLS`) and F10 (what Postgres 17 refuses to an owner role, the `CREATEROLE` step, the setting after `RESET`).
- `packages/mcp-postgres/src/*`: `connect.ts`, `migrate.ts`, `runtime-role.ts`, `testing.ts` and their tests.
- `infra/postgres/init/*.sql`.
- `infra/ops/src/bootstrap.ts`: how the deployed bootstrap creates logins and databases today. M5 calls what you build here.

## Names, fixed by the design

| Object | Name |
| --- | --- |
| Shared database | `answerable_mcps`, owned by `answerable_mcps_migrator`; tests use `answerable_mcps_test`. `revoke all … from public`; `CONNECT` for the three logins; `TEMPORARY` revoked from the two serving logins |
| An MCP's schema, either mode | `<name>`, the provider id (`^[a-z][a-z0-9]{0,11}$`) |
| Shared mode, the MCP's owner role | `<prefix>_<name>_owner`, `NOLOGIN` |
| Shared mode, the MCP's runtime role | `<prefix>_<name>`, `NOLOGIN NOINHERIT`. `<prefix>` is `mcp`, and `mcp_test` in tests |
| Shared mode, the logins | `answerable_mcps_migrator`, `answerable_mcps_toolbox`, `answerable_mcps_standalone` |
| Own mode, the database | `answerable_mcp_<name>` |
| Own mode, the logins | `answerable_mcp_<name>_owner`, `answerable_mcp_<name>_runtime` |
| The organisation setting | `answerable.organisation_id` |

Roles are shared by every database of a cluster. That is why tests use the `mcp_test` prefix and never drop a role that a development database uses. `public` and `drizzle` are refused as names here, as in the CLI.

## What to build

1. **Provisioning, shared mode.** `provisionMcps(sql, { mcps, prefix, logins })`.
   - `mcps` is a list of `{ name, servedBy }`, where `servedBy ⊆ { "toolbox", "standalone" }`.
   - It runs on a connection to `answerable_mcps` as an administrative login that has `CREATEROLE`, not necessarily a superuser.
   - For each MCP it makes, or brings back in line:
     - the owner and runtime roles;
     - schema `<name>`, `AUTHORIZATION` the owner role;
     - `USAGE` on the schema for the runtime role;
     - membership of the owner role for the migrator login, `WITH INHERIT FALSE, SET TRUE`;
     - membership of the runtime role for each serving login, the same way, revoked from a login that no longer serves the MCP.
   - **The admin's own right to create schemas.** The admin login holds `CREATE` on `answerable_mcps` as a member of its owner, `answerable_mcps_migrator`. The bootstrap grants that membership (`grant <database owner> to current_user`, as `infra/ops/src/bootstrap.ts:79` does), and the test that runs as its own `CREATEROLE` login does the same.
   - **Before `CREATE SCHEMA … AUTHORIZATION`,** it runs `grant <owner> to current_user`. Postgres 16 and later refuse the statement to a `CREATEROLE` login that isn't a superuser without it (F10, probed), as `infra/ops/src/bootstrap.ts:79` already does for databases.
   - **Role statements** take the advisory lock `runtime-role.ts:90` takes, so concurrent suites don't race on the cluster's roles.
   - Identifiers are checked against the name rule (`public` and `drizzle` refused) and quoted.
   - Running it twice changes nothing.
   - It never drops anything.
   - **No value imports from `@answerable/mcp`.** The ops image copies only `packages/mcp-postgres` (`infra/ops/Dockerfile`), so the provisioning module imports values only from `pg` and `drizzle-orm`; types are fine. Say so in its header comment.
2. **Provisioning, own mode.** `provisionOwnMcp(sql, { name, owner, runtime })`.
   - It runs on a connection to `answerable_mcp_<name>` as its owner login. The deployed bootstrap creates the database and its two logins, as it does today for the Toolbox (M5).
   - It creates schema `<name>` and gives the runtime login `USAGE`.
   - It sets no default `search_path`: an owner login can't alter another role, and `mcpDatabase` sets the path on every borrow anyway.
3. **The local set-up.**
   - `ensureLocalMcpDatabases(adminUrl)` creates `answerable_mcps`, `answerable_mcps_test` and the three logins on the development Postgres when missing. The password is `answerable`, as `infra/postgres/init/005-create-mcp-runtime-roles.sql` does today.
   - `infra/postgres/init/006-create-mcps-databases.sql` does the same for a new volume. Its header comment says it is safe to run again by hand, as 005's does.
   - The CLI (M3) and the test helper call `ensureLocalMcpDatabases`, so an existing volume needs no manual step.
4. **Migrations.** `migrateMcp({ client, name, folder, mode, grants? })`. `client` is a dedicated `pg.Client`, not a pool: a drizzle transaction on a pool borrows a fresh connection (`drizzle-orm/node-postgres/session.js:181-182`), which would lose the `set role`.
   - **The owner role has no `CREATE` on the database.** Postgres checks that right before it checks whether a schema exists, so `CREATE SCHEMA IF NOT EXISTS` is refused to it (F10, probed). Drizzle's migrator always runs that statement on its journal schema (`drizzle-orm/pg-core/dialect.js:54`), so `migrateMcp` applies the journal itself:
     - it reads the folder with drizzle's `readMigrationFiles`;
     - it keeps drizzle's journal format (`id`, `hash`, `created_at`) in `<name>.__drizzle_migrations`, a table the owner may create in its own schema;
     - it applies what is pending in one transaction;
     - it refuses an applied file whose hash changed or that disappeared, as `migrate()` does today (`src/migrate.ts`; its journal is fixed at `:36`).
   - **Shared mode:** on the client, as the migrator login, `set role "<prefix>_<name>_owner"`, migrate, then `reset role`, then the grants.
   - **Own mode:** the same as the owner login, with no `set role`.
   - **What a migration may contain.** Before anything runs, a file is refused, naming the file and line, when it holds:
     - a schema-qualified name other than `"<name>".` (match `"public".` and `public.` as qualifiers, not the word `public`: drizzle-kit writes `CREATE POLICY … TO public`);
     - `CREATE SCHEMA`;
     - `GRANT`, `REVOKE` or `ALTER DEFAULT PRIVILEGES`.

     Grants are the migration's caller's job, never the MCP's.
   - **The grants:**
     - **Default:** `select, insert, update, delete` on every table of the schema except the journal, plus `usage` on its sequences, for the runtime role.
     - **Narrowed:** with `grants`, the existing `Grant` list (`{ table, privileges }`) replaces the default. Anything not named is revoked.
     - **Then** every privilege on the schema's objects is revoked from `PUBLIC`.
   - **Re-runs:** running it again with nothing pending changes nothing.
   - **`migrate()`** stays unchanged for the hub databases.
   - **Many MCPs.** `migrateMcps(list, connections)` migrates each in turn and stops at the first failure, naming the MCP. M5's single migration Job runs it.
   - **First test, before building the rest:** against Postgres 17, a role without `CREATE` on the database migrates its schema with this loop, and drizzle's own migrator fails in the same place.
5. **The schema line.** `withoutSchemaCreation(sqlText, name)` removes drizzle-kit's `CREATE SCHEMA "<name>";` statement and its breakpoint from a migration file that has just been generated. M3's `bun mcp db <name> generate` calls it. Any other `CREATE SCHEMA` is refused, and an applied migration is never edited.
6. **Organisation isolation (D19).** `organisationIsolation(column)` returns the drizzle `pgPolicy` that an MCP's table puts in its extra-config array, alongside `.enableRLS()`:
   - permissive;
   - `for all`;
   - `using` and `with check` both `<column> = nullif(current_setting('answerable.organisation_id', true), '')::uuid`.

   An unset or reset setting then matches no row, and an insert for another organisation is refused. **Test with drizzle-kit** that a `pgSchema` table with the policy generates `ENABLE ROW LEVEL SECURITY` and `CREATE POLICY` in the MCP's schema. Report the generated SQL. This is the plan's risk 3: if drizzle-kit gets it wrong, stop and report.
7. **The database a tool gets.** `mcpDatabase(pool, { name, prefix?, schema, mode, organisation })` returns drizzle `NodePgDatabase<typeof schema>`, made once per process for each MCP.
   - **On every borrow** (pool `connect`), in one round trip:
     - in shared mode only, `set role "<prefix>_<name>"`;
     - `set search_path to "<name>"`, in both modes;
     - the organisation, from the `organisation()` getter (a UUID, checked, or `undefined`), with `set_config('answerable.organisation_id', '<uuid>', false)`, or `reset answerable.organisation_id` when it is `undefined`.
   - **On release:** `reset role; reset search_path; reset answerable.organisation_id`. A failed reset releases the connection with its error, so pg destroys it rather than returning it to the pool.
   - **Drizzle's checks:** it takes a client as a pool when the constructor's name contains `Pool` (`drizzle-orm/node-postgres/session.js:181`). The probe's `McpRolePool` (F4) is the starting point.
   - **The getter:** `organisation` is a getter so that M2 can bind it to the call scope. Tests pass their own.
8. **The serving logins' assertion.** `assertServingLogin(db, { prefix, names })`. The login must:
   - be a plain login, with none of `SUPERUSER`, `CREATEROLE`, `CREATEDB`, `REPLICATION` or `BYPASSRLS`;
   - hold memberships only in `<prefix>_<name>` roles for `names`, each `INHERIT FALSE`;
   - own nothing;
   - hold no privilege on any MCP schema or table of its own.

   It names everything it refuses. The Toolbox and the standalone server call it before listening (M4), as `assertRuntimeRole` is called today.
9. **The test helper,** in `@answerable/mcp-postgres/testing`: `testMcpDatabase({ name, schema, folder })`.
   - It ensures the local databases.
   - It drops and recreates schema `<name>` in `answerable_mcps_test` (never a role).
   - It provisions with the `mcp_test` prefix, migrates, and creates a fresh serving login for the suite with a generated name.
   - It returns:
     - `db`, an `mcpDatabase` whose organisation comes from `asOrganisation(id, fn)` (an `AsyncLocalStorage` the helper owns);
     - `asOrganisation`;
     - `close()`, which drops the suite's login.
   - It takes an `organisation` getter that replaces its own, so M2 can bind it to the SDK's call scope.
   - **The URL override is `MCPS_TEST_DATABASE_URL`.** Typed configuration's B1 leaves `mcp-postgres` without a definition: it lists `MCP_POSTGRES_TEST_DATABASE_URL` as owned by no one (`docs/goals/typed-config/briefs/b1.md`). Give the package a `defineConfig` with both variables, and rewrite the inventories.
   - **`turbo.json`.** Every MCP the CLI makes is database-backed, so a per-workspace task doesn't scale. Put the test URL variables in `globalPassThroughEnv`, or the generic `test` task's `passThroughEnv`, so each new MCP gets them with no edit. Decide whether the generic `test` task may cache a database-backed suite (each resets only its own schema) and report why.
   - Two suites for different MCPs run at the same time without touching each other.
10. **The guard against role switching in MCP code.**
    - A test in the `scripts` workspace scans `mcps/*/src/**/*.ts`, except files named `*.generated.ts`.
    - It looks for `set role`, `reset role`, `set session authorization` and `answerable.organisation_id`, case-insensitive, with optional `local`.
    - It fails, naming the file and line.
    - It covers the platform's trust boundary (design, Database, Trust).

## Tests first

- `provisionMcps`:
  - creates the roles with the right attributes and memberships;
  - a second run changes nothing (compare `pg_roles`, `pg_auth_members` and `pg_namespace` before and after);
  - changing `servedBy` revokes the old membership;
  - it works when run as a `CREATEROLE` login that is not a superuser, created by the test (the Civo shape), and fails without the `grant <owner> to current_user` step;
  - `answerable_mcps`' owner and database grants;
  - a bad name is refused before any SQL runs.
- `provisionOwnMcp`: schema and `USAGE`, no role setting, and nothing else.
- `migrateMcp`, shared and own:
  - **first:** a role without `CREATE` on the database migrates with the loop, and drizzle's migrator is refused;
  - the tables are owned by the owner role;
  - the journal is in the schema;
  - a second run is a no-op;
  - default grants allow the runtime role CRUD on tables and nothing on the journal;
  - narrowed grants are exact;
  - a folder with a `public.` or another schema's qualifier, a `CREATE SCHEMA`, or a `GRANT` is refused with the file and line, while `CREATE POLICY … TO public` passes;
  - a changed applied file is refused;
  - every privilege on the schema's objects is revoked from `PUBLIC`.
- `withoutSchemaCreation`: removes the one statement and its breakpoint, and refuses other `CREATE SCHEMA` lines.
- `organisationIsolation`, with drizzle-kit generating a fixture schema: the SQL holds `ENABLE ROW LEVEL SECURITY` and `CREATE POLICY` on `"<name>"."<table>"`.
- `mcpDatabase`, against the test database:
  - queries and drizzle transactions run as `<prefix>_<name>` with `search_path` `<name>`;
  - organisation A's rows are invisible as B; an insert with B's id as A is refused;
  - with no organisation, no rows and every insert refused;
  - a thrown transaction rolls back;
  - reading another MCP's schema is refused;
  - after release, whether the query succeeded, failed, or the transaction threw, a connection taken from the shared pool is the serving login with the default `search_path` and no organisation;
  - a reset made to fail (inject a client whose reset query rejects) destroys the connection: the pool's `totalCount` drops, and the next borrow is clean;
  - 200 interleaved calls for two organisations on one database instance never see each other's rows.
- Own mode through `mcpDatabase`: the same isolation without `set role`.
- `assertServingLogin`: passes a correct login; refuses each wrong attribute, a non-MCP membership, an inheriting membership and a direct table privilege, each with its message.
- `testMcpDatabase`: two suites in parallel for two MCPs; `close()` leaves no login behind.
- The scan test catches each forbidden form in a fixture file and passes the repository.

## Measure, and put in the report

- Sequential, 2,000 iterations, after 100 warm-up:
  - a query through `mcpDatabase` (borrow, query, release) against a plain pool query;
  - the same inside one drizzle transaction of 10 queries.
- A burst at 200 MCPs: 1,000 queries over 200 schemas through one pool of 10, with the time and connection count. This is a script under `packages/mcp-postgres/bench/`, not a gate.
