# M6: registration in Answerable ID, automatic on every deploy

You implement brief M6 of the MCP CLI goal. Read [`README.md`](README.md) first.

**Goal.** Every deploy registers what the declared list needs in ID, with no person in the loop and without the root secret once root is locked:
- each standalone MCP's resource, Claude Code client and link.

The standalone server's `standalone-hub` machine client is minted by M5. Staff get an admin MCP tool that gives an organisation access to a standalone MCP.

This builds decision D13 of the v0 code audit (the register Job's own machine client), which docs/02 tracks as `Q-OPS-REGISTER-CLIENT`.

## What to build

1. **The register Job's own machine client, `ops-register`.**
   - **The first run, with root:** it is minted at the first run that holds the root secret, before `make-admin` locks root. That is a `client_credentials` client in the platform organisation, with scopes `platform:read platform:write`, linked to ID's admin resource, through the existing `machine()` helper, link and capability.
   - **Its secret** goes into a Kubernetes Secret, `ops-id-client`, through `SecretStore`.
   - **Every later run** exchanges client credentials for a token (reuse `@answerable/id-admin`'s token handling if it fits) instead of the root secret or `OPS_ID_TOKEN`.
   - **When root is already locked and no client exists:** the Job stops with a message naming the one-time remedy, which the runbook gives as `OPS_ID_TOKEN` from a staff person, once, to mint the client. After that, nothing by hand.
   - **First test:** a machine principal with `platform:write` can create a resource, a client and a link, and patch them, in ID. This is the plan's risk 6, still unverified (F5). Prove it with an integration test against real ID (`apps/id`'s test harness or the acceptance's ID) before building on it. If ID refuses, stop and report with the exact refusal.
2. **Register from the list,** `OPS_MCPS` (M5). For each `standalone` or `both` MCP:
   - **Resource:** `https://mcp.<zone>/<name>/mcp`, `platform_shared`, with `allowedScopes` = the manifest's scopes (`<name>:read`, `<name>:write` when it has a mutation) plus `offline_access`, and `accessTokenTtl` 900, as the Toolbox's.
   - **Host client:** `claude-code-<name>`, public (`none`), `authorization_code` and `refresh_token`, the redirect from Claude Code's callback port (`values.yaml` `ops.claudeCallbackPort`), scopes `openid offline_access` plus the MCP's.
   - **The link.**

3. **Compare, then change.**
   - For each row: read it, compare it with what the list says, and `PATCH` with `If-Match` only what differs, keeping today's idempotency keys on writes.
   - A resource is never narrowed below what it holds. For the Toolbox resource, the union of the declared scopes and what enable calls added stays. Test the Toolbox resource surviving a deploy after an enable widened it.
   - An MCP removed from the list keeps its rows. A row's scopes can be narrowed only when it is an MCP's own resource and the MCP's manifest dropped a scope, and that is logged.
4. **Every deploy.** The deploy runs `register` on every upgrade, not only when a client Secret is missing (`deploy.ts:338-347`).
   - Its duration at 200 standalone MCPs must fit the hook deadline: measure with the fake ID and report.
   - Decide whether a failed register should roll the release back (today it does, `deploy.ts:281`) or leave it up with the MCP unregistered and the smoke test failing. Recommend one with the reason, and implement it.
5. **Access for an organisation: `standalone_enable`,** a new admin MCP mutation, modelled on the Toolbox's enable operation (`mcps/toolbox/src/admin-enable.ts:58-84`) and the admin MCP's `toolbox_enable`.
   - **Why it's needed:** registration makes the rows for the MCP, but an organisation can't sign in until it holds the pair capabilities and the login entitlement. No admin tool writes capabilities today: `access_grant`, `access_revoke` and `access_enable` write entitlements only (F10).
   - **What it writes:**
     - for each host client (default `claude-code-<name>`), the link if missing;
     - the capabilities for both targets, the login (`openid offline_access`) and the MCP's resource (its scopes), for each grant kind;
     - the organisation-wide login entitlement.
   - **What it doesn't write:** the resource scopes (`<name>:read`, `<name>:write`). People get those with `access_grant`, for the organisation, a group or a person. Entitlements only add up, so an organisation-wide resource entitlement written by default would make every narrower grant pointless. An optional `everyone: true` input writes the organisation-wide resource entitlement in the same intent.
   - **Prepare** reads the rows and previews exactly what it would create. **Commit** creates them once, with the intent's idempotency keys, and a second commit finds them.
   - **Role and class:** minimum role `admin`, controlled class.
   - **Undoing it:** `access_revoke` disables the login entitlement and, if `everyone` was used, the resource one.
   - **Its docs row** goes on `apps/web/content/docs/admin/index.mdx`.
6. **The kind stack** proves the whole thing:
   1. the first deploy mints `ops-register` with root;
   2. `make-admin` locks root;
   3. a second deploy, with a new `standalone` MCP added to the list, registers it with the machine client;
   4. the smoke test passes;
   5. staff run `standalone_enable` for an organisation;
   6. a person of that organisation signs in to the MCP through Claude Code's flow, using the SDK's OAuth client as the acceptance does, while a person of another organisation is refused.

## Tests first

- **The machine principal's rights in ID:** the integration test of step 1, first.
- **`register`:**
  - mints on the first run with root;
  - uses the client afterwards;
  - stops with the remedy when root is locked and there is no client;
  - registers per MCP from `OPS_MCPS`;
  - compares and patches only differences, with `If-Match`;
  - never narrows the Toolbox resource;
  - a removed MCP keeps its rows;
  - the standalone server's client.
- **Deploy:** register on every upgrade; the chosen failure behaviour.
- **`standalone_enable`:**
  - conformance;
  - its preview;
  - it creates the rows once, and a second commit finds them;
  - a role below `admin` doesn't see it;
  - against the fake ID.
- **The kind stack** sequence above.
- 100% coverage in `infra/ops` and `infra/pipeline`.
