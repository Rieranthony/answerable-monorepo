# M2: the SDK gives every tool its context and its typed database

You implement brief M2 of the MCP CLI goal. Read [`README.md`](README.md) first.

**Goal.** A tool's handler receives, ready to use:
- `person`;
- `organisation`;
- `client`;
- the MCP's typed `db`;
- `executionId`, `signal` and `principal`, as today.

A provider carries its description, its database and its tools' example inputs, and an MCP's tests serve it against its real test schema with no set-up. This brief changes the SDK's contract, so every existing provider and server moves onto it in the same brief, and every gate stays green.

## What to build

1. **The provider.**
   - `defineProvider` gains:
     - `description` (required, 40 to 1,000 characters, the same rule and message style as a tool's);
     - `database?: { schema, migrations: URL }`, where `schema` is the MCP's drizzle schema module and `migrations` its drizzle folder.
   - The manifest carries `description`. Rewrite every committed manifest.
   - `@answerable/mcp` exports the rules the CLI needs, so the two can't disagree: `checkProviderId`, `checkToolName` and `checkDescription`. Each returns the refusal message, or `undefined`, and is reused by `defineProvider`, `defineTool` and `defineMutation`.
2. **A tool's example.**
   - `defineTool` and `defineMutation` take `example?`: one valid input, checked against `input` when the module loads.
   - `assertProviderConformance` reads each tool's `example` by default.
   - The fixture's `examples` map stays, as an override for an input a static example can't express: an id the fake ID makes at test time (`mcps/admin/src/provider.test.ts:52-60`), or a function that first creates a record (`mcps/e2e/src/conformance.test.ts:14`; `packages/mcp/src/kit.ts:15` supports functions).
   - A tool with neither fails conformance, saying to add an `example`.
   - `moveTarget` stays in the fixture.
   - Move every static example onto its tool, and keep only the dynamic ones in the map.
3. **The context.** `ToolContext` becomes:
   - `person: Readonly<{ id, membershipId, name, email, groups: readonly { id, slug, name }[] }>`: `id` is `principal.userId`, `membershipId` comes from the token, and the rest from the profile resolver;
   - `organisation: Readonly<{ id, name, slug }>`;
   - `client: Readonly<{ id }>`;
   - `executionId`, `signal` and `principal`, unchanged.

   With `database`, the context also carries `db` (below). The documentation comment on each field says where it comes from.
4. **The profile resolver.**
   - `createMcpServer` takes `profiles: (principal) => Promise<{ person: { name, email, groups }, organisation: { name, slug } }>`. It is required: a server that can't say who is calling doesn't start.
   - The SDK calls it once per request that runs a handler (`tools/call`, `prompts/get`, `resources/read`, since prompts and resources also receive a `ToolContext`, `definitions.ts:23, 33`), before the handler. It is never called for `tools/list`.
   - A rejection, or a `ToolError` it throws, answers with the error envelope, `UPSTREAM_UNAVAILABLE` by default.
   - **For the Toolbox:** `mount` is `Provider[]` today (`server.ts:57`). It becomes a list of `{ provider, db? }` entries, and the hub's server takes `profiles` once.
   - **The meta tools and commits** must run the target provider's handler with the target provider's `db` and the caller's profile, not the hub's. That covers `server.call(tool, args, context)` (`mcps/toolbox/src/toolbox.ts:67`) and `commitIntent`/`apply` (`packages/mcp/src/server.ts:270-273`, `commit.ts:43`). Test both.
5. **`createIdProfiles(id, { ttlMs = 60_000, staleMs = 3_600_000, now? })`,** in `@answerable/id-admin`:
   - **What it reads:** `GET /organizations/{org}/members/{memberId}` and `GET /organizations/{org}`, in parallel.
   - **Caching:** per member (the token's `membershipId` is the member id, as `mcps/toolbox/src/grants.ts:64` uses it) and per organisation, for `ttlMs`.
   - **`invalidate(organisationIds, userIds)`:** for the Toolbox's poller, the same shape as the grants reader's (`mcps/toolbox/src/grants.ts:36`, `poller.ts:31-36`). A `user.` event names no organisation, so it drops that user in every organisation.
   - **When ID doesn't answer:** the last value is served for up to `staleMs` after it expired. With none, the call rejects, so the SDK answers `UPSTREAM_UNAVAILABLE`.
   - **The member's own fields:**
     - `groups` maps `groupId` to `id`;
     - a group membership counts while `validFrom` is past and `validUntil` is unset or future, since the group entries have no `effective` field;
     - a member who isn't effective (`effective: false`) is refused with `PERMISSION_DENIED`, a `ToolError`. That gives `@answerable/id-admin` its first workspace dependency, on `@answerable/mcp`, which creates no cycle: name it in the report.
   - **The fake ID** serves the two reads with these shapes, from `apps/id/openapi.admin.json`.
6. **The database in the context.**
   - `withDatabase({ schema })` returns `{ defineTool, defineMutation }`, whose handlers' context type adds `db: NodePgDatabase<typeof schema>`, including `db.query.<table>`. (The brief proposed `mcp`; the build named it `withDatabase`, because `mcp` collides with the `const mcp = await createTestMcp(...)` variable in tests.)
   - The serving process supplies the instance. `createMcpServer({ …, db })` and `mount` entries take the `db` made with M1's `mcpDatabase` for that provider.
   - The SDK runs every `execute`, `prepare` and `commit` inside a call scope (`AsyncLocalStorage`) holding the caller's organisation id, and exports the getter that `mcpDatabase`'s `organisation` option takes.
   - A provider with `database` but no `db` refuses to start, naming it.
   - Tools defined with the plain `defineTool` keep a context without `db`.
7. **Testing.**
   - `@answerable/mcp/testing`'s `createTestMcp` takes `profiles`. The default gives:
     - a test person: `name: "Test Person"`, `email: "person@example.test"`, no groups;
     - a test organisation: `name: "Test Organisation"`, `slug: "test"`.

     `connect({ person?, organisation? })` overrides them.
   - **Both testing entry points take a `db`.** `@answerable/mcp/testing`'s `createTestMcp(provider, { db? })` and `assertProviderConformance(provider, { …, db? })` both accept one. Today the kit builds `createMcpServer` with no `db` (`packages/mcp/src/kit.ts:38`), and a provider with `database` would refuse to start.
   - **`@answerable/mcp-postgres/testing` exports both under the same names,** as wrappers for providers with `database`. They use M1's `testMcpDatabase` and bind its organisation getter to the SDK's call scope, so `connect({ organizationId })` gives isolation by organisation. An MCP with a database imports both from there; `@answerable/mcp` can't import `@answerable/mcp-postgres`, which already depends on it.
   - A type test proves that `context.db` is typed by the schema, and that a plain `defineTool`'s context has no `db`. Use `// @ts-expect-error` in a file the typecheck covers.
8. **Callers moved onto the contract, in this brief:**
   - **`mcps/toolbox` and `mcps/admin`:** `createIdProfiles` with their existing ID clients. The Toolbox's poller calls `profiles.invalidate(organisationIds, userIds)` beside its grants invalidation, on the same events.
   - **`mcps/e2e`:** its standalone server gets a `platform:read` machine client. It adds `MCP_ID_CLIENT_ID`, `MCP_ID_CLIENT_SECRET` and `MCP_ID_ADMIN_RESOURCE` to `readMcpEnvironment`'s typed definition as optional, and requires them when `profiles` uses ID. The acceptance kit registers that client with its existing `registerMachine`. This is temporary: M4 deletes e2e's server and, if nothing else reads it, `readMcpEnvironment`.
   - **The admin MCP's tools** may read `person.name` where a preview names the actor. Don't change any behaviour beyond that.
   - **`mcps/example`, the scaffold templates and the docs snippets** in `mcps/example/src/docs/*`: move onto `description` and `example`.
9. **docs/07 and docs/08.**
   - docs/07's "Definitions are data" gets the one exception: the platform supplies the database (D17).
   - docs/08's context sentence describes what now exists, and keeps "Not yet." for `log`, `upstream` and `secrets`.

## Notes from M1 (landed before you)

- **Logins in test helpers.** M1's test helpers drop their logins under `roleLock`, because two suites dropping logins at once collide (`tuple concurrently updated`). Any helper you add that creates or drops a login does the same.
- **The name rule.** `@answerable/mcp-postgres` keeps its own copy of the MCP name rule (`src/names.ts`), because it can't import values from `@answerable/mcp`. When you export the SDK's rule, add a test in `@answerable/mcp-postgres` that both agree, for valid and invalid names.
- **The API you build on:**
  - `mcpDatabase(pool, { name, prefix?, schema, mode, organisation })`;
  - `testMcpDatabase({ name, schema, folder, organisation? })`;
  - `migrateMcp` (`mode` is `{ mode: "shared", prefix? }` or `{ mode: "own", runtime }`);
  - `assertServingLogin`.

## Tests first

- `defineProvider`: refuses a description outside 40 to 1,000 characters with the shared message; the manifest carries `description`.
- `example`:
  - checked when the module loads;
  - a wrong example is refused, naming the tool and the field;
  - conformance uses it, and a fixture override wins;
  - a tool with neither fails conformance with the message.
- A provider with `database` passes conformance through `@answerable/mcp-postgres/testing`'s `assertProviderConformance`.
- The context:
  - a handler gets `person`, `organisation` and `client` with the resolver's values;
  - the resolver runs once per call, and for a prompt and a resource read, never for a list;
  - through a hub, a meta tool's `execute` and a commit run with the target provider's `db`;
  - a rejecting resolver gives `UPSTREAM_UNAVAILABLE` in the envelope, and no handler runs.
- `createIdProfiles`, against the fake ID:
  - two reads, then a cache hit;
  - `invalidate` forces a read, including a user-only invalidation across organisations;
  - a group membership whose `validUntil` has passed is left out;
  - with ID failing after a value expired, the stale value is served until `staleMs`, then the call rejects;
  - an ineffective member is refused;
  - groups map correctly.
- The database:
  - a provider with `database` and `db` gives the handler a working typed `db`;
  - with two organisations connected through `@answerable/mcp-postgres/testing`'s `createTestMcp`, each sees only its rows;
  - a provider with `database` and no `db` refuses to start.
- The type test.
- Every existing suite stays green, with manifests rewritten.
