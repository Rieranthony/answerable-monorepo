# M3: `bun mcp`, the command that makes MCPs and tools

You implement brief M3 of the MCP CLI goal. Read [`README.md`](README.md) first.

**Goal.** `bun mcp new` and `bun mcp add tool` make a working, tested MCP and tool in seconds, for a person in a terminal and for a coding agent without one. Every rule is the SDK's own, every refusal says what to do, and nothing is ever half-written. `bun mcp list`, `bun mcp check`, `bun mcp db` and `bun mcp help` complete the set. `bun mcp setup` and `bun mcp dev` are M7's.

## The command

- **The entry point.** The root `package.json` script `"mcp": "bun scripts/mcp/cli.ts"`. Every MCP's `package.json` gets `"mcp": "bun ../../scripts/mcp/cli.ts"`. From inside `mcps/<name>`, an MCP argument may be left out, and the MCP comes from the working directory.
- **What's removed.** `mcp:new`, and `scripts/mcp-new.ts` and `scripts/mcp-templates.ts`, are replaced. Update every reference: `AGENTS.md`, `README.md`, docs pages and tests.
- **The layout:**
  - `scripts/mcp/cli.ts`: argument parsing and dispatch;
  - `scripts/mcp/commands/*.ts`: one file per command;
  - `scripts/mcp/templates/*.ts`: pure functions from a name, a date and the answers to file contents, so the docs render exactly what the CLI writes;
  - `scripts/mcp/generate.ts`.
- **Each command is a function.** `run({ argv, cwd, stdin, stdout, stderr, isTTY, prompts })` returns an exit code, so tests drive it in process.
- **Prompts.** `@clack/prompts`, the latest release, and only when `isTTY`.

| Command | Behaviour |
| --- | --- |
| `bun mcp new [name] [--description …] [--serve toolbox\|standalone\|both] [--database shared\|own] [--tool <domain.operation> --tool-description … [--mutation]] [--no-check] [--json]` | Asks for what is missing in a terminal, in the order of the design's questions. Without one, `name`, `--description` and `--serve` are required: a missing one exits with 2 and prints the full command to run again, with placeholders. Every check runs before the first write. Then it writes `mcps/<name>` from the templates and runs the steps below, printing one line per step and a `Next:` block |
| `bun mcp add tool [mcp] <domain.operation> --description … [--mutation]` | Writes `src/tools/<domain>-<operation>.ts` and its test, inserts the import and the array entry between the `// bun mcp: tools` markers in `src/provider.ts`, adds the domain's table to `src/db/schema.ts` when the template needs one that is missing, writes the migration (`bun mcp db … generate`), rewrites the manifest, and runs `check` (unless `--no-check`) |
| `bun mcp list [--json]` | One line per MCP, sorted by name: name, serve, database mode, the number of tools, the description's first sentence, and its local URL. Staging and production URLs are M5's, once the `mcp` host exists |
| `bun mcp check [mcp]` | Runs typecheck, lint and tests for the workspace; then the manifest (a stale manifest is rewritten, and the command says to commit it, exiting 0 when everything else passed); then the generator's drift check; then the role-switching scan. It prints one line per step with counts. `bun run mcp:check <workspace>` stays as the gate CI runs |
| `bun mcp db [mcp] generate` | Runs drizzle-kit for the MCP's schema, then M1's `withoutSchemaCreation` on the files just written. Refuses when `src/db/schema.ts` defines a table outside `pgSchema("<name>")` |
| `bun mcp db [mcp] migrate` | Migrates the MCP's local development schema (M1's `migrateMcp` against `answerable_mcps`, provisioning first), with the grants from `src/db/grants.ts` when it exports `grants`. For an `own` MCP, it creates `answerable_mcp_<name>` and its two logins locally first |
| `bun mcp help [command]` | Usage, with one example per command. `--help` on every command |

The steps after `new` writes its files:
1. The generator, for the dependencies. It runs before the install, so that `bun.lock` covers every dependency it writes; CI installs with `--frozen-lockfile`. It tolerates an MCP with no manifest yet.
2. `bun install`.
3. The local databases (M1's `ensureLocalMcpDatabases`), then this MCP's provisioning.
4. `bun mcp db <name> generate`: the first migration.
5. The tests, run once with `UPDATE_MANIFEST=1` passed to `bun test` directly (Turborepo strips it).
6. The generator again, now that the manifest holds the MCP's scopes and grant strings. `add tool` runs it after its manifest rewrite too, so the generated files are current even with `--no-check`.
7. `bun mcp check <name>`.

When a step fails, it says which, why, and the command that finishes the job (for the database steps, `bun mcp db <name> migrate`), and exits with 1. The files stay.

**Output and exit codes, fixed for every command:**
- **Exit codes:** 0 when done; 1 when a step failed after files were written; 2 when refused before anything was written.
- **`--json`:** success is `{ "ok": true, "steps": [{ "name", "ok", "ms" }], "next": ["…"] }`; a refusal or failure is `{ "ok": false, "error": { "code", "message", "fix" } }`. `code` is a stable kebab-case name, one per refusal, which the docs' Errors table lists (M8).
- **No colour or spinner when stdout isn't a terminal.**
- **Arguments:** in `add tool [mcp] <domain.operation>`, the positional with a dot is the tool, and the one without is the MCP.
- **`--description`** always describes what the command creates: the MCP in `new`, the tool in `add tool`. The first tool's description in `new` is `--tool-description`.

## The rules the CLI enforces (each one a tested refusal with its message)

- **The name:**
  - `checkProviderId` from the SDK;
  - not taken by any directory in `mcps/`;
  - not reserved: `toolbox`, `admin`, `id`, `mcp`, `mcps`, `standalone`, `api`, `www`, `test`, `ops`, `public`, `drizzle`. `e2e` and `example` are protected by the taken check once their directories exist. Refusing `standalone` adds: "to serve your MCP on its own URL, pass --serve standalone";
  - not in `mcps/retired.json`, which this brief creates as `[]`, with a comment in the README on what it's for.
- **The description:** `checkDescription`. Its prompt shows the rule and one good example.
- **The tool name:**
  - `checkToolName`;
  - unique in the MCP;
  - its wire name must not collide with the commit tools (`<name>_commit`, `<name>_commit_confirmed`);
  - the Toolbox name `<mcp>_<domain>_<operation>` stays within 46 characters, already guaranteed by the rules: assert it.
- **The tool description:**
  - `checkDescription`;
  - a mutation's must say "prepare" or "intent", the conformance kit's rule, checked here first with the same message.
- **`--serve` and `--database`:** exactly one of their values.
- **Unknown flags:** refused, listing the known ones.
- **One meaning per flag:** no aliases.

## The templates

Each template carries the design's guidance comments, word for word where the design gives them.

| File | Content |
| --- | --- |
| `mcp.json` | `{ "$schema": "../../scripts/mcp/mcp.schema.json", "name", "serve", "database" }`. The JSON schema is written by this brief, and the CLI validates every `mcp.json` against it |
| `package.json` | `@answerable/mcp-<name>`, private, `type: module`; `exports` `./provider`; scripts `test`, `typecheck`, `lint`, `mcp`; dependencies pinned from the templates, not copied from `mcps/e2e` at run time |
| `tsconfig.json`, `eslint.config.mjs`, `bunfig.toml` | Templates, with the 100% coverage gate |
| `README.md` | What it is, where it runs, its commands, links to the docs pages M8 writes |
| `src/mcp.ts` | `export const { defineTool, defineMutation } = mcp({ schema })` and `export const database = { schema, migrations: new URL("../drizzle", import.meta.url) }`, with a header comment that it is written by the CLI and not edited |
| `src/provider.ts` | `defineProvider({ id, description, version, database, tools: [ /* bun mcp: tools */ ] })` |
| `src/db/schema.ts` | `export const <name> = pgSchema("<name>")`, plus a comment that shows a table with `organisation_id`, `organisationIsolation(...)` and `.enableRLS()`, and says that a table without isolation is a reviewed exception |
| `src/tools/<domain>-<operation>.ts` | **Read:** a list over the domain's table, with `limit` (default 20, max 100), `cursor`, `items`, `next_cursor`, `has_more`, ordered by creation, and an `example`. **Mutation:** `prepare` validates the input, reads nothing that changes, and returns a preview whose summary names the organisation (`organisation.name`); `commit` inserts the row; risk `normal`; an `example`. Both use only `context.db`, `context.person` and `context.organisation` |
| `src/tools/<domain>-<operation>.test.ts` | A test per tool through `@answerable/mcp-postgres/testing`'s `createTestMcp`. Two organisations; each sees only its rows. A mutation is committed with the tool its intent names |
| `src/provider.test.ts` | `assertProviderConformance(provider, { manifest })` from `@answerable/mcp-postgres/testing`, with `moveTarget` only where a mutation has targets |
| `src/db/grants.ts` | Not written by default. The schema file's comment says how to export `grants` to narrow the runtime role's defaults, and that the migration reads it |
| The default first tool, when the question is skipped | `<name>.status`, a read that returns `{ status, person: person.name, organisation: organisation.name }`, so the first run shows the context working |

If a template can't be both real and general for every legal name (for example, a domain that is a reserved word in SQL), quote identifiers. If that isn't enough, refuse the name with a clear message. Report what you chose.

## The generator

`scripts/mcp/generate.ts` writes `charts/answerable/mcps.json` from every `mcps/*/mcp.json`: name, serve, database mode, and the provider's scopes and grant strings read from its manifest.
- It is the one place the declared list becomes data for the deployment.
- M4 adds the Toolbox's and the standalone server's generated lists to it; M5 reads the chart list.
- A test in `scripts` fails when any generated file differs from what the generator would write, naming the file and the command (`bun mcp check`, which rewrites them).
- `mcps/e2e` and `mcps/example` get an `mcp.json`: e2e `both` and `shared`; example `toolbox` and `shared`. e2e's tools move onto the database in M4.

## Tests first

- **Every command in process, with and without a terminal:**
  - each prompt's order and default;
  - every refusal message above (one test each, and no file written);
  - a missing flag without a terminal exits with 2 and prints the full command;
  - unknown flags;
  - `--json` output shapes;
  - inferring the MCP from the working directory;
  - `add tool` refusing a duplicate, naming the file.
- **Templates:** a snapshot per file for a fixed name and date.
- **End to end,** in a temporary copy of the working tree, without a terminal.
  - **The copy:** take the files as they are, untracked ones included (`git ls-files --cached --others --exclude-standard`), never `HEAD`. The agent doesn't commit, so a worktree of `HEAD` would test old code. Then `bun install --frozen-lockfile` in the copy.
  - **The name:** a random one (`t` plus 6 lowercase letters or digits). The run creates schemas and roles on the shared development Postgres, and `acme` is the docs' example name, which a developer may use.
  - **The run:**
    1. `bun mcp new <name> --description … --serve toolbox`: exit 0 and every step's line;
    2. `bun mcp check <name>`: green;
    3. `add tool <name> notes.list`, then `notes.add --mutation`: `check` green after each;
    4. `bun mcp list --json` names it and its 3 tools;
    5. a second `new <name>` refuses.
  - **Clean-up, even on failure:** drop its schemas in `answerable_mcps` and `answerable_mcps_test`, drop its roles (`mcp_<name>_owner`, `mcp_<name>` and the `mcp_test_` pair), and remove the copy.
- **The generator:** a drift test for `charts/answerable/mcps.json`.
- **The scan from M1** passes over everything the CLI writes.
