# M8: the documentation, in plain English

You implement brief M8 of the MCP CLI goal. Read [`README.md`](README.md) first.

**Goal.** A person or a coding agent who has never seen the repository can:
- make an MCP;
- add a tool;
- understand its database and its sign-in;
- ship it to staging and then production;

from the docs alone, in plain English. The owner asked for exactly these pages, and asked that two facts be impossible to miss: every MCP automatically gets a database linked to it, and its sign-in through Answerable ID is set up automatically. `AGENTS.md` gives coding agents the commands in a few lines.

**Read first.**
- `AGENTS.md`'s Documentation section, all ten principles. Read Lee Robinson's page it links before writing.
- [`../design.md`](../design.md): every section.
- The pages as M2 to M7 left them.
- `apps/web/components/docs/*`: every component has a Markdown form (`asMarkdown()`).
- `apps/web/lib/source.ts`, `next.config.mjs` (redirects) and the docs tests (`bun --filter web test`).

## Writing rules for this brief (on top of AGENTS.md)

- **Plain English.** Short sentences, second person, British spelling, sentence-case headings. No jargon without its meaning on first use: MCP, provider, tool, schema, migration, Toolbox, standalone server, staging, production, tag. No marketing. No idioms.
- **A command or a code block first** on every page, then the explanation.
- **Code is included from tested files,** never pasted:
  - `<include>` with regions from `mcps/example` and the CLI's templates;
  - `<ScaffoldFile>` for what `bun mcp new` writes.
- **Every error a person can hit is a row** (you see, what it means, what to do), and its text matches the tested message exactly. A test asserts that the page's error rows match the messages the CLI exports.
- **Anything unbuilt is "Not yet."**, with its trigger.

## Proof beyond the tests

Give a fresh agent the task and the docs' URLs, and nothing else from you. In the repository it also loads `CLAUDE.md`, and with it `AGENTS.md`; that is part of what the docs are for. Tell it: "Create an MCP named `demo` with a tool `items.list`, then add a mutation `items.add`, check it, and tell me how it would reach staging." It works in a temporary copy of the working tree, as M3's end-to-end test does.

Afterwards, delete the copy, and drop `demo`'s schemas and roles from the development Postgres (both databases, both role prefixes).

Report every place it hesitated or guessed, fix the page, and run it again until it doesn't. Report both runs.

## Must not touch

Any code outside `apps/web`, except the CLI's command descriptions and exported messages, which `<CliReference />` and the Errors test read. If a message is wrong, fix it in `scripts/mcp` with its test.
