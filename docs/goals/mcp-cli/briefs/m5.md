# M5: shipping from the declared list

You implement brief M5 of the MCP CLI goal. Read [`README.md`](README.md) first.

**Goal.** A commit that adds an MCP ships it to staging with a `staging/<name>` tag, then to production with `production/<name>`, with no edit outside the MCP's own folder. Its database or schema is created, its migrations run, the Toolbox mounts it or the standalone server serves it, and the smoke test checks it. Registration in ID is M6's.

The rules that bind beyond the README's: nothing from a laptop, no plaintext secret, expand then contract, the image tag is the commit SHA, and the cluster runs digests.

## What to build

1. **One image, `mcps`.**
   - `mcps/Dockerfile` builds every MCP workspace's production install and every view.
   - It replaces `mcps/toolbox/Dockerfile` and `mcps/admin/Dockerfile`, both deleted, with their comments carried over where still true.
   - The probe's version is the starting point (F2).
   - Each Deployment chooses its server by command.
   - `.dockerignore` keeps tests, coverage and local files out; check that no `*.test.ts` is in the image.
   - The images are `id`, `mcps` and `ops`, read from one committed list, `infra/pipeline/images.json`, by:
     - the build matrix (`fromJSON`);
     - the promote loop and its count;
     - `deploy.ts`'s image names and digests;
     - the smoke test.
   - Write the runbook step for the one GHCR visibility flip of the new package.
2. **The chart reads `charts/answerable/mcps.json`** (M3's generator) with `.Files.Get … | fromJson`.
   - **Make the file's root an object** (`{ "mcps": […] }`). `fromJson` on an array silently returns an error map.
   - **Don't name it `values-*.yaml`:** `infra/check.ts` would take it for an overlay. From it the chart renders:
   - **Bootstrap.** `OPS_MCPS` for the bootstrap Job, plus the ops Role's Secret names.
     - The bootstrap (`infra/ops/src/bootstrap.ts`) creates `answerable_mcps`, `answerable_standalone` and their logins (`answerable_mcps_migrator`, `answerable_mcps_toolbox`, `answerable_mcps_standalone`, `answerable_standalone_owner`, `answerable_standalone_runtime`), with their Secrets.
     - For each `own` MCP, it creates `answerable_mcp_<name>` and its two logins and Secrets.
     - It then runs M1's `provisionMcps` and `provisionOwnMcp`.
     - It stays safe to run again, and still never prints a password.
   - **Migrations.**
     - **One new hook Job, `mcps-migrate`,** from the `mcps` image. It runs `mcps/standalone/scripts/migrate-mcps.ts`, which:
       - migrates every MCP with M1's `migrateMcps`: each `shared` MCP as its owner role through the migrator login, each `own` MCP as its owner login;
       - reads each MCP's `grants` from `src/db/grants.ts` when the file exports them.
     - **Why that workspace:** it is in the image, and in `mcps/standalone` the script imports nothing that depends back on it. In `packages/mcp-postgres` it would have to import the hubs' migrations, which depend on that package: a workspace cycle.
     - **The hub databases keep their own Jobs.** `toolbox-migrate` and `admin-migrate` stay as they are, plus a new `standalone-migrate` for `answerable_standalone`. Each mounts only its own owner login (`migrations.yaml:1-5`), and the admin MCP's credential stays apart (D15).
     - **Weights, each explicit:** `id-migrate` -10, `toolbox-migrate` -9, `admin-migrate` -8, `standalone-migrate` -7, `mcps-migrate` -6. Helm runs hooks one at a time in weight order. Say in the template's comment that no Job depends on another's work beyond that order.
     - **The deadline:** check `activeDeadlineSeconds` against 200 MCPs, using M1's measured time.
   - **The Toolbox.** `TOOLBOX_MCPS_DATABASE_URL` and the per-`own` URLs, from their Secrets.
   - **The standalone server,** rendered only when the list has a `standalone` or `both` MCP:
     - its Deployment through `_server.tpl`, with command `bun mcps/standalone/src/server.ts`;
     - its environment;
     - one Ingress on `mcp.<zone>` with two `Prefix` paths per MCP (`/<name>/`, `/.well-known/oauth-protected-resource/<name>/`), serving the shared certificate;
     - its HPA and PDB;
     - its network policy;
     - its client Secret wait, as the Toolbox has today.
   - **The standalone server's client.** The register Job mints `standalone-hub` (`client_credentials`, `platform:read` on ID's admin resource) and writes its Secret, as it mints `toolbox-hub` today (`infra/ops/src/register.ts:63-65, 83-85`), so the standalone server starts in this brief's kind stack. Everything else about registration is M6's. The plumbing the Toolbox's client already has, extended to it:
     - `register`'s `clientSecrets` map (`infra/ops/src/register.ts:27-30`) gains its Secret;
     - `deploy.ts`'s `missingClientSecrets` (`:338-347`) gains it, so the first install runs register;
     - `OPS_START_DEPLOYMENTS` and the ops Role's Deployment names (`charts/answerable/templates/ops.yaml:7`) gain the standalone Deployment, so register starts it from zero replicas.
   - **Smoke checks per standalone MCP:** its metadata URL answers with the right `resource`. The Toolbox's `/health` lists every `toolbox` and `both` MCP.
3. **Terraform.** The `mcp` hostname goes into both tfvars, the edge's key check (`infra/civo/modules/edge/variables.tf:44-47`) and the tests (staging, production and edge `tftest.hcl`). Nothing per MCP follows. Confirm that the DNS record, the reissued certificate and the rule expressions follow from the map, and note the one-time reissue in the runbook.
4. **`run-job`.** Decide and fix the mismatch F6 found: it checks out `main`'s chart with the deployed images. Recommended: render the chart at the deployed revision (the release's `REVISION` label or annotation). Test it.
5. **The kind stack** (`infra/k8s`) proves a commit with e2e (`both`) and example (`toolbox`) end to end:
   - the bootstrap creates the schemas;
   - `mcps-migrate` runs;
   - the Toolbox mounts both;
   - the standalone server serves e2e at `/e2e/mcp` through Traefik on `mcp.<local zone>`, including the well-known path and the Host check;
   - the smoke test passes.

   Every test and helper derives its expectations from `mcps.json` rather than from fixed names (`stack.ts`, `edge.yaml`, `values-local.yaml`, `charts.test.ts`).
6. **Chart tests at scale.** Render with lists of 0, 1, 3 and 200 MCPs, each time from a temporary copy of the chart with its `mcps.json` replaced, because `.Files.Get` reads only the chart's own files. At 200, measure the rendered release's size against Helm's 1 MiB release Secret. If it is close, report it with a recommendation. Don't build around it.
7. **The connection budget.**
   - docs/12's budget gains the two new pools per replica (the Toolbox's and the standalone server's, at their sizes) and one line per `own` MCP.
   - `bun mcp check` warns, from the same numbers in one shared module, when the `own` MCPs' pools would pass the budget. Build that warning here: M3 left it out.
8. **`bun mcp list`'s deployed URLs.** Export the zones from `infra/pipeline/src/environments.ts` (`ZONES` isn't exported today, `:22`), and have `list` print each `standalone` or `both` MCP's staging and production URL on `mcp.<zone>`.
9. **The ops image** copies only `packages/mcp-postgres` (`infra/ops/Dockerfile`). Check that the provisioning it now runs imports no values from `@answerable/mcp` (M1's rule), or copy the packages it needs.

## Notes from M4

- **Test-only variables.** `TOOLBOX_MCPS_ROLE_PREFIX` and `STANDALONE_MCPS_ROLE_PREFIX` (fallback `mcp`) exist only so entry-point tests use their own roles. The chart never sets them, and a chart test asserts it.
- **`/health`.** The Toolbox's and the admin MCP's now answer `{ status, databases, providers }`, and the standalone server's the same. The smoke test reads `providers`.
- **No check on an own MCP's login.** `assertServingLogin` covers the shared serving logins only, so a server starts without checking an own MCP's runtime login. Add an own-login assertion in `@answerable/mcp-postgres` (no ownership, no `CREATE` on its database, its schema's `USAGE`), and call it in the Toolbox and the standalone server before they listen.
- **The images.** M4 patched the Toolbox and admin images only enough to build (the Toolbox image copies e2e and example). The `mcps` image replaces both.
- **e2e's view** is bundled when first imported (about 45 ms; 753 ms cold in a read-only container), so the image needs no build stage.
- **The standalone server's own database** is `answerable_standalone`, with `answerable_standalone_owner` and `answerable_standalone_runtime`, and a migrate script in `mcps/standalone`. Its `platform:read` client is `standalone-hub`.

## Notes from M3

- **The admin login keeps every owner role.** `provisionMcps` leaves the administrative login a member of every MCP owner role, with `INHERIT TRUE`: the `grant <owner> to current_user` step, which `create schema … authorization` needs. On Civo, that login would then inherit every MCP's owner role. Make the self-grant `WITH INHERIT FALSE, SET TRUE` (SET is all the `AUTHORIZATION` check needs) or revoke it after the schema exists, and change M1's assertion in `provision.test.ts` to match.
- **`roleLock` doesn't span databases.** It is an advisory lock, and advisory locks belong to one database. M3 found `ensureLocalMcpDatabases` (lock taken in `postgres`) racing `provisionMcps` (lock taken in `answerable_mcps`) on `GRANT … ON DATABASE`, and fixed it by having the local set-up grant only on a database it has just created. Any exclusion you build across databases needs a lock in one agreed database.
- **The chart's list.** `charts/answerable/mcps.json` exists, written by `bun mcp`'s generator, with an object root: `{ $comment, mcps: [{ name, serve, database, scopes, grants }] }`.

## Notes from M1

- **Attributes.** `provisionMcps` changes only the attributes that are wrong. A `CREATEROLE` login without `CREATEDB` can't even restate `NOCREATEDB` on an existing role, so clearing a drifted `CREATEDB` needs an administrative login that holds `CREATEDB`. Civo's has it (`OPS_DATABASE_ADMIN_URL`, "CREATEDB and CREATEROLE").
- **Database-level privileges.** `provisionMcps` sets them on `answerable_mcps` itself (owner check, `PUBLIC` revoked, `CONNECT` for the three logins, `TEMPORARY` revoked from the serving logins), so the bootstrap needs no grant code of its own for that database.
- **Connections.** `Sql` has the same shape as `infra/ops`' `Sql`, but must be one connection: `provisionMcps` uses `begin` and `commit`.
