## Suspects (to confirm or clear)

- `audit_event_subjects.provenance` admits `legacy_derived`; nothing writes it (grep: only the schema and SQL). The `origin` parameter of `capture_audit_subjects` is always `'recorded'`.
- `capture_audit_subjects` branches on `schema_version` 1, 2, 3 and `record_user_oauth_subjects` on 4. The app writes versions 1, 2, 3 and 4 today (19 files). Pre-production, the versions are history of a never-shipped contract; one version per action may do.
- `oauth_resources.policy_version` is read into the API (services/resources.ts:36) and never written beyond its default; `revision` on the same table is the one the policy reads (member-permission.ts:89).
- `invitations`: Better Auth organisation-plugin table; the app only soft-deletes rows on erasure (queries/organizations.ts:347) and wraps adapter writes. Whether anything creates one is open.
- No sweep of expired `oauth_access_tokens`, `oauth_refresh_tokens`, `verifications`, `oauth_client_assertions`, `sessions`; deletes exist only for revocation and erasure. `expires_at` indexes exist on all five.
- `protect_product_parents` fires on 16 tables including `sessions`, `oauth_access_tokens`, `oauth_refresh_tokens`, running up to seven dynamic `EXECUTE … FOR SHARE` lookups per row.
- `protect_private_resource_assignment` and `protect_resource_ownership` lack `SET search_path`; the other 21 functions have it.
- Two overlapping indexes on `audit_event_subjects` (`entity_idx` and `tenant_entity_idx`, both ending in `event_id`) beside a four-column primary key.
- `oauth_access_tokens` carries seven secondary indexes plus a unique `token`; whether JWT access tokens insert rows at all is to be read in the installed `@better-auth/oauth-provider` 1.7.2.
- `intents` has only its primary key and is never deleted; `evidence_events` has only `unique (organisation_id, seq)`. Both match today's queries (PK and `(org, seq)` walks).

## Audit D (Toolbox, mcp-postgres, admin MCP), 2026-10-06, in `audits/d-toolbox-mcp-postgres.md`

- Core sound: 28-field hash layout agrees in the comment, the trigger and `evidence.ts`; `verify` caught 30 of 30 single-field changes; every hot-path statement is a PK or `(organisation_id, seq)` lookup at 0.009 to 0.036 ms mean. Three suites green (24, 79, 120 with 6 n/a skips).
- Delete: `evidence_events.on_behalf_of`, `operation_id`, `target_type`, `target_id` (never written); 8 of 16 `kind` values (never written); `intents.approval` (derived from `policy_class`, never read); `capabilities.status`; `providers.version/manifest/registered_at/status` (write-only; in-process manifest is the truth); GIN `capabilities_search` (0 scans, planner seq-scans at 137 rows); the legacy-layout migrator test.
- Growth: `intents` never deleted while the SDK's memory store sweeps terminal intents after a one-day replay window; 6,963 B per mutation across the three tables, 2.54 GB a year at 1,000 mutations a day. `intents.preview` duplicates the erasable payload (15 of 15), so `erase()` erases nothing in practice.
- Two reproduced gaps: expiry runs twice per call so an intent can end `expired` with no `intent.expired` row; `verify` never reads payload bodies, so a changed body with its hash kept passes.
- Lock: one organisation caps at 373 to 407 events/s with 20 writers (1,263 to 1,566/s across 20); `hashtext` collision odds for 75 organisations 6.5 × 10⁻⁷. Keep.
- Migrations: reset to one file per directory; record `namespace/file` with a checksum; apply directories in the given order (package first). Reproduced: an edited applied file is skipped silently; a server file that sorts before the package's breaks a fresh database. ID's Drizzle migrator stores a hash and never compares it (`drizzle-orm@0.45.2/pg-core/dialect.js:56-69`).
- Add (cheap): `check (expires_at > created_at)`, `check (commit_token_hash ~ '^[0-9a-f]{64}$')` on `intents`; payload integrity in `verify` and an update guard on `evidence_payloads`.
- Keep separate `answerable_admin*` databases; `mcp:new` scaffolds no database. Timings are upper bounds (host load 23 to 260 during the run).

## Audit B (ID functions, triggers, RLS), 2026-10-06, in `audits/b-id-triggers-rls.md`

- Hot path: `protect_product_parents` on `sessions`, `oauth_access_tokens`, `oauth_refresh_tokens` costs 0.28 to 0.62 ms per row, 55 to 70% of each insert's server time, and duplicates checks the application makes in the same transaction (`federation.ts:180-190`, `currentGrantAuthentication`, `lockResourceGrantPolicy`). Its `FOR SHARE` made 50 of 50 concurrent token inserts hit the 2 s `lock_timeout` behind a 2.5 s client-row update; with the FK alone, none. Verdict delete on those three tables.
- Hole (reproduced by the agent and by the coordinator): the runtime role may create temp tables and Postgres searches `pg_temp` before `pg_catalog` and `public` unless `pg_temp` is listed explicitly, so a caller's temp `oauth_resources` or `system_bindings` shadows the unqualified names in `protect_private_resource_assignment` and `protect_capability_target` (the latter despite `SET search_path = pg_catalog, public`). A cross-tenant entitlement and a platform-scoped `admin_session` capability were inserted (rolled back). Fix: schema-qualify every relation in trigger functions, put `pg_temp` last in `search_path`, revoke TEMP from PUBLIC and assert it at startup. The SECURITY DEFINER functions already qualify with `public.`.
- Constraints can replace most of the deletion machinery: generated `live` columns plus composite FKs hold parent liveness, live-reference refusal and binding protection (probe 11 reproduces the refusals and the tested race, without blocking non-key parent updates); per-table CHECKs hold "a deleted row is inactive and holds no credentials"; a three-line trigger keeps deletion terminal. Not verified: whether drizzle-kit generates composite FKs onto generated columns.
- Dead or duplicated: `grant_delete` policy and the runtime's DELETE on `grant_contexts` (nothing deletes them); `audit_insert` on `audit_event_subjects` (no non-owner can insert); immutability triggers on `system_bindings` and `admin_operations` (owner-only tables); DELETE branch of `touch_client_resource_revision`; two revision functions, two resource-immutability triggers and two grant-context insert triggers to merge (compute the authentication evidence instead of comparing JSON built with `to_char` against `toISOString`).
- Keep: RLS (+0.25 ms on a 0.19 ms policy query; the membership subselect costs nothing measurable; read policies repeat the write clause and carry literal `true`/`false` terms to tidy); audit-subject triggers (recorded decision) at +0.5 ms per machine token, +0.9 per sign-in, +1.8 to 2.2 per user token or refresh, 15 subject rows per refresh at 457 B each: `audit_event_subjects` is 3x the size of `audit_events` and is the main growth driver.
- Caveats: host load 33 to 158 during timings, so only on/off deltas are robust; the ID suite was stopped after 5 files (2 failures, at least one load-related); measurements ran on `answerable_id` in the agent's container.

## Audit C (ID indexes, growth, migration tooling), 2026-10-06, in `audits/c-id-indexes-growth-migrations.md`

- Indexes: delete `audit_event_subjects_tenant_entity_idx` (no query reads subjects by organisation; 27% of the table, 1,914 B per token refresh). The four `expires_at` indexes on sessions, access tokens, refresh tokens and client assertions serve no query today; keep only with the sweep. Every other index has a cited query; none is missing (`sso_providers.domain` is at most ~75 rows; the Toolbox poller's cursor page is a PK backward scan at 0.145 ms).
- `oauth_access_tokens` rows exist only for opaque login-only tokens; resource tokens are JWTs and write no row (`@better-auth/oauth-provider` `introspect-C6P1zrTr.mjs:1800,1852`). The five FK-column indexes cost ~67 µs per insert, within noise; the parent-guard trigger ~236 µs of ~355 µs.
- Growth: Better Auth sweeps `verifications` itself on every `findVerificationValue`. Nothing sweeps `oauth_refresh_tokens` (one row per refresh, kept forever), `oauth_access_tokens`, `oauth_client_assertions` or abandoned `sessions`. Revoking one client's tokens scanned 200,000 rows in 201 ms. Verdict: one batched sweep job in ID as the runtime role (which already may DELETE those tables).
- Per user token refresh about 9.9 KB: 1 audit event (2.1 KB), 14.95 subject rows (7.2 KB, 73%), 1 refresh row (0.56 KB). Only the `user` subject is ever read (`queries/audit.ts:186-191`). Illustration: 1,000 hosts × 8 h at a 900 s TTL is ~316 MB a day.
- Migration file: no drift. Postgres catalogue comparison of two fresh databases: the committed SQL equals drizzle-kit's output from the schema modules plus exactly 23 functions (and their ACLs), 57 triggers, one deferrable FK and two `NULLS NOT DISTINCT` indexes; drizzle-orm 0.45.2 cannot express those three (no `nullsNotDistinct()` on `IndexBuilder`, no deferrable option on `foreignKey`). The catalogue pins all but the two indexes.
- Tooling: Drizzle's migrator runs every pending migration in one transaction, takes no lock and never compares the stored hash (`pg-core/dialect.js:54-71`), so three of `test-migrations.ts`'s four cases re-check Postgres and Drizzle. Reset shape: generated `0000_initial.sql` plus `0001_invariants.sql` (`drizzle-kit generate --custom`: deferrable FK, the two indexes, functions, triggers, REVOKE); replace the 1,191-line hash catalogue with a catalogue-equivalence test; shrink `test-migrations.ts` to fresh-install and re-run-is-a-no-op; move concurrent bootstrap into `bootstrap.integration.test.ts`; set `lock_timeout` on the migration connection; drop and recreate every existing ID database.
- Foreign keys: 45 (30 cascade, 11 restrict, 4 set null); only 3 can fire for the runtime role. None missing. Recommend `restrict` on the five cascades into `grant_contexts`, since an owner-level delete would silently remove retained grant evidence.
- Full ID suite on the loaded host: 1,461 pass, 24 fail, 5 errors in 2,383 s; failures are timeouts (load 106 to 150), not re-run.

## Audit A (ID columns, vocabularies, audit versions, naming), 2026-10-06, in `audits/a-id-columns.md`

- Deciding fact: ID serves only 18 Better Auth routes (`http/auth-allowlist.ts`); client registration, organisation and invitation routes, SSO provider registration, end-session and SAML are unreachable (404 at `app.ts`). Columns only those routes write are dead. A write census of all 73,097 row images in the suite found 27 columns never filled.
- Delete: `oauth_clients.user_id` and the owned-client erasure and `ownerUserId` locking built on it (no writer; 28 fixture rows only); `sso_providers.user_id` and its attribution-clearing block; `sso_providers.saml_config`; 14 never-written `oauth_clients` columns echoed by the admin API; `post_logout_redirect_uris` and `backchannel_logout_uri` (a half-live deferred remote-logout feature: settable, delivered by the plugin's sign-out hook, hidden from discovery); `oauth_resources.policy_version`, `signing_key_id`, `custom_claims` (+ its CHECK), `metadata`, `dpop_bound_access_tokens_required`; `oauth_client_resources.metadata`; `groups.external_id` (nothing syncs directory groups, so a "directory" group is permanently empty); `organizations.logo`, `metadata` (low priority); `audit_event_subjects.provenance`/`legacy_derived`; 8 unreachable version branches of `capture_audit_subjects` that only 34 fixture-inserted events reach; the version-2/3 link-event visibility filter.
- Audit versions: every action is written at one version except entitlement events (1 for member principals, 2 for group/organisation) and `oauth.token.rejected` (2 or 3). Verdict: one payload per action, all version 1, keep the integer column; replace the 4,494-byte `schemaVersion` description (which says "0 is legacy" and "1, 2 or 3" beside version 4) with a per-action payload table.
- Subjects: 14.24 subject rows per `oauth.user.issued`, 1 read; the only reader asks `entity_type = 'user'`. Verdict: keep a trigger-owned subject index (recorded decision) but narrow it to `audit_event_users (user_id, event_id)`: 124 B per event against 7,189 B today (probe 06), lookup 0.037 ms against 0.055 ms. `audit_events` alone covers direct subjects through four indexed queries but not users named only inside bulk manifests (5.6% of user subject rows).
- `grant_contexts.authentication` (10 JSON keys: 5 duplicate columns, 1 never read, 4 needed after the session is gone) → four typed NOT NULL columns named as on `sessions`; one insert trigger instead of two; drop the `data.authentication` copy and comparison in v4 audit rows (read the permanent grant row instead).
- `sessions.active_organization_id` equals `authentication_organization_id` in 3,446 of 3,449 app-written sessions (the 3 others are fixtures) and the plugin route that changes it is unreachable → drop it, its index, the clearing step and manifest.
- `invitations` is always empty (9 fixture inserts in the whole suite) but the SSO plugin reads it on first sign-in while `organizationProvisioning` is on, and `members.role` is mandated by the plugin. Q1: provision membership in ID (it already does for linking, `auth/verified-sso.ts:226-246`), disable plugin provisioning, then delete both. Boot without the table: not verified.
- Keep: all policy tables, revisions, deletion markers, vocabularies (every value has a writer except `legacy_derived`), plugin token/verification columns including untested-but-reachable paths (`requested_user_info_claims`, `confirmation`, rotation replay). `accounts.password` costs nothing. Upstream tokens in `accounts` are stored encrypted and never read by ID (Q3).
- Renames worth taking now: `oauth_*_tokens.revoked` → `revoked_at`; `oauth_client_resources.resource_id` → `resource`; `system_bindings.resource_id` → `resource_instance_id`. Identifiers are consistently American; keep.
- Suite on the loaded host: clean 1,422 pass / 39 fail / 5 errors in 2,407 s (load); census 1,534 pass / 21 fail (20 from the disk-full window, re-run clean). One test failed in both runs: `authorize refuses a malformed request before writing a flow` (`auth/user-oauth.integration.test.ts:2031`, `"null" cannot be parsed as a URL`).
