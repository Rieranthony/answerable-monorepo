Typed configuration

Asked on 21 October 2026 at step 6.1 of the staging tutorial: what the other variables and secrets are, what they default to, and whether the defaults should live in code with one typed place for secrets and settings. Every claim below was read from the tree at e7bce746; the file paths are in docs/goals/typed-config/findings.md. Nothing is coded yet.

The short answer

The secrets already flow the way you asked for: nothing non-secret is pasted into GitHub, and every other value a pod sees is generated in the cluster or computed by the chart from three hostnames. What is missing is the typed place. The defaults are written four times by hand, a clone needs 29 lines of .env to run, and the docs table has drifted once already. The proposal keeps the secrets exactly where they are, moves the development and test defaults into code, and generates the inventories and the docs table from one typed definition per service.

Decisions need your yes

  1. D1 NODE_ENV stays the only switch, with its three values. No staging value and no per-environment branch in application code. Staging and production run the same production profile; their differences stay in values-civo-<env>.yaml, envs/<env>.tfvars and the GitHub environment, where Ingress, DNS, the certificates and the deploy already read them.
  2. D2 Development and test defaults move into code. Every non-secret variable of ID, the Toolbox and the admin MCP gets its localhost value as the default under development and test; ID's own two secrets get a fixed development-only value that the production profile refuses. Result: a fresh clone runs ID with no .env; the Toolbox and the admin MCP need only the client pair your local ID issued; .env holds credentials and nothing else.
  3. D3 One shared package, packages/config. defineConfig(label, fields), each field { schema, secret, default?: { development?, test? }, doc }; it returns a typed read(env) that names the variable it refuses, as the loaders do today, and the fields' metadata. ID's env.ts, the Toolbox's and the admin MCP's environment.ts, the ops Jobs' commands.ts and the SDK's readMcpEnvironment move onto it. No behaviour change under NODE_ENV=production.
  4. D4 Generated, not hand-written. default.env and .env.example come from the metadata, and a test fails when either drifts, as the OpenAPI snapshot and the MCP reference do. docs/06's configuration table becomes a docs component rendered from the same metadata, with its Markdown form.
  5. D5 Secrets do not move. The environment keeps its 14 names and the ops Jobs keep generating the rest. The pipeline reads which secrets go into id-env from ID's metadata, so a new ID secret fails a pipeline test until a workflow hands it over. In the same stroke, both deploy steps pass BETTER_AUTH_SECRETS (F2).
  6. D6 After staging/first. This changes how the services read their environment, so staging proves the current build first; the change ships under the second staging tag.
  7. D7 Hostnames stay out of application code. They remain in the tfvars, the chart overlay and the pipeline's ZONES, which the chart tests and the pipeline tests already tie together.
