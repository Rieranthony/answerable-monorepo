# B1: `packages/config` and the loaders on it

**Goal.** One typed definition per service that names every variable it reads, its type, whether it is a secret, its development and test defaults and its doc line. The loaders of ID, the Toolbox, the admin MCP, the ops Jobs and the MCP SDK use it. `default.env` and `.env.example` are generated from the definitions, and a test fails when either drifts. A clean clone runs ID with no `.env`.

**Read first.** `docs/goals/typed-config/task_plan.md` (D1 to D7, approved 2026-10-21) and `findings.md` (the inventory you are encoding: every variable, its default, its secret flag, its source in staging). Then `AGENTS.md`. This brief implements D2, D3 and the file half of D4; B2 does the docs component, the pipeline and the workflows.

**Rules that bind.** No behaviour change under `NODE_ENV=production`: every variable required today stays required, every default that exists today stays, every refinement stays. No `staging` profile (D1). No hostname in code (D7). No real credential in code or in a committed file. 100% line and function coverage in the new package and in every workspace touched. Style: no semicolons outside `apps/id`. Commits imperative, sentence case, no prefix, no trailing period. Land on `main` once every gate below is green (the owner lands on main, no pull requests); start only after the tag `staging/first` has deployed and smoke-tested (D6).

## 1. The package

`packages/config`, package name `@answerable/config`, modelled on `packages/auth/package.json` (zod 4.6.5 as the only dependency; `test`, `typecheck`, `lint` scripts; 100% coverage in `bunfig.toml` as the other packages). Exports, each with a documentation comment:

- `defineConfig(label, fields, options?)`.
  - `fields`: an object keyed by variable name. Each field: `schema` (a zod schema of the raw string, with the coercions and transforms the loaders use today), `secret` (boolean, default false), `fallback` (optional string: the value in every profile when the variable is unset, such as `"47300"` for `PORT`; replaces zod `.default()` so the generator can print it), `defaults` (optional `{ development?: string; test?: string }`: applied when `NODE_ENV` is that profile and the variable is unset or empty; never under `production`), `doc` (one line: the comment in `default.env`, the docs row), `source` (optional: where the value comes from in a deployed environment, one of `deploy`, `cluster`, `chart`, `image`, `operator`; omitted for tooling and local-only variables).
  - `options.refine`: a `(data, ctx) => void` for cross-field rules (the platform-application pairs, ID's production requirements, the ops Jobs' staff domain and tenant together).
  - Returns `{ label, read, fields }`. `read(env)` parses `env` (a `Record<string, string | undefined>`) and returns typed data; `NODE_ENV` is added by the package as `z.enum(["development", "test", "production"]).default("development")` and is part of the data. `fields` is the metadata for the generator: name, secret, fallback, defaults, doc, source, and `optional` (whether the schema accepts an unset value).
  - Under `production`, `read` refuses a secret whose value equals one of that field's development or test defaults, with the message `<NAME>: a development default`. This is what makes fixed development secrets safe to commit.
  - Errors: throw `ConfigError` with `issues` and the message `Invalid <label> configuration: <NAME>: <problem>; <NAME>: <problem>`, which is the MCP SDK's format today (`packages/mcp/src/environment.ts`). ID's `EnvironmentValidationError` and its message `Invalid environment variables: …` go; update ID's tests to the new message.
- `ConfigError`, the `Field`, `FieldMeta` and `Config` types.

## 3. The generator

`scripts/env-inventory.ts` in the `scripts` workspace, run as `bun run env:inventory` from the root. It imports every definition (ID, ID tooling, Toolbox, Toolbox tooling, admin MCP, admin tooling, the SDK, ops; add the workspace dependencies or `exports` entries that makes possible, and keep `bunx knip` clean) plus a static list, in the generator, of the variables no definition owns, each with a doc line: `apps/web`'s `GOOGLE_SHEETS_ID`, `GOOGLE_SERVICE_ACCOUNT_EMAIL`, `GOOGLE_SERVICE_ACCOUNT_PRIVATE_KEY`, `OAUTH_TEST_ISSUER`, `OAUTH_TEST_CLIENT_ID`, `OAUTH_TEST_CLIENT_SECRET`, `OAUTH_TEST_REDIRECT_URI`; `MCP_POSTGRES_TEST_DATABASE_URL`; the GitHub environment's `CIVO_TOKEN`, `CLOUDFLARE_API_TOKEN`, `GH_SECRETS_TOKEN`, `STATE_ACCESS_KEY_ID`, `STATE_SECRET_ACCESS_KEY`, `KUBE_SERVER`, `KUBE_CA`, `KUBE_TOKEN`; `INFRA_STACK_KEEP`, `TF_PLUGIN_CACHE_DIR`. It writes three files, and `scripts/env-inventory.test.ts` fails when any differs from what it would write (`UPDATE_INVENTORY=1` rewrites them, as `UPDATE_MANIFEST=1` does for manifests):

- `default.env`: the header as today (tracked, empty values, what each means), then one section per group with the group's name and reader as a comment, and `NAME=` per variable with its doc as the comment line above it. Every one of today's 78 names stays present; a name may only disappear when its reader is gone.
- `.env.example`: a header that says every other variable has a development default and `default.env` lists them all, then only the variables a developer must supply because another system issues them: `MICROSOFT_CLIENT_ID`, `MICROSOFT_CLIENT_SECRET`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `TOOLBOX_ID_CLIENT_ID`, `TOOLBOX_ID_CLIENT_SECRET`, `ADMIN_ID_CLIENT_ID`, `ADMIN_ID_CLIENT_SECRET`, with their doc lines and empty values. `apps/web/.env.example` stays as it is (Next.js reads its own file).
- `packages/config/inventory.json`: every group with its fields' metadata (name, secret, fallback, defaults, doc, source, optional), the input of B2's docs component and pipeline test.

ID's test "default.env holds names with empty values only" in `apps/id/src/env.test.ts` moves into the generator's test; ID's own test then checks that its definition's names are exactly the 15 of `findings.md`.
