# B2: the docs table, the pipeline's secret list, the ring in the deploy steps

**Goal.** The configuration tables in the docs render from `packages/config/inventory.json`; the pipeline's knowledge of which secrets the deploy delivers is checked against the same file; both deploy workflows hand `BETTER_AUTH_SECRETS` to the deploy step so the ring rotation the runbook describes can run.

**Read first.** `docs/goals/typed-config/task_plan.md` (D4, D5), `findings.md` (F2, F3), `briefs/b1.md` (the metadata's shape; B1 must have landed), `AGENTS.md` (the Documentation section: how the docs render from the repository, `asMarkdown()`, the turbo inputs). Rules as in B1: no change to any value in staging, land on `main` after the gates.

## 1. The docs component

In `apps/web/components/docs/generated.tsx`, `<Configuration group="…" />`: reads `packages/config/inventory.json` (add the path to `web#build`'s and `web#test`'s inputs in `turbo.json`), renders one row per variable: name, secret or not, what it defaults to (the fallback, or "required", or "optional"), where it comes from in a deployment (the `source`, in words: "the deploy", "generated in the cluster", "the chart", "the image", "an operator"), and the doc line. A Markdown form through `asMarkdown()`, so the `.md` page carries the same table. A test in `apps/web` that renders each group and that the Markdown form has the same rows.

Pages: `docs/06-deploying-answerable-id.md` is not a docs page (it is a repository document); the docs site's pages that carry a hand-written variable table get the component instead. Check these eight, which name variables today, and replace a table where there is one, leave prose alone: `apps/web/content/docs/admin/setup.mdx`, `admin/index.mdx`, `mcp/servers.mdx`, `mcp/claude-code.mdx`, `toolbox/index.mdx`, `mcp/reference.mdx` (generated: leave it), `mcp/quickstart.mdx`, `mcp/local-testing.mdx`. In `docs/06`, replace the Configuration table's rows with a sentence pointing at the ID group of the inventory and keep the paragraph on the fixed constants; the link check must stay green.

## 2. The pipeline

`infra/pipeline/src/deploy.ts` keeps `ID_ENV_REQUIRED`, the pairs and `ID_ENV_OPTIONAL` as the deploy's own contract. Add a test in `infra/pipeline` that the set of ID fields whose `source` is `deploy` in `packages/config/inventory.json` equals the set the three lists name, so a new deploy-delivered secret, or one removed, fails here until the lists and the workflows follow.

## 3. The workflows

`.github/workflows/deploy-staging.yml` and `promote-production.yml`, the Deploy step's `env`: add `BETTER_AUTH_SECRETS: ${{ secrets.BETTER_AUTH_SECRETS }}` (empty when the environment has no such secret, which `idEnv()` already treats as unset). `infra/README.md`'s Rotate table row for `BETTER_AUTH_SECRET` then describes something the pipeline can do; reread it and `apps/id/README.md`'s application secret rotation to make sure the steps are the ones a person would follow: set the ring in the environment, push a tag, two ships apart. `docs/12-deployment.md`'s secrets table: add the ring as optional.
