# Findings: the Answerable admin MCP

Every fact the plan rests on, with how it was verified. The design built on them is [`docs/11-admin-mcp.md`](../../11-admin-mcp.md). "Verified" means read in the installed source at the line given, or observed by a probe whose command and output are recorded below. "Assumed" means a brief must prove it before building on it. Worktree `.claude/worktrees/admin-mcp` at a2b72cc; probes ran on 2026-10-01.

## Verified

### Answerable ID: who may call the admin API

- **F1. The admin API refuses a person's token.** `apps/id/src/http/principal.ts:285-289`: a bearer whose claims carry `sid` answers 401 `invalid_token` "User-delegated tokens are not admin credentials."; a bearer must be a `client_credentials` JWT for the admin resource (`verifyBearer`, audience `ADMIN_RESOURCE_IDENTIFIER`, `principal.ts:70-104`). Probe 1: the person's MCP access token at `GET /api/admin/v1/me` answered 401 `invalid_token`. Every user access token carries `sid` (F2). So a standalone admin MCP acts on ID only through its own machine client, as the Toolbox does.
- **F2. What a user access token carries.** Probe 1 (decoded with `jose`): `aud, authorization_version, azp, client_id, client_instance, exp, grant_id, iat, iss, jti, membership_id, organization_authorization_version, organization_id, resource_instance, scope, sid, sub, subject_type, upstream_auth_time`. No `auth_time`. `upstream_auth_time` is seconds, or null (`apps/id/src/auth/user-token-boundary.ts:60-80`, `identity()`); it is a snapshot taken when the grant was made (`grant-authentication.ts:30-40` `grantAuthenticationSnapshot`), and a refresh keeps the same `grant_id`, `sid` and `upstream_auth_time` (probe 1 `refreshed`: identical values after a forced refresh). `@answerable/auth`'s `UserPrincipal` exposes neither `sid` nor `upstreamAuthTime` (`packages/auth/src/index.ts:605-623`; the zod `shared` schema at 650-663 drops unknown claims).
- **F3. A machine client knows the platform organisation without a slug.** Probe 1: `GET /me` with a `client_credentials` token answers `{ principal: { type: "client", clientId, organizationId }, grants: [{ organizationId, organizationSlug: "answerable", isPlatform: true, scopes: [...] }] }`. `isPlatform` is `exists(select 1 from system_bindings where organization_id = …)` (`apps/id/src/db/queries/grants.ts:99`), never the slug. Machine token claims: `aud, authorization_version, azp, client_id, client_instance, exp, iat, iss, jti, organization_authorization_version, organization_id, scope, sub, subject_type`.
- **F4. ID's freshness rule does not reach machine clients.** `apps/id/src/http/admin/command.ts:89-96`: `if (needsFreshness && principal.type === "user") checkFreshness = freshAuthenticationGuard(...)`; `freshAuthenticationSeconds = 300` (`apps/id/src/auth/fresh-authentication.ts:6`). 49 of the 81 admin operations are writes and all but `updateOrganization` carry `x-fresh-authentication: true` (or `unlessOnly` display fields), by jq over `apps/id/openapi.admin.json` (command below). Through its machine client the admin MCP bypasses this; the person's freshness must be the admin MCP's own rule if wanted (F2 gives `upstream_auth_time`).

### Answerable ID: authority data for roles

- **F5. A group entitlement on a resource is visible in the member access view, live.** Probe 1: `POST /organizations/{org}/groups`, `PUT …/groups/{g}/members/{m}` with `If-None-Match: *` (201, ETag `"<id>:1"`), `POST …/entitlements { groupId, resource, scopes: ["admin/organisations.create", "answerable-owner"] }` (201), then `GET …/members/{m}/access` returned a target `{ kind: "resource", id: "<resource>", scopes: ["admin/organisations.create", "answerable-owner"], via: [{ principal: "group", groupId }] }`. `permission.allowed` is false with reason `capability` for a bare resource target: the Toolbox reads `scopes`, not `permission` (`mcps/toolbox/src/grants.ts:45-49`), and so will the admin MCP. After `DELETE …/groups/{g}/members/{m}` (204) the target was gone on the next read. Member access view latency, 10 reads through root: median 32.4 ms, min 28.0 ms, max 48.9 ms (the Toolbox journeys measured 32–35 ms medians).
- **F6. Grant-string characters.** ID accepts any non-empty string in a resource's `allowedScopes` (`PATCH /resources/{r}` with `If-Match`) and therefore in entitlement scopes: probe 1 tried `admin/organisations.create`, `answerable-owner`, `admin:owner`, `Admin_Owner`, `with space` and a 300-character string: all 200. Schema: `allowedScopes: array<string minLength 1>` (openapi `createResource`); the entitlement check is membership in `allowedScopes` (`apps/id/src/services/entitlements.ts:273-285`). The admin MCP must define and check its own grant-string grammar; ID will not.
- **F7. A member exists only after a first sign-in; there is no invitation route.** The admin OpenAPI has no member-create or invitation operation (jq listing: members have GET list/get/configuration/access, PATCH window, DELETE remove, POST reinstate). An `invitations` table exists in the schema (`apps/id/src/db/schema/auth.ts:240`) with no route. Probe 2: a new organisation's member row appeared (status `active`, membership `active`) after a sign-in whose OAuth authorisation ID then refused for lack of a capability. So "invite a person before their first sign-in" is Not yet; the workaround is granting the organisation or a group and setting group membership once the person has signed in.
- **F8. Only platform-organisation members hold platform authority at ID, and the slug confers nothing.** `effectiveGrants` evaluates membership rows and marks `isPlatform` from `system_bindings` (F3); `authorize()` in `apps/id/src/http/authorize.ts:69-99` grants the platform tier only to a grant with `isPlatform`.

### Answerable ID: writes, correlation, idempotency, versions

- **F9. ID honours `x-request-id` and stores it on audit events.** `apps/id/src/app.ts:25,44-55`: an incoming `x-request-id` matching `^[A-Za-z0-9._:-]{1,128}$` becomes the request's id and is echoed; `services/actor.ts:33-40` puts it on the actor; `db/queries/audit.ts:66` stores it; `GET /audit-events` items carry `requestId` and `operationId` (`http/admin/audit-events.ts:36-80`) and the route filters by `operationId, actorId, action, outcome, targetType, targetId, from, to, organizationId`. Probe 1: `PATCH /organizations/{org}` with `x-request-id: probe-<uuid>` gave an `organization.updated` event with that `requestId` and the response's `Operation-Id`; `GET /audit-events?operationId=…` returned exactly it. A write through a machine client is recorded with `actorType: "client", actorId: "<client id>"` and the same request id (probe 1 `machineWriteAudit`). So an execution id sent as `x-request-id` joins the admin MCP's evidence to ID's audit row.
- **F10. Idempotency replay.** `command.ts:76-81`: `Idempotency-Key` (1–256 characters) is required on every write. Probe 1: same key and input → 201 again with `Idempotency-Replayed: true` and the same `Operation-Id`; same key, different input → 409 `idempotency_key_reused`. So "Idempotency-Key = intent id" makes a lost commit answer safe to retry (R25).
- **F11. Revisions and preconditions.** ETags are `"<id>:<revision>"` (`http/admin/revision.ts:5-6`). Probe 1: `PATCH /organizations/{org}` with the current ETag → 200 and a new ETag; the same, now stale, ETag again → 412 `revision_mismatch` ("Organisation changed; read its current revision before issuing a new command"); an unchanged PATCH keeps the revision. `POST …/disable` and `…/enable` advance the organisation's revision (3 → 4 → 5) and its `authorizationVersion` (1 → 2, staying 2 after enable). Reads that return an ETag: organisation, SSO provider, group, group member, entitlement, capability, client, resource, member configuration; writes that take `If-Match`: PATCH organisation, capability, entitlement, group, member, resource, client; PUT group member and PUT SSO provider (both also `If-None-Match: *`). Creates, disable/enable, deletes and `removeGroupMember` take no precondition.
- **F12. The admin API surface** (`apps/id/openapi.admin.json`): 81 operations, 32 reads and 49 writes; every one carries `x-tier`, `x-kind`, `x-scopes`, `x-fresh-authentication`. Writes need `platform:write`, except member window/remove/reinstate and user disable/enable/retire-email/sessions (`platform:users`). Bodies the admin MCP will send: `createOrganization { slug ^[a-z0-9]+(-[a-z0-9]+)*$, name 1–200, logo?, metadata? }`; `createOrganizationDomain { domain }`; `putSsoProvider { issuer, domain, oidc?: { credentials: "platform" | "own", clientId?, clientSecret?, endpoints?, scopes? } }` (the GET redacts the secret and reports `hasClientSecret`, `pkce`); `createGroup { slug, name, externalId? }`; `putGroupMember { validFrom?, validUntil? }`; `createEntitlement { memberId? | groupId?, clientId?, resource?, scopes[] }`; `updateOrganization { name?, logo?, metadata? }`. List filters: organisations `q, status`; members `email, q, effective`; users `email, q, status, organizationId`.
- **F13. Platform applications.** Omitting `oidc` or sending `credentials: "platform"` signs the organisation in through Answerable's Google or Microsoft application when the issuer is `https://accounts.google.com` or `https://login.microsoftonline.com/<tenant>/v2.0` (`services/federation.ts:36-46` `classifyIssuer`; `http/admin/sso-providers.ts:286-296`); a generic issuer needs own credentials (`platform_credentials_unsupported`); a missing application answers `platform_application_missing`. The SSO connectivity test (`GET …/sso-provider/test`) refuses loopback HTTP issuers: probe 2 answered 200 with `problems: [{ code: "insecure_issuer" }]`, `reachable: false`.
- **F14. Disabling an organisation stops refresh.** Probe 2 and J2: after `POST …/disable`, a refresh answers 400 `invalid_grant`; an access token already issued keeps working until it expires (docs/07 "Offline verification").

## Assumed (prove in the brief named)

- **A1 (B1).** One machine client linked to two resources (ID's admin resource and the Toolbox's `/admin` resource) can get a `client_credentials` token for each audience. Better Auth keeps links in `oauth_client_resources` (memory note `better-auth-172-admin-gotchas`); nothing forbids two rows, but no probe did it. Fallback: a second machine client for the Toolbox.
- **A2 (B2).** The Toolbox's admin API accepts the admin MCP's machine token exactly as it accepts the staff client's (`toolbox:admin`, audience `<toolbox>/admin`): the same code path as the Toolbox journey's `toolboxAdminCall`.
- **A3 (B3).** One access-view read per MCP request (shared across that request's `allow` calls through a `WeakMap` on the principal, as `mcps/toolbox/src/toolbox.ts:40-51` does) costs about one ID round trip, 30–50 ms. Measure in the journey.
- **A4 (B2).** The ETags of `GET …/sso-provider`, `…/groups/{g}/members/{m}` and `…/entitlements/{e}` work as `If-Match` on their PUT/PATCH exactly as the organisation's does (same `requireRevision`, `revision.ts:8-23`; only the organisation was probed).
- **A5 (B3).** Claude Code 2.1.282 prompts before `admin_commit_confirmed` under an allow rule because of `anthropic/requiresUserInteraction` (read from its source for the Toolbox; "Not yet tested in a session", `claude-code.mdx` Limits). The hand demo relies on it; the admin lane records what happens.
- **A6 (B0).** Moving `0002_evidence.sql` and `0004_intents.sql` into a shared package keeps their file names, so the Toolbox's development and test databases, whose `schema_migrations` already list them, are not migrated twice.
