3. **Targets and versions (D7)**: prepare reads each target and binds `version: { kind: "etag", value: <ID's ETag> }`; the SDK re-runs `prepare` at commit and answers `INTENT_STALE` when a target moved (F20); the write then sends `If-Match` with the bound ETag on every operation where ID accepts it (check each in `apps/id/openapi.admin.json` and `apps/id/src/http/admin/*`: organisation PATCH was probed (F11); SSO provider PUT, group member PUT, entitlement PATCH are A4: prove with the fake ID that mirrors the real route's behaviour, and record what the real route does from its source). Creates take `If-None-Match: *` where ID accepts it (SSO provider PUT with no current provider).
4. **Idempotency and correlation (D6)**: the SDK hands `commit` the stored plan and the call's context, not the intent id. So each mutation's `prepare` mints one key (`Bun.randomUUIDv7()`) and returns it in its `plan` data; `commit` sends it as `Idempotency-Key` (`<key>.<step>` when one commit makes several writes) and `x-request-id: <context.executionId>` on every ID call; the receipt's `results` carry ID's `Operation-Id`(s) (`manage` returns `operationId`). Confirm in `commit.ts` that the stored plan, not the re-prepared one, reaches `commit`, and write a test that proves the key is the same across a commit that is resent after a 401.
5. **The Toolbox call (`toolbox.enable`)**: through the Toolbox's platform-tier admin API with a `client_credentials` token for the Toolbox's admin resource (`ADMIN_TOOLBOX_ADMIN_RESOURCE`) and the scope the Toolbox requires (read `admin.ts`; the plan says `toolbox:admin`). Prepare reads the Toolbox's providers (`GET /admin/v1/providers`) to validate the requested providers and host clients.
6. **Freshness for critical tools (D4)**: `prepare` of the four owner tools requires `principal.upstreamAuthTime` within `ADMIN_FRESH_SECONDS` (default 1,800; null counts as stale). Older answers the custom code `ADMIN_REAUTHENTICATION_REQUIRED` (declared on each definition, retry `after_state_change`, `details: { upstream_auth_time, max_age_seconds }`). Because commit re-runs prepare, an intent prepared while fresh cannot be committed once stale. The message names the exact remedy: what a person must do so that the host's next token carries a new `upstream_auth_time`. Determine it from ID's code, not from guesses: a refresh keeps the grant's snapshot (F2, `apps/id/src/auth/grant-authentication.ts`); read how a session's upstream authentication time is set (`/auth/sso/reauthenticate`, `apps/id/src/auth/fresh-authentication.ts`, `verified-sso.ts`, sign-in and `/auth/sign-out`) and how a NEW grant takes its snapshot, then write the shortest true instruction (for example: sign out of Answerable ID at `<issuer>/auth/sign-out` or re-authenticate at …, then in the host clear and redo the server's authentication; in Claude Code `/mcp`, the server, Clear authentication, Authenticate).
