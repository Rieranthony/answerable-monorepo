Answerable Admin MCP

A standalone MCP, for Answerable staff only, that onboards and manages organisations in Answerable ID: create an organisation, route its domain, connect its directory, turn on the Toolbox for it and grant its people access. The plan was written by Fable 5.1 after test runs against real ID. Opus 5.5 and Sonnet 5.5 build it in five steps.

The demo it must make possible

  1. An owner connects Claude Code to the admin MCP and signs in with their Answerable account.
  2. Through the MCP's tools they create an organisation, add its domain, connect its directory, enable the Toolbox for it and grant its people access. Each change is previewed and confirmed before it runs.
  3. A person from that organisation signs in to the Toolbox and uses it. Before the grant, ID turns them away: "Access is unavailable for this organisation."
  4. Anyone who is not staff, or staff without the right role, gets no tools, or no write tools.

Proven twice: automated journeys against a real ID on every run, and a hand lane script that starts ID, the Toolbox and the admin MCP for Claude Code.

owneranswerable-ownerEverything, plus disable or enable an organisation, grant or revoke staff roles, and any change to Answerable's own organisation. These need a sign-in from the last 30 minutes.

Roles are entitlements of three groups in Answerable's own organisation, stored in ID. The MCP reads the person's role from ID on every request, so adding or removing someone takes effect on their next call, with no sign-in again. The MCP keeps no permission table of its own, and nothing is cached: if ID is unreachable, nothing is served.

Every write is prepared first: the MCP shows a preview (what changes, the effects, the warnings), the host asks the person to confirm, and only then does the change run, once. If the target changed in between, the commit is refused and has to be prepared again.

How it stays safe

Who acts on ID

ID's admin API does not accept a person's token, so the MCP calls ID with its own machine credential. It does so only after the person's role allowed the tool. This is the same model the Toolbox uses.

Who did what

ID's audit log names the MCP's machine client. The MCP records the person in its own append-only, hash-chained evidence. Both sides share the request id and ID's operation id, so a change can be traced from either side.

Retries are safe

Each write is sent to ID with the intent id as its idempotency key. A lost answer can be retried without applying the change twice.

Fresh sign-in for critical changes

ID asks people for a sign-in from the last 5 minutes before sensitive changes, but not machines. The MCP adds its own rule: critical tools need a sign-in from the last 30 minutes. Refreshing a token does not count as a new sign-in. To sign in again: ID's security page, Verify sign-in, then re-authenticate the server in the host.

Decisions taken (the owner can overrule any of them)

  • Hand-written and standalone. About 24 curated tools in mcps/admin. The plan's earlier idea, an admin MCP generated from ID's API spec inside the Toolbox, would have exposed 81 raw operations and had no role model.
  • Roles live in ID as group entitlements and are read live on every request, with no cache.
  • Every write is "controlled". The host confirms each one with the server's own summary. The human-approval class has no approval page yet, so it is Not yet.
  • Own database. answerable_admin holds the prepared changes and the evidence, using code extracted from the Toolbox into shared packages rather than copied.
  • Not yet: inviting a person before their first sign-in (ID has no route for it), SSO with an organisation's own credentials (that needs a secret), erasing anything, and the admin MCP for an organisation's own administrators.
