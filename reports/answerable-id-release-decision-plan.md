### Contracts to settle first

1. **Tenant authentication:** proposed first-release rule: the selected tenant must accept the session’s authentication origin and current provider revision; initially require that tenant’s own SSO. Tenant selection and membership alone confer no authentication trust. Explicit cross-tenant trust is a later policy extension unless required now. This remains a product proposal, not an approved or implemented rule.
2. **Historical identity:** UUID attribution is mandatory. Stephen’s named-person requirement needs a separate decision: retain only UUIDs, or provide restricted encrypted identity recovery with defined fields, readers and retention. Do not scatter names/email across permanent audit events. Include encrypted operation results and backups in the retention decision. Real erasure must wait for this decision.
3. **Revocation:** publish separate promises for denying new grants, online token checks, offline JWT expiry and downstream sessions. Set exact lifetimes against the first consumer and verify them. Database deletion alone cannot certify downstream logout.

The first two choices affect dependent implementation; isolation inventories, retry proofs and documentation consolidation can proceed independently. Do not invent approval or a retention duration.

### Idempotency: the public promise

A committed local command, its successful audit effects and its receipt share one PostgreSQL transaction. A lost response is recovered by replaying the same key and input under current authority. A new key expresses a new operation; it is not a way to retrieve the previous result. This provides a precisely scoped local guarantee, not universal exactly-once network delivery.

Keep distinct machine-readable results for in-progress work, mismatched input, stale revision, permanent conflict, expired result and temporary recovery failure. A bare `409` cannot tell an agent what to do. Document a decision table and copy-pasteable retry/recovery examples beside the generated API contract. Existing implementation: [operation execution](/Users/anthonyriera/code/answerable/apps/id/src/services/operations.ts:40).

A future remote side effect requires a durable effect ID and reconciliation; introduce an outbox or resumable workflow when that effect actually exists. A monetary effect requires a unique business key in its owning ledger transaction. No billing or workflow engine is needed to complete today's local ID mutations.

### Native scope contract for the next integration

The pinned provider does not automatically separate identity scopes from resource scopes in its access JWT. With the existing fixture's resource allowance of `openid offline_access proof:read`, code exchange and refresh return all three in the response and JWT; persisted refresh rows also retain all three. The existing evaluator test approves only `proof:read` in `decision.scopes`, after separately checking the requested identity scopes against login permission. See the [native flow assertions](/Users/anthonyriera/code/answerable/apps/id/src/auth/user-grant-boundary.integration.test.ts:558) and [evaluator](/Users/anthonyriera/code/answerable/apps/id/src/auth/member-permission.ts:332).

Consequently, the production issuance check must compare like sets: validate resource scopes against the resource decision and identity scopes against the approved login request, then check the complete issued set without accepting extras. Do not compare the complete JWT scope string directly with resource-only `decision.scopes`. These proofs establish the existing fixture's contract, not production user OAuth readiness.

Two additional native-flow regressions establish the integration constraints:

- **Filtering before the claims hook:** after authorisation, changing the resource allowance to `proof:read` makes code exchange return only that scope and no ID token. It still returns a refresh token: the native issuance condition uses the original request's `offline_access`, whereas the new refresh row stores only the filtered scopes. A successful claims hook alone therefore does not prove that original login scopes remain approved or that the response has the originally expected token kinds.
- **Narrowed renewal:** explicitly refreshing with only `proof:read` returns that scope and no ID token. Asking that new refresh token to regain the original identity scopes returns `invalid_scope` and leaves refresh rows unchanged. Retrying with no scope succeeds using the narrowed set. The next response contains no replacement refresh token, because the consumed row no longer includes `offline_access`.

For production integration, retain the original authorised scope set, each refresh token's current ceiling and the current evaluated request as distinct existing facts. Check original code-request policy before native filtering; check renewal against both its token ceiling and current policy. Define and document token-kind behaviour when `openid` or `offline_access` is removed. Keep the native narrowing rejection; do not add a second refresh ceiling or infer permission from the original grant alone. Test the actual production response and persistence together, including recovery after refusal. This work belongs in the production provider boundary, not a standalone unused audit helper.

The adjacent entitlement review found no equivalent to the corrected link-history leak: [migration 0026](/Users/anthonyriera/code/answerable/apps/id/drizzle/0026_resource_ownership.sql) rejects foreign-private entitlement targets and makes resource ownership/classification immutable. Existing [raw-write regressions](/Users/anthonyriera/code/answerable/apps/id/src/db/identity.integration.test.ts:441) cover the guard. Do not add a duplicate entitlement filter without a reproducing counterexample; this is a source finding, not a claim of complete query isolation.

**One global identity; tenant-local authority.** Keep `sub` stable. Membership identifies the user’s relationship with one organisation. Every user grant binds one tenant, membership, client instance, resource where applicable, authentication origin and original scope limit. A browser’s selected tenant cannot rewrite an existing grant. Tenant A removal must preserve tenant B membership, grants and ordinary global browser access; global disable/erasure remains a distinct platform operation.

**Shared PostgreSQL with explicit boundaries.** Reuse tenant/platform service contexts, tenant predicates, constraints and the restricted runtime role. Finish context adoption at query entry points. Apply RLS deliberately to owned policy data; document narrow global/provider broker access instead of pretending every table is tenant-local. An application-set database scope is defence against missing filters, not a separate credential boundary against compromise of the entire runtime. Test actual non-owner connections and pooled reuse. Evidence: [scope handling](/Users/anthonyriera/code/answerable/apps/id/src/db/isolation.ts), [runtime privileges](/Users/anthonyriera/code/answerable/apps/id/src/db/runtime-role.ts), [isolation inventory](/Users/anthonyriera/code/answerable/reports/answerable-id-isolation-inventory.md).

**Three explicit permission shapes.** App login; exact app–resource pair; reserved direct ID administration. Platform-managed tenant capabilities set the maximum. Tenant assignments select subsets. Registration and client–resource compatibility grant no user permission. Shared resources are available for assignment, never automatically authorised. No arbitrary permission graph or policy language is needed for Stephen’s example.

**Separate authentication from authorisation.** A user resource request needs both authentic protocol evidence and current policy permission. Effective resource scopes are the requested subset of client, resource, tenant capability and matching assignment ceilings. Renewal is additionally bounded by the original grant and current renewal capability. Union assignments only within the same tenant and exact target. Reject explicit scope overreach. Preserve distinct machine ownership rules and direct administration semantics.

**One local command transaction.** Commit mutation, successful audit facts and recoverable operation receipt together. `Idempotency-Key` identifies a logical command; request IDs identify attempts. Re-authorise every replay. A retained key cannot cause a second effect even after its response expires. Revisions address concurrent edits; they do not replace idempotency. OAuth code/refresh replay keeps its protocol-specific handling rather than generic administrative response replay.

### Retry and interruption contract

The current [operation implementation](/Users/anthonyriera/code/answerable/apps/id/src/services/operations.ts) already distinguishes these cases. Preserve them through every route and document the machine-readable error code; HTTP 409 alone is insufficient.

| Situation                                                        | Required client-visible outcome                                                                                                       |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Same actor, authority scope, command, key and input after commit | Re-authorise; return the original recoverable result without repeating the mutation.                                                  |
| Same logical command is running                                  | `409 operation_in_progress`, retryable with the same key and input.                                                                   |
| Retained key reused for different input while recoverable        | `409 idempotency_key_reused`, not retryable as submitted.                                                                             |
| Response recovery expired                                        | `410 operation_result_expired`; retained reservation prevents rerunning the command. Expiry is checked before fingerprint comparison. |
| Recovery key unavailable                                         | `503 operation_replay_unavailable`; restore recovery capability rather than repeating the mutation.                                   |
| Different key requests an already reached state                  | Define per-command truthful no-op or domain conflict; never infer ownership from matching names.                                      |
| Process dies before local commit                                 | No partial mutation, successful audit or receipt; retry can execute.                                                                  |
| Process dies after commit but before response                    | Recover the committed receipt; no second rotation, creation or removal.                                                               |
