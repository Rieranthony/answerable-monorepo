# Host lane (brief B9)

A section for [`mcp-foundation-evidence.md`](mcp-foundation-evidence.md), drafted by the B9 agent on 29 September 2026. Tree: branch `goal/b9` on commit 833809d. Neither host is a gate; every number below was measured on this machine (macOS on arm64, Docker Desktop 28.3.2, one-minute load average about 10 to 19).

**Result.** J8: LibreChat v0.8.8-rc4 signed a person in through ID with `resource`, listed the seven tools the partial entitlement allows and, through a scripted model, ran a read, an agent-class mutation and a controlled one on the text mirror; it refreshes after the 60-second token only when its `oauth.scope` includes `offline_access`, which it does not ask for by default. J9: Claude Code 2.1.282 discovered the Toolbox from its `401`, signed in headlessly with `claude mcp login`, and connected with a token from the same client; the tool list with the partial entitlement and `requiresUserInteraction` on the confirmed commit alone were read with the kit's client. The prompt under an allow rule needs a model session and is left to the owner. Kept in the repository: `packages/acceptance/scripts/host-lane.ts`, `packages/acceptance/host-lane/compose.yaml` and `librechat.yaml`, described under "Host lane" in `local-testing.mdx`. Not kept: the scripted model and the browser drivers.

Versions: Bun 1.3.1; Playwright 1.63.0 Chromium; `@answerable/acceptance` 0.2.0; `@answerable/mcp-toolbox` 0.3.0; Claude Code 2.1.282; LibreChat v0.8.8-rc4 (its `package.json`, on Node v24.16.0), image `ghcr.io/danny-avila/librechat:v0.8.8-rc4@sha256:929f4491cb9a87d6beb02e9e9ce9a54d4ee05bc56b65b1debe5b1f28a327a4fb` (a multi-architecture index; the arm64 image ran natively), MongoDB 8.0.20.

## The stack

`bun packages/acceptance/scripts/host-lane.ts` starts real ID through the kit and serves the Toolbox in process on port 47604 with the e2e provider, as the Toolbox journey's `beforeAll` does. One tenant, `host-lane`, with 12 queued company sign-ins; the Toolbox resource with 60-second tokens; two public host clients, `librechat-lane` (redirect `http://localhost:3080/api/mcp/toolbox/oauth/callback`) and `claude-code-lane` (redirect `http://localhost:47700/callback`), enabled for the organisation through the Toolbox's admin API (16 rows made in ID and the catalogue for the two clients and the `e2e` provider); one entitlement to `e2e/records` only. It logs one line per request the Toolbox answers (method, path, JSON-RPC method, status, protocol version, user agent) and one line per OAuth event ID records. `--check` signs in once as `claude-code-lane` with the kit's browser, lists the tools and exits; two runs took 10.2 and 6.8 seconds and left nothing behind.

`packages/acceptance/host-lane/compose.yaml` runs LibreChat, MongoDB and a `bridge` service in the Compose project `answerable-host-lane`, with `librechat.yaml` beside it.

**What the container needed.** The fixture fixes ID's origin, and so the token's `iss`, at `http://127.0.0.1:47600`, and the Toolbox's resource is `http://127.0.0.1:47604/mcp`; `127.0.0.1` inside the container is the container. The `bridge` service shares the LibreChat container's network and forwards those two loopback ports to `host.docker.internal` (a 9-line `node` script run from the LibreChat image, so nothing else is pulled). LibreChat also blocks private addresses for MCP servers unless `mcpSettings.allowedAddresses` lists them: `127.0.0.1:47600` and `127.0.0.1:47604`, which covers the discovery, authorisation, token and MCP requests. Not measured: what LibreChat does without either.

**Pull and size.** `docker compose pull` took 5 minutes 8 seconds; the images take 2.6 GB (LibreChat) and 940 MB (MongoDB) on disk. The two registries LibreChat's Docker guide names have no such tag: `registry.librechat.ai/librechat-ai/librechat:v0.8.8-rc4` and `ghcr.io/librechat-ai/librechat:v0.8.8-rc4` answer `manifest unknown`; `ghcr.io/danny-avila/librechat:v0.8.8-rc4` exists, and `registry.librechat.ai/librechat-ai/librechat:v0.8.7` (the last stable) exists too. v0.8.8-rc4 is what the research and OmniChat track; v0.8.7 was not run.

## J8: LibreChat

**Sign-in.** Through the browser with a throwaway local account (registration form, then the login form): the MCP settings panel showed `toolbox` as "Needs Auth"; Connect opened a dialog with the authorisation URL, and "Continue with OAuth" opened it in a new tab. LibreChat found OAuth from `HEAD /mcp` (`401` with `resource_metadata`) and the metadata, then built this request (from `POST /api/mcp/toolbox/reinitialize`, and the browser's request to ID):

```text
http://127.0.0.1:47600/auth/oauth2/authorize?response_type=code&client_id=librechat-lane&code_challenge=…&code_challenge_method=S256&redirect_uri=http%3A%2F%2Flocalhost%3A3080%2Fapi%2Fmcp%2Ftoolbox%2Foauth%2Fcallback&scope=toolbox&state=…&resource=http%3A%2F%2F127.0.0.1%3A47604%2Fmcp
```

So `resource` was sent, with PKCE S256, and no client secret. ID's pages were the same as for every host: email (`tester@host-lane.example.test`), organisation, consent (the service `http://127.0.0.1:47604/mcp`, the access `toolbox`), Accept. The callback carried `code`, `state` and `iss=http://127.0.0.1:47600`, LibreChat's page said "Authentication Successful … Connected to: toolbox", and the panel changed to "toolbox - Connected". ID's audit log recorded `oauth.user.authorized` and `oauth.user.issued` (`grantType: authorization_code`) for `librechat-lane`, and on the refresh events I read, `decision.resource.identifier` is `http://127.0.0.1:47604/mcp`. From Connect to the success page took 1.8 seconds by the driver's clock.

**Tools.** After connecting, LibreChat sent `initialize`, `notifications/initialized`, `GET /mcp` (answered `405`, the 2025 revision has no stream), `ping` and `tools/list` twice, all at protocol `2025-11-25`, and listed seven tools, in the Toolbox's order. `GET /api/mcp/tools` and the model request LibreChat built agree:

| Toolbox tool | LibreChat's model-facing key |
| --- | --- |
| `toolbox_whoami` | `whoami_mcp_toolbox` |
| `e2e_records_create` | `e2e_records_create_mcp_toolbox` |
| `e2e_records_delete` | `e2e_records_delete_mcp_toolbox` |
| `e2e_records_list` | `e2e_records_list_mcp_toolbox` |
| `e2e_records_show` | `e2e_records_show_mcp_toolbox` |
| `toolbox_commit` | `commit_mcp_toolbox` |
| `toolbox_commit_confirmed` | `commit_confirmed_mcp_toolbox` |

The partial entitlement showed: no `e2e_identity_get`. LibreChat removes a leading `<server>_` from a tool name (`stripServerNamePrefixes` in `packages/data-provider/src/config.ts`), so with the server named `toolbox` the three `toolbox_` tools lose their prefix; the intents' `commit_tool: "toolbox_commit_confirmed"` and the error messages then name a tool that is listed under another key.

**Calls, through a scripted model.** No model is needed to list tools, but LibreChat calls a tool only for a model, so a scripted OpenAI-compatible endpoint on the host (about 40 lines, run for this test only and not kept) answered a user message `call NAME {json}` with that tool call, and logged the tool names it was offered and the exact tool result LibreChat gave it back. In one conversation of eight messages:

- **Read.** `e2e_records_list` reached the Toolbox as `tools/call e2e_records_list` (`200`). The model was given the text mirror, compact JSON: `{"items":[],"next_cursor":null,"has_more":false}`. LibreChat's card ("Ran e2e_records_list in toolbox") shows the same text pretty-printed when expanded; it shows no other form of the result, because LibreChat ignores `structuredContent`.
- **Agent-class mutation.** `e2e_records_create` returned an intent with `policy_class: "agent"` and `commit_tool: "toolbox_commit"`; `commit_mcp_toolbox` with its `intent_id` and `commit_token` returned the receipt, `status: "committed"`, `committed_by.client_id: "librechat-lane"`; the next list held the record.
- **Controlled class.** `e2e_records_delete` returned `policy_class: "controlled"`. The wrong tool, `commit`, gave the model an error result as text: `{"error":{"code":"APPROVAL_REQUIRED","message":"Intent … is controlled class: show the person its preview, then commit it with toolbox_commit_confirmed and its summary as preview_summary","retry":{"policy":"after_approval"},…}}`. `commit_confirmed` with the summary committed the delete, and the list was empty. LibreChat showed no confirmation to the person before running it: it does not read `anthropic/requiresUserInteraction`, so with LibreChat the controlled class is the model's obedience alone.
- `whoami` returned `client_id: "librechat-lane"`, `grants: ["e2e/records"]` and the four capabilities.

**Refresh.** With the default request (`scope=toolbox`, the metadata's scopes) ID issued no refresh token: MongoDB held `mcp:toolbox` (access token, created 20:20:48, expiring 20:21:47) and `mcp:toolbox:client`, and no `mcp:toolbox:refresh`; ID's audit log recorded `scopes: ["toolbox"]`. After the 60 seconds, a reconnect answered `POST /mcp initialize -> 401` and LibreChat returned `oauthRequired: true` with a fresh authorisation URL: the person signs in again every minute. With `oauth.scope: toolbox offline_access` in `librechat.yaml` (the checked-in file), the request carried `scope=toolbox+offline_access&prompt=consent`, the consent page added "Stay connected after you leave", ID issued `offline_access toolbox`, MongoDB held `mcp:toolbox:refresh` (expiring a year on), and each first use after 60 seconds went `ping -> 401`, then LibreChat logged "Attempting to refresh token … Successfully refreshed and stored OAuth tokens", ID recorded `oauth.user.issued` with `grantType: refresh_token` and `resource.identifier` `http://127.0.0.1:47604/mcp`, and the call went on with the new token (`tools/call … -> 200`). Four refresh grants in the session; the tool list LibreChat re-read after each was the same seven tools. Without a model: on the checked-in files, in a fresh container, 65 seconds after connecting, `POST /api/mcp/toolbox/reinitialize` (what the panel's Reconnect button calls) answered `oauthRequired: false`, and ID recorded one `refresh_token` grant for `librechat-lane` and the resource; the same run's authorisation request carried `scope=toolbox+offline_access&prompt=consent` and `resource=http://127.0.0.1:47604/mcp`, from registering the account to reading the seven tools took 13.3 seconds, 6 of them a fixed wait.

**What did not work first.** LibreChat limits logins to 7 in 5 minutes and answered a scripted eighth with `429 {"message":"Too many login attempts, please try again after 5 minutes."}`. Playwright's request context throws `"/api/auth/login" cannot be parsed as a URL` under Bun 1.3.1 on any response with `Set-Cookie`, so the driver used `fetch` for API calls. With one tool-call id reused for every scripted call, LibreChat did not run the second call (no `tools/call` reached the Toolbox); unique ids fixed it, so that was the scripted model's fault. The Toolbox's prepare descriptions still say to commit "with e2e_commit" and "e2e_commit_confirmed", the e2e provider's own commit tools; through the Toolbox the tools are `toolbox_commit` and `toolbox_commit_confirmed`, and the intent's `commit_tool` says which.

**What the owner runs by hand.** With the stack up (`bun packages/acceptance/scripts/host-lane.ts`), `docker compose -p answerable-host-lane -f packages/acceptance/host-lane/compose.yaml up -d`; open `http://localhost:3080`, register an account, open **MCP Settings**, choose **Connect** on `toolbox`, **Continue with OAuth**, and at ID type `tester@host-lane.example.test`. **Reconnect** after a minute makes LibreChat refresh: ID's OAuth events in the stack's log then show a `refresh_token` grant. To call tools, add a model endpoint with a key to `librechat.yaml` (none is in the checked-in file), then choose `toolbox` in the chat's **MCP Servers** menu. `docker compose … down --volumes` removes everything.

## J9: Claude Code

**Registered in ID.** Read back from ID's admin API: `claude-code-lane` has `tokenEndpointAuthMethod` `none`, the grants `authorization_code` and `refresh_token`, the redirect `http://localhost:47700/callback`, the scopes `offline_access openid toolbox`, and is linked to `http://127.0.0.1:47604/mcp`, a resource with 60-second tokens whose allowed scopes are `offline_access`, `toolbox`, `toolbox/approve` and the grant strings of `e2e`. The enable call made the client's login and `toolbox` capabilities and entitlements for the organisation, and the organisation holds one entitlement to the Toolbox resource whose scope is `e2e/records`.

**Discovery, as Claude Code does it.** `claude mcp add --transport http toolbox-lane http://127.0.0.1:47604/mcp --client-id claude-code-lane --callback-port 47700` under `CLAUDE_CONFIG_DIR` (and `HOME`) set to a temporary directory: accepted, stored as `oauth: { clientId, callbackPort: 47700 }`. `claude mcp get` and `claude mcp list` answered `! Needs authentication`. The Toolbox saw `POST /mcp server/discover -> 401` (protocol `2026-07-28`, user agent `claude-code/2.1.282 (sdk-cli)`), then `GET /.well-known/oauth-protected-resource/mcp -> 200`. The challenge, by `curl`: `HEAD`, `GET` and `POST /mcp` all answer `401` with `WWW-Authenticate: Bearer error="invalid_token", error_description="Missing Authorization header", resource_metadata="http://127.0.0.1:47604/.well-known/oauth-protected-resource/mcp"`; the metadata is `{"resource":"http://127.0.0.1:47604/mcp","authorization_servers":["http://127.0.0.1:47600"],"scopes_supported":["toolbox"],…}`; ID's metadata has no `registration_endpoint`.

**Signing in without a person.** `claude mcp login toolbox-lane` refuses without a terminal (`stdin isn't a terminal, so authentication can't be completed here`). Under a pseudo-terminal with `--no-browser` it printed the authorisation URL, listened on `127.0.0.1:47700` and waited: `client_id=claude-code-lane`, `code_challenge_method=S256`, `redirect_uri=http://localhost:47700/callback`, `scope=toolbox+offline_access`, `prompt=consent`, `resource=http://127.0.0.1:47604/mcp`. The kit's Chromium completed ID's pages (consent listed "Stay connected after you leave" and `toolbox`), the callback reached Claude Code's listener, and it printed `Authenticated with "toolbox-lane". Its tools are now available in Claude Code.` and exited 0. ID recorded `oauth.user.authorized` and `oauth.user.issued` (`authorization_code`, `offline_access toolbox`); Claude Code's own log says `Token expires in: 60` and `Has refresh token: [REDACTED]`. In a temporary `HOME` it could not keep the credential (`saveClientInformation persist resolved unsuccessful`, presumably because the keychain is out of reach; not confirmed), so `claude mcp list` still said `! Needs authentication`. The alternative, the real `HOME` with only `CLAUDE_CONFIG_DIR` changed, writes a keychain item in the owner's login keychain, so it was not tried. The owner's `Claude Code-credentials` item and the list of Claude keychain services were the same before and after.

**Connected, by a token instead.** A token minted for `claude-code-lane` by the kit (the same public client, the kit's sign-in), passed as `--header "Authorization: Bearer …"` to a second registration: `claude mcp list` answered `✔ Connected`, and the Toolbox saw `claude-code/2.1.282` send `server/discover` (`200`), `subscriptions/listen` (`200`) and `tools/list` (`200`), all at `2026-07-28`. `subscriptions/listen` is the call a `2026-07-28` host makes to hear `tools/list_changed`. Both registrations and the temporary directory were removed afterwards.

**The tools, with the partial entitlement**, by `host-lane.ts --check` (the kit's client for `claude-code-lane`, protocol `2026-07-28`): exactly `toolbox_whoami`, `e2e_records_create`, `e2e_records_delete`, `e2e_records_list`, `e2e_records_show`, `toolbox_commit`, `toolbox_commit_confirmed`. The token: `iss` `http://127.0.0.1:47600`, `aud` `http://127.0.0.1:47604/mcp`, `client_id` `claude-code-lane`, `scope` `offline_access toolbox`, 60 seconds. `_meta["anthropic/requiresUserInteraction"]` is `true` on `toolbox_commit_confirmed` and on no other tool, and that tool is the only destructive one; `toolbox_commit` is not read-only and not destructive; the reads and the prepare tools are read-only. `toolbox_whoami` returned `grants: ["e2e/records"]`, and calling `e2e_identity_get` failed with `Tool e2e_identity_get not found`.

**Whether Claude Code prompts under an allow rule: read, not observed.** No model session is possible here (a temporary configuration directory has no Anthropic login, and the owner's must not be used). Claude Code 2.1.282's minified source reads `_meta?.["anthropic/requiresUserInteraction"]===!0` for each listed MCP tool, and its permission function, after the deny rules, the tool's own check and the ask rules, and before it looks up an allow rule or applies bypass mode, returns `{behavior:"ask", decisionReason:{type:"other",reason:"requiresUserInteraction"}}` for a tool that requires interaction. The Toolbox sends the boolean `true`.

**What the owner runs by hand.**

1. `bun packages/acceptance/scripts/host-lane.ts`, then `claude mcp add --transport http toolbox-lane http://127.0.0.1:47604/mcp --client-id claude-code-lane --callback-port 47700`.
2. In Claude Code, `/mcp`, choose `toolbox-lane`, **Authenticate**, and at ID type `tester@host-lane.example.test`. `/mcp` should then list seven tools (`mcp__toolbox-lane__toolbox_whoami`, `…e2e_records_create`, `…e2e_records_delete`, `…e2e_records_list`, `…e2e_records_show`, `…toolbox_commit`, `…toolbox_commit_confirmed`) and no `…e2e_identity_get`.
3. Allow every tool of the server: `/permissions`, add the rule `mcp__toolbox-lane`, or put `{ "permissions": { "allow": ["mcp__toolbox-lane"] } }` in the project's `.claude/settings.local.json`.
4. Ask Claude to create a record called "Lane test" and delete it. The create (`e2e_records_create`, then `toolbox_commit`) should run without a prompt; `toolbox_commit_confirmed` should still show a permission prompt. The stack's log shows `tools/call toolbox_commit_confirmed` only after you answer.
5. `claude mcp remove toolbox-lane`; Ctrl-C stops the stack.

## Not measured

- LibreChat v0.8.7; LibreChat without the bridge or `allowedAddresses`; LibreChat's behaviour with a server not named `toolbox` (read in the source: the prefix is removed only for the server's own name).
