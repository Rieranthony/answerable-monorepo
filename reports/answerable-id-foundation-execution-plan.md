## Architecture to commit to

**Identity and tenancy.** A user is global; a membership belongs to exactly one tenant. Machine authority comes from immutable client ownership. User authority comes from a verified user grant and its selected effective membership. Each grant/token has one tenant. A shared browser session or shared application is not a shared tenant permission boundary.

**Permissions.** Preserve three explicit target shapes: application login, exact application–resource pair, and the reserved ID resource for direct administration. Resource-only administration must never authorise arbitrary OAuth clients. Tenant capabilities are platform-managed ceilings; tenant assignments grant subsets beneath them. Registration and compatibility links alone grant no user authority.

**Writes.** One database transaction commits the change, its audit evidence and its operation receipt. Repeated commands recover the original outcome; they cannot generate a second secret or apply a second effect. Optimistic revisions prevent independent administrators overwriting each other. These are separate guarantees and both are required.

**Evidence.** Retain immutable subject identifiers independently of live rows. Record selected previous/new values and actual changed entities. Do not promise named attribution after erasure unless a separately protected identity mapping and retention policy exist. An audit event proves a committed local fact, not HTTP delivery or remote token rejection.

### Minimum capability model

Use one capability row per **organisation + exact target + grant kind**, with an immutable UUID, scope set, active/disabled status, effective window and server-controlled revision. Reuse existing window/revision helpers and null-aware uniqueness. Separate grant kinds prevent a machine scope ceiling accidentally authorising user delegation. No wildcard target and no configurable policy language.

| Target                       | Proposed grant kind      | Rule                                                                                             |
| ---------------------------- | ------------------------ | ------------------------------------------------------------------------------------------------ |
| Client only                  | `authorization_code`     | Application-login admission; its scopes never join a resource token's scopes                     |
| Client + resource            | `authorization_code`     | Exact user resource grant, also requiring client-login admission and matching assignments        |
| Client + resource            | `refresh_token`          | Explicit renewal permission for an existing bound user grant; never creates authority on its own |
| Client + resource            | `client_credentials`     | Machine-only permission; client must belong to this organisation                                 |
| Reserved admin resource only | Internal `admin_session` | Direct session administration; this is an internal policy kind, not an OAuth grant type          |

Resolve login-only refresh against the provider proof: if supported, it needs an explicit client-only renewal capability with the same original-context rules. Do not admit that combination speculatively. Invalid target/kind combinations fail validation and database constraints where expressible. Reserved admin identity and private resource ownership require transactional reference checks; do not use a mutable URL or slug to designate the system resource.

Only current platform write authority can create, change, disable or remove capabilities. Tenant readers may inspect their own ceilings. **Do not reuse the current tenant-write RLS policy for this table:** it permits tenant writes and would violate this boundary. Add a platform-write-only policy with scoped tenant/broker reads, include the table in runtime-role startup checks, and exercise a real non-owner database connection.

Capability commands use the existing command context, journal, revision, canonicalisation and audit machinery. Do not create another command framework. Enforce immutable target/tenant/kind; replacement is explicit. A disabled or absent capability makes dependent assignments ineffective without deleting them. Keep evidence before physical removal; no new generic tombstone system is required.

### One decision contract

Load trusted state inside the existing issuance/command transaction, then evaluate it through one typed policy function. Treat all supplied tenant, client and authentication fields as untrusted until the caller-specific admission path establishes them. An access preview may report configuration eligibility; it cannot claim the person has supplied consent or fresh protocol evidence when they have not.

For a user resource token, the allowed scopes are:

`requested ∩ client ceiling ∩ resource vocabulary ∩ tenant capability ∩ matching pair assignments`

Assignments may be unioned only within that organisation and exact pair, after user, membership, group and window checks. Client-login admission is a separate prerequisite. Machines omit user assignments and use only the machine capability plus authenticated immutable ownership. Reject requests outside the allowed scope set with the protocol's existing error handling; do not silently broaden or silently make default scopes exceed the intersection. When scopes are omitted, derive defaults from the same allowed set and test this separately.

A renewal must retain the original tenant, membership, subject, client instance and resource. Its scopes cannot exceed the original grant, and both current underlying permission and renewal permission must remain effective. Changing the browser's selected organisation supplies no renewal authority.

Return allowed/denied, a bounded internal reason, exact target, granted scopes and contributing capability/assignment IDs and revisions. Record the evaluator version and evaluation instant separately from row revisions. A configuration ETag is not a global policy version; natural expiry can change a decision without any row update. Include membership/group/window evidence needed to explain the decision. Public errors must not enumerate foreign tenants or hidden assignments.

Wire the same decision to machine issuance, direct session administration and honest access explanations before declaring this slice complete. User protocol integration follows only after the trusted context seam is proven; the [public allowlist](../apps/id/src/http/auth-allowlist.ts) currently exposes only the machine token grant. No registration or compatibility link should automatically create a capability.

### Safe cutover, including bootstrap

- Seed the bound platform's reserved admin ceiling using immutable system bindings. Bootstrap must verify provenance, not adopt same-name rows. Preserve the current six-scope model without granting tenant administrators platform scopes.
- Inventory current tenant admin authority, machine clients and resource-only assignments. Produce explicit proposed capability rows and their source evidence for review. Do not infer user pair permission from client/resource compatibility, or grant all registered scopes to every tenant.
- Treat existing resources backfilled as shared as a reviewed legacy classification, not evidence that customers intended sharing. Current ownership is immutable: corrections need an explicit replacement/migration design, not an ordinary PATCH.
- Keep unsupported legacy non-admin resource-only grants inert for user OAuth until each has an approved pair mapping. Deny missing ceilings; no fallback to legacy grants after enforcement is enabled.
- Rehearse migration with populated data and the runtime role. Quiesce old workers before capability enforcement/pair traffic; a mixed deployment can apply different authority rules. Reconcile rejected grants before reopening traffic.
- Update fixtures with explicit capabilities. A test-only automatic grant in general client registration helpers would hide the production default-deny requirement.

**Acceptance:** Stephen's OmniChat/OpenCode example passes for two tenants; registration alone is denied; disabled/expired/missing capability denies despite retained assignments; user permission cannot satisfy machine permission; tenant SQL/API writes cannot raise ceilings; bootstrap cannot adopt a foreign binding; current admin authority and root behaviour use the same effective ceiling; committed removal is respected by the next grant.

### Close the concurrency proof with the policy

Start with the existing organisation → client → resource lock order. List every new policy reader and writer before extending it. Use the organisation row as the tenant policy barrier where sufficient: issuance reads share it and tenant policy changes take it exclusively. Prefer this existing barrier over locks on every assignment. Global user changes still require a consistent user dependency and ordering; multiple-organisation operations need sorted IDs or an equivalent demonstrated protocol. Never introduce a reverse lock order through authorisation checks.

Prove both commit orders for capability removal, group/member revocation, user disable and resource/client changes. For issuance-first, the writer waits for the committed issuance; for revocation-first, issuance cannot commit stale authority. Time-window expiry also needs a stated evaluation instant and boundary tests. The existing two-second database limit is per lock wait, not a complete request budget.

Protect against explicit removal of the last effective platform administrator using this same policy and serialised writer checks. Time-based expiry and upstream account loss can still remove availability without a local write: monitor those conditions and retain the explicit, audited break-glass procedure.
