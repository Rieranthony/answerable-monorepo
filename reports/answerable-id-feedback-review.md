**1. Compound entitlements: Stephen’s requirement is not representable today**

The database CHECK requires `num_nonnulls(client_id, resource) = 1`. The service independently rejects an input containing both. Principals are an organisation, group or member; grants are additive. This already handles group assignment and effective windows, but cannot record “this member may reach Microsoft 365 MCP through OmniChat only.” [Schema](/Users/anthonyriera/code/answerable/apps/id/src/db/schema/authorization.ts:144), [creation validation](/Users/anthonyriera/code/answerable/apps/id/src/services/entitlements.ts:67), [matching rules](/Users/anthonyriera/code/answerable/apps/id/src/db/queries/grants.ts:19).

There is a client–resource link table, but each link contains the client and resource, without an organisation/member/group restriction. It controls a different relationship from the requested tenant-specific permission. A global OmniChat–Microsoft 365 link cannot express one customer's restriction independently of another customer's restriction. [Link schema](/Users/anthonyriera/code/answerable/apps/id/src/db/schema/oauth.ts:111).

**Changing the CHECK alone would be incomplete.** `effectiveGrants` explicitly requires a null client ID when matching a resource. `targetAccess` excludes the other target field. `memberAccess` chooses “client” whenever `clientId` exists, so it would flatten a pair into a client entry. A pair admitted by a relaxed CHECK would consequently be ignored or misrepresented by existing readers. [Grant query](/Users/anthonyriera/code/answerable/apps/id/src/db/queries/grants.ts:44), [access views](/Users/anthonyriera/code/answerable/apps/id/src/db/queries/access.ts:31).

**Current exposure is bounded:** public user authorization/refresh grants remain closed; the allowlist accepts only `client_credentials` at the token endpoint. Do not describe this as an already-exploitable user MCP policy bypass. It is a model limitation to resolve before exposing that flow. [HTTP allowlist and grant restriction](/Users/anthonyriera/code/answerable/apps/id/src/http/auth-allowlist.ts:28).

**Recommendation:** adopt an explicit request model containing principal, organisation, client, optional resource, requested scopes and grant type. Decide whether a resource-only entitlement permits all otherwise-approved clients, and how broad and paired grants combine. Under today's additive semantics, adding a narrow pair cannot cancel a broader grant; a migration must not silently preserve a broad permission while presenting the pair as a restriction.

A pair is sufficient for Stephen's example: one requesting app and one target server. Nothing in that example establishes a need for arbitrary chains of applications. Keep app-login permission, client–resource compatibility and principal permission distinct in policy evaluation. Preserve resource-only admin grants deliberately. Define machine ownership/ceiling policy separately from user membership policy.

**Proposed acceptance tests:** OmniChat allowed and OpenCode denied for the same person/resource; a second tenant allowed to choose differently; scopes cannot be combined across unrelated pairs; direct/group/organisation grants and expired windows behave consistently; existing admin grants still work; access views explain the same decision as issuance. Apply the policy to authorize, refresh and machine issuance as applicable when those paths open. The migration, HTTP schema, queries and generated OpenAPI must change together; generate OpenAPI rather than editing snapshots.

**2. Ownership: an existing token can acquire another tenant’s authority**

This is the most immediate finding related to Stephen's concern about same-name entities being co-opted.

**Executed reproduction:** create a machine client owned by organisation A, mint an `org:read` JWT, and keep that JWT unchanged. Reading organisation B initially returns 404. Change the client's owner to B: that same JWT now reads B with HTTP 200. Delete the client: the JWT receives 401. Recreate the same public `clientId` under B with a new secret: the original JWT receives 200 again. [Probe results, `oldToken`](/Users/anthonyriera/code/answerable/reports/answerable-id-feedback-evidence.json).

**Cause:** JWT verification extracts the public client identity; principal resolution then loads the current client row and derives organisation authority from its current owner. `setOwner` changes that owner without invalidating issued JWTs. Creation accepts a supplied `clientId`, and deletion removes its uniqueness reservation. The verifier does not bind the token to the client's immutable database row ID or an ownership generation. [JWT verification](/Users/anthonyriera/code/answerable/apps/id/src/http/principal.ts:68), [current-owner authority](/Users/anthonyriera/code/answerable/apps/id/src/http/principal.ts:184), [owner mutation](/Users/anthonyriera/code/answerable/apps/id/src/services/clients.ts:237), [creation](/Users/anthonyriera/code/answerable/apps/id/src/services/clients.ts:141), [client schema](/Users/anthonyriera/code/answerable/apps/id/src/db/schema/oauth.ts:33).

**Scope:** this does not let an unauthenticated attacker reassign clients. Client creation, owner changes and erasure require platform write authority. The failure is that an old credential holder inherits the authority of the newly assigned/recreated entity after an authorised administrative change. The organisation GET route accepts the resulting `org:read` grant, which the probe verified. [Client administration](/Users/anthonyriera/code/answerable/apps/id/src/http/admin/clients.ts:304), [organisation read authorization](/Users/anthonyriera/code/answerable/apps/id/src/http/admin/organizations.ts:167).

**Recommendation:** bind machine tokens to immutable client identity, owner and an issuance/revocation generation, and check those bindings at consumption. Alternatively, make ownership immutable and permanently reserve retired client IDs, with an explicit replacement flow. Merely updating token-table `revoked` timestamps is insufficient for this verifier: it validates JWTs and live client state without looking up token revocation rows. [Verifier](/Users/anthonyriera/code/answerable/apps/id/src/http/principal.ts:68), [database token revocation](/Users/anthonyriera/code/answerable/apps/id/src/db/queries/oauth-tokens.ts:5).

**Proposed acceptance tests:** old tokens fail after transfer, deletion/recreation and any operation intended to invalidate them; freshly issued tokens carry only the new owner's authority; tenant routes as well as `/me` enforce this. Make the observed reproduction a regression test before changing implementation.

**3. Idempotency: good database atomicity, incomplete operation replay**

Stephen's concern spans several guarantees. The code treats them differently:

| Operation | Current repeat behaviour | Consequence |
| --- | --- | --- |
| Disable an already-disabled user | 409 `user_already_disabled` | Desired state is already reached; no second successful mutation |
| Create an organisation with an existing slug | Unique violation mapped to 409 `conflict` | Does not prove that the existing row belongs to this operation or matches its payload |
| Create a client without a supplied client ID | Generates a fresh random client ID | Repeating after response loss can create another client |
| Rotate a client secret | Generates and stores a fresh secret every call | A retry invalidates the secret returned by an earlier call |
| Link the same client and resource | Conflict ignored; returns `created: false` | Relationship creation is repeat-safe, while the service still writes another audit event |
| Bootstrap | Advisory transaction lock, find/create/update reconciliation | Concurrent/repeated startup is handled, but existing rows are identified by configured names/identifiers |

Evidence: [user disable](/Users/anthonyriera/code/answerable/apps/id/src/services/users.ts:37), [unique-error mapping](/Users/anthonyriera/code/answerable/apps/id/src/http/problem.ts:77), [client creation](/Users/anthonyriera/code/answerable/apps/id/src/services/clients.ts:141), [secret rotation](/Users/anthonyriera/code/answerable/apps/id/src/services/clients.ts:222), [link insertion](/Users/anthonyriera/code/answerable/apps/id/src/db/queries/oauth-clients.ts:170), [bootstrap](/Users/anthonyriera/code/answerable/apps/id/src/bootstrap.ts:53).

**409s are not all ambiguous.** The response includes a machine-readable `code`. `user_already_active`, `user_inert`, and `user_email_retired` identify different conditions despite sharing HTTP 409. A caller can branch on those codes today. Unique-creation conflicts are less specific, and none of these codes returns the original successful response. [Lifecycle conflicts](/Users/anthonyriera/code/answerable/apps/id/src/services/users.ts:53), [problem response](/Users/anthonyriera/code/answerable/apps/id/src/http/problem.ts:35).

**Verified retry hazard:** two rotations with the same audit request ID returned different secrets. `x-request-id` is correlation, not deduplication: the app forwards it and the audit schema has no uniqueness constraint on it. [Probe results](/Users/anthonyriera/code/answerable/reports/answerable-id-feedback-evidence.json), [request context](/Users/anthonyriera/code/answerable/apps/id/src/app.ts:38), [audit schema](/Users/anthonyriera/code/answerable/apps/id/src/db/schema/audit.ts:12).

**What already works:** reviewed administrative services put mutation and successful audit insertion in the same database transaction. Kill switches include session deletion/token-row revocation in that transaction. Tests deliberately make audit insertion fail and assert rollback, including secrets, ownership and links. This prevents a partial committed database operation; it does not recover a response lost after commit. [Client rollback tests](/Users/anthonyriera/code/answerable/apps/id/src/services/clients.integration.test.ts:346), [user rollback tests](/Users/anthonyriera/code/answerable/apps/id/src/services/users.integration.test.ts:217), [organisation rollback tests](/Users/anthonyriera/code/answerable/apps/id/src/services/organizations.integration.test.ts:224).

**Recommendation:** define an administrative idempotency contract before automation depends on this API. Scope a caller-supplied operation key to authenticated authority and operation; store a canonical payload fingerprint and outcome atomically with the effect. Same key/same payload returns the prior outcome; same key/different payload is a specific conflict. Re-authorize replays. Specify concurrent-request, expiration and lost-response behaviour. Secret-returning operations need an explicit recovery design because the client table stores only a hash; do not put raw secrets in ordinary audit data.

For “create or reconcile,” check immutable identity and the expected owner before returning/updating an existing entity. A matching name, slug or public client ID alone is insufficient. Bootstrap currently reconciles by configured slug/resource identifier and grants the matching platform-admins group its scopes; there is no independent bootstrap provenance check in that function. This is a configuration/privileged-provisioning concern, not evidence of public self-registration. [Bootstrap lookup and reconciliation](/Users/anthonyriera/code/answerable/apps/id/src/bootstrap.ts:53).

**Checkpointing and ledgers:** no general durable job/checkpoint, outbox or billing ledger was found in the reviewed ID source/schema/package manifest. There are protocol-specific refresh replay fields and client-assertion records; those are not general administrative idempotency. Current database-only service operations can roll back/retry without DBOS. Revisit durable workflow/outbox design when a committed change must reliably trigger an external action. Require a unique business-operation ledger entry in the same transaction as money-related state when such state is introduced. Neither “exactly once across external systems” nor a billing requirement is established by the current code. [Schema inventory](/Users/anthonyriera/code/answerable/apps/id/src/db/schema/index.ts:1), [protocol-specific state](/Users/anthonyriera/code/answerable/apps/id/src/db/schema/oauth.ts:139), [dependencies](/Users/anthonyriera/code/answerable/apps/id/package.json:20).

**4. Audit records: IDs survive, but a complete person history does not**

**Stephen's precise question — can we tie records back to the person after erasure?** We can still correlate raw events carrying that user's UUID. We cannot rely on the current per-person API to retrieve the complete history, and erasure does not itself preserve a human identity snapshot.

`actor_id` and `target_id` are text without foreign keys to users. `eraseUser` writes `user.erased` with the user's ID and an empty data object after deleting the user. Earlier events may contain identifying data, such as `retiredEmail`, but this is operation-dependent; it is not a guaranteed identity record. [Audit schema](/Users/anthonyriera/code/answerable/apps/id/src/db/schema/audit.ts:12), [user erasure and retirement](/Users/anthonyriera/code/answerable/apps/id/src/services/users.ts:79).

**Two reproduced retrieval defects:**

1. After erasure, `listUserAuditEvents` returns 404 because the service first requires the user to exist. A global target-ID audit query still finds `user.erased`.
2. Even before user erasure, removing a membership makes its history disappear from the person's audit query. That query joins events through *current* member rows. The removal event contains `data.userId`, but the query does not use that field for member targets. The probe saw `member.updated` before removal, no person-history events afterwards, and both `member.updated` and `member.removed` still present in the raw audit table.

[Service existence check](/Users/anthonyriera/code/answerable/apps/id/src/services/audit.ts:28), [person-history query](/Users/anthonyriera/code/answerable/apps/id/src/db/queries/audit.ts:93), [member removal event](/Users/anthonyriera/code/answerable/apps/id/src/services/members.ts:75), [recorded reproduction](/Users/anthonyriera/code/answerable/reports/answerable-id-feedback-evidence.json).

**Before/after data is inconsistent.** Organisation and entitlement updates record submitted patches, without previous values. Group membership writes record the group ID without their effective-window values. Client-owner changes are a useful exception: they record `from` and `to`. Entitlement removal and user erasure record empty objects. Consequently, the event history is not sufficient to reconstruct every previous authorization state. [Organisation updates](/Users/anthonyriera/code/answerable/apps/id/src/services/organizations.ts:60), [entitlement updates/removal](/Users/anthonyriera/code/answerable/apps/id/src/services/entitlements.ts:101), [group writes](/Users/anthonyriera/code/answerable/apps/id/src/services/groups.ts), [owner changes](/Users/anthonyriera/code/answerable/apps/id/src/services/clients.ts:237).

**Side effects exist, but their evidence is incomplete.** User disable records session and token-row counts; organisation disable aggregates counts across users and clients. User/member deletion cascades related membership and entitlement data, and tests verify those cascades. No pre-removal manifest records all effective access paths and scopes. Counts prove how many rows the operation changed, not which prior permissions existed or whether an external service stopped accepting an already-issued token. [Disable behaviour](/Users/anthonyriera/code/answerable/apps/id/src/services/users.ts:37), [organisation counts](/Users/anthonyriera/code/answerable/apps/id/src/services/organizations.ts:74), [cascade tests](/Users/anthonyriera/code/answerable/apps/id/src/services/members.integration.test.ts:81), [user cascade tests](/Users/anthonyriera/code/answerable/apps/id/src/services/users.integration.test.ts:199).

**Tenant context also has a separate limitation.** Audit `organization_id` becomes null when an organisation is erased. Its own organisation-target events retain the target UUID, but other entity-target events lose that relational tenant attribution unless their data independently records it. Most client-service audit events omit `organizationId`; creation may contain it inside input data. Stephen corrected his wording, but this additional context loss is present in the code. [Organisation FK](/Users/anthonyriera/code/answerable/apps/id/src/db/schema/audit.ts:19), [client audit helper](/Users/anthonyriera/code/answerable/apps/id/src/services/clients.ts:42).

**Successful token issuance is unaudited in the executed flow.** The probe observed zero new audit events during a successful machine-token request. The HTTP handler forwards token requests to Better Auth; custom sign-in auditing matches SSO callbacks, not token issuance. Existing authentication auditing must not be described as “every token issuance is audited.” [Probe `tokenIssuanceAudit`](/Users/anthonyriera/code/answerable/reports/answerable-id-feedback-evidence.json), [auth dispatch](/Users/anthonyriera/code/answerable/apps/id/src/app.ts:147), [sign-in hook](/Users/anthonyriera/code/answerable/apps/id/src/auth/signin-audit-plugin.ts:79).

**Recommendation:** define a versioned audit event contract now: immutable subject and related-entity IDs independent of live rows; durable tenant attribution; allowlisted before/after fields; operation key; and concrete effects with stable IDs/counts and outcomes. Make person-history queries work for removed memberships and erased users. Decide explicitly whether “specific person” means UUID correlation or a retained identity mapping, and what identifying fields the product intends to retain. Do not indiscriminately snapshot secrets or every user field.

For offboarding, capture the access evidence under a consistent transaction/locking strategy before deleting it. Distinguish local revocation committed, external notification pending, external acknowledgement, and token expiry. Add token issuance/denial event coverage with client, owner, resource, granted scopes and decision reason, without token contents. Audit append-only behaviour is currently an application convention; the shown schema is not proof of database-enforced immutability or externally tamper-evident storage. [Audit table contract](/Users/anthonyriera/code/answerable/apps/id/src/db/schema/audit.ts:5).

**5. Work order before continuing the release**

These are proposed gates derived from the findings, not claims that the implementation already meets them.

| Order | Concrete next work | Evidence required to close it |
| --- | --- | --- |
| 1 | Fix machine-token identity/ownership binding | The transfer and client-ID reuse probes become failing regression tests, then pass with old tokens denied |
| 2 | Repair durable audit subject/tenant attribution and person-history queries | Histories remain queryable after member removal, user erasure and organisation erasure; before/after and effect evidence is asserted |
| 3 | Add audit coverage for currently open token issuance | Successful and denied machine grants produce the specified events; audit failure behaviour is tested |
| 4 | Agree and implement the admin retry contract, starting with client creation and secret rotation | Concurrent duplicates, changed payload, lost response and ownership collision tests; documented secret recovery |
| 5 | Decide paired-entitlement semantics before user OAuth expansion | Approved truth table, migration strategy, accurate access views and policy tests; implementation before user resource issuance |
| 6 | Resume the existing build sequence | Separate evidence for tenant self-service, OIDC/MCP grants, lifecycle, key custody and deployment readiness |

The current implementation can authenticate organisation users and administer ID, and it can issue machine tokens. It is not evidence that the complete OIDC/MCP release is ready: user grants are explicitly blocked in code. The existing plan separately places tenant self-service at 2c, user OIDC at 3, entitlement policy at 4, MCP at 5, lifecycle at 7, custody at 8 and infrastructure at 9. Keep the real-tenant/fork validation and rollout gates; passing the local suite does not replace them. [Reachable grants](/Users/anthonyriera/code/answerable/apps/id/src/http/auth-allowlist.ts:99), [planning context, not implementation evidence](/Users/anthonyriera/code/answerable/docs/02-plan.md:27).

**What can wait:** a general workflow engine until there is an external multi-step operation requiring durable recovery; a money ledger until money-bearing state is introduced; arbitrary multi-hop entitlement modelling without a demonstrated requirement. The existing transaction/constraint foundation supports incremental work. The reproducible authority and history defects deserve attention before that future infrastructure.
