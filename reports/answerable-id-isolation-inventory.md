Policy-user scope bounds the broker to that user's membership organisations; the grant query still evaluates membership/grant windows, revocation and organisation state. It is not a replacement for that evaluator. The policy scope returns no authority itself.

[Scope installation](../apps/id/src/db/isolation.ts) uses transaction-local `set_config(..., true)`. Service context factories set scope after current authority succeeds. Bootstrap sets only its established organisation UUID. The two broker reads own a transaction/savepoint and restore any enclosing scope on success; rollback restores it on failure. Both broker queries return their existing minimal projection (grants or a boolean). No network call belongs inside these transactions.

The runtime role cannot own tables or bypass RLS. Startup rejects disabled RLS on any protected table. The migration owner can bypass RLS, so owner-only tests cannot prove isolation. A process with arbitrary SQL execution can deliberately set trusted scope; RLS protects omitted filters, not a compromised application process.
