# MCP platform research

Research for the Answerable capability platform: the MCP design standard, the Toolbox hub and the SDK that outside developers will build on. This report holds the evidence; the decisions it supports are in [`docs/08-capability-platform.md`](../docs/08-capability-platform.md), the rules in [`docs/09-mcp-design-standard.md`](../docs/09-mcp-design-standard.md) and the build order in [`docs/10-capability-platform-plan.md`](../docs/10-capability-platform-plan.md).

## 28 September 2026

**Inputs.** Stephen's drafts of 27 September, kept verbatim in [`docs/drafts/`](../docs/drafts/): the [MCP design standard](../docs/drafts/2026-09-27-stephen-mcp-design-standard.md) and [Answerable Toolbox](../docs/drafts/2026-09-27-stephen-toolbox.md). The owner's brief: build MCP servers that are secured and powerful in the Palantir sense (an administrator adds or removes tools for people or groups), an in-house equivalent of Executor, one central hub, composable, developer first, designed for the end state without shipping every feature on day one, and easier for agents to use.

**Method.** Three read-only surveys of this repository (`main` at d55220d and the open pull request 11), eight web research passes with primary sources (specifications and their GitHub repositories at pinned commits, vendor documentation, installed package sources under `node_modules/.bun`), one browsing pass through Codex in Chrome for pages that refuse plain fetches, and runtime probes for the sandbox choice. Every fact below names its source. Numbers are quoted from the source or measured here; nothing is estimated. Where two sources disagreed, the installed code won: for example, one pass concluded that no TypeScript SDK on npm implements the 2026-07-28 protocol, and a grep of the installed `@modelcontextprotocol/server@2.1.0` bundle (111 occurrences of `2026-07-28`, `server/discover`, `subscriptions/listen`, `input_required`) plus this repository's own acceptance, which pins 2026-07-28 clients, showed that it does.

Versions in play: Bun 1.3.1, MCP TypeScript SDK 2.1.0 (server, client, core; published 23 September 2026), MCP Apps 2.0.0, Better Auth 1.7.2, LibreChat v0.8.8-rc4, Executor v1.6.10 (2.0.0-beta.4 in flight), ToolHive v0.51.4.

### Findings that change the design

1. **Token scopes cannot be the tool-level permission.** ID narrows the granted scopes to the entitled subset at browser authorisation and stays exact at code exchange and refresh: a request wider than the stored code is `invalid_scope`, and a policy that shrinks makes the refresh fail (`apps/id/src/auth/grant-scopes.ts:2-13`, `user-token-boundary.ts:291-317`). A scope set therefore never grows for the life of a grant. An administrator who adds a tool to a group would wait for the next re-authorisation, up to 30 days. The hub has to read effective grants live.
2. **One token carries one audience.** ID enforces exactly one `resource` per authorisation, exchange, refresh and machine request (`user-oauth-flow.ts:185-188`, `machine-provider.ts:80-91`), and the MCP specification forbids passing a host's token to another server. A hub cannot forward the person's token to provider MCPs; providers run in the hub's process until ID offers token exchange (RFC 8693, already on the backlog).
3. **Entitlements already target one person.** An entitlement principal is the organisation, one group or one member (`entitlements_principal_check`); rows are additive with no deny row and no nested groups (`db/queries/effective.ts:28-52`). Writes are platform-tier only today (`platform:write`); the schema's row-level security already permits tenant writes, so tenant self-service is an API gap, not a data-model gap.
4. **LibreChat sends `resource` and can use a pre-registered public client.** The fork's base (v0.8.8-rc4) sends RFC 8707 `resource` on authorise, token and refresh by default, uses PKCE always, and registers dynamically unless `oauth.client_id` is set, in which case it runs as a public client on the discovered endpoints (`packages/api/src/mcp/oauth/handler.ts`). `Q-RESOURCE-PARAM` resolves as yes. OmniChat needs no fork patch for registration; ID needs CIMD or DCR only for hosts that offer nothing else.
5. **LibreChat shows the model tools only.** No elicitation (issue 11526), no tasks, no MCP Apps (issue 10641), no `structuredContent`, no annotations, no prompts in chat; `tools/list` is paginated with caps of 1,000 tools and 5 MiB per server; `list_changed` is honoured; tool keys are `${tool}_mcp_${server}`. Every tool result must carry its text form.
6. **Hosts govern by tool name and annotations, never by elicitation.** Claude.ai runs `readOnlyHint` tools without a per-call confirmation and always prompts on `destructiveHint`; ChatGPT uses all three hints; Claude Code, VS Code, Cursor, Copilot Studio and Gemini key approvals on tool names. Claude Code honours `_meta["anthropic/requiresUserInteraction"]: true` on a tool and no allow rule or mode can skip it. Elicitation is undocumented on Claude.ai, absent from the Messages API connector and Copilot Studio, and unmerged in Gemini CLI. The specification says annotations are untrusted.
7. **Accuracy falls past 30 to 50 tools.** Anthropic's documentation states selection accuracy degrades past 30 to 50 tools and reports tool search raising Opus 4 from 49% to 74% and Opus 4.5 from 79.5% to 88.1% on its MCP evaluation with an 85% token reduction; VS Code caps a request at 128 tools. A per-person list must be curated, and a meta-tool tier is needed above roughly 40 tools.
8. **Tool names must stay short and plain.** MCP allows 1 to 128 characters of `A-Z a-z 0-9 _ - .` (SEP-986); OpenAI allows 64 of `A-Za-z0-9_-`; LibreChat appends `_mcp_<server>`; Claude Code prefixes `mcp__<server>__`. Dotted capability identities cannot be tool names on every host.
9. **The installed SDK serves both protocol eras but has no task runtime.** SDK 2.1.0 serves 2026-07-28 (per-request `_meta`, `server/discover`, multi round-trip requests, `subscriptions/listen`, cache hints) and stateless 2025 requests; tasks exist only as wire vocabulary (`server/dist` comment: "no SDK runtime"), the 2026 codec strips `capabilities.tasks`, there is no server-side `tools/list` pagination, and elicitation cannot pass through this repository's handler wrapper. Long-running work needs an operations API of our own.
10. **Executor ships one `execute` tool, not four meta-tools.** The vision document describes `search`, `describe`, `execute` and `run_code`; the code at a0b0d91 registers `execute {code}`, `skills` and `resume`, with a passthrough mode (`integrations`, `search`, `invoke`). It has no durable run log, scopes of `org | user` only, global glob policies its author plans to remove, a lexical search over the whole catalogue per call, a QuickJS sandbox at 5 minutes and 64 MiB, and one maintainer with 2,660 of about 2,930 commits. Copy its patterns; do not embed its 34k-line SDK.
11. **ToolHive does not enforce isolation on Kubernetes** (`pkg/container/kubernetes/client.go:368` carries a TODO; its own doc 15 says permission profiles are local Docker only) and would duplicate token validation and RFC 9728 metadata in front of first-party Bun servers. Its value is for third-party workloads and it is 0.x with breaking CRD changes between v0.15 and v0.23.
12. **The prepared-mutation model is standard practice, not an invention.** Kubernetes dry run, Google's `validate_only` (AIP-163), Terraform saved plans that refuse when the state serial moved, the IETF Idempotency-Key draft (replay the stored result, 422 on fingerprint mismatch, 409 while in flight), Open Banking consents bound to exact payment details and single use, and Palantir action types with submission criteria evaluated server-side with the submitting user's identity all converge on the shape Stephen drafted. Model-written GraphQL reaches 31% to 48% accuracy across eight models on 1,845 instances (NL2GraphQL benchmark), and Apollo, Grafbase and Cosmo all default to predefined operations with mutations off.
13. **ID-JAG is the enterprise answer to "connect once for the whole organisation".** draft-ietf-oauth-identity-assertion-authz-grant-04 (May 2026), productised by Okta as Cross App Access and embedded in MCP's Enterprise-Managed Authorization extension (SEP-990 Final). Better Auth 1.7.2 has no token exchange, RAR, CIBA or jwt-bearer grant; each is bespoke code.
14. **Trace context and evidence have vocabularies now.** OpenTelemetry's GenAI and MCP conventions name the span (`tools/call {tool}`), the attributes and the duration histogram; SEP-414 (Final) carries `traceparent` in `_meta` and is written into 2026-07-28; MCP logging is deprecated in favour of OpenTelemetry. ID's `audit_events` already has the actor, action, target, outcome and request id shape that Okta, GitHub and Slack use.

### 2. Stephen's drafts in one page

The standard says: an MCP is a capability provider, not a mini-application; names are `<domain>.<operation>`; every capability is classified READ, MUTATE, START or SUBSCRIBE; state changes follow prepare, preview, commit, receipt with an immutable intent, optimistic concurrency, idempotent commit and a policy layer that decides who may commit (agent, controlled, human); inputs and outputs are typed; collections paginate; errors are structured; no raw secrets or ambient network; evidence is owned by a separate "Answerable Control"; long work goes to Temporal. The Toolbox draft says: one first-party MCP per organisation with `search`, `describe`, `execute`, `commit` and `run_code`; a capability plane behind it with a catalogue, a type model, Executor-derived adapters, a sandbox and a query surface; ToolHive to run MCP workloads; three composition forms (run_code, ToolHive composites, Temporal); an organisation-specific authorised view; a fifteen-step delivery path.

Everything in the standard survives contact with the evidence except four details, and everything in the Toolbox draft survives except its substrate choices; the design document records both. In short: names need a host-safe tool form beside the dotted identity (finding 8); prepare and commit need policy classes so that low-risk mutations commit without a human or a host prompt while high-risk ones cannot; ToolHive, Executor as a dependency, Temporal and a separate Control system are Not yet, each with a written trigger; the evidence store starts inside the hub.

### 3. Protocol facts we build on

### 5. Answerable ID for a hub

Read from `apps/id/src` with line references in the research notes.

- **Principals.** Entitlement rows name the organisation, one group or one member, and a client, a resource or the exact pair. Rows are unioned; there is no deny row, no nested group, and one live row per principal and target. Every row has a status, an effective window and a revision.
- **Ceiling.** `organization_capabilities` rows are platform-owned (write only under `platform-write`), one per (organisation, client, resource, grant kind) with a scope array. A user resource token needs the client-login capability, the exact-pair capability and their `refresh_token` twins.
- **Granted scopes** = requested ∩ client scopes ∩ resource allowed scopes ∩ pair capability scopes ∩ (union of matching pair entitlements) ∩ the original request. Narrowed at browser authorisation, exact at exchange and refresh (finding 1). Machine tokens ignore entitlements.
- **Token claims** (`at+jwt`): `iss`, `sub` = user id, `aud` = the single resource identifier, `client_id`, `azp`, `scope`, `iat`, `exp`, `jti`, `subject_type: "user"`, `organization_id`, `membership_id`, `grant_id`, `client_instance`, `resource_instance`, `organization_authorization_version`, `authorization_version`, `upstream_auth_time` or null. No group, role or email claims, no `act`, no `sid`. Access token lifetime 60 to 3,600 s; refresh rotates, up to 30 days.
- **Access views.** `GET /organizations/{org}/members/{memberId}/access` and `GET /organizations/{org}/access?clientId=&resource=` return per-target scopes, an allowed or denied `permission` with the intersected scopes and evidence, and `via` (entitlement id and principal kind). Each call takes a `FOR SHARE` lock on the organisation row and answers `Cache-Control: no-store`. There is no webhook, outbox, change feed or ETag; change markers are per-row revisions, the organisation and client `authorization_version` (embedded in every token), and the append-only audit log with `entitlement.*`, `group_member.*`, `capability.*`, `member.*` actions, cursor-paginated by event id.
- **Admin API principals.** Session cookie, `client_credentials` JWT with `aud` = the admin resource, or the root secret. User-delegated tokens are refused. A hub acting for a person needs its own machine client with an exact machine capability for the admin resource.
- **Registering an MCP today** takes three platform calls (resource, client, link) plus six per organisation (four capabilities, two entitlements), all `platform:write`.
- **Tenant tier can write** member windows, removals and reinstatements only. Every entitlement, capability, group and group-membership mutation is platform tier, while the table comments and row-level security anticipate tenant writes.

### 6. Executor

Clone at a0b0d915 (24 September 2026). MIT; TypeScript on Bun and Effect 4 beta; 3,991 stars; 224 commits in the last 30 days; 127 releases; latest v1.6.10 with 2.0.0-beta.4 in flight; `plans/kill-plugin-system.md` calls the plugin system "a fiction" and schedules its removal; the home page now says it is an MCP gateway.

What an MCP client sees: query parameters select `?mode=codemode` (default: `execute {code}`, `skills`, `resume`, optional `search_<integration>` nudge tools and MCP Apps artifact tools) or `?mode=passthrough` (`integrations`, `search` with full JSON Schema per hit, `invoke` validated with `@cfworker/json-schema`). Inside the sandbox the model calls `tools.search()`, `tools.describe.tool()` and `tools.<integration>.<owner>.<connection>.<tool>()`, with `fetch` disabled and TypeScript stripped by sucrase. Search is a hand-written lexical scorer over every tool row per call (weights path 12, name 10, integration 8, description 5). Describe compiles only the referenced `$defs` to TypeScript on demand and fills undeclared output types from observed shapes. Execute resolves a three-state policy (approve, require approval, block; most restrictive across owner layers; `destructiveHint` and non-GET default to approval), validates arguments only when a pause is imminent, elicits approval with an argument preview, resolves credentials behind a `CredentialProvider.get(id)` seam, calls the plugin, and retries once after a 401. Pause and resume are an Effect fibre with idempotent resume; paused state is in memory.

Adapters: OpenAPI (about 16k lines including Google Discovery and Microsoft Graph converters; tool path `<group>.<leaf>`; auth templates from security schemes), GraphQL (one tool per root field; a `select` override), MCP (tools persisted with annotations, `destructiveHint` implies approval, re-list on a 15-minute TTL, DCR and PKCE upstream). Custom JavaScript functions are not shipped at this commit. Sandboxes: QuickJS via `quickjs-emscripten` (sync WASM, 5 minutes, 64 MiB, 1 MiB stack) locally and on Docker; Cloudflare Dynamic Workers with `globalOutbound: null` in the cloud; Deno and workerd subprocess runtimes exist but nothing wires them. No durable run or audit log; no prepare and commit; no idempotency keys upstream; rate limits only in the cloud.

Pricing on 28 September: Cloud free for up to three members and 100,000 executions a month, Team at 15 dollars per member per month, Enterprise custom with SSO, SAML, SCIM and tool-call audit logs; self-hosting free. One execution is one call to the `execute` tool, however many inner calls it makes. The public documentation names only `execute`; the meta-tools above come from the source.

Worth adopting: the address grammar with the account in the path; connection equals credential with secrets behind a provider seam; tools materialised per connection with a staleness marker; two tool surfaces from one engine; skinny always-loaded descriptions with docs behind a `skills` tool; describe as compact TypeScript; the uniform result envelope; pause and resume as an engine primitive; validate before asking a human; most restrictive wins; opaque errors with correlation ids; the egress guard. Reusable as packages: `@executor-js/codemode-core` and `@executor-js/runtime-quickjs` (about 800 lines). Not to embed: the SDK, the plugin system, the storage fork.

### 7. ToolHive and the gateway landscape

ToolHive (clone at 61aaf42): Apache-2.0, Go, 2,215 stars, 133 contributors, v0.51.4 on 27 September, twelve releases in 33 days, backed by Stacklok. Thirteen CRDs (`MCPServer`, `MCPRemoteProxy`, `MCPServerEntry`, `MCPGroup`, `VirtualMCPServer`, `VirtualMCPCompositeToolDefinition`, `MCPRegistry`, `MCPToolConfig`, `MCPExternalAuthConfig`, `MCPOIDCConfig`, `MCPAuthzConfig`, `MCPTelemetryConfig`, `MCPWebhookConfig`, `EmbeddingServer`). Runs MCP servers in containers behind a per-server proxy with JWT or introspection validation, RFC 9728 metadata, an embedded authorisation server (CIMD and DCR, Kubernetes only, in memory unless Redis), RFC 8693 outgoing exchange, Cedar policies (`Client::<sub>`, `claim_*`, `arg_*`), tool filtering and renaming, JSON audit and OpenTelemetry with the MCP conventions. Virtual MCP aggregates a group with prefix or priority conflict resolution, Cedar filtering per identity, and composite tools as DAG steps (tool, elicitation, forEach) plus Starlark code mode; request-scoped only, with no preview, commit or receipts, 1,000 sessions per pod, 30-minute TTL and open memory and health-probe bugs (issues 5860, 6687). Permission profiles are not enforced on Kubernetes (finding 11). Two documented behaviours to avoid copying: header passthrough to backends at lowest precedence preserves the original token's privileges (the MCP specification forbids token passthrough), and a remote proxy without an authentication source accepts reachable requests under a synthetic local user.

Alternatives with stars on 28 September: IBM ContextForge 4,538 (virtual servers, teams, user-scoped OAuth); agentgateway 5,073 (Linux Foundation, CEL rules on list and call, alpha tags); MetaMCP 2,690 (slowing); Docker MCP Gateway 1,586; Obot 1,071 (IdP-group rules, token brokering; ACR bypass advisory GHSA-vw82-7fv8-r6gp); Microsoft MCP Gateway 854 (C#); Lasso 390. Cloudflare MCP Server Portals are in open beta with Access policies and curated tools per portal. Every hub that fronts third-party APIs keeps their tokens server side and returns a connect link inside the tool result rather than using elicitation. Meta-tool designs in the field: Composio (`SEARCH_TOOLS`, `MULTI_EXECUTE`), Nango (`search`, `execute`, tools unlisted by default with `pinned_tools`), Klavis Strata (categories, actions, details, execute), Stainless (`list`, `schema`, `invoke`), Docker (`mcp-find`, `mcp-add`), Lasso (`get_metadata`, `run_tool`).

### 8. Governance models

**Palantir.** An action type is a typed, governed mutation: parameters, rules, submission criteria (declarative conditions on the current user, group membership, parameters and execution context, evaluated server-side at submission with the submitting user's identity, each with a user-facing failure message, and dry-runnable), side effects, and an action log object per successful submission (actor, action type version, parameters, edited keys, provenance). In the recommended actions-only edit mode the user needs only Read on the objects; write authority lives in the action type. Application tokens are the runtime intersection of the user's permissions, the application's declared resource and operation restrictions, and the request. Checkpoints (justification prompts with records) and Approvals (a request state machine persisted as audit) are reusable primitives. Chatbot Studio (formerly Agent Studio) gives an agent six tool types, including Action with a per-tool "confirm before apply" switch. Logic functions run user-scoped or project-scoped, so execution identity is a published choice, not always the person. The documentation states that read-time filtering never protects the model's output.

**Enterprise AI products** separate the catalogue (which connectors exist), the audience (which roles or groups may use each) and the action policy (what each may do), and gate by role or IdP group: Claude Team and Enterprise (organisation-enabled connectors, per-connector policy, per-tool blocks); ChatGPT Enterprise (per-app role access, read versus write action sets, new actions disabled until enabled with a diff, per-app "when to ask"); Copilot Studio and Entra (an Agent ID per agent, per-operation scopes at publish, data policies at execution); Glean (CEL policies on tool inputs and outputs, per-tool toggles per surface, two-tier auto-confirmation); Agentforce (an empty-by-default permission set).

**Identity for agents.** ID-JAG (finding 13) is the standard, and Anthropic shipped it: enterprise-managed authorisation for connectors is generally available for Claude Team and Enterprise since 24 August 2026, provisioned by IdP roles, groups and scopes, with Okta at launch and any MCP provider able to implement it; WorkOS positions an in-house authorisation server as the acceptor of customer-IdP assertions. Auth0 adds Token Vault, CIBA with RAR-described transactions and fine-grained authorisation; Descope evaluates scope policy at issuance; Stytch advises checking credentials on every MCP operation. Better Auth 1.7.2 implements none of RAR, CIBA, token exchange or jwt-bearer; its device-authorization plugin is the nearest template for a poll-based approval.

**Engines.** OpenFGA and SpiceDB are servers backed by Postgres, not embeddable in Bun; Cedar runs in process through `@cedar-policy/cedar-wasm` 4.13.0 (stateless, forbid overrides permit); Casbin and OPA compile to WASM; Oso's open-source library is deprecated. For organisation, group, member and capability relations, relational rows plus a computed effective-grants view and JSON constraints evaluated in code cover the need; Cedar WASM is the cheapest upgrade if constraints outgrow that; a ReBAC server is not warranted.

**Standards for bound authorisation.** RFC 9396 `authorization_details` (typed objects, also a JWT claim); Transaction Tokens draft 11 (immutable context, replacements never widen); Biscuit (offline attenuation, WASM 0.6.0); AP2 v0.2 mandates (a Checkout Mandate open with constraints, closed with a `checkout_hash` and `cnf` binding; a Payment Mandate). The recommendation that follows is a server-side immutable intent record with an argument hash as the source of truth, and a short-lived JWT carrying `authorization_details` only when an approval must cross a service boundary.

**Agent-side permission models.** Claude Code evaluates deny, then ask, then allow, first match; `PreToolUse` hooks can veto but not bypass; the Agent SDK order is hooks, deny, ask, mode, allow, `canUseTool`. Server-set markers force prompts but never grant.

### 9. Prepared mutations and approvals

Prior art and the exact semantics to mirror are in the research notes; the design document adopts the following, each element with its precedent. A prepare call validates against the input schema, may carry an idempotency key (same key and fingerprint returns the stored intent; a different fingerprint is a 422; in flight is a 409), expected versions the caller already holds, and `validate_only`. The intent binds the capability and its version, the principal, the canonical input and its RFC 8785 fingerprint, every target with a typed version signal, a semantic preview (changes, effects, warnings, quantities), a server-decided policy class, the approval state, a single-use opaque commit token stored as a hash, and an expiry. Commit takes the intent id and the commit token and nothing else, like `terraform apply plan.out`; a repeat by the same principal returns the stored receipt with `idempotent_replay: true`. The receipt carries the applied changes and effects, new versions of every target, who committed and who approved, and an operation handle when the work continues. The state machine is prepared, awaiting approval, approved, committing, committed, with the side exits denied, cancelled, expired, stale and failed; terminal states never revive. Errors use one envelope with a `retry.policy` of `never`, `after_delay`, `after_fix_input`, `after_state_change`, `after_reprepare` or `after_approval`.

Approval binding: an intent digest over the canonical capability, version, input fingerprint, targets and preview; an approval record written by an authenticated Answerable ID session on a server-rendered page; any re-preparation invalidates it. For the controlled class the host's own confirmation prompt suffices and is recorded as the channel; `_meta["anthropic/requiresUserInteraction"]` makes Claude Code's prompt unbypassable and `x-openai-isConsequential: true` does the same for GPT Actions. Elicitation may carry a hand-off but never the decision.

Version signals exist in the systems clients use: HTTP `If-Match` and 412, Microsoft Graph `@odata.etag` (mandatory `If-Match` on Planner), SharePoint version labels, Salesforce `If-Match` and `If-Unmodified-Since`, Kubernetes `resourceVersion`, Autodesk immutable versions with a tip, Procore `updated_at`.

### 10. Query surfaces

Apollo MCP Server, Grafbase and WunderGraph Cosmo default to predefined, validated operations with mutations off and add `search`, `introspect`, `validate` and `execute` for exploration; Shopify's Storefront MCP and GitHub's server ship fixed tools; Hasura PromptQL executes model-written plans outside the model. Measured evidence: NL2GraphQL 31% to 48% across eight models; the Berkeley Function Calling Leaderboard finds multi-turn and long-horizon calls unsolved; no rigorous GraphQL-versus-fixed-tools study exists. OWASP's GraphQL sheet lists depth and amount limits, pagination caps, cost analysis, timeouts, resolver-level authorisation and introspection off in production.

Conclusion: fixed capabilities stay primary and no mutation ever travels through a query surface. A read-only, typed `describe` plus `query` over Answerable's own projected schema, validated before execution and gated behind a scope, earns its place when an organisation's read set would exceed roughly 30 to 50 tools or when cross-entity reporting is the common question. Saved queries promote into fixed capabilities.

### 11. Programmatic composition and sandboxes

Anthropic's "Code execution with MCP" (4 November 2025), Cloudflare's Code Mode (September 2025 onward) and Hugging Face's smolagents converge on one shape: the model gets one tool that runs a short program; the real tools appear to that program as typed function stubs; raw data stays inside the execution environment; the program reaches the tools only through bindings that call back to a privileged supervisor holding the credentials. Reported gains: 150,000 to 2,000 tokens (98.7%) in Anthropic's worked example; 1.17 million to about 1,000 tokens for the whole Cloudflare API and an 81% cut in Code Mode; 38% fewer billed input tokens on Anthropic's 75-tool programmatic-tool-calling benchmark and 8% more cost on sequential single-call workloads. Anthropic's hosted programmatic tool calling cannot reach MCP connector tools and is Anthropic-only; the pattern itself is provider-neutral when the hub owns the sandbox.

Probes on macOS 15.6, Apple Silicon, Bun 1.3.1 (scripts and raw outputs kept with the research notes):

### 12. Observability, evidence and durable execution

OpenTelemetry's GenAI and MCP conventions (Development status) name the server span `tools/call {tool}` with `mcp.method.name`, `gen_ai.tool.name`, `gen_ai.tool.call.id`, `jsonrpc.request.id`, `error.type` and the `mcp.server.operation.duration` histogram; trace context arrives in `_meta.traceparent` (SEP-414 Final). ToolHive and Docker's gateway emit these names; ContextForge emits generic OTLP. The TypeScript SDK has no tracing hook, so the span belongs in the execute wrapper this repository already owns.

Audit logs at Okta, GitHub, Slack and Google Cloud reduce to actor, action, target, context and outcome; ID's `audit_events` already has that shape plus `request_id`, `operation_id`, `schema_version`, row-level security and append-only writes, and `admin_operations` is an idempotent receipt store. Tamper evidence: a per-organisation SHA-256 hash chain in Postgres with triggers that reject updates and deletes, a nightly verification job and an external anchor; payloads stored separately so erasure keeps the chain intact. Amazon QLDB ended on 31 July 2025 with Postgres as the suggested replacement; immudb is BSL.

Durable execution on Bun and Postgres: pg-boss 12 (MIT, Postgres 13 or later, lists Bun in its README, SKIP LOCKED, retries, deferral, singleton and throttle policies, dead-lettering; use the `pg` driver, since Bun.SQL through Drizzle double-encodes JSON parameters in issue 880); Restate (TypeScript SDK on Node 22, Bun or Deno; one BSL 1.1 binary; awakeables for approvals); DBOS Transact (MIT, Postgres only, Node officially, Bun unofficial); Temporal (its README discourages non-Node workers; experimental Bun fixes in v1.23.0); Hatchet, Inngest, Trigger.dev, BullMQ 6 with a Postgres backend at 1.5 to 2 times Redis latency, and Cloudflare Workflows. Under 2026-07-28 the tasks extension gives the long-running shape (`taskId`, five statuses, `ttlMs`, `pollIntervalMs`, durable creation before responding), but no host documents support and Claude Code times a call out at 60 s, so an operations API in ordinary tool results is the only path that works everywhere today.

Rate and cost limits: a GCRA or token bucket as one `INSERT ... ON CONFLICT DO UPDATE` per key, `429` with `Retry-After` on HTTP and an `isError` result with `retry_after_ms` on MCP, cost units per capability with budgets and a per-upstream breaker, and shadow mode before enforcement (Stripe). Versioning: MCP has no tool version or deprecation field (SEP-1575 dormant); the Stripe and Anthropic convention of a stable id plus a dated version, mirrored into `_meta` and the description, with RFC 9745 `Deprecation` and RFC 8594 `Sunset` headers on HTTP and a twelve-month window (SEP-2596).

### 14. Open questions for the owners

1. Who approves a human-class mutation in an organisation: the organisation administrators, a named approver group per capability pack, or the group manager? The design assumes an approver group per organisation with a per-pack override.
2. Should newly published capabilities in an already-enabled pack be granted automatically to existing entitlements (Glean's read-first default) or stay off until an administrator enables them (ChatGPT's default)? The design assumes off until enabled.
3. Which Better Auth version to pin for CIMD (`@better-auth/cimd` needs 1.7.6; ID pins 1.7.2).
4. Whether the Toolbox's own browser pages (approvals, connect flows) may live in `mcps/toolbox` as an OIDC client of ID, or whether every page with a sign-in must live in `apps/id`. The design assumes the former, since they are product pages, not identity pages.
5. Retention for evidence rows and receipts, and the anchoring cadence for the hash chain.
