# Administrative mutation inventory

This inventories the current [registered route tables](../apps/id/src/http/admin/index.ts), their declared API contracts and service implementations. All administrative mutation families use the existing journal wrappers. The [route contract test](../apps/id/src/http/admin/routes.test.ts) rejects missing replay headers and replacement preconditions; it does not substitute for runtime retry, failure or concurrency tests. Historical slice notes below describe the evidence available at that point; the tables are the current summary.

**Current totals:** 49 mutations; all 49 declare required idempotency keys and operation/replay response headers; no replay contracts remain missing. All seven PATCH operations require If-Match. Group membership window PUT and SSO PUT require either If-None-Match: * for creation or If-Match for replacement. The test asserts no missing replacement preconditions; immutable owner verification and link creation are explicitly distinguished from configuration replacement.

## Transaction and evidence boundaries

The listed service mutations insert their successful audit facts in their database transaction. Client/resource/domain/organisation/SSO/group/entitlement HTTP commands additionally commit the journal result in that transaction through [platformCommand](../apps/id/src/http/admin/command.ts). Member HTTP commands pass a validated tenant context from the journal's authority check into the mutation, with a tenant-scoped receipt. User and session commands also commit journal receipts with their declared platform authority. Middleware authorisation is not equivalent to a transactionally ordered recheck of every revocable authority source.

## Adoption rules

1. For each family, write lost-response/concurrent-duplicate, stale-write where applicable, current-authority and audit-failure tests before changing its contract.
2. Route through the trusted platform/tenant command context and the existing operation journal. Reuse transactions and receipts; do not introduce a second framework.
3. Capture allowlisted before/after and actual effects under the same ordering protocol. Document the resulting no-op and error meanings.
4. Update route headers/responses and retire its exact pending entry from the test only after runtime proof passes. Retire replacement-precondition entries for the two outstanding mutable PUT surfaces only with stale-write proof.
5. Regenerate OpenAPI and update public examples, schema/design and recovery documentation with the implementation.

The metadata test intentionally has a bounded legacy backlog. It cannot replace service/HTTP/fault tests or prove audit completeness. Delete the backlog arrays once every route adopts the contract; retain the contract assertions for future routes.

Session commands use platformUsersCommand, retaining platform:users rather than platform:write. They record exact deleted session IDs and token counts. ## Current last-platform-writer coverage

The capability ceiling guard, membership command runner and global user disable/erasure protect an existing effective human platform writer. Group disable/erasure, assignment removal/window replacement and entitlement update/disable/removal now share the membership before/after check under the target organisation lock. Each refused operation rolls back mutation, successful domain audit and journal receipt. Group metadata updates and additive creations cannot remove current permission. Organisation disable and bound admin-resource scope changes now also use the shared check; resource disable/erasure protect the persisted resource UUID. Time-based expiry, upstream login availability and fresh authentication remain separate concerns; this is not whole-system administrator availability. Restricted-role recovery/replay and mixed-writer concurrency evidence lives in [the execution report](answerable-id-foundation-execution-plan.md#last-platform-writer-during-group-and-entitlement-changes).


**Platform organisation and resource safeguards.** Organisation disable and bound admin-resource scope changes preserve existing effective platform-write authority, returning `409 last_platform_administrator` with transaction rollback when they would remove it. Adding another writer in that same organisation cannot make disabling the whole organisation safe; removing `platform:write` from the shared admin resource vocabulary also affects every writer. Safe scope restrictions retain authority and support ordinary replay. Scope writes acquire the platform lock before the resource lock; unrelated targets avoid it. Resource disable/erasure protection uses the persisted resource UUID, independently of configured names. Recovery can re-enable an already disabled platform organisation. These checks concern current effective permission, not future expiry or upstream availability.


**Group erasure audit (migration 0038).** New `group.erased` events use schema version 2. Alongside group before/after state, `data.effects.removedAssignments` records actual deleted assignment IDs, revisions, tenant/group/member/user UUIDs and validity windows. `removedEntitlements` records actual deleted entitlement IDs/revisions, targets, scopes, status and windows. Expired, disabled and future rows remain part of the evidence. Affected-user UUID history survives later user erasure; another tenant's policy is unaffected. The deletion, event, subject references and operation receipt commit or roll back together. Authorised replay does not repeat them. Apply migration 0038 before deploying the new writer. Older version-one group events lack this complete manifest and are not backfilled from guesses. These are removed policy sources, not a computed proof that every affected user lost all effective access or that remote sessions ended. Maximum supported synchronous deletion size remains a release requirement.


**Assignment history under user erasure.** Restricted-role HTTP concurrency tests prove both commit orders for group-assignment removal and global user erasure. ## Membership window and reinstatement access evidence

**Membership access observations.** Window changes, removal and reinstatement now emit version 2 events with the existing member-access projection under `before.access` and `after.access`. Both reads share the command transaction and tenant lock, and successful decision evidence carries evaluation time, immutable identity, revisions and approved scopes. Assignment scopes remain distinct from permitted scopes. Reinstatement may regain organisation-wide access without restoring removed direct assignments. These separate statement observations do not isolate causality across time or concurrent endpoint changes and do not prove remote revocation. Changed and unchanged removal/reinstatement events use version 2. Removal retains its actual deleted assignments and revoked grant contexts alongside the access observations; a surviving organisation-wide assignment does not make revoked membership effective. Audit/subject failure rolls back the mutation and receipt; replay does not duplicate the event. No schema migration or historical backfill.

Restricted-role HTTP regressions cover expiry/restoration, ceiling intersections, organisation-wide permission after reinstatement, another tenant for the same user, post-erasure history, subject rollback and same-key recovery/replay. Complete causal permission deltas and supported high-cardinality limits remain open.

**Client-resource audit visibility.** Version-two link/unlink/unchanged events retain resource instance UUID, immutable classification and owner alongside actual link before/after state. Shared targets and the client owner's private targets keep owner attribution; foreign-private and unknown targets are platform-only. Unlink reads the target under the existing client→resource lock order before mutation; a missing target still yields its existing no-op result. Organisation history excludes unrecognised/legacy versions of these three link actions before pagination; the platform endpoint retains all original events. No history rewrite, live-target inference or migration. Deploy the updated readers and writers together; an older serving reader does not enforce this filter. **Disabled-user reconciliation.** A new disable command always removes remaining browser sessions and revokes remaining stored tokens and grant contexts, even if the user is already disabled. The operation is applied when any local effect occurs; otherwise it is a no-op. Existing user status timestamps are preserved when status does not change. Replaying an old key returns that command’s original result and does not reconcile later state; use a new key for a new reconciliation. Audit failure rolls back all local effects and the receipt. Token effects now retain exact row IDs as described below; local cleanup is not proof of remote session termination.

RETURNING`, exclude already-revoked and unrelated rows, and contain no token value, scope or credential. Client disable and secret rotation retain this manifest alongside `grantContexts` in platform-only `client.grants_revoked` version 2. The client owner's event retains counts and `grantEffectsEventId`, excluding individual users and tokens. Migration 0044 captures affected users from that explicit contract so history remains queryable by UUID after live rows are erased. Apply it before the new writer; older events are not backfilled. Mutation, subjects, event and receipt commit together, and historical replay adds no revocation. This proves local stored-token revocation, not termination of downstream sessions or already-issued self-contained tokens. Token fan-out capacity remains release work.

Safe projections retain row/user/client/session/refresh references and applicable scopes, resources, expiry and revocation state; token values, secrets and consent claim requests are excluded. Refresh parents are locked before the access-token deletion statement so an insert committed while erasure waits is included in its later snapshot.
