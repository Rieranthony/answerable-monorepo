## Implementation contract

1. **One storage boundary for all three fields.** Cover account creation, login updates, internal adapter transactions and reads. The implementation uses the provider’s supported asynchronous field transforms, verified through the real adapter and native SSO. Reuse authenticated encryption from a supported library; do not write cryptography or patch `node_modules`. Avoid combining a whole-account transform with the provider's access/refresh flag and accidentally encrypting twice. If that seam cannot provide the invariant, document the concrete failing path before adding an adapter wrapper.
2. **Explicit storage state.** Reads after cutover must reject unexpected plaintext, malformed envelopes, missing keys and authentication failures. Never silently return suspect ciphertext as a credential. The one-time migration clears all pre-cutover credentials irrespective of format; it does not guess which values need decryption. Audit records presence only. Do not inspect or print real token values as an inventory mechanism.
3. **Explicit key configuration and rotation.** Define and validate active and retained key versions at application startup. Keep operation-replay keys separate. Prove old-row decryption during rotation, new writes under the active version, refusal with a missing old key, and no free-form secret-bearing error logs. Upstream keys are dedicated, so rotating this ring does not change the configured session/signing secret. Distribute a new decryption key to all instances before promoting it to first position. The separate provider/signing key milestones remain open.
4. **Repeat-safe retirement.** Pause upstream login writes for the initial controlled cutover. Migration 0037 clears all three tokens and both expiry fields, preserving account UUIDs and `(issuer, sub)`/directory bindings. Changes, presence-only audit facts and the existing migration receipt commit together. Restart before commit retries the transaction; restart after commit skips it. Re-run the runner, never standalone SQL. This uses an account writer lock and one transaction, not resumable batches; representative-volume rehearsal must establish acceptable duration before release.
5. **Restore is part of the proof.** Restore a populated disposable database and its separately supplied retained keys into an isolated service. Demonstrate successful reads and a subsequent SSO login; omit a required key and prove safe refusal. Define when old keys can be retired relative to stored rows and retained backups. Local helper round-trips cannot close this gate.

## Production storage integration
