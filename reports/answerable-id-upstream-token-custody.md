# Application-secret custody: evidence

ID stores no upstream token. It requests no `offline_access`, discards an upstream refresh token at write (`accounts.refresh_token` stays null) and has no upstream key ring (v0 code audit, 20 October 2026). The upstream token storage, its retirement migration and the restore rehearsals this report once recorded are in git history. What still holds is the application-secret rotation below; startup now also refuses application secrets that cannot decrypt the newest signing key ([ID's README](../apps/id/README.md#application-secret-rotation)).

## Application-secret rotation

`env.ts` validates optional `BETTER_AUTH_SECRETS` in the provider's native `version:secret` comma-separated format and `createAuth` supplies the parsed ring explicitly. Every retained value is at least 32 characters; versions are distinct non-negative safe integers. Errors contain the field and fixed validation rule, not input values. The singular legacy secret remains required, preserving current installations; this does not retire or rewrite legacy ciphertext.

The [native integration test](../apps/id/src/auth/application-secrets.integration.test.ts) uses actual SSO fixture cookies and production `createAuth`. Staging the old value first preserves the cookie. Promoting a new active secret returns no session for that cookie despite retaining the old version. Legacy private-key signing still succeeds with the singular fallback. Simulating expiry of the old signing key lets the provider generate a replacement encrypted as `$ba$2$…`; a newer active ring retaining version 2 can sign with it, while removal of version 2 refuses and preserves the key row. Independent public-key verification checks continuity. This uses the provider's server-only signer and does not claim public-route or managed rotation support.

The [official secrets contract](https://better-auth.com/docs/reference/options#secrets) documents first-entry encryption and retained decryption. The pinned 1.7.2 `create-context.mjs`, `crypto/index.mjs`, JWT `sign.mjs`/`utils.mjs` and session route establish the actual implementation: cookie verification uses the current secret, not the decryption ring. Documented deployment therefore requires coordinated active-version promotion and fresh sign-in, with in-flight callbacks drained. Keeping legacy ciphertext decryptable is distinct from preserving browser authentication.

**First-principles review:** preserve the provider-native format and crypto, validate at the existing environment boundary, and add one configuration field. No secret-manager abstraction, custom cipher, cookie fallback, new table or re-encryption daemon. Ring activation is opt-in. Legacy retirement and emergency signing-key procedures remain open; the delivery of secrets is in [`docs/12`](../docs/12-deployment.md#secrets).
