## Summary

1. The latest published revision is **2026-07-28**; the revisions are 2024-11-05, 2025-03-26, 2025-06-18, 2025-11-25, 2026-07-28 and `draft` (identical to 2026-07-28, empty changelog). There is no 2026-03 revision. 2026-07-28 is a breaking rewrite: no `initialize`, no sessions (`Mcp-Session-Id` gone), no GET stream, no `Last-Event-ID`, per-request `_meta` carries protocol version and client capabilities, `server/discover` is mandatory, server-to-client requests (elicitation, sampling, roots) become **Multi Round-Trip Requests** (`resultType: "input_required"` + retry), tasks move to the extension `io.modelcontextprotocol/tasks`, list results carry `ttlMs`/`cacheScope`, roots/sampling/logging and **Dynamic Client Registration are deprecated** (CIMD is the recommended registration), and `tools/list` may vary by the caller's authorisation but not per connection.
2. **No TypeScript SDK on npm implements 2026-07-28 yet**: the installed `@modelcontextprotocol/core@2.1.0` (npm latest as of today) compiles `LATEST_PROTOCOL_VERSION = "2025-11-25"` and contains no `2026-07-28`, `server/discover`, `subscriptions/listen` or `input_required` strings; `sdk@1.30.0` also tops out at 2025-11-25. Claude Code's docs claim its "v2 runtime" negotiates 2026-07-28 with HTTP servers; every other host documents 2025-03-26 to 2025-11-25 behaviour. A hub must therefore be a 2025-11-25 server today (stateless: simply do not mint session ids) and plan a dual-era upgrade.
3. Tool annotations are unchanged since 2025-03-26 (`title`, `readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`; nothing newer in the 2026-07-28 schema) and are the only host-portable approval signal: Claude.ai runs `readOnlyHint` tools without per-call confirmation and always prompts on `destructiveHint`; ChatGPT uses all three to choose confirmation behaviour; Claude Code, VS Code, Cursor, Copilot Studio and Gemini CLI key approvals on tool **names** (allow rules, allowlists, per-tool toggles), not annotations.
4. Elicitation is not a reliable approval channel across hosts: Claude.ai does not document it (and excludes "advanced or draft capabilities"), the Messages API connector supports tool calls only, Copilot Studio does not document it, Gemini CLI only gained it mid-2026; Claude Code, VS Code, Cursor and ChatGPT support form mode. The spec's own human-in-the-loop model is the client's confirmation prompt plus annotations; long approvals belong to the tasks extension (`input_required`).
5. The protocol has **no `tools/search`**. Every tool-search SEP was closed (SEP-1821, SEP-1881 administratively; SEP-1300 rejected; SEP-2636 closed unmerged and sent back to the Primitive Grouping Interest Group, still in "Active Exploration"). The official guidance is host-side: `docs/docs/2026-07-28/develop/clients/client-best-practices.mdx` describes a `search_tools` meta-tool (catalogue → inspect → execute) and "Code Mode" brokering, with the warning that approving a script is not blanket approval for its tool calls.
6. Anthropic's API already ships the meta-tool pattern natively (tool search with `defer_loading`, up to 10,000 deferred tools; MCP connector toolsets can defer per server), programmatic tool calling (cannot reach MCP connector tools) and code execution containers; Claude Code turns tool search on by default for MCP tools. These are Anthropic-only mechanisms; the filesystem-of-stubs "code execution with MCP" design (150,000 → 2,000 tokens, 98.7% saving in their example) is portable and now mirrored in the MCP client best-practice guide.

### A1. Tools (`docs/specification/2026-07-28/server/tools.mdx`; `schema/2026-07-28/schema.ts`)

- Definition fields: `name`, `title` (2025-06-18, PR #663), `description`, `icons` (2025-11-25, SEP-973: array of `{ src, mimeType?, sizes?, theme? }`), `inputSchema` (must be an object schema; any JSON Schema 2020-12 keyword since 2026-07-28), `outputSchema` (2025-06-18, PR #371; any 2020-12 schema since SEP-2106), `annotations`, `_meta`.
- `annotations` (introduced 2025-03-26, PR #185), exact `ToolAnnotations` interface in the 2026-07-28 schema: `title?`, `readOnlyHint?` (default false), `destructiveHint?` (default true; meaningful only when `readOnlyHint == false`), `idempotentHint?` (default false; same condition), `openWorldHint?` (default true). No newer hints exist. Clients MUST treat annotations as untrusted unless the server is trusted. Display-name precedence: `title`, then `annotations.title`, then `name`.
- `_meta` conventions (`docs/specification/2026-07-28/basic/index.mdx` § `_meta`, first specified 2025-06-18 PR #710): a key is an optional prefix (dot-separated labels ending in `/`, reverse-DNS recommended, e.g. `com.example/`) plus a name (alphanumeric ends; `-`, `_`, `.` inside). Any prefix whose second label is `modelcontextprotocol` or `mcp` is reserved (`io.modelcontextprotocol/`, `dev.mcp/`, `org.modelcontextprotocol.api/`, `com.mcp.tools/`); `com.example.mcp/` is not. Reserved keys: `progressToken`, `io.modelcontextprotocol/protocolVersion` (required on every request), `io.modelcontextprotocol/clientInfo` (SHOULD), `io.modelcontextprotocol/clientCapabilities` (required), `io.modelcontextprotocol/logLevel`, `io.modelcontextprotocol/subscriptionId`, `io.modelcontextprotocol/serverInfo` (results, SHOULD), and `traceparent`/`tracestate`/`baggage` (OTel, SEP-414). Custom keys for a hub: use your own reverse-DNS prefix (e.g. `com.answerable/`); hosts also define vendor keys (`anthropic/maxResultSizeChars` in Claude Code, `openai/*` in ChatGPT). Note the task's "modelcontextprotocol.io/" spelling is the wrong direction: the spec reserves the reverse-DNS `io.modelcontextprotocol/` form.
- Results: `content[]` of `text`, `image`, `audio`, `resource_link` (2025-06-18, PR #603; not guaranteed to appear in `resources/list`), embedded `resource`; optional `structuredContent` (any JSON value; MUST conform to `outputSchema` if present; clients SHOULD validate; servers SHOULD also serialise it into a text block for backwards compatibility); `isError: true` for tool execution errors including input-validation errors (SEP-1303), while unknown tool / malformed request are JSON-RPC errors (`-32602`).
- `tools/list`: opaque `cursor`/`nextCursor` pagination (page size server-chosen; cursors opaque; invalid cursor → `-32602`), plus in 2026-07-28 the required `ttlMs` and `cacheScope` (`"public"` | `"private"`; private caches MUST NOT be shared across authorisation contexts) from `CacheableResult` (SEP-2549); servers SHOULD return a deterministic order. The set MUST NOT vary per connection or as a side effect of other requests, but MAY vary by the authorisation presented (e.g. only tools the granted scopes permit) — the spec text that legitimises scope-filtered catalogues.
- `notifications/tools/list_changed`: requires `capabilities.tools.listChanged: true`; in 2026-07-28 it is delivered only to clients that opened `subscriptions/listen` with `toolsListChanged: true` (tagged with `io.modelcontextprotocol/subscriptionId`); in 2025-11-25 and earlier it arrives on the GET SSE stream.
- Tool names (SEP-986 → spec text): SHOULD be 1–128 characters, case-sensitive, only `A-Z a-z 0-9 _ - .`, unique within a server; aggregating clients or proxies SHOULD disambiguate (e.g. prefix with a server identifier); `serverInfo.name` is not unique and SHOULD NOT be used for that.
- 2026-07-28 additions: `x-mcp-header` schema annotation (primitive params mirrored into `Mcp-Param-{Name}` headers; clients MUST reject invalid definitions and drop those tools), a non-normative "Stateful Tools" section (explicit server-minted handles as ordinary arguments; handles are names not capabilities; validate authorisation per call; state expiry as tool errors), and `tools/call` MAY return `InputRequiredResult`.
- Security list: servers MUST validate inputs, implement access control, rate-limit, sanitise outputs; clients SHOULD prompt for confirmation on sensitive operations, show inputs before calling, validate results, enforce timeouts, log usage.

### A2. Elicitation (`docs/specification/2026-07-28/client/elicitation.mdx`; `basic/patterns/mrtr.mdx`)

- History: `elicitation/create` added 2025-06-18 (PR #382) as a server→client request; URL mode added 2025-11-25 (SEP-1036, still flagged as possibly changing); enum/defaults improvements 2025-11-25 (SEP-1330, SEP-1034). 2026-07-28 (SEP-2322 MRTR): the server returns `{"resultType": "input_required", "inputRequests": {"<key>": {"method": "elicitation/create", "params": {...}}}, "requestState": "<opaque>"}` and the client retries the original request (new JSON-RPC id) with `inputResponses: {"<key>": {...}}` and the echoed `requestState`. `notifications/elicitation/complete` and `elicitationId` were removed. Allowed on `tools/call`, `resources/read`, `prompts/get` only.
- Capability declaration: `elicitation: { "form": {}, "url": {} }` (an empty `elicitation: {}` means form only); in 2026-07-28 it lives in `_meta["io.modelcontextprotocol/clientCapabilities"]` on each request, in 2025-11-25 in `initialize`. Servers MUST NOT send modes the client did not declare.
- Params: `mode` (`"form"` default when omitted, or `"url"`), `message`. Form: `requestedSchema` restricted to a flat object with primitive properties — string (`minLength`, `maxLength`, `format` ∈ email/uri/date/date-time, `default`), number/integer (`minimum`, `maximum`, `default`), boolean (`default`), single-select enum (`enum` or `oneOf` of `{const,title}`), multi-select (array with `items.enum` or `items.anyOf` of `{const,title}`, `minItems`/`maxItems`); no nested objects or arrays of objects. URL: `url` (MUST be valid; MUST NOT be pre-authenticated or carry PII).
- Result: `action` ∈ `accept` (form: `content` holds the data; URL: `content` omitted, and accept only means the user consented to open the URL, not that the interaction finished), `decline` (explicit refusal), `cancel` (dismissed / escape / load failure). Servers MUST handle decline and cancel and MUST NOT assume the client retries.
- Security: servers MUST NOT collect passwords, API keys, tokens or payment data via form mode and MUST use URL mode for them; clients MUST show which server asks, allow review before sending, show the full URL and get consent, must not prefetch; servers MUST verify the identity of the user opening a URL (phishing/account-takeover scenario); `requestState` is attacker-controlled input — MUST be integrity-protected (HMAC/AEAD) when it affects authorisation, SHOULD embed principal, short TTL and a digest of the originating request; single-use must be enforced server-side. URL mode is explicitly the sanctioned way for a server to become an OAuth client to third-party APIs (token passthrough of the MCP client's token is forbidden).
- Fitness as a human-approval channel for state-changing actions: the spec never positions elicitation as the approval step (that is the client's confirmation prompt, `tools.mdx` § User Interaction Model, plus annotations). Using a form elicitation as "confirm?" works technically but (a) host support is uneven (see Part B), (b) any client can answer programmatically and the server MUST NOT rely on client-provided identity, (c) under MRTR it costs an extra round-trip and a protected `requestState`, (d) the tasks extension already models long approvals as `input_required`. Recommendation: annotations + two-phase tools (see Implications).

### A3. Tasks

- 2025-11-25 core, experimental (`docs/specification/2025-11-25/basic/utilities/tasks.mdx`, SEP-1686 Final): request augmentation `params.task: { ttl }` on `tools/call` (and any request listed under `capabilities.tasks.requests.*`; tools may add `execution.taskSupport`), `CreateTaskResult` with `task: { taskId, status, createdAt, lastUpdatedAt, ttl, pollInterval }`, methods `tasks/get` (poll), `tasks/result` (blocks until terminal, returns exactly what the original request would), `tasks/list` (paginated, capability `tasks.list`), `tasks/cancel` (capability `tasks.cancel`), `notifications/tasks/status`; statuses `working` → `input_required` | `completed` | `failed` | `cancelled` (terminal three); all related messages carry `_meta["io.modelcontextprotocol/related-task"] = { taskId }`.
- 2026-07-28: moved out of core into the official extension `io.modelcontextprotocol/tasks` (SEP-2663 Final; `ext-tasks/specification/2026-07-28/tasks.md`; npm `@modelcontextprotocol/ext-tasks` 0.1.0). Server-directed: the client only declares `extensions["io.modelcontextprotocol/tasks"]: {}` per request and must accept either the normal result or `resultType: "task"` (`CreateTaskResult` with the seed `Task`). Methods: `tasks/get`, `tasks/update` (client sends `inputResponses` for the outstanding `inputRequests` of an `input_required` task), `tasks/cancel` (cooperative; `notifications/cancelled` MUST NOT be used). `tasks/result` and `tasks/list` no longer exist. `Task` fields: `taskId`, `status` (same five values), `statusMessage?`, `createdAt`, `lastUpdatedAt`, `ttlMs: number | null`, `pollIntervalMs?`; `result` on completed, `error` (JSON-RPC error) on failed. Servers MUST durably create the task before returning; MAY rate-limit polling faster than `pollIntervalMs`; `notifications/tasks` (full task state) is optional and flows over `subscriptions/listen`. Positioned for CI pipelines, approval gates and unreliable connections. Host support: `docs/extensions/client-matrix.mdx` has no Tasks column and no host in Part B documents it.
- Progress (`basic/patterns/progress.mdx`): request `_meta.progressToken` (string or integer, unique per sender); `notifications/progress` `{ progressToken, progress, total?, message? }` with monotonically increasing `progress`, delivered on the originating request's response stream; MUST stop after completion. Cancellation (`basic/patterns/cancellation.mdx`, transports): on Streamable HTTP the client closes the request's SSE stream (no `notifications/cancelled` from clients in 2026-07-28); stdio keeps `notifications/cancelled`; servers MUST treat disconnect as cancellation; timeouts SHOULD exist and SHOULD be configurable.

### A5. Sampling, roots, completion, logging, subscriptions (one line each)

- Sampling (`sampling/createMessage`; tools + `toolChoice` since 2025-11-25 SEP-1577, gated by client capability `sampling.tools`): delivered via MRTR in 2026-07-28 and **deprecated** (SEP-2577; migrate to direct LLM APIs; earliest removal ≥ 2027-07-28).
- Roots (`roots/list`): deprecated in 2026-07-28 (`notifications/roots/list_changed` removed); pass paths as tool arguments instead.
- Completion (`completion/complete`, capability `completions`, `context` argument since 2025-06-18): active, unchanged.
- Logging: `logging/setLevel` removed in 2026-07-28; level is per request via `_meta["io.modelcontextprotocol/logLevel"]`; `notifications/message` only on the response stream of requests that set it; feature deprecated (use stderr/OpenTelemetry).

### A6. Authorisation (`docs/specification/2026-07-28/basic/authorization/*.mdx`; `docs/docs/2026-07-28/tutorials/security/security_best_practices.mdx`)

- Basis: OAuth 2.1 draft-ietf-oauth-v2-1-13; RFC 6750, 8414, 7591, 8707, 9728, 9207; draft-ietf-oauth-client-id-metadata-document-00; OIDC Discovery and Dynamic Registration. Authorisation is optional; HTTP transports SHOULD conform; stdio uses environment credentials.
- Roles and MUSTs: the MCP server is an OAuth 2.1 resource server; authorisation servers MUST implement OAuth 2.1; MCP servers MUST implement RFC 9728 Protected Resource Metadata and clients MUST use it for discovery; the AS MUST offer RFC 8414 or OIDC discovery and clients MUST support both.
- Discovery (`authorization-server-discovery.mdx`): (1) `WWW-Authenticate: Bearer resource_metadata="..."` on 401 (optional since SEP-985), else (2) well-known probing: path-suffix form `https://host/.well-known/oauth-protected-resource/<mcp path>` first, then root `/.well-known/oauth-protected-resource`. AS metadata for issuers with a path: `/.well-known/oauth-authorization-server/<path>`, `/.well-known/openid-configuration/<path>`, `<path>/.well-known/openid-configuration`; without a path: `/.well-known/oauth-authorization-server`, then `/.well-known/openid-configuration`. The fetched `issuer` MUST equal the issuer used to build the URL.
- RFC 8707 `resource` MUST be sent on authorisation and token requests (since 2025-06-18), set to the canonical MCP server URI (lowercase scheme/host, no fragment, prefer no trailing slash, path allowed). Servers MUST validate audience; MUST only accept tokens issued for themselves; MUST NOT accept or transit any other token (token passthrough forbidden); invalid/expired → 401; bearer in `Authorization` header only, never in the query string.
- PKCE: clients MUST implement PKCE, MUST use S256, MUST refuse to proceed when `code_challenge_methods_supported` is absent from the AS metadata (OIDC providers MUST include it).
- RFC 9207 (SEP-2468, 2026-07-28): AS SHOULD return `iss` and advertise `authorization_response_iss_parameter_supported: true`; clients MUST validate a present `iss` (exact string compare, no normalisation) before redeeming the code; a future revision is expected to make `iss` a MUST.
- Client registration (`client-registration.mdx`), priority order: (1) pre-registered credentials, (2) **CIMD** when the AS advertises `client_id_metadata_document_supported: true`, (3) **DCR** fallback when `registration_endpoint` exists, (4) prompt the user. CIMD (SEP-991): `client_id` is an HTTPS URL with a path to a JSON document containing at least `client_id` (must equal the URL), `client_name`, `redirect_uris`; `private_key_jwt` optional; the AS MUST validate redirect URIs against the document and SHOULD cache it; CIMD ids are portable across authorisation servers. DCR (RFC 7591) is **deprecated** as of 2026-07-28 (PR #2858) but retained for compatibility; clients MUST send `application_type` (`native` for CLI/desktop/localhost apps, `web` otherwise) and MUST key persisted credentials by issuer and re-register when the AS changes (SEP-2352). Pre-registration: clients SHOULD support static client credentials or a UI to enter them.
- Scopes: servers SHOULD put `scope` in the 401 `WWW-Authenticate` challenge; clients MUST treat challenged scopes as authoritative, else use `scopes_supported` from PRM, else omit `scope`. Runtime step-up: 403 with `WWW-Authenticate: Bearer error="insufficient_scope", scope="...", resource_metadata="...", error_description="..."`; servers SHOULD emit all scopes needed for the operation in one challenge and MUST honour scope hierarchies; clients SHOULD re-authorise with the union of previously requested scopes and the challenge, retry a bounded number of times, and track attempts. `offline_access` SHOULD NOT appear in PRM `scopes_supported`; clients MAY add it when the AS lists it.
- Enterprise-managed authorisation (SEP-990 Final; extension id `io.modelcontextprotocol/enterprise-managed-authorization`; spec at ext-auth `specification/stable/enterprise-managed-authorization.mdx`; overview `docs/extensions/auth/enterprise-managed-authorization.mdx`): the client signs the user in at the enterprise IdP, exchanges the ID token for an **ID-JAG** (Identity Assertion JWT Authorization Grant, the RFC 8693 token-exchange profile from Okta's Aaron Parecki), then exchanges the ID-JAG at the MCP authorisation server for an access token; no redirect to the MCP AS; the IdP holds the policy and revocation. Client matrix: Archestra.AI only; VS Code exposes `oauth.enterpriseManaged` (preview, ID-JAG); Claude documents an "Enterprise Managed Auth" page for connectors.
- OAuth client credentials extension (SEP-1046 Final; id `io.modelcontextprotocol/oauth-client-credentials`; ext-auth `specification/draft/...`): RFC 7523 JWT bearer assertions or `client_secret`, for machine-to-machine; no host in Part B supports it (Claude and ChatGPT both state M2M grants are unsupported).
- Server identity: `server/discover` (MUST implement) returns `supportedVersions`, `capabilities`, `instructions`, `_meta["io.modelcontextprotocol/serverInfo"]`; self-reported and explicitly not for security decisions. There is no signed `server_metadata` in the spec; "SEP-2127 MCP Server Cards via .well-known" exists only as an open PR (status not verified).
- Security best practices (2026-07-28 page sections): Confused Deputy (proxy servers using a static upstream `client_id` MUST keep a per-user registry of approved client_ids and obtain consent per dynamically registered client, with a consent UI showing client name, scopes, `redirect_uri`, CSRF protection, anti-framing), Token Passthrough (MUST NOT accept tokens not issued to the server), SSRF, **State Handle Hijacking** (replaces the 2025-11-25 "Session Hijacking" section: possession of a handle MUST NOT be treated as authentication; handles SHOULD be random and bound server-side as `<user_id>:<handle>`), Local Server Compromise, OAuth URL validation, stdio transport in proxy scenarios, Mix-up, Localhost redirect impersonation, CIMD trust policies, Scope minimisation. The 2025-11-25 page (`docs/docs/2025-11-25/tutorials/security/security_best_practices.mdx` § Session Hijacking) says servers MUST NOT use sessions for authentication, MUST use secure non-deterministic session ids and SHOULD bind them to the user.

### A7. Registry (`registry/docs/...`)

- Status: registry.modelcontextprotocol.io is "in preview" (`docs/modelcontextprotocol-io/about.mdx`); backed by Anthropic, GitHub, PulseMCP, Microsoft; a metaregistry (points at npm/PyPI/NuGet/crates/OCI/MCPB packages, never hosts code).
- `server.json` (`docs/reference/server-json/generic-server-json.md`, `$schema` `https://static.modelcontextprotocol.io/schemas/2025-12-11/server.schema.json`): `name` (reverse-DNS namespace: `io.github.<user>/<server>` verified via GitHub, or `com.example/<server>` verified via DNS), `title`, `description`, `version`, `websiteUrl`, `repository{url, source, subfolder?, id?}`, `packages[]` (`registryType`, `registryBaseUrl`, `identifier`, `version`, `transport{type: stdio|...}`, `runtimeArguments`, `packageArguments` (positional/named, `variables`), `environmentVariables` with `isRequired`/`isSecret`), `remotes[]` (`type: "streamable-http" | "sse"`, `url` with `{template}` variables carrying `description`, `isRequired`, `choices`, `default`, `isSecret`; `headers[]` with `isRequired`/`isSecret`), `_meta`. No per-tool metadata exists in `server.json`.
- Official-registry rules (`official-registry-requirements.md`): namespace ownership proof; package ownership proof; only public package registries; `_meta` keeps only `io.modelcontextprotocol.registry/publisher-provided` (4 KB limit, other keys dropped); registry-managed response-level `_meta` (`status` active/deprecated/deleted, `publishedAt`, `updatedAt`, `isLatest`). Remote servers MUST be publicly reachable; SSE remotes only for legacy clients (`remote-servers.mdx`).
- Private/enterprise catalogues: the official registry does not support private servers; the recommendation is to host your own registry implementing the registry OpenAPI spec (`docs/reference/api/openapi.yaml`), i.e. a **subregistry**; aggregators (Smithery, PulseMCP) ETL from `GET /v0.1/servers` (cursor pagination, `updated_since`) roughly hourly and may inject their own `_meta` keys (e.g. `com.example.subregistry/custom`); host applications are meant to consume subregistries, not the official registry directly; the official codebase is not designed for self-hosting (`about.mdx`, `registry-aggregators.mdx`, `design/ecosystem-vision.md`).

### A8. Transports (`docs/specification/2026-07-28/basic/transports/streamable-http.mdx`; `docs/specification/2025-11-25/basic/transports.mdx`)

- 2025-11-25 (what hosts run today): one MCP endpoint supporting POST and GET; the server MAY assign `Mcp-Session-Id` in the `initialize` response ("stateless mode" = simply not assigning one); if assigned, clients MUST send it on every request, the server returns 400 when it is missing and 404 when expired (client re-initialises), and clients SHOULD send HTTP DELETE to end a session; the client MAY open a GET SSE stream for server-initiated messages; servers MAY attach SSE event ids and support resumption via `Last-Event-ID` on GET (SEP-1699 allows the server to close streams to induce polling); `MCP-Protocol-Version` header MUST be sent after negotiation (absent → assume 2025-03-26); `Origin` MUST be validated with 403 on mismatch; JSON-RPC batching was removed in 2025-06-18; HTTP+SSE (2024-11-05) is deprecated, with the documented POST-then-GET fallback detection.
- 2026-07-28: POST only (GET/DELETE → 405); no protocol sessions (ignore `Mcp-Session-Id`, never mint one); no `Last-Event-ID` (a broken stream loses the in-flight request; re-issue with a new id); every POST MUST carry `MCP-Protocol-Version` (must match `_meta` protocolVersion, else 400 `HeaderMismatch -32020`), `Mcp-Method`, and `Mcp-Name` for `tools/call`/`resources/read`/`prompts/get` (Base64 sentinel `=?base64?...?=` for non-ASCII), plus `Mcp-Param-*` when `x-mcp-header` is used; unsupported version → 400 `UnsupportedProtocolVersionError -32022` listing `supported`; unknown method → 404 with `-32601`; a request's response is JSON or a request-scoped SSE stream carrying only that request's notifications; server-initiated requests never appear on streams (MRTR instead); long-lived change notifications only via `subscriptions/listen` (keep-alive comment lines, `X-Accel-Buffering: no`); closing the stream cancels. Backward compatibility: a dual-era client tries a modern request and falls back to `initialize` only when the 400/404/405 body is not a recognised modern JSON-RPC error; a dual-era server MAY serve both eras on one endpoint (`basic/versioning.mdx` compatibility matrix). Multi-tenant relevance: `cacheScope: "private"` caches MUST NOT be shared across authorisation contexts; intermediaries SHOULD only trust mirrored headers when the version mandates header/body validation.

### A9. Tool search, dynamic discovery, composition guidance

- Protocol level: no `tools/search` or grouping method in any revision; the only shipped catalogue mechanisms are pagination, `ttlMs`/`cacheScope`, deterministic ordering, `listChanged`, and the explicit permission for `tools/list` to vary by authorisation (2026-07-28 tools.mdx).
- SEPs (via `gh api`, 2026-09-28): SEP-1821 Dynamic Tool Discovery (issue #1821: `tools/list` `query` parameter + `tools.filtering` capability) closed 2026-06-24 because SEPs moved to PRs; SEP-1881 Scope-Filtered Tool Discovery (#1881) closed the same day for the same reason; SEP-1300 Tool Filtering with Groups and Tags (#1300) labelled `rejected`; PR #2636 Tool Manifests for Incremental Catalog Synchronization closed unmerged 2026-09-26 and redirected to the interest group; Discussion #1923 "Progressive Tool Discovery" remains a discussion. The **Primitive Grouping Interest Group** (repo `modelcontextprotocol/progressive-disclosure-wg`, README status "Active Exploration", work item "MCP Grouping Convention v0.1" proposed) is the venue; it cannot approve spec changes.
- Official host guidance (`docs/docs/2026-07-28/develop/clients/client-best-practices.mdx`): "Progressive Tool Discovery" — expose a lightweight `search_tools` meta-tool, three layers (catalogue → inspect → execute), dynamic server management (`search_available_servers`), re-index on `notifications/tools/list_changed`, prefer provider-native tool search (OpenAI, Anthropic) when available, mind prompt caching; "Programmatic Tool Calling / Code Mode" — a sandbox with a broker that is still the MCP host, per-call authorisation applies to sandbox-originated calls, categorical grants per script run are acceptable but each call must still be evaluated.
- Composition/proxy guidance scattered in the spec: aggregating proxies SHOULD prefix tool names (tools.mdx); proxies with static upstream client ids MUST obtain per-client consent (security considerations); token passthrough forbidden — a hub must be its own OAuth client to upstream APIs, obtaining consent via URL-mode elicitation or its own connect flow (elicitation.mdx); `x-mcp-header`/`Mcp-Name` exist so intermediaries can route without parsing bodies; stdio-proxy escalation risks (best practices).

## Implications for a hub (full org tool list vs meta-tools search/describe/execute/commit/run_code)

1. **Protocol version.** Serve 2025-11-25 semantics now (installed SDK 2.1.0 and every host except Claude Code's v2 runtime), in stateless mode (never mint `Mcp-Session-Id`, no per-connection state), with pagination and `listChanged`. Design every server-side feature so it survives the 2026-07-28 shape: no state in sessions (explicit user-bound handles), no reliance on server-initiated requests (MRTR turns elicitation into a retry), no reliance on `Last-Event-ID`, `tools/list` deterministic and scope-filtered, `ttlMs`/`cacheScope: "private"` ready. Track the TS SDK for 2026-07-28 support before promising it.
2. **Full list works only when curated per caller.** Hard and soft ceilings: VS Code 128 tools per request (then virtual-tool grouping), Anthropic's own accuracy guidance (30–50), Cursor's undocumented cap, Claude.ai 150k-char results. The spec explicitly allows `tools/list` to vary by the presented authorisation, so the hub can return only the tools the user's scopes/entitlements permit (exactly what Answerable ID's scope subset already models), prefix names by source server (`sourceName.tool` style, ≤ 128 chars, `[A-Za-z0-9_.-]`), keep order deterministic, and push `notifications/tools/list_changed` — honoured by Claude Code, VS Code and Copilot Studio; unknown for Claude.ai, ChatGPT, Cursor, Gemini, so also expect clients to re-list on reconnect.
3. **Meta-tools break host-side governance unless split by risk.** Every host keys approvals and admin blocks on the *tool name* (Claude.ai per-tool Blocked / Needs approval, Claude Code allow rules and `ask`/`blocked`, Cursor tool allowlists, Copilot Studio toggles, VS Code Manage Tool Approval, ChatGPT Action control, Gemini `trust`). A single `execute` tool collapses the whole catalogue into one name, defeating those controls and the annotation-driven auto-approval on Claude.ai/ChatGPT. Anthropic's client guide says approving a script is not blanket approval for its calls. If the hub offers meta-tools, expose at least `search` and `describe` with `readOnlyHint: true`, `execute_read` (`readOnlyHint: true`) separately from `execute_write`/`commit` (`destructiveHint: true`, `idempotentHint` as appropriate), surface the underlying tool's identity and annotations in `structuredContent` and the text block, and keep an audit log keyed by underlying tool. Prefer offering both modes as distinct servers (or a per-connector setting) so admins choose.
4. **Search/describe design.** Mirror the official three-layer pattern (catalogue with brief descriptions → full schema on demand → execute). Claude Code and the Messages API already defer MCP tools behind Anthropic's tool search, so on those surfaces a hub-side `search` is redundant unless it adds entitlement-aware ranking; on ChatGPT, Copilot Studio, Cursor, Gemini and Claude.ai it is the only option for very large catalogues. Return stable identifiers and enough structure for follow-up calls (ChatGPT tool-design guidance) and keep `search` results small.
5. **run_code.** Anthropic's programmatic tool calling cannot reach MCP connector tools, so a hub-side "Code Mode" (sandboxed broker) is the only portable way to get the 37–98% token savings the papers report. Requirements from the client guide and the best-practices page: per-call authorisation inside the sandbox, categorical grants per run, output limits (25k tokens / 150k chars), no network from the sandbox, PII tokenisation if intermediate data should not reach the model. Treat it as a later phase.
6. **Approval channel for state-changing actions.** Do not depend on elicitation (unsupported or undocumented on Claude.ai, the Messages API and Copilot Studio; new on Gemini). Use (a) correct annotations so hosts prompt, (b) two-phase tools where a `propose_*`/`preview` tool returns a server-minted handle bound to the authenticated user (random, HMAC'd or stored `<user_id>:<handle>`, short expiry, single-use) and a `commit_*` tool consumes it — this matches the spec's Stateful Tools and State Handle Hijacking guidance and works on every host, (c) form elicitation as an optional extra on hosts that declare the capability, (d) MCP Apps for rich review UIs on Claude, ChatGPT, VS Code, Cursor, (e) the tasks extension for approvals that outlive a request once hosts adopt it (none documented today).
7. **Authorisation profile the hub must offer** (Answerable ID as AS): RFC 9728 PRM at the path-suffix well-known URL (ChatGPT and Claude probe `/.well-known/oauth-protected-resource/<path>` first, then root) and in the 401 `WWW-Authenticate` with `scope` (Claude requires a 401 to start sign-in and only reads the first `authorization_servers` entry); AS metadata with `code_challenge_methods_supported: ["S256"]`, `authorization_response_iss_parameter_supported: true` (Gemini requires `iss`; ChatGPT/Claude validate it; spec will make it MUST), `registration_endpoint` (DCR is still the default path for Claude.ai, Copilot Studio "Dynamic discovery", Cursor, VS Code, Gemini — so keep DCR despite its deprecation) plus `client_id_metadata_document_supported: true` and `none` in `token_endpoint_auth_methods_supported` (needed for Claude's published identity, Claude Code's CIMD and ChatGPT's preferred path; also accept `private_key_jwt` for ChatGPT); pre-registered client ids for Copilot Studio Manual, Cursor static, VS Code `clientId`, Claude "own OAuth client"; RFC 8707 audience binding; 403 `insufficient_scope` step-up listing every scope still needed; refresh-token rotation for public clients and `offline_access` in `scopes_supported` (ChatGPT loses access otherwise); `application_type` handling in DCR; 10 s endpoint latency budget (Claude). No host will use `client_credentials`; machine access must go through Answerable's own machine-account model, not the MCP auth flow.
8. **Upstream credentials.** The hub is a proxy in the spec's sense: it must not pass the host's token upstream, must hold its own OAuth client per upstream service with per-user consent (URL-mode elicitation or a hub-hosted connect page bound to the `sub` of the MCP token), and, if it ever uses a static upstream client id, must keep a per-user registry of consented MCP clients (confused-deputy rules). Enterprise-managed authorisation (ID-JAG) is the standard's answer to "admin connects once for the org"; only VS Code (preview) and Claude (documented page) expose it today.
9. **Registry/distribution.** Publish a public `server.json` (`remotes: [{ type: "streamable-http", url }]`, `com.answerable/...` namespace) for discoverability; per-organisation private catalogues need a subregistry implementing the registry OpenAPI, since the official registry rejects private servers and `server.json` carries no per-tool metadata. Adding the hub to hosts is an admin act on Claude Team/Enterprise (Owner), ChatGPT Business/Enterprise (admin publish), Copilot Studio (maker + Power Platform DLP, or M365 admin approval), Cursor (team distribution/allowlists), VS Code (gallery/policies).
10. **Apps.** Where a review UI matters, MCP Apps are supported by Claude, ChatGPT, VS Code and Cursor (not Claude Code, Copilot Studio, Gemini, the Messages API); keep every app-backed tool useful as plain text (progressive enhancement) and declare `_meta.ui.csp`/`domain`.
