# Observability, evidence and durable execution for the Answerable MCP hub

Research date: 2026-09-28. Status: COMPLETE.

Marking: **VERIFIED (URL)** = read from the cited page or file this session. **INFERRED** = reasoning from verified facts, or prior knowledge not re-checked today. Search-engine snippets that were not opened are marked **VERIFIED (search snippet)** and should be treated as one notch below a page read.

Context assumed: Answerable is Bun 1.3.1 + Hono + Postgres on K3s (Civo), small team, "Postgres for all state, Redis later", no Temporal. The hub design under discussion has audited capability calls, prepared mutations, long-running operations and an evidence record. Neither "Answerable Control" nor a Temporal deployment exists yet. The repo already uses `@modelcontextprotocol/server|client|core` 2.1.0 and `ext-apps` 2.0.0 (VERIFIED packages/mcp-base/package.json), which implement the 2026-07-28 MCP specification; that changes section 4 materially.

## Summary

1. **Telemetry.** OpenTelemetry now has a Development-status vocabulary for exactly this: GenAI `execute_tool` spans plus the MCP conventions (`mcp.method.name`, `gen_ai.tool.name`, `jsonrpc.request.id`, `mcp.server.operation.duration`). Trace context travels in `params._meta` under un-prefixed `traceparent`/`tracestate`/`baggage`; that is SEP-414, status Final, and it is written into the 2026-07-28 spec. The 2026-07-28 spec also deprecates MCP Logging with the explicit migration "use OpenTelemetry", and removes sessions, so `mcp.session.id` has no meaning for new-spec clients. ToolHive and Docker's gateway emit the semconv names; IBM ContextForge is generic OTLP + Prometheus. The proposal for servers to hand spans back inline (SEP-2448, `_meta.otel`) was closed. The MCP TypeScript SDK has no tracing hook; the hub instruments its own tool-execute wrapper, which `packages/mcp-base` already owns.
2. **Evidence.** Answerable ID's `audit_events` (actor_type/actor_id, action, target_type/target_id, outcome success|failure|denied, reason, request_id, ip, user_agent, data, operation_id, schema_version, RLS, append-only) is the same actor/action/target/context/outcome shape as Okta, GitHub, Slack and Google Cloud audit logs, and ID already has `admin_operations` as an idempotent command receipt. Recommendation: one shared `evidence_events` shape that extends that vocabulary with execution/operation/mutation ids, a per-organisation SHA-256 hash chain in Postgres with periodic external anchoring (QLDB is retired, AWS itself points to Postgres; immudb is BSL 1.1), OCSF 6003 API Activity mapping for export, CloudEvents envelopes for outbound events, and payloads stored beside the chain so personal data can be erased without breaking it.
3. **Durable execution.** v1 should be plain Postgres tables plus **pg-boss 12** (MIT, Postgres 13+, "Node 22.12 or higher, or Bun" in its README, SKIP LOCKED, retries, cron, deferral, singleton/throttle policies, dead-letter, transaction-aware enqueue). Approvals that wait hours are rows with a state, not suspended processes. Trigger to adopt an engine: multi-step compensations across upstreams, a need for replay/debugging of workflows, or more than one service needing durable RPC. At that point the two Bun-realistic candidates are **Restate** (TS SDK states "NodeJS >= v22, Bun, or Deno"; single BSL-licensed binary; awakeables map directly to approvals) and **DBOS** (MIT library, Postgres-only, Node >= 20 engines, Bun unofficial). Temporal's own README strongly discourages workers outside authentic Node.js; Hatchet, Inngest, Trigger.dev and BullMQ 6 (which now has a Postgres backend) are documented below; Cloudflare Workflows only runs on Cloudflare.
4. **MCP long-running semantics.** Under 2026-07-28, Tasks are an official extension `io.modelcontextprotocol/tasks` (SEP-2663, stable): server-directed, `resultType: "task"`, `tasks/get` returns the result inline, `tasks/update` answers `input_required`, `tasks/cancel` is cooperative, there is no `tasks/list`, and the task must be durably created before the response is sent. No client in the official matrix lists Tasks support and Claude Code times out tool calls at 60 s, so the hub needs a universal path: return an `operation_id` in an ordinary tool result and expose `operations.get`/`operations.cancel` tools backed by the same `operations` table that will later serve the Tasks extension.
5. **Limits.** Token bucket or GCRA as a single-statement `INSERT ... ON CONFLICT DO UPDATE` in Postgres, keyed per organisation, principal, capability and upstream; cost budgets with reserve-then-settle; 429 + `Retry-After` (and the IETF `RateLimit-Policy`/`RateLimit` draft) on HTTP, an `isError` tool result with `retry_after_ms` on MCP; hard caps per organisation and per upstream against denial of wallet.
6. **Versioning.** MCP has no tool version or deprecation field today (SEP-1575 is dormant; issue #1915 closed without a decision). Borrow Stripe's dated versions and Anthropic's dated tool types: stable capability `id`, date `version`, `_meta["com.answerable/capability"]` with `status`, `deprecated_at`, `sunset_at`, `replacement`, mirrored in the description text, with `Deprecation`/`Sunset`/`Link rel="deprecation"` headers on HTTP and a 12-month minimum window as MCP's own lifecycle policy requires.

### B. Evidence and audit schema

  actor_id          text
  on_behalf_of      jsonb?                -- delegation chain, GCP serviceAccountDelegationInfo style
  organization_id   uuid?
  client_name       text?                 -- MCP host, from clientInfo
  capability_id     text?
  capability_version text?
  execution_id      uuid?
  operation_id      uuid?
  mutation_id       uuid?
  upstream_name     text?
  target_type       text
  target_id         text?
  outcome           text  in (success, failure, denied)
  reason            text?
  error_type        text?
  request_id        text?
  trace_id          text?
  span_id           text?
  ip                text?
  user_agent        text?
  data              jsonb?                -- bounded, redacted, no secrets
  payload_ref       text?                 -- pointer into evidence_payloads (erasable)
  payload_hash      text?                 -- sha256 of the canonical payload, kept in the chain
  prev_hash         text
  row_hash          text                  -- sha256(canonical fixed columns || data || payload_hash || prev_hash)
  schema_version    int default 1

- **Kinds** (namespaced like GitHub's `category.operation`): `capability.requested`, `capability.completed`, `capability.denied`, `mutation.requested`, `mutation.prepared`, `mutation.reviewed`, `mutation.approved`, `mutation.rejected`, `mutation.committed`, `mutation.receipt_issued`, `operation.started`, `operation.input_required`, `operation.cancel_requested`, `operation.finished`. One row per transition; the mutation record itself holds current state, the evidence stream holds history.
- **Chain**: triggers reject UPDATE/DELETE/TRUNCATE; a `BEFORE INSERT` function takes `pg_advisory_xact_lock(hashtext(stream_id))`, reads the stream head, assigns `seq` and computes `row_hash`; a nightly job verifies each chain, writes an `evidence_verification_runs` row, and publishes the head hash per organisation to object storage (the "anchor"), because a database owner can disable triggers and rewrite rows.
- **Redaction**: personal data and large bodies live in `evidence_payloads` (erasable); only `payload_hash` is chained, so erasure does not break verification. Never store tokens, session ids or credentials (OWASP); hash the principal where the row leaves the trust boundary.
- **Receipts**: a `mutation_receipts` table modelled on `admin_operations`: (organization_id, principal, capability_id, key_digest) unique, `fingerprint` of the arguments, `outcome` (applied | noop), `result_reference` `{type,id}`, `committed_at`, `expires_at`. Replays return the same reference; a different fingerprint under the same key is rejected; an in-flight key returns a "conflict, retry after" error (IETF draft semantics).
- **Export mappings**: OCSF class 6003 with `activity_id` from the capability's annotation (read → 2, create → 1, update → 3, delete → 4), `status_id` from `outcome`, `metadata.correlation_uid` = `execution_id`, `metadata.tenant_uid` = `organization_id`, `api.operation` = `capability_id`. Outbound events as CloudEvents: `type` = `com.answerable.evidence.<kind>`, `source` = `/orgs/{org}/hub`, `subject` = `execution:{id}`, `id` = row id, `traceparent` extension. Retention per organisation (default to a fixed period, then delete payloads first, rows later), with export before deletion.

### C. Durable execution v1 and the upgrade trigger

v1 = Postgres tables + pg-boss worker in Bun:

- `operations` (id, organization_id, principal, capability_id, capability_version, status working|input_required|completed|failed|cancelled, status_message, created_at, updated_at, ttl_ms, poll_interval_ms, attempts, lease_until, worker_id, cancel_requested_at, input_requests jsonb, input_responses jsonb, result_ref, error jsonb, idempotency_key_digest) plus `operation_steps` (operation_id, step_key, status, result jsonb, attempts) so each upstream side effect runs once and restarts resume at the last completed step.
- pg-boss for scheduling, retries with backoff, dead-lettering, deferred wake-ups (reminders, TTL expiry) and per-organisation concurrency via singleton/throttle policies; enqueue inside the same transaction as the evidence row.
- Approvals that wait hours are not waiting processes: the mutation sits in `prepared`/`reviewed` and the approval call (or `tasks/update`) advances it and enqueues the commit job. Nothing holds a connection.
- Use the `pg` driver for pg-boss rather than Bun.SQL through Drizzle for now (issue #880).

Adopt an engine when any of these holds: (1) more than a handful of multi-step operations need compensation across upstreams (sagas); (2) the team needs replay and step-level debugging of failed runs rather than log reading; (3) durable RPC is needed between more than one service; (4) concurrent waiting operations exceed what a polling worker handles comfortably. At that point run a two-day spike on **Restate** (Bun-supported SDK, one binary next to Postgres, awakeables for approvals, BSL acceptable for self-hosting) and **DBOS** (library, Postgres-only, MIT, but Node-only officially); pick on the Bun result. Avoid Temporal unless a Node worker is acceptable (its README discourages anything else) and the operational weight is justified.

### D. Operations API shape

Universal path (works with Claude Code and every host today):

- Any long capability returns immediately with `structuredContent: { operation: { id, status: "working", status_message, created_at, poll_after_ms, expires_at } }` and a text line saying how to check it.
- Tools: `operations.get { operation_id }` → the same shape plus `result` / `error` when terminal and `input_requests` when input is needed; `operations.cancel { operation_id }` → acknowledges, sets `cancel_requested_at`, workers observe it; `operations.answer { operation_id, responses }` for approvals; `mutations.receipt { mutation_id | idempotency_key }` returns the committed receipt idempotently. All scoped to the caller's organisation and principal; ids are 128-bit random and expire with `ttl_ms`.
- Field names map one-to-one to the ext-tasks `Task` (`taskId`, `status`, `statusMessage`, `createdAt`, `lastUpdatedAt`, `ttlMs`, `pollIntervalMs`) so, once `@modelcontextprotocol/ext-tasks` is adopted, the same row serves `tasks/get`, `tasks/update`, `tasks/cancel` for clients that send `io.modelcontextprotocol/tasks` in `_meta`, with the durable-creation rule satisfied by committing the row before responding. Implement 2026-07-28 shapes first; add the 2025-11-25 codec only if a needed host still speaks it.
- Synchronous calls keep `progressToken` → `notifications/progress` and honour `notifications/cancelled` by aborting the upstream call (the mcp-base wrapper already combines abort signals); operations use `status_message` for progress because progress notifications are not supported on tasks.
- A tool result with `isError: true` completes the task as `completed`; reserve `failed` for protocol errors.

### E. Limits

- Dimensions: (organization), (organization, principal), (organization, capability), (upstream). Store one bucket row per key with a GCRA timestamp or token count, updated in one `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` statement inside the request path; concurrency limits from a count on `operations` in `working`; move buckets to Redis only when the hot rows measurably bottleneck.
- Cost: every capability declares `cost_units` (fixed, or estimated then settled for token-priced upstreams); monthly budgets per organisation and per upstream with alerts at 80 % and a hard stop at 100 %; a global per-upstream circuit breaker for denial-of-wallet; anomaly alerts on per-principal spend.
- Responses: HTTP callers get 429 + `Retry-After` (+ `RateLimit-Policy`/`RateLimit` per draft-11); MCP callers get an `isError` result with `error.type = rate_limited`, `retry_after_ms` and a human sentence; every refusal is an evidence row `capability.denied` with `reason = rate_limited | budget_exhausted`.
- Roll out in shadow mode with rejection metrics before enforcing (Stripe).

### F. Capability versioning and deprecation

- Contract identity is `(id, version)`: `id` stable and reverse-domain-ish (`crm.contacts.search`), `version` a date (`2026-09-28`) in Stripe/Anthropic style; behaviour of a `(id, version)` never changes (issue #1915's rule). Ship at most one deprecated version alongside the current one; default callers to current.
- Publish in the tool definition: `_meta["com.answerable/capability"] = { id, version, status: "active" | "deprecated" | "sunset", deprecated_at?, sunset_at?, replacement?: { id, version }, changelog_url }` (the `com.answerable/` prefix is legal; `mcp`/`modelcontextprotocol` prefixes are reserved). Because hosts ignore `_meta`, also prefix the description: "Deprecated since 2026-09-28; use crm.contacts.search 2026-11-01 before 2027-03-01."
- On HTTP surfaces emit `Deprecation: @<unix>`, `Sunset: <HTTP-date>` (never earlier than Deprecation) and `Link: <...>; rel="deprecation"`.
- Window: twelve months minimum between deprecation and removal, mirroring SEP-2596; after sunset return an `isError` result `error.type = capability_sunset` pointing to the replacement for one further release, then remove.
- Record `capability_version` on every span and evidence row so usage of deprecated versions is measurable per organisation before sunset; keep `tools/list` order deterministic and set `ttlMs`/`cacheScope` as 2026-07-28 requires.

## Open questions

1. **OTel on Bun.** Which exporter and context-propagation path works on Bun 1.3.x without `async_hooks`; needs a spike before A is committed.
2. **Chain scope and anchoring cadence.** One chain per organisation (proposed) versus one global chain; where anchors are published (object storage bucket with versioning, or a signed daily digest emailed to compliance).
3. **Which Tasks dialect to serve.** 2026-07-28 only, or also 2025-11-25 for older hosts; the client matrix lists no Tasks support at all today, so the universal `operations.*` path is the only one that is guaranteed to work.
4. **Cost units for non-LLM upstreams.** Whether to price per call, per record or per upstream invoice line; needed before budgets mean anything.
5. **Retention and legal hold.** Default retention per organisation and whether erasure requests apply to evidence payloads only (proposed) or also to actor identifiers.
6. **Restate's BSL clause.** The additional use grant bars offering a "Public Restate Platform Service"; running Restate inside the hub is not that, but counsel should confirm if the hub is ever sold as a managed workflow service.
7. **pg-boss with Bun.SQL.** Issue #880 shows the Drizzle bun-sql driver double-encodes json params; confirm the `pg` driver path on Bun 1.3.1 in CI.
8. **Principal hashing salt.** Per deployment or per organisation; affects cross-organisation correlation in traces.
