# Sandboxes and code mode for a `run_code` capability: research and probes

Date: 2026-09-28. Host for probes: macOS 15.6 (Darwin 24.6.0), Apple Silicon arm64, Bun 1.3.1. Node v24.18.0 was used once, only to contrast the `isolated-vm` failure. Deno is not installed (P3 skipped; no system software was installed). Everything under `/Users/anthonyriera/code/answerable` was left untouched. Probe projects: `scratchpad/probes/{p1-quickjs,p1b-quickjs-0.31,p2-isolated-vm,p3-deno,p4-sebastianwessel}`; each `*.out.json` / `*.out.jsonl` file holds the raw numbers quoted below.

Marking: **VERIFIED** = read from the cited page or measured here; **INFERRED** = my reasoning or a third-party claim I could not confirm on the vendor's own page.

## 1. Summary and recommendation

**What the field does.** Anthropic (Nov 2025), Cloudflare (Sep 2025 onward) and the Hugging Face smolagents team all converge on the same shape: give the model *one* tool that runs a short program, expose the real tools to that program as typed function stubs, keep the raw data inside the execution environment, and only return what the program prints. Anthropic reports 150,000 -> 2,000 tokens (98.7%) on its worked example; Cloudflare reports 1.17 M -> ~1,000 tokens for the whole Cloudflare API and an 81% token cut in Code Mode; Anthropic's hosted programmatic tool calling reports -38% billed input tokens on a 75-tool benchmark. All three vendors say the execution environment must be sandboxed with resource limits and monitoring, and the two that run JavaScript (Cloudflare, and Anthropic's design post) reach the tools only through *bindings/handles* that RPC back to a privileged supervisor which holds the credentials. That is exactly the capability-handle model Answerable wants, and it is provider-neutral: the hub owns the sandbox, any model can write the program.

**v1 choice for Bun 1.3.1: quickjs-emscripten (RELEASE_SYNC, promise-returning host functions) inside a pool of Bun subprocesses, with capability calls RPC'd back to the hub over IPC.** Measured: 19-21 ms to load the engine cold, 0.4 ms per fresh runtime warm, 34 us per in-process capability call, 42 ms to spawn a pool slot, 1.1 ms median per run including one capability round trip over IPC, 3.2 ms for 20 parallel capability calls, 2 ms to kill a runaway slot. The guest has no `fetch`, `process`, `require`, `Bun`, timers or module loader at all (63 globals, all ECMAScript built-ins), so "no ambient network, no raw credentials" holds by construction; the subprocess itself is given no credentials, so nothing in its address space is worth reading.

Three defects in quickjs-emscripten 0.32.0 shape the design and must be engineered around (all reproduced here and all match open upstream issues):

1. `runtime.setMemoryLimit()` bounds a single allocation only. A 16 MB limit let the guest grow the WASM heap to 2,048 MB (the module maximum) before "out of memory" (issues #271, #255, #206; PR #207 open since 2024-09-15). **Fix that works:** instantiate the module with a capped `WebAssembly.Memory` via `newVariant(RELEASE_SYNC, { wasmMemory: new WebAssembly.Memory({ initial: 384, maximum: 1024 }) })`; the bomb then stops at 62.9 MB in 64-311 ms and the context stays usable. WASM memory never shrinks, so a run that hits the cap should retire its process.
2. The interrupt handler (`shouldInterruptAfterDeadline`) is polled per ~10,000 interpreter back-edges, not by time. A loop of native-heavy operations (`new Array(131072).fill(1)`, or asyncified host calls) overran a 2 s deadline by 15x-30x. **Fix that works:** the host enforces the deadline (per-call check inside every capability handle, call budget, and a hard `proc.kill()` from the parent, which took 2.03 ms). Bun `Worker.terminate()` did **not** stop a busy worker within 5 s, which is why the slot is a subprocess, not a worker thread.
3. Disposal bugs: the asyncify variant cannot dispose a runtime while an asyncified host function is still reachable (issue #261), and the sync variant asserts in `JS_FreeRuntime` when a host promise is still pending at dispose (issues #269/#235/#257 are the same assertion). **Fix that works:** avoid asyncify altogether (the promise pattern also allows `Promise.all`, which asyncify cannot), and tear down with a cancel flag, settle or reject every in-flight deferred, pump `executePendingJobs`, then dispose; and treat any dispose failure as "recycle the process".

**Upgrade path to stronger isolation** (each step keeps the same guest API, so agent programs do not change):

- v1.5: move the pool into its own container image with no secrets, a deny-all egress `NetworkPolicy`, `readOnlyRootFilesystem`, dropped capabilities, and a cgroup memory limit; optionally wrap the slot with bubblewrap (`--unshare-net`) as Anthropic does in Claude Code (needs user namespaces on the node; verify on Civo).
- v2: run that sandbox-runner Deployment under a gVisor `RuntimeClass` (`handler: runsc`) on K3s. K3s does not auto-detect `runsc`; add it through the containerd template (`config-v3.toml.tmpl`, or `config.toml.tmpl` on containerd 1.7) and a `RuntimeClass`. gVisor's systrap platform needs no KVM, so it should work on Civo VM nodes (INFERRED; Kata/Firecracker would need nested virtualisation, an open question).
- v3 (only if a hardware boundary or multi-language execution is required): microVMs (Kata + Firecracker/Cloud Hypervisor on nodes with KVM, or hosted E2B / Vercel Sandbox / Modal) or hosted V8 isolates (Cloudflare Dynamic Workers, ~ms start, 128 MB per isolate, $0.002 per unique worker per day plus request/CPU pricing). These add 100+ ms per run (microVMs) or a vendor dependency (Cloudflare), so they are not the v1 choice.

**Do not use:** `node:vm` (official: not a security mechanism), Bun `Worker` as a boundary (same process, shares I/O, terminate unreliable), `isolated-vm` (links the V8 C++ ABI; `dlopen` fails under Bun with 208 unresolved `v8::` symbols), asyncified QuickJS host functions (one suspended call at a time, ~1 ms per call, dispose bug), `@sebastianwessel/quickjs` as the boundary (it injects `fetch`, `process`, timers and 24 other globals; useful as a reference implementation only).

## 2. Verified facts with sources

### A1. Anthropic, "Code execution with MCP" (VERIFIED, https://www.anthropic.com/engineering/code-execution-with-mcp, 2025-11-04, Adam Jones and Conor Kelly)

- Tools are presented as a filesystem of TypeScript stubs (`servers/google-drive/getDocument.ts`, `servers/salesforce/updateRecord.ts`, `index.ts` per server). The model reads a definition only when it needs it (progressive disclosure); an optional `search_tools` with a detail level lets it find tools without loading them all.
- Filtering happens in the sandbox: a 10,000-row sheet is fetched and filtered in code so only five rows reach the model.
- Privacy-preserving tokenisation: the MCP client replaces PII with `[EMAIL_1]`, `[PHONE_1]`-style tokens before the model sees it and detokenises on the way out, so real values flow from Google Sheets to Salesforce without passing through the model.
- State persists as files; reusable code is saved under `./skills/` with a `SKILL.md`.
- Numbers: 150,000 tokens -> 2,000 tokens on the transcript-to-Salesforce example, a 98.7% reduction.
- Sandbox: the post says code execution "requires a secure execution environment with appropriate sandboxing, resource limits, and monitoring", and frames this as operational overhead that direct tool calls avoid; it links Anthropic's Claude Code sandboxing post for the primitives (bubblewrap on Linux, Seatbelt on macOS, network through an allow-listed proxy; VERIFIED https://www.anthropic.com/engineering/claude-code-sandboxing, which also reports "sandboxing safely reduces permission prompts by 84%" and points at `github.com/anthropic-experimental/sandbox-runtime`).

### A2. Hosted "code mode" products

**Anthropic programmatic tool calling** (VERIFIED, https://platform.claude.com/docs/en/agents-and-tools/tool-use/programmatic-tool-calling, GA):
- Needs the code execution tool `code_execution_20260120` or later; a tool becomes callable from code by `allowed_callers: ["code_execution_20260120"]`. Claude writes Python; tools appear as async Python functions returning strings (`asyncio.gather` allowed).
- Mechanics: code runs in Anthropic's container; a tool call pauses the run; the API returns a `tool_use` block with `caller: { type: "code_execution_20260120", tool_id }`; the client answers with a user message containing *only* `tool_result` blocks (text only) and must pass the `container` id back; intermediate results never enter the model context.
- Limits: a pending tool call times out after about 4 minutes (270 s `TimeoutError` in stderr); idle containers checkpoint after about 5 minutes; no container is reusable after 30 days; each Python cell has a 90 s wall-clock limit (`code_execution_20260521` tells the model so); MCP-connector tools, computer/browser toolsets, `strict: true` tools and schemas with recursive `$ref` cannot be called programmatically; each programmatic call counts against rate limits as a separate invocation.
- Security: the doc says "Do not rely on allowed_callers as a security boundary" and warns that tool results are strings that may be interpreted as code by the execution environment.
- Numbers: +11% on BrowseComp/DeepSearchQA with 24% fewer input tokens; -38% billed input tokens on a 75-tool project-management benchmark; +8% cost on tau2-bench (sequential single calls do not benefit); 20-40% savings for requests with 10-49 tools.
- Container and pricing (VERIFIED, https://platform.claude.com/docs/en/agents-and-tools/tool-use/code-execution-tool): 1 CPU, 5 GiB RAM, 5 GiB disk, "Internet access: Completely disabled for security"; free with web search/fetch; otherwise 1,550 free container-hours per organisation per month, then $0.05 per hour per container, 5-minute minimum; containers expire 30 days after creation; not ZDR-eligible.

**Anthropic tool search tool** (VERIFIED, https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool): variants `tool_search_tool_regex_20251119` (Python `re.search`, 200 chars max) and `tool_search_tool_bm25_20251119` (natural language, 500 chars); every tool is still sent in `tools`, deferred ones (`defer_loading: true`) are excluded from the prompt prefix (cache preserved) and expanded from `tool_reference` blocks when found; default 5 results, `limit` 1-10,000; up to 10,000 deferred tools; a typical multi-server setup costs ~55k tokens of definitions and tool search cuts that by over 85%; accuracy degrades past 30-50 tools; not metered separately; client-side custom search is possible by returning `tool_reference` blocks.

### A4. Threats

- **Lethal trifecta** (VERIFIED, https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/): private data + exposure to untrusted content + a way to communicate externally = exfiltration; remove one leg; detection that stops 95% of attacks is a failing grade in security terms; MCP's mix-and-match of tools makes accidental trifectas common; points to the six-pattern paper and DeepMind's CaMeL.
- **Design patterns paper** (VERIFIED, https://arxiv.org/abs/2506.08837, Beurer-Kellner et al., June 2025): Action-Selector, Plan-Then-Execute, LLM Map-Reduce, Dual LLM, Code-Then-Execute (the model writes a program before seeing untrusted data; the program runs on it), Context-Minimization. Core rule: once untrusted input is ingested it must be "impossible for that input to trigger any consequential actions".
- **Cloudflare security model** (VERIFIED, https://developers.cloudflare.com/workers/reference/security-model/): "V8 itself cannot defend against Spectre"; mitigations are a frozen `Date.now()` during execution, no concurrency or `SharedArrayBuffer` timers, dynamic process isolation of suspicious tenants, trust cordons, and a second layer of Linux namespaces plus seccomp with no filesystem syscalls and no direct network.
- **Unbounded consumption / denial of wallet** (VERIFIED, https://genai.owasp.org/llmrisk/llm102025-unbounded-consumption/): pay-per-use abuse imposes "unsustainable financial burdens on the provider"; mitigations are rate limits and quotas per source, timeouts and throttling of expensive operations, dynamic resource caps, and restricting the model's reach to network resources, internal services and APIs.
- **Vendor guidance**: Anthropic (above) says `allowed_callers` is not a security boundary and that tool results are strings that can carry executable content; Cloudflare's whole rationale is that bindings keep credentials in the supervisor; smolagents says no local interpreter is fully secure; Deno's docs say permissions are not enough against FFI/subprocess and recommend OS sandboxing; Anthropic's Claude Code post says both filesystem and network isolation are needed because either alone can be escaped.

## 5. Risks

1. **Engine trust.** quickjs-emscripten is a one-person hobby project, unaudited, with the memory-limit and disposal defects above open for months to years. Mitigate: pin the version, cap `WebAssembly.Memory`, run in a disposable subprocess, keep a fork-ready vendored build (PR #207 shows the malloc accounting fix), and re-run `p1-mem.ts`/`p1-leak.ts` on every upgrade.
2. **Exfiltration through capability handles (trifecta).** Any handle with an external effect (`mutations.prepare()` if it commits, notifications, anything writing where an attacker can read) is the third leg. Mitigate structurally: read handles and staged writes only inside the run; commits happen outside the sandbox after user confirmation (Plan-Then-Execute / Code-Then-Execute); taint values derived from untrusted content so they cannot become mutation arguments without approval (CaMeL); PII tokenisation as in Anthropic's design; every call audited with arguments and byte counts.
3. **Resource exhaustion.** Tight loops are caught by the interrupt handler, but native-heavy loops and pending promises are not; a process pool with a parent-side deadline and `kill()` is mandatory, plus per-run caps on calls, returned bytes and output size. Memory: hard cap the WASM memory; retire the process after any OOM because the heap never shrinks.
4. **Denial of wallet.** Each capability call is a database query or an upstream API call; enforce a per-run call budget (probed: 50), per-user and per-organisation rate limits on the hub, and cost-aware limits for expensive handles.
5. **Timing / Spectre in-process.** A WASM interpreter on one thread with only a millisecond `Date.now()` is a poor timer, and the sandbox process holds no secrets, so the realistic blast radius of a speculative read is the slot process itself. `SharedArrayBuffer` exists in the guest global list but there are no threads or `Atomics.wait`; still, consider freezing or coarsening `Date` in the guest (INFERRED; Cloudflare's model is the reference).
6. **Bun runtime maturity.** `Worker.terminate()` failed to stop a busy thread; IPC and subprocess behaviour under load on Linux were not tested here (only macOS).
7. **Prompt-injected code quality.** Tool results are strings the program will parse; never `eval` them in the guest, cap their size, and validate JSON on the host before returning it.

## 6. Open questions

1. Do Civo K3s nodes expose `/dev/kvm` (nested virtualisation)? Without it, Kata/Firecracker are out and gVisor (systrap) is the only stronger local boundary.
2. Are user namespaces available in the Civo node kernel/containerd setup (needed for bubblewrap `--unshare-net` inside a container)?
3. Should the hub transpile TypeScript to JavaScript with `Bun.Transpiler` before handing code to the guest (so the guest never sees TS), and should type stubs be generated from the capability registry the way Cloudflare and Anthropic generate them? (Not probed.)
4. How will per-user authority be minted: a capability manifest per run derived from the Answerable ID token scopes, with handles bound to the run id and expiring with it?
5. Upstream: will PR #207 land, or is a vendored QuickJS build with `malloc_usable_size` (and a fixed asyncify dispose order) worth maintaining?
6. Cloudflare Dynamic Workers: the pricing page indicates GA (billing from 2026-05-26) while the March blog said open beta; confirm status before considering v3.
7. Linux numbers: all measurements are macOS arm64; repeat `p1-cold.ts`, `p1-proc.ts` and `p1-worker.ts` in the production image.
