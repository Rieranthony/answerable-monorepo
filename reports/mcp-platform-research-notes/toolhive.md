## Summary

ToolHive is Stacklok's Apache-2.0, Go, Kubernetes-first platform for running third-party MCP servers as containers behind a per-server HTTP proxy that carries a middleware chain (OIDC/JWT auth, Cedar authorisation, audit, OpenTelemetry, tool filtering, rate limiting, token exchange). It has three run modes (CLI, desktop UI, operator with 13 CRDs), a Virtual MCP Server (vMCP) that aggregates a group of backends into one endpoint with per-user Cedar filtering and composite/Starlark workflows, and a registry built on the upstream MCP `server.json` format with Sigstore provenance. It is well engineered and unusually well documented, but moves very fast (twelve releases in the last month, 0.x, breaking CRD changes stepped through v0.15–v0.23) and several headline features are narrower than they read: permission profiles and network isolation are enforced only on local Docker (the Kubernetes runtime has a `TODO`), the embedded authorisation server is Kubernetes-only, and vMCP carries hard session caps and open memory/health bugs.

For Answerable: ToolHive would add value only for third-party MCP workloads (containers or SaaS remotes needing per-user upstream OAuth). Fronting the first-party Bun/Hono MCPs that already verify Answerable ID tokens would duplicate token validation and RFC 9728 metadata, add a pod and a hop per server, and give back mainly Cedar argument-level policies and audit JSON. None of the Toolbox draft's distinctive semantics (capability catalogue with stable identities, prepared mutations, commit receipts, per-mutation approval) exist in ToolHive; only "ToolHive composite" maps onto a real feature (composite tools/code mode), and those are request-scoped DAGs without preview/commit.

### 2. Runtime model
- Five ways to run (VERIFIED docs/arch/00): registry name, image, protocol scheme (`uvx://`, `npx://`, `go://` built into images at run time), exported RunConfig (`v0.1.0` schema), remote URL.
- Local: `thv run` forks a detached proxy; runtime auto-detected Podman → Docker (Desktop, Rancher Desktop, OrbStack) → Colima (VERIFIED docs/arch/01). Containers run `--cap-drop ALL`, `no-new-privileges` (docs/arch/05).
- Transports (VERIFIED docs/arch/00, 05): container side `stdio` | `sse` | `streamable-http`. stdio is bridged HTTP↔JSON-RPC over stdin/stdout and exposed as SSE or streamable-http (`proxy_mode`); SSE/streamable are transparently reverse-proxied through the same middleware chain. Defaults 8 MiB body, 30 s read timeout.
- Kubernetes (VERIFIED docs/arch/01, 09): operator → proxy-runner Deployment (1 replica), ClusterIP Service with `SessionAffinity: ClientIP`, ConfigMap RunConfig, optional ServiceAccount; the proxy-runner creates and watches the MCP StatefulSet through the in-cluster API. No Docker socket, no DinD. stdio forces a single proxy replica. `readOnlyRootFilesystem: true` on the `mcp` container by default and a platform security context (runAsNonRoot, seccomp) (VERIFIED https://docs.stacklok.com/toolhive/guides-k8s/run-mcp-k8s; pkg/container/kubernetes/client.go:1358-1399).
- Middleware types (VERIFIED docs/arch/05): auth, tokenexchange, upstreamswap, awssts, obo, mcp-parser, tool-filter, tool-call-filter, ratelimit, usagemetrics, telemetry, authorization, audit, recovery, header-forward, validating-webhook, mutating-webhook.
- Permission profiles (VERIFIED docs/arch/05): `read`/`write` mounts, `network.outbound.{insecure_allow_all, allow_host, allow_port}`, `network.inbound` ("limited implementation"), `privileged`; built-ins `none`, `network`; the global default is `network` (full egress). MCPServer CRD accepts `permissionProfile{type: builtin|configmap, name, key}` and the controller mounts the ConfigMap (mcpserver_controller.go:1380), but the Kubernetes runtime ignores it: `pkg/container/kubernetes/client.go:368` takes `_ *permissions.Profile` with the comment "TODO: Implement permission profile support for Kubernetes". VERIFIED. Egress allow-lists and mount rules are therefore local-only today.
- Network isolation (VERIFIED docs/arch/05, 15): `--isolate-network` builds a per-workload `internal=true` Docker network plus Squid egress (:3128 via HTTP(S)_PROXY), Squid ingress and dnsmasq sidecars; bridge mode only (#5775); non-HTTP TCP cannot pass (#758). Envoy backend "Experimental" via `TOOLHIVE_NETWORK_PROXY=envoy`. Doc 15 states isolation "is a local-Docker feature only"; the K8s guide tells you to write NetworkPolicy yourself; `grep NetworkPolicy` over cmd/thv-operator finds no generation code. Doc 05's claim that K8s generates network policies from profiles is wrong.
- Secrets (VERIFIED docs/arch/04): local providers `encrypted` (AES-256-GCM, Argon2id, keyring password), `1password` (read-only), `environment` (`TOOLHIVE_SECRET_*`); referenced as `name,target=ENV`, never serialised. Kubernetes uses native Secrets via `spec.secrets[{name,key,targetEnvName}]`; Vault/External Secrets through pod annotations.
- Workload states (VERIFIED docs/arch/08): starting, running, stopping, stopped, removing, error, unhealthy, unauthenticated, auth_retrying, policy_stopped, unknown. `thv upgrade check/apply` re-verifies provenance and pulls before recreating; no rollback.

### 3. Gateway and auth
- Incoming (VERIFIED https://docs.stacklok.com/toolhive/concepts/auth-framework, docs/arch/09): JWT via JWKS or opaque via RFC 7662 introspection (auto-detect); named providers Google, GitHub, Entra ID, Okta, Auth0, Kubernetes service accounts. `MCPOIDCConfig` (`kubernetesServiceAccount` | `inline`) referenced through `oidcConfigRef{name, audience (required), scopes, resourceUrl}`; the proxy serves `/.well-known/oauth-protected-resource` (RFC 9728) (VERIFIED docs/observability.md route table; pkg/transport/proxy/*/`oauth-protected-resource`). Open bug #6705: introspection drops custom claims Cedar needs.
- Embedded authorisation server (VERIFIED https://docs.stacklok.com/toolhive/concepts/embedded-auth-server, docs/arch/09, 17): OAuth 2.0 AS inside the proxy (`MCPExternalAuthConfig` type `embeddedAuthServer`, attached by `authServerRef` on MCPServer/MCPRemoteProxy, `spec.authServerConfig` on VirtualMCPServer). Clients identified by CIMD (HTTPS URL as client_id) or DCR `/oauth/register` (confidential DCR rejected, #5321). Federates to upstream OIDC/OAuth2 providers (examples GitHub, Google Workspace, Atlassian); upstream access/refresh/ID tokens stored per session (`tsid` claim); `upstreamswap` replaces the Authorization header with the user's upstream token on the backend hop (bug #6681 in v0.49.0 for MCPRemoteProxy). Storage in-memory (lost on restart) or Redis Sentinel. Docs: Kubernetes-only. Inbound RFC 8693 with delegate clients, `trustedIssuers` (`allowedActors`, CEL `actorMatcher`, `may_act`), RFC 7523 JWT-bearer, `private_key_jwt` DCR, token-only mode; no per-`jti` replay tracking; no DeleteClient; SPIFFE fields exist but any non-empty config is rejected at validation ("not yet a deployable feature"). No consent screen is described anywhere.
- Outgoing (VERIFIED cmd/thv-operator/api/v1beta1/mcpexternalauthconfig_types.go): `MCPExternalAuthConfigSpec.type` ∈ tokenExchange {tokenUrl, clientId, clientSecretRef, audience, scopes, subjectTokenType, externalTokenHeaderName, subjectProviderName} | headerInjection | bearerToken | embeddedAuthServer | awsSts | upstreamInject | obo | xaa. Concept page frames: static credentials, RFC 8693 (same IdP or federated STS), embedded AS.
- Remote HTTP MCP servers (not containers): yes. (a) `MCPRemoteProxy` (VERIFIED mcpremoteproxy_types.go: remoteUrl, allowPrivateEndpoint, proxyPort, transport sse|streamable-http, oidcConfigRef, externalAuthConfigRef, authServerRef, headerForward, authzConfig/authzConfigRef, audit, toolConfigRef, telemetryConfigRef, trustProxyHeaders, endpointPrefix, groupRef, sessionAffinity, replicas, sessionStorage) — one pod with the full chain; private-range URLs rejected unless `allowPrivateEndpoint`; with no auth source it forwards "under a synthetic local-user identity"; the remote must accept the exchanged token's audience, there is no audience translation (VERIFIED https://docs.stacklok.com/toolhive/guides-k8s/remote-mcp-proxy). (b) `MCPServerEntry` (remoteUrl, transport, groupRef, externalAuthConfigRef, headerForward, caBundleRef) — no pods, vMCP-only. (c) CLI `thv run <URL>` with RFC 9728/8414/7591/8707 + PKCE discovery (VERIFIED docs/remote-mcp-authentication.md; audience validation "Partial").
- Authorisation (VERIFIED docs/authz.md @61aaf42, https://docs.stacklok.com/toolhive/concepts/cedar-policies): authorizers `cedarv1` (default) and `httpv1` (external PDP, PORC JSON `POST /decision` → `{"allow":bool}`, claim mapping `mpe`|`standard`). Config `{version:"1.0", type:"cedarv1", cedar:{policies:[...], entities_json:"[]"}}` via `--authz-config`, `MCPAuthzConfig`, or inline/configMap `authzConfig`. Model: principal `Client::<sub>`; actions `call_tool`, `get_prompt`, `read_resource`, `get_skill`; resources `Tool::"x"`, `Prompt::"x"`, `Resource::"<exact URI>"`, `Skill::"<uri>"`; JWT claims as `claim_*` on principal and context, `THVGroup::"g"` entities from group/role claims (`group_claim_name`, `role_claim_name`), args as `arg_*` (objects/arrays only as `arg_<k>_present`), `thv_claim_source` provenance; list methods always allowed but filtered to what the caller may call; forbid > permit > default deny; a denied call is HTTP 403 with a kind-only message. Examples: `permit(principal, action == Action::"call_tool", resource == Tool::"weather");` · `permit(principal, action == Action::"call_tool", resource) when { principal.claim_roles.contains("admin") };` · `permit(principal in THVGroup::"data-team", action == Action::"call_tool", resource in MCP::"analytics-server");` · `… resource == Tool::"calculator") when { resource.arg_operation == "add" || resource.arg_operation == "subtract" };`. Every POST needs `Content-Type: application/json`; opaque upstream tokens deny claim-based rules. Open: #4048 (list vs call not distinguishable in authz/audit), #5483 (no backend-scoped Cedar in vMCP).
- Tool filtering/renaming (VERIFIED toolconfig_types.go; https://docs.stacklok.com/toolhive/concepts/tool-optimization): `MCPToolConfig.spec.toolsFilter []` (allow-list), `toolsOverride map[original]{name, description, annotations{title, readOnlyHint, destructiveHint, idempotentHint, openWorldHint}}`; filters match post-override names; calls translated back. CLI `--tools`, `--tools-override`.
- Audit (VERIFIED pkg/audit/event.go, config.go @61aaf42; https://docs.stacklok.com/toolhive/guides-vmcp/audit-logging): custom JSON on a proprietary `AUDIT` slog level to stdout or `logFile` (0600). Event: `auditId`, `type` (e.g. `mcp_tool_call`, `vmcp_workflow_started/failed/step_completed`), `loggedAt`, `outcome` ∈ success|failure|error|denied|application_error, `component`, `source{type,value,extra{user_agent}}`, `subjects{user,user_id,client_name,client_version}`, `target{endpoint,method,type,name}`, `metadata.extra{duration_ms,transport,backend_name}`, optional `data{request,response}`, `delegation` chain. Config: enabled, component, eventTypes, excludeEventTypes, includeRequestData, includeResponseData, detectApplicationErrors, maxDataSize, maxDelegationDepth, logFile. Not CloudEvents/OCSF. Bug #6720.
- OpenTelemetry (VERIFIED docs/observability.md): flags `--otel-endpoint`, `--otel-tracing-enabled`, `--otel-metrics-enabled`, `--otel-sampling-rate` (CLI 0.1, CRD 0.05), `--otel-service-name`, `--otel-headers`, `--otel-insecure`, `--otel-enable-prometheus-metrics-path`, `--otel-env-vars`, `--otel-custom-attributes`, `--otel-use-legacy-attributes`; K8s `MCPTelemetryConfig` + `telemetryConfigRef{name, serviceName}`. Metrics `toolhive_mcp_requests`, `toolhive_mcp_request_duration`, `mcp.server.operation.duration` (OTel MCP semconv), `toolhive_mcp_tool_calls`, `toolhive_mcp_active_connections`, `toolhive_rate_limit_*`. Spans `{mcp.method.name} {target}` (e.g. `tools/call fetch`) with `mcp.method.name`, `mcp.server.name`, `mcp.session.id`, `gen_ai.tool.name`, `gen_ai.tool.call.arguments` (sanitised, secrets redacted, 200 chars), `mcp.client.name`; W3C context from headers or `params._meta.traceparent` (`_meta` wins). `/metrics` unauthenticated on diagnostics port 9464 (also on the transport port during migration, #6384).

### 4. Virtual MCP Server (vMCP)
- Status: no GA/beta/experimental label on the concept page, guides, README or arch docs (grep for experimental/preview/alpha across README, docs/arch/10, 12, 14 and the operator README found only unrelated CLI `--preview` flags). It ships as a CRD, `thv vmcp serve`, the `vmcp` image and 16 guide pages. Only per-feature caveats exist (below). INFERRED: treat as "GA-by-shipping" with beta-grade sharp edges.
- Composition (VERIFIED docs/arch/10 @61aaf42): `VirtualMCPServer.spec.groupRef` → all MCPServer/MCPRemoteProxy/MCPServerEntry members (static list or dynamic BackendReconciler) are queried in parallel per session (15 s timeout → 504; failure → 503), conflicts resolved, merged into a routing table; health monitor (healthy/degraded/unhealthy/unauthenticated/unknown) filters backends and now resyncs live sessions (#5786).
- Name conflicts: tools `prefix` (default `{workload}_`), `priority`, `manual`; prompts prefixed by default; resource URIs never rewritten (first backend in sorted-ID order wins). Renamed tools are mapped back on call. Doc admits post-prefix tool collisions "pick a nondeterministic winner" (map iteration).
- Filtering: `aggregation.tools[].{excludeAll, filter}`, `excludeAllTools`, `defaultToolVisibility: deny` control advertising only; hidden tools remain routable for composites; Cedar does per-identity admission.
- Composite tools (VERIFIED pkg/vmcp/config/config.go `CompositeToolConfig`/`WorkflowStepConfig`; https://docs.stacklok.com/toolhive/guides-vmcp/composite-tools): `{name, description, parameters (JSON schema), timeout, steps[], output{properties{type,value template,default,description}}, annotations}`; step `{id, type: tool|elicitation|forEach, tool, arguments (Go templates: {{.params.x}}, {{.steps.id.output.field}}, {{.forEach.item}}, fromJson/json/quote/index), condition, dependsOn[], onError{action: abort|continue|retry, retryCount}, defaultResults, message+schema+onDecline/onCancel (elicitation), collection+itemVar+maxParallel(≤50)+maxIterations(≤1000)+step (forEach)}`. DAG, parallel where independent, no nested composites, no general loops, elicitation needs a client that implements `elicitation/create`. Annotations derived (readOnly = AND, destructive/openWorld = OR) then merged; a composite claiming to be safer than its steps is dropped. CRD `VirtualMCPCompositeToolDefinition` inlines this config and is referenced by `spec.config.compositeToolRefs`. Semantics are request-scoped orchestration: no preview/commit, no receipts, no persistence (durable work is explicitly out of scope).
- Code mode (VERIFIED https://docs.stacklok.com/toolhive/guides-vmcp/code-mode, docs/arch/10): `spec.config.codeMode.enabled`; tool `execute_tool_script{script, data}` runs Starlark server-side; limits stepLimit 100,000, parallelMaxConcurrency 10, toolCallTimeout 30 s, wall clock 1 min; inner calls re-enter Cedar under their real names; not labelled experimental.
- Two-boundary auth (VERIFIED virtualmcpserver_types.go, docs/arch/10): `incomingAuth{type, oidcConfigRef, authzConfig|authzConfigRef}` (OIDC | anonymous | local); `outgoingAuth{source, default, backends{name: {type, externalAuthConfigRef}}}` — per-backend token exchange, header injection or unauthenticated; exchanged tokens cached. Per-user upstream tokens via the embedded AS (`authServerConfig`); a token-only vMCP cannot use Cedar.
- Per-user authorisation: Cedar in the core admission seam filters lists and denies calls with HTTP 403 + JSON-RPC 403 and a kind-only message; capability cache keyed by identity + forwarded headers + backend set.
- Protocol revisions (VERIFIED docs/arch/10): serves Legacy 2025-11-25 (sessions) and Modern 2026-07-28 (stateless); Modern disabled when the optimizer is on; elicitation/sampling only Legacy↔Legacy; Modern clients trigger an uncached backend fan-out per request (#5761); `resources/subscribe` and `subscriptions/listen` ack-only; `list_changed` Legacy-only.
- Scale (VERIFIED docs/arch/13): 1,000 sessions per pod (not tunable via CRD), 30 min session TTL (not CRD-exposed), Redis sliding TTL for multi-replica, `(iss,sub)` binding stored in plaintext in Redis, fd pressure, `sessionAffinity: ClientIP` unreliable behind NAT ("prefer vertical scaling"), in-flight calls lost on pod death. Open #5860: memory grows 2–3× over ~24 h; #6687: health probe hangs on `server/discover` (v0.49.0).
- Optimizer: Tier 1 FTS5 keyword, Tier 2 semantic via TEI/`EmbeddingServer`; exposes `find_tool`/`call_tool` (README claims up to 85% token savings).

### 6. Operational footprint for K3s on Civo (Bun/Hono first-party services)
- Install (VERIFIED https://docs.stacklok.com/toolhive/guides-k8s/deploy-operator; deploy/charts/*): `helm upgrade --install toolhive-operator-crds oci://ghcr.io/stacklok/toolhive/toolhive-operator-crds -n toolhive-system --create-namespace` then the `toolhive-operator` chart; Kubernetes current + two previous minors; Helm ≥ 3.10; no cert-manager; no admission webhooks (chart templates contain none; no `SetupWebhookWithManager` in the operator; validation is 77 CEL `XValidation` rules in v1beta1 types); ClusterRole includes create/delete on StatefulSets; storage-version migrator job in cluster mode; namespace mode via `operator.rbac.scope: namespace` + `allowedNamespaces`; images `ghcr.io/stacklok/toolhive/{operator,proxyrunner,vmcp}:v0.51.4`; `operator.defaultImagePullSecrets` and `imageDiscovery` for air-gap; arm64 supported (#3942 closed). Operator pod requests 10m/64Mi, limits 500m/128Mi, 1 replica with leader election.
- Per workload (INFERRED from docs/arch/09 tables): MCPServer = 2 pods + Service + ConfigMap; MCPRemoteProxy = 1 pod; MCPServerEntry = 0; VirtualMCPServer = 1+ pods (+ Redis for HA, + EmbeddingServer StatefulSet for semantic search); MCPRegistry = 1 pod + PostgreSQL. Ingress/HTTPRoute is yours to write (operator creates plain Services). No Docker-in-cluster.
- Coexistence with first-party HTTP MCPs that already do OAuth against Answerable ID (INFERRED from §3): fronting them with `MCPRemoteProxy` gives Cedar argument-level policies, audit JSON, OTel spans, tool filtering and rate limiting, but (a) duplicates JWT validation and RFC 9728 metadata (the proxy advertises its own `resourceUrl`; the MCP behind it advertises another), (b) requires ID to speak RFC 8693 for token exchange or falls back to static bearer/header injection or the unauthenticated "synthetic local-user" passthrough, (c) adds a pod, a hop and a 2 h/30 min session layer per server, (d) the audience must match on both sides (no translation). The value case is third-party MCP workloads (containers with tool filtering, or SaaS remotes needing per-user upstream OAuth via the embedded AS), and possibly vMCP as a single endpoint — but vMCP's per-user model assumes ToolHive is the authorisation server, competing with ID (open #5383 asks for a linked-account model).
- Upgrade cadence risk (VERIFIED §1 releases; https://docs.stacklok.com/toolhive/guides-k8s/migrate-to-v1beta1): chart version = app version; v1beta1 graduated at v0.23.0 after breaking changes in v0.15–v0.21 (removed `spec.port`, `spec.targetPort`, inline `tools`, plaintext `clientSecret`, inline `oidcConfig`/`telemetry`; renamed `remoteURL`→`remoteUrl`, phase `Running`→`Ready`; `groupRef` became a struct; `MCPRegistry` flattened to `configYAML`), with the instruction to step through each breaking version; v1alpha1 removal has no date. Expect to pin versions and rehearse upgrades in kind (repo ships `docs/kind`).
- K3s specifics: no issues mention K3s; kind is the tested local cluster. K3s's bundled network-policy controller must be on for the NetworkPolicy advice to bite (INFERRED, not tested).

### 7. Gaps against Stephen's Toolbox draft (VERIFIED docs/drafts/2026-09-27-stephen-toolbox.md and -mcp-design-standard.md, read-only)
The draft places ToolHive under Toolbox as "Gateway / Runtime / Registry / Isolation", lists "ToolHive composite" as one of three composition mechanisms, and (§61 of the design standard) wants a future capability catalogue to derive semantics from an MCP with little bespoke integration. Against ToolHive as it is:
- Capability catalogue semantics: ToolHive's catalogue is server-level (`server.json` + `_meta` tier/tags/tools/permissions). Tool identity is the backend's tool name (optionally renamed per proxy/vMCP); there is no stable capability identity that survives implementation changes, no query/mutate/subscribe classification beyond MCP tool annotations (`readOnlyHint`, `destructiveHint`, which MCPToolConfig can override), and no schema registry for tools. Toolbox must own these.
- Prepared mutations / commit / receipts: absent. Composite tools and code mode execute immediately; the only human-in-the-loop primitive is an `elicitation` step (works for Legacy clients only, aborts on unsupported clients). No idempotent commit handles, no stale-state checks, no receipts. `thv upgrade apply` has a prepare-then-apply shape but only for ToolHive's own workloads.
- Per-user consent: the embedded AS federates to upstream IdPs and stores per-user tokens, but the docs describe no consent screen or per-tool consent; Cedar is operator-authored policy, not user consent. Consent stays with Answerable ID.
- "ToolHive composite" as predefined deterministic MCP composition: exists (DAG steps, parallelism, retries, `forEach`), but it is vMCP-only, request-scoped (default timeouts, 1 min wall clock for code mode), and the composite's Cedar identity is just the advertised tool name; no organisation dimension.
- Isolation: only local Docker; in Kubernetes the profile is a TODO, so "Isolation" in the draft's ToolHive box is not delivered on K3s.
- Authority model: Cedar principals are `sub` plus claims; organisations exist only as claims/groups you map (`THVGroup`), not as a first-class tenant. Multi-org separation would be per-namespace CRs or claim-conditioned policies (INFERRED).
- Registry ingestion: the upstream `server.json` + publisher-provided `_meta` namespace is a reasonable input to a future Answerable catalogue (design standard §61), but ToolHive does not sign the registry itself; provenance is per image.

## Architecture notes

### Request path, Kubernetes MCPServer (VERIFIED docs/arch/09)
```
client ──HTTP──▶ Service (ClusterIP, ClientIP affinity)
                 └─▶ proxy-runner pod (thv-proxyrunner)
                       recovery → auth (JWT/introspection) → mcp-parser → tool-filter
                       → ratelimit → telemetry → authorization (Cedar) → audit
                       → [tokenexchange | upstreamswap | header inject]
                       └─▶ StatefulSet pod (MCP server: stdio | sse | streamable-http)
operator: watches CRDs, owns Deployment/Service/ConfigMap; proxy-runner owns the StatefulSet
```

### vMCP (VERIFIED docs/arch/10)
```
client ─▶ vMCP pod ─ incoming auth (OIDC | anonymous | embedded AS)
            │  discovery per session ─▶ aggregator (prefix|priority|manual) ─▶ routing table
            │  Cedar admission seam: filters lists, denies calls (403, kind-only)
            │  composite tools (DAG) · code mode (Starlark) · optimizer (find_tool/call_tool)
            └─ outgoing auth per backend (token exchange | headers | none | per-user upstream token)
                 ├─▶ MCPServer  ├─▶ MCPRemoteProxy  └─▶ MCPServerEntry (direct URL)
```

### CRD reference graph (VERIFIED docs/arch/09)
- MCPServer / MCPRemoteProxy → oidcConfigRef (MCPOIDCConfig), telemetryConfigRef, toolConfigRef, externalAuthConfigRef and authServerRef (MCPExternalAuthConfig), authzConfigRef (MCPAuthzConfig), webhookConfigRef (MCPServer only), groupRef (MCPGroup).
- MCPServerEntry → groupRef, externalAuthConfigRef, caBundleRef (ConfigMap).
- VirtualMCPServer → groupRef, incomingAuth.oidcConfigRef, telemetryConfigRef, embeddingServerRef, config.compositeToolRefs (VirtualMCPCompositeToolDefinition), authServerConfig (inline embedded AS).
- Referenced config CRDs carry `configHash` in status; deletion blocked by finalizer while referenced.

## Patterns worth adopting (for Answerable, independent of running ToolHive)
- Shared identity-provider config referenced per server with a mandatory per-server `audience` and explicit `resourceUrl` for RFC 9728 metadata; the audience is the anti-replay boundary (matches ID's per-MCP audience decision).
- Lists filtered by call authorisation, denials returned without an enumeration oracle (uniform 403, kind-only message). Our scope-driven visibility already does the first half; adopt the uniform-denial rule.
- Conservative annotation derivation for composites: readOnly = AND, destructive/openWorld = OR, and refuse to advertise a composite that claims to be safer than its steps. Directly reusable for Toolbox capability classification and prepared-mutation gating.
- Audit event envelope (`type`, `outcome` incl. `denied`, `subjects`, `source`, `target`, `metadata.extra.backend_name`, optional bounded `data`) plus OTel MCP semconv span naming (`tools/call <tool>`, `gen_ai.tool.name`, sanitised arguments) and `_meta.traceparent` propagation — a sensible baseline for Toolbox evidence.
- Registry as upstream `server.json` plus a namespaced publisher-provided `_meta` extension, with per-image Sigstore provenance fields; good input format for design-standard §61 catalogue ingestion.
- Separating "advertising" (filters) from "authorisation" (policy), and caching aggregated capabilities per identity + forwarded headers + backend set.
- Serving `/metrics` on a separate diagnostics port so NetworkPolicy can scope it; scoping external routes to exact MCP paths rather than `/`.
- Verify-then-pull-before-destroy ordering in `thv upgrade apply` and the explicit "no automatic rollback" statement — the shape prepared mutations want, even though ToolHive applies it only to itself.

## Risks / anti-patterns
- Velocity and API churn: twelve releases a month, 0.x, a history of breaking CRD changes with a "step through each version" instruction, chart pinned to app version, and docs that already drift (deploy page says 12 CRDs, doc 05 claims K8s network policies, REGISTRY.md documents a non-existent annotation).
- Security features narrower than marketed on Kubernetes: permission profiles and network isolation are local-Docker only (runtime TODO); on K3s you get pod security context and readOnlyRootFilesystem, and must write NetworkPolicy yourself.
- Embedded AS: Kubernetes-only, in-memory sessions unless Redis Sentinel, confidential DCR rejected, v0.49.0 regression forwarding the wrong token, no consent UX, PII in Redis in plaintext. Running it means a second authorisation server next to Answerable ID.
- vMCP operational limits: 1,000 sessions per pod, memory growth bug, health-probe hang, nondeterministic tool winners after prefixing, Modern-client elicitation impossible, uncached per-request fan-out for Modern clients (DoS surface when anonymous), ClientIP affinity behind NAT.
- Cedar's principal is a bare `sub`; organisations are not first-class; policies are static text in CRDs/ConfigMaps — awkward for per-organisation entitlements that ID already computes.
- Per-server pod pairs and a session layer in front of first-party services add cost and a second place for audience/metadata to diverge; `MCPRemoteProxy` rejects private endpoints unless opted in and cannot translate audiences.
- Default `--image-verification warn` and a global default permission profile of `network` are permissive defaults.
- Missing CORS on the proxy (#4297), introspection dropping custom claims (#6705), audit outcome bug (#6720).

## Open questions
- Would Answerable run the operator at all, or only borrow patterns? The first-party MCP path gains little; third-party MCP workloads are the only clear use.
- Can `MCPRemoteProxy` pass a client's original ID bearer token unchanged to a first-party MCP while still validating it? Header-forward middleware exists, but the documented outgoing strategies do not include authenticated passthrough, and #6394 shows Authorization being blocked in vMCP passthrough. Needs a test.
- Does the embedded AS show any per-user consent? Nothing in docs; unverified.
- Per-organisation isolation model in Cedar/vMCP (namespaces vs claims) — untested.
- K3s behaviour (network-policy controller, ServiceLB, Traefik ingress with SSE) — no upstream evidence either way.
- Stacklok Enterprise boundary and pricing (https://docs.stacklok.com/toolhive/enterprise not fetched).
