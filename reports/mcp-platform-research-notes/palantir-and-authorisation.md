# Palantir model, agent tool governance and authorisation engines: research notes

Date: 2026-09-28. Status: COMPLETE. Scope: Palantir Foundry/AIP model, enterprise AI tool governance, identity-for-agents products, authorisation engines, constrained-authorisation standards, Claude Code permission model, with transferable patterns for Answerable ID and the MCP base. Nothing under /Users/anthonyriera/code/answerable was modified; the installed Better Auth sources were only read.

Marking convention: **VERIFIED (URL)** means the fact was read on the linked page during this research. **INFERRED** means a conclusion drawn from verified facts or from general knowledge that was not checked against a source today.

## Summary

- **Palantir's model, reduced to its mechanics:** a mutation is a typed *action type* (parameters, rules, submission criteria, side effects) evaluated server-side at submission with the submitting user's identity; read authority comes from data-level policy (markings, restricted views, object policies) while write authority comes from the action type itself (actions-only edit mode needs only Read on the objects); every application token is a runtime intersection of the user's permissions, the application's declared resource and operation restrictions, and the request; every successful action produces a linked, queryable action-log object; Checkpoints (justification) and Approvals (request/grant with persisted state) are reusable governance primitives across 60+ interactions. The agent layer (AIP Logic, Chatbot Studio, formerly Agent Studio) inherits all of this and adds two switches: per-tool "confirm before applying" and "stage edits for human review". The docs are explicit that read filtering never protects a model's output.
- **Enterprise AI products** (Claude, ChatGPT, Copilot Studio/Entra, Glean, Agentforce) all separate catalogue, audience and action policy; they gate by role or IdP group rather than per user; ChatGPT splits read and write action sets and needs an explicit policy for newly discovered actions; Entra attaches per-operation scopes to an agent identity at publish and re-validates at execution; Glean evaluates CEL policies on both tool inputs and outputs and makes auto-confirmation a two-tier opt-in; org-level "ask" in Claude cannot be overridden by client rules.
- **Identity for agents** has converged on ID-JAG (IETF draft -04, May 2026), productised as Okta XAA and embedded in MCP as the Enterprise-Managed Authorization extension; Answerable ID's natural role is the resource authorisation server that accepts such assertions. CIBA is the standard shape for out-of-band human approval, RFC 9396 `authorization_details` the standard carrier for a constrained grant, RFC 8693 the substrate for all of it. Installed Better Auth 1.7.2 supports none of these grants (only device code), so each is bespoke code in Answerable ID.
- **Authorisation engines:** the relational tables already in Answerable ID plus a computed effective-grants view are the right store; no ReBAC server is justified by a shallow org/group/capability graph; Cedar via `@cedar-policy/cedar-wasm` (4.13.0) is the only zero-operations upgrade if constraint expressions outgrow JSON.
- **Commit token for prepared mutations:** keep an immutable server-side intent record with an argument hash as the source of truth; represent it as a short-lived JWT with `authorization_details` only when it must cross a service boundary; do not adopt Biscuit or macaroons. AP2 v0.2's open/closed Checkout Mandate (SD-JWT with `checkout_hash` and `cnf` key binding) is the closest external analogue.
- **Claude Code** decides with deny > ask > allow rules matched first-hit with no specificity override, a mode for the remainder, hooks that can veto before rules, and server-side markers that can force but never grant approval; MCP tool annotations are untrusted by spec and are not used for auto-approval.

## 1. Palantir Foundry / AIP model

### 1.1 Ontology and action types

- **Action type = governed mutation.** VERIFIED (https://www.palantir.com/docs/foundry/action-types/overview): an action type is the definition of a set of edits to objects, property values and links that a user can take at once, plus the side effects that fire on submission. The overview's own example: an `Assign Employee` action changes a role property, creates a manager link and notifies people. Changes land in the object type's writeback dataset and are visible everywhere immediately.
- **Components of an action type.** VERIFIED (same page): parameters (typed, user-facing inputs with defaults and dropdown filtering), rules (the edits), submission criteria, side effects (notifications, webhooks, scheduled builds, media uploads), function-backed actions (custom logic), batched execution, inline edits, action logging and monitoring, undo/revert, and Marketplace packaging.
- **Submission criteria = declarative "may this be submitted" gate.** VERIFIED (https://www.palantir.com/docs/foundry/action-types/submission-criteria/): submission criteria are the conditions that decide whether an action can be submitted. Three condition templates: **Current user** (user id, direct or inherited group membership, IdP attributes), **Parameter** (comparisons on the submitted parameters), **Execution context** (is this a Scenario or a real submission). Operators include is / is not / matches / less than / includes / includes any / each is; conditions nest with all / any / none. Every root condition carries a custom failure message shown to the end user in every Foundry app. Criteria can be dry-run against sample parameters inside Ontology Manager.
- **Warning on negative group checks.** VERIFIED (same page): the docs warn against `NOT` conditions on group or organisation membership because a *scoped token* may not carry those attributes and the negation then grants unintended access. INFERRED: this is exactly the trap Answerable would hit if a tool token omits group claims; deny-by-absence must never become allow-by-absence.
- **Who may apply an action.** VERIFIED (https://www.palantir.com/docs/foundry/action-types/permissions/): the submitter must (1) be able to view the edited object and link types and their datasources, (2) pass submission criteria, (3) hold edit rights according to the object type's edit mode. In the recommended **actions-only** edit mode a user only needs *Read* on the objects being edited; the action type carries the write authority. Open editing needs dataset-level Edit. Row and column controls filter what the action can read but do not extend to the write; pair with markings or CBAC for downstream protection. If the user lacks rights on the action log object type, the action fails at submission. Notification recipients only receive object data they can see.
- **Action log = append-only audit as ontology objects.** VERIFIED (https://www.palantir.com/docs/foundry/action-types/action-log/): each successful submission creates one `[Log] <action type>` object, linked to every edited object, recording action RID, action type RID and version, timestamp, user, edited object primary keys, webhook and notification ids, scenario RID and revert provenance; optionally parameter values and unedited context properties. Failures are not recorded. The page frames the log as answering what decision was made, by whom, when and in what context. An object type can be configured to only allow actions that have an action log.

### 1.2 Functions, AIP Logic, AIP Evals

- **AIP Logic.** VERIFIED (https://www.palantir.com/docs/foundry/logic/overview/): a no-code environment for building, testing and releasing LLM-powered functions. A Logic function takes inputs (objects or strings), can return objects or strings, or make Ontology edits. Edits can be applied automatically or *staged for human review*. Access controls filter what the model can read on the user's behalf; the model never sees data the user cannot read. Explicit limitation: those controls do not extend to the model's output or the edits it composes. AIP Evals is integrated and includes a results analyser that groups failing cases by root cause.
- INFERRED: "read filtered by the user, write governed by the action type" is the Palantir split. Reads are enforced by data-level policy at query time; writes are enforced by the action type's own permission and criteria, evaluated at submission with the submitting user's identity.

### 1.3 AIP Agent Studio (now Chatbot Studio) and tool exposure

- **Rename.** VERIFIED (https://www.palantir.com/docs/foundry/agent-studio/overview): the page now says AIP Chatbot Studio was previously AIP Agent Studio and AIP Chatbots were AIP Agents. Chatbots combine LLMs, the Ontology, documents and custom tools for read and write workflows, and the platform's security controls grant an LLM access only to what a task needs.
- **Six tool types.** VERIFIED (https://www.palantir.com/docs/foundry/chatbot-studio/tools/): Action (execute an ontology edit; configurable to run automatically or only after user confirmation), Object query (filter, aggregate, inspect, traverse links on configured object types), Function (including AIP Logic functions; latest or pinned published version), Update application variable, Command (trigger operations in other Palantir apps), Request clarification (pause and ask the user). Two tool-calling modes: prompted (any model, single call per turn) and native (parallel calls, subset of models and tool types).
- **Per-action confirmation.** VERIFIED (same page): confirmation-before-apply is a per-tool configuration on the Action tool, not a global switch. INFERRED: this is the same shape as an MCP tool with a "requires confirmation" annotation that the client must honour; Palantir keeps the switch on the server-side tool definition rather than trusting the client.
- The tools page does not itself spell out that tools run under the user's identity; that comes from the OSDK and Logic pages (token restricted to the logged-in user's access; model never sees what the user cannot read). INFERRED: tool execution inherits the calling user's token, so there is no separate "agent permission" layer; the agent is a pass-through for the user plus the builder's per-tool configuration.

### 1.4 Security model

- **Four principles.** VERIFIED (https://www.palantir.com/docs/foundry/security/overview): strict enforcement, granular controls, transparency, usability.
- **Mandatory vs discretionary controls.** VERIFIED (same page): mandatory controls (Markings, classification-based access control, Organisations) travel with data through derivation via provenance and lineage; discretionary controls (resource roles Owner/Editor/Viewer/Discoverer, restricted views for row and column filtering, object and property security policies) are granted per resource and do not propagate to downstream outputs or exports. Users belong to Organisations, which act as hard silos unless explicitly bridged; resources live in Projects.
- **Checkpoints.** VERIFIED (https://www.palantir.com/docs/foundry/checkpoints/overview/): a checkpoint is a prompt asking a user to justify an interaction. Each record stores timestamp, user, justification, checkpoint type and the associated resources, objects and markings. Integrated into 60+ interactions (exports shown as the example). Configured per organisation or space: who sees it, for which interactions, what wording, and how to justify. Integrates with Approvals for asynchronous requests. Every user can review their own checkpoint records.
- **Justification for sensitive actions.** VERIFIED (https://www.palantir.com/docs/foundry/security/requesting-justification-for-sensitive-actions/): implemented as a checkpoint type; configured with conditions in the Checkpoints app; a Preview shows the prompt users will see; records are reviewable afterwards.

### 1.5 Ontology SDK (OSDK) and Developer Console

- **Generated, application-scoped clients.** VERIFIED (https://www.palantir.com/docs/foundry/ontology-sdk/overview): OSDK generates TypeScript, Python and Java clients (plus an OpenAPI spec) from the Ontology. Generated types include only the Ontology entities the application selected, so the surface is minimal. Row and column controls filter what a user can read through the OSDK; the page says users can never read data they are not authorised to see, but enforcement is read-time and does not follow the payload downstream.
- **Token scope = user permissions ∩ application's selected resources.** VERIFIED (https://www.palantir.com/docs/foundry/developer-console/create-application/): two application types, client-facing (token carries the logged-in user's permissions) and backend service (service user). The token from the OAuth flow is restricted by default to the set of entities selected for the application; applications are restricted by default and can be made unrestricted for platform-wide access. Platform API access is a separate opt-in.
- INFERRED: this is the "scoped token" the submission-criteria page warns about: a user token narrowed to an application's resource set, which is exactly Answerable's "entitled subset of requested scopes" model (see repo memory: narrow at authorisation, exact at issuance).
- **Token scope is a runtime intersection of three sets.** VERIFIED (https://www.palantir.com/docs/foundry/developer-console/application-restrictions/): restricted applications control the maximum resources and operations the OAuth client may request; the scope of a token is decided at runtime as the intersection of (1) the user's own permissions, (2) the application's configured resource and operation restrictions, (3) the operations requested at authorisation. Example given: a user cannot reach a dataset through the app until the dataset's project is added to the resource restrictions *and* `api:use-datasets-read` is added to the operation restrictions. Unrestricted applications consider only the user's permissions and are recommended only for trusted code.
- **Approvals = request/grant workflow with persistent audit.** VERIFIED (https://www.palantir.com/docs/foundry/approvals/overview/): users can request group membership, a project role, marking membership, project references and Ontology changes they lack permission to make; approvers are the owners or managers of the target (group managers, project Owners, marking managers, Ontology owners). Requests carry states (pending, changes requested, action required, completed, rejected). If a checkpoint is configured for the underlying action, a justification is also required on the request. Completed requests are persisted as an audit log of past decisions.
- **Functions.** VERIFIED (https://www.palantir.com/docs/foundry/functions/overview/): server-side TypeScript or Python logic with first-class Ontology support (read properties, traverse links, multi-object edits), versioned and published, consumed by Workshop, AIP, OSDK, Slate and Quiver; function-backed actions use them for complex edits. The overview references permission checks for actions but does not spell out the execution identity.
- **AIP Evals.** VERIFIED (https://www.palantir.com/docs/foundry/aip-evals/overview/): evaluates AIP Logic functions, Chatbot functions and code-authored functions with test cases (inputs plus expected outputs) and evaluation functions; positioned as the way to gain confidence before putting LLM-backed functions into production, including model comparison and variance across runs. No approval gate or governance workflow is described on that page; INFERRED: release gating is organisational practice, not a platform-enforced control.

### 1.6 Transferable design ideas from Palantir (raw list; ranked version in the patterns section)

1. Mutations are first-class *typed* definitions (parameters, rules, criteria, side effects), never ad-hoc writes. Read and write authority are separate: read is filtered by data policy, write is granted by the action type.
2. Submission criteria are evaluated server-side at submission with the submitting user's identity and produce user-facing failure messages; they can be dry-run ("test run") without applying.
3. Actions-only edit mode: the user needs no direct write permission on the underlying store, only Read plus the right to apply that action type. The action type is the capability.
4. The action log is a structured, linked, queryable record, not a text log; only successes are recorded there (failures belong to monitoring).
5. Per-tool confirmation flag, set by the builder, not the model or the client.
6. Checkpoints: a reusable "justify or approve before continuing" primitive with a record, configurable by scope, applied to 60+ interaction types; sensitive actions are a checkpoint type.
7. Application-scoped tokens: a user token narrowed to the application's declared resource set, with generated clients that only expose that subset.
8. Mandatory controls travel with data; discretionary controls do not. The docs are explicit that read-time filtering never protects the model's output.

## 3. Identity-for-agents products

### 3.1 The cross-app standard everyone is converging on: ID-JAG / XAA / MCP Enterprise-Managed Authorization

- **Identity Assertion JWT Authorization Grant (ID-JAG).** VERIFIED (https://datatracker.ietf.org/doc/draft-ietf-oauth-identity-assertion-authz-grant/): draft-ietf-oauth-identity-assertion-authz-grant-04, dated 21 May 2026, an active OAuth WG Internet-Draft. Two steps: (1) the client performs RFC 8693 token exchange at the enterprise IdP with `requested_token_type=urn:ietf:params:oauth:token-type:id-jag`, presenting its identity assertion (ID token or SAML) or refresh token; (2) the client presents the ID-JAG to the *resource application's* authorisation server with `grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer` (RFC 7523) and receives an access token. Required claims: `iss`, `sub`, `aud` (the resource AS), `client_id`, `jti`, `exp`, `iat`; optional `scope`, `resource`, `authorization_details`, `sub_id`, `tenant`, `acr`, `amr`, `email`. JWT header `typ` is `oauth-id-jag+jwt`. The IdP validates the subject token, applies administrator-defined policy to decide whether this client may reach this resource for this user, may *narrow* requested scopes, resources and authorisation details, and can demand step-up authentication from `acr`.
- **Okta Cross App Access (XAA)** is the productised form. VERIFIED (https://developer.okta.com/docs/concepts/xaa/): roles are requesting app, resource app (API server) and IdP; nine-step flow from SSO to scoped data; admins create a connection between the two apps in Okta and assign users or groups to it; the Okta AS issues the ID-JAG only for the scoped access allowed in that connection; the app reaches the resource without extra consent prompts. Search results (developer.okta.com blog posts dated July and August 2026) show XAA guides for OIDC and SAML requesting apps and for resource apps; https://xaa.dev/ is an open sandbox.
- **MCP Enterprise-Managed Authorization extension.** VERIFIED (https://modelcontextprotocol.io/extensions/auth/enterprise-managed-authorization): extension id `io.modelcontextprotocol/enterprise-managed-authorization`; the IdP becomes the authoritative decision-maker for which MCP servers employees may access; the client declares the extension in per-request `_meta` client capabilities, stores the ID token or SAML assertion from SSO, exchanges it for an ID-JAG at the IdP, then exchanges the ID-JAG for an MCP access token at the MCP Authorization Server *without* redirecting to that AS's authorize endpoint. The MCP AS validates the ID-JAG against the IdP JWKS (issuer, audience, expiry), maps `scope`/`resource` claims to permissions, and links accounts by `sub` first, `email` as fallback. Clients must respect scope restrictions that differ from standard MCP authorisation. Revocation happens at the IdP and applies across clients. Originating proposal: SEP-990. Anthropic's enterprise-managed auth (section 2) is this extension. The MCP blog post found by search says the extension is now stable and adopted by Anthropic, Microsoft, Okta and others (https://blog.modelcontextprotocol.io/posts/enterprise-managed-auth/, not fetched; treat the adoption list as INFERRED from the search summary).

### 4.1 Suitability for "which tools may this user use, with which constraints"

- INFERRED from the verified table: the question has two halves. *Visibility and callability* of tools is a set-membership question (user ∈ groups, group → capability, capability → tool) that plain SQL answers in one query; every engine above can express it, but none removes the need to store the org/group/member/entitlement tables that Answerable ID already has. *Constraints* (project ids, amount ceilings, time windows) are attribute checks on the call arguments; Cedar's `context`, OpenFGA conditions and SpiceDB caveats all evaluate CEL-like expressions at check time, and a relational design can do the same by storing a JSON constraint on the entitlement row and evaluating it in code.
- INFERRED: ReBAC servers (OpenFGA, SpiceDB) pay off when permissions derive from deep object graphs (folder → document inheritance, thousands of resources per user, ListObjects at scale). Answerable's graph is shallow: organisation → group → member and organisation/group → capability → tool. There is no per-document authorisation in the IdP.
- INFERRED: Cedar via WASM is the one engine that costs nothing operationally (no server, no second datastore) and adds a real capability: a *validated, declarative policy language* for constraints and deny rules, with a schema that fails bad policies at authoring time. Its cost is a second source of truth for policy text and the need to marshal entities from Postgres into each request.

### 4.2 Recommendation for a small team with existing org/group/member/entitlement tables

1. Keep entitlements relational. Add a computed "effective grants" view (or materialised table) keyed by (organisation, member) → (resource, scope, constraint JSON, source entitlement id), refreshed by the same transactions that change groups and entitlements. Scope issuance at token time already reads this shape (repo memory: narrow at authorisation, exact at issuance).
2. Evaluate constraints in code at tool execution against the call arguments, and log the decision with the entitlement id that allowed it (the Palantir action log shape).
3. Do not introduce OpenFGA, SpiceDB or Permit now: each adds a server, a sync problem and a second store for facts you already hold in Postgres, and the shallow graph gives none of their benefits. Revisit only if per-object sharing inside client MCPs must live in the IdP.
4. If constraint expressions grow beyond a handful of JSON shapes, adopt Cedar WASM inside the MCP base package with entities built from the effective-grants rows, keeping Postgres as the only store. Cedar's forbid rules give a clean way to express organisation-wide denials (e.g. "no destructive tools for contractors") without touching entitlement rows.

## 5. Standards for constrained / transaction-bound authorisation

- **OAuth 2.0 Rich Authorization Requests, RFC 9396.** VERIFIED (https://www.rfc-editor.org/rfc/rfc9396.html): `authorization_details` is a JSON array of objects, each with a mandatory `type`; common optional fields are `locations`, `actions`, `datatypes`, `identifier`, `privileges`; combining several common fields inside one object means the product of all values, so clients needing precision send several objects. It may appear in the authorisation request, pushed authorisation request, token request, token response, introspection response and as a JWT access-token claim. The AS must refuse unknown types or non-conforming objects with `invalid_authorization_details`; the details attached to an issued access token are decided by the token request, and the AS may omit sensitive values in responses. The RFC's running example is payment initiation with currency, amount and creditor.
- **CIBA (OpenID Connect Client-Initiated Backchannel Authentication Core 1.0).** VERIFIED (https://openid.net/specs/openid-client-initiated-backchannel-authentication-core-1_0.html): the client authenticates to the backchannel authentication endpoint (client authentication is mandatory) with `scope`, one of `login_hint`/`id_token_hint`/`login_hint_token`, optional `binding_message`, `user_code`, `requested_expiry`; the AS answers with `auth_req_id`, `expires_in`, `interval`; the user authenticates on their own device; delivery modes are poll, ping and push; grant type `urn:openid:params:grant-type:ciba`; errors `authorization_pending`, `slow_down` (increase interval by at least 5 seconds), `expired_token`, `access_denied`.
- **OAuth 2.0 Token Exchange, RFC 8693.** VERIFIED (https://www.rfc-editor.org/rfc/rfc8693.html): grant type `urn:ietf:params:oauth:grant-type:token-exchange` at the token endpoint with required `subject_token` and `subject_token_type`, optional `resource`, `audience`, `scope`, `requested_token_type`, `actor_token`, `actor_token_type`; response `access_token`, `issued_token_type`, `token_type`, `expires_in`, `scope`; token type URIs for access_token, refresh_token, id_token, saml1, saml2, jwt. Impersonation means the AS treats A as B; delegation keeps A's identity and records it in the `act` claim, with `may_act` declaring who may become the actor. It is the substrate for ID-JAG (section 3), Transaction Tokens, Auth0 Token Vault and Descope connections.
- **Constraint evaluation in ReBAC engines.** VERIFIED (https://openfga.dev/docs/modeling/conditions): OpenFGA conditions are CEL expressions attached to tuples, evaluated at Check/ListObjects time with request context merged under persisted context (persisted wins); use cases are time windows, IP ranges, entitlements and quotas, resource attributes; limits are 32 KB context per tuple, CEL cost cap 100, 512 KB request. VERIFIED (https://authzed.com/docs/spicedb/concepts/caveats): SpiceDB caveats are CEL expressions on relationships; a caveated relationship counts only if the expression is true at check time; when context is missing the check returns `PERMISSIONSHIP_CONDITIONAL_PERMISSION` together with the missing field names; a relationship cannot exist twice with and without a caveat.
- **Transaction Tokens.** VERIFIED (https://datatracker.ietf.org/doc/draft-ietf-oauth-transaction-tokens/): draft-ietf-oauth-transaction-tokens-11, 30 July 2026, active OAuth WG draft. A Txn-Token is a short-lived signed JWT asserting a user or workload identity plus an authorisation context, immutable along a call chain inside one trust domain. Obtained by RFC 8693 token exchange at a Transaction Token Service with `requested_token_type=urn:ietf:params:oauth:token-type:txn_token`, `audience` = trust domain, `scope` = purpose, `subject_token` = the inbound token. Required claims `txn`, `sub`, `aud`, `scope`, `req_wl`; recommended `tctx` (authorisation details that stay immutable) and `rctx` (request context such as IP and authentication method). Lifetime on the order of minutes or less. A replacement token must keep `txn`, `sub`, `aud` and may not widen scope.
- **Eclipse Biscuit.** VERIFIED (https://www.biscuitsec.org/): public-key signed authorisation tokens with decentralised verification, offline attenuation by appending blocks that add checks (e.g. narrower write access or an expiry), a Datalog policy language for facts, rules, checks and allow/deny policies, unique revocation identifiers per block so a token and all its attenuations can be rejected, implementations in Rust, Haskell, Go, Java, JS (node and browser), WebAssembly, C, Python, C#. VERIFIED (https://registry.npmjs.org/@biscuit-auth/biscuit-wasm): `@biscuit-auth/biscuit-wasm` 0.6.0, released 2025-09-26, Apache-2.0.
- **Macaroons.** VERIFIED (https://github.com/nitram509/macaroons.js): HMAC-chained bearer tokens attenuated by adding first-party caveats (verified locally) or third-party caveats (need a discharge macaroon); `MacaroonsBuilder`, `add_first_party_caveat`, `add_third_party_caveat`, `MacaroonsVerifier`; base64url serialisation. The macaroons.js project states it is no longer actively maintained beyond occasional security updates.
- **AP2 (Agent Payments Protocol).** VERIFIED (https://raw.githubusercontent.com/google-agentic-commerce/AP2/main/docs/ap2/specification.md, v0.2, and https://raw.githubusercontent.com/google-agentic-commerce/AP2/main/docs/ap2/checkout_mandate.md): the current spec defines **two** mandates, not the three (intent, cart, payment) of the original announcement. A **Checkout Mandate** proves the Shopping Agent is authorised to purchase an assembled checkout; a **Payment Mandate** proves authorisation to pay for that checkout and binds to it through a cryptographic hash of the merchant-signed checkout JWT. Both are secured as SD-JWTs. A Checkout Mandate is *open* (`vct` `mandate.checkout.open.1`, created by the agent with constraints on allowed merchants and line items, signed by the user for human-not-present flows) or *closed* (`vct` `mandate.checkout.1`, containing `checkout_hash` over the merchant-signed `checkout_jwt`, `cnf` key binding to the user's device, `iat`/`exp`); in human-present flows the user signs the closed mandate on a Trusted Surface, in autonomous flows the agent closes it within the open mandate's constraints. Constraint checking is explicit: the merchant must be among the revealed `allowed` merchants and line items are validated against approved items and quantities (described as a maximal-flow check). Roles: Shopping Agent, Credential Provider, Merchant, Merchant Payment Processor, Trusted Surface. Mandates plus receipts together give a non-repudiable record of the transaction. VERIFIED (https://ap2-protocol.org/overview/): the overview says transactions must be anchored to deterministic, non-repudiable proof of intent from all parties and that merchants keep mandates as dispute evidence. INFERRED mapping: open mandate ≈ Answerable `prepare` with constraints; closed mandate ≈ `commit` bound to a hash of the exact mutation; `cnf` ≈ binding the commit to the approving principal's credential.
- **ID-JAG carries `authorization_details`.** VERIFIED (section 3): the ID-JAG draft lists `authorization_details` as an optional claim and lets the IdP narrow it, so an enterprise IdP can pre-constrain what an app may request of a resource AS.

### 5.1 Mapping a "commit token" for a prepared mutation

INFERRED design comparison (verified building blocks above):

| Option | Shape | Strengths | Weaknesses |
|---|---|---|---|
| A. Server-side record + opaque handle | `prepare` stores the immutable intent (tool, canonical arguments hash, actor, organisation, expiry, required approvals) in Postgres and returns an opaque id; `commit(id)` re-checks entitlement and approval state, then executes once | Simplest; revocation and audit are table rows; no key management; idempotent by construction; matches Palantir's action log and Approvals | Handle is meaningless outside the issuing server; a second service cannot verify it without a call |
| B. Signed JWT with RFC 9396 `authorization_details` | `prepare` issues a short-lived JWT (or the AS issues it via a CIBA or RAR flow) whose `authorization_details[0]` = `{type: "answerable.mutation", identifier: <intent id>, actions: [tool], locations: [mcp resource], ...hash}`; the MCP server verifies signature, audience, expiry and that the executed arguments hash matches | Standards-aligned; introspectable; the same claim can flow through an ID-JAG from a customer IdP; Transaction Tokens `tctx` is the same idea for internal hops | Still needs a server-side record for single-use and revocation (JWTs are not revocable on their own); more surface (keys, clock skew) |
| C. Biscuit attenuated capability | The AS mints a capability token for the tool; the MCP server or client appends a block with checks (`check if mutation_hash == "..."`, `check if time < ...`) | Offline attenuation, third-party blocks for approver signatures, revocation ids | Second token format beside JWT access tokens; small ecosystem; Datalog policy is a new skill for the team; MCP clients only forward bearer tokens they did not attenuate |

Recommendation (INFERRED): A as the source of truth, with B's JWT as an optional *representation* of the same record when a token must cross a service boundary (e.g. a hub calling a bespoke MCP). Never C for the first version. Keep the intent record immutable, bind the commit to the intent's argument hash, make `commit` idempotent, and reject on any entitlement change between prepare and commit (Palantir re-evaluates submission criteria at submission; Descope evaluates policy at issuance; Transaction Tokens keep `tctx` immutable across hops).

## 6. Claude Code and Agent SDK permission models

- **Claude Code.** VERIFIED (https://code.claude.com/docs/en/permissions): a tiered system. Read-only tools (file reads, Grep) need no approval inside the working directories; Bash needs approval except a built-in, non-configurable set of read-only commands (`ls`, `cat`, `grep`, `find`, read-only forms of `git`, ...) which run without a prompt in every mode; commands the parser cannot fully analyse prompt instead of being treated as read-only. Rules are evaluated deny, then ask, then allow, and the first match wins regardless of specificity, so an allow rule can never carve an exception out of a deny rule and an ask rule prompts even when a narrower allow matches. Rule syntax: `Tool`, `Tool(specifier)`, MCP rules `mcp__server`, `mcp__server__tool`, deny/ask accept tool-name globs (`mcp__*`), allow globs only after a literal `mcp__<server>__` prefix; `mcp__` rules with parentheses are skipped. A denied bare tool name is removed from the model's context entirely. Managed settings sit above user, project and local settings and cannot be overridden. Hooks: a `PreToolUse` hook exiting 2 blocks the call before rules are evaluated, but a hook `allow` does not bypass deny or ask rules. Organisation-set claude.ai connector tools marked `ask` prompt on every call even in auto and bypass modes, and are denied in `dontAsk` mode. An `auto` mode exists where a model classifier reviews actions instead of the user.
- **Claude Agent SDK.** VERIFIED (https://code.claude.com/docs/en/agent-sdk/permissions): evaluation order is hooks → deny rules → ask rules → permission mode → allow rules → `canUseTool` callback. Deny rules block even in `bypassPermissions`; ask rules always fall through to `canUseTool`; MCP tools whose server sets `_meta["anthropic/requiresUserInteraction"]` always reach the callback even when an allow rule matches (Claude Code v2.1.199+), as do `AskUserQuestion` and org-`ask` connector tools; in `dontAsk` those are denied instead. Modes: `default`, `dontAsk` (deny instead of prompt, callback never called), `acceptEdits`, `bypassPermissions` (hooks and deny rules still apply), `plan` (writes always go to the callback), `auto` (model classifier). Auto-approved calls never reach `canUseTool`, so per-call checks belong in a `PreToolUse` hook. Bare `allowedTools` entries auto-approve the whole tool; scoped entries (`Bash(npm test *)`) only matching calls. VERIFIED (https://code.claude.com/docs/en/agent-sdk/user-input): `canUseTool(toolName, input, options)` where `options` carries an `AbortSignal` and optional `suggestions` (ready-made `PermissionUpdate` entries); it returns `{ behavior: "allow", updatedInput, updatedPermissions? }` or `{ behavior: "deny", message }`; the callback may rewrite the input before execution (the model is not told), may persist a suggested rule to `.claude/settings.local.json` by echoing it in `updatedPermissions`, and may stay pending indefinitely, with a `PreToolUse` hook `defer` decision recommended when a human may take longer than the process can wait; `AskUserQuestion` also arrives through the same callback with a `questions` array (1-4 questions, 2-4 options each). The page repeats that auto-approved tools never reach the callback, so per-call checks belong in a `PreToolUse` hook. VERIFIED (https://code.claude.com/docs/en/mcp): organisation admins can set claude.ai connector tools to `ask` (prompt on every call, reason "Your organization requires approval for this tool", no remember option, applies even in acceptEdits, auto and bypassPermissions) or `blocked` (tool filtered out before the model sees it); these apply where Claude Code fetches the connectors itself (terminal, VS Code, JetBrains, Agent SDK).
- **MCP tool annotations (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`).** VERIFIED (local clone of https://github.com/modelcontextprotocol/modelcontextprotocol at ab3a39c, 2026-09-24, files `docs/specification/2026-07-28/server/tools.mdx` and `schema.mdx`): the 2026-07-28 spec says clients MUST treat tool annotations as untrusted unless they come from trusted servers; the schema defines `readOnlyHint` (default false: tool does not modify its environment), `destructiveHint` (default true; meaningful only when readOnlyHint is false), `idempotentHint` (default false), `openWorldHint` (default true), and states that all `ToolAnnotations` are hints and clients should never make tool-use decisions on annotations from untrusted servers. A Tool Annotations Interest Group (`docs/community/interest-groups/tool-annotations.mdx`, facilitated by GitHub and OpenAI staff) is reviewing six SEPs on annotations, including trust/sensitivity (SEP-1913), runtime annotations and tool-response annotations. The Claude Code and Agent SDK pages fetched do not mention `readOnlyHint`-based auto-approval; the only server-side marker Claude Code honours is `_meta["anthropic/requiresUserInteraction"]`, which forces a prompt and can never grant one. INFERRED: a server that wants a guaranteed prompt must set that marker; a server that wants auto-approval cannot get it by annotation, only the client's own rules give it.

### 6.1 One-paragraph summary for policy classes

INFERRED synthesis of the verified facts: Claude Code models permission as three ordered rule classes (deny, ask, allow) matched against a tool name plus an argument specifier, with a mode that sets the default for anything unmatched and a hook layer that can veto before rules run. Read-only operations are pre-classified as safe by the harness, not by the tool's own claims; server-side markers can force a prompt but cannot grant one. Translated to Answerable: an entitlement grants *visibility* (allow class), a policy on the capability or tool marks *ask* (requires a prepared-and-approved commit) or *deny* (removed from the tool list), and the MCP base evaluates deny → ask → allow at both `tools/list` and `tools/call`, with a hook-like pre-execution check that runs on every call regardless of caching.

## Transferable patterns for Answerable (ranked)

Ranked by value for the "Palantir model" goal (admins add or remove tools for users or groups; everything governed and audited) against cost for a small team on Postgres + Better Auth. Each pattern names the verified source it is drawn from; the mapping to Answerable is INFERRED.

1. **Tool = governed action definition, with `prepare` as submission criteria.** Palantir action types carry typed parameters, declarative submission criteria evaluated server-side at submission with the submitting user's identity, per-condition user-facing failure messages, and a dry-run. Map: every mutating tool in `@answerable/mcp` declares its parameters, a `prepare(args, principal)` that returns either failure messages or an immutable intent record, and a `commit(intentId)` that re-checks entitlement and executes. Make the failure messages part of the tool contract so the model can repair its call.
2. **Write authority lives in the tool, not in the user's downstream permissions ("actions-only" edit mode).** Palantir lets a user apply an action with only Read on the objects; the action type is the capability. Map: the MCP server holds the downstream service credential; the entitlement (org/group → capability → scopes) is the only thing that decides who may invoke; never forward user credentials for writes. This is the model Salesforce (agent user runs as itself) and Glean agent identity also use for unattended runs.
3. **Effective grant is a runtime intersection of three sets.** Palantir application restrictions: user permissions ∩ application's allowed resources and operations ∩ requested operations; Descope evaluates policy at issuance and strips scopes no policy permits; Answerable already narrows to the entitled subset at authorisation. Map: add the *client application* dimension. Each registered MCP client (Claude, ChatGPT, Toolbox, a customer's agent) gets a maximum resource/operation set; issued scopes are the triple intersection; unrestricted clients are not allowed.
4. **Separate the three admin questions and store them separately.** Every vendor in section 2 distinguishes catalogue (which connectors exist in the tenant), audience (which roles or IdP groups may use each), and action policy (what each may do: Claude per-role scope narrowing; ChatGPT read vs write action sets with a new-actions policy; Entra per-operation scopes; Glean per-tool toggles per surface). Map: capability rows for the catalogue, entitlement rows for audience, and a per-tool policy class (`allow` / `ask` / `deny`) plus an organisation default for *newly published tools* (ChatGPT: disabled until an admin enables, changes shown as a diff). Groups first, per-user grants as the exception (Claude, ChatGPT, Glean, Entra all gate by group or role).
5. **Deny > ask > allow, first match, no specificity override, evaluated at list and at call.** Claude Code's rule order; Cedar's forbid-overrides-permit; ToolHive filters `tools/list` from the `call_tool` policy and returns kind-only denials so tools cannot be enumerated. Map: in the MCP base, `deny` removes the tool from `tools/list` and returns a generic error on call; `ask` lists the tool but routes every call through prepare → approval → commit; `allow` executes. Evaluate the policy on every call (no caching across entitlement changes), like Stytch's advice to check on every MCP operation.
6. **Server-set "requires approval" cannot be overridden by the client; client hints cannot grant approval.** Claude Code honours `_meta["anthropic/requiresUserInteraction"]` and org-level `ask` even in bypass modes, and the MCP spec says tool annotations are untrusted. Map: Answerable's `ask` class is enforced server-side in commit, not by asking clients to prompt; `readOnlyHint`/`destructiveHint` are set honestly for clients but never read for authorisation.
7. **Structured audit as first-class records, successes and approvals separate from failures.** Palantir action log objects (actor, action type version, timestamp, edited object keys, parameters, provenance, linked to affected objects) plus Checkpoints (justification records) plus Approvals (persisted as an audit log of past decisions). Map: `mutation_log` (intent id, actor, tool and version, argument hash, entitlement id that allowed it, approval ids, outcome), an optional justification field captured at prepare for tools flagged "sensitive", and denied calls in a monitoring log rather than the action log.
8. **Approval as a state machine with a poll vocabulary.** Palantir Approvals states; CIBA `auth_req_id` with `authorization_pending` / `slow_down` / `expired_token` / `access_denied`; Auth0's decision that an approval is not a stored consent grant. Map: `approval_request` rows tied to an intent, approvers derived from the capability's owner group, expiry, a poll endpoint the agent can call with the CIBA error vocabulary, and no reuse of an approval beyond its intent. The existing Better Auth device-authorization plugin is the nearest shape to copy.
9. **Two-tier auto-commit.** Glean: admin marks a write tool *eligible* to run without confirmation, then the builder enables it per step; default is confirmation for every write. Map: organisation admin marks a tool "may auto-commit"; a per-group (or per-client) setting turns it on; otherwise `ask`.
10. **Agent identities are distinct principals with a sponsor and a delegated/autonomous flag.** Entra Agent ID (service principal with Agent subtype, sponsor, delegated vs autonomous, paired agent user), Glean agent identity, Salesforce agent user. Map: Answerable ID machine accounts become "agent identities" with a sponsoring member, entitlements of their own, and tokens that carry RFC 8693's `act` claim when acting for a user so audit records both principals.
11. **Accept enterprise IdP assertions (ID-JAG / XAA / MCP Enterprise-Managed Authorization) as the resource authorisation server.** WorkOS and the MCP extension describe exactly this role; account linking by `sub` then `email`. Map: a per-organisation trusted-issuer registry and a `jwt-bearer` grant handler in Answerable ID; Better Auth 1.7.2 has neither, so it is bespoke code. Medium term, but it is the feature that lets a customer's Okta/Entra admin switch a whole group onto a bespoke MCP without consent screens.
12. **Commit token = server record first, RAR JWT as its portable form.** Section 5.1: immutable intent record with argument hash; when a token must cross a service boundary, mint a short-lived JWT whose `authorization_details` names the intent (RFC 9396), keeping Transaction Tokens' rule that the context stays immutable and a replacement cannot widen scope. AP2's signed mandates (Checkout Mandate open until conditions are met, then closed; non-repudiable proof of intent) are the same idea for payments and show why the record, not the token, is the source of truth.
13. **Policy on tool outputs.** Glean evaluates policies after a tool returns (filter or block) and Palantir states that read-time filtering never protects the model's output. Map: a post-execution result hook in the MCP base for redaction rules; lower priority than 1-8.
14. **Generated, application-scoped typed clients (OSDK).** Palantir generates a TypeScript client limited to the application's selected entities. Map: generate a typed client per organisation's entitled tool set from the MCP tool schemas for Toolbox and for tests; convenience rather than security, since MCP already publishes schemas at runtime.

## Do not adopt

- **A ReBAC server (OpenFGA, SpiceDB, Permit.io PDP) for tool entitlements now.** They add a server, a second datastore or a sync layer, and their strength (deep object graphs, ListObjects at scale) does not apply to organisation → group → member → capability → tool. Auth0 FGA positions OpenFGA for document-level RAG control, which is a downstream-system concern, not the IdP's.
- **Biscuit or macaroon capability tokens.** Second token format beside JWT, small ecosystems (macaroons.js is unmaintained), offline attenuation is useless when MCP clients only forward bearer tokens, and revocation still needs a server-side list.
- **Full CIBA conformance (ping/push delivery modes, mTLS or private-key-JWT client authentication).** Copy the poll state machine and error vocabulary only; Auth0's implementation limits show how heavy the full product is.
- **Prompt-driven entitlement checks (Frontegg's "call the is-entitled tool first").** The model can skip a check it is merely asked to perform; enforcement belongs in the tool server.
- **Trusting MCP tool annotations for authorisation or auto-approval.** The 2026-07-28 spec says clients must treat them as untrusted, and Claude Code does not auto-approve on `readOnlyHint`.
- **Unrestricted client applications.** Palantir allows them only for trusted code; every Answerable client should carry a maximum resource/operation set.
- **Palantir-style Markings and mandatory data controls inside the IdP.** Answerable ID holds no business data; mandatory controls belong in the bespoke MCPs and their downstream systems.
- **Per-user tool lists as the primary mechanism.** Every vendor gates by role or IdP group; per-user grants remain the exception path.
- **A separate policy DSL (Cedar) on day one.** Keep constraints as JSON on entitlement rows evaluated in code; adopt Cedar WASM only if constraint expressions outgrow that (it is the cheapest upgrade path: in-process, stateless, validated).
- **Silent failure of unauthorised tool steps inside shared agents (Glean's agent behaviour).** Return an explicit, non-enumerating error to the model instead.
- **Approvals as reusable consent grants.** An approval binds to one intent (Auth0's CIBA behaviour, AP2's per-checkout mandate).

## Open questions

1. Granularity of `ask`: per tool, per capability, or per (group, tool)? Vendors set it per tool per role (ChatGPT) or per role scope (Claude); Glean per tool per surface.
2. Who approves? Palantir uses the owner or manager of the target resource. Answerable needs an "approver" relation on capabilities or groups; is it the organisation admin, the group manager, or a named approver group?
3. Prepare → commit TTL, and behaviour when entitlements change in between (re-check and reject seems right; Palantir re-evaluates at submission).
4. Should the tool list expose the policy class to clients (a `_meta` marker like Claude's `requiresUserInteraction`), so Toolbox and Claude prompt before calling `ask` tools? MCP has no standard marker; the Tool Annotations Interest Group is reviewing trust and sensitivity annotations (SEP-1913).
5. Default for newly published tools in an already-entitled capability: disabled until enabled (ChatGPT) or enabled with read-first guidance (Glean)?
6. Delegated vs autonomous agent tokens: carry `act` (RFC 8693) and record both principals, or issue separate tokens?
7. XAA priority: which customer IdPs first (Okta ships XAA; Entra's ID-JAG issuance was not verified in this research).
8. Do bespoke MCPs need per-object authorisation in their downstream systems? If so, that is where a ReBAC engine would live, not in Answerable ID.
9. Should tool releases be gated by evaluation suites (AIP Evals analogue)? Palantir does not enforce it platform-side.
10. Output-side policies: is redaction needed in the MCP base, or only in specific bespoke tools?
11. Justification prompts (Checkpoints): which tools count as sensitive, and is the justification captured at prepare or at approval?
