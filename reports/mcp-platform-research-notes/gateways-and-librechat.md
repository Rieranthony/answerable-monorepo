## Summary

- LibreChat (repo now `LibreChat-AI/LibreChat`, MIT, 45k stars) is a mature MCP client: per-user OAuth since v0.7.9 (2025-07-23), RFC 9728 discovery, RFC 7591 DCR or pre-registered clients, PKCE always, RFC 8707 `resource` sent by default and validated against the server URL (admin-only opt-out `send_resource_parameter: false`), encrypted per-user token rows in MongoDB, cross-replica refresh leases, `tools/list_changed` honoured, per-user Streamable HTTP connections with DELETE on teardown. It does not support elicitation, tasks, MCP Apps, `structuredContent` or tool annotations; it does render MCP-UI `ui://` resources. Tool keys are `${tool}_mcp_${server}` (issue #7435: 64-char OpenAI limit hit).
- Landscape: two families. (1) Identity-filtered single endpoint: Cloudflare MCP Server Portals, Obot MCP Gateway, Kong `ai-mcp-proxy` consumer ACLs, agentgateway CEL authorisation, Arcade MCP Gateways, Smithery namespaces. (2) Curated virtual servers / toolsets addressed by URL or session: IBM ContextForge virtual servers, MetaMCP namespaces->endpoints, Speakeasy Gram toolsets, Composio/Nango sessions (URL per user session), Pipedream (headers per user and app), Zapier (server per client). The integration hubs (Composio, Nango, Klavis Strata, Stainless, Docker Dynamic MCP, Lasso) converge on meta-tools (search/describe/execute) instead of projecting every tool.
- Evidence: Anthropic's own docs say selection accuracy degrades past 30–50 tools and report Opus 4 49%->74% and Opus 4.5 79.5%->88.1% on MCP evals with tool search; RAG-MCP 13.62%->43.13%; Anthropic guidance is to consolidate related operations and prefix by service. Naming: SEP-986 (Final) 1–64 chars `[A-Za-z0-9_.\-/]`; OpenAI 64 chars `[A-Za-z0-9_-]`; Anthropic API docs now say `^[a-zA-Z0-9_-]{1,128}$`.
- Recommendation for Toolbox: one global Streamable HTTP endpoint, identity from the Answerable ID access token, `tools/list` computed per subject, PRM with `resource` equal to the canonical URL, `resource`-tolerant token endpoint at Answerable ID, DCR or a documented public client, tool names `<domain>_<verb>` under 48 chars, a per-user direct catalogue capped at roughly 30–40 tools plus a meta-tool tier for the long tail, `list_changed` on entitlement change, text mirror of every structured result, stateless sessions, and a token vault keyed by Answerable ID subject for upstream credentials.

Per-user vs app-level: `requiresUserScopedConnection` (`packages/api/src/mcp/utils.ts`) = `requiresOAuth || obo || customUserVars || runtime placeholders`; such servers get one connection per user (`UserConnectionManager.userConnections: Map<userId, Map<serverName, MCPConnection>>`), idle-evicted after `MCP_USER_CONNECTION_IDLE_TIMEOUT` (15 min). Everything else shares app-level connections (`appConnections`). `{{LIBRECHAT_BODY_*}}` makes a server request-scoped: ephemeral connection per run, excluded from the persistent tool cache. Discussion #8790 says user connections will become ephemeral.

Env knobs (`packages/api/src/mcp/mcpConfig.ts`): `MCP_OAUTH_ON_AUTH_ERROR` (default true), `MCP_OAUTH_DETECTION_TIMEOUT` 5 s, `MCP_OAUTH_HANDLING_TIMEOUT` 10 min, `MCP_OAUTH_FLOW_TTL` 15 min (clamped above handling timeout), `MCP_CONNECTION_CHECK_TTL` 60 s, `MCP_TOOLS_LIST_MAX_PAGES` 50, `MCP_TOOLS_LIST_MAX_TOOLS` 1000, `MCP_TOOLS_LIST_MAX_BYTES` 5 MiB, `MCP_TOOLS_LIST_TIMEOUT_MS` 30 s, circuit breaker `MCP_CB_*` (7 cycles / 45 s window, 3 failed rounds, 30 s base backoff capped at 300 s).

Three-layer registry (`registry/MCPServersRegistry.ts` header comment): YAML cache (operator), Config cache (admin-defined overrides, lazily initialised), DB repository (UI-created servers, MongoDB + ACL); query priority Config -> YAML -> DB. Process-backed (`stdio`, `command`, `args`, `env`, `cwd`, `stderr`) servers are YAML-only; the admin API and DB reject them. `mcpSettings.allowedDomains` / `allowedAddresses` gate internal addresses, with user/role-scoped overrides.

### A2. OAuth (per user)
- Introduced: v0.7.9 (2025-07-23) "MCP OAuth 2.0 Discovery Support", user-provided credentials, reinitialise + OAuth in UI, Streamable HTTP transport. v0.8.1-rc1 (2025-10-30) `oauth_headers`; v0.8.2 (2026-01-28) UI-created servers with ACL, API-key auth, domain restrictions; v0.8.4 (2026-03-20) reconnection-storm circuit breaker, OAuth race fixes, fail-closed domain validation; v0.8.7 (2026-06-23) OBO; v0.8.8-rc4 (changelog 2026-09-20, GitHub 2026-09-23) refresh serialised across replicas, `send_resource_parameter`, refresh of already-expired credentials, sign-in requested when a server rejects a refreshed token.
- Detection (`oauth/detectOAuth.ts`, `oauth/resourceHint.ts`): HEAD then POST `{}` to the server URL; a 401 with `WWW-Authenticate: Bearer resource_metadata="..."` (RFC 6750/9728 §5.1) supplies the PRM URL (own regex handles multi-scheme headers); then SDK `discoverOAuthProtectedResourceMetadata` (hint first, else path-aware `/.well-known/oauth-protected-resource`); a Bearer challenge without metadata still means OAuth required; `MCP_OAUTH_ON_AUTH_ERROR` treats a HEAD 401/403 as OAuth required (POST-only 401/403 deliberately ignored because WAFs 403 empty POSTs). The hint URL is SSRF-validated. Practical consequence: the Toolbox must answer HEAD with 401 plus the header, not only POST.
- Flow (`oauth/handler.ts` `MCPOAuthHandler.initiateOAuthFlow`), two branches:
  1. Pre-configured when `authorization_url`, `token_url` and `client_id` are all set (lines ~821-1010). Secret allowed only here; `assertNoUnpinnedClientSecret` refuses a secret with discovered endpoints. Optional capability discovery is accepted only if the discovered `token_endpoint` equals the configured one. Token auth method resolves from `token_exchange_method`/`token_endpoint_auth_methods_supported`, default `client_secret_basic` (or `none` without secret). PKCE via SDK `startAuthorization`; `code_challenge_methods_supported` defaults `['S256','plain']`; `skip_code_challenge_check` forces S256.
  2. Discovered (lines ~1010-1230): `discoverMetadata` -> PRM -> `discoverAuthorizationServerMetadata` (RFC 8414/OIDC, with base-URL fallbacks). Client: `oauth.client_id` alone => public client (`token_endpoint_auth_method: 'none'`) on discovered endpoints; else reuse the stored DCR registration if redirect_uri, issuer, server_url, token_endpoint, `resource` and `credential_set_id` still match; else `registerClient` (RFC 7591) with `client_name: 'LibreChat MCP Client'`, `grant_types: ['authorization_code', 'refresh_token' if advertised]`, `response_types` from metadata, auth method via `selectRegistrationAuthMethod`, `scope` = PRM `scopes_supported` or AS `scopes_supported`.
- Scope requested: `config.scope || PRM.scopes_supported.join(' ') || AS.scopes_supported.join(' ')`. So whatever the Toolbox advertises in PRM `scopes_supported` is what LibreChat asks for by default.
- PKCE: always (SDK `startAuthorization` returns `codeVerifier`, stored in flow state). `state` = 32 random bytes base64url. Flow state lives in the flow manager (Redis or memory) keyed `userId:serverName[:tenant]`, TTL `MCP_OAUTH_FLOW_TTL`.
- RFC 8707 `resource` (Q-RESOURCE-PARAM): sent by default on `/authorize` (`authorizationUrl.searchParams.set('resource', canonicalResource)`), on the code exchange (`exchangeAuthorization(..., { resource })`) and on refresh (`appendResourceParameter`). The value is always the PRM `resource`, never operator-supplied. `assertResourceBoundToServer` enforces RFC 9728 §3.3: PRM without `resource`, or whose `resource` does not match the MCP URL (SDK `checkResourceAllowed`), aborts the flow (GHSA-gvpj-vm2f-2m23). No PRM at all => warning and no `resource`. Opt-out `oauth.send_resource_parameter: false` strips it from the authorisation URL, token endpoint URL and refresh body; added because Entra ID v2.0 returns `AADSTS9010010` when `resource` accompanies `scope`. Admin-only: `UserOAuthOptionsSchema` sets `send_resource_parameter`, `audience`, `forward_audience_on_refresh` to `z.never()` and rejects user-supplied endpoint URLs containing `audience` or `resource` query params. Separate `oauth.audience` for Auth0/Cognito.
- Refresh (`oauth/tokens.ts`, `handler.ts` ~1741-1810): sends `scope` on refresh, retries without it on `invalid_scope`-style 400s (Salesforce); rotation-aware (RFC 9700); process-local single flight per `tenantId:userId:serverName:bindingScope` plus a cross-replica lease keyed `['refresh', tenantId, userId, serverName]`; expired credentials refreshed before use; rejected refresh => user asked to sign in again; `invalid_client` on refresh can clean up stale DCR registration.
- Storage: MongoDB `Token` collection rows per user, `type` `mcp_oauth` (identifier `mcp:<server>`), `mcp_oauth_refresh` (`mcp:<server>:refresh`), `mcp_oauth_client` (`mcp:<server>:client`), values `encryptV2` (`@librechat/data-schemas` crypto, `CREDS_KEY`/`CREDS_IV`), metadata incl. `credential_set_id` generation and client binding (issuer, server_url, token_endpoint, resource, client_source).
- Runtime: on a tool call without a usable token, `MCP.js createToolInstance` starts a flow (`flowId = ${server}:oauth_login:${thread}:${run}`), streams the authorisation URL to the UI as a run-step delta (`createOAuthStart`) and waits up to `MCP_OAUTH_HANDLING_TIMEOUT`. UI shows "OAuth Required" with a connect button; routes `/api/mcp/:serverName/oauth/initiate|callback`, `/api/mcp/oauth/status/:flowId`, `/oauth/cancel/:serverName`, `/oauth/tokens/:flowId`, `/:serverName/oauth/bind`. `OAuthReconnectionManager` reconnects a user's OAuth servers after login, staggered 500 ms, 10 s connect timeout; reconnection halts when OAuth is required or on 429.
- Routes are Express; `GET /api/mcp/:serverName/oauth/callback` is unauthenticated (state-bound).

### A3. Tool exposure
- Naming: `${toolName}_mcp_${normalizeServerName(serverName)}` (`api/server/services/MCP.js createToolInstance`, `packages/api/src/mcp/tools.ts formatMCPServerTools`; `Constants.mcp_delimiter = '_mcp_'`, `mcp_prefix = 'mcp_'`, `mcp_all = 'sys__all__sys'` at `config.ts:4128-4132`). `normalizeServerName` (`config.ts:4172`) keeps `[a-zA-Z0-9_.-]`, replaces the rest with `_`, hashes if empty. `stripServerNamePrefixes` removes a redundant `<server>_` prefix from tool names for the model-facing key; the upstream call always uses the original name (`serverToolName`). No truncation to 64 chars: issue #7435 (open, 10 reactions) reports OpenAI 400 "string too long" at 67 chars.
- Definition: LangChain `tool()` with `responseFormat: CONTENT_AND_ARTIFACT`; `description = tool.description ?? ''` passed through verbatim; `inputSchema` normalised (`normalizeJsonSchema(resolveJsonSchemaRefs(...))`), Gemini-sanitised; empty schema replaced with `{ input: string }`. `outputSchema`, `title`, `annotations` are not read.
- UI: agents "Tools" picker groups tools per server; author expands a server to enable individual tools (docs: each server is a single catalogue entry that expands); chat dropdown (`MCPSelect`) lists servers with `chatMenu: true`; model specs can pin `mcpServers`. Chat-level selection is per server, not per tool.
- `tools/list`: cursor pagination with caps (50 pages, 1000 tools, 5 MiB, 30 s) per server (`connection.ts fetchTools`). `notifications/tools/list_changed` honoured: `subscribeToToolListChanges` -> `refreshToolList` (`connection.ts` ~1846, fixes #7117), coalesced with exponential retry in `toolsChanged.ts`, catalogue re-synced on every reconnect; rc4 makes discovery lazy ("discovered only when needed").
- Result parsing (`parsers.ts`): `text`, `image` (data URIs), `resource` (text, image, binary summarised; `ui://` resources collected as MCP-UI with `\ui{id}` markers rendered by `@mcp-ui/client ^5.7.0`), `resource_link`; unknown parts JSON-stringified. `structuredContent` has zero references outside tests: ignored. `isError` handled at tool-call level. Tool `annotations` (`readOnlyHint`, `destructiveHint`): zero references: ignored.
- Not supported (zero source references, open issues): elicitation (#11526, 16 reactions; URL-mode #13267), tasks, MCP Apps/ext-apps (#10641, 61 reactions). Resources and prompts: `fetchResources`/`fetchPrompts` exist on the connection and are inspected, but prompts are not surfaced in chat (#11533 open).
- Transport/session: `StreamableHTTPClientTransport` with a custom undici fetch (SSRF guard, proxy, live per-request headers, direct-bearer recovery); SDK-managed `Mcp-Session-Id`; a 400/404/405/406 with an active session is treated as "session lost" and triggers reconnection (`connection.ts` ~2312-2335); teardown sends the spec `HTTP DELETE` (`terminateStreamableSession`, bounded timeout) before `client.close()` so stateful servers do not leak sessions; SDK internal SSE reconnection is respected, higher-level backoff reconnection with `MAX_RECONNECT_ATTEMPTS`, 429 stops retries; circuit breaker against reconnection storms. SSE transport kept with the same guards; websocket supported.
- Timeouts: `timeout` per request (30 s), `initTimeout` (10 s), `sseReadTimeout` (5 min), tools/list discovery deadline 30 s, OAuth handling 10 min.
- serverInstructions: injected into the agent's instructions when configured (`packages/api/src/agents/load.ts`); bug #15081 (instructions never delivered for OAuth/OBO servers) and #15885 (instructions injected without tools) are open.

### A4. Admin governance
- Permission type `MCP_SERVERS` -> `interface.mcpServers` (`packages/data-provider/src/permissions.ts:237`): `USE`, `CREATE`, `SHARE`, `SHARE_PUBLIC`, `CONFIGURE_OBO`. Defaults (`roles.ts`): USER `USE: true`, others false; ADMIN all true. Every tool call re-checks `USE` (`MCP.js userCanUseMCPServers`, `checkAccessWithRequestCache`).
- Server visibility: `registry.getAllServerConfigs(userId, configServers, role)` merges YAML servers, admin Config overrides and DB servers filtered by ACL (cache key includes role). UI-created servers carry ACLs shareable to users, groups, roles or public at Viewer/Editor/Owner. YAML servers are governed by the feature flags and by admin Config overrides (user/role scoped); per-role hiding of individual YAML servers goes through those overrides, not the YAML itself.
- User-managed servers are restricted: remote transports only, no `${ENV}` in URLs, only `{{VAR}}` custom vars, no `audience`/`resource`/`send_resource_parameter`, no `proxy`, no server-managed fields (`omitServerManagedFields`).
- Per-tool restriction by admin: not found; tool selection is per agent by the agent author (issue #11088 "MCP Tool Filtering" open, 7 reactions). Approval/HITL policies exist per tool name (`collectMCPToolAliases`, hook matchers).
- Audit: admin routes (`api/server/routes/admin/audit.js`) and Langfuse tracing; MCP calls are logged with `[MCP][server][tool][User: id]` prefixes.

Notes.
- Docker: the only "gateway" here that is explicitly single-user; useful as a reference for the Dynamic MCP vocabulary (find/add/config/remove) and for the observation that code mode is still unreliable.
- ContextForge is the most complete open-source "virtual server per audience" implementation: register gateways, compose virtual servers, scope by team, propagate identity upstream. It does not offer a model-facing search tool.
- agentgateway is the cleanest "one endpoint, filtered by claims" data plane: JWT validation, CEL rules evaluated on `list_tools` and `call_tools`, and automatic `target_` prefixing (rules see the bare name). Being a proxy, it needs the upstream servers to exist already; per-user upstream credentials are outside its scope.
- Obot and Cloudflare are the closest products to Answerable's Toolbox brief (enterprise users, many servers, one governed entry). Obot's GHSA-vw82-7fv8-r6gp (any authenticated user could use any `/mcp-connect/{id}`) is the cautionary tale for per-server URLs that rely on obscurity.
- Kong shows the enterprise pattern for ACL at both `tools/list` and `tools/call`, plus audit records keyed by session id and JSON-RPC method.
- The hubs (Composio, Nango, Pipedream, Arcade, Smithery, Zapier) all keep third-party tokens server-side and surface a connect link inside the tool result when a user lacks a connection; none rely on MCP elicitation for that.
- Meta-tool designs: Composio (search / multi-execute / manage connections / workbench), Nango (search / execute / proxy / create connection), Strata (categories -> actions -> details -> execute), Stainless (list / schema / invoke), Lasso (metadata / run), Docker Dynamic MCP (find / add). Nango's "searchable but unlisted, pin a few" is the most direct template for a hybrid catalogue.

Client-side constraints worth recording (for the apps Answerable targets):
- Claude.ai custom connectors: available on all plans; Team/Enterprise owners add connectors, users connect individually; Advanced settings accept an OAuth Client ID and Secret; otherwise DCR is attempted; servers must be reachable from Anthropic's cloud. Claude Code names tools `mcp__<server>__<tool>` (plugin form `mcp__plugin_<plugin>_<server>__<tool>`, non `[A-Za-z0-9_-]` replaced by `_`).
- ChatGPT: Responses API `allowed_tools` and `require_approval`; the `authorization` value is never stored; docs warn that many tools raise cost and latency. Third-party reports cite an error that all tool definitions must stay under 5,000 tokens (not confirmed in OpenAI docs; a community thread mentions ~19,700 characters per description instead).
- Microsoft Copilot Studio (Microsoft Learn, 2026-05-28): Streamable transport only (SSE dropped after August 2025); auth None, API key (header/query) or OAuth 2.0 in three modes: Dynamic discovery (DCR + discovery), Dynamic (DCR with manual endpoints), Manual (client id/secret, auth/token/refresh URLs, scopes); access runs through Power Platform connectors and data policies. Third-party compatibility pages cite 128 tools per agent with 25–30 recommended and a 500 KB connector response cap (not verified on Microsoft Learn).

## Part C — Patterns with evidence

### C1. Virtual server per tenant vs one global endpoint with tenant resolved from the token
- Per-tenant/per-audience virtual servers: ContextForge virtual servers, MetaMCP namespace endpoints, Gram toolsets, Kong listener routes, agentgateway per-route backends, Cloudflare portals (one per use case), Obot vMCP URLs, Arcade gateway ids, Zapier server per client. Advantages: static `tools/list` per URL (easy caching in clients that cache the catalogue), simple audit key, no dependency on token introspection to shape the catalogue. Costs: URL sprawl for the end user, a URL becomes a capability (Obot advisory), and every entitlement change means a new URL or a re-add in the client.
- Global endpoint, tools from identity: Cloudflare portal (Access identity -> servers), Obot gateway rules, Kong consumer ACL at discovery and call, agentgateway CEL on `list_tools`, Arcade User Source, Smithery scoped tokens with `metadata.userId`, and the session hubs (Composio/Nango) where the URL itself is a per-user session. Advantages: one URL to add in every app, entitlements change without client reconfiguration, one audit stream. Costs: `tools/list` must be computed per subject on every call (or per subject-version cache), clients that cache tool lists need `notifications/tools/list_changed` (LibreChat honours it; Claude.ai/ChatGPT/Copilot behaviour n/d), and `tools/call` must re-check entitlement (Kong and agentgateway both check at both stages; the ACL-at-list-only bug class is exactly Obot's advisory).
- Middle path used by several products: one global endpoint plus optional named "toolsets" selected by path or header for app-specific curation (Kong tags, agentgateway routes, Composio session toolkits, Nango `pinned_tools`). This keeps the identity model global while letting an admin hand a smaller catalogue to a specific app.

### C2. Direct tool projection vs meta-tools (search/describe/execute)
Evidence on tool count and accuracy:
- Anthropic tool search docs: accuracy "degrades once you exceed 30–50 available tools"; a five-server setup costs ~55k tokens of definitions, tool search cuts that by over 85%; recommended when 10+ tools, >10k tokens of definitions, or aggregating MCP servers (200+ tools); keep 3–5 hot tools non-deferred; namespace by service prefix.
- Anthropic "Advanced tool use" blog: Opus 4 49% -> 74% and Opus 4.5 79.5% -> 88.1% on MCP evaluations with the Tool Search Tool; ~77K -> ~8.7K tokens before work begins; programmatic tool calling 43,588 -> 27,297 tokens on complex tasks.
- Anthropic "Code execution with MCP": progressive disclosure via `servers/<server>/<tool>.ts`, 150,000 -> 2,000 tokens (98.7%) on the worked example.
- Cloudflare Code Mode: rationale only (models have seen far more code than tool calls), no measurements.
- RAG-MCP (arXiv 2505.03275): retrieval before prompting raises tool-selection accuracy 13.62% -> 43.13% and halves prompt tokens under an "MCP stress test".
- "How Many Tools Should an LLM Agent See?" (arXiv 2605.24660): adaptive shortlists averaging 7 tools nearly match showing 50 on BFCL (90.3% vs 90.8%); with Claude Sonnet 4.6, shorter adaptive lists reach 93.1% vs 87.1% for fixed five-tool lists.
- Toollery (arXiv 2609.22218): each added candidate raises tokens and latency and adds distractors; retrieval to compact candidate sets keeps accuracy on BFCL-V4 (440+ tools) and a 220-tool cockpit set.
- Klavis Strata: claims +15.2% pass@1 vs the official GitHub server and +13.4% vs Notion with progressive discovery (vendor benchmark).
- LibreChat issue #11088 documents the cost side: 20+ Atlassian tools at ~0.6–1.3k tokens each.
- OpenAI docs: many tools mean "high cost and latency"; `allowed_tools` exists for that reason. Copilot Studio third-party guidance: 25–30 tools recommended.
Design reading: direct projection is best below roughly 30–40 well-named tools; above that, either an app-side deferred loader (Claude's `defer_loading`, OpenAI `allowed_tools`) or a server-side meta-tool tier. Because Answerable cannot control OmniChat/ChatGPT/Copilot loaders, the meta-tool tier has to live in the Toolbox itself. Meta-tools cost one extra round trip and lose provider-side strict schemas on the executed tool, so keep the hot set projected directly (Nango's pin model, Anthropic's 3–5 rule).

### C3. Upstream per-user credentials (token vault patterns)
- Vault-in-the-hub: Composio connected accounts, Nango connections, Pipedream Connect, Arcade engine, Smithery, Zapier: tokens never reach the client; a tool result carries a connect link when a connection is missing. Nango: "The agent never sees raw credentials". Obot's token-brokering argument: the client holds only a control-plane token scoped to MCP; the gateway exchanges it internally (RFC 8693 style) so the raw OAuth credential stays in the vault, revocation is central, and audit is complete.
- Vault-in-the-IdP: Auth0 Token Vault: `grant_type=urn:ietf:params:oauth:grant-type:token-exchange`, `requested_token_type=urn:auth0:params:oauth:token-type:federated-connection-access-token`; the agent exchanges the user's Auth0 token for a Google/Microsoft/Slack/GitHub token. LibreChat's OBO does the equivalent against Entra (jwt-bearer) and its OpenID token passthrough placeholders hand raw upstream tokens to trusted servers.
- Client-side vault (LibreChat): per-user encrypted rows, refresh leases, generation ids; workable but every client app repeats the work, which is the argument for doing it once in the Toolbox.

### C4. Naming and namespacing
| Consumer | Rule |
| --- | --- |
| MCP SEP-986 (Final, created 2025-07-16) | SHOULD be 1–64 chars, case-sensitive, `A-Z a-z 0-9 _ - . /`, no spaces/commas, unique per namespace; examples `user-profile/update`, `admin.tools.list` |
| Anthropic Messages API (`define-tools`, fetched 2026-09-28) | `^[a-zA-Z0-9_-]{1,128}$` (older docs said 64; the current page says 128) |
| OpenAI function tools | letters, numbers, `_`, `-`, max 64 (community error text and SDK docs) |
| LibreChat | model-facing key `${tool}_mcp_${server}`; no truncation; #7435 hit OpenAI's 64 |
| Claude Code / Agent SDK | `mcp__<server>__<tool>`; other chars replaced by `_` |
| agentgateway | `<target>_<tool>` when multiplexing (`prefixMode`) |
| Anthropic guidance | prefix by service (`github_list_prs`), consolidate related operations into one tool with an `action` parameter |
Budget arithmetic for the Toolbox: if OmniChat registers the server as `toolbox`, LibreChat's key is `<tool>_mcp_toolbox` (+12 chars); to stay under 64 for OpenAI-backed agents, tool names must be <= 52; a 48-char ceiling leaves room for longer server aliases. Avoid `.` and `/` (valid in SEP-986, invalid for OpenAI and Anthropic).

## Recommendations for Answerable's Toolbox

1. Topology: one global Streamable HTTP endpoint (e.g. `https://toolbox.<domain>/mcp`), stateless JSON responses where possible (no server-held session state; accept and ignore `Mcp-Session-Id`, answer DELETE with 200/405), identity from the Answerable ID access token on every request; `tools/list` computed per subject from admin-managed user/group grants and re-checked on every `tools/call` (Kong/agentgateway two-stage model; Obot advisory as the anti-pattern). Optional named toolsets via path (`/mcp/<toolset>`) for app-specific curation, but never as the security boundary.
2. OAuth contract (LibreChat-verified): return 401 with `WWW-Authenticate: Bearer resource_metadata="https://toolbox.<domain>/.well-known/oauth-protected-resource/mcp"` on HEAD, GET and POST; PRM `resource` must equal the canonical MCP URL (LibreChat aborts otherwise), `authorization_servers: [<Answerable ID issuer>]`, `scopes_supported` limited to what the Toolbox actually wants (LibreChat requests exactly that list); Answerable ID must expose RFC 8414 metadata, accept RFC 8707 `resource` on authorise, token and refresh (or reject it in a way that is not fatal), tolerate `scope` on refresh, and either support RFC 7591 DCR or document a pre-registered public client id (LibreChat then uses `token_endpoint_auth_method: none` with PKCE). Confirm Answerable's entitled-scope-subset issuance (60ce89b/d55220d) composes with the `scopes_supported` list LibreChat sends.
3. Catalogue shape: default direct projection of the user's hot set (target <= 30–40 tools, hard cap ~50) with `<domain>_<verb>` names <= 48 chars, `[a-z0-9_]` only, descriptions of 3–4 sentences; a meta-tool tier (`toolbox_search_tools`, `toolbox_describe_tool`, `toolbox_execute_tool`) always present for the long tail, with the hot set pinned (Nango model); admin-set per-user "mode" (direct only, direct + search, search only) to fit ChatGPT's tighter budget and Copilot's ceiling.
4. Change propagation: emit `notifications/tools/list_changed` to open sessions when grants change; document that clients without list_changed support (Claude.ai, ChatGPT, Copilot: n/d) need a reconnect; keep the per-subject catalogue versioned (ETag-style) so LibreChat's lazy discovery and cache generations stay cheap.
5. Results: always include a `text` mirror of `structuredContent` (LibreChat ignores structured, Claude Code shows only structured per project memory); set `annotations` (`readOnlyHint`, `destructiveHint`) for clients that use them; return `isError: true` with a plain-language next step and, for third-party connections, a connect link (Pipedream/Composio pattern) since LibreChat has no elicitation; add `instructions` in `initialize` and expect OmniChat admins to set `serverInstructions: true` (note #15081).
6. Credential vault: hold upstream credentials in the Toolbox keyed by Answerable ID subject and provider; first-party adapters take the user's Answerable ID token via RFC 8693 token exchange or scoped internal tokens; third-party OAuth runs through the Toolbox's own callback, encrypted at rest with per-generation ids and single-flight refresh (LibreChat's `tokens.ts` shows the race classes to cover).
7. Audit and safety: log subject, group grants version, tool, server, argument hash, latency and error per call (Kong/Cloudflare field set); rate limit per subject; SSRF-guard any URL an adapter fetches.
8. Acceptance matrix in `mcps/e2e`: LibreChat v0.8.8-rc4 (discovered flow with DCR and with a pre-registered public client; `send_resource_parameter` default), Claude.ai custom connector (with and without client id/secret), Claude Code, ChatGPT developer mode (`allowed_tools`), Copilot Studio (Dynamic discovery mode, Streamable only). Include a probe that HEAD returns 401 with the header.

## Open questions
- Q-RESOURCE-PARAM: does Answerable ID (Better Auth 1.7.2 OAuth provider) accept `resource` on authorise/token/refresh? LibreChat sends it by default and only admins can disable it per server; if ID rejects it, OmniChat needs `send_resource_parameter: false` while Claude.ai/Copilot behaviour must be tested separately.
- Do Claude.ai, ChatGPT and Copilot Studio re-fetch `tools/list` per session or cache it, and do any honour `list_changed`? Not documented; test.
- ChatGPT's reported 5,000-token cap on tool definitions and Copilot Studio's 128-tool ceiling are third-party claims; verify against vendor docs before sizing the direct catalogue.
- Which LibreChat version does OmniChat track, and does the fork keep the `_mcp_` naming and the admin Config override layer?
- Should Toolbox expose MCP prompts/resources at all, given LibreChat surfaces neither in chat today?
- Elicitation (URL mode) is arriving in clients over 2026; when LibreChat lands #11526/#13267, the connect-link-in-result fallback should remain for older clients.
