```sh
bun mcp new acme --description "Notes for construction projects: list, read and add notes on a project." --serve toolbox
```

An **MCP** (Model Context Protocol) server gives an AI app, such as Claude Code or Claude.ai, tools it can call: *list the notes of a project*, *add a note*. The app lists the tools, its model chooses one, and the server runs it and answers. Every tool works on one organisation's data, so a server must know who is calling and which organisation they act for. Answerable makes that automatic. You write the tools, each one a few lines. The platform supplies the rest.

## What you get without doing anything

| You get | What it means | You write |
| --- | --- | --- |
| **A database, linked to your MCP** | Its own Postgres schema, made and migrated for you on your machine and on every deploy. Every table is limited to the caller's organisation by Postgres. [Your MCP's database](/docs/mcp/database) | Your tables |
| **Sign-in with Answerable ID** | Who is calling, and their organisation, checked on every call. Your tool receives `person` and `organisation`. [Your MCP's sign-in](/docs/mcp/sign-in) | Nothing |
| **Deployment to staging, then production** | A tag ships the commit: the database, the migrations, the registration in Answerable ID, and a test that the MCP answers. [Ship an MCP](/docs/mcp/deploy) | Two `git tag` commands |

## Where an MCP runs

You choose when you make the MCP, with `--serve`, and can change it in `mcps/acme/mcp.json`.

| Where | `--serve` | Reached at | Who reaches it |
| --- | --- | --- | --- |
| **In the Toolbox** | `toolbox`, the default and the recommended choice | The Toolbox's one URL, `https://toolbox.<zone>/mcp`, as the tools `acme_<domain>_<operation>` | People whose organisation enabled the MCP, and who hold a grant that covers the tool. Staff decide both |
| **On its own** | `standalone` | `https://mcp.<zone>/acme/mcp` | People whose token carries the MCP's scopes, `acme:read` and `acme:write`. Staff give an organisation the sign-in, then the scopes |
| **Both** | `both` | Both | Each by its own rule |

The `<zone>` is `answerable-staging.uk` in staging and `answerable.org` in production. On your machine the Toolbox is `http://localhost:47400/mcp`, and an MCP on its own `http://localhost:47400/acme/mcp`. In the Toolbox one connection serves every MCP and every organisation, and staff govern each person's tools in one place. Run on its own when an MCP needs a sign-in of its own, and so a URL of its own. The Toolbox's process serves both, so neither needs a deployment of its own.

## How it works

### The building blocks

| Block | What it is | Made with |
| --- | --- | --- |
| [Read tool](/docs/mcp/tools) | Answers a question; changes nothing | `defineTool` |
| [Mutation](/docs/mcp/mutations) | Changes data in two steps: prepare a preview, then commit it with a one-time token | `defineMutation` |
| [Provider](/docs/mcp/servers#the-provider) | A named, dated set of tools, prompts and resources | `defineProvider` |
| [Server](/docs/mcp/servers#the-server) | Serves one provider over HTTP, behind Answerable ID sign-in | `createMcpServer` |
| [Manifest](/docs/mcp/servers#manifest) | The provider's contract as JSON, committed and checked on every test run | `manifest` |

Each definition is plain data, checked when the module loads. A tool is five fields: `name`, `description`, `input`, `output` and `execute`. Everything else has a default.

**In the Toolbox, on its own, or both.** The Toolbox serves an MCP alone at its own path, with its own resource. Or its provider is mounted in [the Toolbox](/docs/toolbox)'s hub, one endpoint for every organisation, where staff decide who may use each tool: [Add tools to the Toolbox](/docs/toolbox/add-tools).

### How a request is authorised

**A server served alone**

1. The host posts to the MCP endpoint. The server refuses a foreign `Host` or browser `Origin`.
2. Without a valid token, the server answers `401` with `WWW-Authenticate: Bearer resource_metadata="…"`. The host reads the [protected-resource metadata](https://datatracker.ietf.org/doc/html/rfc9728), discovers Answerable ID and signs the person in with PKCE and the server's URL as `resource`.
3. The server verifies the token against ID's published keys: issuer, audience (the server's URL), type `at+jwt`, expiry and the user and organisation claims.
4. It lists only the tools, prompts and resources whose scopes the token carries, and answers in the host's protocol version. A tool failure is a result carrying the [error envelope](/docs/mcp/errors), not a protocol error.
5. A commit applies an intent only for the person, membership and client that prepared it, with its single-use token, before it expires and while its targets are unchanged.

**Through the Toolbox**

1. The sign-in is the same, with the Toolbox's URL as `resource`. The token carries `toolbox` and no capability.
2. On every request that lists or calls tools, the Toolbox reads the person's grant strings from ID and keeps the ones their organisation's catalogue allows.
3. A capability the person may not use is not listed, and calling it is the unknown-tool error. What is listed is one tool each (direct) or a few tools that search and run capabilities (meta), by the host client's settings.
4. A mutation is prepared, then committed with the tool its policy class names. Every call is an evidence row and a span.

The server never sees a password, never runs Better Auth and never reads ID's database. [How Answerable ID works](/docs/id) explains the sign-in and the token.

## Status

**Built.** `@answerable/mcp` defines read tools, [prepared mutations](/docs/mcp/mutations) and providers, serves them on the official MCP TypeScript SDK, answers every tool failure with one [error envelope](/docs/mcp/errors), exports each provider's contract as a manifest, and checks a provider against [the standard](/docs/mcp/standard) with [the conformance kit](/docs/mcp/testing). `@answerable/auth` verifies Answerable ID access tokens. `mcps/e2e` is the reference MCP, served both in the Toolbox and on its own URL, and `mcps/example` the finished example; `mcps/admin` is [the admin MCP](/docs/admin), for Answerable staff. [The Toolbox](/docs/toolbox) mounts every MCP whose `serve` is `toolbox` or `both` in its hub, and [serves every one](/docs/mcp/servers#served-alone) whose `serve` is `standalone` or `both` at its own path. `bun mcp new` makes an MCP, `bun mcp add tool` adds a tool and `bun mcp dev` runs one on your machine, [a tag ships it](/docs/mcp/deploy) to staging, which has run, and to production, which has not, and [the acceptance](/docs/mcp/local-testing) signs organisations into the reference server, the Toolbox and the admin MCP through real ID with a browser and the official MCP OAuth client.

**Not yet.** Human approvals (a human-class intent waits and answers `APPROVAL_REQUIRED`), operations for long work, `toolbox_run`, the OpenAPI adapter, administration by an organisation's own administrators, remote providers, a production deployment and a public npm release. [The standard](/docs/mcp/standard#not-yet) lists the rules nothing enforces yet.

**External hosts.** [Connect Claude Code](/docs/mcp/claude-code) registers a client for the Toolbox or the e2e server. LibreChat signs a person into the Toolbox in the [host lane](/docs/mcp/local-testing#host-lane). Claude Code with a model against the Toolbox or the [admin MCP](/docs/admin), and Claude.ai: Not yet tested.

## Limits

**Partial entitlements.** ID issues the entitled subset of the requested scopes. A server served alone lists only the tools, prompts and resources the token's scopes cover.

**Revocation.** A server verifies tokens offline, so a disabled organisation's issued access token works until it expires; refresh stops at once. Keep resource token lifetimes short.

**Client registration.** Hosts use a client registered in ID ahead of time. Dynamic registration and client ID metadata documents: Not yet.
