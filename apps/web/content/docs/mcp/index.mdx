```sh
bun run mcp:new acme
bun install
UPDATE_MANIFEST=1 bun run --filter @answerable/mcp-acme test
bun run mcp:check @answerable/mcp-acme
```

Run these from the monorepo. They write `mcps/acme`, a server with one tool and its conformance test, install it, write its manifest with the first test run, then typecheck, lint and test it. [Author an MCP](/docs/mcp/authoring#create-a-workspace) shows what to change next.

The Answerable MCP kit builds servers that sign people in with Answerable ID. A tool is five fields (`name`, `description`, `input`, `output`, `execute`), a mutation adds `prepare` and `commit`, and everything else has a default. A server runs alone, or its provider is mounted in the Toolbox, one endpoint that serves each person exactly the capabilities their organisation granted them.

## Status

**Built.** `@answerable/mcp` defines read tools, [prepared mutations](/docs/mcp/authoring#mutations) and providers, serves them on the official MCP TypeScript SDK, answers every tool failure with one [error envelope](/docs/mcp/errors), exports each provider's contract as a manifest, and checks a provider against [the standard](/docs/mcp/standard) with [the conformance kit](/docs/mcp/testing). `@answerable/auth` verifies Answerable ID access tokens. `mcps/e2e` is the reference server. `bun run mcp:new` scaffolds a server, and [the acceptance](/docs/mcp/local-testing) signs organisations into the reference server and the Toolbox through real ID with a browser and the official MCP OAuth client.

[The Toolbox](/docs/mcp/toolbox) (`mcps/toolbox`) reads a person's grant strings from ID with a 60-second cache and an audit-log poller, holds the catalogue, and serves the granted tools directly or through its meta tools. It keeps intents in Postgres, sends `tools/list_changed` when a grant changes, records every call and intent transition in a hash-chained evidence log and every call as a span, and mounts the e2e provider. Its [admin API](/docs/mcp/toolbox-admin) enables an organisation in one call.

**Not yet.** Human approvals (a human-class intent waits and answers `APPROVAL_REQUIRED`), operations for long work, `toolbox_run`, the OpenAPI adapter and the admin MCP, administration by an organisation's own administrators, remote providers, hosted deployment and a public npm release. [The standard](/docs/mcp/standard#not-yet) lists the rules nothing enforces yet.

**External hosts.** [Connect Claude Code](/docs/mcp/claude-code) registers a client for the Toolbox or the e2e server. Claude Code against the Toolbox by hand, Claude.ai and LibreChat: Not yet tested.

Views import the official MCP Apps browser API, `@modelcontextprotocol/ext-apps`, directly. Every export of `@answerable/auth` and `@answerable/mcp` is in the [API reference](/docs/mcp/reference).

## How a request is authorised

**A server served alone**

1. The host posts to the MCP endpoint. The server refuses a foreign `Host` or browser `Origin`.
2. Without a valid token, the server answers `401` with `WWW-Authenticate: Bearer resource_metadata="…"`. The host reads the [protected-resource metadata](https://datatracker.ietf.org/doc/html/rfc9728), discovers Answerable ID and signs the person in with PKCE and the server's URL as `resource`.
3. The server verifies the token against ID's published keys: issuer, audience (the server's URL), type `at+jwt`, expiry and the user and organisation claims.
4. It lists only the tools, prompts and resources whose scopes the token carries, and answers in the host's protocol version. A tool failure is a result carrying the [error envelope](/docs/mcp/errors), not a protocol error.
5. A commit applies an intent only for the person, membership and client that prepared it, with its single-use token, before it expires and while its targets are unchanged.

**Through the Toolbox**

1. The sign-in is the same, with the Toolbox's URL as `resource`. The token carries `toolbox` and no capability.
2. On every request that lists or calls tools, the Toolbox reads the person's grant strings from ID and keeps the ones their organisation's catalogue allows.
3. A capability the person may not use is not listed, and calling it is the unknown-tool error. What is listed is one tool each (direct) or a few tools that search and run capabilities (meta), by the host client's settings.
4. A mutation is prepared, then committed with the tool its policy class names. Every call is an evidence row and a span.

The server never sees a password, never runs Better Auth and never reads ID's database.

## Limits

**Partial entitlements.** ID issues the entitled subset of the requested scopes. A server served alone lists only the tools, prompts and resources the token's scopes cover.

**Revocation.** A server verifies tokens offline, so a disabled organisation's issued access token works until it expires; refresh stops at once. Keep resource token lifetimes short.

**Client registration.** Hosts use a client registered in ID ahead of time. Dynamic registration and client ID metadata documents: Not yet.
