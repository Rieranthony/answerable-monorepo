```sh
bun run mcp:test:e2e
```

The acceptance tests the MCPs against a real Answerable ID, through ID's pages in a real browser and the official MCP client, and runs `bun mcp` end to end. CI runs it on every push. To run one MCP on your machine and try it in Claude Code, use [Run an MCP on your machine](/docs/mcp/run-locally) instead.

## Run the acceptance

```sh
bun install
(cd packages/acceptance && bun x playwright install chromium)
bun run mcp:test:e2e
```

Requires Bun 1.3.1, Docker Compose and the development Postgres on `47432` (`bun run env:up`, from the main checkout). Run it from the repository root. It runs `bun test` in `packages/acceptance`: the journeys and the kit's own tests. It exits non-zero when a test fails, and it removes its database and processes either way, including after Ctrl-C (exit 130) or SIGTERM (exit 143).

## What the acceptance proves

Each journey file in `packages/acceptance/src/journeys` starts what it needs, signs people in through a real browser where it uses ID, and says in its test names what it proves; `packages/acceptance/README.md` lists the files. `e2e`, `toolbox` and `admin` cover the e2e MCP at its path, the Toolbox and the admin MCP against a real ID; `mcp-cli` registers ID as `bun mcp setup` and `bun mcp dev` do, then signs in through those registrations and reads who is calling from ID in `example`'s `notes.add`; `register` runs the register Job's code; and `scaffold` runs `bun mcp new`, `check`, `add tool` and `list` in a copy of the working tree, against the development Postgres on `47432`, with no ID. The tests are the record: what each asserts, and the timings it prints, are in the files and in the run's output.

## Ports

| Service | Loopback port |
| --- | --- |
| Disposable PostgreSQL | `47532` |
| ID | `47600` |
| OAuth callback | `47603` |
| Toolbox, and e2e at `/e2e/mcp` | `47604` |
| A second Toolbox, for the e2e journeys | `47605` |
| Admin MCP | `47606` |

Keep these free. The scaffold journey also needs the development Postgres on `47432`, as `bun run mcp:test` does. PostgreSQL on `47532` belongs to the Compose project `answerable-mcp-e2e` and holds ID's database, the Toolbox's `answerable_toolbox_acceptance` and the shared MCP database `answerable_mcps_acceptance`, with its two logins; the run never reads your `DATABASE_URL`. Journey files run one after another, each that uses ID starting and stopping its own, so they share these ports and cannot run in parallel. Two runs at once cannot either: the Compose project name is fixed, so one run's cleanup removes the other's PostgreSQL. Run one at a time.

## The kit

`@answerable/acceptance` (`packages/acceptance`) exports these functions, and `intentSchema`, the Zod schema of what a prepare tool answers as far as the journeys read it. Everything that a journey varies is provisioned by the kit through ID's admin API with the root secret, the plan's organisations, domains and single sign-on included. The fixture only starts the plan's company directories (`tenants`, `platform` and `spares`), before ID boots, so that ID trusts them.

| Function | What it does |
| --- | --- |
| `startId({ tenants, platform?, spares? })` | Starts PostgreSQL and ID, and returns `{ manifest, admin, stop }`. `tenants` is `[{ slug, signIns }]`: one organisation each, which `startId` creates and connects to a company directory that accepts `signIns` sign-ins. `platform: { signIns }` gives the platform organisation (Answerable staff) the domain `answerable.example.test` and such a directory for `staff@answerable.example.test`; given a list such as `["staff", "colleague", "staff"]`, the directory's sign-ins are each listed person's, `<person>@answerable.example.test`, in that order. `spares` is `[{ slug, signIns }]`: directories that ID trusts from boot and no organisation uses yet, for organisations a journey creates later (ID accepts an identity provider's endpoints only if they were listed at boot). `manifest` holds `idOrigin`, `adminResource`, `rootSecret`, each tenant's `slug`, `email` and `organizationId`, `platform` (`organizationId`, `domain` and `email`, when the plan had one) and `spares` (each directory's `slug`, `domain`, `email`, `issuer`, `authorizationEndpoint`, `tokenEndpoint`, `jwksEndpoint`, `clientId` and `clientSecret`). |
| `id.admin(method, path, body?, headers?)` | Calls ID's admin API as root with a fresh `Idempotency-Key` and any extra `headers`. A status outside 2xx throws with the body. |
| `id.stop()` | Ends ID, brings PostgreSQL down with its volume, removes the temporary directory and closes everything else the kit opened. Safe to call twice; also runs on Ctrl-C and SIGTERM. |
| `registerResource(admin, { identifier, scopes, accessTokenTtl })` | Registers the MCP's resource; `offline_access` is added to `scopes` unless listed. |
| `registerClient(admin, { clientId, redirectUri, scopes })` | Registers a public client for the authorisation code and refresh token grants. |
| `linkClient(admin, clientId, resource)` | Lets the client ask for the resource. |
| `grantOrganisation(admin, organizationId, { clientId, resource, scopes, entitledScopes? })` | Approves the client and the resource for an organisation and entitles its members to `entitledScopes`, all of `scopes` by default. |
| `registerMachine(admin, organizationId, clientId, audiences)` | Registers a machine client owned by the organisation, for the `client_credentials` grant. `audiences` maps each resource to the scopes the client may ask there: `{ [manifest.adminResource]: ["platform:read"], [toolboxAdmin]: ["toolbox:admin"] }`. Returns `{ clientId, clientSecret }`; ID shows the secret once. |
| `setSsoProvider(admin, organizationId, spare)` | Sets an organisation's single sign-on to a spare directory from `manifest.spares`, with the directory's own credentials. The organisation must already hold `spare.domain` and have no single sign-on yet: the call sends `If-None-Match: *`. |
| `serve(port, fetch)` | Serves a fetch handler on a loopback port until the kit stops. |
| `serveCallback(callback)` | Serves the sign-in's OAuth callback URL on its port until the kit stops, answering the browser ID sends back. |
| `launchBrowser()` | Starts headless Chromium with Playwright's signal handlers off, so cleanup runs on Ctrl-C. |
| `signIn(browser, { idOrigin, resource, clientId, callback, scopes }, { slug, email, scopes })` | Signs one person in as a host does, in a browser, or in one of its contexts when ID's session must carry from one sign-in to the next: the SDK follows the MCP's `401`, a real browser completes ID's pages, the SDK exchanges the code. Returns an `OAuthSession`, `{ provider, state }`: the SDK's `OAuthClientProvider` for a client registered in ID ahead of time, and the tokens, authorisation URL and discovery result it saved. The first `scopes` are what the MCP advertises; the second are what the organisation is entitled to, and the consent page must list exactly those and name the rest as not approved. |
| `verifySignIn(context, idOrigin)` | What ID's Security page asks of a person whose last company sign-in is too old: in the context that holds their ID session, opens `<idOrigin>/security`, chooses **Verify sign-in**, and returns when the company directory has brought the browser back. ID makes a new session, so the next `signIn` through the context carries the new sign-in time. Throws with ID's message when ID refuses. Takes one queued sign-in. |
| `signInRefused(browser, target, tenant)` | Like `signIn`, for a person ID refuses, such as one of an organisation that is not yet entitled to the MCP. Returns the refusal ID shows at the organisation chooser at once, where `signIn` would wait 30 seconds for a consent page. |
| `connect(resource, provider, protocol)` | Connects the official MCP client, as a `"2025"` client or pinned to `"2026-07-28"`. A `"2026-07-28"` client hears `tools/list_changed` once it calls `listen({ toolsListChanged: true })` with a handler set by `setNotificationHandler`, as J3 does. |
| `tool(client, name, args?)` | Calls a tool and returns its `structuredContent`. A failed call throws with the envelope's code and message. |
| `refusal(client, name, args?)` | Calls a tool that must fail and returns the `error` of its envelope, read with [`errorOf`](/docs/mcp/testing#serve-a-provider-in-process). |
| `refreshRefused(session, clientId, resource)` | Refreshes the session's tokens for `resource` as `clientId` and throws unless ID answers `400 invalid_grant`, as it does once the organisation is disabled. |
| `step(message)` | Prints `[acceptance] message`. |

## Write a journey

Save this as `packages/acceptance/src/journeys/records.journeys.test.ts` and run `bun run mcp:test:e2e`. It signs one organisation in and reads its records.

```ts
import { afterAll, beforeAll, expect, test } from "bun:test"
import { connect, grantOrganisation, launchBrowser, linkClient, registerClient, registerResource, serve, serveCallback, signIn, startId, tool, type Id, type OAuthSession } from "../index"
import { prepareToolbox } from "../toolbox"

const origin = "http://127.0.0.1:47604"
const resource = `${origin}/e2e/mcp`
const callback = "http://127.0.0.1:47603/callback"
const clientId = "my-journey"
const scopes = ["e2e:identity", "e2e:read", "e2e:write"]
let id: Id
let oauth: OAuthSession

beforeAll(async () => {
  id = await startId({ tenants: [{ slug: "acme", signIns: 1 }] })
  const { admin, manifest } = id
  const acme = manifest.tenants[0]!
  await registerResource(admin, { identifier: resource, scopes, accessTokenTtl: 60 })
  await registerClient(admin, { clientId, redirectUri: callback, scopes })
  await linkClient(admin, clientId, resource)
  await grantOrganisation(admin, acme.organizationId, { clientId, resource, scopes })
  const { start } = await prepareToolbox(id, { database: "answerable_toolbox_acceptance" })
  serve(47_604, (await start(origin)).fetch)
  serveCallback(callback)
  oauth = await signIn(await launchBrowser(), { idOrigin: manifest.idOrigin, resource, clientId, callback, scopes }, { slug: acme.slug, email: acme.email, scopes })
})
afterAll(() => id?.stop())

test("a new organisation has no records", async () => {
  const client = await connect(resource, oauth.provider, "2026-07-28")
  expect(await tool(client, "records_list")).toEqual({ items: [], next_cursor: null, has_more: false })
})
```

**Serve the MCPs in the test process.** `prepareToolbox(id, …)` and `startToolboxStack(id, …)` (`src/toolbox.ts`) start the Toolbox as the deployment runs it, with the MCPs of its generated list over `answerable_mcps_acceptance`, in its hub and at their paths; each journey registers the resources and clients it signs in to. `start(origin)` builds a Toolbox at another origin, or the same one again on fresh pools, when a journey needs a token refused elsewhere or a restart.

**`signIns`** counts the company sign-ins a directory may perform: one per `signIn`, `signInRefused` or `verifySignIn`, for a tenant, the platform organisation or a spare. A person who signs in more often than queued fails at the company directory. The platform organisation's list form queues several people in the order they sign in.

**Every file gets its own ID.** Start it in `beforeAll` and call `stop()` in `afterAll`, as above. A `startId` that throws has already stopped.

Copy `e2e.journeys.test.ts` for a fuller one: several organisations, a partial entitlement, refresh and revocation.

## Faster checks

```sh
bun run mcp:test
```

This runs the `@answerable/auth`, `@answerable/id-admin`, `@answerable/mcp`, `@answerable/mcp-postgres`, `@answerable/mcp-platform`, e2e, Toolbox and admin MCP suites and `bun mcp`'s with a local test issuer, including Chromium rendering the real MCP Apps view through the official host bridge. It also runs every MCP that `bun mcp new` has added under `mcps/`. These suites need the development PostgreSQL on port `47432` (`bun run env:up`): the servers' reset their own test databases first, each MCP's resets its own schema in `answerable_mcps_test`, and the Toolbox's and `@answerable/mcp-platform`'s make shared MCP databases of their own, with logins of their own, and drop them at the end. It does not include the acceptance, which holds `bun mcp`'s end-to-end run.

## Run the e2e MCP by hand

```sh
bun mcp dev e2e
```

e2e is served both ways, so this starts the Toolbox with e2e in its hub and at `http://localhost:47400/e2e/mcp`, registers its client, `claude-code-e2e`, and prints both commands. [Run an MCP on your machine](/docs/mcp/run-locally#run-an-mcp) says what it does; [Connect Claude Code](/docs/mcp/claude-code#the-e2e-server) what you see.

## Host lane

```sh
bun packages/acceptance/scripts/host-lane.ts
```

`bun mcp dev` is the everyday local loop; this lane checks a host. It tries the Toolbox from two real hosts. It is also the way to sign in from Claude Code without a company directory's credentials: [Signing in needs a company directory](/docs/mcp/run-locally#signing-in-needs-a-company-directory). It starts real ID and the Toolbox on ports `47600` and `47604`, with one organisation entitled to `e2e/records` only, and keeps them up until Ctrl-C. It prints the email to type at ID's sign-in and the commands below, and logs each request the Toolbox answers and each OAuth event ID records. It is not part of `mcp:test:e2e` and cannot run beside it: the ports and the Compose project are the same. It starts the Toolbox from the same code as the Toolbox journeys (`startToolboxStack`), which prove what it serves.

**Claude Code.**

```sh
claude mcp add --transport http toolbox-lane http://127.0.0.1:47604/mcp --client-id claude-code-lane --callback-port 47700
```

Then `/mcp`, choose `toolbox-lane` and **Authenticate**. The Toolbox lists that client seven tools and no `e2e_identity_get`. To see the prompt for `toolbox_commit_confirmed` under an allow rule, allow `mcp__toolbox-lane` in `/permissions` and ask Claude to create a record and delete it.

**LibreChat.**

```sh
docker compose -p answerable-host-lane -f packages/acceptance/host-lane/compose.yaml up -d
```

Open `http://localhost:3080`, register an account, open **MCP Settings**, choose **Connect** on `toolbox` and **Continue with OAuth**. `docker compose -p answerable-host-lane -f packages/acceptance/host-lane/compose.yaml down --volumes` removes it. The images take 2.6 GB (LibreChat) and 940 MB (MongoDB) on disk.

**Why the extra service.** ID's fixture names itself `http://127.0.0.1:47600`, and the Toolbox is `http://127.0.0.1:47604`, so the token's issuer and audience are loopback addresses that inside a container mean the container. The `bridge` service shares LibreChat's network and forwards those two ports to the host, and `librechat.yaml` lists them in `mcpSettings.allowedAddresses`, which LibreChat needs for any private address. Its `oauth.scope` adds `offline_access`; without it LibreChat gets no refresh token ([The Toolbox](/docs/toolbox#limits)).

Ports beyond the acceptance's: `3080` (LibreChat) and `47700` (Claude Code's callback).

## Admin lane

```sh
bun packages/acceptance/scripts/admin-lane.ts
```

`bun mcp dev` is the everyday local loop; this lane checks the admin MCP. It tries the whole onboarding story from Claude Code by hand. It starts real ID, the admin MCP and the Toolbox on ports `47600`, `47606` and `47604`, registered as the admin journeys register them, makes the staff member an owner, and keeps everything up until Ctrl-C. It prints the staff email, the `claude mcp add` command for the admin MCP, the organisation to create (slug `newco` and its domain) and the command for the Toolbox, then the email of the new organisation's person. While it runs it sets the SSO provider of any organisation that holds the spare directory's domain, because a directory with its own credentials needs a secret no tool takes. It is not part of `mcp:test:e2e` and cannot run beside it. [Try it locally](/docs/admin/setup#try-it-locally) has the prompts to type and what each step shows; the admin journeys run the same story headlessly. Both lanes remove ID, its database and their servers when a step fails, and on Ctrl-C.

## Errors

| You see | Meaning | What to do |
| --- | --- | --- |
| `Executable not found in $PATH: "docker"` | Docker is not installed, or not on `PATH` | Install Docker with Compose v2 and start it |
| `Command failed: docker compose -p answerable-mcp-e2e`, often with `ports are not available` | Compose could not start PostgreSQL: port `47532` is taken (often by another run), or the Docker daemon is not running | Wait for the other run, or free the port; start Docker |
| `Failed to start server. Is port 47604 in use?` (or `47603`, `47605`) | A journey could not listen | Find the holder with `lsof -nP -iTCP:47604 -sTCP:LISTEN` and stop it |
| `ID fixture stopped (1)`, after `Failed to start server. Is port 47600 in use?` | ID could not listen on `47600` | Free the port and run again |
| `Timed out after 90000 ms waiting for the ID fixture` | ID was not ready within 90 seconds. Seen at a load average of 132 | Run again on a quieter machine, or pass a larger `timeoutMs` to `startId` |
| `launch: Executable doesn't exist at …` | Playwright's Chromium is not installed | Run `(cd packages/acceptance && bun x playwright install chromium)` |
| `[acceptance] ID page: /path text` before a Playwright timeout | A step on ID's pages did not appear within 30 seconds; the text is what ID showed instead | Read the page text: an error page names the cause, such as a scope the organisation is not entitled to |
| `POST /… returned 400: {…}` | ID's admin API refused a provisioning call | Read the `errors` in the body, for example `Scopes are not allowed for this resource` |
| `ID refused Verify sign-in` with "Your provider must confirm when you authenticated" | The company directory's identity carried an `auth_time` older than the flow: ID accepts only a sign-in made since Verify sign-in began, and at most five minutes ago | In a journey, queue the sign-in in the plan, not in a fixture that stamped the time at boot |
| `<slug> never signed in; the first test shows why` | The first journey test failed, so the later ones have no session | Fix the first failure |

## Limits

**What it certifies.** The acceptance does not certify an external host, a real company directory or a production deployment. The [host lane](#host-lane) and [Connect Claude Code](/docs/mcp/claude-code) try two hosts by hand.

**The MCP under test** runs inside the test process on a real port, not as a separate deployed process.

**Time.** Token lifetimes and intent expiry use real time; no journey controls a clock.

**Browser.** Chromium only.

**Shutdown.** ID ends with `SIGKILL`, not a graceful shutdown; its database is removed with the container. After Ctrl-C the command can return up to about a second before Compose finishes bringing PostgreSQL down.
