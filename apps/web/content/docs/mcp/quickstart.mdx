---

```sh
bun mcp new acme --description "Notes for construction projects: list, read and add notes on a project." --serve toolbox
```

An MCP gives an AI host, such as Claude Code, tools it can call. With `@answerable/mcp` each tool is plain data: a name, a description, the shape of its input and output, and a function. The kit does the rest: sign-in through [Answerable ID](/docs/id), who is calling, a database limited to their organisation, checking every input and output, errors the model can act on, and the protocol.

You will build `acme`, an MCP that keeps notes: `notes.list` reads them and `notes.add` adds one. The finished code is `mcps/example` in the repository, made with the same commands; every snippet below comes from it, so it compiles and its tests pass.

**Before you start.** Bun 1.3.1, a checkout of the monorepo, and the development PostgreSQL on port 47432 (`bun run env:up`). Run every command from the repository root. Handing this to a coding agent instead? Use the [prompt](/docs/agents#build-an-mcp-server).

### Make the MCP

Run the command above. In a terminal, `bun mcp new` asks for what you leave out: the name, what the MCP is for, where it runs and a first tool. Without a terminal, as in a coding agent's shell, it asks nothing: the name, `--description` and `--serve` are required, and a missing one exits with code 2 and prints the command to run, with placeholders.

It checks every answer before it writes anything, then prints one line per step:

| Step | What it does |
| --- | --- |
| `write` | Writes `mcps/acme` |
| `generate` | Writes `charts/answerable/mcps.json`, the list of MCPs the deployment reads, and the lists the Toolbox and the standalone server serve, with their dependencies |
| `install` | `bun install`, which links the new workspace |
| `database` | Creates schema `acme` and its two roles in `answerable_mcps` on the development Postgres |
| `migration` | Writes the first migration, `drizzle/0000_initial.sql` |
| `manifest` | Runs the tests once to write `manifest.json`, the MCP's contract |
| `generate` | Writes the list again, now with the MCP's scopes |
| `check` | `bun mcp check acme`: the typecheck, the lint and the tests |

The name is the provider id: a lowercase letter, then up to 11 lowercase letters or digits. It prefixes every tool, `acme_notes_list` in the Toolbox, and names the database schema. `--serve toolbox` declares that it runs in the Toolbox, in `mcp.json`:

### Add a read tool

```sh
bun mcp add tool acme notes.list --description "List your organisation's notes, newest first, 20 per page by default and at most 100. When has_more is true, pass next_cursor as cursor to read the next page."
```

It writes `src/tools/notes-list.ts` and its test, adds the tool to `src/provider.ts`, adds the `notes` table to `src/db/schema.ts`, writes the migration and the manifest, and checks the MCP:

<include lang="ts" meta='title="src/tools/notes-list.ts"'>../../../../../mcps/example/src/tools/notes-list.ts#list</include>

Five fields make a tool, and a sixth gives an example:

| Field | What it is |
| --- | --- |
| `name` | `<domain>.<operation>`. Hosts call it `notes_list` |
| `description` | What the model reads to choose a tool: what it does, when to use it and its limits. 40 to 1,000 characters |
| `input` | A Zod object: the arguments. Unknown fields are refused |
| `output` | A Zod object: the result. The server checks it before it leaves |
| `execute` | The function. It receives the checked input and the caller: `person`, `organisation`, the AI app they use and `db`, the MCP's database |
| `example` | One valid input, checked when the file loads. The conformance kit calls the tool with it |

A list returns a page at a time, with `limit`, `cursor`, `next_cursor` and `has_more`: the standard's [pagination](/docs/mcp/tools#pagination) rule, which the conformance kit checks. Every other field: [Read tools](/docs/mcp/tools).

The table it reads:

<include lang="ts" meta='title="src/db/schema.ts"'>../../../../../mcps/example/src/db/schema.ts#notes</include>

Every table has `organisation_id` and the `organisationIsolation` policy, so Postgres limits every query to the caller's organisation, even one that forgets to filter.

### Add a mutation

```sh
bun mcp add tool acme notes.add --mutation --description "Prepare adding a note to your organisation. Changes nothing: returns a preview and a commit token; commit the intent with the tool its commit_tool names to add the note."
```

A tool that changes data works in two steps, so a person can see what will happen before it does:

<include lang="ts" meta='title="src/tools/notes-add.ts"'>../../../../../mcps/example/src/tools/notes-add.ts#add</include>

1. **Prepare.** `prepare` works out the change and returns a preview, with a summary in plain words that names the organisation. It changes nothing. The host receives an *intent*: the preview, a one-time commit token and the name of the commit tool to call.
2. **Commit.** The host calls that commit tool with the token. `commit` then applies exactly what was prepared.

`risk: "normal"`, the default, makes the host show the person the summary first; `"low"` lets the agent commit on its own. A mutation's description says that it prepares an intent: `bun mcp add tool` and the conformance kit refuse one that does not. [Mutations](/docs/mcp/mutations) explains the rest.

### Test and check it

Each tool has its own test, which `add tool` wrote beside it, and `src/provider.test.ts` runs the conformance kit. This one also adds a note and lists it, as a host would:

<include lang="ts" meta='title="src/provider.test.ts"'>../../../../../mcps/example/src/provider.test.ts</include>

```sh
bun mcp check acme
```

- `assertProviderConformance` registers one test per check of the standard, for every tool, calling each with its `example`, and compares `manifest.json` with the code.
- `createTestMcp`, from `@answerable/mcp-postgres/testing`, serves the MCP inside the test with a local ID issuer, the official MCP client and its own schema in `answerable_mcps_test`: no port, no network. `connect()` signs in as the test person of a new organisation each time.
- `bun mcp check` runs the typecheck, the lint and the tests with a 100% coverage gate. A stale manifest is rewritten, and the check says to commit it.

[Test an MCP](/docs/mcp/testing) covers every check and helper.

</Step>
<Step>

### Run it

**Run it locally.** It has no server of its own: the Toolbox mounts it when its `serve` is `toolbox` or `both`, and the standalone server serves it at `http://localhost:47510/<name>/mcp` when its `serve` is `standalone` or `both`, each from a list `bun mcp` generates from `mcp.json`.

```sh
bun mcp db example migrate
bun run toolbox:dev
```

`bun mcp db example migrate` makes its schema in your local `answerable_mcps`, which `bun mcp new` already did; run it again after a migration. `bun run toolbox:dev` serves it at `http://localhost:47400/mcp` as `example_<domain>_<operation>`, or `bun run standalone:dev` at its path. Signing in to it needs the servers' registrations in your local ID: [the Toolbox's](/docs/toolbox#run-it-locally), [the standalone server's](/docs/mcp/claude-code#the-e2e-server). A single command that does all of it, `bun mcp dev`: Not yet.

</Step>

## What you built

| File | What it does |
| --- | --- |
| `mcp.json` | Where the MCP runs and its database mode; `bun mcp` writes it, and you may change `serve` and `database` |
| `src/mcp.ts` | `defineTool` and `defineMutation` bound to the MCP's database; never edited |
| `src/provider.ts` | The provider: the MCP's id, description, version, database and tools |
| `src/tools/*.ts` | One tool per file, each with its test |
| `src/db/schema.ts` | The MCP's tables, in its own Postgres schema |
| `drizzle/` | Its migrations, written by `bun mcp db acme generate` |
| `src/provider.test.ts` | The conformance kit and your own tests, in-process |
| `manifest.json` | The contract, rewritten by `bun mcp check` and reviewed with every change |

## Errors

`bun mcp` exits with 2 when it refuses before writing anything, and with 1 when a step fails after. A refusal names every wrong or missing answer at once, a line each, then one command to run again with a placeholder in place of each. With `--json` it is `{ "ok": false, "error": { "code", "message", "fix", "problems": [{ "code", "message" }] } }`: one entry in `problems` for each answer, each with its stable `code`.

| You see | Code | What to do |
| --- | --- | --- |
| `MCP name "…" must be a lowercase letter then up to 11 lowercase letters or digits, for example acme` | `invalid-name` | Use a name such as `acme` |
| `acme is taken by mcps/acme; choose another name` | `name-taken` | Choose another name |
| `toolbox is reserved; choose another name` | `name-reserved` | Choose another name; `standalone`'s says to pass `--serve standalone` |
| `Missing --serve: where it runs, toolbox, standalone or both` | `missing-argument` | Run the command it prints, with the placeholders filled in |
| `acme has a tool notes.list: mcps/acme/src/tools/notes-list.ts; choose another name` | `tool-exists` | Choose another tool name |
| `acme/notes.add: a mutation's description must say that it prepares an intent…` | `mutation-description` | Say "prepare" or "intent" in the description |
| `database failed: the development Postgres does not answer on localhost:47432…` | `database-failed` | Start Postgres, then run the command under `Finish the job with:` |
| `…/manifest.json is out of date; regenerate it with UPDATE_MANIFEST=1…`, from `bun run mcp:check` | | Run `bun mcp check acme`, which rewrites it, review the diff and commit |
| A conformance test fails, such as `list_paginates` | | [Test an MCP](/docs/mcp/testing#errors) says what to change for each message |
| `Tool name "…" must be <domain>.<operation>…` when the module loads | | [When a definition is refused](/docs/mcp/errors#when-a-definition-is-refused) |
