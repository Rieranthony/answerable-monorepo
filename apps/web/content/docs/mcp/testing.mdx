This is the e2e server's; `mcps/example/src/provider.test.ts` has a smaller one. Put it in a test file of the provider's workspace and run `bun run test`. It registers one test per check from [the standard's checklists](#the-checks), so a failing test names the check and the tool to change. Call it at the top level of a test file, once for each provider.

## Serve a provider in-process

`assertProviderConformance` serves the provider with `createTestMcp`, signs in as one caller who holds every scope the provider advertises, and gives the server its own intent store.

Use `createTestMcp` directly to test your own logic. It serves a provider inside the test process with a local ID issuer and the official MCP client: no port, no network.

<include lang="ts" meta='title="mcps/example/src/provider.test.ts"'>../../../../../mcps/example/src/provider.test.ts#add-then-list</include>

The MCP's URL is `https://mcp.test/mcp`.

| Option | Default |
| --- | --- |
| `connect({ scopes })` | Every scope the MCP advertises |
| `connect({ organizationId, userId, membershipId })` | Random UUIDs |
| `connect({ clientId })` | `test-client` |
| `connect({ protocol })` | The client's default; `"2026-07-28"` pins the new revision |

Pin `userId`, `organizationId` and `membershipId` to connect as the same principal twice, for example to replay a commit from a second connection. `mcp.fetch` sends a raw HTTP request, for example to check a `401`. `mcp.issuer.sign` makes an unusual token, such as an expired one. `mcp.close()` closes every client.

**Server options.** In place of a provider, pass a function that builds the server from the local issuer's `auth`. To move time, give the server a store whose clock you control; the store decides every expiry:

<include lang="ts" meta='title="mcps/example/src/intents.test.ts"'>../../../../../mcps/example/src/intents.test.ts#expiry</include>

**A refusal.** `errorOf(result)` returns the `error` of a failed call's [envelope](/docs/mcp/errors), and throws, saying what is wrong, when the call succeeded or the result is not the envelope:

<include lang="ts" meta='title="mcps/example/src/errors.test.ts"'>../../../../../mcps/example/src/errors.test.ts#refusal</include>

**A caller without a server.** `testPrincipal(overrides?)` returns a verified caller for code that takes a principal, such as a store: fresh ids, the client `test-client`, no scopes and a directory sign-in now (`upstreamAuthTime`), each replaced by `overrides`. `records.create(testPrincipal({ organizationId }), "Title")` seeds a record for a connection with that `organizationId`.

`mcps/example/src/*.test.ts` and `mcps/e2e/src/mcp.test.ts` are working examples. Reference: [`createTestMcp`](/docs/mcp/reference#createtestmcp), [`errorOf`](/docs/mcp/reference#errorof), [`testPrincipal`](/docs/mcp/reference#testprincipal).

## The fixture

<AutoTypeTable path="../../packages/mcp/src/kit.ts" name="ConformanceFixture" />

- **`manifest`**: `manifest_matches_snapshot` compares the file with `manifest(provider)`.
- **`examples`**: `read_has_no_side_effect` and the mutate checks call each definition with its example. A function runs each time the kit needs an input, so a delete gets a fresh record every time.
- **`moveTarget`**: `commit_rejects_stale` moves a target, then commits. Needed only when a mutation prepares targets; the check fails without it.

While it registers the checks, the kit prepares each mutation once with its example, to see whether it prepares targets. An example that fails stops the test file with the kit's message, such as `notes_add answered INVALID_INPUT: …`.

The principal is the caller the kit signed in as. Its `userId`, `organizationId`, `membershipId`, `clientId` and `scopes` are the token's; `grantId` and `expiresAt` are placeholders. Store data under `principal.organizationId`, as the provider does. Reference: [`ConformanceFixture`](/docs/mcp/reference#conformancefixture).

## The checks

Read checks run once for the provider, mutate checks once for each mutation, and provider checks once. The rules are on [the design standard](/docs/mcp/standard) page, which says what enforces each; the R numbers are its rules.

The kit checks only what a provider built with `defineTool`, `defineMutation` and `defineProvider` can get wrong. The SDK enforces the rest on every provider, so no check repeats it: identities and host-safe names, closed inputs, timeouts, deprecation sentences and the error envelope when a definition is made; the commit token, expiry, replay and the preparer's identity when a commit runs. `commit.test.ts`, `server.test.ts`, `tool.test.ts` and `provider.test.ts` in `packages/mcp` test those.

**Read**

| Check | What it proves | Rule |
| --- | --- | --- |
| `output_schema_declared` | A property named `*_at` is a string with `format: date-time`; `amount`, `area` and `duration` are objects with `value` and `unit` | R9, R13 |
| `list_paginates` | A read whose output has an `items` array declares `limit` and `cursor` inputs and `next_cursor` and `has_more` outputs | R10 |
| `read_has_no_side_effect` | Each read called twice with its example returns equal structured content, and the server records no intent | R5 |
| `manifest_matches_snapshot` | `manifest(provider)` equals the committed file | R37, R38 |

**Mutate**, for every mutation

| Check | What it proves | Rule |
| --- | --- | --- |
| `prepare_has_no_side_effect` | After two prepares, every read with its example returns what it returned before | R16 |
| `preview_is_semantic` | The preview has a summary that is not blank and at least one change or effect | R17 |
| `targets_have_versions` | Every target has a non-empty `version.value` | R16, R19 |
| `commit_rejects_stale` | After `moveTarget`, the commit answers `INTENT_STALE` | R19 |
| `receipt_is_structured` | Committing the example returns the receipt: `commit` runs, and its results match the mutation's `output` | R35 |

A mutation that prepares no targets, such as a create, cannot have a version move: its `targets_have_versions` and `commit_rejects_stale` are registered as skipped, named `targets_have_versions (not applicable: e2e/records.create prepares no targets)`, and `bun test` counts them as skips.

**Provider**

| Check | What it proves | Rule |
| --- | --- | --- |
| `descriptions_operational` | A mutation's description says `prepare` or `intent` | R14 |

An `errors` entry that is not a custom code is refused when the tool is defined, and a handler that throws an undeclared custom code answers `INTERNAL`; see [tool errors](/docs/mcp/tools#tool-errors).

**Human class.** A `high` risk mutation has the `human` class, which cannot be committed yet. The kit runs it as `controlled`, so its commit checks still run; the commit tool for the class it really has answers `APPROVAL_REQUIRED`.

## The manifest snapshot

```sh
UPDATE_MANIFEST=1 bun run test
```

Run it in the provider's workspace. With `UPDATE_MANIFEST=1`, `manifest_matches_snapshot` writes `manifest(provider)` to the fixture's `manifest` path instead of comparing, so the file appears the first time and changes with the code after that. Review the diff and commit the file with the change: every contract change shows in review. Without the variable, a difference fails the test, and the failure message gives this command.

The file holds the tools sorted by identity, with their wire names, schemas, scopes, declared `errors`, `risk` and `effects`, the two commit tools, the prompts and the resources. It holds no code, and no view HTML. `mcps/e2e/manifest.json` is the working example. Reference: [`manifest`](/docs/mcp/reference#manifest).

## Check a workspace

```sh
bun run mcp:check @answerable/mcp-e2e
```

Run this from the repository root with a workspace name. It runs the workspace's typecheck, lint and tests with Turborepo (`turbo run typecheck lint test --filter <workspace>`); the conformance checks and the manifest drift test are tests, so they run too. The `@answerable/auth`, `@answerable/mcp`, `@answerable/acceptance`, e2e and Toolbox suites, and every server that `bun run mcp:new` writes, enforce 100% line and function coverage. `bun run mcp:test` runs the auth, SDK, e2e, Toolbox, scaffolded servers and scaffold suites together.

## Not yet

The standard's checks for human approvals (`approval_bound_to_digest`), declared secrets (`secrets_declared`) and the egress-guarded client (`egress_guarded`) are not in the kit, because what they would check is not built. [The design standard](/docs/mcp/standard#not-yet) lists them.

## The acceptance

The in-process tests use a local issuer. `bun run mcp:test:e2e` signs three organisations into the e2e MCP through a real Answerable ID with a real browser, and needs Docker; see [Test MCPs locally](/docs/mcp/local-testing).

## Limits

| Limit | Value |
| --- | --- |
| Callers | One person with every advertised scope. Scope filtering and organisation isolation are not checked: test them with `createTestMcp` |
| Protocol | The client's default revision |
| Reads | Two calls with the same example must return equal structured content, so a read that returns the time or a counter fails. Without a read tool, `prepare_has_no_side_effect` has nothing to compare |
| Schemas | The schema checks read the manifest's JSON Schema. `output_schema_declared` looks through `properties`, `items`, `anyOf` and `oneOf`, not `$ref` |
| Errors | The kit calls no handler's own `ToolError` paths: test them yourself |
| Stale | `commit_rejects_stale` moves the first target only |
| Intent store | A memory store of the kit's own |

## Errors

A failed check names the check in its test and the tool or mutation in its message.

| Message begins | Meaning | What to change |
| --- | --- | --- |
| `fixture.examples has no entry for …` | A tool or mutation has no example | Add a valid input for it under its name |
| `… output property "…" is named like a timestamp…` | A `*_at` property is not a `date-time` string | Use `z.iso.datetime()` |
| `… output property "…" is named like a quantity…` | `amount`, `area` or `duration` is not `{ value, unit }` | Use `z.object({ value: z.number(), unit: z.string() })` |
| `… returns an items array but does not declare …` | A list lacks part of the pagination contract | Add `limit`, `cursor`, `next_cursor` and `has_more`; see [pagination](/docs/mcp/tools#pagination) |
| `… returned different results for the same input twice…` | A read changed state, or returned something that varies | Remove the side effect, or the varying field |
| `… recorded an intent; only a mutation's prepare tool does that` | A read created an intent | Make it a mutation |
| `… is out of date; regenerate it with UPDATE_MANIFEST=1…` | The manifest differs from the code | Run the command in the message, review the diff and commit |
| `… answered INVALID_INPUT: …`, `… answered NOT_FOUND: …` in any check | An example does not fit the tool, or names something the provider does not hold | Fix the example, or have its function create what it names first |
| `…: preparing changed what the reads return…` | `prepare` changed state | Move the change into `commit` |
| `…: the preview names no change and no effect…`, `…: the preview summary is blank` | The preview only echoes the arguments | Say what will change, from what, to what |
| `…: target … has no version…` | A target has an empty version value | Set `version.value` from the source's etag, version, timestamp or serial |
| `… succeeded where INTENT_STALE was expected; make moveTarget change …`, `… answered … where INTENT_STALE was expected…` | `moveTarget` did not move the version `prepare` reads, or removed the target | Make `moveTarget` change the resource, or bind the version in the target from the resource's current state |
| `… prepares targets, so the fixture needs moveTarget…` | A mutation with targets and no `moveTarget` | Add `moveTarget` to the fixture |
| `… prepared no targets this time, though it did when the kit registered its checks…` | The example's prepare returns targets only sometimes | Make its example prepare the same targets every time |
| `… answered INTERNAL: …` in any check | A handler threw something unexpected | Read the server log for the `request_id`; if it threw a custom code, add it to `errors` |
| `… a mutation's description must say that it prepares an intent…` | A mutation's description breaks R14 | Name `prepare` or `intent` in it |
