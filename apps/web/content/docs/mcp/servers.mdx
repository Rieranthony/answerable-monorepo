A **provider** is a named, dated set of tools, prompts and resources. A **server** serves one provider over HTTP: it signs callers in through Answerable ID, lists what their token allows and runs their calls. `mcps/e2e` has both; an MCP made by [`bun mcp new`](#make-an-mcp) has a provider, which a hub serves.

## The provider

<include lang="ts" meta='title="mcps/example/src/provider.ts"'>../../../../../mcps/example/src/provider.ts#provider</include>

`defineProvider` fills in each definition's identity (`example/notes.list`), version and scopes, refuses a duplicate tool name, prompt name or resource URI, and returns frozen data.

<AutoTypeTable path="../../packages/mcp/src/provider.ts" name="ProviderFields" type="Parameters<typeof defineProvider>[0]" />

**Description.** What the MCP is for, in a sentence or two: 40 to 1,000 characters, the rule a tool's description follows. The [manifest](#manifest) carries it.

**Database.** `database: { schema, migrations }` names the MCP's drizzle schema module and its migrations folder. The server that serves the provider then needs its `db`, and tools made with `withDatabase` receive it: see [the database](/docs/mcp/tools#the-database). `defineProvider` refuses a tool made with `withDatabase` when the provider declares no database, or another schema.

**Scopes.** Each read tool needs `<id>:read` and each mutation `<id>:write`, unless its definition sets `scopes`. A person's token carries the scopes their organisation entitles them to, and they see only the tools those scopes cover. Through [the Toolbox](/docs/toolbox), grant strings take the place of scopes.

## The server

`createMcpServer` takes the provider, the ID settings and who is calling, and returns a web-standard `fetch` handler that `Bun.serve` serves.

<AutoTypeTable path="../../packages/mcp/src/server.ts" name="McpServerConfig" />

It returns:

<AutoTypeTable path="../../packages/mcp/src/server.ts" name="McpServerHandle" />

**What it serves.** `GET /health`, the protected-resource metadata, and the MCP endpoint at the resource URL's path behind the bearer gate. It answers both the 2026 and the 2025 protocol revisions, builds a fresh MCP server per request and sends `Cache-Control: no-store`. A JSON-RPC batch, which the protocol no longer has, answers `400` with a JSON-RPC error (`-32600`): send one request per POST. The server's name and version are the provider's id and version.

**Sign-in.** Without a valid token the endpoint answers `401` with `WWW-Authenticate: Bearer resource_metadata="…"`. The host reads that [protected-resource metadata](https://datatracker.ietf.org/doc/html/rfc9728), finds Answerable ID and signs the person in. The server then verifies every token against ID's published keys: issuer, audience (its own URL), type `at+jwt`, expiry, and the user and organisation claims. It never sees a password and never calls ID per request. [How Answerable ID works](/docs/id#how-a-person-reaches-an-mcp-server) walks through it.

**Hosts and origins.** It refuses a `Host` header or browser `Origin` other than the resource URL's host name.

**Cache hint.** `tools/list` tells `2026-07-28` hosts they may keep the list for 30 seconds, for that caller alone (`ttlMs: 30000`, `cacheScope: "private"`): a token's scopes never change during its life.

### Who is calling

<include lang="ts" meta='title="mcps/e2e/src/server.ts"'>../../../../../mcps/e2e/src/server.ts#profiles</include>

The token carries only ids. `profiles` gives the rest every handler receives: the person's name, email and groups, and the organisation's name and slug ([the caller](/docs/mcp/tools#the-caller)). It is required: a server that cannot say who is calling does not start.

- **When it runs.** Once for each request that runs a handler (`tools/call`, `prompts/get`, `resources/read` of a resource), before the handler, and never for a list or a view.
- **`createIdProfiles(id, { ttlMs, staleMs })`**, from `@answerable/id-admin`, reads the member and the organisation from ID's admin API in parallel, with the server's machine client and `platform:read`. It keeps each for `ttlMs` (60 seconds), per member and per organisation. `invalidate(organisationIds, userIds)` drops them sooner: the Toolbox's audit-log poller calls it on the same events as its grants.
- **When ID does not answer.** The last value is served for up to `staleMs` (an hour) after it expired. With none, the call answers `UPSTREAM_UNAVAILABLE` and the handler does not run.
- **Who is refused.** A member whose membership is not in force (ID's `effective: false`), or whom ID no longer knows, gets `PERMISSION_DENIED`, whatever an earlier read cached. A group membership counts while its `validFrom` is past and its `validUntil` unset or future.

The Toolbox, the admin MCP and the e2e server use `createIdProfiles`; the e2e server's machine client is `MCP_ID_CLIENT_ID` ([Configure](#configure)). Tests use a [test person](/docs/mcp/testing#who-is-calling).

### Changes

```ts
server.toolsChanged() // every caller listening for changes lists its tools again
```

Every server advertises `tools.listChanged: true`. `toolsChanged()` sends `notifications/tools/list_changed` to every caller that listens: a `2026-07-28` host that opened `subscriptions/listen` with `toolsListChanged`, as the official client does when given `listChanged` options. It reaches every listener of the server, whoever they are. A listen stream sends a keep-alive comment every 5 seconds, inside `Bun.serve`'s default 10-second idle timeout, which would otherwise close it.

**2025 hosts: Not yet.** The SDK serves the 2025 revision statelessly, so `GET` answers `405` and no stream can carry a notification; a 2025 host sees a change when it lists again.

### Hubs

`mount`, `allow`, `project` and `wrapCall`, off by default, serve several providers at one endpoint, as [the Toolbox](/docs/toolbox) does. The table above says what each does. `mount` takes `{ provider, db? }` entries, `db` as for the server's own provider, and the hub takes `profiles` once for all of them.

**Each handler gets its own provider's database.** A mounted tool, called directly or through `call`, receives its provider's `db`, never the hub's; so do a mounted mutation's `prepare` and `commit` when the hub's commit tool commits its intent.

**`call(tool, args, context)`** runs a tool the server serves exactly as its direct call runs it, for the caller in `context`: the arguments are checked (`INVALID_INPUT` names the tool's own fields), the handler runs within its own timeout with its provider's `db`, the output is checked, and a mutation is prepared and its intent recorded, with the commit tool of its class. The codes the tool declares pass through the calling tool unchanged. It is for a hub's own tools, such as the Toolbox's `toolbox_execute`: it does not decide whether the caller may use the tool, and it runs inside the calling tool's `wrapCall`.

## Make an MCP

```sh
bun mcp new acme --description "Notes for construction projects: list, read and add notes on a project." --serve toolbox
```

Run it from the repository root. It refuses a name that is not a [provider id](#the-provider), a reserved or retired name and one a directory of `mcps/` has, before it writes anything; then it writes `mcps/acme`, installs it, creates its local schema, writes its first migration and its manifest, and checks it. [Build your first MCP](/docs/mcp/quickstart) walks through it.

| File | Holds |
| --- | --- |
| `mcp.json` | Where it runs (`serve`: `toolbox`, `standalone` or `both`) and its database mode (`shared` or `own`) |
| `package.json` | The workspace `@answerable/mcp-<name>`, its provider exported as `./provider`, and its versions pinned to the repository's |
| `tsconfig.json`, `eslint.config.mjs`, `bunfig.toml` | The compiler and lint settings, and the gate of 100% line and function coverage over `src` |
| `src/mcp.ts` | `defineTool` and `defineMutation` bound to its database |
| `src/provider.ts` | `defineProvider` with its description, version, database and tools |
| `src/tools/` | One file per tool, each with its test; the first is `<name>.status` unless `--tool` names another |
| `src/db/schema.ts` | Its tables, in schema `<name>` |
| `src/provider.test.ts` | The conformance kit |
| `README.md` | What it is, where it runs, its commands and the guides |

It writes no server: the Toolbox serves an MCP, and mounting one from `mcp.json` is Not yet. `bun run mcp:test` runs every MCP under `mcps/`.

## Configure

<Configuration group="MCP" />

`readMcpEnvironment(process.env)` reads these variables and returns `{ auth, port, id }`. Outside production (`NODE_ENV` unset, `development` or `test`), an unset issuer is `http://localhost:47300` and an unset resource `http://localhost:47500/mcp`, the e2e server's.

**The machine client.** `id` is what `createIdAdmin` takes, set when `MCP_ID_CLIENT_ID` is: the client, `MCP_ID_CLIENT_SECRET` and `MCP_ID_ADMIN_RESOURCE`, ID's admin API (locally `http://localhost:47300/api/admin`). The server reads who is calling through it, so it needs `platform:read` on ID's admin API; register it as [Connect Claude Code](/docs/mcp/claude-code#register-the-server) does for the e2e server. A server whose profiles use ID, as the e2e server's do, refuses to start without it. The secret without the client, or the client without its secret, is refused. A server with variables of its own lists them with `defineConfig` from `@answerable/config` and reads them with `parseEnvironment(config, env, names)`, as the Toolbox and the admin MCP do: it reads `env` with the definition, checks the issuer and resource URL in the two variables `names` gives, and throws `Invalid <label> configuration: <VARIABLE>: <problem>`.

**Issuer.** The Answerable ID origin. The verifier reads ID's signing keys from the issuer's metadata; never take an issuer from a token.

**Resource.** The MCP's canonical URL, exactly as registered in ID. It is the token audience, and its path is the MCP endpoint.

**HTTP.** Both URLs must use HTTPS, except on `localhost`, `127.0.0.1` or `[::1]`.

Register the resource, a client and its access in ID before the first sign-in; see [Connect Claude Code](/docs/mcp/claude-code#register-the-server). Each MCP running at the same time needs its own port.

## Health

`GET /health` returns `{ "status": "ok" }` without authentication, whatever the `Host` header, so load balancers and container probes can call it by address.

## Manifest

`manifest(provider)` returns the provider's contract as plain JSON: `id`, `version`, `description`, every tool (sorted by identity) with its identity, wire name, version, kind, title, description, deprecation, scopes, declared `errors`, annotations and the JSON Schema of its input and output, then the prompts and resources. It carries no code.

<ManifestEntry workspace="example" identity="example/notes.add" />

**Mutations.** A mutation's entry adds `risk` and `effects`; its `input` is the definition's input, without `validate_only`, and its `output` is the schema of the receipt's `results`. A provider with mutations also lists the two commit tools, `kind: "commit"`, whose `scopes` are the union of the mutations' scopes.

Commit the file next to the source and let the conformance kit's `manifest_matches_snapshot` fail on drift. A change to any definition fails the test until you regenerate the file and commit it, so every contract change shows in review:

```sh
UPDATE_MANIFEST=1 bun run test
```

Run it in the provider's workspace. [Test an MCP](/docs/mcp/testing#the-manifest-snapshot) has the details.

## Prompts and resources

<include lang="ts" meta='title="mcps/e2e/src/mcp.ts"'>../../../../../mcps/e2e/src/mcp.ts#prompt</include>

<include lang="ts" meta='title="mcps/e2e/src/mcp.ts"'>../../../../../mcps/e2e/src/mcp.ts#resource</include>

`definePrompt` takes `name`, `description`, a Zod `input` and `execute(input, context)`, which returns an MCP prompt result. `defineResource` takes `name`, a fixed `uri`, `description`, `mimeType` and `read(context)`, which returns text. Both take optional `scopes`, defaulting to `<provider id>:read`, and follow the same visibility rule as tools. Names are lowercase letters, digits and underscores. Reading a prompt or resource must not change data; a failure answers the protocol error `Content could not be read`. Pass them to `defineProvider` as `prompts` and `resources`.

## Views

<include lang="ts" meta='title="mcps/e2e/scripts/build.ts"'>../../../../../mcps/e2e/scripts/build.ts</include>

A view is an interactive page a host shows with a tool's result (MCP Apps). Build each view before starting the server, pass the HTML to `defineView({ name, html })`, and set the view on a tool. The server registers it as a `ui://` resource with the MCP Apps MIME type. Browser code imports `useApp` from `@modelcontextprotocol/ext-apps/react` or `App` from `@modelcontextprotocol/ext-apps`. A view calls tools through the host, with the same scope and organisation checks; it never receives a token. `mcps/e2e` (`records.show`) is the working example.

## Limits

| Limit | Value |
| --- | --- |
| Provider id | 12 characters: a lowercase letter, then lowercase letters or digits |
| Tools, prompts, resources | Unique names and URIs per provider |
| Protocol revisions | `2026-07-28` and 2025; change notices reach `2026-07-28` listeners only |
| Hubs | Mounted providers' prompts and resources are not served |
