A read tool answers a question and changes nothing. Define it with `defineTool`: five fields are required and everything else has a default. `defineTool` checks the definition when the module loads, and returns it as frozen data. A tool that changes data is a [mutation](/docs/mcp/mutations). New here? [Make an MCP](/docs/mcp/create) and [add a tool](/docs/mcp/add-a-tool) first.

## Fields

<AutoTypeTable path="../../packages/mcp/src/tool.ts" name="ToolFields" type="Parameters<typeof defineTool>[0]" />

**Field descriptions.** Describe each input field with `.describe()`: the text reaches the model in the tool's `inputSchema`. Recommended, not enforced.

**Example.** `example` is one valid input, such as `{ limit: 5 }` for `notes.list` above. `defineTool` checks it against `input` when the module loads and refuses one that does not fit, naming the field. [The conformance kit](/docs/mcp/testing#the-fixture) calls the tool with it, so every tool should have one; a tool without one fails conformance.

## Names and identity

| Form | Example | Rule |
| --- | --- | --- |
| Tool name | `notes.list` | `<domain>.<operation>`; each part a lowercase letter, then up to 15 lowercase letters or digits |
| Identity | `example/notes.list` | `<provider id>/<name>`; never changes for the life of the tool |
| Wire name | `notes_list` | The name with `_` for `.`; what hosts list and call |

Hosts add their own prefixes and suffixes to tool names, and some limit names to 64 characters, so the wire name uses only `[a-z0-9_]`. The dotted identity travels in `_meta`. Through [the Toolbox](/docs/toolbox) the wire name gains the provider id: `example_notes_list`.

## Descriptions

The description is what a model reads to choose a tool. Write operational documentation, not a title:

| Say | Example |
| --- | --- |
| What it does | `List your organisation's notes, oldest first.` |
| When to use it and what to call first | `Use projects.search first to find the project id.` |
| Its limits | `20 per page by default and at most 100.` |
| Whether it changes state | A mutation: `Prepare adding a note. Changes nothing: returns a preview; commit the intent with the tool its commit_tool names.` Name no commit tool: a hub serves the mutation under its own commit tools, and the intent's `commit_tool` says which |
| What identifiers mean | `id is the note's id from notes.list.` |

`defineTool` refuses fewer than 40 or more than 1,000 characters, and a deprecated tool's description gets the deprecation sentence on the wire. The conformance kit adds one check: `descriptions_operational` (a mutation's description says `prepare` or `intent`).

## The caller

<include lang="ts" meta='title="mcps/example/src/docs/caller.ts"'>../../../../../mcps/example/src/docs/caller.ts</include>

`execute(input, context)` receives the parsed input and a frozen context: who is calling, the verified token, this call's id and its cancel signal. Prompts and resources receive the same context.

<AutoTypeTable path="../../packages/mcp/src/definitions.ts" name="ToolContext" />

**Where it comes from.**

| Field | Source |
| --- | --- |
| `person.id`, `person.membershipId`, `organisation.id`, `client.id` | The access token, verified offline against ID's published keys |
| `person.name`, `person.email`, `person.groups`, `organisation.name`, `organisation.slug` | The server's [`profiles`](/docs/mcp/servers#who-is-calling), which reads them from Answerable ID's admin API before the handler runs, cached 60 seconds per member and per organisation |
| `executionId`, `signal` | The server, for this call |

`person.groups` holds the groups the person is in now, each `{ id, slug, name }`. When ID cannot be read, the call answers `UPSTREAM_UNAVAILABLE` and the handler does not run; see [What the server answers](#tool-errors). In tests, the caller is a test person you can change: [Test an MCP](/docs/mcp/testing#who-is-calling).

`principal` is the verified token, for anything the fields above do not cover:

<AutoTypeTable path="../../packages/auth/src/index.ts" name="UserPrincipal" />

**Keep to the caller's organisation.** A table with the organisation policy needs no filter; data from anywhere else is constrained by `organisation.id`: [the rule](/docs/mcp/database#add-a-table). Join on `person.id`, never on an email address. [How Answerable ID works](/docs/id) explains the token.

### The database

<include lang="ts" meta='title="mcps/example/src/mcp.ts"'>../../../../../mcps/example/src/mcp.ts</include>

An MCP with a database defines its tools with the `defineTool` and `defineMutation` that `withDatabase({ schema })` returns, given its drizzle schema module. `bun mcp new` writes this file, and every tool imports the two from it, as `notes.list` above does. Their handlers also receive:

<AutoTypeTable path="../../packages/mcp/src/database.ts" name="DatabaseFields" type="Pick<DatabaseContext<Record<string, unknown>>, 'db'>" />

- **The provider declares it.** `defineProvider` takes `database: { schema, migrations }`, and refuses a tool made with `withDatabase` unless that is the same schema. See [Providers and servers](/docs/mcp/servers#the-provider).
- **The server supplies it.** The process that serves the provider passes its `db` to `createMcpServer` or a hub's `mount`, made with `mcpDatabase` from `@answerable/mcp-postgres`; a test gets one from [`@answerable/mcp-postgres/testing`](/docs/mcp/testing#an-mcp-with-a-database).
- **Each call is its caller's.** The server runs every handler inside its call, and `callerOrganisation()` gives that call's organisation. `mcpDatabase` sets it on each connection a query borrows, so a table with the `organisationIsolation` policy, as every table `bun mcp` writes has, returns and accepts only that organisation's rows.
- **A plain `defineTool` has no `db`.** Its context type has none, so `context.db` fails the typecheck.

`bun mcp new` writes an MCP's `src/mcp.ts`, `src/db/schema.ts` and first migration, and `bun mcp add tool` adds the table a new domain needs: [Make an MCP](/docs/mcp/create), [Your MCP's database](/docs/mcp/database).

## Pagination

<include lang="ts" meta='title="mcps/example/src/tools/notes-list.ts"'>../../../../../mcps/example/src/tools/notes-list.ts#page</include>

Every tool that can return an unbounded list takes `limit` and `cursor`, and returns `items`, `next_cursor` and `has_more`, as `notes.list` above does. Never truncate silently.

| Field | Rule |
| --- | --- |
| `limit` | Integer; default at most 20; the schema enforces the maximum |
| `cursor` | Optional; opaque to callers |
| `items` | The page |
| `next_cursor` | The cursor for the next page, or `null` on the last |
| `has_more` | `true` when another page exists |

`@answerable/mcp` exports nothing for pagination: declare the fields in your schemas. The conformance kit's `list_paginates` fails a tool whose output has an `items` array without them. A cursor that is not one the tool issues answers `INVALID_INPUT`: here, anything but a row's id, a UUID v7, which sorts by creation.

**Size.** Through [the Toolbox](/docs/toolbox#limits), a read whose result is above 100 KiB of JSON answers `RESULT_TOO_LARGE`, so keep the default page well below that.

## Tool errors

<include lang="ts" meta='title="mcps/example/src/docs/tool-errors.ts"'>../../../../../mcps/example/src/docs/tool-errors.ts</include>

Throw `ToolError(code, message, options?)` for a failure you expect. The caller receives an error result whose one text block is the [error envelope](/docs/mcp/errors) as JSON:

```json
{
  "error": {
    "code": "NOT_FOUND",
    "message": "No accessible note exists",
    "retry": { "policy": "never" },
    "request_id": "0199a4e2-7b06-7000-87bd-91723fe45f93"
  }
}
```

`retry.policy` tells the model what to do next without reading the message. Each standard code has a default policy; [MCP errors](/docs/mcp/errors#codes) lists them all. `details` appears only when given.

**Custom codes.** A provider may add its own codes, `<PROVIDER>_<CODE>` in capitals, each with an explicit retry policy. List them in the definition's `errors`; the manifest carries the list, so a reviewer sees every code a provider can answer:

<include lang="ts" meta='title="mcps/example/src/docs/custom-error.ts"'>../../../../../mcps/example/src/docs/custom-error.ts</include>

A custom code must start with the provider's id in capitals: `defineProvider` refuses `OTHER_QUOTA` in provider `example`. A handler that throws a custom code its definition does not list answers `INTERNAL`, and the server log names the code to add.

**What the server answers for you.**

| Case | Answer |
| --- | --- |
| Who is calling cannot be read: the server's `profiles` fails | `UPSTREAM_UNAVAILABLE`, `Who you are could not be read; try again shortly`, and `[mcp] reading who is calling failed` in the server log; `execute` does not run |
| `profiles` throws a `ToolError`, such as `PERMISSION_DENIED` for a member whose membership is not in force | That error; `execute` does not run |
| The input fails `input` | `INVALID_INPUT`, one field violation per issue (`{ field: "a.b", message }`); `execute` does not run |
| `execute` runs past `timeoutMs` | `TIMEOUT`; `context.signal` aborts and the answer does not wait for `execute` |
| Any other exception, an undeclared custom code, or an output that fails `output` | `INTERNAL` with the message `The tool could not complete`, and `[mcp] tool <name> failed` with the execution id in the server log |

## Dependencies

<include lang="ts" meta='title="mcps/example/src/docs/dependencies.ts"'>../../../../../mcps/example/src/docs/dependencies.ts</include>

Pass an API client or any other dependency by closure: define the tools inside a function that receives them, and return the provider. The server passes the real one; a test passes a stand-in. `mcps/e2e/src/mcp.ts` builds its provider this way. The MCP's own database is the one exception: the platform supplies it in the context, as [the database](#the-database) shows.

**Composition.** A tool is plain data, so ordinary code composes it: collect tools from several modules into one array, wrap `execute` to audit every call, or call `execute` directly in a unit test.

## Versions and deprecation

<include lang="ts" meta='title="mcps/example/src/docs/deprecation.ts"'>../../../../../mcps/example/src/docs/deprecation.ts</include>

**Version.** A date, `YYYY-MM-DD`; it defaults to the provider's version. The behaviour of one identity at one version never changes.

**Deprecation.** `since` and `sunset` are dates; `replacement` is optional and names another tool of the same provider that is not deprecated. The description sent to hosts ends with a sentence naming all three, for example `Deprecated since 2026-09-30; removed on 2027-09-30; use notes.list instead.`, and `_meta` carries the `deprecated` object.

Two versions of one tool name in one provider: Not yet. `defineProvider` refuses a duplicate name.

## What hosts receive

| `tools/list` field | Value |
| --- | --- |
| `name` | The wire name |
| `title` | `title`, when set |
| `description` | `description`, plus the deprecation sentence |
| `inputSchema` | The JSON Schema of `input`, with `additionalProperties: false` |
| `outputSchema` | The JSON Schema of `output` |
| `annotations` | `readOnlyHint: true`, `destructiveHint: false`, `idempotentHint: true`, `openWorldHint: false` |
| `_meta["com.answerable/capability"]` | `{ identity, version, kind: "read" }`, plus `deprecated` when set. A mutation's prepare tool: [see Mutations](/docs/mcp/mutations#the-prepare-tool) |
| `_meta.ui.resourceUri` | The view's URI, when the tool has a [view](/docs/mcp/servers#views). The MCP Apps helper also writes the older `_meta["ui/resourceUri"]` |

The manifest holds the same contract. This is `notes.list`'s entry:

<ManifestEntry workspace="example" identity="example/notes.list" />

**Results.** The server checks the value `execute` returns against `output`, drops every field `output` does not declare, and sends it as `structuredContent` and as the same JSON in one text block. Claude Code shows the model only the structured content, so put everything the model needs in the output. A failure carries no structured content; see [tool errors](#tool-errors).

**Scopes decide visibility.** A token lists only the tools, prompts and resources whose every scope it carries. A tool it cannot use is absent from `tools/list`, and calling it returns the protocol's unknown-tool error.

**Closed input.** `defineTool` applies `.strict()` to `input`, so an unknown top-level field answers `INVALID_INPUT`. Nested objects keep Zod's default of dropping unknown fields; use `z.strictObject` to close them too.

Annotations describe the tool for hosts; they never authorise anything.

## Limits

| Limit | Value |
| --- | --- |
| Tool name part | 16 characters |
| Description | 40 to 1,000 characters |
| `timeoutMs` | 1 to 55,000; default 25,000. Longer work: Not yet |
| Declared errors | Custom `<PROVIDER>_<CODE>` codes only, starting with the provider id in capitals |
| Tool kinds | Read and mutate. Start and subscribe: Not yet |
| Versions per tool name in a provider | One |

A definition that breaks a rule throws when the module loads: [When a definition is refused](/docs/mcp/errors#when-a-definition-is-refused) lists every message.
