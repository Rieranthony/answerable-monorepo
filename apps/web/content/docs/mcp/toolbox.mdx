```bash
claude mcp add --transport http answerable-toolbox http://localhost:47400/mcp \
  --client-id claude-code-toolbox --callback-port 47700
```

The Toolbox (`mcps/toolbox`) is one MCP server for every organisation. It signs people in with Answerable ID, reads what their organisation granted them from ID, and serves exactly those capabilities: as one tool each, or through a few tools that find and run them. Every call is checked again, recorded in a hash-chained evidence log and traced as a span.

Run the line above once the Toolbox runs locally with its registrations ([below](#run-it-locally)), then choose **Authenticate** in Claude Code's `/mcp` and ask Claude to call `toolbox_whoami`.

## What a person sees

Each caller gets one of two **projections** of the same granted set, chosen on every request from their host client's settings ([host clients](#host-clients)):

| Projection | When | Tools |
| --- | --- | --- |
| Direct | The host client is set to `direct`, or to `auto` (the default) while the caller's granted tools, prepare tools included, number at most its `direct_limit`, 40 by default | `toolbox_whoami`, one tool per capability, the commit tools |
| Meta | The host client is set to `meta`, or to `auto` above that limit | `toolbox_whoami`, the four meta tools, the commit tools |

`toolbox_whoami` and the commit tools are not counted against the limit. Pins, capabilities that always appear directly: Not yet.

### The direct projection

| Order | Tools |
| --- | --- |
| First | `toolbox_whoami`, for every caller whose token carries `toolbox` |
| Then | Each provider's tools by provider id, then domain, then operation, named `<provider>_<domain>_<operation>`: `e2e_identity_get`, `e2e_records_create`, `e2e_records_delete`, `e2e_records_list`, `e2e_records_show` |
| Last | `toolbox_commit` and `toolbox_commit_confirmed`, when at least one mutation is listed |

**Hidden means refused.** A capability the person may not use is absent from `tools/list`, and calling it answers the protocol's unknown-tool error, as a name that does not exist does. Authority is checked on every request, never taken from an earlier list.

**`_meta` and annotations** are those of [`@answerable/mcp`](/docs/mcp/authoring#what-the-wire-carries): `_meta["com.answerable/capability"]` carries the identity (`e2e/records.list`), version and kind, and for a mutation its risk and the caller's policy class. They describe; they never authorise.

**Cache hint.** `tools/list` tells `2026-07-28` hosts they may keep it for 30 seconds, for that caller alone, as [every `@answerable/mcp` server](/docs/mcp/authoring#the-server) does.

**Views** keep their URIs: `e2e_records_show` opens `ui://records/index.html`, served while the tool is listed.

A token without the `toolbox` scope lists nothing, and every call is the unknown-tool error. The Toolbox's protected-resource metadata lists `scopes_supported: ["toolbox"]`, so hosts ask for `toolbox` and `offline_access` only.

### The meta projection

```json
{ "name": "toolbox_search", "arguments": { "query": "oldest" } }
```

```json
{
  "items": [
    { "identity": "e2e/records.list", "title": null, "description": "List your organisation's test records, oldest first, 20 per page by default and at most 100.", "kind": "read", "policy_class": null }
  ],
  "next_cursor": null,
  "has_more": false
}
```

Then `toolbox_execute` with `{ "identity": "e2e/records.list", "arguments": { "limit": 5 } }` returns what `e2e_records_list` would.

| Tool | Takes | Returns |
| --- | --- | --- |
| `toolbox_whoami` | `{}` | As in the direct projection, [below](#toolbox_whoami) |
| `toolbox_search` | `query` (1 to 200 characters), `limit` (1 to 20, default 10), `cursor` | `items` of `{ identity, title, description, kind, policy_class }`, `next_cursor`, `has_more`. `description` is the first sentence |
| `toolbox_describe` | `identities`: 1 to 5 | `capabilities` of `{ identity, kind, policy_class, description, input, output }`: the full description and the JSON Schemas of the manifest, where `input` is what `arguments` takes and a mutation's `output` is its receipt's `results` |
| `toolbox_execute` | `identity`, `arguments` | The read's own result |
| `toolbox_prepare` | `identity`, `arguments`, `validate_only` | The intent, as the mutation's own prepare tool returns it |
| `toolbox_commit`, `toolbox_commit_confirmed` | As in any [`@answerable/mcp` server](/docs/mcp/authoring#commit-tools) | The receipt. Listed when the caller may use at least one mutation |

**Search.** Postgres full text over each capability's identity, title, description and argument names. A word in the identity weighs most, then the title, then the description, then an argument name. Any word of the query may match, and titles and descriptions also match other English forms of a word: `summary` finds "Quarterly summaries". Only the capabilities the caller may use are searched. Embeddings: Not yet.

**Execute and prepare** run the capability exactly as its direct tool would: the same argument check, whose `INVALID_INPUT` names the capability's own fields; its own timeout, up to 55 seconds, and its declared error codes; the same intent, commit token and commit tool. A mutation sent to `toolbox_execute`, or a read sent to `toolbox_prepare`, answers `INVALID_INPUT` naming the right tool.

**Hidden means not found.** An identity the caller may not use answers `NOT_FOUND` from `toolbox_describe`, `toolbox_execute` and `toolbox_prepare`, with the same message as an identity that does not exist, so the catalogue cannot be enumerated. A capability's direct tool is an unknown tool in this projection, and views are not served.

The meta tools carry read-only annotations, since none of them changes anything; the commit tools keep theirs.

## toolbox_whoami

```json
{
  "user_id": "0199a0d2-…",
  "organisation_id": "0199a0d1-…",
  "membership_id": "0199a0d3-…",
  "client_id": "claude-code-toolbox",
  "grants": ["e2e/records"],
  "capabilities": [
    { "identity": "e2e/records.create", "kind": "mutate", "policy_class": "agent" },
    { "identity": "e2e/records.delete", "kind": "mutate", "policy_class": "controlled" },
    { "identity": "e2e/records.list", "kind": "read", "policy_class": null },
    { "identity": "e2e/records.show", "kind": "read", "policy_class": null }
  ]
}
```

The caller's person, organisation, membership and host client from the token; the grant strings ID holds for them; and each capability they may use, with the policy class of each mutation in their organisation (`null` for a read). Its identity is `toolbox/toolbox.whoami`: the Toolbox's own provider is `toolbox`, and its tools are named after their `toolbox` domain.

## Mutations through the Toolbox

```json
{ "name": "e2e_records_delete", "arguments": { "id": "5b0e…" } }
```

The prepare tool, or `toolbox_prepare` in the meta projection, returns the intent; its `commit_tool` says which commit tool applies:

```json
{ "name": "toolbox_commit_confirmed", "arguments": { "intent_id": "0199a4e2-…", "commit_token": "act_Yc1…", "preview_summary": "Delete record “Q3 plan”" } }
```

| Class | Commit with |
| --- | --- |
| `agent` | `toolbox_commit` |
| `controlled` | `toolbox_commit_confirmed`, with the preview's summary word for word, once the person has seen it |
| `human` | Nothing yet: both commit tools answer `APPROVAL_REQUIRED` with `details.approval` `{ "class": "human", "commit_tool": "toolbox_commit_confirmed", "status": "pending" }` and no `url`, and the intent waits as `awaiting_approval` until it expires 24 hours after prepare. Approval pages: Not yet |

**Policy class.** A mutation's class for a caller is the organisation's `policy_class` override in [the catalogue](#the-catalogue), else the class its `risk` gives. It shows in the prepare tool's `_meta`, in `toolbox_whoami` and in `toolbox_search`.

**The intent store.** Intents live in the Toolbox's `intents` table, one row per intent, with the commit token kept only as its SHA-256. Each status change is one compare-and-set on the status, so two commits never both run. An intent past `expires_at` is marked `expired` when a commit or a read finds it, judged by the database's clock. Every step of the commit is the one [every `@answerable/mcp` server](/docs/mcp/authoring#commit-tools) takes, and a commit checks again that the caller may still use the mutation.

## Grant strings

An entitlement whose resource is the Toolbox carries grant strings in its `scopes`:

| Grant string | Covers |
| --- | --- |
| `e2e/records.list` | One capability |
| `e2e/records` | Every capability of that domain in the provider |
| `e2e` | Every capability of the provider |
| `toolbox/approve` | Approving human-class intents. Read, not yet used: approvals are Not yet |
| `toolbox/code` | `toolbox_run`. Read, not yet used: Not yet |

Rows are additive; there is no deny. Principals are the organisation, a group or a member, as for any entitlement. The pair rows `(host client, Toolbox)` carry `toolbox` and let ID issue the token; they stay separate from grant rows, so a person's capabilities do not depend on the host. `toolbox`, `offline_access` and anything that is not a grant string are ignored.

ID refuses an entitlement scope that is not in the resource's `allowedScopes`, so the Toolbox resource must allow every grant string it accepts. `allowedScopes(providers)` from `@answerable/mcp-toolbox/grants` returns the list: `offline_access`, `toolbox`, `toolbox/approve` and each mounted provider's id, domains and capabilities. The [enable call](/docs/mcp/toolbox-admin#what-the-call-does) widens the resource to the providers it names.

## How authority is read

For each request that lists or calls tools, the Toolbox takes the verified token's organisation and membership and asks ID, while it reads the organisation's catalogue and the host client's settings from its own database:

```bash
curl "$ID/api/admin/v1/organizations/$ORGANISATION_ID/members/$MEMBERSHIP_ID/access" \
  -H "Authorization: Bearer $TOOLBOX_MACHINE_TOKEN"
```

**The access view.** It keeps the top-level `scopes` of every target whose resource is the Toolbox, both `kind: "resource"` and `kind: "client_resource"`, and keeps the grant strings. The token is the Toolbox's machine client's, a `client_credentials` token for ID's admin resource with `platform:read`, reused until 30 seconds before it expires.

**The cache.** Grant strings are cached per organisation, member and the token's `organization_authorization_version` for 60 seconds. A token with another version reads again.

**The poller.** Every 15 seconds the Toolbox reads ID's audit log (`GET /api/admin/v1/audit-events?limit=200`, newest first, back to the last event it saw) and marks stale the cache of every organisation named by an `entitlement.*`, `group_member.*`, `group.*`, `member.*` or `organization.*` event; the next request reads again. Its first poll only records the newest event.

**The bound.** A change in ID reaches the person within 60 seconds even when the poller is down, and usually within one poll. In the acceptance, an entitlement added to a member reached the same access token after 15.0 seconds in each of three runs, listed by polling `tools/list` every 5 seconds; a listening host is told sooner ([change](#change)).

**When ID fails.** A stale entry answers until its 60 seconds end. Without one, a call answers `UPSTREAM_UNAVAILABLE` whatever tool it names, and listing tools fails; connecting still works.

A capability is **allowed** when its provider is enabled in the organisation's catalogue, the organisation has not disabled it, and one of the caller's grant strings covers it.

## Change

When the poller finds an audit event that can change an organisation's grants, the Toolbox sends `notifications/tools/list_changed` to every caller that listens: a `2026-07-28` host that opened `subscriptions/listen` with `toolsListChanged`, as the official MCP client does when given `listChanged` options. The host lists its tools again and sees the change. In the acceptance, a listening client heard it 10.8 to 11.8 seconds after an entitlement was added in ID, over three runs, and its new list held the granted tool.

**Every listener, not only the organisation's: Not yet.** The SDK's notifier reaches every listener of the server, so a change in one organisation tells every listening caller to list again; each still sees only its own tools.

**2025 hosts: Not yet.** The SDK serves the 2025 revision statelessly: `GET` answers `405`, so no stream carries the notice. A 2025 host sees a change on its next `tools/list`, within 60 seconds.

**Other changes.** A catalogue row, a host client's settings or a new manifest send no notice yet; callers see them on their next list, which a `2026-07-28` host may keep for 30 seconds.

## The catalogue

The catalogue is the ceiling: an organisation uses only providers enabled for it, whatever its entitlements say.

| Table | Holds |
| --- | --- |
| `providers` | Each mounted provider's id, version and manifest |
| `capabilities` | Each capability at each version: kind, risk, title, description, schemas and the search vector [`toolbox_search`](#the-meta-projection) ranks |
| `organisation_catalogue` | Per organisation and provider: `enabled`, and `overrides` with `disabled` (identities) and `policy_class` (identity to class) |
| `host_clients` | Per host's OAuth client id: `projection` and `direct_limit` |

**At boot** the Toolbox ingests every provider's manifest. A capability already stored at the same version with another kind, risk, input or output refuses the boot, naming it: give the tool a new version. Titles and descriptions update in place.

**Policy class.** A mutation's class for a caller is the organisation's `policy_class` override, else the class its `risk` gives (`low` agent, `normal` controlled, `high` human); see [mutations](#mutations-through-the-toolbox).

**Enable an organisation** with one call to the [admin API](/docs/mcp/toolbox-admin#enable-an-organisation): it makes the rows Answerable ID needs to issue a host client's token to the organisation and enables the named providers in the catalogue. Repeating it changes nothing. Then disable a capability or set a policy class with `PUT /admin/v1/organisations/{id}/catalogue/{provider}` ([the catalogue](/docs/mcp/toolbox-admin#the-catalogue)).

**New capabilities stay off until enabled.** When a provider version adds a capability the provider never had, the boot appends its identity to `overrides.disabled` of every organisation that has the provider enabled, and the organisation's entry is what turns it on.

## Host clients

| Column | Values | Without a row |
| --- | --- | --- |
| `client_id` | The host's OAuth client in ID, the token's `client_id` | |
| `projection` | `direct`, `meta` or `auto` | `auto` |
| `direct_limit` | A whole number from 0; `auto` serves the direct projection up to this many granted tools | 40 |

The `host_clients` table, read with one primary-key lookup per request that lists or calls tools. Staff set a row with `PUT /admin/v1/host-clients/{clientId}` ([host clients](/docs/mcp/toolbox-admin#host-clients)); in code, `writeHostClient(db, clientId, { projection?, direct_limit? })` from `@answerable/mcp-toolbox/catalogue` does the same, and a field left out takes its default.

## Evidence

Every call of a tool, a prepare tool or a commit tool appends one event to its organisation's chain in `evidence_events`, and so does every transition of an intent:

| Kind | When | Outcome |
| --- | --- | --- |
| `capability.completed` | The call ran | `success`, with `data.result_bytes`, or `failure` with `error_code`, such as `RESULT_TOO_LARGE`. A prepare's row names its `intent_id`; a commit's its `intent_id` and `receipt_id` |
| `capability.denied` | A call named a capability that exists but the caller may not use, by its tool or through `toolbox_execute` or `toolbox_prepare` | `denied`, with `reason` `not granted` or `no toolbox scope` |
| `intent.prepared` | An intent was recorded; `data.policy_class` is its class and its preview is the [payload](#payloads) | `success` |
| `intent.approval_requested` | A human-class intent was recorded | `success` |
| `intent.committed`, `receipt.issued` | A commit ended `committed`; both name the `receipt_id` | `success` |
| `intent.stale` | A commit found a target moved | `success` |
| `intent.expired` | A commit or a read found the intent past `expires_at`: once per intent | `success` |

Intent events carry the intent's organisation, person, host client, capability and `intent_id`. A commit that fails is its call's `capability.completed` failure. A call of `toolbox_execute` or `toolbox_prepare` is recorded as the capability it ran or refused; one that names no capability the Toolbox serves is recorded as the meta tool's own. A call to a name that does not exist records nothing. The kinds `intent.approved`, `intent.denied`, `operation.*`, `run.*` and `limit.refused` are accepted by the table and not yet written.

**What a row holds.** The organisation, actor, host client, capability identity and version, execution id, JSON-RPC id, trace and span ids, outcome and bounded `data` (at most 4 KiB). Inputs, results and secrets are never recorded.

**The chain.** A database trigger takes a per-organisation lock, sets `seq` to the organisation's next number and `row_hash` to SHA-256 over the previous row's hash and every field, each written as its byte length, a colon and its text. The migration `mcps/toolbox/migrations/0002_evidence.sql` spells the layout out. Another trigger refuses `UPDATE`, `DELETE` and `TRUNCATE`.

```ts
import { SQL } from "bun"
import { createEvidence } from "@answerable/mcp-toolbox/evidence"

const db = new SQL(process.env.TOOLBOX_DATABASE_URL!)
const evidence = createEvidence(db)
console.log(await evidence.verify(organisationId)) // { ok: true, length: 2 }, or { ok: false, length, broken_at }
```

`verify` walks the chain in `seq` order and recomputes every hash; `broken_at` is the first event whose fields, number or link no longer match.

### Payloads

```ts
const [{ payload_ref }] = await db`select payload_ref from evidence_events where intent_id = ${intentId} and kind = 'intent.prepared'`
await evidence.erase(payload_ref)
```

Each `intent.prepared` stores the intent's preview in `evidence_payloads`; the event holds its id in `payload_ref` and its SHA-256 in `payload_hash`, which the chain covers. `erase(payloadId)` removes the body for good: `payload_hash` stays, and the chain still verifies.

**Not yet:** nightly verification, publishing chain heads outside the database, and retention.

## Spans

One server span per call, named `tools/call <identity>`: for a commit, `toolbox/commit` or `toolbox/commit_confirmed`; for `toolbox_execute` and `toolbox_prepare`, the capability they ran or refused:

| Attribute | Value |
| --- | --- |
| `mcp.method.name` | `tools/call` |
| `gen_ai.tool.name` | The tool name called, such as `e2e_records_list` |
| `gen_ai.tool.call.id` | The execution id, also the error envelope's `request_id` and the evidence row's `execution_id` |
| `jsonrpc.request.id` | The JSON-RPC id |
| `error.type` | The error code of a failed call |
| `answerable.organisation.id` | The organisation |
| `answerable.user.hash` | SHA-256 of the Toolbox's resource URL, a colon and the user id; never the id itself |
| `answerable.client.name` | The host's OAuth client id |
| `answerable.capability.identity`, `answerable.capability.version` | The capability |
| `answerable.outcome`, `answerable.result.bytes` | `success` with the result's size, `failure`, or `denied` for a capability refused through a meta tool |

A W3C `traceparent` in the request's `_meta` becomes the span's parent. Set `OTEL_EXPORTER_OTLP_ENDPOINT` to export spans over OTLP/HTTP as JSON to `<endpoint>/v1/traces`, with `service.name` `answerable-toolbox`; without it, spans get ids and go nowhere. **Not yet:** client spans per upstream call, and the `mcp.server.operation.duration` histogram.

## Run it locally

[Register the Toolbox in ID](/docs/mcp/toolbox-admin#register-the-toolbox-in-id), put the machine client's secret in `TOOLBOX_ID_CLIENT_SECRET` in the root `.env`, with `TOOLBOX_ID_CLIENT_ID=toolbox-hub`, and start the Toolbox:

```bash
bun --env-file=.env run --filter @answerable/mcp-toolbox db:migrate
bun run toolbox:dev
```

Then [enable your organisation](/docs/mcp/toolbox-admin#enable-an-organisation), [entitle its members](/docs/mcp/toolbox-admin#grant-strings-for-people) and connect Claude Code with the line at the top of this page.

## Environment

Read from the root `.env` by `bun run toolbox:dev`; every variable is listed in `default.env`.

| Variable | Meaning | Local value |
| --- | --- | --- |
| `TOOLBOX_DATABASE_URL` | The Toolbox's Postgres | `postgres://answerable:answerable@localhost:47432/answerable_toolbox` |
| `TOOLBOX_TEST_DATABASE_URL` | The test database, reset by `db:test:migrate` | `postgres://answerable:answerable@localhost:47432/answerable_toolbox_test` (the default) |
| `TOOLBOX_ID_ISSUER` | Answerable ID's origin | `http://localhost:47300` |
| `TOOLBOX_RESOURCE_URL` | The Toolbox's URL as registered in ID; its path is the endpoint | `http://localhost:47400/mcp` |
| `TOOLBOX_PORT` | The loopback port | `47400` (the default) |
| `TOOLBOX_ID_CLIENT_ID`, `TOOLBOX_ID_CLIENT_SECRET` | The Toolbox's machine client in ID, with `platform:read` and `platform:write` | `toolbox-hub` and its secret |
| `TOOLBOX_ID_ADMIN_RESOURCE` | ID's admin resource, ID's `ADMIN_RESOURCE_IDENTIFIER` | `http://localhost:47300/api/admin` |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | Optional OTLP/HTTP collector | `http://localhost:4318` |

The admin API's audience is the origin of `TOOLBOX_RESOURCE_URL` and `/admin`, such as `http://localhost:47400/admin`; it has no variable. `GET /health` answers `{ "status": "ok" }` while the database answers `select 1`, and `503` with `{ "status": "unavailable" }` otherwise, whatever the `Host` header.

## Limits

| Limit | Value |
| --- | --- |
| Result size | A read's result above 100 KiB of JSON (102,400 bytes) answers [`RESULT_TOO_LARGE`](/docs/mcp/errors#codes) with `details.bytes` and `details.limit`, directly or through `toolbox_execute`. Prepare and commit results are not limited |
| Grant freshness | At most 60 seconds, usually one 15-second poll; a `2026-07-28` host that keeps `tools/list` for its 30 seconds lists a change up to 30 seconds later, while every call is checked against current grants |
| Providers | Mounted in process; each provider id once. Their prompts and resources are not served through the Toolbox; their views are |
| Scope checks inside a provider | A Toolbox token carries only `toolbox`, so a handler that reads `principal.scopes` sees no provider scopes: the e2e view's `canWrite` is false through the Toolbox, and its create and delete buttons stay hidden |
| Search | Up to 20 capabilities a page; the query up to 200 characters. In the acceptance, `toolbox_search` answered in a median of 7.5 to 10.6 ms and a maximum of 11.5 to 20.7 ms, over 20 calls in each of three runs |
| Describe | Up to 5 identities a call |
| `tools/list_changed` | Every listening `2026-07-28` caller, whichever organisation changed; 2025 callers: Not yet. Catalogue, host client and manifest changes: Not yet |
| Mutations | Intents in Postgres; human approvals and cancelling an intent: Not yet |
| Pins | Not yet |
| Rate limits and budgets | Not yet |
| Administration | The [admin API](/docs/mcp/toolbox-admin) is platform tier: machine clients with `toolbox:admin`. Self-service purchase, and administration by an organisation's own administrators: Not yet |

## Errors

| You see | Meaning | What to do |
| --- | --- | --- |
| `Tool <name> not found` | No such tool, or you may not use it: no grant string covers it, its provider is not enabled for your organisation, the organisation disabled it, or the token lacks `toolbox` | Call `toolbox_whoami` to see your grants; ask an administrator for an entitlement |
| Tool result `UPSTREAM_UNAVAILABLE` | ID did not answer with your access and none is cached | Retry after `retry.after_ms`; check ID and the `TOOLBOX_ID_*` settings |
| `tools/list` fails with an internal error | The same, for a list | Retry; the server log shows `[toolbox] reading access failed` |
| Tool result `RESULT_TOO_LARGE` | A read answered more than 100 KiB of JSON | Call it again with a smaller `limit`, a `cursor` or narrower filters |
| `tools/list` holds only `toolbox_whoami`, the meta tools and the commit tools | The host client is set to `meta`, or to `auto` and the caller has more granted tools than its `direct_limit` | Find capabilities with `toolbox_search`; to list them directly, set the host client to `direct` or raise its limit ([host clients](#host-clients)) |
| Tool result `NOT_FOUND`: `You may use no capability <identity>; find one with toolbox_search` | The identity does not exist, or you may not use it | Search for it; ask an administrator for an entitlement |
| Tool result `INVALID_INPUT`: `<identity> is a mutation; prepare it with toolbox_prepare` | `toolbox_execute` runs reads only | Call `toolbox_prepare`, then the commit tool it names |
| Tool result `INVALID_INPUT`: `<identity> is a read; run it with toolbox_execute` | `toolbox_prepare` prepares mutations only | Call `toolbox_execute` |
| Commit answers `APPROVAL_REQUIRED` with `status: "pending"` | The organisation set the mutation to the human class | Not yet: approvals cannot be given, so the intent expires after 24 hours; ask for the class to be changed |
| A host hears no `tools/list_changed` | It speaks the 2025 revision, or does not listen | List tools again; the change shows within 60 seconds |
| Log `Answerable ID refused the Toolbox's client credentials (401)…` | The machine client's ID, secret or `platform:read` capability is wrong, or, for the enable call, its `platform:write` | Fix `TOOLBOX_ID_CLIENT_ID`, `TOOLBOX_ID_CLIENT_SECRET` or the capability |
| Log `[toolbox] reading ID's audit log failed` | The poller could not read the audit log | Changes still arrive within 60 seconds; fix ID or the machine client |
| Commit answers `PERMISSION_DENIED` | Your grant no longer covers the prepared mutation | Ask for access, then prepare again |
| `401 invalid_token` | The token is for another resource, or expired | Sign in for the Toolbox's exact URL |
| `Invalid Toolbox configuration: <VARIABLE>: …` at start | A variable is missing or invalid | Set it as in [Environment](#environment) |
| `Capability <identity> version <date> changed its input without a new version…` at start | A provider changed a contract without a new version | Give the tool a new version in its definition or its provider |
| `Missing the e2e records view…` at start | The view is not built | Run `bun run --filter @answerable/mcp-e2e build` |
| `503 {"status":"unavailable"}` from `/health` | The database does not answer | Check `TOOLBOX_DATABASE_URL` and Postgres |
| Log `relation "host_clients" does not exist`, or `"intents"`, and every list or call fails | The database lacks this version's migrations | Run `bun --env-file=.env run --filter @answerable/mcp-toolbox db:migrate` |
| `evidence_events is append-only: UPDATE is refused` | Something tried to change evidence | Evidence is never changed; erase a payload with `erase` instead |
| `Refusing to reset <database>; expected answerable_toolbox_test` | `db:test:migrate` points elsewhere | Point `TOOLBOX_TEST_DATABASE_URL` at `answerable_toolbox_test` |

Administration errors are in [Administer the Toolbox](/docs/mcp/toolbox-admin#errors). The journeys that prove this against real ID are in [Test MCPs locally](/docs/mcp/local-testing#what-the-toolbox-journeys-prove). The SDK options the Toolbox is built on are in [the server section](/docs/mcp/authoring#the-server).
