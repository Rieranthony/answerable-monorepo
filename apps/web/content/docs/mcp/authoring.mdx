```ts
import { defineTool } from "@answerable/mcp"
import { z } from "zod"

export const identityGet = defineTool({
  name: "identity.get",
  description: "Read your verified identity: your user id and the organisation you signed in to.",
  input: z.object({}),
  output: z.object({ userId: z.uuid(), organizationId: z.uuid() }),
  async execute(_input, { principal }) {
    return { userId: principal.userId, organizationId: principal.organizationId }
  },
})
```

Save this as `mcps/example/src/tools.ts`. A read tool is these five fields; everything else has a default. `defineTool` checks the definition and returns it as frozen data.

| Field | Default |
| --- | --- |
| `title` | None |
| `version` | The provider's version |
| `scopes` | `["<provider id>:read"]` |
| `deprecated` | None |
| `view` | None |
| `timeoutMs` | `25000` |
| `errors` | None. The custom [error codes](#tool-errors) the handler throws |

**Field descriptions.** Describe each input field with `.describe()`; the text reaches the model in the tool's `inputSchema`. Recommended, not enforced.

A tool that changes data is a [mutation](#mutations): prepared first, committed second. Check either with [the conformance kit](/docs/mcp/testing); the rules a definition follows are on [the design standard](/docs/mcp/standard) page, and every export is in the [API reference](/docs/mcp/reference).

## Names and identity

| Form | Example | Rule |
| --- | --- | --- |
| Tool name | `records.list` | `<domain>.<operation>`; each part a lowercase letter, then up to 15 lowercase letters or digits |
| Identity | `example/records.list` | `<provider id>/<name>`; never changes for the life of the tool |
| Wire name | `records_list` | The name with `_` for `.`; what hosts list and call |

Hosts add their own prefixes and suffixes to tool names, and some limit names to 64 characters, so the wire name uses only `[a-z0-9_]`. The dotted identity travels in `_meta`.

## Versions and deprecation

```ts
export const recordsFind = defineTool({
  // ...the five fields
  deprecated: { since: "2026-09-29", sunset: "2027-09-29", replacement: "records.search" },
})
```

**Version.** A date, `YYYY-MM-DD`; it defaults to the provider's version. The behaviour of one identity at one version never changes.

**Deprecation.** `since` and `sunset` are dates; `replacement` is optional and names another tool of the same provider that is not deprecated. The description sent to hosts ends with a sentence naming all three, for example `Deprecated since 2026-09-29; removed on 2027-09-29; use records.search instead.`, and `_meta` carries the `deprecated` object.

Two versions of one tool name in one provider: Not yet. `defineProvider` refuses a duplicate name.

## What the wire carries

| `tools/list` field | Value |
| --- | --- |
| `name` | The wire name |
| `title` | `title`, when set |
| `description` | `description`, plus the deprecation sentence |
| `inputSchema` | The JSON Schema of `input`, with `additionalProperties: false` |
| `outputSchema` | The JSON Schema of `output` |
| `annotations` | `readOnlyHint: true`, `destructiveHint: false`, `idempotentHint: true`, `openWorldHint: false` |
| `_meta["com.answerable/capability"]` | `{ identity, version, kind: "read" }`, plus `deprecated` when set. A mutation's prepare tool: [see below](#the-prepare-tool) |
| `_meta.ui.resourceUri` | The view's URI, when the tool has a view. The MCP Apps helper also writes the older `_meta["ui/resourceUri"]` |

**Results.** The server checks the value `execute` returns against `output`, drops every field `output` does not declare, and sends it as `structuredContent` and as the same JSON in one text block. Claude Code shows the model only the structured content, so put everything the model needs in the output. A failure carries no structured content; see [tool errors](#tool-errors).

**Scopes decide visibility.** A token lists only the tools, prompts and resources whose every scope it carries. A tool it cannot use is absent from `tools/list`, and calling it returns the protocol's unknown-tool error.

**Closed input.** `defineTool` applies `.strict()` to `input`, so an unknown top-level field answers `INVALID_INPUT`. Nested objects keep Zod's default of dropping unknown fields; use `z.strictObject` to close them too.

Annotations describe the tool for hosts; they never authorise anything.

## Context

`execute(input, context)` receives the parsed input and a frozen context.

| Field | Meaning |
| --- | --- |
| `principal` | `userId`, `organizationId`, `membershipId`, `grantId`, `clientId`, `scopes`, `expiresAt` and `organizationAuthorizationVersion` from the verified token |
| `executionId` | A UUIDv7 minted for this call; it is the error envelope's `request_id` and appears in the server log |
| `signal` | Aborts when the host cancels, disconnects or the tool's timeout passes |

Constrain every query by `principal.organizationId`. Prompts and resources receive the same context.

## Dependencies

```ts
import { defineProvider, defineTool } from "@answerable/mcp"
import { z } from "zod"

export function createExampleProvider({ records }: { records: RecordStore }) {
  const recordsCount = defineTool({
    name: "records.count",
    description: "Count the records of your organisation. Use records.list to read them.",
    input: z.object({}),
    output: z.object({ count: z.number().int() }),
    async execute(_input, { principal }) {
      return { count: await records.count(principal.organizationId) }
    },
  })
  return defineProvider({ id: "example", version: "2026-09-29", tools: [recordsCount] })
}
```

Pass dependencies by closure: define the tools inside a function that receives them. The server takes the provider that function returns; a test passes an in-memory store.

**Composition.** A tool is plain data, so ordinary code composes it: collect tools from several modules into one array, wrap `execute` to audit every call, or call `execute` directly in a unit test.

```ts
import { defineTool, type Tool } from "@answerable/mcp"

function audited(tool: Tool, log: (line: string) => void): Tool {
  return defineTool({
    ...tool,
    async execute(input, context) {
      log(`${context.principal.userId} ${tool.name} ${context.executionId}`)
      return tool.execute(input, context)
    },
  })
}
```

## Mutations

```ts
import { defineMutation, ToolError } from "@answerable/mcp"
import { z } from "zod"
import { records } from "./records"

export const recordsDelete = defineMutation({
  name: "records.delete",
  description: "Prepare deleting one of your organisation's records. Changes nothing: returns a preview; show the person its summary, then commit the intent with the tool its commit_tool names.",
  input: z.object({ id: z.uuid() }),
  output: z.object({ deleted: z.literal(true) }),
  async prepare({ id }, { principal }) {
    const record = await records.get(principal.organizationId, id)
    if (!record) throw new ToolError("NOT_FOUND", "No accessible record exists")
    return {
      targets: [{ resource_type: "record", resource_id: id, label: record.title, version: { kind: "serial", value: String(record.version) } }],
      preview: { summary: `Delete record “${record.title}”`, changes: [{ path: `records[${id}]`, from: record, to: null }] },
      plan: { id },
    }
  },
  async commit({ plan, preview }, { principal }) {
    await records.remove(principal.organizationId, plan.id)
    return { results: { deleted: true }, applied_changes: preview.changes, effects_performed: [] }
  },
})
```

Add it to the provider's `tools`. A mutation is a read tool's fields with `prepare` and `commit` in place of `execute`. The server turns it into a prepare tool, `records_delete`, which records an intent and changes nothing, and adds two commit tools that apply intents. `output` is the schema of the receipt's `results`.

| Field | Default |
| --- | --- |
| `risk` | `normal`. `low`, `normal` or `high`; sets the [policy class](#policy-classes) |
| `effects` | `[]`. The effects a preview may name, from `notification`, `external_call`, `money_movement`, `cascade_delete`, `permission_change`, `publication` |
| `expiresInMs` | The class's expiry. It may shorten it, never lengthen it |
| `scopes` | `["<provider id>:write"]` |
| `title`, `version`, `deprecated`, `timeoutMs`, `errors` | As for a read tool. `errors` covers both `prepare` and `commit` |

### Prepare and commit

**`prepare(input, context)`** resolves the targets, reads their current state and returns `{ targets, preview, plan }`. It must not change anything; the conformance kit checks it with `prepare_has_no_side_effect`.

**`plan`** is your own data for `commit`, optional. It is stored as JSON, so keep it plain data. Its type flows from `prepare` to `commit`.

**`commit(plan, context)`** receives exactly what `prepare` returned, as stored: `{ targets, preview, plan }`. It applies the change and returns `{ results, applied_changes, effects_performed }`. The server checks `results` against `output` and drops undeclared fields. When no target moved, the prepared `preview.changes` are the applied changes.

Both throw `ToolError` for expected failures, as `execute` does. `context` is the same as a read tool's.

### Targets and versions

Every resource `commit` reads or writes is a target: `{ resource_type, resource_id, label, version: { kind, value } }`. `kind` is `etag`, `version`, `timestamp` or `serial`; `value` is a string; `label` names it for people. A mutation that creates something has no target yet: `targets: []`.

**Staleness.** At commit the server runs `prepare` again with the stored input and compares the targets by type and id. A version that moved, a target that disappeared or one that appeared answers `INTENT_STALE` with `details.targets`, the intent becomes `stale` and `commit` does not run. Nothing is locked while the person reviews the preview.

### The preview

| Field | Rule |
| --- | --- |
| `summary` | Required, 1 to 500 characters: the words the person confirms |
| `changes` | `{ path, from, to }`; `from` and `to` default to `null` |
| `effects` | Effects beyond the change, from the mutation's `effects`. Naming another answers `INTERNAL` and logs the definition to fix |
| `warnings` | Consequences that are possible, not certain |
| `quantities` | `{ name, value, unit }` |

Every array defaults to empty. Echoing the arguments is not a preview: say what will change, from what, to what.

### Policy classes

| `risk` | Class | Commit with | Expiry after prepare |
| --- | --- | --- | --- |
| `low` | `agent` | `<id>_commit` | 10 minutes |
| `normal` | `controlled` | `<id>_commit_confirmed`, after the person sees the summary | 30 minutes |
| `high` | `human` | A person's approval. Not yet | 24 hours |

`<id>` is the provider id. A human-class intent is recorded as `awaiting_approval`; both commit tools answer `APPROVAL_REQUIRED` with `details.approval.status: "pending"` until it expires, because approval pages are Not yet.

```ts
import { createMcpServer, riskClass } from "@answerable/mcp"

// People confirm low-risk mutations too.
createMcpServer({ provider, auth, policyClass: mutation => (mutation.risk === "low" ? "controlled" : riskClass[mutation.risk]) })
```

`policyClass` decides the class for each caller and request; the default is `riskClass`, the table above as data. The prepare tool's `_meta` and the intent carry the result, and the class's expiry caps `expiresInMs`.

### The prepare tool

| `tools/list` field | Value |
| --- | --- |
| `name` | The wire name, as for a read tool: `records_delete` |
| `inputSchema` | `input` plus `validate_only`, a boolean, default `false` |
| `outputSchema` | The intent, below |
| `annotations` | `readOnlyHint: true`, `destructiveHint: false`, `idempotentHint: true`, `openWorldHint: false`: preparing changes nothing |
| `_meta["com.answerable/capability"]` | `{ identity, version, kind: "mutate", risk, policy_class }`, plus `deprecated` when set |

It returns the intent as structured content and as the same JSON in text:

```json
{
  "intent_id": "0199a4e2-7b06-7000-87bd-91723fe45f93",
  "capability": "example/records.delete",
  "version": "2026-09-29",
  "policy_class": "controlled",
  "commit_tool": "example_commit_confirmed",
  "commit_token": "act_Yc1…",
  "expires_at": "2026-09-29T12:30:00.000Z",
  "targets": [{ "resource_type": "record", "resource_id": "5b0e…", "label": "Q3 plan", "version": { "kind": "serial", "value": "1" } }],
  "preview": { "summary": "Delete record “Q3 plan”", "changes": [{ "path": "records[5b0e…]", "from": { "title": "Q3 plan" }, "to": null }], "effects": [], "warnings": [], "quantities": [] },
  "approval": { "required": false, "status": "not_required" }
}
```

**Commit token.** `act_` and 32 random bytes in base64url. It is returned once; the store keeps only its SHA-256.

**`validate_only: true`** runs the same path and records nothing: `intent_id` and `commit_token` are `null`.

**Human class.** `approval` is `{ "required": true, "status": "pending" }`; `approval.url` is Not yet.

### Commit tools

| Tool | Input | Annotations | `_meta` |
| --- | --- | --- | --- |
| `<id>_commit` | `{ intent_id, commit_token }` | `readOnlyHint: false`, `destructiveHint: false`, `idempotentHint: true`, `openWorldHint: false` | `com.answerable/capability`: `{ identity: "<id>/commit", kind: "commit" }` |
| `<id>_commit_confirmed` | `{ intent_id, commit_token, preview_summary }` | The same, with `destructiveHint: true` | `{ identity: "<id>/commit_confirmed", kind: "commit" }` and `anthropic/requiresUserInteraction: true` |

A server with mutations serves both. A caller sees them when their token can use at least one mutation; otherwise they are unknown tools. The intent's `commit_tool` names the one to call. `preview_summary` must equal the intent's `preview.summary` word for word, so the host confirms the server's words. Whether each host honours `anthropic/requiresUserInteraction`: not yet tested.

They return the receipt:

```json
{
  "receipt_id": "0199a4e3-1f20-7000-8c55-0e7d2b9a4f10",
  "intent_id": "0199a4e2-7b06-7000-87bd-91723fe45f93",
  "status": "committed",
  "results": { "deleted": true },
  "applied_changes": [{ "path": "records[5b0e…]", "from": { "title": "Q3 plan" }, "to": null }],
  "effects_performed": [],
  "committed_at": "2026-09-29T12:04:11.000Z",
  "committed_by": { "user_id": "…", "membership_id": "…", "client_id": "claude-code-local" },
  "idempotent_replay": false
}
```

**What a commit checks, in order.**

1. The intent exists: else `INTENT_NOT_FOUND`.
2. The caller's user, membership and client are the preparer's: else `PRINCIPAL_MISMATCH`, before anything about the intent is revealed.
3. Its status: `committed` returns the stored receipt with `idempotent_replay: true`; `committing` answers `COMMIT_IN_PROGRESS`; `expired`, `stale` and `failed` answer `INTENT_EXPIRED`, `INTENT_STALE` and `INTENT_CONSUMED`; `awaiting_approval` answers `APPROVAL_REQUIRED`.
4. This server serves the intent's capability version, else `INTENT_NOT_FOUND`; the caller can still use the mutation (the token carries its scopes, or a hub's `allow` still admits it), else `PERMISSION_DENIED`.
5. The SHA-256 of `commit_token` matches: else `COMMIT_TOKEN_INVALID`.
6. The tool matches the class, and a controlled intent's `preview_summary` matches: else `APPROVAL_REQUIRED` with `details.approval`.
7. The intent moves to `committing`: the token is spent.
8. `prepare` runs again and the targets are compared: a change answers `INTENT_STALE`.
9. `commit` runs. The receipt is stored and the intent is `committed`. A `ToolError` marks it `failed` and is returned; any other exception marks it `failed` and answers `INTERNAL`. A later commit answers `INTENT_CONSUMED`.

A refusal in steps 1 to 6 leaves the intent committable. [MCP errors](/docs/mcp/errors) has every code.

**Replay.** A repeat by the same principal returns the same receipt with `idempotent_replay: true`; `commit` runs once.

**Concurrency.** A commit while another runs answers `COMMIT_IN_PROGRESS`. The store claims an intent by compare-and-set, so two commits never both run.

**Timeouts.** `timeoutMs` bounds `prepare` in the prepare tool, and bounds `prepare` plus `commit` in a commit tool. Past it the caller gets `TIMEOUT` while the commit carries on to `committed` or `failed`; calling again answers `COMMIT_IN_PROGRESS`, then the receipt.

### The intent store

```ts
import { createMcpServer, createMemoryIntentStore } from "@answerable/mcp"

let clock = Date.now()
const intents = createMemoryIntentStore({ now: () => clock })
const server = createMcpServer({ provider, auth, intents })
clock += 10 * 60_000 // every agent-class intent prepared so far has expired
```

By default each server keeps intents in memory, lost when the process stops. The store owns the clock and decides expiry, so a test moves `now` instead of waiting. `IntentStore` is four members: `now()`, `insert(intent)`, `get(intentId)`, which marks an intent `expired` once `expires_at` has passed, and `transition(intentId, from, to, receipt?)`, a compare-and-set on the status. [The Toolbox](/docs/mcp/toolbox#mutations-through-the-toolbox) keeps its intents in Postgres with a store of its own.

### Views and mutations

A view prepares, shows `preview.summary`, then calls the tool in `commit_tool` with `intent_id`, `commit_token` and, for a controlled intent, `preview_summary`. The view in `mcps/e2e` creates a record with `records_create` then `e2e_commit`, and deletes one with `records_delete`, a confirmation that shows the summary, then `e2e_commit_confirmed`.

## The provider

```ts
import { defineProvider } from "@answerable/mcp"
import { identityGet } from "./tools"

export const provider = defineProvider({ id: "example", version: "2026-09-29", tools: [identityGet] })
```

Save this as `mcps/example/src/provider.ts`. A provider is a named, dated set of tools, prompts and resources. `defineProvider` fills each definition's identity, version and scopes, refuses a duplicate tool name, prompt name or resource URI, and returns frozen data.

| Field | Rule |
| --- | --- |
| `id` | A lowercase letter, then up to 11 lowercase letters or digits |
| `version` | A date, `YYYY-MM-DD`. Change it when the provider's contract changes |
| `tools` | Definitions from `defineTool` and `defineMutation`. A declared [error code](#tool-errors) starts with the provider id in capitals |
| `prompts`, `resources` | Optional; see [prompts and resources](#prompts-and-resources) |

## The server

```ts
import { createMcpServer, readMcpEnvironment } from "@answerable/mcp"
import { provider } from "./provider"

const { auth, port } = readMcpEnvironment(process.env)
const server = createMcpServer({ provider, auth })
Bun.serve({ hostname: "127.0.0.1", port, fetch: server.fetch })
```

Save this as `mcps/example/src/server.ts`. `createMcpServer` returns `{ fetch, toolsChanged, call }`: `fetch` is the web-standard handler the entry point serves; the other two are for [changes](#changes) and [hubs](#hubs).

**What it serves.** `GET /health`, the protected-resource metadata, and the MCP endpoint at the resource URL's path behind the bearer gate. It answers both the 2026 and the 2025 protocol revisions, builds a fresh MCP server per request and sends `Cache-Control: no-store`. The server's name and version are the provider's id and version.

**Hosts and origins.** It refuses a `Host` header or browser `Origin` other than the resource URL's host name.

**Cache hint.** `tools/list` tells `2026-07-28` hosts they may keep the list for 30 seconds, for that caller alone (`ttlMs: 30000`, `cacheScope: "private"`): a token's scopes never change during its life.

### Changes

```ts
server.toolsChanged() // every caller listening for changes lists its tools again
```

Every server advertises `tools.listChanged: true`. `toolsChanged()` sends `notifications/tools/list_changed` to every caller that listens: a `2026-07-28` host that opened `subscriptions/listen` with `toolsListChanged`, as the official client does when given `listChanged` options. It reaches every listener of the server, whoever they are. A listen stream sends a keep-alive comment every 5 seconds, inside `Bun.serve`'s default 10-second idle timeout, which would otherwise close it.

**2025 hosts: Not yet.** The SDK serves the 2025 revision statelessly, so `GET` answers `405` and no stream can carry a notification; a 2025 host sees a change when it lists again.

### Hubs

Four options, off by default, serve several providers at one endpoint, as [the Toolbox](/docs/mcp/toolbox) does:

| Option | Effect |
| --- | --- |
| `mount` | Providers served beside `provider`. Their tools are named `<provider id>_<wire name>` after `provider`'s own, their mutations commit through `provider`'s commit tools, and their views keep their URIs. Their prompts and resources are not served; `scopes_supported` lists `provider`'s scopes only |
| `allow(principal, tool, called)` | Decides which tools the caller may use, in place of scopes, for each request that lists or calls tools or reads views; `called` is true for the tool a call names. A `ToolError` it throws answers any call with that envelope, and a list fails |
| `project(principal, usable)` | Returns which of the usable tools are served to the caller as tools, for a hub that offers some capabilities through its own tools instead. The others stay usable: their intents commit, and `call` runs them. A tool the caller may not use is never served, whatever it returns |
| `wrapCall(call, run)` | Runs around every tool, prepare and commit call with the tool, wire name, principal, execution id, JSON-RPC id and `_meta`. For a commit, `call.tool` is `{ kind: "commit", identity, version }`: `<id>/commit` or `<id>/commit_confirmed` at the provider's version. Return what `run()` returns, or throw a `ToolError` to answer with it instead |

**`call(tool, args, context)`** runs a tool the server serves exactly as its direct call runs it, for the caller in `context`: the arguments are checked (`INVALID_INPUT` names the tool's own fields), the handler runs within its own timeout, the output is checked, and a mutation is prepared and its intent recorded, with the commit tool of its class. The codes the tool declares pass through the calling tool unchanged. It is for a hub's own tools, such as the Toolbox's `toolbox_execute`: it does not decide whether the caller may use the tool, and it runs inside the calling tool's `wrapCall`.

## Create a workspace

```sh

bun install
UPDATE_MANIFEST=1 bun run --filter @answerable/mcp-example test

[Test an MCP](/docs/mcp/testing#check-a-workspace) says what that runs.

## Configure

```dotenv
MCP_ID_ISSUER=http://localhost:47300
MCP_RESOURCE_URL=http://localhost:47500/mcp
MCP_PORT=47500
```

`readMcpEnvironment(process.env)` reads these three variables and returns `{ auth, port }`.

**Issuer.** The Answerable ID origin. The verifier reads ID's signing keys from the issuer's metadata; never take an issuer from a token.

**Resource.** The MCP's canonical URL, exactly as registered in ID. It is the token audience, and its path is the MCP endpoint.

**HTTP.** Both URLs must use HTTPS, except on `localhost`, `127.0.0.1` or `[::1]`.

Register the resource, a client and its access in ID before the first sign-in; see [Connect Claude Code](/docs/mcp/claude-code#register-the-server). Each MCP running at the same time needs its own port.

## Health

`GET /health` returns `{ "status": "ok" }` without authentication, whatever the `Host` header, so load balancers and container probes can call it by address.

## Descriptions

The description is what a model reads to choose a tool. Write operational documentation, not a title:

| Say | Example |
| --- | --- |
| What it does | `List the RFIs of a project, newest first.` |
| When to use it and what to call first | `Use projects.search first to find the project id.` |
| Its limits | `20 per page by default and at most 100.` |
| Whether it changes state | A mutation: `Prepare deleting a record. Changes nothing: returns a preview; commit the intent with the tool its commit_tool names.` Name no commit tool: a hub serves the mutation under its own commit tools, and the intent's `commit_tool` says which |
| What identifiers mean | `id is the record's id from records.list.` |

`defineTool` refuses fewer than 40 or more than 1,000 characters. The conformance kit adds two checks, `descriptions_operational` (a mutation's description says `prepare` or `intent`) and `deprecations_mirrored` (a deprecated tool's description ends with the deprecation sentence).

## Pagination

```ts
input: z.object({
  limit: z.number().int().min(1).max(100).default(20).describe("Records per page, 1 to 100"),
  cursor: z.string().optional().describe("next_cursor from the previous page; omit it for the first page"),
}),
output: z.object({ items: z.array(record), next_cursor: z.string().nullable(), has_more: z.boolean() }),
```

Every tool that can return an unbounded list takes these two fields and returns these three. Never truncate silently.

| Field | Rule |
| --- | --- |
| `limit` | Integer; default at most 20; the schema enforces the maximum |
| `cursor` | Optional; opaque to callers |
| `items` | The page |
| `next_cursor` | The cursor for the next page, or `null` on the last |
| `has_more` | `true` when another page exists |

`@answerable/mcp` exports nothing for pagination: declare the fields in your schemas, and the conformance kit's `list_paginates` fails a tool whose output has an `items` array without them. `records.list` in `mcps/e2e` is the working example; a cursor it did not issue answers `INVALID_INPUT` with a field violation on `cursor`.

**Size.** Through [the Toolbox](/docs/mcp/toolbox#limits), a read whose result is above 100 KiB of JSON answers `RESULT_TOO_LARGE`, so keep the default page well below that.

## Tool errors

```ts
import { ToolError } from "@answerable/mcp"

throw new ToolError("NOT_FOUND", "No accessible record exists")
throw new ToolError("RATE_LIMITED", "Try again shortly", { retry: { policy: "after_delay", after_ms: 30000 } })
throw new ToolError("PRECONDITION_FAILED", "The record is locked", { details: { preconditions: ["unlocked"] } })
```

Throw `ToolError(code, message, options?)` for an expected failure. The caller receives `{ "isError": true, "content": [{ "type": "text", "text": "…" }] }`, with no `structuredContent` ([why](/docs/mcp/errors)); the one text block is the envelope as JSON:

```json
{
  "error": {
    "code": "NOT_FOUND",
    "message": "No accessible record exists",
    "retry": { "policy": "never" },
    "request_id": "0199a4e2-7b06-7000-87bd-91723fe45f93"
  }
}
```

`details` appears only when given. `retry.policy` tells the model what to do next without reading the message. `after_delay` without `after_ms` gets `after_ms: 1000`.

| Code | When a handler throws it | Retry |
| --- | --- | --- |
| `INVALID_INPUT` | A business rule refuses the input; pass `details.field_violations` | `after_fix_input` |
| `NOT_FOUND` | A named resource does not exist for this caller | `never` |
| `PERMISSION_DENIED` | The caller may not perform this operation on this target | `never` |
| `PRECONDITION_FAILED` | The current state does not allow the operation; `details.preconditions` says what | `after_state_change` |
| `UPSTREAM_REJECTED`, `UPSTREAM_UNAVAILABLE` | The source refused, or did not answer | `never`, `after_delay` |

[MCP errors](/docs/mcp/errors) lists every code, including those the server and the commit tools answer, with what the caller does for each. `errorCodes` exports the full table as data, and `ErrorCode` as a type.

**Custom codes.** A provider may add `<PROVIDER>_<CODE>` in capitals, for example `ACME_QUOTA_EXCEEDED`, with an explicit retry: `new ToolError("ACME_QUOTA_EXCEEDED", "…", { retry: { policy: "after_delay" } })`. Any other code, or a custom code without `retry`, throws when the error is constructed.

**Declare them.** A tool or mutation lists the custom codes it throws in `errors`; standard codes need no declaration. The list reaches the [manifest](#manifest), so a reviewer sees every code a provider can answer.

```ts
export const projectsCreate = defineMutation({
  // ...the mutation's fields
  errors: ["ACME_QUOTA_EXCEEDED"],
  async prepare(input, { principal }) {
    if (await quotaUsed(principal.organizationId)) {
      throw new ToolError("ACME_QUOTA_EXCEEDED", "Your plan allows 100 projects", { retry: { policy: "after_state_change" } })
    }
    // ...
  },
})
```

Each entry must be a custom code that starts with the provider's id in capitals: `defineProvider` refuses `OTHER_QUOTA` in provider `acme`. A handler that throws a custom code its definition does not list is an author's bug: the caller receives `INTERNAL`, and the server log says which code to add.

**What the server answers for you.**

| Case | Answer |
| --- | --- |
| The input fails `input` | `INVALID_INPUT`, one field violation per issue (`{ field: "a.b", message }`); the message lists them; `execute` does not run |
| `execute` runs past `timeoutMs` | `TIMEOUT`; `context.signal` aborts and the answer does not wait for `execute` |
| Any other exception, an undeclared custom code, or an output that fails `output` | `INTERNAL` with the message `The tool could not complete`, and `[mcp] tool <name> failed` with the execution id in the server log |

## Manifest

`manifest(provider)` returns the provider's contract as plain JSON: `id`, `version`, every tool (sorted by identity) with its identity, wire name, version, kind, title, description, deprecation, scopes, declared `errors`, annotations and the JSON Schema of its input and output, then the prompts and resources. It carries no code.

**Mutations.** A mutation's entry adds `risk` and `effects`; its `input` is the definition's input, without `validate_only`, and its `output` is the schema of the receipt's `results`. A provider with mutations also lists the two commit tools, `kind: "commit"`, whose `scopes` are the union of the mutations' scopes.

Commit the file next to the source and let the conformance kit's `manifest_matches_snapshot` fail on drift. A change to any definition fails the test until you regenerate the file and commit it, so every contract change shows in review:

```sh
UPDATE_MANIFEST=1 bun run test
```

Run it in the provider's workspace. [Test an MCP](/docs/mcp/testing#the-manifest-snapshot) has the details; `mcps/e2e/manifest.json` is the working example.

## Prompts and resources

`definePrompt` takes `name`, `description`, a Zod `input` and `execute(input, context)`, which returns an MCP prompt result. `defineResource` takes `name`, a fixed `uri`, `description`, `mimeType` and `read(context)`, which returns text. Both take optional `scopes`, defaulting to `<provider id>:read`, and follow the same visibility rule as tools. Names are lowercase letters, digits and underscores. Reading a prompt or resource must not change data; a failure answers the protocol error `Content could not be read`.

## Views

```ts
import { buildView } from "@answerable/mcp/build"

const html = await buildView({ entry: "src/views/records.tsx", title: "Records" })
```

Build each view before starting the server, pass the HTML to `defineView({ name, html })`, and set the view on a tool. The server registers it as a `ui://` resource with the MCP Apps MIME type. Browser code imports `useApp` from `@modelcontextprotocol/ext-apps/react` or `App` from `@modelcontextprotocol/ext-apps`. A view calls tools through the host, with the same scope and organisation checks; it never receives a token. `mcps/e2e` is the working example.

## Test

```ts
import { assertProviderConformance, createTestMcp } from "@answerable/mcp/testing"
```

`createTestMcp(provider)` serves a provider in-process, with no port and no network, for tests of your own logic. `assertProviderConformance(provider, fixture)` runs the standard's checks against it. [Test an MCP](/docs/mcp/testing) covers both, the helpers beside them, the manifest snapshot and `bun run mcp:check`; [Test MCPs locally](/docs/mcp/local-testing) covers the real sign-in through ID. `mcps/e2e/src/mcp.test.ts` and `mcps/e2e/src/conformance.test.ts` are the working examples.

## Limits

| Limit | Value |
| --- | --- |
| Tool name part | 16 characters |
| Provider id | 12 characters |
| Description | 40 to 1,000 characters |
| `timeoutMs` | 1 to 55,000; default 25,000. Longer work: Not yet |
| Declared errors | Custom `<PROVIDER>_<CODE>` codes only, starting with the provider id in capitals |
| Tool kinds | Read and mutate. Start and subscribe: Not yet |
| Versions per tool name in a provider | One |
| Preview summary | 1 to 500 characters |
| Intent expiry | 10 minutes, 30 minutes or 24 hours by class; `expiresInMs` only shortens it |
| Intents in the memory store | Kept until the process stops. For a long-lived server, pass your own `IntentStore` |
| Human approvals, operations, idempotency keys, batches of intents | Not yet |

## Errors

| Error | Meaning | What to do |
| --- | --- | --- |
| `Tool name "…" must be <domain>.<operation>…` at start | The name breaks the naming rule; a mutation says `Mutation name` | Rename it, for example `records.list` |
| `Tool …: the description is N characters…` | Shorter than 40 or longer than 1,000; a mutation says `Mutation …` | Say what it does, when to use it and its limits |
| `Tool …: timeoutMs … must be a whole number of milliseconds from 1 to 55,000` | The timeout is out of range | Use at most 55,000 |
| `Mutation …: risk "…" must be low, normal or high` | Another value | Use one of the three, or omit it for `normal` |
| `Mutation …: effect "…" is not in the vocabulary…` | An effect outside the six | Use a name from the vocabulary |
| `Mutation …: expiresInMs … must be a whole number…; a mutation may shorten its expiry, not lengthen it` | Longer than the expiry its `risk` gives, or not a whole number | Shorten it, or omit it |
| `…must be a date, YYYY-MM-DD` | A version or deprecation date is not a calendar date | Write the date as `YYYY-MM-DD` |
| `…scopes must be non-empty and contain no spaces…` | An empty scope list or a scope with a space | Omit `scopes` for the default, or fix the list |
| `Provider id "…" must be a lowercase letter…` | The id breaks the rule | Use up to 12 lowercase letters or digits, starting with a letter |
| `Provider … defines tool … twice` | Two definitions share a tool name, prompt name or resource URI | Rename one |
| `Provider … defines two different views at …` | Two views share a name | Share one `defineView` result, or rename a view |
| `Provider …: tool … is deprecated in favour of …, which is not a current tool of this provider` | The replacement is missing or itself deprecated | Name a current tool of the provider |
| `View name "…" must be…`, `Prompt name "…" must be…`, `Resource name "…" must be…` | The name breaks its rule | Rename it as the message shows |
| `View …: the HTML is empty…` | The view was not built | Build it with `buildView` before `defineView` |
| `Resource …: uri "…" must be an absolute URI…`, `Resource …: … is a ui:// view…` | The URI is relative, or it is a view's | Use an absolute URI such as `fixture://guide`; define a view with `defineView` |
| `Views must bundle to one script and optional CSS…` | The view imports a file that the bundler emits on its own | Embed it in the script or the CSS |
| `Provider … is mounted twice…` | A hub mounts one provider twice, or mounts its own provider | Mount each provider once |
| `ToolError code "…" must be a standard code or <PROVIDER>_<CODE>…` | The code is not in the table and has the wrong shape | Use a standard code, or `ACME_SOMETHING` |
| `ToolError code "…" is not in the standard table; pass { retry }…` | A custom code without a retry policy | Pass `{ retry: { policy } }` |
| `Tool …: errors entry "…" must be a custom code…` | An entry in `errors` is a standard code, or not `<PROVIDER>_<CODE>` in capitals; a mutation says `Mutation …` | Remove standard codes; write custom ones as `ACME_QUOTA_EXCEEDED` |
| `Provider …: … declares error "…"; a custom code of this provider starts with …_` | A declared code does not start with the provider id in capitals | Rename it, for example `ACME_QUOTA_EXCEEDED` in provider `acme` |
| `401 invalid_token` | Missing, expired or foreign token, or a token for another MCP | Sign in through ID for this MCP's resource URL |
| `403` on the MCP endpoint | The `Host` or browser `Origin` is not the resource URL's host name | Call the MCP by its registered host name |
| Unknown tool, prompt or resource | Not defined, or the token lacks its scopes | Check the token's scopes against the definition |
| Tool result `INVALID_INPUT` | The arguments failed the schema or a business rule | Fix the fields in `details.field_violations` |
| Tool result `TIMEOUT` | The handler ran past `timeoutMs` | Make it faster, or raise `timeoutMs` up to 55,000 |
| Tool result `INTERNAL` | Unexpected handler failure, or output that does not match `output` | Read the server log for `[mcp] tool <name> failed` and the `request_id`; a commit tool logs under its wire name |
| `INTERNAL` from a prepare tool, logged with `Mutation …: the preview names effects it does not declare…` | The preview names an effect missing from `effects` | Declare it in `effects`, or leave it out of the preview |
| `INTERNAL` from a prepare tool, logged with a Zod error | The plan breaks its shape: no summary, a summary over 500 characters, a target without a version | Return the shape in [the preview](#the-preview) and [targets](#targets-and-versions) |
| A commit tool's result code | The intent cannot be committed as it is | See [MCP errors](/docs/mcp/errors) |
| A conformance test fails | A definition breaks a rule of the standard | See [Test an MCP](/docs/mcp/testing#errors) |
| Tool result `INTERNAL`, logged as `… threw ACME_…, which its definition does not declare; add it to errors` | The handler threw a custom code missing from `errors` | Add the code to the definition's `errors` |
| Tool result with your code | A `ToolError` you threw | Handle the code |
| `Invalid MCP configuration: …` at start | A missing or invalid variable | Set the named variable |
| `Server name "…" must be a lowercase letter then up to 11 lowercase letters or digits…` from `mcp:new` | The name is not a provider id | Use a name such as `acme` |
| `mcps/<name> already exists; choose another name or remove it` from `mcp:new` | The directory exists | Choose another name, or remove the directory |
| `…/manifest.json is out of date; regenerate it with UPDATE_MANIFEST=1…` from a new server's first `mcp:check` | Its manifest has not been written yet | Run `UPDATE_MANIFEST=1 bun run --filter @answerable/mcp-<name> test` |
