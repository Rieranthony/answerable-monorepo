```ts
import { defineTool } from "@answerable/mcp-base"
import { z } from "zod"

export const identityGet = defineTool({
  name: "identity_get",
  description: "Read your authenticated organisation",
  input: z.object({}).strict(),
  output: z.object({ organizationId: z.uuid() }),
  scopes: ["example:read"],
  annotations: { readOnlyHint: true, openWorldHint: false },
  async execute(_input, context) {
    return {
      data: { organizationId: context.principal.organizationId },
      text: "Authenticated with Answerable ID",
    }
  },
})
```

Approve the tool's scopes in ID before calling it. Definitions are ordinary TypeScript exports: select them explicitly in each MCP's `tools` array. Move shared domain tools into a package when a second MCP needs them.

## Create a workspace

Create `mcps/example/package.json` with the shared base and the schemas your tools use:

```json
{
  "name": "@answerable/mcp-example",
  "private": true,
  "type": "module",
  "scripts": {
    "dev": "bun --hot src/server.ts",
    "start": "bun src/server.ts"
  },
  "dependencies": {
    "@answerable/mcp-base": "workspace:*",
    "zod": "4.6.5"
  }
}
```

Save the tool above as `mcps/example/src/tools.ts`, then add the server below as `src/server.ts`. Run `bun install` from the monorepo root. The existing `mcps/*` workspace pattern includes the new package.

Register a distinct resource in ID and authorise a client, capabilities and assignments for `example:read`. In `mcps/example/.env`, set:

```dotenv
MCP_ID_ISSUER=http://localhost:47300
MCP_ID_JWKS_URL=http://localhost:47300/auth/jwks
MCP_RESOURCE_URL=http://localhost:47500/mcp
MCP_RESOURCE_INSTANCE_ID=replace-with-the-registered-resource-uuid
MCP_ALLOW_LOCAL_HTTP=true
MCP_PORT=47500
```

Use the exact registered resource URL and UUID. Each simultaneously running MCP needs its own port. From `mcps/example`, run `bun run dev`; Bun loads that workspace's `.env`. Root `bun dev` starts the ordinary apps only.

`mcps/e2e` is the executable reference for React Apps views, build scripts, TypeScript/ESLint configuration and tests. Add only the dependencies and scripts your consumer uses; its SQLite store and real-ID orchestration are test-fixture concerns. Workspace generation is deferred until a second real MCP establishes what repeats.

## Create the server

```ts
import { createMcpApp, readMcpEnvironment } from "@answerable/mcp-base"
import { identityGet } from "./tools"

const { auth, port } = readMcpEnvironment(process.env)
const app = createMcpApp({
  name: "example",
  version: "0.1.0",
  auth,
  services: {},
  tools: [identityGet],
})
const server = Bun.serve({ hostname: "127.0.0.1", port, fetch: app.fetch })
const close = () => { void server.stop() }
process.once("SIGINT", close)
process.once("SIGTERM", close)
```


`createMcpApp` takes `name`, `version`, `auth`, `services` and `tools`; `prompts` and `resources` are optional arrays. It returns a Hono app without opening a port. A Bun entry point serves `app.fetch` and owns process shutdown.

Use `readMcpEnvironment(process.env)` from the base for the common ID and port settings. It validates the `MCP_*` variables documented in the repository environment example and returns `{ auth, port }`.

`auth` contains the trusted `issuer`, `jwksUrl`, canonical `resource` URL and `resourceInstanceId`. Local HTTP requires `allowLocalHttp: true` and loopback addresses. Never derive these values from an incoming token.

A handler receives `principal`, injected `services`, `requestId` and an abort `signal`. Read the organisation from the verified principal and constrain every domain query by it. Business services own their storage and retry behaviour.

## Health and logs

`/health` reports liveness. Consumers own any dependency-specific operational checks.

The default request log contains only request ID, HTTP status and duration. Pass `log(event)` for your own sink or `log: false` to disable it. Tools and services supply their own business audit facts.

## Deadlines

The factory's `handlerTimeoutMs` defaults to 30 seconds after authentication, with a maximum of five minutes. A deadline aborts the handler signal and returns HTTP 504 with `request_timeout`. Pass the signal to downstream calls and check it before writes.

Cancellation is cooperative and does not undo committed effects. Retry an uncertain write with its original operation key. This stateless transport does not keep a session-wide registry for cancellation notifications sent in another HTTP request.

## Attach a view

Use `buildView({ entry, title })` from `@answerable/mcp-base/build` to compile a browser entry into HTML. Pass that HTML to `defineView({ name, html })`, then assign the returned view to a tool's `view` property.

For the first Apps view, use `mcps/e2e/scripts/build.ts` and `src/views/records.tsx` as working examples. Declare React, React DOM and their types in your workspace when using React, matching the versions in the reference consumer. Build the HTML before starting the server; keep the browser entry separate from `src/server.ts`.

The base registers the `ui://` resource and associates it with the tool through the official MCP Apps SDK. React views import the official `useApp` hook through `@answerable/mcp-base/apps/react`; framework-independent views use `/apps`.

Keep browser schemas in browser-safe modules. Do not import server entry points, databases or authentication configuration into a view. A view's tool calls pass through the same scope and tenant checks as calls from the model.

## Prompts and resources

`definePrompt` accepts `name`, `description`, a Zod object `input`, `scopes` and `execute(input, context)`. Return the official MCP prompt result, including its `messages`. Retrieving a prompt should describe actions, never perform writes.

`defineResource` accepts `name`, a fixed `uri`, `description`, `mimeType`, `scopes` and `read(context)`. Return text. Use `defineView` for `ui://` resources. Both helpers enforce scopes before invoking the handler.

The test MCP exposes `fixture_walkthrough` and `fixture://guide`; retrieving them leaves its records unchanged.

## Failure behaviour

| Failure | Result | Caller action |
| --- | --- | --- |
| Missing or invalid token | HTTP 401 with resource discovery challenge | Authenticate through ID for this resource |
| Untrusted browser origin | HTTP 403 | Use an explicitly permitted host origin |
| Missing tool scope | Tool error with `insufficient_scope` | Obtain the required authorised grant |
| Missing prompt/resource scope | Protocol error with `insufficient_scope` | Obtain the required authorised grant |
| Handler deadline | HTTP 504 with `request_timeout` | Retry uncertain writes with their original operation key |
| Cancelled HTTP request | HTTP 408 with `request_cancelled`, if deliverable | Check the operation outcome before starting a new action |
| Invalid tool input | SDK validation error result | Correct the arguments |
| Invalid tool output or unexpected handler failure | Tool error with `tool_failed` | Investigate the handler; retry uncertain writes with their original operation key |
| Unknown tool, prompt or resource | SDK protocol error | Discover the registered definitions |
| Unexpected prompt/resource failure | Generic protocol error and request ID | Investigate the server using the request ID |

`ToolError(code, message)` marks a safe domain error for callers. Never include credentials or internal exception details in it. Tool annotations describe behaviour; they do not enforce permissions or make operations idempotent.
