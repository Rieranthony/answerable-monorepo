`bun mcp` makes, checks and runs the MCPs of the repository. Run it from the repository root, or from inside `mcps/<name>`, where the MCP's name can be left out. This page is rendered from the command's own definitions, so it says what `bun mcp help` says.

| Command | Use it to |
| --- | --- |
| [`bun mcp new`](#bun-mcp-new) | Make an MCP: its files, its database schema, its first migration and its tests |
| [`bun mcp add tool`](#bun-mcp-add-tool) | Add a tool to an MCP |
| [`bun mcp list`](#bun-mcp-list) | See every MCP, where it runs and its URLs |
| [`bun mcp check`](#bun-mcp-check) | Typecheck, lint and test an MCP |
| [`bun mcp db`](#bun-mcp-db) | Write a migration for a change to its tables, or migrate its local schema |
| [`bun mcp setup`](#bun-mcp-setup) | Connect `bun mcp` to your local Answerable ID, once |
| [`bun mcp dev`](#bun-mcp-dev) | Run an MCP on your machine and connect Claude Code to it |
| [`bun mcp help`](#bun-mcp-help) | Print this reference |

## How it behaves

- **A terminal asks. A coding agent's shell does not.** In a terminal, a missing answer is asked, one question at a time. Without a terminal, `bun mcp` never waits for input: a missing answer exits with code 2 and prints the exact command to run again, with a placeholder where each missing answer goes.
- **One name for each flag.** The flags are the same in the questions, on the command line and in these docs: `--description`, `--serve`, `--database`, `--tool`, `--tool-description` and `--mutation`. There are no short forms and no aliases. `--description` always describes what the command makes: the MCP in `new`, the tool in `add tool`.
- **Every answer at once.** A command checks every answer it was given before it writes anything. Without a terminal it lists every answer that is missing or wrong, a line each, in the order of the questions, then one command to run again.
- **Nothing is half-written.** Every check runs before the first file is written. A step that fails after that leaves the files, says which step failed, and names the command that finishes the job.
- **Short, steady output.** One line for each step, then `Next:` with the commands that come next. `--json` prints the same facts as one object: `{ "ok": true, "steps": […], "next": […] }`, or `{ "ok": false, "error": { "code", "message", "fix", "problems": [{ "code", "message" }] } }` with a problem for each wrong answer.
- **Safe to repeat where it can be.** `check`, `dev`, `db migrate` and `setup` can run any number of times. `add tool` refuses a name that exists, and names the file.
- **The arguments.** In `add tool [mcp] <domain.operation>`, the word with a dot is the tool and the other is the MCP.

## bun mcp list

<CliReference command="list" />

Each MCP takes two lines. The first is its name, where it runs, its database mode, how many tools it has, the first sentence of its description and its local URL. The second is its staging and its production URL. The URLs are those the deployment gives it: the Toolbox's `/mcp` for a `toolbox` MCP, and `/<name>/mcp` on the `mcp` host, where the Toolbox serves it alone, for a `standalone` one; locally both are on the Toolbox's origin. An MCP that runs `both` has both.

## Errors

Every error has a code. With `--json` it is `error.code`, and each wrong answer has its own in `error.problems`. A step that fails answers `<step>-failed`, such as `database-failed`, for each step in the tables above.

## Not yet

- **`bun mcp retire`.** To remove an MCP, put its name in `mcps/retired.json`, which `bun mcp new` refuses for ever, and delete its folder. What it left in the databases and in Answerable ID stays. A command that does all of this: Not yet. Trigger: the first MCP that is removed.
- **`bun mcp move`.** Changing an MCP between the shared database and a database of its own is a dump and a restore of its schema, by hand. A command: Not yet. Trigger: the first MCP that changes its database mode.
