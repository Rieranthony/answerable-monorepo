---
title: Connect Claude Code
description: "Register the Toolbox or the e2e server and a Claude Code client in Answerable ID, then sign in from Claude Code and see the tools your organisation granted."
---

```bash
claude mcp add --transport http answerable-toolbox http://localhost:47400/mcp \
  --client-id claude-code-toolbox --callback-port 47700
```

Run this once the Toolbox is running and your organisation is enabled for it ([below](#the-toolbox)). Then open Claude Code, run `/mcp`, select `answerable-toolbox` and choose **Authenticate**. Your browser opens Answerable ID: sign in with your work account, choose the organisation and accept. Without a browser on that machine, run `claude mcp login answerable-toolbox --no-browser` in a terminal: it prints the address to open on another machine and asks you to paste back the address you are sent to. Ask Claude to call `toolbox_whoami`; it returns you, your organisation and the grants you hold. To connect the e2e server instead, see [the e2e server](#the-e2e-server).

**An MCP that has shipped.** The deploy registers it and prints these commands, and staff enable your organisation: [Your MCP's sign-in](/docs/mcp/sign-in#connect-claude-code).

**An MCP you are making.** `bun mcp dev <mcp>` registers it in your local ID, gives your organisation access and prints the command that connects Claude Code to it ([Run an MCP on your machine](/docs/mcp/local-testing#run-an-mcp-on-your-machine)). For an MCP that runs on its own URL, the command is:

```bash
claude mcp add --transport http acme http://localhost:47510/acme/mcp \
  --client-id claude-code-acme --callback-port 47700
```

For an MCP that runs in the Toolbox it is the Toolbox's command above. Then `/mcp`, choose the connection and **Authenticate**, as above. The sections below show by hand what `bun mcp dev` does.

## The Toolbox

[The Toolbox](/docs/toolbox) serves the tools your organisation granted you, and no others.

### What you see

| Your grants | Tools Claude Code lists |
| --- | --- |
| None | `toolbox_whoami` |
| `e2e/records` | `toolbox_whoami`, the four `e2e_records_*` tools, `toolbox_commit` and `toolbox_commit_confirmed` |
| `e2e` | The above and `e2e_identity_get` |

**Writes.** Ask Claude to create a test record: it calls `e2e_records_create`, which prepares an intent and changes nothing, then `toolbox_commit`. Deleting calls `e2e_records_delete`, then `toolbox_commit_confirmed` with the preview's summary. The confirmed tool carries `anthropic/requiresUserInteraction: true`, and Claude Code 2.1.282's source asks whenever a tool has it, whatever the allow rules say. Seeing that prompt in a session: Not yet tested; [Host lane](/docs/mcp/local-testing#host-lane) has the steps.

**Changes.** An entitlement changed in ID reaches your token within 60 seconds, without signing in again. The tool list follows when Claude Code lists tools again.

### Register the Toolbox and Claude Code

Set `ID` to the ID origin, `TOKEN` to a [staff token](/docs/id/onboard#get-a-staff-token) and `TOOLBOX` to `http://localhost:47400`. Each write sends its own `Idempotency-Key`, so a lost answer can be retried.

1. **Register and start the Toolbox**, as [Run it locally](/docs/toolbox#run-it-locally) shows: its resource, its machine client and a staff client in ID, the machine client's ID and secret in the root `.env`, then `bun run toolbox:dev`.

2. **Register Claude Code as a host client.** It is a public client, so PKCE protects the code; the redirect URI must match `--callback-port` exactly.

   ```bash
   curl "$ID/api/admin/v1/clients" \
     -H "Idempotency-Key: claude-code-toolbox-v1" -H "Authorization: Bearer $TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"clientId":"claude-code-toolbox","name":"Claude Code (Toolbox)","tokenEndpointAuthMethod":"none","grantTypes":["authorization_code","refresh_token"],"redirectUris":["http://localhost:47700/callback"],"scopes":["openid","offline_access","toolbox"]}'
   ```

3. **Enable your organisation.** One call links the client to the Toolbox and makes the capabilities and entitlements ID needs to issue its token to the organisation. Get `TOOLBOX_TOKEN` and `ORG` as [Enable an organisation](/docs/toolbox/admin#enable-an-organisation) does.

   ```bash
   curl "$TOOLBOX/admin/v1/organisations/$ORG/enable" \
     -H "Authorization: Bearer $TOOLBOX_TOKEN" -H "Content-Type: application/json" \
     -d '{"hostClientIds":["claude-code-toolbox"],"providers":["e2e"]}'
   ```

4. **Entitle people.** What each person may use is an entitlement to the Toolbox resource whose scopes are grant strings:

   ```bash
   curl "$ID/api/admin/v1/organizations/$ORG/entitlements" \
     -H "Idempotency-Key: e2e-organisation-v1" -H "Authorization: Bearer $TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"resource":"'"$TOOLBOX"'/mcp","scopes":["e2e"]}'
   ```

[Grant strings for people](/docs/toolbox/admin#grant-strings-for-people) covers a group or one member, and [Grant strings](/docs/toolbox#grant-strings) what each covers. Then run the `claude mcp add` line at the top of this page.

## The e2e server

```bash
claude mcp add --transport http answerable-e2e http://localhost:47510/e2e/mcp \
  --client-id claude-code-local --callback-port 47700
```

e2e runs on [the standalone server](/docs/mcp/servers#the-standalone-server), at its own path. `bun mcp dev e2e` registers everything below, with the client `claude-code-e2e`, and prints its own command; the steps are what it does, by hand. Run this once the resource and client below are registered. Then open Claude Code, run `/mcp`, select `answerable-e2e` and choose **Authenticate**. Ask Claude to call `identity_get`; it returns your organisation.

**Writes.** Ask Claude to create a test record: it calls `records_create`, which prepares an intent and changes nothing, then `e2e_commit`. Deleting calls `records_delete`, then `e2e_commit_confirmed` with the preview's summary. See [mutations](/docs/mcp/mutations).

### Register the server

Set `ID` to the ID origin, `TOKEN` to a [staff token](/docs/id/onboard#get-a-staff-token) and `ORG` to the organisation that will use the server. Each write sends its own `Idempotency-Key`, so a lost answer can be retried.

```bash
export ID=http://localhost:47300
export MCP=http://localhost:47510/e2e/mcp
export MCP_PATH=http%3A%2F%2Flocalhost%3A47510%2Fe2e%2Fmcp

curl "$ID/api/admin/v1/resources" \
  -H "Idempotency-Key: e2e-resource-v1" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"classification":"platform_shared","organizationId":null,"identifier":"'"$MCP"'","name":"E2E MCP","allowedScopes":["e2e:identity","e2e:read","e2e:write","offline_access"],"accessTokenTtl":900}'
```

**Resource.** The URL is the token audience. It must be `STANDALONE_ORIGIN` and the MCP's path exactly: `localhost` and `127.0.0.1` are different resources.

**Lifetime.** Claude Code refreshes an access token that is close to expiry before using it. With a 300-second lifetime it refreshed before every request; with 900 seconds it did not. A shorter lifetime ends access sooner after a revocation, at the cost of those refreshes.

### Register Claude Code as a client

```bash
curl "$ID/api/admin/v1/clients" \
  -H "Idempotency-Key: claude-code-local-v1" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"clientId":"claude-code-local","name":"Claude Code (local)","tokenEndpointAuthMethod":"none","grantTypes":["authorization_code","refresh_token"],"redirectUris":["http://localhost:47700/callback"],"scopes":["openid","offline_access","e2e:identity","e2e:read","e2e:write"]}'

curl -X PUT "$ID/api/admin/v1/clients/claude-code-local/resources/$MCP_PATH" \
  -H "Idempotency-Key: claude-code-local-link-v1" -H "Authorization: Bearer $TOKEN"
```

**Public client.** Claude Code runs on your machine, so it has no secret; PKCE protects the code. The redirect URI must match `--callback-port` exactly.

### Grant the organisation access

```bash
for grant in authorization_code refresh_token; do
  curl "$ID/api/admin/v1/organizations/$ORG/capabilities" \
    -H "Idempotency-Key: claude-login-$grant-v1" -H "Authorization: Bearer $TOKEN" \
    -H "Content-Type: application/json" \
    -d '{"clientId":"claude-code-local","resource":null,"grantKind":"'"$grant"'","scopes":["openid","offline_access"]}'
  curl "$ID/api/admin/v1/organizations/$ORG/capabilities" \
    -H "Idempotency-Key: claude-e2e-$grant-v1" -H "Authorization: Bearer $TOKEN" \
    -H "Content-Type: application/json" \
    -d '{"clientId":"claude-code-local","resource":"'"$MCP"'","grantKind":"'"$grant"'","scopes":["e2e:identity","e2e:read","e2e:write"]}'
done

curl "$ID/api/admin/v1/organizations/$ORG/entitlements" \
  -H "Idempotency-Key: claude-login-entitlement-v1" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"clientId":"claude-code-local","scopes":["openid","offline_access"]}'

curl "$ID/api/admin/v1/organizations/$ORG/entitlements" \
  -H "Idempotency-Key: claude-e2e-entitlement-v1" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"clientId":"claude-code-local","resource":"'"$MCP"'","scopes":["e2e:identity","e2e:read","e2e:write"]}'
```

**Every scope.** Claude Code asks for every scope the MCP lists. ID issues the ones the organisation is entitled to, and Claude Code sees only the tools they cover: without `e2e:write`, the three read tools and no commit tools. See [capabilities and entitlements](/docs/id/onboard#grant-access).

**Registered before writes existed?** Add `e2e:write` with `PATCH` to the resource's `allowedScopes`, the client's `scopes`, and the `scopes` of each capability and entitlement above, each call with its own `Idempotency-Key`. See [manage](/docs/id/manage).

### Register the server's machine client

The standalone server reads who is calling, their name, email and groups and their organisation's name, from ID's admin API, through a machine client of the platform organisation with `platform:read`, `standalone-hub` ([Who is calling](/docs/mcp/servers#who-is-calling)). Register it once, for every MCP it serves. Set `PLATFORM_ORG` to the platform organisation's id. The first call answers `clientSecret` once.

```bash
export PLATFORM_ORG=...   # the platform organisation's id
export ID_ADMIN_PATH=http%3A%2F%2Flocalhost%3A47300%2Fapi%2Fadmin

curl "$ID/api/admin/v1/clients" \
  -H "Idempotency-Key: standalone-hub-v1" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"clientId":"standalone-hub","name":"Standalone server","organizationId":"'"$PLATFORM_ORG"'","tokenEndpointAuthMethod":"client_secret_basic","grantTypes":["client_credentials"],"clientCredentialsScopes":["platform:read"]}'

curl -X PUT "$ID/api/admin/v1/clients/standalone-hub/resources/$ID_ADMIN_PATH" \
  -H "Idempotency-Key: standalone-hub-link-v1" -H "Authorization: Bearer $TOKEN"
curl "$ID/api/admin/v1/organizations/$PLATFORM_ORG/capabilities" \
  -H "Idempotency-Key: standalone-hub-capability-v1" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"clientId":"standalone-hub","resource":"'"$ID"'/api/admin","grantKind":"client_credentials","scopes":["platform:read"]}'
```

Put the client's id and secret in the root `.env`: `STANDALONE_ID_CLIENT_ID=standalone-hub` and `STANDALONE_ID_CLIENT_SECRET`. Without them the standalone server does not start.

### Start the server

```bash
bun mcp db e2e migrate
bun --filter @answerable/mcp-standalone db:migrate
bun run standalone:dev
```

The first two make e2e's schema in the shared database `answerable_mcps` and the standalone server's own database, `answerable_standalone`, on the development Postgres; run them again after a migration changes. The last reads the root `.env` and serves every standalone MCP at its path, e2e at `http://localhost:47510/e2e/mcp`; the issuer, the origin, the databases and ID's admin API default to the local ones.

## The admin MCP

```bash
claude mcp add --transport http answerable-admin http://localhost:47520/mcp \
  --client-id claude-code-admin --callback-port 47700
```

For Answerable staff: [the admin MCP](/docs/admin) onboards and manages organisations from Claude Code, each tool behind a role read live from ID. Register it with the cURL in [Set up the admin MCP](/docs/admin/setup), or try it on your machine with the lane that registers everything for you: `bun packages/acceptance/scripts/admin-lane.ts`, described in [Try it locally](/docs/admin/setup#try-it-locally). It uses the callback port `47700`, so the Toolbox in the same session needs another, such as `--callback-port 47701`.

## Other hosts

**Claude.ai and Claude Desktop connectors.** They connect from Anthropic's servers, so they cannot reach `localhost`. Register `https://claude.ai/api/mcp/auth_callback` as the redirect URI and enter the client ID under the connector's advanced settings once the server has a public URL: Not yet tested.

**Automatic registration.** Claude Code and Claude.ai can register themselves when an authorisation server supports dynamic registration or client ID metadata documents. ID supports neither: Not yet.

## Errors

| Error | Meaning | What to do |
| --- | --- | --- |
| "Access is unavailable for this organisation" | The organisation lacks a login capability or entitlement for the client, or a capability or entitlement for the server (a partial entitlement is fine: ID issues the entitled subset) | The Toolbox: run the enable call for the organisation. The e2e server: grant the capabilities and an entitlement above |
| `invalid_redirect` | The callback port differs from the registered redirect URI | Use `--callback-port 47700`, or register the port you use |
| `invalid_target` | The resource is unknown, not linked to the client, or written differently | Use the exact registered URL and link it; the enable call links the Toolbox's host client |
| `invalid_client` | The client ID is unknown or disabled | Check `claude mcp get answerable-toolbox` (or `answerable-e2e`) against the registration |
| `claude mcp login`: `stdin isn't a terminal, so authentication can't be completed here` | It needs a terminal to read the redirect | Run it in an interactive terminal (`ssh -t` for a remote machine) |
| `401` after signing in | The server's issuer or resource differs from ID's | Set `TOOLBOX_ID_ISSUER` and `TOOLBOX_RESOURCE_URL`, or `STANDALONE_ID_ISSUER` and `STANDALONE_ORIGIN`, to ID's origin and the registered URL's |
| `Invalid standalone server configuration: STANDALONE_ID_CLIENT_ID: …` at start | The standalone server has no machine client to read who is calling | [Register it](#register-the-servers-machine-client) and set `STANDALONE_ID_CLIENT_ID` and `STANDALONE_ID_CLIENT_SECRET` in the root `.env` |
| `The standalone server cannot start: Database role answerable_mcps_standalone may not serve MCPs: is not a member of mcp_e2e…` | The MCP's schema and roles are not made in your local `answerable_mcps` | `bun mcp db e2e migrate`, for each MCP the message names |
| A tool call answers `UPSTREAM_UNAVAILABLE`, `Who you are could not be read…` | ID refused the server's machine client, or did not answer | Check `STANDALONE_ID_CLIENT_ID`, `STANDALONE_ID_CLIENT_SECRET` and the client's `platform:read` capability on ID's admin API; the server log says what ID answered |
| `Tool <name> not found`, and `toolbox_whoami` lists no grants or too few | The Toolbox: no grant string covers the tool, its provider is not enabled for your organisation, or the token lacks `toolbox`. The e2e server: the token lacks the scope, for example `e2e:write` for `records_create` | The Toolbox: ask for an entitlement, [entitle people](#the-toolbox). The e2e server: add the scope as above, then choose **Authenticate** again |
| A commit tool answers an error | The intent cannot be committed as it is | See [MCP errors](/docs/mcp/errors) |

Toolbox errors are in [The Toolbox](/docs/toolbox#errors) and [Administer the Toolbox](/docs/toolbox/admin#errors).
