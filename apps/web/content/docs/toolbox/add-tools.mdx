---

```json title="mcps/acme/mcp.json"
{ "name": "acme", "serve": "toolbox", "database": "shared" }
```

The Toolbox serves tools from **MCPs** mounted inside it: every MCP whose `mcp.json` says `"serve": "toolbox"` or `"both"`. To add tools, make an MCP with `bun mcp new acme --serve toolbox`, let the Toolbox mount it, then let organisations use it: staff **enable** it in an organisation's catalogue, and **grant** its capabilities to people. On your machine `bun mcp dev acme` does all of this for you ([Make an MCP](/docs/mcp/create#run-it-and-try-it-in-claude-code)), and in staging and production a tag mounts it ([Ship an MCP](/docs/mcp/deploy)). The steps below do it by hand, against your local Toolbox, and were run end to end against real Answerable ID with `mcps/example` in place of `acme`.

**Before you start.** An MCP that passes `bun mcp check`, such as the one [Make an MCP](/docs/mcp/create) ends with, and the Toolbox [running locally](/docs/toolbox#run-it-locally) with its registrations in ID. Handing this to a coding agent? Use the [prompts](/docs/agents#make-an-mcp).

<Steps>
<Step>

### Check the names fit

Through the Toolbox each tool is named `<provider id>_<wire name>`, such as `acme_notes_list`, at most 46 characters. `defineProvider` and `defineTool` keep every name within it: an id has at most 12 characters and a tool name at most 33. The provider's id must differ from every provider the Toolbox mounts, and from `toolbox`.

</Step>
<Step>

### Say where it runs

`bun mcp new acme --serve toolbox` writes `"serve": "toolbox"` in `mcps/acme/mcp.json`, as at the top of this page; `both` also serves it on its own URL. For an MCP that runs elsewhere, change `serve` there, then:

```sh
bun mcp check acme
bun install
```

`check` rewrites the Toolbox's generated list and its dependencies, as `bun mcp new` does; commit both with the MCP. Never edit them by hand.

<include lang="ts" meta='title="mcps/toolbox/src/mounted.generated.ts"'>../../../../../mcps/toolbox/src/mounted.generated.ts</include>

The Toolbox mounts each MCP of the list with its database: its schema in the shared database `answerable_mcps`, which the Toolbox reaches as its serving login, `answerable_mcps_toolbox`, granted the MCP's schema and tables, or the MCP's own database, from the variable the list names.

</Step>
<Step>

### Make its schema locally

```sh
bun mcp db acme migrate
```

It makes the MCP's schema in your local `answerable_mcps` and migrates it, and grants the Toolbox's serving login the schema and its tables. `bun mcp new` ran it once; run it again after `bun mcp db acme generate` writes a migration. In staging and production the deployment does it.

</Step>
<Step>

### Restart the Toolbox

```sh
bun run toolbox:dev
```

At boot the Toolbox checks that its serving login has `USAGE` on the schema of every mounted MCP, and nothing more than provisioning gave it, then reads every provider's manifest into its catalogue. `GET /health` lists the mounted MCPs in `providers`. Staff see the new provider and its capabilities in the admin API:

```sh
curl "$TOOLBOX/admin/v1/providers" -H "Authorization: Bearer $TOOLBOX_TOKEN"
```

`TOOLBOX_TOKEN` is a staff token for the Toolbox's admin API: [Enable an organisation](/docs/toolbox/admin#enable-an-organisation) shows how to get one.

</Step>
<Step>

### Enable it for an organisation

In staging and production, staff run `toolbox_enable` in [the admin MCP](/docs/admin); this call is what it makes, and what you run against your local Toolbox.

```sh
curl "$TOOLBOX/admin/v1/organisations/$ORG/enable" \
  -H "Authorization: Bearer $TOOLBOX_TOKEN" -H "Content-Type: application/json" \
  -d '{"hostClientIds":["claude-code-toolbox"],"providers":["acme"]}'
```

The catalogue is the ceiling: an organisation uses only the providers enabled for it. This call enables `acme` for the organisation, and widens the Toolbox's resource in Answerable ID to accept `acme`'s grant strings. Run it again for every organisation that should have the provider, including those enabled before it existed. [What the call does](/docs/toolbox/admin#what-the-call-does) lists every step.

</Step>
<Step>

### Grant it to people

In staging and production, staff run `access_grant` in the admin MCP ([Your MCP's sign-in](/docs/mcp/sign-in#what-staff-do-for-each-organisation)). By hand:

What each person may use is an entitlement in Answerable ID whose scopes are **grant strings**: the provider, a domain or one capability. For `mcps/example`, read from its manifest:

<GrantStrings workspace="example" />

Everyone in the organisation, every capability of the provider:

```sh
curl "$ID/api/admin/v1/organizations/$ORG/entitlements" \
  -H "Idempotency-Key: acme-organisation-v1" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"resource":"'"$TOOLBOX"'/mcp","scopes":["acme"]}'
```

`TOKEN` is a [staff token for ID](/docs/id/onboard#get-a-staff-token). A group or one member takes `groupId` or `memberId`: [Grant strings for people](/docs/toolbox/admin#grant-strings-for-people). A change reaches the person within 60 seconds, without signing in again.

</Step>
<Step>

### Try it

In Claude Code, connected to the Toolbox as [Connect Claude Code](/docs/mcp/claude-code#the-toolbox) shows, ask Claude to call `toolbox_whoami`: its `capabilities` now include `acme/notes.add` and `acme/notes.list`. With `mcps/example` mounted and the grant string `example`, before `bun mcp` remade it with a database and `example.status`, the Toolbox listed exactly:

```text
toolbox_whoami, example_notes_add, example_notes_list, toolbox_commit, toolbox_commit_confirmed
```

Ask Claude to add a note: it calls `acme_notes_add`, which returns an intent whose `commit_tool` is `toolbox_commit`, then commits it.

</Step>
</Steps>

## What changes inside the Toolbox

The provider's code is the same; how hosts reach it changes.

| | Served alone | In the Toolbox |
| --- | --- | --- |
| Tool name | `notes_list` | `acme_notes_list` |
| Commit tools | `acme_commit`, `acme_commit_confirmed` | `toolbox_commit`, `toolbox_commit_confirmed` |
| Who sees a tool | A token carrying its scopes, `acme:read` or `acme:write` | A person whose grant strings cover it, in an organisation that enabled the provider. The token carries only `toolbox` |
| `principal.scopes` in a handler | The provider's scopes | `toolbox` and `offline_access`: never decide access from provider scopes in a handler |
| Policy class of a mutation | From its `risk` | The organisation's override in the catalogue, else its `risk` |
| Prompts and resources | Served | Not served. Views are |
| Result size | Unbounded | A read above 100 KiB of JSON answers `RESULT_TOO_LARGE` |
| Finding a tool | By name | Also by `toolbox_search` in the meta projection, which searches identities, titles, descriptions and argument names: write [operational descriptions](/docs/mcp/tools#descriptions) |
| Every call | Logged by your server | Also an evidence row and a span |

## Changing a provider later

**A new tool** is off for every organisation that already has the provider enabled, until staff enable it: it is added to their catalogue entry's `disabled` list when the Toolbox boots. [The catalogue](/docs/toolbox/admin#the-catalogue) shows how to turn it on.

**A changed contract** needs a new version. A capability stored at the same version with another kind, risk, input or output refuses the boot, naming it. Give the tool a new `version`, or change the provider's, and regenerate its manifest. Titles and descriptions update in place.

**Taking an MCP out of the Toolbox's hub,** by changing its `serve` to `standalone`, stops serving its tools there at the next boot; the Toolbox then serves it at its own path only. Entitlements in ID that name its grant strings stay, and cover nothing. Removing an MCP for good puts its name in `mcps/retired.json`: `bun mcp retire` is Not yet.

## Not yet

Remote providers: the Toolbox mounts MCPs in its own process, so adding one is a change to `mcp.json`, a deployment and a restart. Administration by an organisation's own administrators: staff enable providers and write entitlements. See [the Toolbox's limits](/docs/toolbox#limits).

## Errors

| You see | Meaning | What to do |
| --- | --- | --- |
| `Cannot find module '@answerable/mcp-acme/provider'` | The Toolbox's dependencies were rewritten and not installed, or the workspace has no `exports` entry | `bun install`; `bun mcp new` writes the `exports` entry |
| `The Toolbox cannot start: Database role answerable_mcps_toolbox may not serve MCPs: lacks USAGE on schema acme…` | The MCP's schema is not made in the shared database, or the serving login was not granted it | Locally, `bun mcp db acme migrate` |
| `mounted.generated.ts` or the Toolbox's `package.json` is stale in `bun mcp check` | `mcp.json` changed without the generated files | `bun mcp check acme` rewrites them: commit them |
| `Provider … is mounted twice…` at start | Two providers share an id, or a provider is the Toolbox's own | Rename the provider's id |
| `Capability <identity> version <date> changed its input without a new version…` at start | A contract changed under an old version | Give the tool or the provider a new version |
| `422 unknown_provider` from the enable call | The Toolbox does not mount that provider | Mount it and restart; `GET /providers` lists what is mounted |
| `Tool acme_notes_list not found` | The organisation has not enabled `acme`, no grant string covers the tool, or the tool is disabled in the catalogue | Run the enable call; add an entitlement; check `GET /organisations/{id}/catalogue` |
| The entitlement is refused with `Scopes are not allowed for this resource` | The Toolbox's resource does not accept `acme`'s grant strings yet | Run the enable call for `acme` first; it widens the resource |

The Toolbox's other errors are in [The Toolbox](/docs/toolbox#errors) and [Administer the Toolbox](/docs/toolbox/admin#errors).
