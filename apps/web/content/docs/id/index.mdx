```bash
curl http://localhost:47300/.well-known/openid-configuration
```

That is Answerable ID running locally, describing itself: where to sign in, where to get tokens and the keys that sign them. Answerable ID is the front door to every Answerable product. People sign in with the work account their organisation already has, in Microsoft Entra ID or Google Workspace. Apps and MCP servers never see a password: they receive a token from ID that says who the person is, which organisation they act for, and what they may do.

## The words

| Word | Meaning |
| --- | --- |
| **Organisation** | A company that uses Answerable. Its people sign in through its own directory. Answerable itself is one, the platform organisation |
| **User** | A person, with one global id, `sub`, across every organisation |
| **Member** | A user's place in one organisation, made the first time they sign in to it. A person in two organisations signs in to each separately |
| **Group** | A named set of members of one organisation |
| **Client** | An app that asks for tokens: Claude Code, LibreChat, a web app, a script. Registered in ID ahead of time. A client on a person's machine is public and has no secret |
| **Resource** | What a token is for, named by its URL: an MCP server, the Toolbox, ID's admin API. A token works at one resource only |
| **Scope** | One permission, written as a word such as `acme:read` or `toolbox` |
| **Capability** | The organisation's ceiling, set by Answerable staff: this client may be used with this resource and these scopes, in this organisation |
| **Entitlement** | Who inside the organisation gets which scopes: everyone, one group or one member |
| **Access token** | What a client sends to a resource: a signed JWT for that one resource, valid for the lifetime the resource sets, such as 15 minutes |
| **Refresh token** | Lets the client get a new access token without a new sign-in, for as long as the person may still have it |

**Two layers decide access.** A capability says a client may reach a resource in an organisation at all. An entitlement says which people there get which scopes. ID issues the scopes that were asked for, that the capability allows and that the person is entitled to, and drops the rest: the **entitled subset**. The consent page names what was dropped.

## How a person reaches an MCP server

```text
person ── host (Claude Code) ── 1. call ────────────▶ MCP server
                 ▲   ◀────────── 401: sign in at ID ───┘
                 │
          2–4. browser: Answerable ID ──▶ company directory (Entra ID, Google)
                 │         access token: who, which organisation, which scopes
                 ▼
               host ── 5. call with the token ──▶ MCP server checks it offline
```

1. **The host calls the server.** Without a token the server answers `401` and names Answerable ID as the place to sign in.
2. **ID signs the person in.** The host opens ID in the browser. The person gives their work email, and ID sends them to their company's directory, which checks the password and any second factor. ID then checks the account: a member, not a guest or a personal account, with a verified email on a domain the organisation has enabled.
3. **The person chooses and approves.** They choose the organisation to act for, and approve the client's access on a consent page that lists the scopes.
4. **ID issues the tokens.** An access token for that one server, carrying the entitled subset of scopes, and a refresh token.
5. **The server checks the token itself.** It verifies the signature with ID's published keys, the issuer, the audience (its own URL) and the expiry. It never calls ID on each request.
6. **Renewal.** When the access token expires, the host refreshes it. ID checks again that the person, membership, client and organisation are still allowed; a disabled organisation gets no new token.

An app that is not an MCP host follows the same OAuth flow with its own code: [Connect an application](/docs/id/oauth). [Sign in](/docs/id/sign-in) covers the directory step and every reason it can refuse.

## What a token says

An MCP server built with the kit receives the verified token as `principal`, in every handler:

| Claim | `principal` field | Meaning |
| --- | --- | --- |
| `sub` | `userId` | The person's global id |
| `organization_id` | `organizationId` | The organisation they chose for this token |
| `membership_id` | `membershipId` | Their membership in that organisation |
| `grant_id` | `grantId` | The authorisation; a refreshed token keeps it |
| `client_id` | `clientId` | The client that asked for the token |
| `scope` | `scopes` | The entitled subset of the scopes asked for |
| `exp` | `expiresAt` | Expiry, in seconds since the epoch |
| `organization_authorization_version` | `organizationAuthorizationVersion` | Advances when ID changes the organisation's authority, such as disabling it |
| `aud` | | The resource URL. A server refuses a token for any other |
| `subject_type` | | `user` for a person; a machine client's own token says `client` |

[Connect an application](/docs/id/oauth#exchange-the-code) lists every claim; [Read tools](/docs/mcp/tools#the-caller) shows `principal` in a handler.

## Rules to build on

- **`sub` is the only identifier to join on.** Email is display data: it can change, and a matching email proves nothing.
- **Scope every query by organisation.** A token is for one organisation. Another organisation's data is not found, never forbidden.
- **Tokens are checked offline**, so taking access away takes effect when the access token expires, while refresh stops at once. Keep resource token lifetimes short.
- **Hidden means refused.** A server lists only what the token allows, and answers anything else as if it did not exist.

## Machines

A script or a service can get a token for itself, with its client's id and secret and no person involved: the OAuth `client_credentials` grant. Its token says `subject_type: "client"`, and its scopes are the ones the client is allowed. The Toolbox reads grants from ID this way. See [machine access](/docs/id/sign-in#machine-access).

## Endpoints

Answerable ID has not yet been deployed to production. Locally it runs at `http://localhost:47300`; the other pages' examples use `https://id.answerable.org`, the address it will have.

| Endpoint | Purpose |
| --- | --- |
| `/.well-known/openid-configuration` | Discovery: endpoints, supported flows and the key set |
| `/auth` | Sign-in and session routes |
| `/auth/oauth2/authorize`, `/auth/oauth2/token` | Authorisation, code exchange, refresh and client credentials |
| `/auth/jwks` | The public keys that sign tokens |
| `/api/admin/v1` | [Admin API](/docs/id/admin-api) |
| `/healthz`, `/readyz` | Liveness and readiness |

Every public route is in the [API reference](/docs/id/api).
