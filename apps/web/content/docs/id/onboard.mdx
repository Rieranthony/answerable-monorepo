**Answerable staff.** This page is for us. It covers setting the service up for the first time, then creating and looking after client organisations. Organisation admins have their own page, [Manage your organisation](/docs/id/manage). The reads below are also tools of [the admin MCP](/docs/admin), for staff working in an AI host; [Set up the admin MCP](/docs/admin/setup) registers it in your ID. Every step is a `curl` command against the admin API; the [reference](/docs/id/admin-api) lists every field.

## Words used on this page

| Word             | Meaning                                                                                                                                      |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| **Organisation** | A company that uses Answerable. Answerable itself is one too, called the **platform organisation**. The service creates it by itself.        |
| **Member**       | A person's place in an organisation. It appears the first time they sign in, or when staff list their address first.                         |
| **Group**        | A named set of members inside an organisation. `platform-admins` is the group of Answerable staff.                                           |
| **Scope**        | One permission, written as a word such as `platform:read`. A session or token carries a list of them.                                        |
| **Resource**     | Something people and apps get tokens for, named by a URL. The admin API is one; MCP servers are the others.                                  |
| **Entitlement**  | A rule saying who may use which resource with which scopes. Members of `platform-admins` get every platform scope on the admin API this way. |
| **Client**       | An app or script that asks for tokens. It has a `clientId` and a secret.                                                                     |
| **Root secret**  | A one-off password for the first setup. It locks itself as soon as a person holds admin rights.                                              |

## First run

A new service has no accounts at all. You get in with the root secret, sign in with your work account, give that account admin rights, and the root secret locks itself. Seven steps.

Each write below sends a new `Idempotency-Key`. A key retries one attempt after a lost answer, and never repeats a step later: ID keeps its first answer for ever, so a step repeated under an old key does nothing.

**Before you start.** Make the secret and keep it somewhere safe for the next hour:

```bash
openssl rand -base64 48
```

**On your machine,** skip it: with `ROOT_ADMIN_SECRET` unset, a local ID uses its development value, `development-only-root-admin-secret-never-for-production`, committed in `apps/id/src/config.ts`. ID in production refuses to start with that value. Start the local ID as [Run an MCP on your machine](/docs/mcp/run-locally#before-you-start) shows, then go to step 2.

**Name the service once.** Every command below calls `$ID`, the service's origin:

```bash
ID=http://localhost:47300        # on your machine
# ID=https://id.answerable.org   # production; staging is https://id.answerable-staging.uk
```

1. **Start the service with the secret.** Set `ROOT_ADMIN_SECRET` to that value.

   Apply the migrations before starting the service; migration also provisions the restricted runtime database role (`DATABASE_RUNTIME_ROLE`, default `answerable_id_runtime`). On an empty database, startup creates and binds the platform organisation, the admin API resource and the `platform-admins` group. Repeated migration and startup preserve those IDs. The first start names the organisation `Answerable`, with the slug `answerable`. Rename it later through the admin API: a restart does not change it back. Production key delivery, capacity and recovery objectives remain release work.

   ```bash
   bun --filter @answerable/id db:migrate
   ```

   `Refusing to migrate: drizzle/<file>.sql is not the migration this database applied` means that file changed after this database applied it. Restore the applied file; before production, recreate the database instead.

   Give the runtime role login credentials through deployment tooling, then set the application's `DATABASE_URL` to that role. Keep `DATABASE_MIGRATION_URL` available only to migration.

2. **Write down two IDs.** The secret works as a bearer token. Ask the service for the platform organisation (slug `answerable`) and its `platform-admins` group; the next steps use both.

   ```bash
   export ROOT_ADMIN_SECRET="paste the secret here"   # on your machine: development-only-root-admin-secret-never-for-production

   PLATFORM_ORG=$(curl -s "$ID/api/admin/v1/organizations?q=answerable" \
     -H "Authorization: Bearer $ROOT_ADMIN_SECRET" | jq -r '.items[] | select(.slug=="answerable") | .id')
   PLATFORM_GROUP=$(curl -s "$ID/api/admin/v1/organizations/$PLATFORM_ORG/groups?q=platform-admins" \
     -H "Authorization: Bearer $ROOT_ADMIN_SECRET" | jq -r '.items[] | select(.slug=="platform-admins") | .id')
   ```

3. **Say which work accounts are staff.** The first says that emails on our domain belong to the platform organisation. The second says which directory checks those accounts: Google Workspace or Microsoft Entra, using Answerable’s platform application from the service environment. A third call checks that the directory answers.

   Set `STAFF_DOMAIN` (for example `answerable.org`) and `STAFF_ISSUER` (the directory's issuer URL from the [table below](#connect-the-directory)). Configure the matching `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` or `MICROSOFT_CLIENT_ID`/`MICROSOFT_CLIENT_SECRET` pair in the service environment first. They are the client ID and secret of an application registered in that directory, an app registration in Entra or an OAuth client in Google Cloud, whose redirect URI is `$ID/auth/sso/callback`. On your machine they go in the root `.env`, and ID reads them when it starts. Without a directory's credentials a local ID cannot sign anyone in: [the host lane](/docs/mcp/run-locally#signing-in-needs-a-company-directory) is the way to try a sign-in without them.

   ```bash
   curl "$ID/api/admin/v1/organizations/$PLATFORM_ORG/domains" \
     -H "Idempotency-Key: $(uuidgen)" \
     -H "Authorization: Bearer $ROOT_ADMIN_SECRET" \
     -H "Content-Type: application/json" \
     -d '{"domain":"'"$STAFF_DOMAIN"'"}'

   curl -X PUT "$ID/api/admin/v1/organizations/$PLATFORM_ORG/sso-provider" \
     -H "Idempotency-Key: $(uuidgen)" \
     -H "If-None-Match: *" \
     -H "Authorization: Bearer $ROOT_ADMIN_SECRET" \
     -H "Content-Type: application/json" \
     -d '{"issuer":"'"$STAFF_ISSUER"'","domain":"'"$STAFF_DOMAIN"'"}'

   curl "$ID/api/admin/v1/organizations/$PLATFORM_ORG/sso-provider/test" \
     -H "Authorization: Bearer $ROOT_ADMIN_SECRET"
   ```

   An empty `problems` list means the directory is reachable. The test cannot check the credentials themselves; the next step does that.

4. **Sign in.** Open `$ID/login` in your browser, such as `http://localhost:47300/login`, and sign in with your work account. This creates your user and your membership of the platform organisation. You have no admin rights yet.

5. **Give yourself admin rights.** Find your member record by email, copy its `id` into `STAFF_MEMBER`, then add it to the `platform-admins` group. The group already carries every platform scope, so joining it is all it takes.

   ```bash
   curl --get "$ID/api/admin/v1/organizations/$PLATFORM_ORG/members" \
     -H "Authorization: Bearer $ROOT_ADMIN_SECRET" \
     --data-urlencode "email=you@answerable.org"

   curl -X PUT "$ID/api/admin/v1/organizations/$PLATFORM_ORG/groups/$PLATFORM_GROUP/members/$STAFF_MEMBER" \
     -H "Idempotency-Key: $(uuidgen)" \
     -H "If-None-Match: *" \
     -H "Authorization: Bearer $ROOT_ADMIN_SECRET" \
     -H "Content-Type: application/json" \
     -d '{}'
   ```

6. **Check it worked.** In your browser's developer tools, copy the `Cookie` header from any request to `$ID` into `SESSION_COOKIE`. Then ask the service who you are:

   ```bash
   curl "$ID/api/admin/v1/me" \
     -H "Cookie: $SESSION_COOKIE"
   ```

   The answer lists `platform:read`, `platform:users` and `platform:write` among your scopes. Now repeat the summary call from step 2 with the root secret: it is refused with `403 root_locked`. That is the point. A person holds `platform:write`, so the secret has locked itself.

7. **Put the secret away.** Remove `ROOT_ADMIN_SECRET` from the deployment, or keep it in your secret store with `ROOT_ADMIN_BREAK_GLASS=false`. If one day no staff member can administer the service, deploy with the secret and `ROOT_ADMIN_BREAK_GLASS=true`, repair access, then turn it off again. Every use of the secret, allowed or refused, is written to the audit log as `admin.root_request`.

**The next staff member.** They sign in once (step 4). You repeat step 5 for them with your own browser session instead of the root secret, adding `-H "Origin: $ID"` because writes from a browser session must name the site they come from. Nothing else is needed.

## Get a staff token

Your browser session is enough for commands you type by hand. For scripts and agents, create a client owned by the platform organisation, allow it to use the admin API, and swap its secret for a token.

Set `MACHINE_LINK_KEY` and `MACHINE_CAPABILITY_KEY` once for their separate commands. A human cookie requires [fresh authentication](/docs/id/manage#fresh-authentication). Send client creation with an `Idempotency-Key`: without one, a resend creates a second client. Use a distinct key for each intended registration, and reuse it after a lost response. A retry returns the receipt; a lost secret requires another rotation with a new key; see [retries and receipts](/docs/id/manage#retries-and-receipts).

```bash
curl https://id.answerable.org/api/admin/v1/clients \
  -H "Idempotency-Key: staff-automation-v1" \
  -H "Cookie: $SESSION_COOKIE" \
  -H "Origin: https://id.answerable.org" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Staff automation",
    "organizationId": "'"$PLATFORM_ORG"'",
    "tokenEndpointAuthMethod": "client_secret_basic",
    "grantTypes": ["client_credentials"],
    "redirectUris": [],
    "clientCredentialsScopes": ["platform:read", "platform:users", "platform:write"]
  }'

# Save clientId as CLIENT_ID and the returned clientSecret as CLIENT_SECRET.
curl -X PUT "https://id.answerable.org/api/admin/v1/clients/$CLIENT_ID/resources/https%3A%2F%2Fid.answerable.org%2Fapi%2Fadmin" \
  -H "Idempotency-Key: $MACHINE_LINK_KEY" \
  -H "Cookie: $SESSION_COOKIE" \
  -H "Origin: https://id.answerable.org"

# Approve the machine ceiling separately from registration and linking.
curl "https://id.answerable.org/api/admin/v1/organizations/$PLATFORM_ORG/capabilities" \
  -H "Idempotency-Key: $MACHINE_CAPABILITY_KEY" \
  -H "Cookie: $SESSION_COOKIE" \
  -H "Origin: https://id.answerable.org" \
  -H "Content-Type: application/json" \
  -d '{"clientId":"'"$CLIENT_ID"'","resource":"https://id.answerable.org/api/admin","grantKind":"client_credentials","scopes":["platform:read","platform:users","platform:write"]}'

curl https://id.answerable.org/auth/oauth2/token \
  --user "$CLIENT_ID:$CLIENT_SECRET" \
  --data-urlencode 'grant_type=client_credentials' \
  --data-urlencode 'resource=https://id.answerable.org/api/admin' \
  --data-urlencode 'scope=platform:read platform:users platform:write'
```

**The secret is shown once.** Save `clientSecret` when the first call returns it; it cannot be read back. Use `clientId`, not the record's `id`, in client URLs. The token call returns `access_token`; set `TOKEN` to it. Every command below uses `TOKEN`, but your browser cookie plus the `Origin` header works just as well.

**Why the platform organisation.** A client acts for the organisation that owns it. Only a client owned by the platform organisation gets platform scopes; one owned by a client organisation only ever acts for that organisation, whatever scopes it lists.

## Why can't someone sign in

```bash
curl --get "https://id.answerable.org/api/admin/v1/organizations/$ORG/sign-in-diagnosis" \
  -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "email=$EMAIL"
```

[diagnoseSignIn](/docs/id/admin-api/diagnostics/diagnoseSignIn) checks this tenant's configuration and memberships without changing state. `verdict.checked` lists the local checks evaluated in order; `verdict.code` is the first applicable result. It rechecks current `org:users` or staff `platform:read` authority inside its transaction and returns `Cache-Control: no-store`.

| Verdict                   | Meaning                                                  | What to do                                                |
| ------------------------- | -------------------------------------------------------- | --------------------------------------------------------- |
| `provider_not_found`      | The organisation has no directory and links are off.     | Configure the provider, or turn links on.                 |
| `organization_disabled`   | Organisation is disabled.                                | Review whether to enable it.                              |
| `domain_not_allowed`      | Email domain does not route here.                        | Check this tenant's active domain assignment.             |
| `user_disabled`           | The user linked to this tenant's membership is disabled. | Ask platform staff to review the account.                 |
| `membership_revoked`      | This tenant's membership was revoked.                    | Review whether to reinstate it.                           |
| `magic_link_not_listed`   | Links are the way in, the firm admits its listed members only, and this address is no effective member here. | List the person, or see [who may ask](/docs/id/magic-links#who-may-ask). |
| `magic_link_address_limit` | Links are the way in and this address has had 50 mails in the last day. | Wait: the count falls as the oldest passes a day. [Not yet](/docs/id/magic-links#not-yet) can staff clear it. |
| `magic_link_suppressed`   | Links are the way in and Postmark refused the last send to this address as suppressed (406). | Staff reactivate the address in Postmark: [deliverability](/docs/id/magic-links#deliverability). |
| `authentication_required` | Local checks found no blocker.                           | Complete a real IdP authentication, or a link's confirmation, to establish identity. |

**Links in the answer.** `magicLink` has `enabled`, `admission`, `suppressed`, `requestsInLastDay`, `dailyLimit`, `lastRequest` (the newest sign-in mail to this exact address, kept seven days, with Postmark's code) and `directoryConnection`: a directory sign-in this address has made and not yet connected, waiting on the code mailed to it. A `sendStatus` of `sent` means no failure has been recorded: whether the mail arrived is in that server's Activity in Postmark. In the admin MCP this answer is [`signin_diagnose`](/docs/admin#why-did-someone-get-no-mail).

**It reads this tenant alone.** A person who holds another firm's directory account is refused a link, and this answer cannot say so. In `domain` mode `magic_link_not_listed` does not apply.

**Tenant visibility.** `user` and `membership` are null unless this tenant has a membership for the exact email. A null user does not mean the email is globally unused. Routing names only this organisation, never another tenant. Account issuers, directory IDs and retired-email state are excluded for all callers, including staff. Platform-wide user inspection remains a separate permission-controlled API.

**A real IdP authentication is required** to establish identity and evaluate `directory_mismatch`, `guest_account`, `personal_account`, `hosted_domain_mismatch`, `email_unverified`, `identity_conflict` and `email_conflict`, listed in `verdict.requiresToken`. This diagnosis does not predict account creation or successful sign-in. A non-effective membership does not prevent sign-in, but stops grants. See [sign-in checks](/docs/id/sign-in#what-is-checked).

**Contract change.** The diagnostic response no longer includes `accounts` or `user.retiredEmail`. `authentication_required` replaces `new_user_would_be_created` and `would_sign_in`; `identity_conflict` is deferred to real authentication. Update diagnostic consumers before releasing this API change.

## Test an SSO configuration

```bash
curl "https://id.answerable.org/api/admin/v1/organizations/$ORG/sso-provider/test" \
  -H "Authorization: Bearer $TOKEN"
```

[testSsoProvider](/docs/id/admin-api/diagnostics/testSsoProvider) runs discovery as sign-in runs it, then fetches JWKS, without sending credentials or changing state. It reports reachability, exact issuer equality, as at sign-in, key count and elapsed time, and stops at the first problem, as sign-in does. It requires current `platform:read` when reading the endpoint configuration and returns `Cache-Control: no-store`. Network requests run after that read transaction closes, so the result describes the captured endpoints even if configuration changes during the probe. It does not prove client credentials, consent, a usable signing key or a person's ability to sign in; complete a real sign-in for those checks.

| Problem code            | Meaning                                                                                                | What to do                                                                                          |
| ----------------------- | ------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| `insecure_issuer`       | The issuer or discovery URL is not an absolute HTTP or HTTPS URL.                                      | Correct the configured URLs.                                                                        |
| `discovery_unreachable` | Discovery failed, timed out or returned a non-success status; redirects are refused.                   | Check the discovery URL and connectivity.                                                           |
| `discovery_invalid`     | Discovery JSON is missing required URLs.                                                               | Correct the provider's discovery document.                                                          |
| `untrusted_origin`      | The discovery URL's origin, or a discovered endpoint's, is missing from `BETTER_AUTH_TRUSTED_ORIGINS`. | Ask Answerable staff to add its exact trusted origin and check outbound HTTPS, then rerun the test. |
| `issuer_mismatch`       | Discovery issuer differs from the configured issuer.                                                   | Use the exact tenant issuer.                                                                        |
| `jwks_unreachable`      | JWKS failed, timed out or returned a non-success status; redirects are refused.                        | Check the discovery document's JWKS URL and connectivity.                                           |
| `jwks_invalid`          | JWKS is not a JSON array of keys.                                                                      | Correct the provider's key document.                                                                |

No provider returns HTTP `404 provider_not_found`; configure it first. Other failed checks appear in `problems` on a successful HTTP response.

## Create the organisation

```bash
curl https://id.answerable.org/api/admin/v1/organizations \
  -H "Idempotency-Key: $ORGANISATION_CREATE_KEY" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"slug":"contoso","name":"Contoso"}'
```

**Retry key.** Set `ORGANISATION_CREATE_KEY` once for this intended creation and reuse it with identical input after a lost response. All organisation mutations accept keys; retries return receipts. PATCH also accepts the optional strong If-Match ETag from getOrganization; see [retries and receipts](/docs/id/manage#retries-and-receipts).

**Slug.** Lowercase labels joined by single hyphens, the same grammar as the Omni-Weaver tenant id. It cannot change later. Set `ORG` to the returned `id`.

## Route its email domains

```bash
curl "https://id.answerable.org/api/admin/v1/organizations/$ORG/domains" \
  -H "Idempotency-Key: $DOMAIN_OPERATION_KEY" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"domain":"contoso.com"}'
```

**One owner.** A domain routes to at most one active organisation. To move it, disable or delete the old row first, then add the new one. Sign-in with an email outside the organisation's active domains is refused.

**Where the person goes next.** The address's domain finds the organisation, and the organisation decides what the person sees: its directory if it has only that, a page asking for a link if it has only links, and a choice page, **Continue with Microsoft** (or Google, or company sign-in) beside **Email me a sign-in link**, if it has both. A new organisation's [sign-in by email link](/docs/id/magic-links) is off, so routing a domain to it lets nobody ask for a link until [staff turn links on](#turn-on-sign-in-by-link).

**Prove the domain.** The answer carries a `verificationRecord`: a TXT record at `_answerable-challenge.<domain>`. Publish it, then call [verifyOrganizationDomain](/docs/id/admin-api/domains/verifyOrganizationDomain). A proof is what lets a firm open links to anyone at the domain ([who may ask](/docs/id/magic-links#who-may-ask)); nothing else depends on it, and nothing re-checks it on a schedule: [Not yet.](/docs/id/magic-links#not-yet)

```bash
curl -X DELETE "https://id.answerable.org/api/admin/v1/organizations/$ORG/domains/$DOMAIN" \
  -H "Idempotency-Key: $DOMAIN_DELETE_KEY" \
  -H "Authorization: Bearer $TOKEN"
```

**Domain operation keys.** Set `DOMAIN_OPERATION_KEY` and `DOMAIN_DELETE_KEY` to different stable keys for the two logical commands. Reuse each key with identical input when retrying; retries return receipts. The root setup example also uses a stable key. Repeated enable/disable under a new key records a no-op; changed input under an existing key conflicts.

**Delete an assignment.** Set `DOMAIN` to its domain row ID. [deleteOrganizationDomain](/docs/id/admin-api/domains/deleteOrganizationDomain) removes sign-in routing and records `domain.deleted`. No `confirm` is required; disable the assignment for a reversible suspension. Removing or disabling a domain also ends the link sessions and grants of that domain's addresses, and leaves the rest of the organisation signed in.

## Connect the directory

```bash
curl -X PUT "https://id.answerable.org/api/admin/v1/organizations/$ORG/sso-provider" \
  -H "Idempotency-Key: $SSO_OPERATION_KEY" \
  -H "If-None-Match: *" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "issuer": "https://login.microsoftonline.com/00000000-0000-0000-0000-000000000000/v2.0",
    "domain": "contoso.com"
  }'
```

**Platform credentials are the default.** Omit `oidc`, as above, or send `oidc: {"credentials":"platform"}`. Google and Entra use Answerable's single application for that directory. Staff configure its client ID and secret together in the service environment; the row stores no secret. Every provider returns to `https://id.answerable.org/auth/sso/callback` (local: `http://localhost:47300/auth/sso/callback`).

| Directory        | `issuer`                                                | What is pinned                                        | What the organisation's IT does                                                                          |
| ---------------- | ------------------------------------------------------- | ----------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Microsoft Entra  | `https://login.microsoftonline.com/<directory-id>/v2.0` | The directory ID; guests and other directories refuse | Use the admin consent link below, or an admin signs in first and grants organisation-wide consent.       |
| Google Workspace | `https://accounts.google.com`                           | The hosted domain; personal accounts refuse           | If third-party apps are restricted, mark Answerable's client ID Trusted in Workspace App access control. |
| Generic OIDC     | The directory's exact issuer URL                        | Issuer and verified email/domain                      | Register the callback URL and send own client credentials to Answerable staff.                           |

**Entra consent.** Send IT `https://login.microsoftonline.com/<tenant-id>/v2.0/adminconsent?client_id=<MICROSOFT_CLIENT_ID>&scope=openid%20profile%20email&redirect_uri=https%3A%2F%2Fid.answerable.org%2Flogin&state=<slug>`. It returns `admin_consent=True&tenant=<GUID>`. Alternatively, a Global Administrator signs in first and ticks **consent on behalf of your organisation** (only Privileged Role Administrators see it). Default tenant policy blocks ordinary users from consenting to unverified multi-tenant apps.

```bash
curl -s "https://login.microsoftonline.com/$CUSTOMER_DOMAIN/v2.0/.well-known/openid-configuration" | jq -r .issuer
```

**Find the Entra tenant ID.** Set `CUSTOMER_DOMAIN` to the customer's domain. The returned issuer contains its tenant GUID; use that complete tenant-specific issuer in the PUT.

**Google app access.** The default Workspace policy allows third-party apps. If restricted, IT uses **Security → Access and data control → API controls → Manage App Access → Configure new app**, finds the client ID and marks it **Trusted**. The `hd` request parameter is only a hint; Answerable ID verifies the ID-token claim.

**Own credentials are the exception.** Use this body for a separate Entra registration; generic OIDC also requires its own credentials and issuer:

```bash
curl -X PUT "https://id.answerable.org/api/admin/v1/organizations/$ORG/sso-provider" \
  -H "Idempotency-Key: $SSO_OPERATION_KEY" \
  -H "If-None-Match: *" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "issuer": "https://login.microsoftonline.com/00000000-0000-0000-0000-000000000000/v2.0",
    "domain": "contoso.com",
    "oidc": { "clientId": "'"$ENTRA_APP_ID"'", "clientSecret": "'"$ENTRA_APP_SECRET"'" }
  }'
```

**Defaults.** When scopes are omitted, every row, platform or own credentials, uses `email openid profile`. ID asks no directory for `offline_access` and stores no upstream refresh token.

**Changing the directory.** Creating, replacing or deleting SSO configuration revokes that organisation's directory grants, and a directory session then needs a new sign-in before it can authorise anything. Its [email-link](/docs/id/magic-links) sessions and grants stay: the two ways are independent, and a link still signs in a person whose old directory account no longer matches. Switching between own and platform credentials is a configuration change; for Entra it also changes every user's pairwise `sub`, so existing accounts stop matching. Unchanged configuration preserves grants; restoring an earlier configuration does not restore revoked grants. Other organisations and global browser sessions are preserved. [User OAuth](/docs/id/oauth) checks the accepted account, provider UUID and configuration revision.

**Retries.** Set `SSO_OPERATION_KEY` once and reuse it with identical input. PUT and delete require keys; retries return receipts. Use `If-None-Match: *` for creation or the current provider ETag in `If-Match` to refuse stale updates, retaining the original header on retry. For own credentials, omit `clientSecret` on an update to keep the stored secret.

**One row per organisation.** `PUT` creates or replaces it. `GET` returns `oidc.credentials` (`platform` or `own`), `clientId` and `hasClientSecret`, never the secret. See [sign-in checks](/docs/id/sign-in#what-is-checked). Guest opt-in: [Not yet.](/docs/id#today-and-next)

## Turn on sign-in by link

For a firm with no directory, or one that wants links beside it. A firm that requires its directory leaves them off, and a link never passes through its MFA or conditional access.

1. **Ask the firm's IT team to allow the sender**, `sign-in@id.answerable.org`, on its mail gateway, before anyone signs in. A gateway can quarantine the mail or rewrite the link.
2. **List the people**, unless the firm has a directory: `members_import`, or [importMembers](/docs/id/admin-api/members/importMembers). At a firm with a directory, people become members at their first directory sign-in, and a person imported first has to prove their mailbox with a code at that sign-in.
3. **Turn links on**: `magiclink_enable`, or [enableMagicLink](/docs/id/admin-api/organizations/enableMagicLink).
4. **Pilot with about 20 people**, on real mailboxes, phones included, before the firm starts. Postmark's Activity shows what arrived; `signin_diagnose` shows why someone got no mail.

## Register what they may use

**Resources** are MCP servers, identified by the URL that becomes the token audience. **Clients** are apps and tools that request tokens.

```bash
curl https://id.answerable.org/api/admin/v1/resources \
  -H "Idempotency-Key: $RESOURCE_CREATE_KEY" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"identifier":"https://tutor.answerable.org","name":"Tutor","allowedScopes":["tutor:read"]}'
```

```bash
curl https://id.answerable.org/api/admin/v1/clients \
  -H "Idempotency-Key: omnichat-contoso-v1" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "clientId": "omnichat-contoso",
    "name": "OmniChat Contoso",
    "organizationId": "'"$ORG"'",
    "tokenEndpointAuthMethod": "client_secret_post",
    "grantTypes": ["authorization_code", "refresh_token"],
    "scopes": ["openid", "profile", "email", "offline_access", "tutor:read"],
    "redirectUris": ["https://contoso.omnichat.example/oauth/openid/callback"]
  }'
```

**LibreChat / OmniChat.** The example registers a server client using `client_secret_post`; every sign-in still requires S256 PKCE. Save the returned `clientSecret` once in the application's secret store. A replay returns a receipt without the secret; if the first response is lost, rotate the secret with a new operation key. Public clients (`none`) and key-based clients (`private_key_jwt`) receive no shared secret. See [LibreChat settings](/docs/id/oauth#configure-librechat-sign-in) before enabling sign-in.

**Trusted applications.** Set `skipConsent: true` only for an explicitly approved Answerable-operated application. It bypasses the consent screen; it does not grant access. Register a separate client for each isolated deployment and environment, owned by the organisation it serves, then approve capabilities and assign scopes below.

**Links.** A client may only request tokens for resources it is linked to: `PUT /clients/{clientId}/resources/{resource}` with the resource URL encoded. A registering client can never link itself. Registered applications can use [OIDC sign-in](/docs/id/oauth).

```bash
curl "https://id.answerable.org/api/admin/v1/clients/$CLIENT_ID" \
  -H "Authorization: Bearer $TOKEN"

curl "https://id.answerable.org/api/admin/v1/resources/https%3A%2F%2Ftutor.answerable.org" \
  -H "Authorization: Bearer $TOKEN"

curl -X DELETE "https://id.answerable.org/api/admin/v1/clients/$CLIENT_ID?confirm=$CLIENT_ID" \
  -H "Idempotency-Key: $CLIENT_DELETE_KEY" \
  -H "Authorization: Bearer $TOKEN"
```

**Inspect links.** [getClient](/docs/id/admin-api/clients/getClient) includes `resources`; [getResource](/docs/id/admin-api/resources/getResource) includes `clients`. Resource path values are percent-encoded URLs.

**Delete a client.** [eraseClient](/docs/id/admin-api/clients/eraseClient) tombstones the client, links and consents, clears credentials and revokes grants. Token records follow their separate removal contract. Remove every referencing entitlement and capability first, including disabled/future rows, or deletion returns a reference error. Prefer `POST /clients/{clientId}/disable` to suspend use reversibly. Erasures require a `confirm` query parameter equal to the target identifier, with no DELETE body.

## Grant access

An **entitlement** assigns scopes to the whole organisation, a group or a member. A matching platform capability is also required. First approve client-only login and the exact client/resource code and refresh ceilings using [capability commands](/docs/id/manage#approve-user-capabilities). Registration and a resource-only assignment do not grant application access.

```bash
curl "https://id.answerable.org/api/admin/v1/organizations/$ORG/entitlements" \
  -H "Idempotency-Key: $LOGIN_ENTITLEMENT_KEY" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"clientId":"omnichat-contoso","scopes":["openid","profile","email","offline_access"]}'

curl "https://id.answerable.org/api/admin/v1/organizations/$ORG/entitlements" \
  -H "Idempotency-Key: $ORG_ENTITLEMENT_KEY" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"clientId":"omnichat-contoso","resource":"https://tutor.answerable.org","scopes":["tutor:read"]}'
```

**Narrow it to a group.** Create the group, add members, and grant the group instead of the organisation:

```bash
curl "https://id.answerable.org/api/admin/v1/organizations/$ORG/groups" \
  -H "Idempotency-Key: $GROUP_CREATE_KEY" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"slug":"finance","name":"Finance"}'

curl -X PUT "https://id.answerable.org/api/admin/v1/organizations/$ORG/groups/$GROUP/members/$MEMBER" \
  -H "Idempotency-Key: $GROUP_MEMBER_KEY" \
  -H "If-None-Match: *" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"validUntil":"2026-12-31T00:00:00Z"}'

curl "https://id.answerable.org/api/admin/v1/organizations/$ORG/entitlements" \
  -H "Idempotency-Key: $GROUP_ENTITLEMENT_KEY" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"groupId":"'"$GROUP"'","clientId":"omnichat-contoso","resource":"https://tutor.answerable.org","scopes":["tutor:read"]}'
```

**Withhold access.** Do not create the row. **Remove access.** `POST …/entitlements/{id}/disable`, or `DELETE` it. **Time-bound access.** Every membership, group membership and entitlement takes `validFrom` and `validUntil`; outside the window it does not count.

**Where entitlements apply.** Direct-session assignments authorise browser access to the admin resource. User OAuth checks client-only login permission and, for service access, the exact client/resource capability and assignment at authorisation, code exchange and refresh. Machine clients require an exact capability as well as their scope ceiling and compatibility link. See [application access](/docs/id/oauth).

## Let the organisation manage itself

First [approve an admin-session capability](/docs/id/manage#approve-direct-administrator-access) for this organisation and the admin resource. Once its administrator signs in through its own current SSO, assign the same or narrower scopes. Set `MEMBER` from the members list.

```bash
curl "https://id.answerable.org/api/admin/v1/organizations/$ORG/entitlements" \
  -H "Idempotency-Key: $ADMIN_ENTITLEMENT_KEY" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"memberId":"'"$MEMBER"'","resource":"https://id.answerable.org/api/admin","scopes":["org:read","org:users"]}'
```

They can then follow [Manage your organisation](/docs/id/manage). Self-service configuration is [Not yet.](/docs/id#today-and-next)

## Check who can reach what

```bash
curl "https://id.answerable.org/api/admin/v1/organizations/$ORG/access?resource=https%3A%2F%2Ftutor.answerable.org" \
  -H "Authorization: Bearer $TOKEN"
```

**Two views.** `…/access?resource=` or `?clientId=` lists the members who can reach a target with their scopes. `…/members/{memberId}/access` lists a member's targets and which rows grant them. Both compute effective grants for access reviews; [App and service OAuth](/docs/id/oauth) re-evaluates the current policy at each exchange.

## Offboard

| Situation                        | Do this                                                                                                                                              | Effect                                                                                                                                                                                                                                                                                               |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A person leaves the organisation | `members_remove` in the [admin MCP](/docs/admin#stopping-someone), or `PATCH …/members/{memberId}` with `validUntil` now, or `DELETE` the membership | Their sign-in to that organisation and its grants stop; other memberships stay. Reverse with `members_reinstate` or `POST …/members/{memberId}/reinstate`; the grants and group assignments removed with the membership are not restored. Offline JWTs remain subject to expiry and consumer checks. |
| A person must be cut off at once | `users_disable`, or `POST /users/{userId}/disable`                                                                                                   | Global browser sessions and local stored grants/tokens are revoked atomically, and no sign-in works at any organisation. Reverse with `users_enable`: revoked sessions are not restored. Offline JWTs and downstream sessions retain separate exposure.                                              |
| Their address will be reused     | `users_retireemail` (owner role) after `users_disable`, or `POST /users/{userId}/retire-email` after disabling                                       | The address is released; the old account keeps a tombstone, and the next holder is a new person with a new `sub`. Until the previous holder is disabled and retired, a new person who signs in with the address gets `email_conflict`, and listing it for another person is refused as `disabled`. Terminal.                                                     |
| The organisation leaves          | `POST /organizations/{org}/disable`                                                                                                                  | Sign-in refuses; the tenant epoch advances and owned machine tokens are revoked. Global browser sessions remain; tenant grants are revoked and old provider/tenant state cannot authorise renewal                                                                                                    |
| An app is retired                | `DELETE /clients/{clientId}?confirm={clientId}` after removing its entitlements                                                                      | Client, links and consents are tombstoned; credentials are cleared/revoked and history remains                                                                                                                                                                                                       |
| A domain no longer belongs here  | `DELETE /organizations/{org}/domains/{domainId}`                                                                                                     | Sign-in routing is removed; no confirmation needed                                                                                                                                                                                                                                                   |
| Product access must be removed   | `DELETE /users/{userId}` or `DELETE /organizations/{org}` with `?confirm=<id>` and no body                                                           | Terminal tombstones deny ordinary reads/authority; identifying fields and UUID history remain. Remove owned clients/resources and policy references first                                                                                                                                            |

**In the admin MCP.** `users_disable`, `users_enable` and `users_retireemail` take a person's `email`; `members_remove` and `members_reinstate` take an `organizationId` and a member's `email`. Each finds the person with the exact `email` filter of [listUsers](/docs/id/admin-api/users/listUsers) or [listMembers](/docs/id/admin-api/members/listMembers). The first four need the `admin` role. `users_retireemail`, which cannot be undone, needs `owner`, and so does any of the five on a member of Answerable staff. Each needs a recent company sign-in. [Stopping someone](/docs/admin#stopping-someone) has the previews and the errors.

**What stopping does not reach.** A service token already issued lives to its expiry, and each app's own session is the app's to end: ending it belongs to each app's integration, such as [App and service OAuth](/docs/id/oauth). No company directory can tell Answerable ID that someone left, so removing the member in ID is the staff step.

**Bulk import of an existing cell's users.** `POST /organizations/{org}/members/import` lists up to 1,000 addresses a call, each with its own answer: [who may ask](/docs/id/magic-links#who-may-ask).

```bash
curl --get https://id.answerable.org/api/admin/v1/entitlements \
  -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "clientId=$CLIENT_ID"

curl --get https://id.answerable.org/api/admin/v1/entitlements \
  -H "Authorization: Bearer $TOKEN" \
  --data-urlencode 'resource=https://tutor.answerable.org'
```

[listAllEntitlements](/docs/id/admin-api/entitlements/listAllEntitlements) lists recorded grants across organisations with each organisation's ID and slug. Filter by `clientId`, `resource` or `status`; paginate with `limit` and `cursor`. These rows are not proof of current effective access: check status and windows, or use the access views above. [User OAuth exchanges](/docs/id/oauth) check current effective access.

## One person's trail

```bash
curl --get https://id.answerable.org/api/admin/v1/users \
  -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "email=$EMAIL"

# Set USER_ID to the returned user's id.
curl "https://id.answerable.org/api/admin/v1/users/$USER_ID/audit-events?outcome=success" \
  -H "Authorization: Bearer $TOKEN"
```

**Find the person.** [listUsers](/docs/id/admin-api/users/listUsers) and `listMembers` accept an exact `email` filter, normalised to lowercase. [listUserAuditEvents](/docs/id/admin-api/audit/listUserAuditEvents) returns events where the person is the actor or the target is their user, membership or session. Filter by `action`, `outcome`, `from` or `to`; use `limit` and `cursor` to page. Omit `outcome` to include every outcome.

## Read the trail

```bash
curl "https://id.answerable.org/api/admin/v1/audit-events?organizationId=$ORG&outcome=denied&from=2026-09-01T00:00:00Z" \
  -H "Authorization: Bearer $TOKEN"
```

Every write, every denied attempt, every sign-in success, rejection and sign-out is a row. Filter by `action`, `actorId`, `targetType`, `targetId` and `outcome` (`success`, `failure`, `denied`); send an `x-request-id` header on writes to find them again.

## Errors

| Code                               | Meaning                                                                            | What to do                                                                                                                                                                                |
| ---------------------------------- | ---------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `platform_credentials_unsupported` | HTTP 400: platform credentials requested for an issuer other than Google or Entra. | Supply own OIDC credentials or use the correct Google/Entra issuer.                                                                                                                       |
| `platform_application_missing`     | HTTP 409 on PUT: the platform application is absent from the service environment.  | Configure both client ID and secret, restart the service and retry. A later disappearance gives HTTP 503 JSON at sign-in; see [sign-in errors](/docs/id/sign-in#when-sign-in-is-refused). |
| `root_locked`                      | Root is locked because a human platform administrator exists.                      | Use your own credentials, or enable break-glass for emergency recovery.                                                                                                                   |
| `client_has_entitlements`          | Entitlements still reference the client.                                           | Remove all referencing entitlements before erasure.                                                                                                                                       |

See [all admin error codes](/docs/id/manage#errors), including confirmation and lifecycle errors. SSO test problems and sign-in verdicts are listed above.

Use a different key for each separate command. Group PATCH accepts the optional current getGroup ETag in If-Match.
