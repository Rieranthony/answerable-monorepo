**Answerable staff.** This page is for us. It covers setting the service up for the first time, then creating and looking after client organisations. Organisation admins have their own page, [Manage your organisation](/docs/id/manage). Every step is a `curl` command against the admin API; the [reference](/docs/id/admin-api) lists every field.

## Words used on this page

| Word             | Meaning                                                                                                                                      |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| **Organisation** | A company that uses Answerable. Answerable itself is one too, called the **platform organisation**. The service creates it by itself.        |
| **Member**       | A person's place in an organisation. It appears the first time they sign in.                                                                 |
| **Group**        | A named set of members inside an organisation. `platform-admins` is the group of Answerable staff.                                           |
| **Scope**        | One permission, written as a word such as `platform:read`. A session or token carries a list of them.                                        |
| **Resource**     | Something people and apps get tokens for, named by a URL. The admin API is one; MCP servers are the others.                                  |
| **Entitlement**  | A rule saying who may use which resource with which scopes. Members of `platform-admins` get every platform scope on the admin API this way. |
| **Client**       | An app or script that asks for tokens. It has a `clientId` and a secret.                                                                     |
| **Root secret**  | A one-off password for the first setup. It locks itself as soon as a person holds admin rights.                                              |

## First run

A new service has no accounts at all. You get in with the root secret, sign in with your work account, give that account admin rights, and the root secret locks itself. Seven steps.

**Before you start.** Make the secret and keep it somewhere safe for the next hour:

```bash
openssl rand -base64 48
```

1. **Start the service with the secret.** Set `ROOT_ADMIN_SECRET` to that value and configure `OPERATION_REPLAY_CONFIG` in deployment secret storage, independently of `BETTER_AUTH_SECRET`. Its JSON shape is `{"activeKeyId":"v1","keys":{"v1":"<canonical-base64url-encoded random 32-byte key>"}}`. Generate a dedicated random key; the placeholder is not a usable key. Keep older keys until their replay windows close. Without this configuration, domain commands return `503` before changing state.

   Also configure independent upstream token keys before sign-in: `UPSTREAM_TOKEN_SECRETS=[{"version":1,"value":"<canonical-base64url-encoded random 32-byte key>"}]`. The first version encrypts upstream access, refresh and ID tokens; retain previous versions for reads. Missing keys make sign-in fail with `500 authentication_unavailable`. For rotation, distribute the new key to every instance before making it the first entry. Do not reuse authentication or replay keys.

   Apply the migrations, then start the service the way you deploy it. On an empty database it creates the platform organisation, the admin API resource and the `platform-admins` group on its own. `PLATFORM_ORGANIZATION_NAME` names the organisation; the default is `Answerable`. Migration 0037 clears pre-cutover upstream credentials once while preserving identity bindings and browser sessions; fresh SSO stores encrypted replacements. Existing installations still require an external-consumer review, stopped old writers, separately provisioned keys, and representative migration/backup-restore rehearsal before cutover. These operational release gates are **not yet** complete.

   ```bash
   bun --filter @answerable/id db:migrate
   ```

2. **Write down two IDs.** The secret works as a bearer token. Ask the service for its summary and copy `platform.organizationId` into `PLATFORM_ORG` and `platform.groupId` into `PLATFORM_GROUP`; the next steps use both.

   ```bash
   export ROOT_ADMIN_SECRET="paste the secret here"

   curl https://id.answerable.org/api/admin/v1/platform/summary \
     -H "Authorization: Bearer $ROOT_ADMIN_SECRET"
   ```

3. **Say which work accounts are staff.** Two calls. The first says that emails on our domain belong to the platform organisation. The second says which directory checks those accounts: Google Workspace or Microsoft Entra, with the app credentials that directory gave us. A third call checks that the directory answers.

   Set `STAFF_DOMAIN` (for example `answerable.org`), `STAFF_ISSUER` (the directory's issuer URL from the [table below](#connect-the-directory)), `SSO_CLIENT_ID` and `SSO_CLIENT_SECRET` first.

   ```bash
   curl "https://id.answerable.org/api/admin/v1/organizations/$PLATFORM_ORG/domains" \
     -H "Idempotency-Key: platform-domain-setup" \
     -H "Authorization: Bearer $ROOT_ADMIN_SECRET" \
     -H "Content-Type: application/json" \
     -d '{"domain":"'"$STAFF_DOMAIN"'"}'

   curl -X PUT "https://id.answerable.org/api/admin/v1/organizations/$PLATFORM_ORG/sso-provider" \
     -H "Idempotency-Key: platform-sso-setup" \
     -H "If-None-Match: *" \
     -H "Authorization: Bearer $ROOT_ADMIN_SECRET" \
     -H "Content-Type: application/json" \
     -d '{"issuer":"'"$STAFF_ISSUER"'","domain":"'"$STAFF_DOMAIN"'","oidc":{"clientId":"'"$SSO_CLIENT_ID"'","clientSecret":"'"$SSO_CLIENT_SECRET"'"}}'

   curl "https://id.answerable.org/api/admin/v1/organizations/$PLATFORM_ORG/sso-provider/test" \
     -H "Authorization: Bearer $ROOT_ADMIN_SECRET"
   ```

   An empty `problems` list means the directory is reachable. The test cannot check the credentials themselves; the next step does that.

4. **Sign in.** Open [the login page](https://answerable.org/login) and sign in with your work account. This creates your user and your membership of the platform organisation. You have no admin rights yet.

5. **Give yourself admin rights.** Find your member record by email, copy its `id` into `STAFF_MEMBER`, then add it to the `platform-admins` group. The group already carries every platform scope, so joining it is all it takes.

   ```bash
   curl --get "https://id.answerable.org/api/admin/v1/organizations/$PLATFORM_ORG/members" \
     -H "Authorization: Bearer $ROOT_ADMIN_SECRET" \
     --data-urlencode "email=you@answerable.org"

   curl -X PUT "https://id.answerable.org/api/admin/v1/organizations/$PLATFORM_ORG/groups/$PLATFORM_GROUP/members/$STAFF_MEMBER" \
     -H "Idempotency-Key: platform-admin-membership-setup" \
     -H "If-None-Match: *" \
     -H "Authorization: Bearer $ROOT_ADMIN_SECRET" \
     -H "Content-Type: application/json" \
     -d '{}'
   ```

6. **Check it worked.** In your browser's developer tools, copy the `Cookie` header from any request to `id.answerable.org` into `SESSION_COOKIE`. Then ask the service who you are:

   ```bash
   curl https://id.answerable.org/api/admin/v1/me \
     -H "Cookie: $SESSION_COOKIE"
   ```

   The answer lists `platform:read`, `platform:users` and `platform:write` among your scopes. Now repeat the summary call from step 2 with the root secret: it is refused with `403 root_locked`. That is the point. A person holds `platform:write`, so the secret has locked itself.

7. **Put the secret away.** Remove `ROOT_ADMIN_SECRET` from the deployment, or keep it in your secret store with `ROOT_ADMIN_BREAK_GLASS=false`. If one day no staff member can administer the service, deploy with the secret and `ROOT_ADMIN_BREAK_GLASS=true`, repair access, then turn it off again. Every use of the secret, allowed or refused, is written to the audit log as `admin.root_request`.

**The next staff member.** They sign in once (step 4). You repeat step 5 for them with your own browser session instead of the root secret, adding `-H "Origin: https://answerable.org"` because writes from a browser session must name the site they come from. Nothing else is needed.

## Get a staff token

Your browser session is enough for commands you type by hand. For scripts and agents, create a client owned by the platform organisation, allow it to use the admin API, and swap its secret for a token.

Client creation requires configured replay encryption and a stable `Idempotency-Key`. Use a distinct key for each intended registration, and reuse it after a lost response. Recovery lasts 24 hours; see [operation status and retries](/docs/id/manage#operation-status).

```bash
curl https://id.answerable.org/api/admin/v1/clients \
  -H "Idempotency-Key: staff-automation-v1" \
  -H "Cookie: $SESSION_COOKIE" \
  -H "Origin: https://answerable.org" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Staff automation",
    "organizationId": "'"$PLATFORM_ORG"'",
    "tokenEndpointAuthMethod": "client_secret_basic",
    "grantTypes": ["client_credentials"],
    "redirectUris": [],
    "clientCredentialsScopes": ["platform:read", "platform:users", "platform:write"]
  }'

# Save clientId as CLIENT_ID and the returned clientSecret as CLIENT_SECRET.
curl -X PUT "https://id.answerable.org/api/admin/v1/clients/$CLIENT_ID/resources/https%3A%2F%2Fid.answerable.org%2Fapi%2Fadmin" \
  -H "Cookie: $SESSION_COOKIE" \
  -H "Origin: https://answerable.org"

curl https://id.answerable.org/auth/oauth2/token \
  --user "$CLIENT_ID:$CLIENT_SECRET" \
  --data-urlencode 'grant_type=client_credentials' \
  --data-urlencode 'resource=https://id.answerable.org/api/admin' \
  --data-urlencode 'scope=platform:read platform:users platform:write'
```

**The secret is shown once.** Save `clientSecret` when the first call returns it; it cannot be read back. Use `clientId`, not the record's `id`, in client URLs. The third call returns `access_token`; set `TOKEN` to it. Every command below uses `TOKEN`, but your browser cookie plus the `Origin` header works just as well.

**Why the platform organisation.** A client acts for the organisation that owns it. Only a client owned by the platform organisation gets platform scopes; one owned by a client organisation only ever acts for that organisation, whatever scopes it lists.

## Read the platform

```bash
curl https://id.answerable.org/api/admin/v1/platform/summary \
  -H "Authorization: Bearer $TOKEN"
```

[getPlatformSummary](/docs/id/admin-api/platform/getPlatformSummary) returns organisation and user counts by status, clients (including disabled and unowned), resources, active sessions, and sign-ins and admin denials over the trailing 24 hours. `platform` contains the seeded organisation and group IDs. Rejected sign-ins have no organisation, so rejection counts are available only across the platform.

## Read an organisation

```bash
curl "https://id.answerable.org/api/admin/v1/organizations/$ORG/summary" \
  -H "Authorization: Bearer $TOKEN"
```

Set `ORG` to an organisation ID from creation or the organisations list. [getOrganizationSummary](/docs/id/admin-api/organizations/getOrganizationSummary) returns the organisation, domain and SSO configuration summary, member counts and effective windows, groups, entitlement targets, owned clients and successful sign-ins over the trailing seven days. Status counts include stored rows; entitlement target counts include disabled and out-of-window rows. Exact app–resource pairs use `kind: "client_resource"`, `id` for the client and `resource` for the resource identifier. Standalone targets use `kind: "client"` or `kind: "resource"`. These counts describe stored assignments, not effective permission. Global browser session counts are omitted from organisation summaries. There is no per-organisation rejection count.

## Why can't someone sign in

```bash
curl --get "https://id.answerable.org/api/admin/v1/organizations/$ORG/sign-in-diagnosis" \
  -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "email=$EMAIL"
```

[diagnoseSignIn](/docs/id/admin-api/diagnostics/diagnoseSignIn) checks this tenant's configuration and memberships without changing state. `verdict.checked` lists the local checks evaluated in order; `verdict.code` is the first applicable result. It rechecks current `org:users` or staff `platform:read` authority inside its transaction and returns `Cache-Control: no-store`.

| Verdict                   | Meaning                                                  | What to do                                                |
| ------------------------- | -------------------------------------------------------- | --------------------------------------------------------- |
| `provider_not_found`      | No SSO provider is configured.                           | Configure the provider.                                   |
| `organization_disabled`   | Organisation is disabled.                                | Review whether to enable it.                              |
| `domain_not_allowed`      | Email domain does not route here.                        | Check this tenant's active domain assignment.             |
| `user_disabled`           | The user linked to this tenant's membership is disabled. | Ask platform staff to review the account.                 |
| `membership_revoked`      | This tenant's membership was revoked.                    | Review whether to reinstate it.                           |
| `authentication_required` | Local checks found no blocker.                           | Complete a real IdP authentication to establish identity. |

**Tenant visibility.** `user` and `membership` are null unless this tenant has a membership for the exact email. A null user does not mean the email is globally unused. Routing names only this organisation, never another tenant. Account issuers, directory IDs and retired-email state are excluded for all callers, including staff. Platform-wide user inspection remains a separate permission-controlled API.

**A real IdP authentication is required** to establish identity and evaluate `directory_mismatch`, `guest_account`, `personal_account`, `hosted_domain_mismatch`, `email_unverified` and `identity_conflict`, listed in `verdict.requiresToken`. This diagnosis does not predict account creation or successful sign-in. A non-effective membership does not prevent sign-in, but stops grants. See [sign-in checks](/docs/id/sign-in#what-is-checked).

**Contract change.** The diagnostic response no longer includes `accounts` or `user.retiredEmail`. `authentication_required` replaces `new_user_would_be_created` and `would_sign_in`; `identity_conflict` is deferred to real authentication. Update diagnostic consumers before releasing this API change.

## Test an SSO configuration

```bash
curl "https://id.answerable.org/api/admin/v1/organizations/$ORG/sso-provider/test" \
  -H "Authorization: Bearer $TOKEN"
```

[testSsoProvider](/docs/id/admin-api/diagnostics/testSsoProvider) fetches discovery and JWKS without sending credentials or changing state. It reports reachability, exact issuer equality, key count and elapsed time. It requires current `platform:read` when reading the endpoint configuration and returns `Cache-Control: no-store`. Network requests run after that read transaction closes, so the result describes the captured endpoints even if configuration changes during the probe. It does not prove client credentials, consent, a usable signing key or a person's ability to sign in; complete a real sign-in for those checks.

| Problem code            | Meaning                                                                              | What to do                                                |
| ----------------------- | ------------------------------------------------------------------------------------ | --------------------------------------------------------- |
| `insecure_issuer`       | A fetched endpoint or issuer is not an absolute HTTPS URL.                           | Correct the configured URLs.                              |
| `private_host`          | A host is private or resolves to a private address.                                  | Use public provider endpoints.                            |
| `discovery_unreachable` | Discovery failed, timed out or returned a non-success status; redirects are refused. | Check the discovery URL and connectivity.                 |
| `discovery_invalid`     | Discovery JSON is missing required URLs or exceeds the size limit.                   | Correct the provider's discovery document.                |
| `issuer_mismatch`       | Discovery issuer differs from the configured issuer.                                 | Use the exact tenant issuer.                              |
| `jwks_unreachable`      | JWKS failed, timed out or returned a non-success status; redirects are refused.      | Check the discovery document's JWKS URL and connectivity. |
| `jwks_invalid`          | JWKS is invalid or exceeds the size limit.                                           | Correct the provider's key document.                      |

No provider returns HTTP `404 provider_not_found`; configure it first. Other failed checks appear in `problems` on a successful HTTP response.

## Create the organisation

```bash
curl https://id.answerable.org/api/admin/v1/organizations \
  -H "Idempotency-Key: $ORGANISATION_CREATE_KEY" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"slug":"contoso","name":"Contoso"}'
```

**Retry key.** Set `ORGANISATION_CREATE_KEY` once for this intended creation and reuse it with identical input after a lost response. All organisation mutations require keys; ordinary result recovery lasts seven days. PATCH also requires the strong If-Match ETag from getOrganization; see [editing organisation configuration](/docs/id/manage#operation-status).

**Slug.** Lowercase labels joined by single hyphens, the same grammar as the Omni-Weaver tenant id. It cannot change later. Set `ORG` to the returned `id`.

## Route its email domains

```bash
curl "https://id.answerable.org/api/admin/v1/organizations/$ORG/domains" \
  -H "Idempotency-Key: $DOMAIN_OPERATION_KEY" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"domain":"contoso.com"}'
```

**One owner.** A domain routes to at most one active organisation. To move it, disable or delete the old row first, then add the new one. Sign-in with an email outside the organisation's active domains is refused. Domain verification by DNS: [Not yet.](/docs/id#today-and-next)

```bash
curl -X DELETE "https://id.answerable.org/api/admin/v1/organizations/$ORG/domains/$DOMAIN" \
  -H "Idempotency-Key: $DOMAIN_DELETE_KEY" \
  -H "Authorization: Bearer $TOKEN"
```

**Domain operation keys.** Set `DOMAIN_OPERATION_KEY` and `DOMAIN_DELETE_KEY` to different stable keys for the two logical commands. Reuse each key with identical input when retrying; recoverable responses last seven days. The root setup example also uses a stable key. Repeated enable/disable under a new key records a no-op; changed input under an existing key conflicts.

**Delete an assignment.** Set `DOMAIN` to its domain row ID. [deleteOrganizationDomain](/docs/id/admin-api/domains/deleteOrganizationDomain) removes sign-in routing and records `domain.deleted`. No `confirm` is required; disable the assignment for a reversible suspension.

## Connect the directory

**Changing the directory.** Creating, replacing or deleting SSO configuration revokes existing user authorisations for that organisation. An unchanged configuration preserves them. Restoring an earlier configuration does not restore revoked grants. Other organisations and global browser sessions are preserved. [User OAuth](/docs/id/oauth) validates the selected organisation's accepted account, provider UUID and configuration revision before creating or using a grant.

Set `SSO_OPERATION_KEY` once for this configuration command and reuse it with identical input on retry. PUT and delete require keys; redacted result recovery lasts seven days. Omit `clientSecret` to retain the stored secret on a new update. Creation requires `If-None-Match: *`; replacement requires the current provider ETag in `If-Match`. Send exactly one precondition and retain it with the key on retry.

```bash
curl -X PUT "https://id.answerable.org/api/admin/v1/organizations/$ORG/sso-provider" \
  -H "Idempotency-Key: $SSO_OPERATION_KEY" \
  -H "If-None-Match: *" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "issuer": "https://login.microsoftonline.com/00000000-0000-0000-0000-000000000000/v2.0",
    "domain": "contoso.com",
    "oidc": { "clientId": "'"$ENTRA_APP_ID"'", "clientSecret": "'"$ENTRA_APP_SECRET"'" }
  }'
```

| Directory        | `issuer`                                                | What is pinned                                        |
| ---------------- | ------------------------------------------------------- | ----------------------------------------------------- |
| Microsoft Entra  | `https://login.microsoftonline.com/<directory-id>/v2.0` | The directory id; guests and other directories refuse |
| Google Workspace | `https://accounts.google.com`                           | The hosted domain; personal accounts refuse           |

**One row per organisation.** `PUT` creates or replaces it; omit `clientSecret` on an update to keep the stored one. `GET` never returns the secret. The consent the client's IT gives is to Answerable's single multi-tenant app; nothing is registered per app. What each sign-in checks is on the [sign-in page](/docs/id/sign-in#what-is-checked). Guest opt-in per organisation: [Not yet.](/docs/id#today-and-next)

## Register what they may use

**Resources** are MCP servers, identified by the URL that becomes the token audience. **Clients** are apps and tools that request tokens.

```bash
curl https://id.answerable.org/api/admin/v1/resources \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"identifier":"https://tutor.answerable.org","name":"Tutor","allowedScopes":["tutor:read"]}'
```

```bash
curl https://id.answerable.org/api/admin/v1/clients \
  -H "Idempotency-Key: omnichat-contoso-v1" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "clientId": "omnichat-contoso",
    "name": "OmniChat Contoso",
    "organizationId": "'"$ORG"'",
    "tokenEndpointAuthMethod": "private_key_jwt",
    "grantTypes": ["authorization_code", "refresh_token"],
    "redirectUris": ["https://contoso.omnichat.example/oauth/callback"],
    "jwksUri": "https://contoso.omnichat.example/.well-known/jwks.json"
  }'
```

**Links.** A client may only request tokens for resources it is linked to: `PUT /clients/{clientId}/resources/{resource}` with the resource URL encoded. A registering client can never link itself. Registered applications can use [OIDC sign-in](/docs/id/oauth).

```bash
curl "https://id.answerable.org/api/admin/v1/clients/$CLIENT_ID" \
  -H "Authorization: Bearer $TOKEN"

curl "https://id.answerable.org/api/admin/v1/resources/https%3A%2F%2Ftutor.answerable.org" \
  -H "Authorization: Bearer $TOKEN"

curl -X DELETE "https://id.answerable.org/api/admin/v1/clients/$CLIENT_ID?confirm=$CLIENT_ID" \
  -H "Authorization: Bearer $TOKEN"
```

**Inspect links.** [getClient](/docs/id/admin-api/clients/getClient) includes `resources`; [getResource](/docs/id/admin-api/resources/getResource) includes `clients`. Resource path values are percent-encoded URLs.

**Erase a client.** [eraseClient](/docs/id/admin-api/clients/eraseClient) removes its resource links, tokens and consents. Remove every referencing entitlement first, including disabled rows, or it returns `client_has_entitlements`. Prefer `POST /clients/{clientId}/disable` to suspend use reversibly. Erasures require a `confirm` query parameter equal to the target identifier, with no DELETE body.

## Grant access

An **entitlement** says who may obtain tokens for what, with which scopes. Its principal is the whole organisation, one group, or one member. Grants add up; there are no deny rows.

```bash
curl "https://id.answerable.org/api/admin/v1/organizations/$ORG/entitlements" \
  -H "Idempotency-Key: $ORG_ENTITLEMENT_KEY" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"resource":"https://tutor.answerable.org","scopes":["tutor:read"]}'
```

**Narrow it to a group.** Create the group, add members, and grant the group instead of the organisation:

```bash
curl "https://id.answerable.org/api/admin/v1/organizations/$ORG/groups" \
  -H "Idempotency-Key: $GROUP_CREATE_KEY" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"slug":"finance","name":"Finance"}'

curl -X PUT "https://id.answerable.org/api/admin/v1/organizations/$ORG/groups/$GROUP/members/$MEMBER" \
  -H "Idempotency-Key: $GROUP_MEMBER_KEY" \
  -H "If-None-Match: *" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"validUntil":"2026-12-31T00:00:00Z"}'

curl "https://id.answerable.org/api/admin/v1/organizations/$ORG/entitlements" \
  -H "Idempotency-Key: $GROUP_ENTITLEMENT_KEY" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"groupId":"'"$GROUP"'","resource":"https://tutor.answerable.org","scopes":["tutor:read"]}'
```

**Withhold access.** Do not create the row. **Remove access.** `POST …/entitlements/{id}/disable`, or `DELETE` it. **Time-bound access.** Every membership, group membership and entitlement takes `validFrom` and `validUntil`; outside the window it does not count.

**Where entitlements apply.** Direct-session assignments authorise browser access to the admin resource. User OAuth checks client-only login permission and, for service access, the exact client/resource capability and assignment at authorisation, code exchange and refresh. Machine clients require an exact capability as well as their scope ceiling and compatibility link. See [application access](/docs/id/oauth).

## Let the organisation manage itself

Once one of their admins has signed in, grant them scopes on the admin API. Set `MEMBER` from the members list.

```bash
curl "https://id.answerable.org/api/admin/v1/organizations/$ORG/entitlements" \
  -H "Idempotency-Key: $ADMIN_ENTITLEMENT_KEY" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"memberId":"'"$MEMBER"'","resource":"https://id.answerable.org/api/admin","scopes":["org:read","org:users"]}'
```

They can then follow [Manage your organisation](/docs/id/manage). `org:write` exists but self-service configuration is [Not yet.](/docs/id#today-and-next)

## Check who can reach what

```bash
curl "https://id.answerable.org/api/admin/v1/organizations/$ORG/access?resource=https%3A%2F%2Ftutor.answerable.org" \
  -H "Authorization: Bearer $TOKEN"
```

**Two views.** `…/access?resource=` or `?clientId=` lists the members who can reach a target with their scopes. `…/members/{memberId}/access` lists a member's targets and which rows grant them. Both compute effective grants for access reviews; [App and service OAuth](/docs/id/oauth) re-evaluates the current policy at each exchange.

## Offboard

| Situation                        | Do this                                                                                    | Effect                                                                                                                                                        |
| -------------------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A person leaves the organisation | `PATCH …/members/{memberId}` with `validUntil` now, or `DELETE` the membership             | Their admin access and stored user OAuth grants in that organisation stop; other memberships stay. Offline JWTs remain subject to expiry and consumer checks. |
| A person must be cut off at once | `POST /users/{userId}/disable`                                                             | Every session ends and every token is revoked, in one transaction                                                                                             |
| Their address will be reused     | `POST /users/{userId}/retire-email` after disabling                                        | The address is released; the old account keeps a tombstone                                                                                                    |
| The organisation leaves          | `POST /organizations/{org}/disable`                                                        | Sign-in refuses; the tenant epoch advances and owned machine tokens are revoked. Global browser sessions and unbound user grants remain                       |
| An app is retired                | `DELETE /clients/{clientId}?confirm={clientId}` after removing its entitlements            | Links, tokens and consents are erased; audit rows remain                                                                                                      |
| A domain no longer belongs here  | `DELETE /organizations/{org}/domains/{domainId}`                                           | Sign-in routing is removed; no confirmation needed                                                                                                            |
| Data must be erased              | `DELETE /users/{userId}` or `DELETE /organizations/{org}` with `?confirm=<id>` and no body | Cascades; audit rows keep erased IDs. Remove owned clients before organisation erasure                                                                        |

**Bulk import of an existing cell's users.** [Not yet.](/docs/id#today-and-next)

## Who may use an app or server

```bash
curl --get https://id.answerable.org/api/admin/v1/entitlements \
  -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "clientId=$CLIENT_ID"

curl --get https://id.answerable.org/api/admin/v1/entitlements \
  -H "Authorization: Bearer $TOKEN" \
  --data-urlencode 'resource=https://tutor.answerable.org'
```

[listAllEntitlements](/docs/id/admin-api/entitlements/listAllEntitlements) lists recorded grants across organisations with each organisation's ID and slug. Filter by `clientId`, `resource` or `status`; paginate with `limit` and `cursor`. These rows are not proof of current effective access: check status and windows, or use the access views above. [User OAuth exchanges](/docs/id/oauth) check current effective access.

## One person's trail

```bash
curl --get https://id.answerable.org/api/admin/v1/users \
  -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "email=$EMAIL"

# Set USER_ID to the returned user's id.
curl "https://id.answerable.org/api/admin/v1/users/$USER_ID/audit-events?outcome=success" \
  -H "Authorization: Bearer $TOKEN"
```

**Find the person.** [listUsers](/docs/id/admin-api/users/listUsers) and `listMembers` accept an exact `email` filter, normalised to lowercase. [listUserAuditEvents](/docs/id/admin-api/audit/listUserAuditEvents) returns events where the person is the actor or the target is their user, membership or session. Filter by `action`, `outcome`, `from` or `to`; use `limit` and `cursor` to page. Omit `outcome` to include every outcome.

## Read the trail

```bash
curl "https://id.answerable.org/api/admin/v1/audit-events?organizationId=$ORG&outcome=denied&from=2026-09-01T00:00:00Z" \
  -H "Authorization: Bearer $TOKEN"
```

Every write, every denied attempt, every sign-in success, rejection and sign-out is a row. Filter by `action`, `actorId`, `targetType`, `targetId` and `outcome` (`success`, `failure`, `denied`); send an `x-request-id` header on writes to find them again.

**Group operation keys.** Set `GROUP_CREATE_KEY` and `GROUP_MEMBER_KEY` once for their respective creation and membership commands, and reuse it with identical input after a lost response. Use a different key for each separate command. Group PATCH requires the current getGroup ETag in If-Match. Membership PUT requires If-None-Match: \* for creation or the getGroupMember ETag in If-Match for replacement. Keep the original precondition when retrying a key.

**Entitlement operation keys.** Set `ORG_ENTITLEMENT_KEY`, `GROUP_ENTITLEMENT_KEY` or `ADMIN_ENTITLEMENT_KEY` once for the corresponding creation command. Reuse that key with identical input after a lost response; use a new key for a separate command. Entitlement create, PATCH, enable, disable and delete all require keys and recover committed responses for seven days. Unchanged scopes/windows or lifecycle state records a noop and preserves timestamps. Scope order and duplicates do not change the command's meaning. PATCH requires the getEntitlement ETag in If-Match. Keep that original precondition when retrying its key.
