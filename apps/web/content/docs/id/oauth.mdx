```bash
curl https://id.answerable.org/.well-known/openid-configuration
```

Use the returned issuer, authorisation endpoint, token endpoint and public signing keys. Both discovery documents describe the supported public routes. Client registration, introspection, device flows and OIDC logout are not public endpoints.

## Prepare access

**Register the application.** Answerable staff register its client ID, redirect URI, authentication method, scopes and `authorization_code` grant. Add `refresh_token` if the application needs renewal. Every authorisation uses S256 PKCE, including confidential clients.

**Choose the authentication method.** Server applications can register `client_secret_basic` (HTTP Basic) or `client_secret_post` (form fields). Creation returns a shared secret once; rotation replaces it. Keep it on the application server. Public browser and native clients register `none`; key-based server clients register `private_key_jwt`. These methods receive no shared secret. A client must use its registered method at the token endpoint: Basic and POST are not interchangeable. See [app registration](/docs/id/onboard#register-what-they-may-use).

**Approve each organisation.** A client-only `authorization_code` capability and assignment approve login identity scopes. Access to a service also requires a capability and assignment for the exact client/resource pair. Renewal needs a separate `refresh_token` capability for the same target: null resource for login-only access, or the exact service URL. Registration and a client/resource compatibility link confer no permission. See [user capabilities](/docs/id/manage#approve-user-capabilities).

**Authenticate the selected organisation.** Membership in two organisations does not establish trust between them. Each requires its own current sign-in, at its directory or by an [email link](/docs/id/magic-links). A person can [connect another independently verified work identity](/docs/id/sign-in#connect-another-work-account) to the same global account. Email never merges identities.

## Start an authorisation

```bash
export ID_URL='https://id.answerable.org'
export CLIENT_ID='your-registered-client'
export REDIRECT_URI='https://your-app.example/callback'
export VERIFIER="$(openssl rand -base64 48 | tr '+/' '-_' | tr -d '=\n')"
export CHALLENGE="$(printf '%s' "$VERIFIER" | openssl dgst -sha256 -binary | openssl base64 -A | tr '+/' '-_' | tr -d '=')"
export STATE="$(openssl rand -hex 24)"
export NONCE="$(openssl rand -hex 24)"

curl --get --include "$ID_URL/auth/oauth2/authorize" \
  --data-urlencode "client_id=$CLIENT_ID" \
  --data-urlencode 'response_type=code' \
  --data-urlencode "redirect_uri=$REDIRECT_URI" \
  --data-urlencode 'scope=openid email offline_access' \
  --data-urlencode "state=$STATE" \
  --data-urlencode "nonce=$NONCE" \
  --data-urlencode 'code_challenge_method=S256' \
  --data-urlencode "code_challenge=$CHALLENGE"
```

Open that authorisation URL in the person's browser. Retain the verifier, state and nonce in the application's own session. Add one `resource` parameter and its registered scopes when requesting service access. Multiple resources require separate authorisations.

The browser signs in, selects an organisation and reviews the application and the access it will receive. These details come from the validated server request. Consent applies to every new authorisation, except an explicitly configured first-party bypass. A flow lasts ten minutes. Completed or denied flows cannot issue another code; start again from the application to change organisation.

**Issued scopes.** ID issues the requested scopes the selected organisation is approved for and drops the rest. The consent page lists them and names what was not approved. The token response `scope` is the issued set. ID refuses with `access_denied` when nothing requested is approved or, with a `resource`, when no service scope is. If the organisation's approval shrinks between consent and code exchange, the exchange returns `invalid_grant`; start again.

**Callback validation.** Check the returned `state` and issuer before exchanging the code. The redirect URI must match the original request. A code is short-lived and single-use.

## Exchange the code

```bash
curl "$ID_URL/auth/oauth2/token" \
  --user "$CLIENT_ID:$CLIENT_SECRET" \
  --data-urlencode 'grant_type=authorization_code' \
  --data-urlencode "code=$CODE" \
  --data-urlencode "code_verifier=$VERIFIER" \
  --data-urlencode "redirect_uri=$REDIRECT_URI"
```

For a service grant, include the same `resource` URL. Public clients use their registered `none` authentication method and send `client_id` without a secret. Registered confidential clients use HTTP Basic, `client_secret_post` or `private_key_jwt`; assertion audiences bind to the particular endpoint and each request requires a fresh assertion.

**ID token.** Returned only when the issued scopes include `openid`. Verify its signature using discovery's keys, issuer, audience and expiry. At code exchange, also verify the original nonce; refresh ID tokens omit it. `sub` is the stable global user UUID. Profile and email claims come from UserInfo under the consented scopes or individual claims request, not from the ID token. Email is display data.

**Access token.** Login-only tokens are opaque and can call UserInfo. Service tokens are JWTs whose audience includes the requested resource. An ID token is not a service access token. Refresh tokens and the immutable authorisation context expire after 30 days, or 7 days for a sign-in by [email link](/docs/id/magic-links); other token expiry comes from provider defaults and configured resource lifetimes.

| Claim                                | Meaning                                                             |
| ------------------------------------ | ------------------------------------------------------------------- |
| `sub`                                | Global user UUID                                                    |
| `subject_type`                       | `user`; machine tokens use `client`                                 |
| `organization_id`                    | Selected organisation UUID                                          |
| `membership_id`                      | Membership authorising this grant                                   |
| `grant_id`                           | Immutable authorisation context shared by refresh rotations         |
| `client_instance`                    | Durable registered client UUID                                      |
| `resource_instance`                  | Durable resource UUID, or null for login-only access                |
| `authorization_version`              | Client authorisation version at issuance                            |
| `organization_authorization_version` | Organisation authorisation version at issuance                      |
| `auth_time`                          | Native ID-token broker authentication time                          |
| `upstream_auth_time`                 | Verified company-provider authentication time, or null when unknown, as for a sign-in by link |
| `authentication_method`              | `directory` or `magic_link`: how the person proved who they are. Absent from a token made before ID said so |
| `groups`                             | The selected organisation's UUID, then the UUIDs of the person's active groups in it, sorted. Absent from a token made before ID said so |

**Groups.** `groups` is on access tokens, ID tokens and in UserInfo, whatever scopes the client asked for. The organisation's own UUID stands for "everyone in the organisation": match it by value, not by its place in the list. The other values are group ids, never names; an administrator reads the names with the [admin API](/docs/id/manage). A group counts only while it is active and the person's membership is in its window. A token keeps the groups of the moment it was issued; a refresh and UserInfo read them again, so UserInfo can show newer groups than an older token.

The broker time does not establish upstream freshness. The five-minute freshness rule applies to sensitive human commands and identity linking, not ordinary application browsing.

**How the person signed in.** `authentication_method` is on access tokens and in UserInfo. `magic_link` means a link or code mailed to their work email, which shows only that they could read that mailbox: no MFA or conditional access of the company directory applied. The application decides what that is enough for. The `POST /auth/oauth2/flow` response in the [API reference](/docs/id/api) has the same value as `authenticationMethod`: ID's own pages read it to decide whether to offer a directory action. A `magic_link` session lasts 24 hours and its grant 7 days: [what a sign-in by email is worth](/docs/id/magic-links#what-a-sign-in-by-email-is-worth).

## Read identity and renew access

```bash
curl "$ID_URL/auth/oauth2/userinfo" \
  -H "Authorization: Bearer $ACCESS_TOKEN"

curl "$ID_URL/auth/oauth2/token" \
  --user "$CLIENT_ID:$CLIENT_SECRET" \
  --data-urlencode 'grant_type=refresh_token' \
  --data-urlencode "refresh_token=$REFRESH_TOKEN"
```

Include the original resource for service renewal. Save the returned replacement refresh token. A narrowed `scope` must fit the current token and original grant. Refresh never regains a scope that the authorisation did not issue or that an earlier refresh dropped; start a new authorisation after approval widens.

Removing `openid` removes the ID token. Removing `offline_access` can return one final replacement refresh token with the narrowed scopes; using that token returns access without another refresh token. Resource scope filtering also applies to identity scopes. Use the response's `scope` and token fields as the issued contract.

Every exchange checks the original authentication tuple, current user/account/provider/membership, client/resource state and permissions. Provider replacement, terminal deletion or administrative grant revocation prevents renewal. Ordinary sign-out preserves delegation; [explicit administrative session revocation](/docs/id/manage#global-session-retries) revokes the affected grants.

**Refresh once.** Each refresh token works once. Reusing a rotated refresh token, including a retry after a lost response or two refreshes sent at once, is treated as replay and revokes the grant; the user must authorise again. Serialise refreshes per grant. A retry window: Not yet.

## Revoke access

```bash
curl "$ID_URL/auth/oauth2/revoke" \
  --user "$CLIENT_ID:$CLIENT_SECRET" \
  --data-urlencode "token=$REFRESH_TOKEN" \
  --data-urlencode 'token_type_hint=refresh_token'
```

Refresh revocation closes that authorisation family. Another authorisation for the same user/client remains independent. Opaque access-token revocation removes that token. Unknown or foreign tokens produce an empty success without changing another client's grants.

**Offline JWTs.** Revocation does not remove an already-issued JWT from a resource server. The server must verify its signature, issuer, audience, expiry, user subject and tenant claims, and enforce its own current-authority contract. Native JWT revocation returns `unsupported_token_type`. Consumer integration and first deployment require separate acceptance; local provider tests do not certify an external application or resource server.

## Configure LibreChat sign-in

**Use confidential POST authentication with S256 PKCE.** LibreChat's OpenID strategy uses `client_secret_post` when supplied with a secret. Register that method in ID and use the exact server origin plus `/oauth/openid/callback` as the redirect URI. The [registration example](/docs/id/onboard#register-what-they-may-use) uses that callback.

| LibreChat setting                 | Value                                                             |
| --------------------------------- | ----------------------------------------------------------------- |
| `OPENID_ISSUER`                   | Exact ID issuer; staging uses `https://id.answerable-staging.uk`  |
| `OPENID_CLIENT_ID`                | Registered client ID for this deployment                          |
| `OPENID_CLIENT_SECRET`            | Secret returned by ID; retain it in the deployment's secret store |
| `DOMAIN_SERVER`                   | Public LibreChat server origin, without a trailing slash          |
| `DOMAIN_CLIENT`                   | Public LibreChat browser origin                                   |
| `OPENID_SESSION_SECRET`           | Deployment-managed random secret, shared by replicas              |
| `OPENID_CALLBACK_URL`             | `/oauth/openid/callback`                                          |
| `OPENID_USE_PKCE`                 | `true`                                                            |
| `OPENID_GENERATE_NONCE`           | `true`                                                            |
| `OPENID_SCOPE`                    | `openid profile email` for login-only access                      |
| `ALLOW_SOCIAL_LOGIN`              | `true` to show federated sign-in                                  |
| `OPENID_BUTTON_LABEL`             | `Continue with Answerable ID`                                     |
| `OPENID_REUSE_TOKENS`             | `false` to use LibreChat's local session                          |
| `OPENID_USE_END_SESSION_ENDPOINT` | `false`; ID publishes no OIDC logout endpoint                     |

Approve and assign the login scopes before testing. Add `offline_access`, a registered refresh grant and its capability only when the application needs ID token renewal and correctly serialises refreshes. Do not set `OPENID_AUDIENCE` for login-only access; it does not send ID's `resource` parameter.

**First sign-in creates the local account.** ID signs the person in through the organisation's company directory. LibreChat must permit OpenID account creation and retain ID's issuer and `sub`; email is not an identity key. Registration in ID does not itself create a LibreChat user.

**Trust and sessions are separate.** An Answerable-operated client can explicitly set `skipConsent` to bypass repeated consent. It still requires capabilities and assignments. Revoking ID access prevents new grants and renewal; LibreChat's existing local session needs its own expiry or revocation control.

**Fork acceptance: [Not yet](/docs/id#today-and-next).** These settings follow the [audited upstream strategy](https://github.com/LibreChat-AI/LibreChat/blob/8d3da9bbb220a0a96be9330a2e1cbd385fb786d5/api/strategies/openidStrategy.js). Complete real-fork sign-in, denial, refresh and session checks before rollout. Provider tests alone do not prove the deployed application.

## Errors

| Error                                           | Meaning                                                                          | What to do                                                                    |
| ----------------------------------------------- | -------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| `invalid_request`                               | Malformed, expired, completed or mismatched request/flow                         | Start a new authorisation from the application                                |
| `invalid_signature`                             | The browser continuation was changed or expired                                  | Restart; preserve the native signed query unchanged                           |
| `login_required`                                | No accepted browser sign-in is available                                         | Sign in through the selected organisation                                     |
| `interaction_required`, `consent_required`      | Silent authorisation cannot complete                                             | Start an interactive browser authorisation                                    |
| `invalid_client`, `client_disabled`             | Client authentication or registration is unavailable                             | Check registration, credentials and assertion audience                        |
| `unauthorized_client`                           | The client cannot use this grant type                                            | Ask Answerable staff to update its registration                               |
| `invalid_redirect`, `unsupported_response_type` | Redirect or response type is not supported                                       | Use the exact registered redirect and `response_type=code`                    |
| `invalid_scope`                                 | A scope is unregistered for the client or resource, or exceeds the refresh token | Request registered scopes; refresh can only narrow                            |
| `invalid_target`                                | Resource is missing, changed, incompatible or repeated                           | Use the single approved resource, or omit it for login-only access            |
| `access_denied`                                 | Consent denied, tenant sign-in or permission insufficient, or no scope approved  | Check the selected company sign-in and assignments                            |
| `invalid_grant`                                 | Code, refresh token, stored authentication or grant authority is no longer valid | Restart authorisation; reused credentials cannot restore it                   |
| `invalid_token`                                 | UserInfo access token is inactive or invalid                                     | Obtain a current access token                                                 |
| `unsupported_token_type`                        | A self-contained JWT cannot be revoked through this endpoint                     | Revoke the refresh family and enforce expiry/current authority at the service |
| `unsupported_grant_type`                        | The requested protocol grant is closed                                           | Use authorisation code, refresh or client credentials                         |
| `temporarily_unavailable`                       | Policy locks, database capacity or required audit storage are unavailable        | Respect `Retry-After`; retry with fresh client authentication                 |
| `authentication_unavailable`                    | An unexpected provider failure occurred                                          | Retry; contact Answerable staff if it persists                                |

Transport limits can return HTTP 408, 413 or plain-text HTTP 503 before OAuth processing. The [API reference](/docs/id/api) describes each reachable endpoint. Successful authorisation, code exchange and revocation persist [audit facts](/docs/id/manage) that target the grant, and record its user, in the same transaction as native effects. A refresh records no audit fact.

For hosted MCP development, use the [shared MCP foundation](/docs/mcp) and its [local browser acceptance test](/docs/mcp/local-testing).
