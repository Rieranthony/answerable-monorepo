## The flow

**Two ways in.** This page is the directory flow. A firm may also sign its people in by an [email link](/docs/id/magic-links). A firm with a directory alone goes straight to it. A firm with both asks which, on a page that redirects nothing. A firm with links alone asks for the address and mails a link and a code. [Sign in by email link](/docs/id/magic-links) covers that side, and what each is worth.

1. The app sends you to `https://id.answerable.org/login?organization=<slug>` or `https://id.answerable.org/login?login_hint=<email>`.
2. The page calls `POST /auth/sign-in/sso` with `organizationSlug` or `email`, plus `callbackURL` and `errorCallbackURL`.
3. Answerable ID returns a `url`. Your browser follows it to Microsoft or Google.
4. The provider returns to `GET /auth/sso/callback`. Answerable ID checks the token and sets a session cookie.
5. The app reads the session from `GET /auth/get-session`.

Answerable's own Google and Microsoft applications carry the redirect to `https://id.answerable.org/auth/sso/callback` when the organisation uses [platform credentials](/docs/id/onboard#connect-the-directory).

## Start sign-in

```bash
curl -i -c cookies.txt \
  -X POST https://id.answerable.org/auth/sign-in/sso \
  -H 'Content-Type: application/json' \
  --data '{"email":"you@company.com","callbackURL":"https://id.answerable.org/login","errorCallbackURL":"https://id.answerable.org/error"}'
```

The response contains the identity provider `url`. The cookie jar keeps the state cookie used when the provider redirects back.

You can send `organizationSlug` instead of `email` when you already know the organisation slug.

## Read the session

```bash
curl -i -b cookies.txt \
  https://id.answerable.org/auth/get-session
```

This reads the session associated with the cookie in `cookies.txt`.

## Sign out

```bash
curl -i -b cookies.txt -c cookies.txt \
  -X POST https://id.answerable.org/auth/sign-out
```

Sign out ends the current session and updates the cookie jar.

## What is checked

| Check                 | Requirement                                               |
| --------------------- | --------------------------------------------------------- |
| Issuer                | The organisation's tenant-scoped issuer                   |
| Microsoft directory   | The Entra `tid` matches the organisation                  |
| Google hosted domain  | The Google `hd` matches the organisation and email domain |
| Email                 | `email_verified` is `true`                                |
| Account type          | A member account, not a guest or personal account         |
| Email domain          | Enabled for the organisation                              |
| Answerable ID account | Active                                                    |

A sign-in by [email link](/docs/id/magic-links) checks different things, at the request and again when it is confirmed:

| Check | Requirement |
| --- | --- |
| Switch | The organisation has links on. The platform organisation never does |
| Who | An effective member, or in `domain` mode anyone at a proved domain |
| Domain | Active, routed to the organisation, and not a public mail provider |
| Account | An active user, not removed, with no account from another organisation's directory |
| Browser | The one that asked: the link and the code are bound to its cookie |
| Time and tries | Not expired, and not out of code tries |

The SSO configuration must stay unchanged from the start of sign-in until the callback completes. Changing the provider row's credentials or changing and then restoring its configuration requires a new sign-in attempt. Rotating a platform secret in the environment leaves rows, revisions and grants unchanged. Replacing a platform client ID interrupts in-flight sign-ins with `invalid_state` and `error_description=sso_provider_changed_during_authentication`, from the SSO plugin's application check; no row revision changes, so `SSO_PROVIDER_CHANGED` does not apply. Saving unchanged configuration does not interrupt sign-in.

## When sign-in is refused

If a configured platform application disappears, `POST /auth/sign-in/sso` returns HTTP `503` JSON with `platform_application_missing`. Start again later and contact Answerable staff. This is an HTTP error, not a `?error=` redirect code.

| HTTP code | Meaning | What to do |
| --- | --- | --- |
| `authentication_unavailable` (500) | The service failed unexpectedly; no session was created. | Start again later. If it repeats, contact Answerable staff. |
| `platform_application_missing` (503) | The organisation’s platform application is unavailable. | Start again later and contact Answerable staff. |

Redirect codes arrive on the error page as `?error=<code>`. The page also shows `error_description` when it is a code of at most 128 letters, digits, `_`, `.`, `:` or `-`, and drops any other text.

| Code                               | Meaning                                                                                                                 | What to do                                                                                                       |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `invalid_state` | The sign-in state no longer matches, for example the platform application changed during sign-in or the state cookie is missing. | Start sign-in again. |
| `provider_not_found`               | No company sign-in was found for the email address.                                                                     | Check the address. Ask your IT team whether your organisation uses Answerable ID.                                |
| `SSO_USER_RESOLUTION_FAILED`       | The service could not safely resolve the verified identity.                                                             | Contact Answerable staff. Operators should check identity records.                                               |
| `SSO_PROVIDER_CHANGED`             | SSO configuration changed during sign-in, or the server could not verify its original configuration.                    | Start sign-in again; no session was created for this attempt.                                                    |
| `authentication_origin_missing`    | Sign-in could not retain its verified company authentication.                                                           | Start sign-in again. If it repeats, contact your administrator; no session was created.                          |
| `authentication_origin_mismatch`   | The verified company account did not match the user selected for the session.                                           | Start sign-in again. If it repeats, contact your administrator; no session was created.                          |
| `invalid_auth_time`                | The signed upstream token supplied an invalid or future authentication time.                                            | Ask your identity-provider administrator to check its `auth_time` claim and clock.                               |
| `reauthentication_required`        | Fresh upstream evidence is missing, too old or predates the requested verification.                                     | Use [verification](#verify-your-sign-in), then retry the original action. No session-time fallback is available. |
| `identity_flow_invalid`            | The verification expired, was already consumed, used another browser session or no longer matches current authority.    | Start again from Account security in the same browser.                                                           |
| `authentication_identity_mismatch` | Reauthentication returned a different upstream identity.                                                                | Start again and choose the same work account.                                                                    |
| `membership_revoked`               | The target membership is revoked, deleted or outside its validity window.                                               | Ask the organisation administrator; linking cannot restore membership.                                           |
| `organization_disabled`            | Sign-in has been paused for your organisation.                                                                          | Ask your IT team for help.                                                                                       |
| `directory_mismatch`               | The account belongs to a different company directory.                                                                   | Use the work account provided by your organisation.                                                              |
| `guest_account`                    | The account is a guest in your organisation's directory.                                                                | Use a member account or ask your IT team for help.                                                               |
| `personal_account`                 | Personal accounts cannot sign in.                                                                                       | Use the account provided by your organisation.                                                                   |
| `email_unverified`                 | The provider has not confirmed the email address.                                                                       | Verify the address with the provider, then try again.                                                            |
| `domain_not_allowed`               | The email domain is not enabled for Answerable ID.                                                                      | Ask your IT team or use another work email.                                                                      |
| `hosted_domain_mismatch`           | The account is managed by a different organisation.                                                                     | Use your company account.                                                                                        |
| `user_disabled`                    | The Answerable ID account is disabled.                                                                                  | Ask your IT team for help.                                                                                       |
| `identity_conflict`                | The company identity is already connected or reserved, including an imported identity. An account of a directory the organisation replaced is also one. | Use its existing sign-in or ask your IT team. Linking never transfers an account. Where links are on, a link still signs the person in. |
| `email_conflict`                   | The email address belongs to another Answerable ID account, including a disabled one, or to an account of a directory the organisation replaced. Signing in never takes it over. | Ask your IT team for help. Answerable staff can free the address by [disabling the previous account](/docs/id/admin-api/users/disableUser) and then [retiring its email](/docs/id/admin-api/users/retireUserEmail); sign in again afterwards. Where links are on, a link still signs a member in. |
| `sign_in_rate_limited`             | Too many sign-in attempts from one client.                                                                              | Wait a few seconds, then try again.                                                                              |

**When the address is a member's own.** If the address belongs to an effective member of the organisation who has no directory account yet, listed by staff or signed in by link, the directory sign-in is not refused with `email_conflict`. ID mails an 8-digit code to that mailbox and asks for it at `/connect-directory` in the same browser. The right code connects the directory to the same user, and the person signs in through the directory again. See [a person with both ways](/docs/id/magic-links#a-person-with-both-ways).

**Unexpected sign-in failure.** HTTP 500 with `code: "authentication_unavailable"` means the authentication handler encountered an unexpected failure. It returns no underlying exception details. Start sign-in again; if it continues to fail, contact Answerable staff. This is an HTTP JSON response, not a redirect error code.

## Sessions

Sessions use cookies. Browser calls from another origin need `credentials: "include"`, and that origin must be trusted by Answerable ID.

**Organisation authority.** Administration requires authentication through that organisation's current SSO configuration, an active account and membership, and the required permissions. Selecting another organisation or holding its membership does not authenticate you there. Answerable staff use platform SSO and explicit platform permissions to manage other organisations. See [browser administration](/docs/id/manage#get-a-token).

**Provider changes.** A directory session can remain open after SSO configuration changes, but its earlier authentication cannot authorise new tenant grants or administration. Sign in again through the current provider. An unchanged configuration save preserves authority. Deleted accounts, users, organisations and memberships cannot regain authority through sign-in.

**Authentication time.** When the provider supplies a valid signed `auth_time`, Answerable ID stores it separately from session creation. An absent claim stays unknown. [Sensitive human commands](/docs/id/manage#fresh-authentication) and identity linking require verified upstream authentication within five minutes. Ordinary browsing keeps the normal session lifetime.

**Sign-in by link.** Its session lasts 24 hours from creation and is never extended, and its grants last 7 days. It carries no `upstream_auth_time`, has no administrator authority, and offers neither **Verify sign-in** nor **Connect another work account**: both need a directory sign-in. Changing, replacing or removing the organisation's directory revokes directory grants only, so a firm's link sessions stand. Turning links off ends link sessions and grants only. A token says which it was in `authentication_method`: [what a sign-in by email is worth](/docs/id/magic-links#what-a-sign-in-by-email-is-worth).

Signing out ends the session.

Applications use [OpenID Connect and OAuth](/docs/id/oauth) with an independently authenticated organisation and per-flow consent.

## Verify your sign-in

```bash
curl -b cookies.txt -c cookies.txt \
  https://id.answerable.org/auth/sso/reauthenticate \
  -H 'Origin: https://id.answerable.org' \
  -H 'Content-Type: application/json' \
  --data '{"callbackURL":"https://id.answerable.org/security","errorCallbackURL":"https://id.answerable.org/security"}'
```

**Browser journey.** Open [Account security](https://id.answerable.org/security) and choose **Verify sign-in**. The API example describes the same request; follow its returned `url` using the browser that holds the initiating session and state cookies. Do not copy only the URL into another browser.

**Upstream proof.** The request uses OIDC `prompt=login` and `max_age=0`. The returned signed `auth_time` must be valid, fresh and at or after the request began. The verified account, user and current provider must match the initiating identity. Missing evidence fails; a newly created broker session does not substitute for upstream authentication.

**Retry.** After verification, return to your action and retry the same input and `Idempotency-Key`. A current account can reauthenticate after its provider configuration revision changes. A deleted or replaced provider binding cannot be adopted by this flow.

## Connect another work account

```bash
curl -b cookies.txt -c cookies.txt \
  https://id.answerable.org/auth/sso/link \
  -H 'Origin: https://id.answerable.org' \
  -H 'Content-Type: application/json' \
  --data '{"providerId":"other-company","callbackURL":"https://id.answerable.org/security","errorCallbackURL":"https://id.answerable.org/security"}'
```

**Directory sessions only.** A session made by an email link is refused here, and Account security shows it neither action: a person who signed in by link and meets a directory proves their mailbox with a code instead ([a person with both ways](/docs/id/magic-links#a-person-with-both-ways)).

**Two proofs.** Verify your current sign-in first. Then use **Connect another work account** on [Account security](https://id.answerable.org/security), entering the provider ID supplied by the target organisation’s administrator. Sign in independently through that provider. Both identities must still be eligible when the callback commits; the initiating evidence must remain within five minutes.

**One Answerable identity.** A previously unowned upstream identity is bound to your existing global user UUID. Your profile stays unchanged. An absent target membership is created; a revoked, deleted or ineffective membership is rejected. Existing permissions are still required to administer the target organisation.

**No transfer or merge.** An owned or imported identity cannot be moved from another user. Matching email addresses establish no ownership. Replays and concurrent competing links cannot create a second binding. Binding, any new membership and the required `identity.linked` audit fact commit in the native session transaction.

**Expiry and errors.** Each purpose expires after five minutes and can be consumed once, in the initiating browser session. A failed callback requires a new start. Rejected initiation and invalid purpose claims return HTTP JSON errors; other callback failures use `?error=` on the supplied error page. See the [error table](#when-sign-in-is-refused). No unlinking, account transfer or generic recovery journey is available.

## Machine access

```bash
curl https://id.answerable.org/auth/oauth2/token \
  --user "$CLIENT_ID:$CLIENT_SECRET" \
  --data-urlencode 'grant_type=client_credentials' \
  --data-urlencode 'resource=https://id.answerable.org/api/admin' \
  --data-urlencode 'scope=org:read'
```

**Machine token.** HTTP Basic authenticates the client. The returned JWT is bound to one resource; it represents the client, not a signed-in user. Ask Answerable staff for credentials and the required grants, then follow [Manage your organisation](/docs/id/manage).

| Code                      | Meaning                                                                                                                                            | What to do                                                                                             |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `unsupported_grant_type`  | The requested grant type is unsupported.                                                                                                           | Use client credentials, authorisation code or refresh; see [user OAuth](/docs/id/oauth).               |
| `unauthorized_client`     | The client is no longer allowed to use this grant.                                                                                                 | Ask staff to review its allowed grant types; do not retry the same request unchanged.                  |
| `invalid_client`          | Client authentication or client eligibility failed.                                                                                                | Check credentials, client status, organisation ownership and the resource link with staff.             |
| `temporarily_unavailable` | A database lock, statement or connection checkout timed out, PostgreSQL aborted a deadlock, or issuance could not write its audit fact (HTTP 503). | Wait at least the `Retry-After` delay, then make a new token request with fresh client authentication. |
| `invalid_scope`           | Requested scopes exceed the client's allowed scopes.                                                                                               | Request only granted scopes or ask staff to review them.                                               |

**Revoked membership.** A valid corporate login still returns `membership_revoked` when that organisation has revoked the membership. An authorised administrator must [reinstate membership](/docs/id/manage#revoke-and-reinstate-membership); signing in again does not restore it or its deleted assignments.

**Transport limits.** Bodies are limited to 256 KiB, except the sign-in pages' forms (4 KiB: `POST /login`, `POST /magic-link`, `POST /magic-link/code` and `POST /connect-directory`) and the sign-in start at `/auth/sign-in/sso` (64 KiB), and must finish within five seconds of application body acquisition. Oversized bodies return 413; stalled bodies return 408. These responses can precede OAuth handling and need not use the OAuth JSON error format. See [request boundaries](/docs/id/manage#request-boundaries).

**Busy authorization state.** The two-second limit applies to each database lock wait during issuance. Database statements also have a configurable server-side deadline, ten seconds by default. Neither is a total transaction or HTTP deadline. A timed-out or deadlocked issuance rolls back before returning `503 temporarily_unavailable` with `Retry-After: 1`. Wait at least one second and use bounded retries with increasing delay. Clients using `private_key_jwt` must generate a new assertion: an authenticated assertion remains consumed even when issuance fails. This is a fresh OAuth request, not administrative operation-key replay.

**Issuance audit.** Every successful machine token request commits an `oauth.token.issued` event before returning the JWT. If that audit write fails, issuance rolls back and returns `503 temporarily_unavailable` with retry guidance. The event records the token's `jti`, identities, granted/requested scopes, configuration revisions and Unix issuance/expiry seconds. It excludes the bearer token, client secret and request metadata. An event proves committed issuance, not delivery to the client or use at a remote resource.

**Rejected requests.** After credentials have been verified, failed validation, authorisation or issuance records an `oauth.token.rejected` event after the issuance transaction exits with an error. Audit storage failure keeps the original rejection and emits an operational error signal. Failed native client authentication writes no event: it is logged as `token_rejected` with the request ID, client address and reason. Transport and body refusals occur before that boundary. See [rejection evidence](/docs/id/manage#read-rejected-machine-requests).

**Retries are new issuances.** Reusing `x-request-id` only correlates attempts. Two successful token requests create distinct token identifiers and audit facts; OAuth token issuance does not use administrative operation-key replay. User OAuth records authorisation, code exchange and revocation separately, and no event for a refresh; see [user OAuth](/docs/id/oauth).

**Network attribution.** ID takes the client address from `cf-connecting-ip`, which Cloudflare sets on every request to Answerable's deployment. When that header is absent, or names an address inside the trusted ingress proxies, ID takes it from `x-forwarded-for` instead, skipping those proxies. That address keys rate limits, session IPs and audit IPs. A request on `/auth/*` or `/api/admin/*` with no resolvable address gets `403 {"error":"untrusted_ingress"}` before authentication. Sign-in success and the session commit together; an audit failure rolls back sign-in. Sign-out retains null IP attribution because historical session addresses have no recorded trust provenance. New and replaced upstream SSO configurations enable PKCE; supplying `pkce` in provider administration requests is a validation error. Re-save any existing configuration that disabled PKCE.

**Failure evidence.** A refused callback writes no audit event: the log line `signin_rejected` keeps a known failure code for diagnosis; unknown error strings become `sso_callback_failed`, and free-form error descriptions are never logged. This does not change the browser redirect. New session and sign-in/sign-out user-agent metadata accepts 1–512 printable ASCII characters; other values are omitted. Existing session values are checked again before they enter new audit events.
