Every page of these docs is Markdown for agents, with the type tables and the code from the repository written out. The prompts below give a coding agent, such as Claude Code, a job, the pages to read, the commands to run and the proof that it is done. Replace the words in angle brackets. Every MCP gets a database and its sign-in through Answerable ID without any work, so no prompt asks for either.

## Make an MCP

```text
In the Answerable monorepo, make an MCP named <name> that <what it does>, with bun mcp.

Read first: AGENTS.md, then https://www.answerable.org/docs/mcp/create.md and https://www.answerable.org/docs/mcp/database.md. mcps/example is a finished MCP made with the same commands.

1. Run `bun mcp new <name> --description "<what it is for, 40 to 1,000 characters>" --serve toolbox`. Use --serve standalone only when it needs its own URL, and say why.
2. Run `bun mcp check <name>` and commit every file bun mcp wrote or rewrote, as "What to commit" in create.md lists them; git status shows them. Never edit a *.generated.* file or charts/answerable/mcps.json by hand.
3. Run `bun mcp list` and check that <name> is listed with its URLs. It has no tool until you add one, as the next prompt does, unless step 1 named one with --tool.

Its database and its sign-in through Answerable ID are made for you. Do not add a Better Auth instance, a database connection or a login, and do not read Answerable ID's database. Never run `bun run env:up` from a worktree.

Proof: the output of `bun mcp check <name>` (it passes, with 100% coverage) and the line `bun mcp list` prints for <name>.
```

The guide it follows: [Make an MCP](/docs/mcp/create); what to commit: [What to commit](/docs/mcp/create#what-to-commit).

## Add a tool

```text
In the Answerable monorepo, add the tool <domain.operation> to the MCP <name>: <what the caller can do with it>.

Read first: AGENTS.md and https://www.answerable.org/docs/mcp/add-a-tool.md.

1. Run `bun mcp add tool <name> <domain.operation> --description "<what it does, when to use it, its limits>"`. For a change, add `--mutation` and say "prepare" in the description. Name the tool for what the caller can do, never for the vendor.
2. Change the generated file into the real tool: its input, its output, and its table in mcps/<name>/src/db/schema.ts. Every table keeps organisation_id and its organisationIsolation policy. Queries on those tables need no organisation filter, since Postgres adds it; data from anywhere else is constrained by organisation.id. prepare returns a preview and changes nothing; commit applies exactly that. Throw ToolError for expected failures.
3. After a change to the schema, run `bun mcp db <name> generate`, review the migration and commit it. Never edit, regenerate or remove a migration that was applied.
4. Keep the tool's test proving that each organisation sees only its own rows.
5. Run `bun mcp check <name>` until it passes, and commit what its Next: line lists.

Proof: the output of `bun mcp check <name>`, the migration file, and the tool's manifest entry in mcps/<name>/manifest.json.
```

The guide it follows: [Add a tool](/docs/mcp/add-a-tool).

## Ship an MCP

```text
Prepare mcps/<name> to ship to staging, then production, and tell me the commands. Do not tag, do not push to main and do not deploy: only the owner does.

Read first: AGENTS.md, https://www.answerable.org/docs/mcp/deploy.md and https://www.answerable.org/docs/mcp/sign-in.md.

1. Run `bun mcp check <name>`. It must pass and leave nothing to commit.
2. On a branch, commit every file that "What to commit" in https://www.answerable.org/docs/mcp/create.md lists. If a tool's kind, risk, input or output changed since the last staging tag, check that its version changed too: "Change a tool after it ships" in https://www.answerable.org/docs/mcp/add-a-tool.md.
3. Tell me: the branch and its last commit; the two tag names, `staging/<name>-<change>` and `production/<name>-<change>`, in lowercase letters, digits and hyphens with one slash; the URLs `bun mcp list` prints for staging and production; and the two steps staff take in the admin MCP once it has shipped. For an MCP in the Toolbox: toolbox_enable, then access_grant. For one on its own URL: standalone_enable, then access_grant with clientId claude-code-<name>.

Proof: the branch, the commit hash, the output of `bun mcp check <name>` and `bun mcp list`, and the two tag names.
```

The guide it follows: [Ship an MCP](/docs/mcp/deploy), whose [hand-over](/docs/mcp/deploy#before-you-tag) the owner expects; what to commit: [What to commit](/docs/mcp/create#what-to-commit).

## Review a server against the standard

```text
Review mcps/<name> against the Answerable MCP design standard.

Read first: https://www.answerable.org/docs/mcp/standard.md and https://www.answerable.org/docs/mcp/tools.md.

Run `bun mcp check <name>`: the conformance kit checks the rules marked Kit and SDK. Then, for each rule marked Review, say whether the server meets it, with the file and line that shows it, and what to change if it does not. Change no code.
```

The rules it checks: [MCP design standard](/docs/mcp/standard).

## How agents read these docs

| Ask for | You get |
| --- | --- |
| `https://www.answerable.org/docs/<page>.md` | One page as Markdown |
| Any docs URL with `Accept: text/markdown` | The same, at the page's own URL |
| `https://www.answerable.org/llms.txt` | Where to start, then an index of every page with its description |
| `https://www.answerable.org/llms-full.txt` | Every page in one file: 2.1 MB, most of it the API reference's operations |

**Give an agent the page for its job**, not the whole set: the pages above link to the ones they need. Each page on the site has **Copy Markdown** and **View as Markdown** buttons under its title.

**The repository has its own rules.** `AGENTS.md` at the root holds the commands, the ports, the gates and what never to do, and `CLAUDE.md` loads it for Claude Code. An agent working in the repository reads it first.

**The Markdown is generated from the source.** Type tables come from the TypeScript types and their doc comments, and code comes from files that are typechecked and tested, so an agent reads what the code does today.
