# Answerable ID

Identity and authorization service for Answerable. The schema, organisation sign-in, machine access and administrative read and write routes are implemented.

## HTTP surface

- Better Auth: `/auth/*` behind an explicit allowlist: `GET /auth/ok`, `POST /auth/sign-in/sso`, `GET /auth/sso/callback`, `GET /auth/get-session`, and `POST /auth/sign-out`; it also exposes `POST /auth/oauth2/token` for `client_credentials` only. Every SSO administration/SAML route and every other OAuth-provider route remains unreachable until a later milestone. The provider's admin endpoints also require a session and privilege hooks that deny by default; client administration uses the admin API
- Admin API: `/api/admin/v1` — caller, organisations, domains, SSO provider, users, sessions, members, groups and group members, clients and their owners/resource links, resources, entitlements, access views and audit events
- Public OpenAPI contract: `/openapi.json` — the reachable routes only; snapshot: `apps/id/openapi.json`
- Admin OpenAPI: `/api/admin/openapi.json` — snapshot: `apps/id/openapi.admin.json`; regenerate both snapshots with `bun run openapi:export`
- Admin docs: `/api/admin/docs` in development and test only
- Liveness: `/healthz` (no database query)
- Readiness: `/readyz` (one `select 1`)

Production uses `https://id.answerable.org` as `BETTER_AUTH_URL`; Better Auth's separate `basePath` is `/auth`. Local development keeps `BETTER_AUTH_URL=http://localhost:47300`.

`src/env.ts` validates `Bun.env` once during startup and returns a typed configuration object. `DATABASE_URL`, `BETTER_AUTH_URL`, and `BETTER_AUTH_SECRET` are required and produce a named startup error when absent. `BETTER_AUTH_TRUSTED_ORIGINS` is a comma-separated browser/IdP origin allowlist (defaults to `AUTH_PAGES_URL` when unset), and `AUTH_PAGES_URL` is the absolute login/consent-page origin (default `http://localhost:47100`). Runtime settings such as `PORT` and pool limits declare their defaults in the same schema; see [`.env.example`](../../.env.example).

**Request admission.** `MAX_CONCURRENT_REQUESTS` bounds active handlers per application instance (one per service process), default 64; it must be a positive safe integer. Admission includes body acquisition, authentication and handler work. Excess requests are not queued: they receive plain-text `503 Service Busy`, `Retry-After: 1`, `Cache-Control: no-store` and a request ID before authentication or database work. Rejected bodies are cancelled without waiting for cancellation cleanup. Only bodyless GET/HEAD `/healthz` bypasses the limit; readiness participates and may report overload. Do not use liveness as an overload signal.

**Public authentication admission.** `/auth/*` requests now share a pre-body, pre-credential concurrency bound across app and Drizzle wrappers using the same PostgreSQL pool. The bound is `max(1, actual pool maximum − 1)`: a pool with at least two connections admits fewer authentication requests than its connection count. A one-connection pool still accepts one authentication request. This counts handlers, not individual connection checkouts. Excess requests receive the existing plain-text `503 Service Busy`, `Retry-After: 1`, `Cache-Control: no-store` and request ID; their body is cancelled and the provider is not called. Capacity remains held until the handler and its audit work finish, including after disconnect. Admitted token failures retain their usual rejection audit; requests refused before authentication create no token-attempt event. This does not identify a tenant from an unverified claim, allocate a dedicated database connection, bound admin-route authentication or provide cluster-wide rate limits. Other work can still consume shared connections; legitimate authentication can be refused when this lane is occupied.

**Shared machine issuance admission.** After client authentication and current identity/policy locks, the token endpoint admits at most two concurrent machine issuance transactions per immutable owner organisation across instances using the same PostgreSQL database. All that organisation's clients share the two slots. A full tenant receives OAuth JSON `503 temporarily_unavailable` with `Retry-After: 1`; rejected issuance records its authenticated client/tenant through the existing failure-audit path. Retry with fresh client authentication, including a new assertion where applicable. Slots cover policy evaluation, signing and successful audit commit and release with the transaction. The fixed limit avoids configuration drift between replicas; all replicas must run the enforcing version before claiming the deployment-wide bound. Two is an initial conservative limit, not a benchmark-derived capacity target. This adds no queue or lease table. It does not bound authentication queries, policy-lock waits, connection checkout, failure-audit work, administrative/user flows or unauthenticated rates; it does not establish overall tenant fairness.

A slot is released when the handler finishes, including errors. Disconnecting a client does not free capacity while its handler continues. Retry with backoff; keep the same idempotency key and input for an administrative command. This early transport refusal can precede CORS headers. It is not a per-tenant/IP rate limit, cross-replica quota, TCP connection limit, total request deadline or bound on future streaming-response lifetime. Tune the default using production capacity evidence; the implementation does not claim that 64 is a measured optimum.

## Commands

From the repository root:

```bash
bun install
docker compose up -d --wait postgres
bun --filter @answerable/id db:test:migrate
bun --filter @answerable/id typecheck
bun --filter @answerable/id lint
bun --filter @answerable/id build
bun --filter @answerable/id test
```

**Existing installations.** Migration 0007 does not infer platform identity from existing names. After reviewing the intended IDs, run from `apps/id` with the deployment environment loaded:

```bash
bun scripts/bind-system.ts "$PLATFORM_ORGANIZATION_ID" "$ADMIN_RESOURCE_ID" "$PLATFORM_ADMINS_GROUP_ID"
```

The resource argument is its row UUID, not its URL. The command validates group ownership and the configured admin audience, audits the binding, and permits only identical repeats. A conflicting binding returns `system_binding_conflict`. Start the service after this succeeds.

**First run.** Set `ROOT_ADMIN_SECRET`, the dedicated `OPERATION_REPLAY_CONFIG` keys and `UPSTREAM_TOKEN_SECRETS` described below, start the service (the platform organisation, admin resource and admin group are seeded and bound by immutable IDs at boot), then with the root bearer add the platform domain and SSO provider, sign in once, and add yourself to the `platform-admins` group; root locks itself afterwards.

**Upstream token storage.** `UPSTREAM_TOKEN_SECRETS` is a JSON array such as `[{"version":1,"value":"<canonical-base64url-encoded random 32-byte key>"}]`. Versions are distinct positive integers; the first key encrypts new values and all listed keys can decrypt their own versions. Keep these keys outside PostgreSQL and separate from authentication/signing and operation-replay secrets. Invalid supplied configuration stops environment loading without echoing values. The provider's supported account transforms encrypt access, refresh and ID tokens; the provider's separate access/refresh flag stays disabled to avoid double encryption. Missing keys, plaintext, unversioned legacy encryption and damaged ciphertext are refused. Null imported credentials remain valid. A missing key during native SSO produces safe `500 authentication_unavailable` and rolls back that attempt's identity/session writes.

**Rotation and cutover.** First distribute a new key to every instance while leaving the old version first; only then promote the new version to first. Never reuse a version number for different key material. Retain old keys until every surviving token field and required backup can be read without them. Migration 0037 retires all pre-cutover stored upstream credentials and their expiry fields once, regardless of their old format. It preserves account bindings, memberships, browser sessions and Answerable-issued grants. Fresh SSO stores encrypted replacements. Each changed account gets an atomic audit fact with presence flags and durable account/user UUID attribution; no credential values enter the audit. Run through the migration runner, never by replaying its SQL after new logins. The migration receipt prevents a completed cutover clearing new credentials.

**Cutover gates.** Before deployment, confirm no external consumer needs these stored upstream credentials, stop old writers, provision the dedicated keys, and rehearse backup/restore and the migration at representative volume. The migration locks account writers and completes in one transaction; it is not a bounded batch job. Local tests prove rollback, process interruption, replay and fresh SSO, not production lock duration or backup recovery. Clearing local copies does not revoke tokens at the upstream IdP or sanitise old backups. Reopen login only after these gates pass. Retain required backup keys. See the [custody contract](../../reports/answerable-id-upstream-token-custody.md).

`db:generate` generates migrations in `apps/id/drizzle` without a database connection. `db:migrate` applies committed migrations to `DATABASE_MIGRATION_URL`. `db:test:migrate` drops the `public` and `drizzle` schemas, recreates `public`, and applies the committed migrations, so the catalog contract test guards them. Both safety gates refuse any database whose name is not exactly `answerable_id_test`; data in that explicitly disposable database is not recoverable after a run.

**Disposable restore rehearsal.** With local Compose PostgreSQL running and the test schema migrated, run `bun --filter @answerable/id test:restore` from the repository root. Run it separately from database tests and local test processes. It creates synthetic fixtures in `answerable_id_test`, verifies that Compose and the application see the same fixture UUID, and takes a PostgreSQL custom-format dump. It refuses non-local/default-port source targets.

Restore runs in a new temporary cluster using the source container's exact local image ID, with no image pull, persistent data volume or public listener. The target uses a temporary filesystem and random loopback port. The proof checks a different PostgreSQL system identifier, rebuilds the missing runtime role/permissions using the production provisioner, and requires newly supplied login credentials. It restores encrypted tokens, sessions, migration receipts, real command responses and audit subjects. Missing keys fail safely, purged responses cannot rerun a command, and revoked tenant B stays blocked while A can sign in. Keys remain separate from the archive. Signing recovery independently verifies pre-backup and new machine tokens with the original public key; the retained application secret resumes signing without replacing keys. Wrong application-secret custody returns `500 authentication_unavailable` without a successful issuance fact. This does not test managed key rotation or production secret delivery. A newly provisioned retention login is checked against restored data: direct payload reads, reservation deletion and forged audit writes are refused; an audit failure rolls back purging; bounded expiry cleanup preserves fresh responses and permanent reservations. The rehearsal also starts the actual production-mode runtime in child processes: the owner login is refused before listening; two restricted-login starts preserve platform bindings, revisions and capability ceilings, serve health/readiness and recover the restored browser session. This uses supplied configuration and a loopback listener, not production ingress or environment distribution.

CI runs this after coverage. The temporary cluster/archive and source live identities/runtime role are removed on normal completion or handled failure. Permanent test audit, operation and identifier records remain until the disposable schema is reset. It is a local recovery proof, not a production restore procedure: remote backup storage, production maintenance scheduling/signing-key custody, post-snapshot revocation/replay reconciliation, capacity and recovery objectives still need rehearsal. See the [restore evidence](../../reports/answerable-id-upstream-token-custody.md#populated-postgresql-restore-proof).

Coverage thresholds require 100% of application lines and functions. Tests, fixtures, generated output, and the composition-only `src/server.ts` process entry are excluded; its runtime behavior lives in the fully tested `src/runtime.ts`.

## Database roles

Run migrations and permission provisioning with a separate schema-owner connection. From `apps/id`, with `DATABASE_MIGRATION_URL` loaded:

```bash
bun scripts/migrate.ts
bun scripts/configure-runtime-role.ts answerable_id_runtime
```

The provisioner creates a role without login credentials, or validates an existing unprivileged role, and configures its permissions transactionally. Enable LOGIN on that role itself and supply its password through deployment tooling. Set the application's `DATABASE_URL` to this runtime login. Do not pass the migration credentials to the application. Rerun permission provisioning after migrations add tables.

The runtime can read and write ordinary application tables, insert audit events and create the initial system binding. It cannot update/delete audit events, write audit subjects or identifier reservations directly, alter the system binding or completed operation reservations, truncate tables or create public-schema objects. Owner-executed triggers capture subjects and reserve identifiers atomically; direct invocation of the subject-capture function is revoked.

Production startup checks role attributes, memberships, ownership and protected-object permissions before bootstrap or listening. An unsafe role fails startup and closes the pool. Auth/app construction or listen failures also close that pool before propagating the startup error. Development retains the owner connection in `.env.example` for local setup. These permissions restrict the application credential; database owners and backup administrators remain trusted. Targeted tenant RLS and the separate bounded retention function are implemented; broader isolation, production scheduling and release proof remain governed by the foundation plan.

## Application-secret rotation

`BETTER_AUTH_SECRET` remains required as the legacy decryption secret. Optional `BETTER_AUTH_SECRETS` uses the provider's native comma-separated `version:secret` format: the first entry is active and remaining entries decrypt retained versions. Versions must be distinct non-negative safe integers; every secret must contain at least 32 characters. Generate independent high-entropy values. Invalid configuration fails without printing values. Keep these secrets separate from `UPSTREAM_TOKEN_SECRETS` and `OPERATION_REPLAY_CONFIG`.

For an existing installation, stage a ring whose first entry has the existing secret value, retaining the new secret as a later entry. After all instances have the staged configuration, coordinate promotion of the new first entry. **Promotion requires users to sign in again:** Better Auth 1.7.2 verifies ordinary browser cookies with the active secret only. Drain in-flight authentication callbacks and avoid serving different active versions across replicas. This is not seamless rolling session rotation. Changing configuration does not delete the stored sessions or revoke already-issued JWTs.

Keep the original singular secret while legacy ciphertext remains. Adding the ring does not rewrite existing private keys. Newly generated signing keys use versioned encryption; previous keys remain readable with retained versions. Do not remove a version until all dependent ciphertext and retained backups have been accounted for. Removing a required version fails signing rather than replacing its key. Legacy-secret retirement, automatic rewrapping, emergency signing-key rotation, production secret delivery and recovery of post-snapshot changes remain separate release work.

The integration test proves staged cookie continuity, cookie refusal after promotion, fresh native SSO accepted only by the promoted active version, legacy signing continuity, provider-generated versioned keys after simulated expiry, retained-version signing and refusal when that version is removed. The server-only signing API used in this proof does not open a public JWT endpoint. See [the custody evidence](../../reports/answerable-id-upstream-token-custody.md#application-secret-rotation).

## Replay keys and retention

`OPERATION_REPLAY_CONFIG` is a JSON object with `activeKeyId` and `keys`, a map from key IDs to canonical base64url-encoded random 32-byte keys. Supply it through deployment secret storage, independently of `BETTER_AUTH_SECRET`. It is required for every administrative mutation; without it these routes return 503 before changing state. Invalid configuration stops environment loading without echoing key values. New results use the active key; retain prior keys until their live replay windows have closed. Backups and key retirement need their own retention policy.

Provision the maintenance role using `DATABASE_MIGRATION_URL`, from `apps/id`:

```bash
bun scripts/configure-retention-role.ts answerable_id_retention
```

Enable LOGIN on the retention role and provision credentials separately. Give only the maintenance process its `DATABASE_RETENTION_URL`. It has no table read/write privileges; it can invoke the fixed purge function. The application runtime cannot invoke that function.

```bash
bun scripts/purge-operation-results.ts
```

Each invocation deletes at most 1,000 expired ciphertext rows, using database time and skipping rows another purge holds. It records the removed operation IDs and count atomically in `operation.results_purged`. Audit failure restores the deleted ciphertext. Empty runs make no audit event. Permanent operation reservations are never removed, so a purged result cannot cause a command to run again.

Schedule this command in deployment operations, and repeat when a batch reaches 1,000. Physical deletion occurs when the job runs; the replay deadline is enforced independently. No production schedule has been installed by this change. Reapply role provisioning after migrations. Do not give runtime processes the migration or retention credentials.

## Boundaries

**Machine identity.** Token requests require exactly one `resource`. Issuance requires an owned client in an active organisation and binds `client_instance`, `organization_id`, `authorization_version`, `organization_authorization_version` and `subject_type=client` into the JWT. The admin verifier requires these claims and compares them with current client state. The same query requires a current link to the enabled admin resource; effective scopes are intersected with that resource's current ceiling and an effective machine capability for the exact owner/client/resource. Tokens issued before this change must be reissued. Database triggers advance the client version on client disable and changes to the secret digest, JWK set, JWK URL or authentication method; re-enable does not restore old tokens. Offline resource servers cannot observe version changes until they perform an online check or the token expires. Resource custom claims cannot override these five identity fields.

**Ownership.** Set the client owner when creating it. The owner-write route only accepts the existing owner; changing, attaching or detaching an owner returns `409 ownership_conflict`. Create a replacement client for another owner. Database triggers also reject changes to client instance, public identifier or owner, including ownership adoption of an unowned client. Resource instance and public identifier are immutable too. The `security_identifiers` table permanently reserves client/resource public identifiers and instance UUIDs. Erasure retains these records; attempted reuse returns `409 identifier_reserved`. Reservations contain no credentials and cannot be updated or deleted by ordinary writes.

**Platform authority.** `system_bindings` identifies the platform organisation, admin resource and group. Authorisation, root lockout and summaries use the binding; slugs are descriptive after initial creation. `/me` grants include `isPlatform`, derived from the database binding. Bootstrap refuses unrelated existing names, and the database prevents changing/deleting the binding or its referenced records.

**Audit history.** Audit events retain tenant UUIDs after erasure. Subject references capture person links at insertion, allowing authorised history reads after membership or user deletion. Legacy derivation is labelled and cannot recover missing evidence. The production runtime role cannot update, delete or truncate retained audit records. Audit responses include schemaVersion (0 for pre-migration events, 1 for original payloads, 2 for machine issuance decision snapshots and bounded callback rejection categories) and a nullable operationId. Client creation/rotation events link to their committed operations; platform and organisation history can filter by operationId. Client creation/update snapshots omit raw JWK configuration and credentials, and rotation records its actual version change. Full effect manifests and other event payloads remain unfinished.

**Operation journal.** The internal `executeOperation` primitive commits local effects, audit writes and an immutable result reference together. Identical retries recover the reference after a fresh authority check; concurrent execution and changed-input reuse have distinct retry classifications. Client creation and secret rotation now require Idempotency-Key and recover their original responses for 24 hours. Client configuration patches require both Idempotency-Key and the strong If-Match ETag from getClient; they recover ordinary responses for seven days. Disable, enable, owner verification, resource linking/unlinking and erasure also require keys, with seven-day recovery. Every client mutation rechecks current authority inside the journal transaction. Resource create/patch/enable/disable/erase commands also require keys and recover for seven days; resource PATCH requires If-Match. Member update/removal/reinstatement use tenant-scoped keys and seven-day recovery. Domain and organisation creation/configuration/lifecycle/deletion also require keys with seven-day recovery under platform authority. Organisation PATCH requires the If-Match ETag from getOrganization. SSO PUT/delete and all seven group mutations also use the platform journal. Remaining route families do not use it yet. Operation-status GET routes expose only references to the original tenant actor or a platform reader. The journal can now encrypt and recover response JSON with dedicated versioned keys: at most 24 hours for secret responses and seven days for ordinary responses. Expiry or payload loss returns `operation_result_expired` and never repeats the effect. `OPERATION_REPLAY_CONFIG` validates dedicated deployment keys, and a restricted maintenance role can purge expired ciphertext with an atomic audit record. Remaining route integration, production scheduling/key provisioning and revision preconditions on other configuration remain unfinished.

**Foundation status.** The provider transaction seam, database identity guards and machine identity regressions are implemented. The 49 administrative mutations use operation recovery. Machine capability ceilings are enforced; tenant-bound user grants, complete user ceiling policy and complete audit/operational proof remain work in [the foundation specification](../../docs/05-id-enterprise-foundation.md). Passing token tests does not establish those guarantees.

Admin route families export their route table; `src/__tests__/admin-routes.ts` generates the negative suite for every table entry, while `src/http/admin/routes.test.ts` compares the tables to the OpenAPI document.

`src/db/client.ts` owns the one process-wide pool and Drizzle construction. Database operations live in `src/db/queries`, grouped by domain. Vocabularies live once in `src/db/schema/vocabulary.ts`, and `src/db/schema/columns.ts` carries the identifier, timestamp, and CHECK conventions. The integration test freezes the PostgreSQL catalog, so a schema change is a deliberate edit to that snapshot. HTTP routes receive `db`, `auth`, and request metadata through typed Hono context. Administrative routes call services, and services call these query modules—routes never contain Drizzle or SQL.

The default pool maximum is five connections per process and one in tests. Timeouts and the maximum are configurable through the environment. Session resolution remains route-scoped; liveness and public metadata do not resolve a session.

See [`../../docs/04-answerable-id-schema.md`](../../docs/04-answerable-id-schema.md) for the schema contract.

**Client revisions.** Migration 0014 adds a server-controlled positive revision. The database advances it on changed client rows and resource links, through explicit link removal. Reads hold the client row while reading links. PATCH rejects a missing If-Match with 428, an invalid tag with 400, and a new stale command with 412. Identical committed retries recover before checking their old revision. Unchanged patches write a `client.update_unchanged` audit event and a `noop` operation without changing the row or timestamp. ETags identify both the immutable client instance and revision; resource links are returned in stable order.

**Client lifecycle retries.** Enable/disable and link/unlink commands record a noop when the requested state already holds, keeping the existing client revision and timestamp. Owner verification remains immutable and records a noop. Replaying an old command returns its original result without reversing a later command. Erasure and unlink responses remain bodyless 204 on replay, including after client deletion; a new erasure key against a missing client returns 404. Creation and rotation keep the shorter 24-hour secret recovery window. Lifecycle audits now retain tenant/operation attribution and selected before/after evidence; complete token and deletion effect manifests remain unfinished.

**Resource revisions and recovery.** Migration 0015 reuses the database revision guard for resources and extends the link trigger to update both endpoint revisions. Resource GET holds a shared row lock while reading sorted clients. Resource PATCH requires its If-Match tag, skips unchanged writes, and recovers committed results before checking old revisions. Every resource mutation requires Idempotency-Key with seven-day recovery, including erasure after the live row is gone. Enable/disable noops preserve timestamps and revisions; admin-resource protection still applies. The configuration revision is separate from the existing policyVersion field; complete issuance policy versioning and common grant/revocation ordering remain unfinished.

**Membership admission.** Migration 0016 retains removed memberships as `revoked`, with the same immutable member/user/organisation IDs and a revocation time. Effective access checks reject revoked rows regardless of validity windows. Removal deletes only that membership's direct grants and group assignments, recording pre-removal effective access and the removed rows atomically with the revocation. Valid SSO cannot re-enrol that same membership, including imported identities; sign-in diagnostics reports membership_revoked too. `POST /api/admin/v1/organizations/{organizationId}/members/{memberId}/reinstate` explicitly activates it, preserving its window but not restoring assignments. Replay for other tenant mutation families, tenant grant/session isolation and the common concurrent issuance protocol remain unfinished.

Existing deleted memberships cannot be inferred by this migration. Review historical offboarding and reconstruct required admission denials before cutover. Global user/organisation erasure still cascades memberships; a later identity enrolment is a new identity unless an explicitly retained admission block says otherwise.

**Organisation disable and machine epochs.** Migration 0017 adds the positive, monotonic `organizations.authorization_version`. Active-to-disabled transitions advance it; re-enable retains it. Machine JWTs bind this as `organization_authorization_version`, checked against current owner state by the admin verifier and command authority. Older JWTs without the claim must be reissued. Organisation disable revokes stored machine access-token rows for owned clients and records their IDs with the before/after epoch in the same transaction. It preserves global browser sessions and unbound user grants: an app's owner is not proof of a user's tenant. Complete user grant contexts, tenant session routes and issuance/revocation ordering remain unfinished. External offline verifiers still require token expiry or an online invalidation mechanism.

**Global browser session boundary.** The member-session GET/DELETE aliases have been removed and return 404. They previously exposed/revoked global user sessions through tenant authority. Organisation summaries also omit global session counts. Global session administration remains on platform-only `/users/{userId}/sessions`; tenant tools must not substitute that route. Tenant offboarding uses membership revocation. Tenant grant/delegation views are not yet implemented and require verified tenant-bound grant contexts before user OAuth opens.

**Machine lifecycle ordering.** `auth/database-adapter.ts` wraps the supported Drizzle adapter transaction method and exposes only its active SQL transaction to policy code. The map entry is removed on commit or rollback. Before the provider reads policy, issuance takes shared locks in organisation-then-client-then-resource order and rereads current client configuration after checking its authenticated identity/version. Organisation/client disable therefore either commits first and denies issuance, or waits for issuance to commit and advances the relevant authorization version. Re-enable still cannot revive the JWT. These JWTs are stateless; do not expect a stored access-token row for every issuance. Tests observe PostgreSQL blocker relationships, concurrent shared readers, rollback and transaction-handle expiry. Locks currently span local signing and commit; production latency/load measurement, administrative wait bounds and the complete capability/assignment ordering protocol remain release work.

**Bounded issuance lock waits.** The machine provider sets transaction-local `lock_timeout = '2s'` before issuance. A PostgreSQL lock timeout rolls back and becomes OAuth `503 temporarily_unavailable` with `Retry-After: 1`; other errors retain their existing handling. The setting covers each lock wait and is not a total request/signing/pool deadline. Clients should wait at least the indicated delay and use bounded backoff; private_key_jwt retries require new assertions because authentication occurs before the rolled-back issuance transaction. Tests hold an organisation lock, verify rollback and successful retry, and inspect every pool connection after rollback and commit. Administrative lock waits and the remaining common writer protocol are still unfinished.

**Resource policy ordering and erasure.** Machine issuance locks the resource before the provider reads its scope ceiling, lifetime or other policy fields. Client configuration is refreshed through the supported adapter under the client lock; a pre-authentication scope snapshot cannot bypass a later committed restriction. Tests observe blocked resource writers, verify scope denial and a new lifetime on later tokens, and order unlinking against issuance. Migration 0018 changes the resource-link FK to ON DELETE RESTRICT. Resource erasure requires explicit unlinking (`409 resource_has_clients`) and never cascades into client revision updates, avoiding the reverse resource-to-client lock order. The indexed existence check reads at most one link. Existing links survive migration; client deletion still removes its own links. Capability policy versions, all assignment writers, user grant contexts and production load measurement remain unfinished.

**Machine issuance audit.** After provider signing and before the transaction commits, `recordMachineIssuance` writes `oauth.token.issued` with the token jti as target. Evidence includes immutable tenant/client/resource identities, configuration revisions, current scope ceilings, requested/granted scopes, client/organisation authorization versions and Unix issuance/expiry seconds. Only allowlisted fields from our newly produced JWT and locked rows are copied; decoding is not used to authenticate client input. Raw JWTs, secrets, request metadata and forwarded IP claims are excluded. Audit-write failure rolls back issuance and returns OAuth 503 temporarily_unavailable with Retry-After: 1. Tests prove rollback of an extension write, no returned token on failure, distinct audit facts for repeated correlation IDs, and insertion by the restricted runtime login. The event proves committed issuance, not HTTP delivery or remote use. Rejected grants, capability/assignment decision evidence, user grants and issuance monitoring remain unfinished.

**Member command authority.** HTTP member update, removal and reinstatement now enter a transaction-scoped tenant member context. They lock the target organisation, then recheck current session/user or machine identity and the required platform:users or target-tenant org:users scope before applying the service mutation and audit write. A membership revoked after middleware admission cannot authorise the pending member write. Platform client/resource commands retain platform:write. The three member write services require this context directly; a private runtime registry rejects copied contexts and the command wrapper expires the context after callback success or failure. Services reuse the organisation lock held by the context factory. Member list/detail and configuration reads also require scoped contexts, acquire a shared organisation lock and recheck current authority inside their read transaction. Directory contexts require platform:read or org:read; configuration contexts require platform:users or org:users and cannot be used to read profile data or mutate membership. Read callbacks expire their contexts before the transaction completes, and HTTP responses use no-store. Member-access and target-access services now use the same read transaction boundary. Member access preserves platform:read or org:users; target access uses the directory permission. The member-access existence check reads only membership configuration. Other tenant services and query functions still accept explicit organisation IDs; complete TenantContext adoption, platform-authority/client-resource writer ordering and bounded waits remain pending. The context factory must run inside the operation transaction, with its mutation callback managed by the context wrapper.

**Tenant directory reads.** Organisation detail/summary, redacted SSO provider reads, group list/detail, group member list/detail, domain listing and tenant entitlement list/detail now require the same validated directory context (platform:read or org:read). Their HTTP handlers recheck current authority inside a shared-lock read transaction and return no-store. Copied, expired and differently scoped contexts are rejected. Platform-wide lists and platform-only writes remain separate; this does not complete context adoption or query-layer/RLS isolation.

**Member operation replay.** Member update/removal/reinstatement now require Idempotency-Key and use seven-day encrypted ordinary response recovery. Keys are scoped to actor, target tenant and command; input includes member identity and the normalised window patch. The journal owns the transaction and obtains the validated tenant context before mutation or replay. Same-key retries return the original result and operation ID without another mutation fact; changed input conflicts, absent recovery data returns 410 without rerunning, and new-key unchanged requests record a noop outcome. Member PATCH requires If-Match from getMemberConfiguration; identical replay includes the original precondition.

**Member revisions.** Migration 0019 adds a positive server-controlled membership revision using the existing configuration guard. Any row change advances it; an unchanged update does not. GET /api/admin/v1/organizations/{organizationId}/members/{memberId}/configuration returns only stable membership fields and their strong ETag under member-administration scope. Member PATCH requires that If-Match value, checks it under organisation/member locks, and audits before/after configuration with the revision. Missing tags return 428, malformed tags 400, stale new commands 412. Replay includes the original precondition and runs before the stale check. Rich member profiles and time-dependent effective access intentionally have no configuration-only ETag.
