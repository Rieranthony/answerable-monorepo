# Enterprise foundation planning findings

## Implementation evidence

- Client creation/rotation audit records now carry their journal operation ID and target tenant. A deferred FK prevents orphaned links from committing. The envelope distinguishes legacy/new schema versions, and the committed SQL migration is exercised against seeded legacy data. Broad client creation/update input copies have been replaced by selected security snapshots; raw JWK configuration is no longer copied to those events.

- Client creation and rotation now have actual HTTP replay coverage: canonical duplicates, concurrent creation, original-secret recovery, deletion replay, revoked callers, expired recovery and audit-failure rollback. They require a key and replay configuration. Current authority is checked in the transaction, but the complete grant/revocation locking protocol remains unfinished.
- Source review confirms client creation still copies validated input, including JWK configuration, into its legacy audit data. F2's typed allowlisted audit payload work must replace this broad input copy; the new encrypted operation result does not itself fix that legacy audit shape.

- A separate retention login can invoke a bounded expiry-only purge but cannot read or mutate tables. Audit insertion failure restores ciphertext; repeated batches retain permanent retry keys and fresh payloads. Dedicated replay-key environment validation rejects invalid configuration without disclosing values. Production job/key provisioning remains a deployment requirement.

- Encrypted operation results are now transactionally stored separately from permanent reservations. Tests prove exact recovery across key rotation, tamper/operation binding checks, bounded replay, and no repeated effect after expiry or payload removal. Encryption failure rolls back local data/audit/journal writes. Status reads report stored availability only; deployment key setup, physical purging and mutation-route adoption remain pending.

- Operation-status routes now enforce original-actor plus tenant scope for tenant reads, or existing platform audit authority. HTTP tests exercise real human sessions and issued machine tokens. The projection excludes digests and secrets and uses retained records without live-target joins. Administrative mutation adoption and encrypted response recovery remain outstanding.

- The completed-operation journal primitive proves one local commit per scoped key across two connections. Failed mutation/journal insertion rolls back its separate data effect and audit event. Reference replay rechecks caller-supplied current authority. No administrative route adopts the helper yet; complete HTTP replay, secret recovery and revisions remain unimplemented.

- The runtime-role integration tests use a real separate login: permitted token issuance succeeds while retained-evidence mutation and owner-role switching fail. Production startup checks protected permissions before bootstrap/listening. Migrations use a separate DATABASE_MIGRATION_URL. This is application-credential protection, not tenant RLS or protection against database owners.

- A regression reproduced lost person-history retrieval after membership deletion. Migration 0008 captures durable audit subjects at insertion and preserves event tenant UUIDs after erasure. History reads no longer depend on current membership joins. Legacy derivation is explicit and cannot recover missing user links or previously nulled tenant IDs. A subject-write failure test verifies atomic rollback with its event.

- Bootstrap formerly adopted existing names and could choose another organisation after a configuration slug change. Three tests reproduced this. Immutable system bindings now drive bootstrap, platform authority, root lockout and summaries; real HTTP tests prove a tenant taking the old platform slug gains no platform authority. Existing deployments require explicit reviewed UUID import, not name-derived backfill.

- Migration 0006 reserves client/resource public identifiers and immutable instances through an atomic AFTER INSERT trigger and unique constraints. Deletion does not release them; failed transactions do. The initial reuse regression failed before the migration. Historical identifiers already erased cannot be inferred from current rows and remain a cutover inventory requirement.

- Direct SQL regressions reproduced mutable client/resource identities, decreasing client versions and credential writes without version advancement. Migration 0005 now guards them in PostgreSQL. The mutable ownership helper and application version increments were deleted. Identifier reuse after deletion remains separate pending work; an UPDATE trigger does not solve retirement reservations.

- The installed provider extension receives the authenticated client and grant context. `getOAuthProviderApi` exposes authentication separately from issuance. Keeping authentication outside the issuance transaction preserves consumed private-key assertion IDs even when policy denies; integration tests demonstrate this ordering.
- Resource custom claims are merged after extension claims by the installed provider. The provider reserves RFC claims but not Answerable's four identity claims. A database CHECK now excludes those keys; this avoids another per-request resource read and its possible snapshot race.
- The current admin verifier requires immutable instance/tenant/version claims. Raw ownership mutation and recreation no longer give an old token another client's authority. This does not make ownership itself immutable or reserve retired identifiers; those remain F1 work.

- Prior review reproduced machine JWT authority transfer/client-ID revival, loss of person audit history, no machine issuance audit and non-idempotent secret rotation. Existing suite: 1,144 tests passed; no suite rerun in this planning task.
- Current tenancy has global users, tenant memberships, tenant groups and entitlements with composite tenant foreign keys. OAuth clients have nullable organisation ownership; resources are global.
- Tenant entitlement mutations are presently platform-only. Opening org:write without a platform ceiling would permit self-escalation.
- Global user deletion differs from tenant membership removal. Tenant offboarding must preserve access and identity belonging to other tenants.
- Provider-bound login must not automatically recreate a removed membership on the next valid upstream login; inspect admission policy before defining offboarding.
- Existing plans retain Bun/Hono/Better Auth/Postgres, prohibit email identity linking, and defer external provisioning outbox until a consumer exists.
- Proposed direction: immutable ownership and identifiers; explicit tenant request context; approved catalog ceiling plus tenant assignments; positive paired grants; transactional operation journal; immutable audit facts with restricted identity evidence; no general workflow engine.
- Installed SSO assignOrganization checks for an existing member, then creates one when absent; removal currently deletes the member. Plan a revoked membership state and test login-after-offboarding. This is a source-derived risk, not a new executed reproduction.
- Provider customAccessTokenClaims exposes user/referenceId/scopes/resources/metadata, not an authenticated client or transaction argument directly. Require a bounded integration proof for verified context and atomic success-audit/token grant; never use client metadata as authority.
- Local PostgreSQL is version 16. Shared schema remains appropriate; RLS has owner/bypass caveats and needs explicit transaction context. Prefer scoped repository boundaries everywhere, targeted defence-in-depth where provider access can be proven.
- Additional source-confirmed tenancy defect: listMemberSessions resolves userId then lists all global sessions; revokeMemberSessions calls revokeAll for that user, including every user's token row. Organisation disable similarly revokes globally by member user IDs. Tenant revocation must be redesigned before multi-tenant self-service; do not expose global session metadata/actions to tenant admins.

- Client PATCH now has journal recovery and database revisions (0014). Client GET locks the parent while reading sorted resource identifiers; link changes also advance the revision. New stale commands fail 412 while committed retries recover first. No-op patches skip UPDATE and keep timestamps/revisions while recording operation-linked unchanged evidence. Coverage: raw SQL revision guard, concurrent edits, precondition errors, link/cascade changes and seven-day ordinary recovery. Other entity revisions and all-writer grant/revocation ordering remain unfinished.

- Every client administration mutation now requires Idempotency-Key. Creation/rotation recover secrets for 24 hours; PATCH and lifecycle/owner/link/erase commands recover for seven days. Same-key historical replay does not reverse subsequent state. New enable/disable and link/unlink desired-state noops succeed and audit the unchanged state. Erasure/unlink retain bodyless 204 on replay after client deletion. Complete removal manifests and all other route families remain unfinished.

- Resource create/patch/enable/disable/erase now use the journal with required keys and seven-day recovery. Migration 0015 adds configuration revisions and links now advance both endpoint revisions, including client deletion. Resource GET uses a shared lock and sorted links; PATCH rejects stale writes while recovering committed retries first. PolicyVersion and the common issuance/revocation protocol remain unfinished and are not replaced by configuration revisions.

- Real SSO reproduced re-enrolment after physical member removal. Migration 0016 retains active/revoked membership state and immutable IDs; shared effective checks deny revoked rows. Removal deletes tenant-local direct/group assignments with returned-row evidence, and explicit reinstatement restores neither. Exact/imported SSO resolution and email diagnosis reject revoked membership. Tests compare another membership of the same person. This is admission/effective-access progress, not proof of completed tenant grant/session isolation or command replay.
